# 13.1.1 Data: Load, Validate and Snapshot the Portfolio

GridCap's planning team wants one tool in place of the dozens of scripts the course has written: a
small **CIPT** (Capital Investment Planning Tool) that takes the planning export, builds the
multi-period model, values every project, explains its answers, proves it repeats itself, and
answers over HTTP. This module builds it, on GridCap medium (400 projects over the ten years 2027
to 2036), one milestone per lesson. Every milestone assembles code you already wrote in an earlier
module, so each lesson names the lesson that taught each part and spends its words on how the
parts fit.

The first milestone is the one every later one stands on: read the export, refuse it if it is
wrong, and give the accepted inputs a name that never changes. GridCap is a fictional utility; its
data is generated by the course, and no number in it describes a real company.

It is the shape a planning database's export has, and like any export it can be wrong in ways the
model would never notice.

## Read Every Cell and Keep Every Problem

`gridcap.load_csv` trusts its files: a cost typed `1,200` stops it with a `ValueError` at the
first bad row, and a misspelt region goes straight into the model. The milestone's reader checks
each cell as it converts it and records a **finding** (a rule, a severity, a subject and a detail)
instead of raising, the pattern of lesson 1.3.2's row validator:

```python
    def whole(self, row: dict, column: str, low: int = 0) -> int:
        text = row.get(column, "")
        try:
            value = int(text)
        except ValueError:
            self.found.append(Finding("not-a-whole-number", "error", self.subject, f"{column} = {text!r}"))
            return low
```

Every column gets the check its meaning calls for, read off the model's parameters as lesson
12.2.1 reads a schema: costs and crew-months are whole numbers (money is whole $k), programs and
regions come from a known list, a project's window must fit the horizon with all its years of work
(lesson 6.4.1), every start year in the window needs an NPV, and every parent and asset id must name
a row that exists. Only when no cell has an error does the reader build a `Portfolio`.

`planted_defects.py` writes GridCap medium's export and plants six mistakes an export really makes,
one at a time:

```text
P010 cost typed with a comma         -> not-a-whole-number      P010           cost = '1,200'
P020 region misspelt                 -> unknown-code            P020           region = 'Vally'
P030 window reversed                 -> empty-window            P030           starts 2036-2034 with 3 year(s) of work in 2027-2036
P040 parent retired                  -> unknown-parent          P040           parent = 'P999'
P050 and P051 each other's parent    -> parent-cycle            P050 -> P051 -> P050 a project cannot be its own ancestor
2029 budget typed 391                -> must-spend-over-budget  2029           must-do work spends at least $880k; the budget is $391k
```

Each defect is refused with a sentence a planner can act on: which row, which column, what it holds.
The first four are cell problems. The last two pass every cell check, because every cell in them
is a valid value on its own; they need the next stage.

## Rules Across Projects Run Only on Clean Cells

A parent cycle is two valid parent ids that point at each other. A budget of 391 is a valid whole
number. Only a rule that looks at several rows at once sees the problem, and lesson 12.2.2 calls
those rules the **quality gate**. The milestone's gate has four: a project that is its own ancestor,
a child whose parent cannot start early enough for any of its starts (an error for a must-do,
a warning otherwise), two must-dos in one alternative group, and a year whose budget is below what
must-do work has to spend in it whatever start years it gets:

```python
def must_spend_over_budget(pf: Portfolio) -> list[Finding]:
    """Each year: the least that must-do work must spend there, against the year's budget."""
    found = []
    for y in pf.years:
        least = sum(min(p.spend(t).get(y, 0) for t in p.starts()) for p in pf.projects if p.must_do)
        if least > pf.budget[y]:
```

The `min` over start years is what makes the rule **sound**: it never refuses a portfolio that has a
plan, because no plan can spend less than that least amount (lesson 9.1.2). P097 is must-do and can
start only in 2029, where it spends $880k, so a 2029 budget of $391k proves there is no plan.

The gate runs on a `Portfolio`, so it runs only after the cells are clean:

```python
def snapshot(folder: str | Path) -> tuple[Portfolio, str, list[Finding]]:
    """Read, validate and hash an export: (portfolio, digest, warnings), or raise Rejected."""
    pf, found = read_export(folder)
    if pf is None:
        raise Rejected(found)
    found += gate(pf)
    if blocked(found):
        raise Rejected(found)
    return pf, digest(pf), found
```

That ordering has a visible cost. With all six defects planted at once, the export is refused with
the four cell errors only:

```text
all six planted at once: refused with 4 errors
   not-a-whole-number      P010           cost = '1,200'
   unknown-code            P020           region = 'Vally'
   empty-window            P030           starts 2036-2034 with 3 year(s) of work in 2027-2036
   unknown-parent          P040           parent = 'P999'
```

The cycle and the budget typo are found on the next attempt, after the four are fixed. That is the
right trade: a cross-project rule on unclean cells would follow a parent id that names no project,
or add a cost it could not read, and report nonsense with an error's authority. So the reader
reports every cell problem in one pass, and the gate reports every cross-project problem in one
pass, and neither guesses.

## The Snapshot Is Named by the Hash of Its Canonical Content

An accepted export becomes a **snapshot**: the validated inputs, frozen and named by their content
hash, so that every later run, manifest and result can say exactly which inputs it used (lessons
10.2.4 and 12.2.3). The name is the SHA-256 of the **canonical form**, one chosen way to write the
validated content: projects and assets sorted by id, every key sorted, every float fixed to six
decimals, no spaces.

```python
def canonical(pf: Portfolio) -> bytes:
    """Validated content, one way: records sorted by id, keys sorted, floats fixed, no spaces."""
    tree = pf.to_dict()
    tree["projects"].sort(key=lambda p: p["project_id"])
    tree["assets"].sort(key=lambda a: a["asset_id"])
```

`snapshot_medium.py` puts the name to the test. It accepts GridCap medium, then exports the same
content three ways and one changed way, and hashes the first export in two fresh processes with
different hash salts:

```text
GridCap medium: 400 projects, 382 assets, 10 years, 39 must-do
accepted with 0 warning(s); digest df4edafe8608
```

```text
export                             digest
as written                         df4edafe8608
every CSV in reverse row order     df4edafe8608
discount rate 0.0700000001         df4edafe8608
P101 first-year cost $10k higher   2d173fe29605
as written, PYTHONHASHSEED=1       df4edafe8608
as written, PYTHONHASHSEED=2       df4edafe8608
```

Row order and a float's last digits do not change the content, so they do not change the digest;
one cost $10k higher does. The digest is also the one the `gridcap` package pins for GridCap medium
(`Portfolio.content_hash()`, `df4edafe8608…`), because that hash sorts keys and writes the
generator's projects in id order too. The module's tests pin the full 64 hex digits, so a change to
the reader or the canonical form that shifted a single byte would fail a test instead of quietly
renaming every snapshot.

Medium has 400 projects and 382 assets: 18 pairs of alternatives (repair or replace) share one asset
each.

The snapshot store keeps each snapshot once, under its digest, and checks the digest again on every
read (lesson 12.2.3):

```text
store: put twice -> same key True, files 1
read back equals the original: True
after an edit in place: refused, df4edafe8608.json no longer hashes to its name
```

From here on, every milestone receives a `Portfolio` that passed both stages, and a digest to quote.

## Summary

- **CIPT Lite is one program built in six milestones.** Data, model, value, diagnostics, trust,
  service: each a module of `src/`, each importing only the ones before it, each assembled from
  lessons you have done.
- **Read every cell and keep every problem.** Convert each cell with a check that records a finding
  instead of raising; build the portfolio only when no cell has an error. Six planted defects, six
  sentences a planner can act on.
- **Rules across projects run only on clean cells.** Cycles, unreachable parents, mandated
  alternatives and must-do spend above a year's budget need several rows at once; each rule is
  sound, and none runs on values that could not be read.
- **The snapshot is named by the hash of its canonical content.** Sorted records and keys, fixed
  floats, no spaces: the same content gives `df4edafe8608` in any row order and any process, and a
  $10k change gives another name.

## Reference

| Stage | Function | Refuses |
| --- | --- | --- |
| read | `read_export(folder)` | `not-a-whole-number`, `below-minimum`, `out-of-range`, `unknown-code`, `duplicate-id`, `empty-window`, `unknown-asset`, `unknown-parent`, `npv-missing`, `missing-budget` |

| name | `canonical`, `digest` | nothing: equal content, equal digest |
| store | `SnapshotStore.put`, `.get` | a file that no longer hashes to its name |

| Term | Meaning |
| --- | --- |
| finding | one problem: rule, severity (error or warning), subject, detail |
| sound check | a check that never refuses inputs that have a plan |
| snapshot | validated inputs, frozen and named by their content hash |
| canonical form | one chosen way to write a value, so equal values give equal bytes |

## Challenges

1. The gate's budget rule counts only must-do projects. A planner adds a `fix_start` override that
   requires P086 to start in 2027 (lesson 6.5.6). Which stage should know about overrides, and what
   would the rule then add up?
2. Two exports differ only in a project's `name`. Should their digests differ? Think of a report
   that quotes project names next to the digest.
3. The reader refuses a whole export for one bad cell. Write down one case where a planner would
   rather drop the bad project and solve the rest, and what the result must then say.

## Design Note: Refuse Loudly, Never Repair Quietly

The reader could have "fixed" `1,200` to 1200 and `Vally` to Valley. It does not, because a reader
that guesses turns a data problem into a plan problem that nobody can trace: the plan would be
built on inputs no one exported. Refusing with a finding sends the problem back to the system that
made it, and the snapshot that is finally accepted is exactly what the export said.
