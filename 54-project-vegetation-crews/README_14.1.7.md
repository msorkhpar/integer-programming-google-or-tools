# 14.1.7 The Same Plan Every Run: Determinism and Regression Tests

GridCap's vegetation planner now runs the planner every Monday on the medium season (sixty circuits,
six crews) and sends the plan to the crews. Then the program manager asked a question nobody could
answer:

> I ran the plan twice this morning on the same data, to check something, and got two different plans,
> with different risk totals. Which one did we send the crews? When the regulator asks why C27 waited
> until September, I need to rerun the plan and get the *same* plan, and I need to know that next
> month's code change did not quietly change it.

Two requirements in one: **determinism**, the same input gives the same plan every run, and
**regression tests**, a change that alters the plan fails a test until someone accepts it on purpose.
(GridCap and its seasons are fictional, generated by the project's seeded generator.) This lesson
takes the project from `steps/06` to `steps/07`.

## Four Racing Workers and a Wall Clock Give a Different Plan Each Run

`steps/06` solves with `max_time_in_seconds = 10` and `num_workers = 4`. On the small season the
search proves optimality before the limit (the lesson *Weather and access windows: calendars and optional work*). The medium season
is too large to prove in ten seconds (the lesson *Risk grows while a circuit waits: the objective changes* showed why the proof got hard), so the search
stops when the clock says so, and four workers race to improve the plan in parallel, each at its own
pace. `repeat_runs.py` plans the medium season three times with `steps/06`, each in a fresh process.
One run on the author's machine printed this (the risk totals and plan fingerprints differ from
run to run, so yours will too):

<!-- unverified -->
```text
steps/06, medium season, 3 runs:
  FEASIBLE risk carried $13,897k  plan 7fb2b92f78b8
  FEASIBLE risk carried $14,157k  plan cf2377415b4f
  FEASIBLE risk carried $14,196k  plan c50419981d88
```

Every run prints its verdict on whether the plans matched, and that line is stable:

```text
same plan every run: no
```

Three runs, three plans, and in that run a $299k spread in risk. None is wrong: each keeps every rule, and none is
proven optimal. Lesson 4.6.3 named the two causes, and both are here: a **wall-clock limit** stops
the search at a different point each run, because the same work takes a different number of seconds
on a busy machine; and **parallel workers race**, so which worker's plan is best at the moment of the
stop depends on thread timing. The code has no bug to fix; its settings ask for this.

## Determinism Is a Setting, and a Record Proves It

The design decision has two parts: how to make the search repeat, and how to know that it did.

| Option | What it gives | Why not, or why |
| --- | --- | --- |
| One worker, a seed, a limit on deterministic time | repeats on one OR-Tools version (lesson 4.6.3) | gives up parallel search: one search path at a time |
| Four workers with `interleave_search`, a seed, a limit on deterministic time | repeats on one OR-Tools version; lesson 4.6.3 quotes the parameters proto, which calls the mode deterministic whatever the number of workers and marks it experimental, and lesson 10.2.5's harness passed with it | chosen: parallel search that takes turns in batches instead of racing |
| Keep the race, and add a tie-break objective so that equal plans are told apart (lesson 10.2.3) | one plan among *proven* optima | does not help a search stopped before proving anything: the stop point itself moves |

**Deterministic time** is CP-SAT's own count of the work it has done, computed from what the search
did rather than read from a clock (lesson 4.6.3). A limit on it stops the same search at the same
point however busy the machine is. Four workers is what `steps/06` used too, so the only change in
parallelism is how the workers share the work.

Knowing that the plan repeats needs a **record**: everything that identifies the plan and how it was
made, as canonical text, so that two runs gave the same plan if and only if their records are equal
byte for byte (lessons 10.2.4 and 10.2.5). The record names the input by a hash of its canonical JSON
(the lesson *Versioned snapshots and content hashes* in section 12), and the solver by its version and settings. When two records differ, the fields
that differ say why: other data, another OR-Tools, other settings, or (with all three equal) a search
that did not repeat.

A **golden record** is a reviewed record checked into the tests (the lesson *Golden datasets and regression tests* in section 12). A test that compares
today's record with it catches any change to the plan, and the diff shows the change.

## The Model Does Not Change

No set, parameter, variable, objective or row changes in this lesson; the formulation is the lesson
*Planner overrides and why a plan failed*'s, exactly. What changes is how it is solved: `num_workers = 4`, `interleave_search = true`,
`random_seed = 7`, `max_deterministic_time = 10` in place of a 10-second wall-clock limit. That is
worth saying plainly, because "the plan changed" is so often blamed on the model. Here the model was
never the cause.

## The Change, File by File

**`vegcrew/planner.py`.** Two constants and four lines become one dict and a loop:

<!-- snapshot: steps/06/vegcrew/planner.py -->
```python
TIME_LIMIT = 10.0                                   # seconds
WORKERS = 4                                         # parallel search workers
```

<!-- snapshot: steps/07/vegcrew/planner.py -->
```python
# The search repeats exactly, run after run, on any machine, for one OR-Tools version: four workers
# that take turns in batches instead of racing, a fixed seed, and a limit on work done, not on seconds.
SETTINGS = {"num_workers": 4, "interleave_search": True, "random_seed": 7, "max_deterministic_time": 10.0}
```

<!-- snapshot: steps/07/vegcrew/planner.py -->
```python
    solver = cp_model.CpSolver()
    for name, value in SETTINGS.items():
        setattr(solver.parameters, name, value)
```

Settings as one dict is the change that matters most: the record can store exactly what the solve
used, by reading the same object. Two separate constants and four `solver.parameters` lines would let
the record and the solve disagree after the next edit.

**`vegcrew/record.py`.** A stub in `steps/06`; now the record. The fingerprint hashes the season and
the overrides as canonical JSON (sorted keys, no spaces), so equal inputs give equal hashes whatever
order their keys came in:

<!-- snapshot: steps/07/vegcrew/record.py -->
```python
def fingerprint(raw: dict, overrides: tuple[Override, ...] = ()) -> str:
    """SHA-256 of the season and the overrides as canonical JSON: equal inputs, equal fingerprints."""
    given = {"season": raw, "overrides": [vars(o) for o in overrides]}
    return hashlib.sha256(canonical(given).encode()).hexdigest()
```

`plan_record(raw, plan, overrides)` builds the record itself, and the page leaves its code to the
practice. It returns a dictionary of the eight things that decide whether two runs agree, under these
keys: `input_sha256`, the fingerprint of the input; `ortools`, the version string
`ortools.__version__`; `settings`, the `SETTINGS` dictionary the solve used; `status`,
`risk_carried` and `cost`, from the plan; `trims`, one string per trim, `<cid> on <crew> weeks
<first>-<last>` with both weeks included (so the last is `end - 1`), sorted by circuit id; and
`explanation`, the plan's explanation as a list. The golden record `step07.py` prints below shows
every key filled in. For the version and the settings, `record.py` now imports `ortools`, and
`SETTINGS` beside `Plan` from the planner.

Each trim is one string, so a changed trim is a one-line diff in review, and trims are sorted by
circuit, never in the order a dict happened to hold them. The record keeps no timestamp and no wall
time: those differ every run by nature, and a record that holds them can never compare equal. `dumps`
writes the record with sorted keys, one level of indent and a final newline: the bytes that are stored
and compared.

**`vegcrew/__main__.py`.** A `--record` flag prints the record instead of the report, so a fresh
process can produce it, and so can a scheduled job.

**`main.py`.** From `steps/03` to `steps/06` it set `planner.WORKERS = 1` before planning, so that the
report Run prints would repeat. That line goes: `WORKERS` is gone, and the planner's own settings now
repeat the search. A new section, `show_record`, prints the tiny season's fingerprint and whether two
plans of it, made one after the other in the same process, gave records equal byte for byte.

**`tests/golden/tiny.json` and `tests/golden/small.json`.** The two reviewed records, written by

## The Medium Season Now Repeats, Byte for Byte

`repeat_runs.py` then plans the medium season twice with `steps/07`, each time in a fresh process
with `python -m vegcrew medium --record`, and hashes the two records:

```text
steps/07, medium season, 2 runs:
  FEASIBLE risk carried $14,571k  record sha256 74f5661a1999
  FEASIBLE risk carried $14,571k  record sha256 74f5661a1999
  records identical byte for byte: yes
```

Same plan, same record, same bytes. The plan is still FEASIBLE, not proven optimal: determinism
makes the answer repeatable, not better. And at this limit the repeatable plan is worse than the
racing runs above, $14,571k against $13,897k to $14,196k in that run. That is a trade to state, not
hide: a fixed limit of 10 units of work buys a plan anyone can reproduce; more work buys a better one,
and stays reproducible as long as the limit is part of the record. The manager can choose the limit;
what the planner no longer does is choose a plan at random.

## Five Tests: Fingerprint, Record, Two Goldens, Two Fresh Processes

`steps/07` adds `tests/test_records.py`. The determinism test runs the entry point in two fresh
processes and compares the bytes with each other and with the golden file, following the pattern of the lesson
*Determinism tests and back-testing against history* in section 12:

<!-- snapshot: steps/07/tests/test_records.py -->
```python
def test_two_fresh_processes_print_the_golden_record_byte_for_byte():
    runs = [subprocess.run([sys.executable, "-m", "vegcrew", "tiny", "--record"], cwd=ROOT,
                           capture_output=True, text=True) for _ in range(2)]
    assert [r.returncode for r in runs] == [0, 0]
    assert runs[0].stdout == runs[1].stdout == (GOLDEN / "tiny.json").read_text()
```

Fresh processes matter: two solves inside one process share memory, hash seeds and imported state,
and can agree for reasons a scheduled job would not share. The golden tests compare parsed records, so
a failure shows which field changed:

<!-- snapshot: steps/07/tests/test_records.py -->
```python
def test_the_small_plan_matches_its_golden_record():
    assert json.loads(record_of("small")) == json.loads((GOLDEN / "small.json").read_text())
```

The other two check that the fingerprint changes with the budget and with an override but not with a
copy of the same data, and that the record names its input, a seed of 7, at most 4 workers and a
three-part OR-Tools version. The module's docstring says how to accept a new plan: write the golden
file again and review its diff. `step07.py`:


Against `steps/06`, the stub record is empty, and `--record` is an unknown flag, so both fresh
processes exit with argparse's code 2.

Notice what the golden test is and is not. It fails on *any* change to the small plan, including a
better one from a smarter model; it does not say the plan keeps the rules (the rule tests of the lessons
*A trim takes weeks on one crew: from MILP to CP-SAT intervals* to *Planner overrides and why a plan failed* do that). The lesson *Golden datasets and regression tests* in section 12 calls this the difference between a regression and a rule
error, and both kinds of test are needed. The golden test also pins the OR-Tools version: upgrading
OR-Tools fails it on purpose, and the reviewed diff decides whether the new plan is accepted.

## Summary

- **Four racing workers and a wall clock give a different plan each run.** On the medium season,
  three runs gave three plans; nothing in the code was wrong.
- **Determinism is a setting, and a record proves it.** Interleaved workers, a seed and a limit on
  deterministic time, in one `SETTINGS` dict the record also reads.
- **The medium season now repeats byte for byte,** at a stated price: the repeatable plan at this
  limit carries more risk than the racing runs found.
- **Five tests,** including two golden records and a determinism test in fresh processes. The model
  did not change.

## Design Note: A Plan Nobody Can Reproduce Is Not an Answer

The racing runs found better plans than the repeatable one. Why not keep the race and store whatever
plan it returns? Because the plan is not the only thing the team must defend; the planner is. "We ran
it and got this" is an answer once. "Anyone can run it on that data with that version and get this,
byte for byte" is an answer to the regulator, to the next engineer, and to a test suite that must tell
a regression from noise. If a better plan matters more, give the search more work, and write the new
limit into the record.
