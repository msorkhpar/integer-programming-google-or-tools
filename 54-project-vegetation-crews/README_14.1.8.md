# 14.1.8 From Script to Service, and What the Code Became

The planner is trusted now: it keeps the calendars, takes overrides, explains a failure and gives the
same plan every run (the lessons *Weather and access windows: calendars and optional work* to *The same plan every run: determinism and regression tests*). The last request comes from the team that builds
GridCap's work-management system:

> We don't want to run a Python script on someone's laptop. Give us an endpoint: we POST a season
> (the same JSON our inventory exports) and the planner's overrides, and get back the plan's record.
> Keep every plan you return, so we can fetch it again by its id months later, after the laptop is
> gone. Bad input should be refused with a reason, before anything runs.

(GridCap and its seasons are fictional, generated by the project's seeded generator.) This lesson
takes the project from `steps/07` to `steps/08`, and then looks back over all eight steps.

## The Script Has No Door, and Forgets Every Plan

`steps/07` is used from a shell: `python -m vegcrew small --record` plans a *generated* season and
prints a record to standard output. There is no way to hand it a season from another system, no way
to pass overrides except from Python, and no memory: a plan exists only as long as someone keeps the
terminal's output. The record of the lesson *The same plan every run: determinism and regression tests* is exactly the answer the work-management team wants;
what is missing is a way in and a place to keep it.

## A Thin HTTP Layer Validates at the Edge and Calls the Library

The design decisions, each with its alternative:

| Decision | Chosen | Alternative, and why not |
| --- | --- | --- |
| How a caller reaches the planner | a FastAPI app with `POST /plans` and `GET /plans/{id}` (the lesson *A REST API with FastAPI* in section 12) | a command-line tool fed by files: no fit for another system calling it, and still no memory |
| How long a request may take | the solve runs inside the request, in a plain `def` endpoint, which FastAPI runs on a worker thread (the lesson *A REST API with FastAPI* in section 12) | submit, poll, fetch with a job store (the lesson *Long solves: submit, poll, fetch* in section 12): needed when solves outlast a request; here the deterministic limit of the lesson *The same plan every run: determinism and regression tests* bounds the work, so not yet |
| Where input is checked | pydantic models on the request, then `check_overrides` (the lesson *Planner overrides and why a plan failed*) | inside the model: a bad season would fail deep in `build` with a `KeyError` |
| Where plans are kept | one SQLite table, one row per plan, the record as its canonical text (the lesson *Storing scenarios and results in SQLite* in section 12) | files on disk: no ids and no safe concurrent writes; a database server: more than one table needs |
| What a failed season returns | 200 with status INFEASIBLE and the explanation (the lesson *A REST API with FastAPI* in section 12) | an HTTP error: but "no plan keeps these rules" is an answer, not a fault |

The service adds nothing to the planner's logic: every endpoint is a few lines that check input, call
`make_plan` and `plan_record`, and store or fetch. That keeps everything the earlier lessons tested
in the library, where the tests already are.

The model does not change in this lesson; its formulation is the lesson *Planner overrides and why a plan failed*'s.

## The Change, File by File

**`vegcrew/api.py`.** In `steps/07` a stub:

After, it imports FastAPI and pydantic, and what it calls from four modules of the library:

<!-- snapshot: steps/08/vegcrew/api.py -->
```python
from typing import Literal

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

from vegcrew.data import Override, season_from_dict
from vegcrew.planner import check_overrides, make_plan
from vegcrew.record import plan_record
from vegcrew.store import Store
```

Then the request's shape as pydantic models. Each field carries its bound, so FastAPI refuses a
negative budget or zero crews with a 422 and the field's path before any code of ours runs:

<!-- snapshot: steps/08/vegcrew/api.py -->
```python
class SeasonIn(BaseModel):
    name: str = "season"
    budget: int = Field(ge=0)
    crews: int = Field(ge=1, le=50)
    months: int = Field(ge=1, le=12)
    crew_off: dict[str, list[Span]] = {}
    circuits: list[CircuitIn] = Field(min_length=1)


class OverrideIn(BaseModel):
    kind: Literal["pin", "skip", "force"]
    cid: str
    crew: str | None = None
    start: int | None = None
    reason: str = ""
```

`CircuitIn` does the same for a circuit's columns, with `windows` and `must` defaulting as the loader
of the lesson *Weather and access windows: calendars and optional work* does. A `Span` is a pair of weeks, first and last, both included, and a
request is a season with a list of overrides, empty unless given:

<!-- snapshot: steps/08/vegcrew/api.py -->
```python
Span = tuple[int, int]


class CircuitIn(BaseModel):
    id: str
    region: str
    miles: int = Field(gt=0)
    cost: int = Field(ge=0)
    risk: int = Field(ge=0)
    weeks: int = Field(ge=1)
    growth: float = Field(ge=0)
    windows: list[Span] = []
    must: bool = False
```

<!-- snapshot: steps/08/vegcrew/api.py -->
```python
class PlanRequest(BaseModel):
    season: SeasonIn
    overrides: list[OverrideIn] = []
```

A circuit's miles must be positive and its weeks at least 1; its cost, risk and growth may be 0 but
not negative. Then the two endpoints, inside a factory that takes the database's path. It opens the
store first:

<!-- snapshot: steps/08/vegcrew/api.py -->
```python
def create_app(db: str = ":memory:") -> FastAPI:
    app = FastAPI(title="Vegetation crew planner")
    store = Store(db)
```

The first endpoint, `post_plan`, is where the service meets the planner, and the page leaves its body
to the practice. It is `@app.post("/plans")` on a plain `def post_plan(request: PlanRequest) -> dict`,
and it does four things in order, with no planning logic of its own:

- take the validated season as a plain dictionary with `request.season.model_dump()`, and read it
  into a `Season` with the loader, `season_from_dict`;
- turn each validated override into the library's `Override`, its fields passed as keywords;
- run `check_overrides`, and if it finds problems, raise FastAPI's `HTTPException` with status code
  422 and the list of problems as its `detail`, before any model is built;
- otherwise plan with `make_plan`, make the record with `plan_record`, from the dumped season (not
  the `Season`), the plan and the overrides, save it in the store, and return
  `{"id": <the id save returns>, "record": <the record>}`. An infeasible season takes this path too.

The second endpoint reads a plan back:

<!-- snapshot: steps/08/vegcrew/api.py -->
```python
    @app.get("/plans/{plan_id}")
    def get_plan(plan_id: int) -> dict:
        record = store.get(plan_id)
        if record is None:
            raise HTTPException(status_code=404, detail=f"no plan {plan_id}")
        return {"id": plan_id, "record": record}

    return app
```

Three details. The record's fingerprint is taken from `model_dump()`, the validated season with its
defaults filled in, so two requests that mean the same season get the same fingerprint even if one
left out an empty `windows`. A factory, `create_app(db)`, instead of a module-level `app`, lets each
test have its own database and lets a test open a second app on the same file. And the endpoint is
`def`: a CP-SAT solve blocks, and an `async def` endpoint would block the server's event loop for every
caller (the lesson *A REST API with FastAPI* in section 12).

**`vegcrew/store.py`, new.** One table, `plans(id, input_sha256, record)`, with the record stored as
`dumps(record)`, the same canonical text the golden files hold:

<!-- snapshot: steps/08/vegcrew/store.py -->
```python
    def __init__(self, path: str = ":memory:"):
        # FastAPI runs plain `def` endpoints on worker threads, so one connection is shared under a lock.
        self.db = sqlite3.connect(path, check_same_thread=False)
        self.lock = threading.Lock()
        with self.lock, self.db:
            self.db.execute("CREATE TABLE IF NOT EXISTS plans ("
                            "id INTEGER PRIMARY KEY, input_sha256 TEXT NOT NULL, record TEXT NOT NULL)")

    def save(self, record: dict) -> int:
        with self.lock, self.db:
            cursor = self.db.execute("INSERT INTO plans (input_sha256, record) VALUES (?, ?)",
                                     (record["input_sha256"], dumps(record)))
            return cursor.lastrowid
```

`get` reads one row back and parses the stored text, or answers `None` for an id with no row:

<!-- snapshot: steps/08/vegcrew/store.py -->
```python
    def get(self, plan_id: int) -> dict | None:
        with self.lock:
            row = self.db.execute("SELECT record FROM plans WHERE id = ?", (plan_id,)).fetchone()
        return json.loads(row[0]) if row else None
```

`with self.db` commits the insert, or rolls it back on an error. The values go in as `?` parameters,
never formatted into the SQL. The `input_sha256` column lets a later query find every plan made from
one season without parsing records.

No other file changes. `make_plan`, `plan_record` and the model are called as they are.

## The Service Answers, Refuses and Remembers

`service_demo.py` calls the app in-process through FastAPI's test client. The runner has no network,
so no server is started; the test client sends real HTTP requests to the app object.

```text
POST /plans -> 200, id 1, OPTIMAL, risk carried $568k
  trims: C01 on K1 weeks 12-14; C02 on K1 weeks 15-16; C03 on K1 weeks 0-2; C06 on K1 weeks 3-4
GET /plans/1 from a new app on the same file -> 200, same body: True
GET /plans/7 -> 404 {'detail': 'no plan 7'}
crews 0 -> 422: ['body', 'season', 'crews'] Input should be greater than or equal to 1
pin on K3 -> 422: {"detail": ["override 1: no crew K3"]}
every circuit a must -> 200, INFEASIBLE:
  - C04 is overdue and must be trimmed this season
  - C06 is overdue and must be trimmed this season
  - the season's budget is $170k
```

The first request skips C05 on the tiny season ("flooded"); the plan works around it. The second app,
opened on the same SQLite file, returns the stored plan unchanged: the plan outlives the process that
made it. Then the three kinds of refusal and failure, each where it belongs: pydantic's 422 for a
malformed season, `check_overrides`' 422 for an override naming a crew that does not exist, and a 200
with an explanation for a season whose rules clash.

## Six Tests Through the HTTP Layer

`steps/08` adds `tests/test_api.py`, every test a request through the test client. The first checks
that the service and the library agree, the property that keeps the service thin:

<!-- snapshot: steps/08/tests/test_api.py -->
```python
def test_posting_a_season_returns_the_record_the_library_gives():
    raw = scenario("tiny")
    reply = client().post("/plans", json=tiny_request())
    assert reply.status_code == 200
    expected = plan_record(raw, make_plan(season_from_dict(raw)))
    assert reply.json()["record"]["trims"] == expected["trims"]
    assert reply.json()["record"]["risk_carried"] == expected["risk_carried"]
```

It compares trims and risk, not the whole record: the fingerprints differ on purpose (the service
hashes the validated season, the library call the raw one). The others: a stored plan comes back by
its id and an unknown id is a 404 with its message; a negative budget is a 422 naming the field; an
override naming no circuit is a 422 listing the problem; an all-must season is a 200 with an
explanation; and a plan survives a new app on the same SQLite file (pytest's `tmp_path` gives the
file). Importing the test client prints a deprecation notice from Starlette 1.10 about httpx, so the
test module imports it inside `warnings.catch_warnings()`.

- **The model is small.** The rules live in one function, `build`, which reached 42 lines by the lesson
  *Planner overrides and why a plan failed* and stayed there: determinism and the service did not touch it.
  The planner file was rewritten once (the lesson *A trim takes weeks on one crew: from MILP to CP-SAT intervals*, MILP to CP-SAT) and *shrank* that time; it was
  split once (the lesson *Planner overrides and why a plan failed*) when it had four jobs.
- **The data grew as much as the model.** `data.py` and `generate.py` went from 48 to 108 lines; a
  rule usually costs a line in the model and several in getting its data in with the right defaults
  (the lesson *Weather and access windows: calendars and optional work*).
- **Steps 06 to 08 added files, not length.** `explain.py`, `record.py`, `api.py` and `store.py` each
  have one reason to change. The longest function is 42 lines, and the functions grew from 7 to 29.
- **The tests grew with the code from the first step,** and ended at 289 lines and 40 tests against 446
  lines of package, about two lines of test for every three of code. Their kinds widened step by step:
  hand-made seasons with their arithmetic in comments (every step), a brute force (step 1, rewritten
  in step 4), the rule written twice (step 4), exact explanation wording (step 6), golden records and
  fresh processes (step 7), HTTP (step 8).

And by what changed hands. Two requirements changed the model's *kind*: crews and weeks (a packing
problem became a scheduling problem, and the solver changed) and growing risk (the objective began to
depend on order, and the proof stopped finishing on the small season). Those two drove everything
after: the time limit made runs differ (the lesson *The same plan every run: determinism and regression tests*), and the harder proof moved tests to seasons
small enough to prove. Every other requirement was "one more rule" or "one more layer", and cost a few
lines where it belonged.

## Summary

- **The script had no door and forgot every plan.** A service needs a way in, input checking at the
  edge, and storage.
- **A thin HTTP layer validates at the edge and calls the library.** Pydantic models, `check_overrides`,
  `make_plan`, `plan_record`, and a one-table SQLite store, in 76 new lines; the planner did not change.
- **The service answers, refuses and remembers:** 200 with a record, 422 with a reason, 200 with an
  explanation, and a plan fetched by id from a new process.
- **What the code became:** 98 lines to 446, 3 tests to 40; one 42-line model function; two
  requirements that changed the model's kind, and six that each added a rule or a layer.

## Design Note: The Service Is the Last Layer, Not the First

Built in the order of these lessons, the HTTP layer came last and cost 76 lines, because everything
it needed already had a boundary: a plan type, a record, a data check, an explanation. Had the
project started as a service, each requirement would have been threaded through request handling,
and the tests would have needed a client to check a constraint. Grow the model and its tests as a
library, give its answers a stable shape, and the service is a thin translation that can be replaced
(by a job queue, or by another framework) without touching a rule.
