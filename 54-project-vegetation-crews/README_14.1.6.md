# 14.1.6 Planner Overrides and Why a Plan Failed

With calendars in place (the lesson *Weather and access windows: calendars and optional work*), GridCap's vegetation planner started using the plan every
week, and two requests followed:

> Sometimes I know something the model doesn't. A crew is already on site near C17, so start it there
> in week 0. The county closes the road to C17 until October, so leave it. A landowner complained, so
> trim C02 first. I need to tell the planner these things and have it plan *around* them.
>
> And when it can't, "INFEASIBLE" is not an answer. Last week I forced in five circuits after a storm
> and got an empty plan and that one word. Tell me *which* of my decisions clash, in my words, so I
> know what to give up.

The first request is **overrides**: a planner's decision that the plan must keep. The second is
**explanation**: when no plan keeps every rule, a short list of the rules that cannot hold together.
(GridCap and its seasons are fictional, generated by the project's seeded generator.) This lesson
takes the project from `steps/05` to `steps/06`.

## The Planner Takes No Instructions, and Its Failure Says Nothing

`steps/05` has one input, the season. A planner who wants C17 left out can only edit the season's data
(delete the circuit, or set its window to nothing), which loses the record that it was a decision,
by whom and why, and makes the next season's data wrong. And when a season is infeasible, `make_plan`
returns `Plan("INFEASIBLE")`: a true statement that tells the planner nothing. CP-SAT proved that the
rules cannot all hold, and the code threw that proof away.

## An Override Is One More Rule, and Every Rule a Planner Can Change Sits Behind a Literal

Three override kinds cover the requests: **pin** (trim this circuit, optionally on this crew and from
this week), **skip** (leave it for next season) and **force** (trim it this season, anyhow). Each is a
rule of the same shape as a must: a few rows that hold when the override is in force.

For the explanation, the design options (lessons 9.1.2, 9.1.4 and 9.1.5 compared them):

| Option | What it gives | Why not, or why |
| --- | --- | --- |
| Check the data before solving (lesson 9.1.2): sum the musts' costs, compare with the budget | instant, and the message writes itself | only for conflicts someone thought of in advance; two pins that overlap on one crew, or a pin outside a window, need the model |
| Elastic rows: add slack to every rule and minimize the slack (lesson 9.1.4) | says how far each rule is from holding | changes the objective and the model's meaning; the planner wants names, not amounts |
| One literal per changeable rule, solved as **assumptions**; CP-SAT names a set of them enough for the proof; a deletion filter makes it minimal (lessons 4.6.2 and 9.1.5) | the rules that clash, by name, from the real model | chosen: it finds any conflict the model can prove, and needs no change to the model's meaning |

An **assumption** is a literal the solver must take as true for this solve (lesson 4.6.2). Every rule a
planner can change, each must, the budget and each override, is written as rows enforced by its own
literal. A normal solve fixes all those literals to true, so the model means exactly what it meant
before. When the season is infeasible, a second solve passes the literals as assumptions, and
`sufficient_assumptions_for_infeasibility` returns those the proof used. That set is enough, but not
always the smallest (lesson 4.6.2), so a **deletion filter** tries each name in turn: drop it, and if
the rest still cannot hold, it stays dropped.

The hard facts stay hard: windows, crews' weeks off, one trim per crew at a time. They are physics,
not decisions; an explanation that says "or let K1 work two circuits at once" is not one a planner can
act on.

## The Model

The lesson *Weather and access windows: calendars and optional work*'s model, with every changeable rule behind a literal, and the overrides. In full:

**Sets.** As in the lesson *Weather and access windows: calendars and optional work*: $`C`$, $`K`$, weeks, $`M`$, windows $`W_c`$, time off $`O_k`$; and
← *this lesson* the overrides $`V`$, split into pins $`V^{\text{pin}}`$ (each with a circuit, and
optionally a crew $`k_v`$ and a first week $`f_v`$), skips $`V^{\text{skip}}`$ and forces
$`V^{\text{force}}`$; $`c_v`$ is override $`v`$'s circuit.

**Parameters.** $`\text{cost}_c`$, $`B`$, $`w_c`$, $`R_c(e)`$, $`D`$, as before.

**Variables.** $`t_c`$, $`p_{c,k}`$, $`s_{c,k} \in S_c`$, $`I_{c,k}`$, $`e_c`$, $`\rho_c`$ as before;
← *this lesson* a rule literal $`\ell_r \in \{0, 1\}`$ for every changeable rule $`r`$: one per must,
one for the budget, one per override.

**Objective.**

```math
\min \; \sum_{c \in C} \rho_c
```

**Constraints.** The rows of the lesson *Weather and access windows: calendars and optional work* (once, ends, waits, risk, crew) unchanged, and:

```math
\begin{aligned}
\ell_{\text{must},c} = 1 \;&\Rightarrow\; t_c = 1 && \forall c \in M && \text{(must}_c) \quad \leftarrow \text{now behind a literal} \\
\ell_{\text{budget}} = 1 \;&\Rightarrow\; \textstyle\sum_{c} \text{cost}_c\, t_c \le B && && \text{(budget)} \quad \leftarrow \text{now behind a literal} \\
\ell_v = 1 \;&\Rightarrow\; t_{c_v} = 0 && \forall v \in V^{\text{skip}} && \text{(override}_v) \quad \leftarrow \text{this lesson} \\
\ell_v = 1 \;&\Rightarrow\; t_{c_v} = 1 && \forall v \in V^{\text{pin}} \cup V^{\text{force}} && \text{(override}_v) \quad \leftarrow \text{this lesson} \\
\ell_v = 1 \;&\Rightarrow\; p_{c_v, k_v} = 1 && \forall v \in V^{\text{pin}} \text{ with a crew} && \text{(override}_v) \quad \leftarrow \text{this lesson} \\
\ell_v = 1 \;&\Rightarrow\; e_{c_v} = f_v + w_{c_v} && \forall v \in V^{\text{pin}} \text{ with a week} && \text{(override}_v) \quad \leftarrow \text{this lesson} \\
\ell_r &= 1 && \forall r && \text{(every rule holds)} \quad \leftarrow \text{the planning solve only}
\end{aligned}
```

The last row belongs to the planning solve. The explaining solve leaves it out and passes the
$`\ell_r`$ as assumptions instead. A pin's week is stated on the end, $`e_c = f + w_c`$, because the
end is one variable per circuit, whatever crew does the work.

## The Change, File by File

`planner.py` held the plan, the model and the solve, and now needs a fourth job, explaining. That is
one job too many for one file, so this step splits it: **`model.py`** (new) holds the model,
**`explain.py`** (new) the explanation, and `planner.py` keeps the plan and the solve.

**`vegcrew/data.py`.** `Override`, a frozen dataclass like the others, which can say itself in the
planner's words:

<!-- snapshot: steps/06/vegcrew/data.py -->
```python
@dataclass(frozen=True)
class Override:
    """A planner's decision the plan must keep: pin a trim, skip a circuit, or force one in."""
    kind: str                       # "pin", "skip" or "force"
    cid: str
    crew: str | None = None         # pin: this crew (None: any crew)
    start: int | None = None        # pin: this first week (None: any week)
    reason: str = ""

    def says(self) -> str:
        where = "".join([f" on {self.crew}" if self.crew else "", f" from week {self.start}"
                         if self.start is not None else ""])
        what = {"pin": f"trim {self.cid}{where}", "skip": f"leave {self.cid} for next season",
                "force": f"trim {self.cid} this season"}[self.kind]
        return f"{what} ({self.reason or 'no reason given'})"
```

The `reason` is carried into every message. A planner reading "override 4: trim C01 this season
(regulator letter)" knows which decision it was and why it was made.

**`vegcrew/model.py`, new.** `crew_ids`, `horizon`, `start_domain`, `TrimModel` and `build`, moved
from `planner.py`. `TrimModel` gains the rule literals and their words, and a method that makes one:

<!-- snapshot: steps/06/vegcrew/model.py -->
```python
    rules: dict[str, cp_model.IntVar] = field(default_factory=dict)                   # name -> literal
    says: dict[str, str] = field(default_factory=dict)                                # name -> words

    def rule(self, name: str, says: str) -> cp_model.IntVar:
        """A literal that switches one of the planner's rules on; the rows it guards hold only if it is 1."""
        self.rules[name] = self.model.new_bool_var(name)
        self.says[name] = says
        return self.rules[name]
```


If a pin names a crew for a circuit that has no crew options (no window fits it), the crew row is
skipped; $`t_c = 1`$ alone then cannot hold, and the explanation names the pin.

**`vegcrew/explain.py`, new.** Three small functions. `holds` asks whether a set of rules can all
hold at once, with one worker, stopping at the first plan found, since only yes or no matters:

<!-- snapshot: steps/06/vegcrew/explain.py -->
```python
def holds(tm: TrimModel, names: list[str]) -> bool:
    """Can these rules all hold at once? One worker, stopped at the first plan: only yes or no matters."""
    tm.model.clear_assumptions()
    tm.model.add_assumptions([tm.rules[n] for n in names])
    solver = cp_model.CpSolver()
    solver.parameters.num_workers = 1
    solver.parameters.stop_after_first_solution = True
    return solver.solve(tm.model) != cp_model.INFEASIBLE
```

`conflict(tm)` asks CP-SAT for its set, filters it, and returns the rules that remain in the order
they were made. It is the explanation, and the page leaves its code to the practice. Its contract is
the method of *An Override Is One More Rule, and Every Rule a Planner Can Change Sits Behind a
Literal* above, in four steps:

- solve once with every rule literal of `tm.rules` as an assumption, after clearing any assumptions
  already on the model, with one worker (assumptions need a single worker); if the status is not
  INFEASIBLE, every rule can hold, and the answer is `[]`;
- read the solver's set with `sufficient_assumptions_for_infeasibility()`;
- run the deletion filter over that set: for each name in it, in turn, if the set without that name
  still cannot hold (`holds` answers False), leave the name out for good;
- return the names that remain, sorted in the order the rules were made, which is the order of
  `tm.rules`.

The solver returns indices of literals (its docstring says "the indices of the infeasible
assumptions"), not the literals, so map each literal's `.index` back to its rule name. The rules are
made in a fixed order,
each must in the inventory's order, then the budget, then the overrides in the order given, and the
explanation lists its rules in that order, whatever order the solver named them in. The third
function, `why_infeasible`, builds the model and maps the conflict's names to the planner's words:

<!-- snapshot: steps/06/vegcrew/explain.py -->
```python
def why_infeasible(season: Season, overrides: tuple[Override, ...] = ()) -> list[str]:
    tm = build(season, overrides)
    return [tm.says[n] for n in conflict(tm)]
```

**`vegcrew/planner.py`.** Shorter: it imports the model, and `make_plan` gains an `overrides` argument
(a stub in `steps/05`), a data check before any model is built, the "every rule holds" row, and the
explanation on failure:

<!-- snapshot: steps/06/vegcrew/planner.py -->
```python
    problems = check_overrides(season, overrides)
    if problems:
        raise ValueError("; ".join(problems))
    tm = build(season, overrides)
    tm.model.add_bool_and(list(tm.rules.values()))     # every rule holds
    solver = cp_model.CpSolver()
    solver.parameters.max_time_in_seconds = TIME_LIMIT
    solver.parameters.num_workers = WORKERS
    status = solver.status_name(solver.solve(tm.model))
    if status == "INFEASIBLE":
        return Plan(status, explanation=tuple(why_infeasible(season, overrides)))
```

`check_overrides` catches what is wrong with an override as data (an unknown circuit, crew or kind, a
week outside the season) and returns every problem at once. These are typing mistakes, not conflicts,
and the model is the wrong place to find them (lesson 9.1.2): a pin naming circuit Z9 would otherwise
fail as a `KeyError` deep in `build`.

**`vegcrew/report.py`.** When a plan has an explanation, the report prints it as a list headed
"these rules cannot all hold; change one of them". `steps/06` also carries a stub `record.py` for
the lesson *The same plan every run: determinism and regression tests*.

## Overrides Have a Price, and a Clash Names Its Rules

`overrides_demo.py` plans the small season with `steps/06` (`WORKERS` set to 1, so the output
repeats). First with two overrides the plan can keep, the road closure and the school:

```text
no overrides: OPTIMAL, risk carried $4,571k
season small-54: 20 circuits, budget $962k, crews 2, weeks 24
status OPTIMAL: 9 trims, cost $954k, risk carried $5,197k
  K1 666666600.xx44444446666.  C16:0-6 C10:7-8 C04:12-18 C06:19-22
  K2 22233555511111xxxx5555..  C02:0-2 C03:3-4 C15:5-8 C01:9-13 C05:18-21
the two overrides cost $626k of risk
```

C17 is gone (skipped), C02 runs on K2 from week 0 (pinned), and everything else moved around them.
The plan is OPTIMAL *for the season with those overrides*: the overrides are rules, so it is the best
plan that keeps them, and it carries $626k more than the plan without them. That number belongs in
front of whoever asked for the overrides.

Then two pins that cannot both hold: C17 (seven weeks) on K1 from week 0, and C02 on K1 from week 5:

```text
status INFEASIBLE: 0 trims, cost $0k, risk carried $0k
these rules cannot all hold; change one of them:
  - override 1: trim C17 on K1 from week 0 (crew already on site)
  - override 2: trim C02 on K1 from week 5 (complaints near the school)
```

Two rules, in the planner's words, with their reasons. Of the season's five changeable rules (two
musts, the budget and these two pins), the other three are not mentioned, because they are not part
of the clash.

Then the storm week: five forced circuits on top of the two musts.

```text
status INFEASIBLE: 0 trims, cost $0k, risk carried $0k
these rules cannot all hold; change one of them:
  - C05 is overdue and must be trimmed this season
  - C16 is overdue and must be trimmed this season
  - the season's budget is $962k
  - override 1: trim C08 this season (storm damage)
  - override 2: trim C11 this season (fire-risk area)
  - override 3: trim C14 this season (customer complaints)
  - override 4: trim C01 this season (regulator letter)
  - override 5: trim C19 this season (new subdivision)
the arithmetic: 85 + 213 + 178 + 105 + 112 + 179 + 117 = $989k > $962k
rules behind literals: 8; named by the solver: 8; after the deletion filter: 8
```

All eight rules are in the conflict: seven circuits cost $989k, $27k over the budget, and dropping any
one of them (the cheapest is $85k) or raising the budget by $27k ends it. The list is long because
the conflict is: every rule is needed for the proof, and the deletion filter confirmed each one. Here
the solver's set was already minimal; lesson 4.6.2 shows a case where it is not, which is why the
filter stays.

## Summary

- **The planner took no instructions, and its failure said nothing.** Overrides had to be data edits,
  and INFEASIBLE threw CP-SAT's proof away.
- **An override is one more rule, and every rule a planner can change sits behind a literal.** The
  planning solve fixes the literals to true; the explaining solve passes them as assumptions.
- **Overrides have a price** ($626k on the small season for two of them), **and a clash names its
  rules,** minimal by a deletion filter, in the planner's words with their reasons.
- **Six tests,** including one that checks an innocent rule is left out of the explanation.

## Design Note: Keep Physics Hard and Decisions Soft

Only rules a planner can change got literals: musts, the budget, overrides. Windows, time off and
"one trim per crew at a time" did not. An explanation is useful only if every rule it names is one the
reader can act on; "or let K1 work two circuits at once" is not. The line also keeps the explaining
solve small: eight literals to filter, not one per row. If an explanation ever needs to name a window
("C01's ground is too wet in week 2"), give windows a literal then, and decide on purpose that a
window is negotiable.
