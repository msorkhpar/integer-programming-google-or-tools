GridCap's analysts compute each project's present value: what a cost paid in a later year is worth today, once money's yearly return is taken into account. One analyst writes it as a division, another rewrites it as a multiplication, and the test that compared the two results with == starts failing. Both formulas are right. Meanwhile the loader of lesson Typed inputs with dataclasses and pydantic has six rules and no test that proves each one still fires. This lesson writes tests for numerical code with pytest, in four rules: what a test is, how to compare floats, how to share an input between tests, and how to turn a table of cases into tests. GridCap is a fictional utility, and its numbers are generated, not real data.

A Test Is a Function That Asserts, and pytest Runs Every One It Finds

pytest is a widely used Python test runner. A test is a function whose name starts with test_ and that checks something with assert. assert condition does nothing when the condition is true and stops the function with an AssertionError when it is false. pytest collects the test functions of a file, runs each one, and reports it as passed (it returned) or failed (it raised). You run it from a shell with python -m pytest path/to/file.py; the programs of this lesson call pytest.main([...]), which does the same from inside Python.

On its own, pytest only collects files whose names start with test_ or end with _test.py, plus any file you name on its command line. The programs of this lesson have ordinary names, so the course's own test runs leave them alone, and each one names itself when you run it.

Compare Computed Floats With a Tolerance You Chose, Never With ==

A float stores a number in binary with about 16 significant decimal digits, so most results are rounded in their last digit. Dividing by $1.07$ and multiplying by $1.07^{-1}$ round at different steps, and the two answers can land on neighbouring floats:

These compute P001's present value (one year of work, $2,150k, starting in 2028, one year after the plan's first year, 2027). The two results differ by about $2 \times 10^{-13}$ $k, a tiny fraction of a cent, and == says they are different. A tolerance says how far apart two numbers may be and still count as equal. math.isclose and pytest's approx both compare with one.

What tolerance does approx use? Printing it shows:

By default approx(expected) allows a relative tolerance of one millionth of expected (rel=1e-6), or an absolute tolerance of $10^{-12}$ (abs=1e-12), whichever is larger. For $2,009k that is $0.002k, two dollars, which is a sensible "equal" for money in $k. Near zero the relative part vanishes: one millionth of 0 is 0, so approx(0.0) allows only $10^{-12}$. A number that should be zero, such as the unspent part of a budget a solver used up, needs an absolute tolerance you choose, as in approx(0.0, abs=1e-6).

Why not round both sides instead? Because rounding moves a tiny difference to a big one when the value sits near a rounding boundary:

0.125 + 1e-12 and 0.125 - 1e-12 differ by two trillionths, and rounded to two decimals they differ by a whole cent. A tolerance never does that.

Not every number needs one. GridCap keeps money as whole $k in ints, and Python adds integers exactly, so a total cost is tested with ==. A tolerance is for floats: present values, rates, and the variable values a solver returns, which lesson The problem zoo: LP, MILP, CP, NLP and how to pick printed as floats such as 1.0 and 0.099.

Problem statement

A solver returned a crew-overtime plan, and the report tool must flag every year the plan spends over its budget. The plan's yearly spend is a sum of floats, so a year that spends its budget exactly can come back a few trillionths above it. The budget row of the model is $\text{spend}_y \le B_y$; the check allows a tolerance, as approx does: relative or absolute, whichever is larger. Year $y$ is over when

with relative tolerance $\rho$ (rel) and absolute tolerance $\alpha$ (abs_tol).

Write years_over(spend, budget, rel=1e-9, abs_tol=1e-6) in budget_check.py. spend maps each year to the plan's spend (a float, $k) and budget maps each year to its budget (an int, $k); every year of spend has a budget. It returns the years that are over, in increasing order.

A Fixture Builds an Input Once and Hands It to Every Test That Names It


Several tests often need the same input, such as the tiny portfolio. A fixture is a function marked @pytest.fixture that builds that input. A test asks for it by naming it as a parameter, and pytest calls the fixture and passes its result in:






A fixture's scope says how long one result is kept. The default, scope="function", builds a fresh one for every test that asks, so no test can see what another test did to it. scope="module" builds it once for all the tests in the file, which is right for an input that is slow to build and that no test changes (a GridCap Portfolio is frozen). tmp_path is a fixture pytest provides: a new empty folder per test (pytest keeps those of the last three runs and deletes older ones), so the round-trip test writes its CSV files where nothing else can collide with them. The test checks that writing the portfolio and reading it back gives the same content hash, the fingerprint gridcap computes from every number in a portfolio.


--setup-show makes pytest print when it builds (SETUP) and discards (TEARDOWN) each fixture, with its scope as a letter: S for the whole session, M for the module, F for one function:



tiny is set up once and used by all three tests. tmp_path is set up for the one test that asked for it and torn down right after. (tmp_path_factory and request are pytest's own helpers behind tmp_path.)


Parametrize Turns a Table of Cases Into One Test per Row, and Each Case Breaks One Rule


Lesson Typed inputs with dataclasses and pydantic's loader has six rejection rules, and each deserves a test. Writing six near-identical functions invites copy mistakes. @pytest.mark.parametrize takes a list of cases and runs one test function once per case, passing each case's values in as parameters:






The first argument names the parameters, the second is the table, and ids= gives each case a readable name in the report. rejected is a module-scoped fixture that loads the dirty export of lesson Preparing model input with pandas once and returns load's list of rejections, (line, project id, reason) triples. Run with -v (verbose), pytest lists every case on its own line:



Each case is a separate test: if one fails, the report names it, and the others still run. Adding a seventh rule is one more line in the table.


The table is only as good as its cases, and two habits make it trustworthy. First, each case breaks exactly one rule. A row with a negative cost and an unknown region is rejected even if the negative-cost check is deleted, because the region check still rejects it, so the test would keep passing over a broken loader. Every row the planner appended in lesson Preparing model input with pandas breaks one rule, and that is why they make good cases. Second, each case checks its reason, not only that the row was rejected. The test above asserts the reason text for that project, so it fails if P010 is ever rejected for something other than its negative cost. The last test of the file checks the other direction: no good row is rejected at all.

The Model


The selection model of lesson Decisions, objectives and constraints: turning a planner's question into a model, whole, with the budget row written as a test checks it on a plan that came from a solver. A test cannot ask a float sum to be at most $B$ exactly, so it allows a tolerance, and the mark shows the change.


Sets. $P$ the candidate projects; $M \subseteq P$ the must-do projects; $C \subseteq P$ the child projects, each with parent $p(c)$; $\mathcal{G}$ the alternative groups.


Parameters. $\text{capex}_i$ and $\text{npv}_i$ for each project ($k); $B$, the capital budget ($k); in a test, a relative tolerance $\rho$ and an absolute tolerance $\alpha$ (for example $\rho = 10^{-6}$, $\alpha = 10^{-6}$).


Variables. $x_i \in \{0, 1\}$ for each $i \in P$: 1 if project $i$ is funded.


Objective.



Constraints.



The model itself keeps $\le B$. The tolerance belongs to the test, because the test reads values a solver computed in floating point, and $\max(\rho|B|, \alpha)$ is the same "relative or absolute, whichever is larger" rule that approx uses.


Summary


  • A test is a function that asserts, and pytest runs every one it finds. A failure shows the values on both sides of the assert, and any failure makes the run's exit code 1.
  • Compare computed floats with a tolerance you chose, never with ==. approx is relative by default; near zero, pass abs=. Never round both sides. Integer money is compared exactly.
  • A fixture builds an input once and hands it to every test that names it. The default scope is one build per test; scope="module" shares one build across a file. tmp_path gives each test its own folder.
  • Parametrize turns a table of cases into one test per row, and each case breaks one rule. Check the reason, not only the rejection.
