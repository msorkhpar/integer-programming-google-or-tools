GridCap's planning database exports the portfolio every Monday as five CSV files and one small JSON file, and the selection model of lesson Decisions, objectives and constraints: turning a planner's question into a model runs on them. Last month a planner pasted six rows into the export by hand. One had a cost of "1,250", one started after it ended, and one named a parent project that does not exist. The model has no idea what a CSV file is. It needs a set of projects, a cost and a value for each, the must-do set, the parent of each child and the alternative groups, and every one of those numbers has to be right. This lesson goes from the files to those sets and numbers with pandas, in three rules. GridCap is a fictional utility, and these files are generated, not real data.

pandas is Python's table library. A DataFrame is a table with named columns, and each column holds one type, its dtype. pd.read_csv(path) reads a CSV file into a DataFrame.

Read Each Column With the Type the Model Needs, Not the Type pandas Guesses

Here is the start of the tiny portfolio's projects.csv, read with pandas' defaults:

cost_profile is what a project spends in each year of its work, joined by ;. must_do is 1 for a compliance project. parent names the project this one depends on, and it is blank for most rows.

pandas guesses each column's dtype from what is in it. The guess is right for this file, and it is the reason a loader that works for months fails one Monday. Read only the vegetation rows, whose projects all take one year. (text holds the whole file as one string; io.StringIO wraps a string so that read_csv can read it as if it were a file.)

With a 980;1490 in the column, pandas reads it as text (str). .str is how pandas applies a string method, here split, to every cell of a text column. Without one, every cell looks like a number, so the same column becomes int64, and the code that splits profiles on ; breaks. The column's type depends on the data, not on the file's format.

Blank cells have a second trap. pandas reads a blank as NaN ("not a number"), its marker for a missing value. NaN is a float, and every float but zero is true in an if:

The tiny portfolio has one child project, P004. The if parent test counts all eight, because the seven blanks are NaN. A model built that way would add a parent constraint for every project, with a parent called nan. Test for missing values with .notna() or pd.isna(), never with truthiness.

The fix for the first trap is to say what each column is. dtype= takes a dict from column name to type, and the loader of this module keeps one:

Read the vegetation rows again, the ones that broke .str.split above, this time with dtype=TYPES:

Now cost_profile is text (str) even when every profile is one number, so .str.split(";") works: each of the two vegetation projects has a one-year profile, which splits into a list holding one string, ['250'] and ['580']. And must_do is a real boolean, False for both, instead of the 0 in the file.

The declared "int64" matters when a number is missing. Blank out P001's earliest start and read the file both ways:

With guessed types the whole column quietly becomes floats; with "int64" declared, read_csv refuses the file. That is the failure you want, at the first line of the loader rather than inside the model.

Turn Each Table Into the Sets and Dicts the Model Indexes

Each row of a DataFrame also has a label, its index. read_csv numbers the rows 0, 1, 2, … in file order, and the code below uses those labels to find rows again.

The model in lesson Decisions, objectives and constraints: turning a planner's question into a model talks about $P$, $M$, $p(c)$, $\mathcal{G}$, $\text{capex}_i$, $\text{npv}_i$ and $B$. They come from three of the six files the export writes: projects.csv, npv.csv, and portfolio.json for the budget $B$ (its key capital_budget). The loader reads those three from folder, the folder the export was written to:

assets.csv, budgets.csv and crews.csv feed later models (asset risk, yearly and regional budgets, crew capacity); the selection model does not need them. JSON is a text format for numbers, strings, lists and named fields, and json.loads turns a JSON text into Python dicts and lists.

Each set or parameter is a Python set or a dict keyed by project id, and building them is the loader's job. DataFrames are the tool for reading and checking the files. Python sets and dicts are what the model code indexes, one entry per project, so the model never touches pandas.

npv.csv is a long table: one row per project and start year, because a project's value depends on when it starts. set_index([...]) makes the two key columns the row label, and .to_dict() turns the column into a dict keyed by (project, year) pairs, which is exactly how a model indexes a two-index parameter. The Decisions, objectives and constraints: turning a planner's question into a model model uses each project's value if it starts as early as it can, so value looks up the pair (pid, earliest_start). projects["must_do"] is a boolean column, and using it inside .loc[...] keeps only the rows where it is true. A boolean column used this way is a mask, and the next rule is built from them. projects[projects["parent"].notna()] is the same idea without .loc: the rows that have a parent. Finally, groupby("alt_group") splits the grouped rows by their group name, and iterating over it gives each name with the project ids in it, which is exactly an alternative group $g \in \mathcal{G}$.

The same table pivoted (start years as columns) is easier for a person to read, and worse for a model:

A start year outside a project's window has no row in the long table, so the wide table fills the hole with NaN, and a column holding NaN cannot be int64: the whole table turned into floats. The dicts the model gets:

Problem statement

The feeder team exports its candidate projects as two CSV files, and the selection model needs three of its parameters from them. For each project $i \in P$:

and, for each child project $c \in C$, its parent $p(c)$. A project whose parent cell is blank is not a child.

Write model_inputs(projects, npv) in inputs.py. It returns three dicts keyed by project id: capex, value, and parent (child id to parent id, children only).

  • projects has the columns project_id, cost_profile (yearly costs joined by ;, for example 300;200), earliest_start and parent.
  • npv is long: the columns project_id, start_year and npv, one row per project and start year.

Both frames come straight from pd.read_csv with no dtype=, as the team's loader reads them, so every column has the type pandas guessed for that file.

Check Every Row Before the Model Sees It, One Mask per Rule


Now the export with the planner's six rows appended:



None of these stops read_csv. Each one would reach the model as a wrong number or a broken rule: a cost the solver cannot read, a negative cost that makes a project look like income, a start window that holds no year, a region no budget covers, two variables for one project, and a parent constraint on a project that does not exist.


Each rule the data must satisfy becomes one boolean mask, a column with one True or False per row. A mask is easy to read and to test on its own:




Three pandas tools carry it. .explode() puts each year of a profile on its own row, keeping the project's row label, so "980;1490" becomes two rows. pd.to_numeric(..., errors="coerce") turns what is not a number into NaN instead of raising, so "1,250" is caught as a reason rather than as a crash. .groupby(level=0).any() folds the years back: a project is bad if any of its years is. isin tests membership in a list, ~ negates a mask, and & is "and" for two masks. The last two lines turn the masks into a report: for each rule, .loc[mask, ["project_id"]] keeps the marked rows and .assign(reason=...) adds a column naming the rule; pd.concat stacks the six small tables into one, and sort_index() puts it back in file order by row label. A row that broke two rules would appear twice, once per reason.



The report gives the file's line number, so a planner can find the row: the header is line 1 and the row labelled 0 is line 2, so the line is the label plus 2. Both copies of P008 are rejected: duplicated(keep=False) marks every copy, because the loader cannot tell which one is right, and guessing would hand the model a project nobody checked. The good P008 goes back to the planners with its copy.


duplicated takes subset=[...] when a row's key is more than one column. In npv.csv the key is the pair (project_id, start_year): P001 has one row per start year, and that is fine, but two rows for the same project and year are not. Here P001's 2028 value is typed in a second time, with a different number, and the mask finds both copies. df.index[mask] gives the row labels where a mask is True:






(pd.concat(..., ignore_index=True) numbers the stacked rows afresh, so the copy gets label 13.) The last line is why the check matters: without it, set_index(...).to_dict() keeps one of the two values without a word, and the model gets a value nobody chose. Why not repair "1,250" to 1250? Because the loader cannot know whether it meant 1,250 or 1.25 written with a decimal comma, and a guessed cost is a wrong plan the model will defend as optimal.

The Model


The selection model of lesson Decisions, objectives and constraints: turning a planner's question into a model, unchanged, with where each set and parameter comes from.


Sets. $P$ the candidate projects; $M \subseteq P$ the must-do projects; $C \subseteq P$ the child projects, each with parent $p(c) \in P$; $\mathcal{G}$ the alternative groups, each a set of projects.


Parameters. $\text{capex}_i$, the total cost of project $i$ ($k), the sum of its cost profile; $\text{npv}_i$, its NPV if it starts in its earliest start year ($k); $B$, the capital budget ($k).


Variables. $x_i \in \{0, 1\}$ for each $i \in P$: 1 if project $i$ is funded.

Every rejection rule above protects one part of this model: an unknown parent would make $p(c) \notin P$, a duplicate id would give one project two variables, and a cost that is not a number has no place in the budget row.


Summary


  • Read each column with the type the model needs. pandas guesses a column's dtype from its content, so pass dtype=, and test for blanks with .notna(), never with if.
  • Turn each table into the sets and dicts the model indexes. Long tables become dicts keyed by tuples with set_index(...).to_dict(); pivot tables are for people.
  • Check every row before the model sees it, one mask per rule. Collect every broken rule with its line number, reject the row, and never guess a repair.

Design Note: Reject Rows, Don't Repair Them


A loader that repairs data ("treat 1,250 as 1250", "keep the first copy of P008") makes a guess the planners never see, and the model then optimizes the guess. A loader that rejects a row with a reason sends the question back to the person who can answer it. It costs a round trip, and in return every number the model uses is one somebody wrote on purpose.
