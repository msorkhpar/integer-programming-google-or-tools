  15. Sparse model matrices

GridCap's planning team adds a rule from the regulator: each of the four regions has its own budget in each year, on top of the company-wide one. On the tiny portfolio the model matrix grows from 7 rows to 17. On the large portfolio, 10,000 projects over ten years, it has 1,044 rows, and the NumPy array of lesson Vectors, matrices and Ax ≤ b in NumPy would hold 10,440,000 numbers. Almost all of them are zero. This lesson counts those zeros, stores only the numbers that are not, and shows that a solver is handed the model in exactly that form. Four rules, one per heading.

GridCap is a fictional utility; none of its numbers describe a real one. Every project in this lesson still starts in its earliest start year, as in lesson Vectors, matrices and Ax ≤ b in NumPy.

Most Entries of a Model Matrix Are Zero

The model matrix here has four kinds of rows: a budget per year (budget_2027), a budget per region and year (region_Valley_2028), one parent row per child project ($x_c - x_{p(c)} \le 0$) and one row per alternative group ($\sum_{j \in g} x_j \le 1$). A nonzero is an entry of the matrix that is not 0, and the density is the share of entries that are nonzeros.

The density falls as the portfolio grows: 19% on tiny, a third of one percent on large. The reason is in the rows, not in GridCap's numbers:

A project only spends in the one to three years it is worked on, so it appears in few of the ten budget rows. It belongs to one region, so it appears in at most three of the forty region rows. A parent row touches two projects, whatever the size of the portfolio. Most rows of a real model are like the parent row: a local rule about a few variables. Add projects and you add columns and rows, while each row keeps about the same number of nonzeros, so the share of nonzeros keeps falling. A matrix where most entries are zero is called sparse; one stored with every entry is dense.

Store Only the Nonzeros: Triplets, Then Compressed Rows

The simplest sparse form lists each nonzero as a triplet (row, column, value). This is also called coordinate or COO form, and it is how a model is naturally built: each rule adds its entries as it goes.

Triplets repeat each row number once per nonzero. Compressed sparse row form (CSR) sorts the nonzeros by row and stores the row numbers only as boundaries. It keeps three arrays:

  • data: the nonzero values, row after row;
  • indices: the column of each value in data;
  • indptr (index pointer): where each row starts in data, plus one last entry for where the last row ends. Row $i$'s nonzeros sit at positions indptr[i] up to, but not including, indptr[i + 1].

SciPy is Python's library for scientific computing, built on NumPy. Its module scipy.sparse holds sparse matrices; the programs import it with from scipy import sparse. sparse.coo_array takes the triplets, and .tocsr() converts them to CSR:

indptr has 18 entries for 17 rows. The last line is the size of one entry of each array (itemsize, in bytes): each value takes 8 bytes, and so does each column index and each indptr entry, because SciPy stored all three as 64-bit integers here. Reading a row is a slice:

These are exactly the nonzeros of the 2028 row of lesson Vectors, matrices and Ax ≤ b in NumPy's matrix. An empty row shows up as two equal neighbours in indptr: positions 5 and 6 are both 13, so row 5 (region_Ridge_2029) has no nonzeros, because no Ridge project spends in 2029 when every project starts early.

Problem statement

A water utility's model builder adds terms to its rules one at a time, as (row, column, value) triplets: row is the pumping station's rule, column the pump, value the coefficient. Before the matrix goes to the checker it is compressed into CSR form, and you write the compressor, with no SciPy.

Write to_csr(n_rows, triplets) in csr.py. It returns three lists, (indptr, indices, data):

  • data: the values, row 0 first, then row 1, and so on; within a row, by increasing column;
  • indices: the column of each value in data;
  • indptr: n_rows + 1 entries; row $i$'s values are data[indptr[i]:indptr[i + 1]], so indptr[0] is 0 and the last entry is len(data).

The triplets may arrive in any order. A row may have no triplets at all, including the last rows. When two triplets name the same row and column, the builder meant their sum: store one entry with the two values added.

Sparse Products Give the Same Answer in a Fraction of the Memory


A CSR matrix supports A @ x like a NumPy array. To compute row $i$'s activity it only visits row $i$'s nonzeros, data[indptr[i]:indptr[i+1]] times the matching entries of $x$, and never the zeros:



Here is that product checked against the dense one, for a plan that funds every third project:




size runs over "medium" and "large", and stored_bytes(A) is the memory of the CSR form, shown below.



The answers are identical, entry for entry. The memory is not: on the large portfolio the dense matrix takes 83.5 MB and the CSR one 0.56 MB, about 150 times less. The CSR size is the bytes of its three arrays:



With 8 bytes per entry, as printed above, that is 8 bytes of value and 8 bytes of column index per nonzero, plus 8 bytes per indptr entry. On large: 34,610 nonzeros × 16 bytes + 1,045 indptr entries × 8 bytes = 562,120 bytes, as printed. The dense array holds 8 bytes for every one of its 10,440,000 entries, zeros included: 83,520,000 bytes. So CSR's three arrays grow with the number of nonzeros (plus one indptr entry per row), while a dense matrix grows with rows times columns. If a model's rows and columns both double while each row keeps its few nonzeros, the dense matrix quadruples and the CSR one only doubles. Section 11 works at the scales where that difference decides what fits in memory.

A Solver Receives the Model as Nonzeros, Not as a Grid


OR-Tools' MathOpt, the modeling library of lesson The problem zoo: LP, MILP, CP, NLP and how to pick, can export the model it hands to a solver. Then ask for the exported model and read its constraint matrix:






export_model() returns the model in MathOpt's exchange format: a ModelProto, a protocol buffer, which is Google's format for structured data that programs in different languages can pass to each other. It is the complete description solve hands to a solver. Its field linear_constraint_matrix is a SparseDoubleMatrixProto, a sparse matrix stored as triplets in three parallel lists: row_ids, column_ids and coefficients (the program prints the first nine of each). There are 26 of them, the same 26 nonzeros. The 110 zeros of the 17-by-8 grid are not in it, and all 17 rows are, including the empty region_Ridge_2029. LinearExpression(...) wraps each sum so that a row with no terms is still an expression to constrain, not the plain number 0 that sum of nothing gives.


So when you write x[P003] * 980 into a MathOpt constraint, you are adding one triplet. A model with a million variables is buildable because a typical row mentions a handful of them. This is also why model-building code should never form a dense row (sum(A[i, j] * x[j] for j in range(n))) when it can loop over a row's nonzeros: the dense loop visits every zero on the way.


How the solver then works on those nonzeros, keeping its own data sparse through every step, is inside the algorithms of section 2 and is not something this lesson's programs measure.


The Model


The model of lesson Vectors, matrices and Ax ≤ b in NumPy with regional budgets added (marked), and must-do projects written as variable bounds rather than rows. Nothing in this lesson solves it; it is built and stored.


Sets. $P$ the projects; $Y$ the years; $R$ the regions (Ridge, Valley, Coast, Plains); $P_r \subseteq P$ the projects in region $r$; $M \subseteq P$ the must-do projects; $C \subseteq P$ the child projects, with parent $p(c)$; $\mathcal{G}$ the alternative groups.


Parameters. $\text{npv}_j$ ($k); $a_{yj}$, what project $j$ spends in year $y$ if it starts in its earliest start year ($k); $B_y$, the budget of year $y$ ($k); $B_{r,y}$, the budget of region $r$ in year $y$ ($k).


Variables. $x_j \in \{0, 1\}$ for $j \in P \setminus M$, and $x_j = 1$ (lower bound 1) for $j \in M$.


Objective.



Constraints.



Rows: $|Y| + |R|\,|Y| + |C| + |\mathcal{G}|$, which is 3 + 12 + 1 + 1 = 17 on GridCap tiny and 10 + 40 + 419 + 575 = 1,044 on large.


Summary


  • Most entries of a model matrix are zero. Each row is a rule about a few variables, so the density falls as the model grows: 0.33% on GridCap large.
  • Store only the nonzeros. Triplets (row, column, value) are how a model is built; CSR (indptr, indices, data) is how it is stored and read row by row.
  • Sparse products give the same answer in a fraction of the memory. On GridCap large, 0.56 MB instead of 83.5 MB, with identical activities.
  • A solver receives the model as nonzeros. MathOpt's exported constraint matrix is a list of triplets, one per nonzero.

Further reading: MathOpt (OR-Tools) (what a MathOpt model can hold and the solvers it is handed to); MathOpt model.proto (the ModelProto that export_model() returns, which keeps linear constraints in a struct-of-arrays form); MathOpt sparse_containers.proto (SparseDoubleMatrixProto: triplets in row-major order, each (row, column) pair at most once); SciPy sparse arrays (build in COO, convert to CSR for arithmetic, and the move from sparse matrices to sparse arrays); SciPy csr_array (the data, indices, indptr layout, and duplicate triplets summed on conversion).


Challenges


  1. Add one row per project that says "fund it at most once" ($x_j \le 1$). How many nonzeros and how much density does the large matrix get? Is such a row worth having?
  2. The medium matrix has 86 rows. Without running anything, how many entries does its indptr have?
  3. A colleague builds each constraint as sum(A[i, j] * x[j] for j in range(n)) over the dense large matrix. How many terms does that visit in total, and how many are zero?


Design Note: Build Sparse From the Start


It is tempting to build $A$ as a NumPy array first, because indexing A[r, j] is easy, and convert at the end. On GridCap large that first array is 83.5 MB for 0.56 MB of information, and on the models of section 11 it would not fit at all. Build the triplets as the rules are written, as model_matrix.py does, and convert to CSR once. MathOpt does the same: every term you add to a constraint is one triplet, and nothing ever forms the grid.
