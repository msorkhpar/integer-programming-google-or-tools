  15. Decisions, objectives and constraints

GridCap's capital planning team has $7.39M to commit this cycle and eight candidate projects that would cost $13.44M together. The director's question is short: which projects do we fund? An analyst sorts the list by value per dollar and funds from the top until the money runs out. The plan is cheap to make and easy to explain, and it breaks two of the utility's own rules. This lesson turns the director's question into a model: the decisions, one number that ranks every plan, and the rules that say which plans are allowed. Four rules, one per heading.

Here is the tiny GridCap portfolio. All money in this course is in thousands of dollars ($k).

Capex is what a project costs over its life. NPV (net present value) is what it is worth to the utility, in today's dollars, after paying for it; section 7 shows where these numbers come from. The rules column holds the business rules this lesson turns into constraints.

A Model Starts From the Decisions You Control, One Variable per Choice

The director cannot choose the budget, the costs or the values. Those are data. What the team does control is, for each project, fund it or not. Each of those choices is a decision variable, and a plan is one value for every variable.

In code, a plan starts as a set of project ids. The moment you want to write the rules as arithmetic, write it as a vector with one 0/1 entry per project instead:

Written mathematically, $x_i = 1$ if project $i$ is funded and $x_i = 0$ if it is not. A variable that can only be 0 or 1 is a binary variable, and almost every capital planning model in this course is built from them.

The common mistake is to start from the data ("we have NPVs, let's rank them") rather than from the decision. Ranking answers which project is best on its own. The director asked which combination is best, and the best combination can leave out the project with the top NPV, as you will see below.

The Objective Is One Number That Ranks Every Plan

To compare plans, the model needs one number per plan, the objective. Here it is the total NPV of the funded projects, and we want it as large as possible:

One number is a strong demand. "Maximize value and minimize risk" is two numbers, and a model cannot rank plans with two numbers until you say how they trade off. Section 8 is about exactly that. Until then each model has one objective, and everything else the planners care about has to be either part of that number or a constraint.

What goes wrong when the objective is not the thing people care about? The model gives you the best plan for the wrong question. Here is the best plan, with every rule below respected, when GridCap counts projects funded instead of NPV:

It swaps the transformer replacement P006 for the cheaper repair P007 and adds a vegetation project. Five projects instead of four, and $845k less value than the plan you will meet below. A progress report that counts projects would call that an improvement.

Constraints Decide Which Plans Are Allowed, and Business Rules Are Constraints Too

A constraint is a rule every allowed plan must satisfy. The budget is the obvious one:

Two plans, checked against it:

The second plan is worth more and is not allowed, so it is not a candidate at all. A plan that satisfies every constraint is feasible. Optimization looks for the best feasible plan, never the best plan.

The budget is not the only rule. The rules column holds three more, and each one is a constraint as real as the budget:

  • Must-do. P002 is a compliance project. Every allowed plan funds it: $x_{P002} = 1$.
  • Parent and child. P004 (a breaker bay replacement) only makes sense if P003 (the tower set it sits on) is funded too. Funding the child without the parent is not allowed: $x_{P004} \le x_{P003}$.
  • Alternatives. P006 replaces a substation transformer and P007 repairs the same one. The utility does one or neither: $x_{P006} + x_{P007} \le 1$.

Pause on the parent-child rule. Why is it $x_{P004} \le x_{P003}$ and not $x_{P004} = x_{P003}$? Because the parent may be funded alone. The equation would force them to go together in both directions, which is a different rule (an all-or-nothing bundle, lesson Parent-child bundles and all-or-nothing).

A rule that lives only in a planner's head is the costliest kind. The model has never heard of it, so it will happily break it, and the plan that comes back looks optimal and is useless. Section 6 is a catalogue of these rules and how to write each one.

Problem statement

The planning tool rejects plans, and planners keep asking why. A rejection that only says "infeasible" sends them to the spreadsheet; one that names the broken rule lets them fix the plan in a minute.

Write evaluate_plan(projects, budget, plan) in plans.py. It returns a pair: the plan's total value, and a list of problems, one string for each rule the plan breaks:

problemwhen
"budget"the plan's total cost is over budget
"must-do:<id>"a must-do project is not in the plan (one string per missing project)
"parent:<id>"project <id> is in the plan and its parent is not
"alternatives:<group>"the plan holds more than one project of alternative group <group>

An allowed plan returns its value and an empty list. The order of the problems does not matter. projects is a list of Project records (defined at the top of the file) and plan is a set of project ids.

The checks of the previous practice are the first half of this one: paste your evaluate_plan into best.py (the starter leaves it empty), or write the checks again. The director wants the plan itself: of every allowed plan, the most valuable one. Portfolios in this tool have at most 15 projects, so checking every subset is fast enough.


Write best_plan(projects, budget) in best.py. It returns (value, plan), where plan is a frozenset of project ids, for the allowed plan with the highest total value. When two allowed plans have the same value, return the one that costs less. When no plan is allowed at all, return None.

The Model


Everything this lesson built, as one model. Every allowed plan is a solution of it, and the optimal plan is its best solution.


Sets. $P$ the candidate projects; $M \subseteq P$ the must-do projects; $C \subseteq P$ the child projects, each with parent $p(c)$; $\mathcal{G}$ the alternative groups, each a set of projects (on GridCap tiny, $\{P006, P007\}$).


Parameters. $\text{capex}_i$ and $\text{npv}_i$ for each project ($k); $B$, the capital budget ($7,390k on GridCap tiny).


Variables. $x_i \in \{0, 1\}$ for each $i \in P$: 1 if project $i$ is funded.


Objective.



Constraints.



On GridCap tiny its optimum is the brute-force plan, ['P001', 'P002', 'P005', 'P006'], worth $3,627k. Lesson The problem zoo: LP, MILP, CP, NLP and how to pick hands this same model to a solver.


Summary


  • A model starts from the decisions you control. Write each yes/no choice as a binary variable; a plan is one value for each.
  • The objective is one number that ranks every plan. A second goal is either folded into that number or written as a constraint, or the model answers a different question.
  • Constraints decide which plans are allowed. Must-do, parent-child and alternative rules are constraints like the budget, and a rule the model does not know about is one it will break.
  • Checking a plan is cheap; finding the best one is not. Greedy rules ignore everything but one constraint, and brute force doubles with every project.

Challenges


  1. The director asks to "fund as many vegetation projects as possible, then maximize NPV". Is that one objective or two? How would you write it?
  2. Change the alternative rule to "exactly one of P006 and P007". What does the utility lose, and when would that rule be right?
  3. Find a greedy rule (some other sort order) that returns the optimal plan for the tiny portfolio. Would you trust it on the small one?


Design Note: Why the Rules Go Into the Model, Not Into a Post-Check


A tempting shortcut is to let a simple method propose a plan and then reject it if it breaks a rule. On GridCap that rejects the greedy plan and leaves you with nothing to offer. Writing the rules as constraints costs modeling time up front, and in return the solver only ever proposes plans the utility can use, and can prove that none of them is better than the one it returns.
