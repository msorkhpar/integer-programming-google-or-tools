A contractor left GridCap a PuLP script: lesson Decisions, objectives and constraints: turning a planner's question into a model's one-period selection (fund projects within one capital budget, with must-do, parent and alternative-group rules), written in the style of PuLP code from before version 3.3. Planners have since added their own rules to copies of it, and some of those copies give answers nobody can explain. GridCap now wants three things: read the script, find the lines that do not do what they say, and move it to MathOpt, the API the rest of GridCap's planning code uses. GridCap is a fictional utility's portfolio.

PuLP is easy to write and easy to misread. Most of its traps share one cause: PuLP gives no error, and the model quietly becomes a different model. Five rules, one per heading. They run on PuLP 3.3.2, the course's pinned version (lesson A PuLP model end to end with CBC).

Older PuLP Code Makes Variables Apart From the Problem and Reads Answers Off Them

Here is the inherited script, legacy_selection.py, whole:

Read it line by line against lesson A PuLP model end to end with CBC's version:

  • LpVariable.dicts("x", ids, cat="Binary") makes one variable per key, before any problem exists, and names each one by the prefix, an underscore and the key: x_P001. A variable joins the problem only when a row or the objective uses it.
  • prob += lpSum(...) with no name sets the objective. PuLP names it OBJ.
  • prob += ... <= ..., "budget" adds a named row, as in lesson A PuLP model end to end with CBC.
  • prob.solve(PULP_CBC_CMD(msg=0, gapRel=gap)) runs the bundled CBC quietly. The script ignores what solve returns and reads prob.status through LpStatus instead.
  • value(x[i]) reads a value. It is the same number as x[i].varValue.

On GridCap small it finds the value lesson Reading pywraplp code found with pywraplp, and you can look inside what it built:

A binary is stored as an integer with bounds 0 and 1, which is why x_P001 prints Integer 0 1. A row's sense is a number: -1 for <= (pulp.LpConstraintLE), 1 for >=, 0 for ==.

The idioms map to the forms of lesson A PuLP model end to end with CBC, which PuLP 4 keeps:

Python hides a DeprecationWarning raised inside a library unless warnings are switched on (python -W default), so nobody saw that PuLP 3.3 warns about two of the script's lines, printed above. PuLP 4 removed both, and LpStatus as well, so the script will not run on PuLP 4 as it stands.

+= Adds a Row Only When It Is Handed a Constraint

+= decides what to do from the type of what it is given. A comparison of PuLP expressions is an LpConstraint, and += adds it as a row. A PuLP expression with no comparison becomes the objective, replacing the old one. And a plain Python True is accepted and dropped, because PuLP lets prob += True pass on purpose (a comparison between two numbers is always True or False). False raises a TypeError. That is how PuLP 3.3's LpProblem.__iadd__ is written.

Three planner rules were added to copies of the script, each in a way that looks right. Each is run on GridCap small next to the line it meant:

What each line did:

  • The lock written on data. last_plan holds last year's answers, read from a file: numbers, not variables. last_plan["P005"] == 1 is Python comparing 1.0 with 1, which is True, so += dropped it. The row count stays at 9 and P005 stays out. Written on the variable, the lock is a tenth row, P005 is in, and the plan is worth $264k less, the price of the planners' rule.
  • The chained band. Python reads a <= b <= c as (a <= b) and (b <= c). A PuLP constraint counts as true in an and, so the expression's value is its right half alone: the printed row has only <= 12000. Ridge stayed at $7,360k, below the $9,000k floor. As two rows, Ridge gets $9,060k.
  • The crew row with no <=. It is an expression, so it became the objective. CBC maximized crew-months (111), and the plan's value fell to $20,347k. PuLP did warn, with a UserWarning on standard error, which a nightly job's log is unlikely to show anyone.

None of the three is an error, and none changes the status: each run says Optimal. Two defenses catch them. Count the rows: a rule that adds no row, or one row where two were meant, shows up in prob.numConstraints() and in the LP file. Refuse anything but a constraint before adding it: isinstance(row, pulp.LpConstraint) is False for the lock written on data and for the bare crew expression, and True for a real row, as the last line printed. A chained comparison does pass that check, since its right half is a real constraint, so the rule there is simpler: never chain. Write a band as two rows, each with its own name.

Row and Variable Names Must Stay Unique After PuLP Rewrites Them

Names identify rows in the LP file, in a solver's log and in get_constraint_by_name. PuLP enforces them, and also rewrites them. names.py shows how two names become one. attempt(label, action) runs action and prints its result, or the error it raised cut to its first line; add adds one named row; lp_rows writes the problem as an LP file and returns its row lines:

Read it as four rules:

  1. A repeated row name is refused with PulpError when the second row is added. That one is loud. It usually means a loop built names from too little: alt_ plus a region where the groups are per region and program, say.
  2. PuLP rewrites characters an LP file cannot hold, such as a space or a -, to _. So budget-2027 and budget_2027 are the same name, and the second is refused. Build names from ids that are already plain: letters, digits and _.
  3. A row with no name gets one from a counter, _C1, _C2, ... in the order rows were added. One more row in front, and every later row's name moves: z <= 8 was _C1, then _C2. Two runs' LP files can then no longer be compared row by row, so name every row.
  4. Two variables with one name are not refused when they are made, because LpVariable.dicts makes them apart from the problem. Keys P-017 and P_017, from two systems that spell ids differently, both became x_P_017, and the solve failed with a message that says only that CBC could not run. prob.checkDuplicateVars() says what is wrong; call it before solving a model whose variable names come from data.

Read status and sol_status Before Any Value, and Expect None

Lesson A PuLP model end to end with CBC showed that status 1 with sol_status 2 is a plan nobody proved best. The inherited script has worse problems: it reads values whatever the status, and older code often guards the solve with if prob.solve(...):. status_traps.py runs both on a budget too small for the must-do projects, so no plan exists:

The status code for Infeasible is -1, and Python treats every number but 0 as true, so if prob.solve(): runs its "we have a plan" branch exactly when there is none. The values left in the variables are whatever CBC had when it gave up: four must-do projects at 1, and x_P034, a binary, at -0.469. The script prints them as a plan worth $1,687.29k. A value read after a run with no plan is not a plan.

The other trap is None. A variable that never entered the problem has no value, and neither does an objective that was never set:

LpVariable.dicts made x["P003"], but no row or objective used it, so CBC never saw it, and its varValue is still None. pulp.value(x) passes that None through, and the comparison fails. A feasibility check with no objective has prob.objective set to None, and pulp.value(None) fails too. In inherited code, these errors usually mean a variable the code made and then forgot to use, which is worth knowing before you fix the crash.

So read a result in this order, as read_plan does:

Problem statement

A gas utility inherited valves.py, a PuLP script that picks which valves to replace this year. It runs every night without an error, and every night it reports Optimal. The planners have stopped trusting it: it once proposed more crew-weeks than the utility has, it has dropped valves that last year's plan funded, it left the harbor district below its agreed share, and once it returned a plan for a year when the rules could not all be met.

Design Note: Fix the Legacy Code Before You Port It, and Say Which You Did


A port proves that the new code gives the same answers as the old. If the old code has a dropped lock row, a port that is "the same" faithfully keeps the bug, and a port that quietly fixes it fails the test for a good reason. So do it in two steps. First fix the PuLP script, with a test for each fix (a row count, a value), and record the new answers. Then port, and prove the port against the fixed script. Each step then has one reason to change the numbers, and a reviewer can see which step changed which number.
