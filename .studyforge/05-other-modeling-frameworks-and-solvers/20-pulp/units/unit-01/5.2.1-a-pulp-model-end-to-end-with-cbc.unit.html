A PuLP Model Is a Problem, Its Variables, and Rows Added With +=

PuLP has three building blocks:

  • pulp.LpProblem(name, sense) holds the whole model: its objective, its rows and, through them, its variables. sense is pulp.LpMaximize or pulp.LpMinimize.
  • Variables. prob.add_variable(name, lowBound, upBound, cat=...) creates one and ties it to the problem. cat is pulp.LpContinuous (the default), pulp.LpInteger or pulp.LpBinary. Older code creates variables on their own with pulp.LpVariable(...); lesson Reading PuLP code you inherit reads that style, which PuLP 4 removed.
  • prob += ... adds to the problem. Handed a linear expression, it sets the objective. Handed a comparison (<=, >=, ==) of expressions, it adds a row. A second item after a comma is the name: prob += expr <= 5, "cap".

pulp.lpSum(...) adds up a sequence of terms into one linear expression, the way Python's sum does. Here is the start of lesson Start-time variables x(i,t) and timing windows's model, from pulp_timing.py:

One binary $x_{i,t}$ per project $i$ and allowed start year $t$, named x_P001_2028 and so on. As in lesson Start-time variables x(i,t) and timing windows, a start year outside the project's window has no variable at all. The names matter: they are what the solver sees, what an LP file shows, and how you find a variable again.

Most rows talk about $\text{started}(i) = \sum_{t \in T_i} x_{i,t}$, so the builder has a helper for it. With by set, it sums only the start years up to by, which the precedence rows need:

Then the objective, the once and must-do rows, and the yearly budgets, each with the name the model block below gives it:

The alternative-group rows (alt_G006) and the precedence rows (after_P004_2028) follow the same pattern; the full builder is in pulp_timing.py.

Read += with care. The same operator sets the objective or adds a row, depending only on what stands to its right, so a row that lost its <= quietly becomes the new objective. Lesson Reading PuLP code you inherit shows that bug and three others.

Write the LP File and Read It Before You Solve

A model built in a loop is hard to check by reading the loop. PuLP can write the model in the LP format, a plain-text file that lists the objective, then every row by name, then the variables' bounds and types, the way a solver will see them. prob.writeLP(path) writes it. Here it is for the tiny portfolio:

Three things to read in it:

  • Every term moved to the left. The precedence row was written as $\text{started}(P004, \le 2028) \le \text{started}(P003, \le 2027)$; the file shows it as - x_P003_2027 + x_P004_2028 <= 0. That is the same row. PuLP keeps variables on the left and one number on the right.
  • The rows come sorted by name, not in the order the code added them (prob.constraints() keeps that order). Name rows so that sorting groups them: every budget row starts budget_.
  • The 2027 budget row has four projects, not eight. Only projects that can be spending in 2027 appear in it, which is the spreading of lesson Cash-flow spreading across years made visible.

When a model gives a strange answer, this file is the first thing to read. The PuLP debugging guide gives the same advice for infeasible models: write the LP file and check each row in an editor.

Problem statement

A water utility refurbishes some of its pump stations each year. A refurbished pump uses less energy, so each refurbishment saves a known amount a year, but it costs money, takes crew-days, and takes the station offline while the work is done. Some stations share a bypass main: if both of a pair were offline at once, the district they serve would lose pressure. The regulator also names stations that must be done this year.

In refurbish.py, the variables and the objective are written. Add the rows, so that:

  • build(stations, budget, crew_days, bypass_pairs) returns the PuLP problem and its variables y[sid], with one row per rule below, named as in the labels;
  • refurbish(...), already written, solves it with CBC and returns the yearly savings and the sorted ids of the stations to refurbish.

The formulation. $S$ is the stations, $K$ the pairs that share a bypass, $M \subseteq S$ the must-do stations. Each station $i$ saves $s_i$ ($k a year), costs $c_i$ ($k) and takes $h_i$ crew-days; the year has a budget $B$ and $H$ crew-days.

Name each row as its label says, with the ids filled in: budget, crew, bypass_S1_S2, must_S4. A station may appear in more than one bypass pair. About six lines.

Write the model out as an LP file and read it once before you run the tests. Run and the tests start in the course's root folder, not in this practice's folder, so prob.writeLP("pumps.lp") would put pumps.lp at the root of the course. Write it inside your practice folder, next to refurbish.py, instead: prob.writeLP(str(Path(__file__).with_name("pumps.lp"))), with from pathlib import Path at the top.

CBC Runs as a Separate Program, Set Up Through a Solver Object


prob.solve(solver) hands the model to a solver. In PuLP 3.3, pulp.PULP_CBC_CMD(...) is the CBC executable that ships inside the PuLP package. As the _CMD in its name says, it is a command-line integration: PuLP writes the model to a file, runs cbc on it as a separate program, and reads the solution file back. Its options are arguments of the constructor. The module's helper keeps CBC quiet unless asked:



OptionMeaning
msg=FalseDon't print CBC's log. The default, True, prints it.
timeLimit=60Stop after 60 seconds.

The Status Says How CBC Stopped; sol_status Says Whether the Plan Is Proved


In PuLP 3.3, prob.solve() returns a status code, an int also kept in prob.status. The dict pulp.LpStatus turns it into words. A second code, prob.sol_status, describes the solution itself, and pulp.LpSolution turns that one into words. Here are both dicts, then GridCap small solved in full and stopped by maxNodes=1 (after the first node of the search), GridCap medium stopped by a two-second time limit, and GridCap small with a row added that no plan can meet:








Read the middle line twice. CBC stopped after one node with a plan worth $23,944k, $316k short of the optimum, and status still says Optimal. The time limit on medium gives the same pair. In both runs the search stopped early with a plan in hand, and PuLP 3.3's CBC interface reported status 1. Only sol_status tells a finished search from a stopped one: 1 is a proved optimum, and 2 is a solution with no proof.


So the rule for PuLP 3.3:


  • status == pulp.LpStatusOptimal and sol_status == pulp.LpSolutionOptimal: a proved optimum.
  • status == pulp.LpStatusOptimal and sol_status == pulp.LpSolutionIntegerFeasible: a plan that keeps every row, but the search stopped before proving it best. Report it as such.
  • Any other status: there is no plan to read, whatever the variables hold (lesson Reading PuLP code you inherit shows what they hold).


PuLP 4 replaced both codes. There solve() returns an LpSolveStats object, LpStatus and the LpSolution constants are gone, a run stopped by a limit reports the limit (TimeLimit, NodeLimit, ...) instead of Optimal, and stats.has_solution says whether a plan exists.

Problem statement


A bus operator plans depot upgrades in PuLP and solves them with CBC every night. A reporting job reads each run and writes one line for the operations manager: was a plan found, is it proved the best, and what is it worth. Write report(prob) in verdict.py. It is called after prob.solve(...) and returns:


  • ("proved", value) when CBC finished its search with an optimal plan;
  • ("unproved", value) when CBC stopped early, for instance at a time limit, with a plan it has not proved best;
  • ("no plan", None) in every other case.

A Port Is Proved by a Test: Same Optimum, Same Rows, Each Plan Allowed


"The same answer" means three checks, the ones lesson Migrating a pywraplp model to MathOpt uses to prove a port:


  1. The same optimal value, with both solvers at a gap of 0. At the default gap, a solver may stop at a plan within its tolerance of the best, and two correct models can then disagree.
  2. Each plan keeps the other model's rules. Two optimal plans can differ when several tie, so plans are not compared directly. Instead, plan_rules.broken_rules checks a plan against the rules from the data, with no solver. A port that dropped a row could reach a higher value with a plan the original forbids; this check catches it.
  3. The same rows by name. A dropped or doubled rule shows up before any solve.


same_optimum.py runs all three on tiny and small:




Why SCIP here and not HiGHS, the course's default? Because in the runner, a Python process that has imported pulp is killed when MathOpt then solves a MIP with HiGHS. highs_after_pulp.py runs each case in a fresh child process, since the crash takes down the process it happens in:



SIGSEGV is a segmentation fault: native code read memory it should not, and the operating system ended the process. No Python exception is raised and no try can catch it. The program asks Python's faulthandler for the native stack of the crash: it runs through OR-Tools' HiGHS solver and the highspy library, the HiGHS that PuLP's own HiGHS interface loads. Until that is fixed, keep PuLP and MathOpt-with-HiGHS in separate processes, or use another MathOpt solver in a process that needs both.


The module's test keeps them apart. It solves the PuLP port with CBC. Then, in a child process, it runs lesson Start-time variables x(i,t) and timing windows's own builder with HiGHS, the model and solver that lesson used. It checks the same value, that both plans keep every rule, and the same row names. It passes on tiny and small, so the regional office's PuLP model answers $24,260k, as the MathOpt model does.

Summary


  • A PuLP model is a problem, its variables and rows added with +=. += with an expression sets the objective; with a comparison and a name, it adds a named row.
  • Write the LP file and read it before you solve. It shows every row as the solver sees it, sorted by name.
  • CBC runs as a separate program, set up through a solver object. In PuLP 3.3 that object is PULP_CBC_CMD(msg=False, gapRel=0, ...); PuLP 4 renamed it COIN_CMD. Values are read from varValue and pulp.value(...).
  • The status says how CBC stopped; sol_status says whether the plan is proved. After one node, CBC reported Optimal with sol_status 2 and $23,944k, against $24,260k proved.
  • A port is proved by a test. Same value at gap 0, each plan keeping every rule, and the same rows by name: the PuLP port matched MathOpt on tiny ($2,473k) and small ($24,260k). In the runner, keep PuLP and MathOpt's HiGHS in separate processes.

Design Note: Write PuLP 3.3 Code That PuLP 4 Still Reads


The pinned PuLP 3.3.2 already accepts most of PuLP 4's forms: prob.add_variable instead of LpVariable, prob.constraints() as a list, get_constraint_by_name. Use them, and keep the version-specific parts in one place. In this module, that is the cbc() helper, the only line that names a solver class, and the status checks. Moving to PuLP 4 is then a change to two functions, not to every model. The test of the last section is what tells you the move worked.
