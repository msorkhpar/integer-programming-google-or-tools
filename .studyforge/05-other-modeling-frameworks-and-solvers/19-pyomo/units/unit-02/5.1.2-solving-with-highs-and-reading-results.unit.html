The Pyomo port of GridCap's five-year model (lesson Concrete models with indexed Sets, Params, Vars and Constraints) now runs every night, and the planners want each run to say plainly what happened: an optimal plan, a plan that is good but not proven best, or no plan at all and why. They also want to know what one more $k of budget would be worth. All of that is in what the solver hands back, if you know where to read it. This lesson solves the model with HiGHS through Pyomo, reads the results object field by field on four kinds of solve, and then reads duals, including the case where Pyomo has none to give. GridCap is fictional.

The Model

The model is lesson Concrete models with indexed Sets, Params, Vars and Constraints's, unchanged: $x_{i,t} \in \{0, 1\}$ for each allowed start $(i, t) \in S$, the once, alternative, precedence and per-year budget rows, and $\max \sum_{(i,t) \in S} \text{npv}_{i,t}\, x_{i,t}$. The Model of lesson Concrete models with indexed Sets, Params, Vars and Constraints states it in full. The last section of this lesson uses a second, smaller model, stated where it is used.

HiGHS Is Called Through One of Two Pyomo Interfaces

Pyomo does not solve anything itself; a solver interface writes the model in the form a solver reads, calls the solver, and brings the answer back. For HiGHS (the open-source solver section 4 used through MathOpt) Pyomo 6.10 has two interfaces, both talking to the highspy package in process:

  • the newer one, pyomo.contrib.solver, whose factory is imported from pyomo.contrib.solver.common.factory. Its solve returns a Results object with flat fields. The Pyomo documentation calls these interfaces a development preview whose API may still change.
  • the older one, pyo.SolverFactory("appsi_highs") (or "highs"), which returns the classic SolverResults object that most existing Pyomo code reads.

This lesson reads both. pyomo_timing.highs() returns the older one with a zero gap and is what the module's other programs use; the newer one has the clearer results, so it comes first:

Options go to solve as keywords: rel_gap, abs_gap, time_limit, threads and tee=True (which prints HiGHS's log) are common to the newer interface's solvers, and solver_options={...} passes HiGHS's own options by their HiGHS names.

Termination Condition and Solution Status Answer Different Questions

Four fields carry the answer:

  • termination_condition says why the solver stopped. convergenceCriteriaSatisfied means it met its stopping rule, which for a MILP is "the gap is within the tolerance". Other values say it hit a limit (maxTimeLimit, iterationLimit), proved something (provenInfeasible, unbounded), or could not tell (infeasibleOrUnbounded, error).
  • solution_status says what the solution in hand is: optimal, feasible (it satisfies every row, but nothing proves it is the best), infeasible, or noSolution.
  • incumbent_objective is the objective of the best plan found, the incumbent.
  • objective_bound is the best bound the solver proved: for this maximization, no plan can be worth more.

By default the newer interface loads the solution into the model, so the values sit on the variables: m.x["P031", 2028].value is 1.0 (P031 starts in 2028, as lesson Start-time variables x(i,t) and timing windows found), and pyo.value(m.value) evaluates the objective at those values. A program reads the plan from the model, never from the log.

The Incumbent and the Bound Give the Gap

rel_gap=0.0 asked for a proven optimum. Without it, HiGHS uses its own default tolerance:

Both runs report optimal, but the second one stopped with the bound at 24,262 and the incumbent at 24,260: HiGHS proved only that no plan is worth more than $2k above this one, a relative gap of 0.0082%, within its default tolerance, HiGHS's mip_rel_gap of 0.0001 (0.01%). Here the incumbent happens to be the true optimum (the first run proved it), but the default run did not prove it. "Optimal" from a MILP solver always means "optimal within the gap tolerance"; when two runs or two solvers must agree to the last $k, pass rel_gap=0.0 (section 3.4 covers gaps and the denominators solvers use).

An Infeasible Solve Raises Unless You Ask It to Return

Cut every budget to 0 and the must-do projects cannot be funded:

With its defaults the newer interface raises NoOptimalSolutionError whenever the result is not an optimal one, and it would also fail trying to load a solution that does not exist. A nightly job that must report rather than crash passes raise_exception_on_nonoptimal_result=False and load_solutions=False, then reads the fields: provenInfeasible, noSolution, no incumbent. The bound printed as inf means no bound: with no plan there is nothing to bound.

load_solutions=False has a cost when there is a plan: nothing is put on the variables. The results object still holds the plan, and results.solution_loader.load_vars() copies it onto the model's variables when the program has checked that it wants it:

So a job that never raises reads the fields first, and calls load_vars() only when the solution status is optimal or feasible; for noSolution there is nothing to load.

A MILP that can improve without limit is a different failure that looks similar. Give the model a new integer variable with no upper bound and a positive objective coefficient (a forgotten bound, the commonest cause):

HiGHS stops with infeasibleOrUnbounded: for this MILP it did not establish which of the two it is. A report that turns every non-optimal result into "infeasible" sends a planner looking for a conflict between rows that does not exist; the fix here is a bound on loan, not a relaxed budget. Solving the same model again is no fix either: the missing bound is in the model, not in the run. Map each termination condition to its own message, and keep infeasibleOrUnbounded separate.

Problem statement

A crew-rostering service runs a Pyomo model every night and posts one line about the result to the operations channel. Last week a roster nobody could meet crashed the job with an exception, and a model with a missing bound was posted as "infeasible", which sent a planner looking for a conflict that did not exist.

Write outcome(model, **options) in report.py. Solve model with HiGHS through Pyomo's newer interface (SolverFactory("highs") from pyomo.contrib.solver.common.factory), passing options on to solve, and never raise because of the result. Return a dict:

  • "status": the word WORDS gives the termination condition, or "stopped" for any condition WORDS does not list;
  • "objective": the incumbent's objective when the solve has a solution (its solution status is optimal or feasible), else None;
  • "plan": when there is a solution, {v.name: v.value} for every variable of the model after the solution is loaded; else {}.

WORDS and the imports are in the starter. The tests build small rostering models: one with an optimum, one no roster can meet, and one whose objective can improve forever. About twelve lines.

A Limit Leaves a Feasible Plan That Is Not Proven Optimal


On GridCap medium (400 projects, 887 start variables), stop HiGHS after its first node of branch-and-bound with its own option mip_max_nodes:






The termination condition says a limit stopped the search; the solution status says the plan in hand is feasible. The plan is loaded (here load_solutions was left on, and a feasible solution can be loaded) and it is a real plan, worth $226,745k, within $170k (0.075%) of the bound. Whether that is good enough is the planners' call, which is why a report should print the gap with every plan that is not proven optimal. A wall-clock time_limit stops the search the same way, with maxTimeLimit, but where it stops depends on the machine's speed; a node limit stops at the same place on every run, which is why this lesson uses one.


Older Code Reads a SolverResults Object


Most Pyomo code you inherit uses the older interface:






The same information sits in other places: results.solver.status (ok, warning, error), results.solver.termination_condition (optimal, infeasible, maxTimeLimit, ...), and the objective's two ends as results.problem.lower_bound and upper_bound, which for a maximization are the incumbent and the bound. pyo.check_optimal_termination(results) is the usual one-line test, and pyo.assert_optimal_termination(results) raises when it fails. The older interface also raises on an infeasible model unless solve gets load_solutions=False; lesson Piecewise functions and the IIS tools meets that when a Pyomo tool needs a solver that reports instead of raising.


A MILP Has No Duals; Fix the Integers and Re-Solve the LP


A dual value of a row (section 2.3) is how much the optimal objective changes per unit of the row's right side: the value of one more $k of budget. Pyomo imports duals through a Suffix, a component that holds one value per row (or per variable) and is filled by the solver interface:






The LP relaxation has duals: in it, one more $k of 2027 budget is worth $0.64k of NPV. But these are the relaxation's prices, for a plan with fractional projects that nobody will fund. The MILP has none at all: a MILP is not an LP, so the solver has no dual solution to hand over, and asking for one makes the solve raise. Pyomo does not quietly do anything else for you: it does not fix the integers and re-solve.


The usual way to price a MILP's plan is yours to write: solve the MILP, fix every integer variable at its value (v.fix(...) turns a variable into a constant for the solver), turn integrality off with the core.relax_integer_vars transformation, declare the Suffix and solve the LP that is left:






Every dual is 0, and that is the right answer for this model: once every $x_{i,t}$ is fixed, nothing is left to decide, so one more $k of budget changes nothing. The fixed-integer duals price the continuous part of a model, with the integer decisions held as they are. They say something only when continuous variables remain.


A model that has some: lesson Piecewise functions and the IIS tools's contractor model. A one-period selection on GridCap small funds projects within the capital budget, and its transmission projects need crew-months; GridCap's crews cover 40, and every month beyond is bought from contractors at tiered prices. Its formulation:


Sets. $P$ the projects; $T \subseteq P$ the transmission projects; $M \subseteq P$ the must-do projects. Parameters. $\text{value}_i$, $\text{capex}_i$ ($k); $\text{months}_i$, the crew-months project $i$ needs; $B = 38{,}390$, the capital budget ($k); $O = 40$, the crew-months GridCap's crews cover. Variables. $x_i \in \{0, 1\}$; $0 \le b \le 40$, contractor crew-months bought; $c \ge 0$, what they cost ($k).



The three tier rows say contractor months cost $30k each for the first 10, $45k for the next 10 and $70k beyond (lesson Piecewise functions and the IIS tools shows Pyomo writing exactly these rows). The same fix-and-re-solve:






With the funded projects held fixed, the plan buys 21 contractor months for $820k (10 at $30k, 10 at $45k, 1 at $70k), and the crews row's dual is 70: one more crew-month of GridCap's own saves one contractor month in the $70k tier. That is a price the planners can use. The budget's dual is 0 because, with every project fixed, no spending can change. Summary


  • HiGHS is called through one of two Pyomo interfaces. The newer pyomo.contrib.solver returns flat Results; the older SolverFactory("appsi_highs") returns a SolverResults.
  • Termination condition and solution status answer different questions. Why it stopped, and what the solution in hand is; a loaded solution is read from the model's variables.
  • The incumbent and the bound give the gap. HiGHS's default tolerance stopped with a bound of 24,262 over an incumbent of 24,260; rel_gap=0.0 proves the optimum.
  • An infeasible solve raises unless you ask it to return. raise_exception_on_nonoptimal_result=False and load_solutions=False; an unbounded MILP came back infeasibleOrUnbounded, not infeasible.
  • A limit leaves a feasible plan that is not proven optimal. iterationLimit with status feasible, and a gap to report.
  • Older code reads a SolverResults object. results.solver.termination_condition, results.problem bounds, check_optimal_termination.
  • A MILP has no duals; fix the integers and re-solve the LP. The Suffix raises on the MILP; the fixed-plan LP priced a contractor crew-month at $70k.

Design Note: Report Every Field, Not a Word


A nightly report that prints "optimal" or "failed" loses exactly what a planner needs: whether the plan is proven, how far from proven it is, and whether "failed" means a conflict between rows or a missing bound. Print the termination condition, the solution status, the incumbent and the bound, and the gap computed from them. Section 9 builds the full planner message on these fields.
