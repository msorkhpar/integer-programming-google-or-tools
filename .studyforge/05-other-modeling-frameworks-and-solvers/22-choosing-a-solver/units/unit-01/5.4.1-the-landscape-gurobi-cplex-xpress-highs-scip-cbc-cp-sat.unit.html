  15. The solver landscape

GridCap's architecture review meets before the planning service goes to production. One reviewer asks the question every optimization team hears sooner or later: "Why HiGHS? Everyone says Gurobi is the fastest. Shouldn't we just buy it?" Nobody in the room can answer with evidence. This module builds that evidence. It surveys the solvers (this lesson), measures them honestly (Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean), prices and packages them (License cost and fit for containers), and writes the recommendation the reviewer asked for (Writing a solver recommendation). GridCap is a fictional utility, and its numbers are teaching data.

This lesson maps the field: who makes each of the seven solvers in the title, what each one solves, how you reach it from Python, and which of them you can actually run in the course runner, the offline container every program in this course runs in (OR-Tools 9.15.6755). Lesson Versions and the backends that ship with it already listed the backends each OR-Tools API accepts and how each one refuses. This lesson does not repeat that list. It asks what a person choosing a solver needs to know next: which solvers give the same answer, which model features each accepts, and what each reports about the work it did.

Three terms used below. A MILP solver solves mixed-integer linear programs (lesson The problem zoo: LP, MILP, CP, NLP and how to pick) by branch and bound (lesson Branching on a fractional variable). A commercial solver is sold under a license that you pay for beyond a free size or time limit. An open-source solver publishes its code under a license that lets anyone use it without paying, a permissive license (Apache 2.0, MIT, EPL 2.0) being one that also allows use inside a closed commercial product.

A few facts from those pages matter for the choice and are easy to get wrong:

  • "Commercial" does not mean "unusable for free". Each commercial maker offers a free tier: the Gurobi pip package carries a size-limited license, the Xpress pip package runs under the free Community License, IBM's CPLEX Community Edition is free up to 1,000 variables and 1,000 constraints, and Gurobi and FICO both offer evaluation licenses with no size limit for a trial period. Lesson License cost and fit for containers measures GridCap's models against those limits.
  • The open-source licenses differ, but all four allow commercial use. SCIP moved from an academic license to Apache 2.0 with version 8.0.3; releases up to 8.0.2 are still under the old academic license, which matters if an old pin is lying around. CBC is maintained by a small group of volunteers under the non-profit COIN-OR Foundation, as its own README says.
  • CP-SAT is not a MILP solver in the usual sense. It is OR-Tools' constraint programming solver built on SAT techniques. It takes integer data only: lesson Versions and the backends that ship with it showed it refusing a 0.37 coefficient while the model is being built.

Public Benchmarks Compare Only Open-Source Solvers, Because the Commercial Three Withdrew

The reviewer's "everyone says Gurobi is fastest" usually traces back to public benchmarks. The best known are Hans Mittelmann's Benchmarks for Optimization Software at Arizona State University. Its front page, read on 2026-11-11, says that for many years the benchmarks included CPLEX, Gurobi and Xpress, and that this ended: after an action by Gurobi at the 2018 INFORMS Annual Meeting, IBM and FICO demanded that their results be removed, and Gurobi withdrew its own in August 2024.

So the current MILP benchmark (the page dated 28 Oct 2026: the 240 instances of the MIPLIB 2017 benchmark set, 2 hours each, 12 threads) lists COPT, SCIP, FiberSCIP, HiGHS (serial and parallel) and Optverse, and no Gurobi, CPLEX or Xpress. It reports how many of the 240 each solved, and a shifted geometric mean of run times scaled so that the best solver is 1 (lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean explains that mean). Two rows of its table:

The newer MIPFEAS benchmark on the same site (dated 30 Oct 2026), which measures how fast a solver finds good feasible plans rather than how fast it proves optimality, includes CPLEX, Xpress and COPT, but only as one "virtual mean commercial solver": the vendors agreed to aggregated results, not individual ones.

Three conclusions for the review:

  1. No current public benchmark ranks Gurobi, CPLEX and Xpress against each other or against HiGHS. A claim that one of them is fastest cannot be checked on these pages today.
  2. A public benchmark is someone else's instances on someone else's machine. MIPLIB 2017 is a standard test set built to compare MIP solvers, which is its strength; it is not GridCap. HiGHS solving 158 of 240 says little about whether it solves GridCap's portfolio in the nightly window.
  3. So the team benchmarks on its own models. That is lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean, and the free evaluation licenses above are how a commercial solver enters that benchmark without buying it first.

The Model

Every solver in this module solves the same model: GridCap's project-selection MILP from lesson Best bound, incumbent, absolute and relative gap, on a program slice of a GridCap medium portfolio. A slice keeps one program's projects (transmission, distribution or vegetation), so the instance set of lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean can have several models of different difficulty that share one formulation.

Sets. $P$ the projects of one program in the medium portfolio drawn with a given seed, keeping a child only when its parent is in the same program; $Y$ the plan's ten years; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups with at least two members in $P$; $C \subseteq P$ the child projects, each with its parent $p(c) \in P$.

Parameters. $v_i$, the NPV of project $i$ started at its earliest start ($k); $c_{i,y}$, what project $i$ spends in year $y$ when it starts at its earliest start ($k); $B_y$, the budget of year $y$ in the whole portfolio ($k); $S_y$ and $S^P_y$, the year-$y$ spend of all projects and of the slice's projects, each at earliest start ($k). The slice's budget is the whole budget scaled to the slice's share, rounded down to whole $k:

Variables. $x_i \in \{0, 1\}$ for every $i \in P$: 1 if project $i$ is in the plan.

In the Runner, Four Solvers Solve GridCap's Selection Model to the Same Optimum

landscape.py solves the transmission slice of the medium portfolio drawn with seed 2027 with each solver the runner has. Every run uses one thread, a random seed of 1 where the API takes one, and a relative gap target of 0, so each solver must prove optimality rather than stop at its own default target (lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean shows why that matters). run in solvers.py hides the three APIs behind one call:

Read it in three passes.

The answer is the same. All four prove the same optimum, NPV $145,971k, with the bound equal to it. On a pure-binary model with whole-number data, any correct solver must agree, and when one does not, the disagreement is the finding (the next section shows a solver that quietly answers a different model). Running a second solver on the same model is the cheapest correctness check a team has.

The work is reported in different units. HiGHS, SCIP and CBC report LP iterations (simplex pivots, the steps of the LP solves inside branch and bound) and nodes (subproblems of the search tree). CP-SAT reports deterministic time, its own estimate of the work done, computed from what the search did and meant to be close to a second (lesson Deterministic time, seeds and reproducible runs), and branches, its search decisions. These counts are deterministic measures: they depend only on the path the search took, so a run that repeats its path repeats them. The program prints which one the benchmark of lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean ranks each solver by:

The same name does not make the same unit. HiGHS's 14,289 LP iterations and SCIP's 5,783 come from different LP solvers (SCIP runs SoPlex, lesson Versions and the backends that ship with it) on different subproblems, after different presolves and cuts; a SCIP node and a CBC node are not the same amount of work either. Never compare one solver's count with another's. A count compares runs of one solver: two settings, two seeds, two versions. Lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean builds on exactly that line.

CBC takes no seed here. The linear solver wrapper's common parameters have no seed, and the way to pass a solver its own settings, SetSolverSpecificParametersAsString, is not supported for CBC: the program asks, and the call returns False (it also writes a warning saying so to the log):

CBC runs on one fixed path, so its benchmark has one run per instance where the others have three.

Model Features Decide Before Speed Does


Speed only matters among solvers that can solve your model at all. capabilities.py asks the three MathOpt solvers about three tiny models, each with one feature that GridCap's models may grow: a continuous variable (the carry-over $r_y$ of lesson Carry-over budgets and multi-year caps), a quadratic objective, and an indicator constraint, a row that applies only when a binary is 1 (lesson Indicator constraints). Each model's optimum is known by hand, so a wrong answer is visible:




Two kinds of "no" appear, and the second is the dangerous one:


  • A refusal. HiGHS and CP-SAT refuse the quadratic objective and the indicator constraint through MathOpt; mathopt.solve raises, and the reason sits on the exception's __context__ (lesson Common vs. solver-specific parameters, and what each solver rejects). A refusal costs you a failed run, never a wrong plan.
  • A quiet change. CP-SAT accepts the continuous model, reports OPTIMAL, and returns $a = 8$: it treated the continuous $a$ as an integer, and its "optimum" of 19.68 is below the true 20.3078 (lesson Switching solvers: HiGHS, SCIP, CP-SAT, GLOP, Gurobi met the same rounding on GridCap small). A benchmark that only checked statuses would score CP-SAT as correct here.

Problem statement


A team keeps a table of what each solver it may use does with each model feature, built the way lesson The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT built its feature probe. For each solver the table holds two sets of feature names: "refuses", the features the solver rejects with an error, and "alters", the features it accepts but silently changes (as CP-SAT does with continuous variables). Before benchmarking a new model, the team screens the candidates.


Write screen(features, table) in screen.py. features is the set of features the model uses. Return a dict with one verdict per solver in table:


  • "refuses <feature>" if the solver refuses any feature the model uses, naming the alphabetically first such feature;
  • otherwise "alters <feature>" if it alters any feature the model uses, again the alphabetically first;
  • otherwise "ok".


A refusal costs a failed run; a quiet change costs a wrong plan. Both rule a solver out, and the verdict names the kind, so a reader knows which one happened. About eight lines.

Summary


  • Seven solvers, two families. Gurobi, CPLEX and Xpress are commercial, each with a free size-limited tier and evaluation licenses; HiGHS (MIT), SCIP (Apache 2.0 since 8.0.3), CBC (EPL 2.0) and CP-SAT (Apache 2.0) are open source. Four of the seven solve in the course runner.
  • Public benchmarks compare only open-source solvers. Mittelmann's pages lost CPLEX and Xpress after 2018 and Gurobi in August 2024, so "X is fastest" cannot be checked there: benchmark your own models.
  • In the runner, four solvers find the same optimum on GridCap's selection model and report their work in different deterministic units, which compare runs of one solver, never two solvers.
  • Model features decide before speed does. SCIP alone takes quadratic objectives and indicator constraints through MathOpt; CP-SAT silently rounds continuous variables.

Design Note: Keep the Model Solver-Neutral as Long as You Can


Every feature you use that only one solver accepts narrows the choice to that solver, and every later argument about speed, license or price becomes moot. GridCap's formulation sticks to what all the candidates solve exactly: binaries, linear rows, and big-M or cumulative forms where an indicator would be shorter. When a feature is worth the lock-in, take it on purpose, write down which solvers it leaves, and keep a test that solves the model with the second-best one, so the day the license or the version changes you are not starting from zero.
