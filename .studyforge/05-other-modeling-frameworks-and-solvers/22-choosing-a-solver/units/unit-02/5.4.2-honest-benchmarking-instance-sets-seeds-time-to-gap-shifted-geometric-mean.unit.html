  18. Honest benchmarking

A GridCap engineer switches HiGHS's presolve off, solves the transmission slice of portfolio 1, and posts in the team channel: "Presolve off cuts the work by 32%: 2,301 LP iterations down to 1,563. Let's ship it." Both numbers are real, and the program below prints them. The conclusion is not: over the whole instance set and three seeds, the same switch makes no difference at all. This lesson is about the gap between those two statements. It builds the benchmark harness that lesson Writing a solver recommendation's recommendation rests on, one rule at a time: what to solve, how often, what to measure, how to stop, and how to average. GridCap is a fictional utility, and its numbers are teaching data.

A benchmark here is a set of solver runs designed to answer one comparison question ("which solver?", "which setting?") in a way someone else could repeat and check. Each rule below exists because breaking it has misled real benchmarks. The sources are the ones the optimization community itself uses: Hans Mittelmann's benchmark pages, the MIPLIB 2017 test set, and a FICO article on how MIP benchmarks get abused.

The Model

The model is lesson The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT's project-selection MILP on a program slice, unchanged: one binary $x_i$ per project, maximize $\sum_i v_i x_i$, subject to the rows $\text{must}_i$, $\text{alt}_g$, $\text{needs}_c$ and $\text{budget}_y$ with the slice's scaled budgets $b_y$. What varies in this lesson is never the model. It is the instance (which slice), the seed, the solver and its settings, and the stopping rule.

A Benchmark Is an Instance Set, Not an Instance

The engineer's claim rests on one model. One model tells you about that model. A solver choice or a setting will meet every model the service ever solves, so the benchmark needs a set of instances that stands in for them: the same formulation, a range of sizes and difficulties, chosen before anyone looks at the results.

GridCap's set has six instances: the transmission, distribution and vegetation slices of the medium portfolios drawn with seeds 2027 and 1. The harness prints them:

The sizes are alike; the difficulty is not. Lesson The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT's runs and the tables below show the vegetation slices solved at the root node with a hundred LP iterations or fewer, and the distribution slices taking tens of thousands. A set with only easy instances would rank solvers by their start-up cost; a set with only hard ones would hide what the service mostly solves. Keep both, and keep them all.

This is also what the MIP community's standard practice asks. MIPLIB 2017's benchmark set of 240 instances is the standard test set for comparing MIP solvers, and FICO's article MIP Benchmarking: Don't Abuse the Standards (O. Bastert, 2018) names the first abuse: picking a subset of a standard set that favours your solver, then making claims that read as if they held for the whole set. If a subset is reported at all, it is named, instance by instance, next to the full-set result. For a team benchmark the same rule reads: fix the instance set before the first run, and report on all of it.

Seeds Expose Performance Variability, So Each Instance Runs Under Several

A MILP solver makes many choices that have no right answer (which fractional variable to branch on when two score the same, which of two equal cuts to add first), and it breaks such ties with a pseudo-random number generator. Its random seed fixes that generator's sequence. MathOpt passes SolveParameters(random_seed=...) to the solver, with a valid range that depends on the solver (parameters.py); CP-SAT's random_seed reinitializes its generator at the start of each solve (sat_parameters.proto); SCIP's randomization/randomseedshift shifts all its random seeds. A different seed sends the search down a different path to the same optimum, and the work can differ a lot. That is performance variability: a change in work that comes from the path, not from the solver being better or worse.

The harness solves every instance with seeds 1, 2 and 3 and prints, per instance, the largest over the smallest work across the three seeds, in each solver's own unit:

CP-SAT's work on transmission-2027 varies by a factor of 4.11 between seeds; SCIP's on distribution-2027 by 2.02. A comparison that ran each solver once could report a factor of 2 or 4 that is nothing but the seed. So each (solver, instance) pair runs under several seeds, and each (instance, seed) pair counts as one observation. Mittelmann's MILP page adds variability another way: it preprocesses each instance by randomly perturbing the order of its rows and columns with SCIP, so no solver benefits from the order the file happened to be written in.

These ratios are unit-free, so unlike raw counts they can be set side by side across solvers: "how much does this solver's work depend on luck" is a fair question to ask of each. Lesson Writing a solver recommendation uses it.

The Shifted Geometric Mean Summarizes Ratios, and Its Shift Keeps Easy Instances From Dominating

After the runs, each solver has one number per observation, and the comparison needs one number per solver. Which average? sgm.py compares three on made-up times for two solvers, A and B, on the same five instances. A is twice as fast on the four easy ones, B twice as fast on the one hard one:

  • The arithmetic mean says B takes half as long (0.501). It is decided entirely by the one hard instance; the four others could change tenfold and the ratio would barely move. Run times of MILP solvers spread over orders of magnitude, so the arithmetic mean is a report on the slowest instance.
  • The geometric mean, the $n$-th root of the product, averages ratios: each instance counts the same however long it takes. It says B is 1.516 times slower, because B is twice as slow on four instances out of five. But those four are differences between a tenth of a second and two tenths, which no user would ever notice.
  • The shifted geometric mean adds a shift $s$ to every value before taking the geometric mean, and subtracts it after. Values much smaller than $s$ all look alike; values much larger than $s$ keep their ratios. With $s = 10$, B comes out ahead (0.851): the hard instance, where the difference is half an hour, counts; the easy ones, where it is fractions of a second, do not.

The form Mittelmann's pages define, for nonnegative values $v_1, \dots, v_n$ and a shift $s \ge 0$:

His benchmarks measure wall-clock seconds and use $s = 10$, then divide each solver's mean by the smallest one, so the best solver scores 1 (the "scaled" row of lesson The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT's table). The $\max(1, \cdot)$ keeps every logarithm nonnegative, so a run of a few milliseconds cannot drag the mean toward zero. That only works when the unit makes 1 small. Every $v_i + s$ below 1 counts as exactly 1, so values that small all tie, whatever their ratios. In seconds with $s = 10$ no value gets there. In a unit where typical values are fractions, such as 0.0001, most values fall under 1 and the mean measures the clamp instead of the solver. So pick a unit in which even the easiest instance costs well above 1, and a shift $s \ge 1$. In code:

The second half of sgm.py isolates the shift's job. Solvers C and D tie on four hard instances (100 s each); on four easy ones C takes 0.01 s and D 0.1 s:

The plain geometric mean calls D more than three times slower, over differences of nine hundredths of a second. With a shift of 10 the two are within 1%, which is the truth a user would see.

Three rules follow, and the program's first table shows why each matters:

  1. The shift is a choice, and it can flip the ranking. A beats B at shift 0 and shift 1 and loses at 10 and 100. Report the shift with every mean, and pick it before looking at the results.
  2. Choose the shift at the size of a difference nobody cares about. Mittelmann's 10 seconds fits runs with a two-hour limit. GridCap's harness measures work, not seconds, so it uses a shift of 100 LP iterations, or 100 millionths of a deterministic second for CP-SAT: about what the cheapest runs in the set cost (the harness prints them below). CP-SAT reports its deterministic time in seconds, and its cheapest run costs 0.0001 of one, so the harness counts that time in millionths (micro_det_time), where the same run costs 100. Counted in seconds with a shift of 0.01, every run under about one deterministic second would hit the $\max(1, \cdot)$ and tie.
  3. A run that fails still counts. Dropping it would reward a solver for failing on the hardest instances. Mittelmann counts every non-success as the time limit; the harness counts an unfinished run at a cap. The FICO article also warns against swapping in other scores: PAR10, which charges a failure ten times the limit, is a penalty score, so it cannot support "solver A is $k$ times faster than solver B".

Fix the Gap Target Before You Time Anything, Then Measure Time-to-Gap


"How long to solve it" sounds like one question, but a MILP solver stops when its relative gap, the distance between its best plan and its bound on all plans, divided by a reference value (lesson Best bound, incumbent, absolute and relative gap), falls below a target. Different targets are different questions. time_to_gap.py first solves the hardest instance with no target set, each solver on its own default:



All three say OPTIMAL, but HiGHS stopped with its bound $5k above its plan: its documented default mip_rel_gap is $10^{-4}$, so a gap of 0.0089% counts as optimal for HiGHS. SCIP's documented limits/gap default is 0, and it closed the gap. A benchmark run on defaults would time HiGHS to "within 0.01%" and SCIP to "exactly", and call both "time to optimal". Set one gap target for every solver: the harness passes a relative gap of 0 to each.


The gap's formula differs too: HiGHS divides by its primal bound, SCIP by the smaller of the two values (its limits/gap documentation and lesson Best bound, incumbent, absolute and relative gap), and CP-SAT's parameters proto defines its relative gap as $|O - B| / \max(1, |O|)$. So the harness never trusts a solver's own gap. It computes one gap for every run, $|\text{bound} - \text{objective}| / |\text{objective}|$, from the objective and bound each solver returns:



Then the measure that matters to a service. GridCap's planners accept a plan within 1% of optimal when the night is short. Time-to-gap is the work a solver needs to reach a given gap, and it can rank solvers differently from time to optimal. The program stops each solver at targets of 5%, 1%, 0.1% and 0 on the same instance, with seed 1:






What the table shows:


  • The last fraction of a percent costs most of the work. HiGHS reaches 1% with 6.1% of the LP iterations it needs to prove optimality, SCIP with 10.0%, CBC with 23.6%. Each had the optimal plan, $56,119k, well before it could prove it: at 0.1%, HiGHS, SCIP and CP-SAT already hold it, and the rest of the run only lowers the bound.
  • The shares rank the solvers differently at each target. At 1%, CP-SAT has spent 28.2% of its work to optimal and HiGHS 6.1%. A benchmark of time to optimality and a benchmark of time to 1% can recommend different solvers, so measure the one your service will run.
  • A solver checks its gap only at points of its own choosing, so it overshoots the target: asked for 5%, HiGHS stopped at 1.4999%. Report the gap reached, not the target asked.
  • A count can leave work out. CBC reports 0 LP iterations at the 5% stop, though it holds a bound of 56,899.2 that only an LP solve could give: its iteration count evidently does not include the root LP. One more reason a count compares runs of one solver only.


The same idea appears in public benchmarks. Mittelmann's MIPFEAS page ranks solvers by the primal integral: the gap between the incumbent and the optimum, integrated over the run and divided by its length, so a solver that finds good plans early scores well even if it proves nothing. Time-to-gap is its simplest form: one point on that curve.

Measure Deterministic Work Where You Can, and Mask Wall Time Where You Cannot


Wall-clock seconds are what users feel, and they are what Mittelmann's pages report, all measured on one machine. They are also different on every run: the same solve takes longer when another process is busy, when the CPU throttles, or when the machine is a different one. A course page has to print output that repeats, and so does a benchmark report that someone else is meant to check. So the harness follows one rule: measure each solver in a deterministic unit when it offers one, and treat wall time as a measurement whose method you publish but whose numbers you do not.


Each cell (solver, instance, seed) runs twice, and a cell counts as repeated only if both runs agree on the status, the objective and every work count. The summary for one solver:






How to read each column:


  • solved, repeats. Every run of every solver proved its optimum, the optima agree, and every cell repeated exactly, SCIP included. Lesson Indicator constraints vs. big-M saw SCIP node counts change between runs on its indicator model; on this set, with one thread and a fixed seed, they did not. The harness does not assume either: it checks, cell by cell, and a NO would stop a count from being quoted.
  • SGM, in each solver's own unit. These numbers repeat, so they can be quoted, tracked across versions, and put in a regression test. They are not a ranking: SCIP's 1,432 LP iterations against HiGHS's 3,066 do not mean SCIP does half the work (lesson The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT showed why units of different solvers do not compare). CBC has 6 runs because it takes no seed. CP-SAT's 56,578.77 is in millionths of a deterministic second, about 0.057 of one.
  • cheapest run. The least any run cost, in the unit the mean counts. Every one is at least 14, so with a shift of 100 every $v_i + s$ is well above 1 and the $\max(1, \cdot)$ never decides a value.
  • wall SGM. The program computes the shifted geometric mean of wall seconds (shift 1 s) for every solver, because across solvers that is the only common unit. It prints <masked>, because the numbers change on every run, and a page that printed them would be wrong the next time it ran. Run harness.py yourself and print s['wall_sgm'] to see them on your machine; run it twice to see them move.


So across solvers, an honest report states the wall-clock method (same machine, one thread, same instance set and seeds, same gap target, shift and cap) and gives its results with the date and machine, as Mittelmann's pages do. Within one solver, deterministic units make a comparison you can repeat exactly. The next section uses that.

Compare Settings of One Solver Pairwise, Over Every Seed


Back to the engineer's claim. Within one solver a deterministic unit is a fair yardstick: HiGHS's LP iterations with presolve on and off count the same steps. ab_test.py solves every instance with every seed both ways, and each (instance, seed) pair is one paired observation:






The engineer's row is there: transmission-1, seed 1, 2,301 down to 1,563 (0.68). On that instance the effect is real and steady across seeds. On transmission-2027, seed 3, the same switch multiplies the work by 2.66; on the other two seeds it does nothing. Averaged:



Someone who benchmarked with seed 2 only would report "presolve off saves 10%"; with seed 3, "presolve off costs 10%". Over all 18 pairs the ratio is 0.996, and presolve off wins 8 and loses 10: no effect worth a configuration change. The rule: compare settings pairwise on every instance and seed, report the ratio of shifted geometric means and the win/loss count, and treat any single pair as an anecdote.


Summary


  • A benchmark is an instance set, not an instance. Fix the set before the first run, mix easy and hard, and report on all of it (FICO: no cherry-picked subsets).
  • Seeds expose performance variability. On GridCap's set one seed against another changed the work by up to 4.11 times; run several seeds and treat each (instance, seed) as one observation.
  • The shifted geometric mean summarizes ratios, and its shift keeps easy instances from dominating. $\text{SGM}_s = \exp(\frac1n\sum \ln\max(1, v_i + s)) - s$; Mittelmann uses $s = 10$ s and counts failures at the limit. The shift can flip a ranking, so report it.
  • Fix the gap target, then measure time-to-gap. Defaults differ (HiGHS stops at $10^{-4}$), formulas differ, and the work to reach 1% can be a small share of the work to optimal.
  • Measure deterministic work where you can, and mask wall time where you cannot. Counts repeat and compare runs of one solver; wall time is the only cross-solver unit and is reported by method, date and machine.
  • Compare settings of one solver pairwise, over every seed. HiGHS presolve off: 0.996 over 18 pairs, though single seeds said 0.895 and 1.104.

Design Note: A Benchmark Is a Program, Kept With the Code


Everything that decides a benchmark's outcome (instances, seeds, threads, gap target, shift, cap, the solver versions) lives in harness.py and its pinned image, not in a slide. That makes the result something a reviewer can rerun, and something the team reruns when OR-Tools is upgraded: the deterministic SGMs then say exactly how much each solver's work changed, with no noise to argue about. Keep the harness in the repository next to the model, and keep its instance set under version control like test fixtures.
