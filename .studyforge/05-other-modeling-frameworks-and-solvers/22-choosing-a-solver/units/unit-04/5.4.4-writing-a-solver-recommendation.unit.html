The architecture review from lesson The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT is back on the calendar, and the reviewer's question has not changed: "Why HiGHS? Shouldn't we just buy Gurobi?" This time the team has a survey of the field (The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT), a benchmark harness whose numbers repeat (Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean), and the license and container facts with their dates (License cost and fit for containers). What is missing is the document that turns those into a decision someone can approve, challenge, or revisit in a year. This lesson writes it, as a program, recommend.py, so that every number in it comes from a run and the whole memo can be regenerated when anything changes. GridCap is a fictional utility.

A solver recommendation here is a short memo that answers one question ("which solver should this service use?") for one service, in a fixed order: the requirements, the candidates checked against them, the evidence, the decision with its fallback, and the conditions that would reopen it. The order matters more than the prose. A reviewer who disagrees should be able to point at the line they disagree with: a requirement, a fact, or a measurement.

The Model

The model is lesson The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT's project-selection MILP on GridCap's six program slices: one binary $x_i$ per project, maximize $\sum_i v_i x_i$, subject to the rows $\text{must}_i$, $\text{alt}_g$, $\text{needs}_c$ and $\text{budget}_y$. The service will also run the timing model of lesson Carry-over budgets and multi-year caps, which adds a continuous carry-over variable $r_y \ge 0$, the money a year leaves unspent and passes to the next. Lesson Carry-over budgets and multi-year caps is in section 6, later in the course; all this lesson needs from it is that $r_y$ is a continuous variable. That is why one requirement below is about continuous variables, though the benchmark's model has none.

Reading the "out" lines:

That is a cost and an architecture change, so the memo says so in the "revisit" section rather than pretending the option does not exist.
  • CPLEX and Xpress were not measured, and the memo says that, with the dated terms instead of a silence a reader might take for a verdict.

Notice what the filter did not use: speed. Three of five candidates are out before a single benchmark number is read.

The Evidence Is What the Harness Can Repeat, and Wall Time Enters Only as a Masked Check

The program then runs lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean's harness (six instances, seeds 1 to 3, one thread, gap target 0, every cell twice) and prints only what it can repeat:

The memo reports three kinds of evidence, chosen because each can be compared across solvers honestly:

  • Correctness: every solver found the same optimum on every instance. This is the cross-check of lesson The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT, run over the whole set.
  • Reliability: every run solved, and every cell repeated exactly. For a service whose plans are audited (lesson Deterministic time, seeds and reproducible runs), a solver that does not repeat would be a finding on its own.
  • Seed spread: on each instance, the largest work over the smallest across seeds, and here the worst instance. A ratio has no unit, so unlike raw counts it compares across solvers: it says how much a solver's effort on GridCap's models depends on luck. HiGHS's worst is 1.23, SCIP's 2.02, CP-SAT's 4.11.

And one thing it deliberately does not report: which solver is fastest. Across solvers the only common unit is wall time, which changes from run to run and machine to machine (lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean). The program computes each solver's shifted geometric mean of wall seconds and asks one coarse question: are they all within a factor of 3 of one another? It prints the answer, not the values:

On this set the answer is yes: speed does not separate the four, and a memo that ranked them by a few hundredths of a second would be ranking noise. The factor is wide on purpose. A claim like "X is faster" belongs in a recommendation only when it holds on every repetition of the benchmark, by a margin larger than the run-to-run noise, with the machine and date stated, as Mittelmann's pages do.

    When may a memo say 'faster'?

    • correctness, reliability and seed spread as evidence, wall time only as a coarse masked check

    Not startedPassed

Problem statement

A team ran its benchmark harness several times on the same machine and kept, for each repetition, each solver's shifted geometric mean of wall seconds. The numbers move from run to run, so the team adopts a rule for its recommendation memo: a solver may be called faster only if it is ahead by at least a stated factor on every repetition.

Write faster(a, b, factor) in claim.py. a[k] and b[k] are the two solvers' wall-clock means in repetition k (positive numbers, same length). Return "a" if b[k] / a[k] >= factor for every k, "b" if a[k] / b[k] >= factor for every k, and "neither" otherwise. The factor is greater than 1.

Name a Default, a Fallback, and What Would Change the Decision


Among the candidates that passed every requirement, solved every run and repeated, the program picks the one whose work depends least on the seed, and keeps the others as fallbacks:






Three parts, each with a job:


  1. The default, with its reason in one sentence, each clause backed by a line above it. The reason is not "HiGHS is the best solver"; it is that HiGHS met the requirements and was the most predictable on these models. A reviewer can check every word.
  2. The fallback, chosen so that switching costs nothing: SCIP is one SolverType away, and it covers the features HiGHS refuses. If the default ever fails in production, or the model grows an indicator constraint, the team already knows where to go and has measured it.
  3. The conditions that reopen the decision. This is the real answer to "shouldn't we just buy Gurobi?": not now, and here is exactly when. GridCap large (10,000 projects) is beyond every free tier (lesson License cost and fit for containers) and was not in this benchmark; if it misses its gap target in the nightly window, the team requests a commercial evaluation license, adds that solver to the harness, prices the token server or the internet route, and reruns this program. An OR-Tools upgrade reruns it too, because every solver in the runner is a bundled build.


Two habits keep the memo honest after it is approved. Every figure that can change carries its date: the commercial terms say "as of the pages opened on 2026-11-11", and a reader in a year knows to check. The memo is regenerated, not edited: recommend.py lives next to the harness, so the next review starts from a fresh run instead of last year's numbers.

Problem statement


A team at a rail operator is writing the recommendation for its crew-rostering service. It has already filtered the candidates by the service's hard requirements, and it has run its benchmark harness. Now it needs the rule that turns these into a decision, written down as code so the memo can be regenerated.


Write pick(passing, evidence) in pick.py. passing lists the solvers that met every requirement. evidence[solver] is a dict with "solved" and "runs" (counts), "repeat" (whether every cell repeated) and "spread" (the worst seed spread, a ratio of at least 1). A finalist passed the requirements, solved every run and repeated. A solver in passing may be missing from evidence: it was never measured, so it is not a finalist. Rank the finalists by spread, lowest first, breaking ties by name in alphabetical order. Return (default, fallback): the first and second finalists, with None for any that does not exist.

Summary


  • Start from the requirements, and make each one a yes-or-no test with a fact behind it; the filter ruled out CP-SAT, CBC and Gurobi before any benchmark number was read.
  • The evidence is what the harness can repeat: correctness, reliability and the unit-free seed spread. Wall time enters only as a masked check, within a factor of 3 here, so speed separated nothing.
  • Name a default, a fallback, and what would change the decision. HiGHS through MathOpt, SCIP one enum away, and a revisit when GridCap large misses its window, the network may reach a license service, or OR-Tools is upgraded.

Design Note: A Recommendation Is a Program, Not a Slide


A slide records a decision; a program records how it was reached. The prose around it (who asked, what was decided in the meeting) goes in the team's decision log, with a link to the commit of the program that produced it.
