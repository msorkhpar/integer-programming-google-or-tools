  16. Gurobi licenses

GridCap's scenario service (section 12) will run its solves as container jobs on AWS. The partner from lesson Models, attributes and the matrix API suggests Gurobi for them, and the team lead asks three plain questions before anyone writes a line: which license would those containers use, what happens on a laptop or a build server that has none, and how do we keep license details out of logs and pages? Gurobi is commercial software. Unlike HiGHS, SCIP and CP-SAT, which ship inside OR-Tools, it runs only with a license, and what that license allows (model size, machines, containers, who may use it) decides where a Gurobi model can run at all. GridCap is a fictional utility.

To run this module's programs you need your own Gurobi license. The course does not supply one, and no license is stored in the course's images, files or pages. The last section shows how to give the course's runner yours. The practices of this module need none: they work with gurobipy's constants and with plain data.

gurobipy Needs a License Before It Builds Anything

A Gurobi environment reads the license when it starts (lesson Models, attributes and the matrix API), and every model lives in an environment, so without a license nothing can be built. license_errors.py shows what a program then sees. It runs each case in a child process with its own environment variables, so the result does not depend on the license of the machine it runs on: first with no license anywhere, then with GRB_LICENSE_FILE pointing at a file that does not exist.

Both are error 10009, a license error, raised by start() before any model exists. The first message names the machine: the user running the program, the host's name, a host id and the number of cores. The output above is masked: mask (next-but-one section) replaced each of those with a placeholder before printing. The raw message carries real values, and a program that prints it, logs it or returns it from an API hands them to whoever reads that output. Every Gurobi message in this course goes through mask first.

Where Gurobi looks, according to its support article on placing the license file: on Linux, in /opt/gurobi and in the user's home directory; on Windows C:\gurobi, on macOS /Library/gurobi, each also with the home directory. A file anywhere else is found only through the environment variable GRB_LICENSE_FILE, which must name the file itself, not its folder. The second case shows the message when the variable names a file that is not there: it names the file Gurobi could not open.

The first row is what pip install gurobipy gives on your own computer. Its limits are checked when the model is solved, as the next section shows.

The Web License Service is the license for machines that come and go. Instead of a file tied to one machine, a program holds an API key, three values from Gurobi's Web License Manager: an access id (WLSAccessID), a secret (WLSSecret) and a license id (LicenseID, a number). When the environment starts, Gurobi exchanges them over the Internet for a short-lived token (the WLSTokenDuration parameter caps its life at 5 to 60 minutes) and renews it as needed. A container on AWS Batch or Fargate is exactly such a machine, so running there does not remove the licensing question: it answers it with WLS (or a license server the containers can reach), and the container needs outbound Internet access to Gurobi's servers.

The Size-Limited License Stops at 2,000 Variables or 2,000 Rows

The course's runner, where this page's outputs were produced, has the size-limited license. Its limit, measured at both edges and on three GridCap timing models:

The limits are exactly 2,000: one more variable, or one more row, and optimize() raises GurobiError 10010. Building the model was allowed; the check came at the solve. GridCap small and medium fit, and every model in this module is small. GridCap large, 10,000 projects, is ten times over, and with this license it cannot be solved at all; with an academic or commercial license the same program solves it (within the 60-second time limit try_solve sets). A team planning on the size-limited license should count before it builds: NumVars and NumConstrs after an update() tell, without solving, whether a model will be refused.

A Container Gets Its License at Run Time, Never in the Image

A container image is copied, cached and shared. A license file or WLS key built into it goes everywhere the image goes, and the Docker Hub page for Gurobi's own image advises against baking the license into an image. The rule is the same for both kinds of license: the image holds code, and the license arrives when the container starts.

  • A license file is mounted read-only into the container and named by GRB_LICENSE_FILE (Gurobi's Kubernetes example mounts it from a secret and sets that variable).
  • A WLS key is passed in as environment variables or secrets, and the program hands it to gp.Env(params=...). Gurobi's support article on WLS shows the three parameters given that way, with LICENSEID as a number and the other two as strings.

licensed_env.py is one function for both. It reads the process's environment variables (here named after Gurobi's parameters) and returns the parameters for gp.Env:

With no WLS variables it adds nothing, and Gurobi finds the license file itself through GRB_LICENSE_FILE or its default places. A half-given key is refused before Gurobi sees it, with a message that names the missing variables and none of the values. OutputFlag=0 goes in the same dictionary, so the banner is never printed. The demo uses placeholder values, all zeros and ones, and starts no environment, so it contacts nothing:

Problem statement

A logistics company runs Gurobi jobs in containers. Before a job starts Gurobi, it must decide which license it will use and log that decision, without logging any secret. Write license_plan(environ, exists): environ is a dict of the job's environment variables, and exists(path) returns whether a file is there (passed in, so the tests need no files). Return a pair (kind, detail), following these rules in order:

  1. If all three of WLSACCESSID, WLSSECRET and LICENSEID are set (non-empty), return ("wls", {"WLSACCESSID": ..., "WLSSECRET": ..., "LICENSEID": <int>}): Gurobi's LICENSEID parameter is a number.
  2. If one or two of them are set, return ("error", "incomplete WLS key: <missing names> not set"), naming the missing variables in the order above, joined by ", ". Never put a value in the message.
  3. If GRB_LICENSE_FILE is set, return ("file", <that path>) if the file exists, otherwise ("error", "license file not found: <that path>"). Gurobi does not look elsewhere when the variable names a missing file, so neither does this function.
  4. Otherwise try Gurobi's default places on Linux, in this order: /opt/gurobi/gurobi.lic, then <HOME>/gurobi.lic with HOME from environ (skip it if HOME is not set). Return ("file", path) for the first that exists.
  5. If none does, return ("error", "no license").

No Gurobi license is needed. About twenty lines.

Running This Module's Programs in the Course


The course's runner image carries gurobipy 13.0.3 with its bundled license file removed: no license is baked into any image. To run the programs of this module on the course site, give the runner your own license file:


  1. Get a license file: the size-limited file that pip install gurobipy puts inside the installed package (gurobipy/.libs/gurobi.lic), or one your organization provides for containers.
  2. Set GUROBI_LICENSE_FILE in the course's course.env to that file's path on your computer.
  3. The runner then mounts it read-only at /licenses/gurobi.lic and sets GRB_LICENSE_FILE to that path. The file is never copied into the image or the course's folder.


Without it, every program of this module stops at quiet_env() with error 10009, as in the first section, and the module's tests skip themselves with that reason. The size-limited license runs every program here; the lesson outputs were produced with it. It is also, in practice, the license the course's runner can use: an academic named-user license does not work in containers (the academic licensing article says so), and a WLS license needs the container to reach Gurobi's servers, which the runner, offline by design, cannot do. Academic and WLS licenses are for your own machine or your own deployments, as the sections above describe.


What about MathOpt with SolverType.GUROBI? In the course's runner it fails (lesson Switching solvers: HiGHS, SCIP, CP-SAT, GLOP, Gurobi): OR-Tools 9.15 cannot load the Gurobi 13 library that comes with gurobipy. A license does not change that; the version mismatch does. That is why this module teaches Gurobi through gurobipy.


Summary


  • gurobipy needs a license before it builds anything. Env.start() raises GurobiError 10009 without one; the message names the user and host, so it is masked before it is shown. GRB_LICENSE_FILE names the file; otherwise Gurobi looks in its default places.
  • Four kinds of license, and where each can run. Size-limited (pip), academic named-user (one machine, no containers), academic WLS (containers, online), commercial.
  • The size-limited license stops at 2,000 variables or 2,000 rows, at optimize(), with error 10010. GridCap small and medium fit; large does not.
  • A container gets its license at run time, never in the image: a file mounted read-only, or a WLS key passed to gp.Env(params=...), logged only redacted.
  • Gurobi's messages can name you; mask them: users, hosts, ids, addresses, before anything is printed or stored.

Design Note: License Is Configuration, Not Code


Every program in this module gets its environment from one place (quiet_env, or open_env in a service), and nothing else in the code knows which license is in use. Swapping the size-limited file for an academic WLS key, or a laptop's file for a container's secret, changes the deployment, never the model. The same place is where the banner is silenced and the messages are masked, so the rule "no license data in any output" is kept by construction, not by remembering it in every program.
