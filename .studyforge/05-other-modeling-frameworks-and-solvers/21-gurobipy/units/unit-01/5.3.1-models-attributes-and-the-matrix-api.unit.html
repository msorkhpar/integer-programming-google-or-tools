  17. gurobipy models and attributes

GridCap's planning team runs its selection model on HiGHS through MathOpt. A new partner, a consulting firm, sends its models as gurobipy code and asks whether GridCap's numbers can be reproduced in Gurobi. To answer, someone on the team has to read and write gurobipy: build the same model, solve it, and read back the same plan. This lesson ports GridCap small's selection model (lesson Model, variables, constraints, objective) and its timing model (lesson Start-time variables x(i,t) and timing windows) to gurobipy, and checks that Gurobi finds the optimum MathOpt found. GridCap is a fictional utility, and its numbers are teaching data.

gurobipy is the Python interface of Gurobi, a commercial MIP and LP solver. Unlike MathOpt, it is not a layer over several solvers: a gurobipy model is always solved by Gurobi. That makes it a second, independent way to write the same model, and the API most Gurobi users meet first. Every gurobipy program needs a Gurobi license to start; lesson Licenses: size-limited, academic, and cloud/container (WLS) explains the kinds of license and how to give the course's runner yours. The course runner has a size-limited license, the one the outputs below come from, and every model in this module stays within its 2,000 variables and 2,000 rows.

Can MathOpt hand a model to Gurobi instead? SolverType.GUROBI exists, but in the course's runner it fails: OR-Tools 9.15 cannot load the Gurobi 13 library that comes with gurobipy, and the call raises RuntimeError: bad_function_call (lesson Switching solvers: HiGHS, SCIP, CP-SAT, GLOP, Gurobi shows the attempt). So this module teaches Gurobi through gurobipy itself.

The Model

The selection model of lesson Model, variables, constraints, objective on GridCap small: fund projects, each at its earliest start, for the most NPV within each year's budget.

Sets. $P$ the candidate projects; $Y$ the plan's years (2027–2031); $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$.

Parameters. $v_i$, the NPV of project $i$ at its earliest start ($k); $c_{i,y}$, what it spends in year $y$ when it starts at its earliest start ($k); $B_y$, the budget of year $y$ ($k).

Variables. $x_i \in \{0, 1\}$ for every $i \in P$: 1 if project $i$ is funded.

An Environment Holds the License, and a Quiet One Prints Nothing

Everything in gurobipy lives in an environment (gp.Env): it reads the license, holds parameters, and every model is created inside one. If you never create one, gurobipy makes a default environment the first time you build a model, and that one prints a license banner as it starts. The banner names the license, and it can name the license holder; it does not belong in a program's output, a log a service keeps, or a page like this one.

The Gurobi documentation's pattern for settings that must be in place before the license is read is an empty environment: create it with empty=True, set parameters, then start() it. Setting OutputFlag to 0 there turns off all output, the banner included. Every program in this module gets its environment from this function in grb.py:

start() is where a missing license shows up, as a GurobiError (lesson Licenses: size-limited, academic, and cloud/container (WLS) shows the messages). A model is then made with gp.Model(name, env=env), and inherits the environment's parameters: no solver log either.

A first model, small enough to check by hand: three projects and one budget of $1,000k.

$\max\; 420 f + 250 b + 190 t$ subject to $600 f + 300 b + 250 t \le 1000$ (budget), with $f, b, t \in \{0, 1\}$.

The four calls map one to one onto MathOpt's:

gurobipyMathOpt (lesson Model, variables, constraints, objective)
m.addVar(lb=0.0, ub=GRB.INFINITY, obj=0.0, vtype=GRB.CONTINUOUS, name="")model.add_variable(lb=..., ub=..., is_integer=..., name=...)
vtype=GRB.BINARY (or "B"); GRB.INTEGER ("I")add_binary_variable, add_integer_variable

m.setObjective(expr, GRB.MAXIMIZE)model.maximize(expr)
m.optimize()mathopt.solve(model, solver_type)

Three differences matter in practice:

  • A variable's default lower bound is 0, not $-\infty$. addVar() with no arguments is a continuous variable in $[0, \infty)$. A free variable needs lb=-GRB.INFINITY.
  • Changes are lazy. gurobipy queues every addition and change and applies them at the next update(), optimize() or write(). Before the update the model above still reported 0 variables and 0 rows, and a new variable's attributes cannot be read yet. Building a model and solving it never needs an explicit update(), because optimize() applies the queue; you call it only to read something back before solving.
  • optimize() returns nothing. The result is stored in the model, and you read it from there: m.Status, m.ObjVal, each variable's X. There is no separate result object as in MathOpt.

The plan is right: feeder and breaker cost 900 and earn 670; any plan with trim either leaves out feeder (at most 440) or breaks the budget.

Three gurobipy tools appear here:

  • addVars(keys, ...) adds one variable per key and returns a tupledict, a dictionary from key to variable with extra methods (the last section uses them). Its names are the prefix and the key in brackets: x[P001].
  • gp.quicksum(...) adds up terms into a linear expression (LinExpr), as Python's sum does; it is gurobipy's own summation function, and the form gurobipy code usually uses.

Everything You Read or Write Is an Attribute

A gurobipy model reports everything through attributes: named values held by the model, by each variable or by each row. m.NumVars is a model attribute, x["P001"].X a variable attribute, budget[2030].Slack a row attribute. Some can be written (bounds, right-hand sides, objective coefficients, names); others are results, filled by optimize(). Here is GridCap small's model read through its attributes:

  • Before a solve there is no X, and reading it raises AttributeError with the message "Index out of range for attribute 'X'": the attribute exists, but the model holds no solution to index into.
  • Model attributes describe the model (NumVars, NumConstrs, NumBinVars, NumNZs, the number of nonzero coefficients) and the solve (Status, ObjVal, ObjBound the best bound, MIPGap the gap reached, SolCount the number of plans Gurobi kept).
  • A variable's attributes are its data (LB, UB, VType, Obj its objective coefficient, VarName) and its value (X). A row's are ConstrName, Sense (<, > or =), RHS, and Slack, the right-hand side minus the row's value: 2030's budget has $70k left.

The Matrix API Takes the Model as Arrays


The model so far was written row by row, the way the formulation reads. The same model is also a matrix: one column per variable, one row per constraint. In the matrix form of lesson Standard form, slack and surplus, it is



where $(A_{\text{budget}})_{y,i} = c_{i,y}$, each row of $A_{\text{alt}}$ has a 1 for every member of one group, each row of $A_{\text{needs}}$ has $+1$ for a child and $-1$ for its parent ($x_c - x_{p(c)} \le 0$), and $\ell_i = 1$ for a must-do project, 0 otherwise. The must-do rows have become lower bounds: $x_i = 1$ for a binary is the same as $1 \le x_i \le 1$.


gurobipy's matrix API takes exactly this. addMVar(n, ...) adds a vector of $n$ variables (an MVar, which behaves like a NumPy array), and addMConstr(A, x, sense, b) adds the rows $A x \;\text{sense}\; b$ for a NumPy array or SciPy sparse matrix $A$. The data are built as arrays first, here as SciPy sparse matrices, which store only the nonzeros:








The same optimum, 22,532, with 9 rows instead of 13: the 4 must-do rows are now bounds. c @ xv is the objective $c^\top x$, written with NumPy's matrix product, and xv.X reads the whole plan as a NumPy array. Building rows from arrays skips writing one Python expression per row; lesson Vectorized model building from DataFrames measures what that saves when a model is built from data that are already in arrays.


The other direction is getA(): any model, however it was built, hands back its constraint matrix as a SciPy sparse matrix, one row per constraint and one column per variable, in the order the model holds them (each row's position is its index attribute):






The row-by-row model's budget rows are exactly the spend matrix built for the matrix model. getA() is how to check a builder: build the model two ways and compare matrices, or read the matrix to count nonzeros, find empty rows, or look at the range of coefficients (lesson Coefficient ranges and scaling).

Summary


  • An environment holds the license, and a quiet one prints nothing. gp.Env(empty=True), setParam("OutputFlag", 0), start(): no banner, no log, and a GurobiError at start() if there is no license.
  • A model is variables, constraints and an objective, added lazily. addVar, addConstr, setObjective, optimize; changes apply at the next update() or optimize(); variables default to $[0, \infty)$.
  • GridCap's selection model ports row for row, with addVars, quicksum and addConstrs, and Gurobi finds MathOpt's optimum, 22,532.
  • Everything you read or write is an attribute. m.Status, m.ObjVal, v.X, c.Slack; getAttr for many at once; assignment (v.UB = 0, c.RHS += 1000) edits the model for the next solve. A limit status needs SolCount to say whether there is a plan.
  • The matrix API takes the model as arrays. addMVar and addMConstr(A, x, sense, b); getA() reads any model's matrix back.
  • tupledict wildcards write sums over indices. x.sum("P017", "*") and x.select(...); the timing model's optimum is 24,260, as in MathOpt.
