Finance's scenario from lesson Callbacks and compute_infeasible_subsystem is back: the board promises P032 for 2027, and the 2030 and 2031 budgets are capped at $5,000k each. The model says INFEASIBLE. In lesson Callbacks and compute_infeasible_subsystem MathOpt could not explain it, because only Gurobi computes an infeasible subsystem through MathOpt and Gurobi does not load there; the team found the conflict with a hand-written deletion filter. Now they have gurobipy, and finance has two more questions: if the scenario cannot hold, what is the smallest change that makes it hold, and, once it does, can the plan put NPV first and spending second? This lesson answers all three with Gurobi's own tools, computeIIS, feasRelax and setObjectiveN, and adds a fourth, addGenConstrPWL, for the piecewise-linear curves of lesson The lambda (SOS2-style) formulation built from binaries. GridCap is a fictional utility, and its numbers are teaching data.

Each tool is checked against the course's MathOpt result for the same question: the deletion filter (lesson Callbacks and compute_infeasible_subsystem), solving objectives in order (lesson Prioritized objectives with add_auxiliary_objective), and the lambda form of a curve (lesson The lambda (SOS2-style) formulation built from binaries). The Model

The timing model of lesson Models, attributes and the matrix API (build_plan), with the scenario's three changes marked.

Sets. $P$ the projects; $Y$ the years 2027–2031; $T_i \subseteq Y$ the start years of project $i$; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C$ the child projects, with parent $p(c)$ and lag $L_c$.

Parameters. $\text{npv}_{i,t}$ ($k); $c_{i,k}$, project $i$'s spend in its $k$-th year of work ($k); $B_y$, the budget ($k), with $B_{2030} = B_{2031} = 5{,}000$ in the scenario $\leftarrow$ scenario.

Variables. $x_{i,t} \in \{0, 1\}$ for $i \in P$, $t \in T_i$, and $x_{\text{P032},2027} \ge 1$, the board's promise, as a lower bound $\leftarrow$ scenario.

Objective. $\max \sum_{i \in P} \sum_{t \in T_i} \text{npv}_{i,t}\, x_{i,t}$.

Constraints, with $\text{spend}_y = \sum_{i \in P} \sum_{t \in T_i,\, t \le y} c_{i,\,y-t}\, x_{i,t}$:

The code names the rows once_P001, must_P017, alt_G001, after_P007_2029 and budget_2030, the names of lesson Callbacks and compute_infeasible_subsystem's MathOpt model. The later sections change the objective, and state each change where they make it.

computeIIS Names the Rows That Clash

An irreducible infeasible subsystem (IIS) is a set of constraints and bounds that cannot all hold, and from which no member can be dropped without the rest becoming feasible (lesson Callbacks and compute_infeasible_subsystem). In gurobipy it is one call on an infeasible model, and the answer comes back as attributes:

The same three rows the deletion filter found in lesson Callbacks and compute_infeasible_subsystem, and the module's tests check that the two agree. P017 is a must-do project that can start only in 2030 or 2031 and spends $5,310k in its start year; both years are capped at $5,000k. The board's promise of P032 is not part of the conflict.

What computeIIS sets, as the Python reference lists them:

AttributeOf1 means
IISConstrlinear rowthe row is in the IIS
IISLB, IISUBvariableits lower / upper bound is in the IIS
IISGenConstr, IISQConstr, IISSOSgeneral, quadratic, SOS constraintthat constraint is in the IIS
IISMinimalmodel1 if the subsystem is irreducible; 0 if the search stopped early

Three details from the documentation decide how to read the result:

  • An IIS is one explanation, not the smallest one. A model can hold several conflicts; the reference says the IIS found is not necessarily the smallest. Fix one, solve again, and another may appear: Gurobi's workforce2 example repeats IIS-and-remove until the model is feasible.
  • It can stop early. TimeLimit and the other limits apply to computeIIS; it then returns the smallest infeasible subsystem found so far, and IISMinimal is 0. On a MIP the computation "can be quite expensive", in the words of the infeasibility page.
  • Binary bounds never take part. The variable attribute page says so for IISLB and IISUB. The promise here is a lower bound on a binary, so Gurobi could not have named it even if it mattered. A rule a planner may need to see in an IIS belongs in a named row (m.addConstr(x == 1, name="promise_P032")), not in a binary's bound. The IIS...Force attributes (IISConstrForce = 1 forces a row in, 0 keeps it out) steer the search when some rules are known to be fixed.

The IIS can also be written to a file. m.write(path) with the extension .ilp writes only the subsystem, in Gurobi's LP text format:

The program elides the continuation lines of the two budget sums and the list of binaries; the file holds them in full, with every variable that appears in the three rows. An .ilp file is what to attach to a ticket: it is small, it is readable, and it holds no row outside the conflict.

Problem statement

A hospital's nurse-rostering model came back INFEASIBLE, and computeIIS() has run. The team has copied what it set into plain data (so the report can be written and tested anywhere, even without a license):

  • status: the model's Status code;
  • rows: one dict per linear row, {"name": ConstrName, "sense": Sense, "rhs": RHS, "iis": IISConstr}, where Sense is "<", ">" or "=" as gurobipy reports it;
  • bounds: one dict per variable, {"name": VarName, "lb": LB, "ub": UB, "iis_lb": IISLB, "iis_ub": IISUB}.

Write iis_report(status, rows, bounds), which returns sorted lines for a planner:

In the IISLine
a row with iis 1"<name> <= <rhs>", "<name> >= <rhs>" or "<name> == <rhs>", by its sense
a variable with iis_lb 1"<name> >= <lb>"
a variable with iis_ub 1"<name> <= <ub>"

Numbers are written with :g (40.0 prints as 40). Only what the IIS marks is listed. If status is not GRB.INFEASIBLE (from gurobipy import GRB), there is no IIS to read, and the function returns an empty list. About twelve lines.

Problem statement


A freight planner's tool can say whether a set of business rules can hold together, but it cannot compute an IIS. Write the deletion filter (lesson Callbacks and compute_infeasible_subsystem) that turns that yes/no check into an irreducible conflict, the same kind of answer computeIIS gives.


deletion_filter(rules, feasible) takes a list of rule names and a function feasible(subset) that returns True when the rules in subset (a set of names) can all hold. Then:


  1. If feasible(set(rules)), there is no conflict: return [].
  2. Otherwise keep a working set, starting with every rule. Go through the rules in the given order: remove the rule from the working set, and ask feasible about what is left. If it is still infeasible, the rule was not needed: leave it out. If it became feasible, the rule is part of the conflict: put it back.
  3. Return the rules left in the working set, in the given order.


Each test runs on the working set as it stands, without the rules already left out; that is what makes the result irreducible. No Gurobi license is needed. About ten lines.

feasRelax Repairs the Model, and the Penalties Decide What Gives


An IIS says which rules clash. Finance's second question is how little must change. A feasibility relaxation answers it: let some rows or bounds be broken, pay a penalty for each unit broken, and solve for the plan with the least penalty. Gurobi builds it for you with feasRelax (and a short form, feasRelaxS): it adds artificial variables that measure each violation, replaces the objective by their weighted total, and optimize() then finds the cheapest repair. Lesson Elastic constraints and feasibility relaxation writes such elastic rows by hand; here Gurobi writes them.


The infeasibility page states two rules first. feasRelax changes the model it is called on, so each case below builds the scenario afresh (scenario(), the timing model with the scenario's three changes) and relaxes a copy of it, pl.model.copy(): no relaxation is stacked on an earlier one. And the cost of a repair is yours to define, in three parts:


ArgumentMeaning
relaxobjtype0: minimize the weighted sum of violations; 1: the weighted sum of their squares; 2: the weighted number of rows and bounds violated
minrelaxFalse: the result is the least-violation plan; True: among least-violation plans, the best for the original objective
what may give, at what pricefeasRelaxS(type, minrelax, vrelax, crelax): every bound (vrelax) and/or every row (crelax) at penalty 1; feasRelax(type, minrelax, vars, lbpen, ubpen, constrs, rhspen): only the listed variables and rows, each with its own penalty


First, every row may give, at 1 per unit:






changes lists the artificial variables that took a value. The cheapest repair is to break must_P017 by 1: do not fund the must-do project. One unit of violation on a row measured in "projects" is cheaper than 310 units on a row measured in $k, so with equal penalties the relaxation drops the rule a regulator imposed. That is the arithmetic of unit penalties, not advice. The penalties must say what may give.


Finance's answer is that budgets may move and the must-do rule may not. So only the budget rows are offered, at 1 per $k:






The smallest budget repair is $310k more in 2030, exactly P017's $5,310k less the $5,000k cap. The names follow a pattern the infeasibility page documents: ArtP_<row> and ArtN_<row> are a row's positive and negative artificial variables, ArtL_<var> and ArtU_<var> a variable's lower- and upper-bound violations. Each enters its row with coefficient $+1$ or $-1$. The same program reads the budget_2030 row of that relaxed copy:






So the relaxed row reads $\text{spend}_{2030} - \text{ArtN} \le 5{,}000$: ArtN is how far spend may run over the cap, and ArtP_must_P017 = 1 above read $\sum_t x_{\text{P017},t} + \text{ArtP} = 1$, P017 left out. A $\le$ row is offered only the variable that loosens it.


Counting instead of measuring (relaxobjtype = 2) asks a different question, "how few rules must give?":






One row gives, as before, but by 1,000,000: once a row is counted as broken, how far it breaks costs nothing more, so any violation is as good as any other and the number Gurobi returned means nothing. The count works through a binary per offered row, ArtNB_budget_2031 here, which is 1 for the row that gives. A count is the right measure for "how many caps must finance lift", never for "by how much".


Last, minrelax=True: among the repairs of least violation, the plan with the best NPV. The call then optimizes at once, in two phases, and returns the least violation:






Phase 1 found the least violation, 310; phase 2 added the row feasobj, holding the violation at that value, and restored the NPV objective. With $310k more in 2030, the best plan is worth $19,249k. That is the full answer finance asked for: the cheapest budget change that makes the scenario hold, and what the plan is worth after it.

Write relaxation_changes(values, tol=1e-6), which returns the sorted lines for every artificial variable with a value above tol. Numbers are written with :g. setObjectiveN Solves Objectives by Priority, Highest First


Lesson Prioritized objectives with add_auxiliary_objective asked the scenario-free model for the most NPV first, then the least total spend among those plans, and solved it in order by hand, because no solver in the runner takes MathOpt's auxiliary objectives. Gurobi takes several objectives natively. The model is the timing model with two objectives in place of one:



with $f_0^*$ the best NPV and $\varepsilon$ the share of it the plan may give up. In gurobipy:




The three rows are lesson Prioritized objectives with add_auxiliary_objective's, to the dollar: exact, 24,260 of NPV for 41,630 of spend; with 1% of NPV allowed to go, 24,031 for 40,440; spend first, the four must-do projects alone. The module's tests compare Gurobi's spend under the 1% tolerance with lesson Prioritized objectives with add_auxiliary_objective's solve in order. Four rules from the multiple-objectives page make the code read right:


  • Higher priority goes first. priority=2 beats priority=1. MathOpt is the other way round: its lowest priority number goes first (lesson Prioritized objectives with add_auxiliary_objective). Porting a model between the two means reversing the order.
  • One sense for all. ModelSense applies to every objective, so a minimized objective in a maximized model gets weight=-1.0. ObjNVal still reports the objective as written: spend is printed as 41,630, not $-41{,}630$.
  • Tolerances belong to the earlier objective. reltol and abstol on objective 0 say how far it may degrade while later ones are optimized; the looser of the two applies. For a MIP the page measures that from a base that includes the MIP gap of the earlier pass, which is why the program sets MIPGap = 0: with the default gap, "exact" would already allow a little loss.
  • Equal priorities blend. Objectives with the same priority are summed with their weights in one pass; distinct priorities are solved one after another. Each objective is read with Params.ObjNumber = k then ObjNVal.


The page also lists what a multi-objective model gives up: no duals or basis (Pi, RC, VBasis, CBasis), and no ObjBound or MIPGap for the whole solve. Every objective must be linear.

Lessons Convex piecewise costs without binaries to Incremental and logarithmic formulations wrote piecewise-linear curves by hand, because MathOpt's Python model has no SOS2 constraint: the lambda form of lesson The lambda (SOS2-style) formulation built from binaries needed a weight per breakpoint and a binary per segment. gurobipy has a general constraint for it, addGenConstrPWL(x, y, xpts, ypts): the point $(x, y)$ must lie on the curve through the breakpoints $(x_j, y_j)$, and Gurobi builds the formulation itself.

"Lesson The lambda (SOS2-style) formulation built from binaries's optimum" below means the lines that lesson recorded when it solved this model in MathOpt, with a weight per breakpoint and a binary per segment:




The curve is one call:






$26,753k with a $4,900k draw costing $1,240k: lesson The lambda (SOS2-style) formulation built from binaries's optimum, which its lambda form with segment binaries reached. The model holds 42 variables, the 40 projects plus the draw and its cost, and one general constraint; the weights and segment binaries of lesson The lambda (SOS2-style) formulation built from binaries are Gurobi's business now. The constraints page says each such general constraint has an equivalent MIP formulation and that adding one to a continuous model makes it a MIP.


Two rules for the breakpoints, from the objectives page, which defines the piecewise-linear function both features share: the $x$ values must not decrease (a repeated $x$ makes a jump), and outside the first and last breakpoints the curve goes on, along the first and last pieces:






The first piece has slope $675 / 1{,}500 = 0.45$, so $f(-1{,}000) = -450$; the last has slope $200 / 2{,}000 = 0.1$, so $f(6{,}000) = 1{,}250 + 100 = 1{,}350$. A credit line does not lend past $5,000k at 10 cents on the dollar, so the curve's domain must be enforced by the variable's bounds: draw has ub=XS[-1]. Leave the bound off and the model may draw more on terms the offer never made.


Summary


  • computeIIS names the rows that clash. IISConstr, IISLB, IISUB mark the subsystem; IISMinimal says whether it is irreducible; .ilp writes only the conflict. Gurobi named must_P017 and the two caps, as the deletion filter did; binary bounds never take part.
  • feasRelax repairs the model, and the penalties decide what gives. On a copy: unit penalties on every row dropped the must-do project; budget rows only gave $310k more in 2030; counting gave one row broken by an arbitrary amount; minrelax=True gave the best NPV, $19,249k, at least violation.
  • setObjectiveN solves objectives by priority, highest first. One sense for the model, weight $-1$ to minimize, reltol on the earlier objective; the results match lesson Prioritized objectives with add_auxiliary_objective's.
  • addGenConstrPWL states y = f(x) in one row. The credit line reached lesson The lambda (SOS2-style) formulation built from binaries's $26,753k; the curve extends past its ends, so bound the variable.

Design Note: Penalties Are Policy


Every feasRelax call above answered a different question, and each answer was correct: drop a must-do, add $310k, lift one cap by any amount. The solver does not know which rules are law and which are wishes; the penalties tell it. A service that offers "make it feasible" (lesson Turning an IIS into a planner message) keeps those penalties in configuration, reviewed with planners, and reports the repair together with the penalties that chose it.
