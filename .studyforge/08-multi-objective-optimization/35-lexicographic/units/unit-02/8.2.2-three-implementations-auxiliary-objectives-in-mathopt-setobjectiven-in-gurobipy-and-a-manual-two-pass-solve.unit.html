  15. Three implementations of a lexicographic objective

The board has approved the plan of lesson Hierarchical objectives with tolerances: NPV within 1% of its best, then the most risk removed. Two requests come with the approval. Finance adds a third level: if two plans tie on NPV and risk, fund the one that spends less. And the audit team wants to know that the plan does not depend on the tool, because GridCap's production service runs on HiGHS while one analyst checks plans in Gurobi.

There are three ways to write the same hierarchy, and this lesson builds all three on the small portfolio:

  • MathOpt's prioritized objectives: the hierarchy stored in the model (lesson Prioritized objectives with add_auxiliary_objective taught the API);
  • gurobipy's setObjectiveN: Gurobi's native multi-objective solve;
  • a manual two-pass solve: one ordinary solve per objective, with a kept row between them.

They should return the same plan. They do, as long as you know where they differ: which priority goes first, how a minimized objective is written, what a tolerance defaults to, and what a MIP gap left in an early pass does. GridCap is a fictional utility.

MathOpt Stores the Hierarchy in the Model, and Every Runner Solver Refuses It

In MathOpt the whole question lives in the model: NPV is the primary objective (priority 0), and risk and spend are auxiliary objectives with priorities 1 and 2. The lowest number goes first. The 1% is a per-objective solve parameter, keyed by the objective object (lesson Prioritized objectives with add_auxiliary_objective):

Two auxiliary objectives, so they are added with add_auxiliary, which sets each term one at a time. In OR-Tools 9.15, add_auxiliary_objective(expr=...) erases the terms of every auxiliary objective already in the model, and nothing raises (lesson Prioritized objectives with add_auxiliary_objective shows it). Read the objectives back, as above: each has its 80 terms, one per start variable.

The model is complete and correct. No solver in the runner will solve it:

As lesson Common vs. solver-specific parameters, and what each solver rejects shows, in OR-Tools 9.15 a solver's refusal reaches Python as an AttributeError raised by MathOpt's own error handling, and the solver's message is on the exception's __context__; the program prints it from there.

Lesson Prioritized objectives with add_auxiliary_objective showed that SCIP and CP-SAT refuse it the same way. MathOpt can pass auxiliary objectives to Gurobi, but in OR-Tools 9.15 MathOpt cannot load the runner's Gurobi 13 library (lesson Prioritized objectives with add_auxiliary_objective), so this course shows no result from MathOpt with Gurobi.

What does run is lesson Prioritized objectives with add_auxiliary_objective's solve_in_order, copied into this module as in_order.py. It reads the objectives and tolerances from the model and the parameters, and solves them one at a time on a copy of the model:

The values are each pass's best, $\Gamma_1, \Gamma_2, \Gamma_3$: NPV $24,260k in pass 1, then risk $12,750.5k, then spend $41,780k. gurobipy Solves the Hierarchy Natively, and Its Priorities Run the Other Way

Gurobi takes several objectives in one model with Model.setObjectiveN(expr, index, priority, weight, abstol, reltol, name). The same three levels:

Three things are different from MathOpt, and each one is a way to port a model wrong:

  • The highest priority goes first. Gurobi's documentation: one pass per distinct priority, in decreasing order. NPV has priority 2 here, spend 0. MathOpt's numbers run the other way, lowest first. Copy MathOpt's priorities 0, 1, 2 into setObjectiveN and spend is optimized first.
  • One sense for the whole model. ModelSense applies to every objective, so a minimized objective in a maximized model gets weight=-1: minimizing spend is maximizing −spend. In MathOpt each objective has its own is_maximize.
  • A small default absolute tolerance. abstol defaults to 1e-6 and reltol to 0. MathOpt's default for both is "not set", which allows no loss.

The first one is the costly one. The same program, with MathOpt's numbers copied unchanged (NPV 0, risk 1, spend 2):

Spend went first, so the plan is the must-do projects alone, the least money that can be spent: the same four projects lesson Prioritized objectives with add_auxiliary_objective found when it put spend first on purpose. Nothing warns: the model is valid, it simply asks the other question.

The tolerances themselves mean the same: Gurobi's documentation says the looser of the two applies when both are set, as in MathOpt. The values are read per objective, by pointing the ObjNumber parameter at one and reading its ObjN... attributes:

ObjNVal is each objective's value in the plan Gurobi returns, so NPV reads $24,019k here, where solve_in_order reported pass 1's best, $24,260k. The plan's three values are the same as MathOpt's.

The program runs on the size-limited Gurobi license mounted read-only in the course's runner; the model has 80 variables and 49 rows, well inside the limit. Section 5 covers gurobipy, licenses and the limit. quiet_env sets OutputFlag=0 before the environment starts, so no license banner or log reaches the output; without a license, the program stops with Gurobi's message, with user and host names masked.

reltol applies to MIPs only. The setObjectiveN reference says the relative tolerance is ignored for LP models, where Gurobi degrades an objective a different way (by fixing variables from their reduced costs, with abstol as the allowed violation). Problem statement

A hospital's theatre-scheduling team stores its ranked objectives the MathOpt way, as a list of levels:

A lower priority is optimized first; a tolerance of None means "not set", which in MathOpt allows no loss. An analyst wants to check the schedules in Gurobi, so the same levels must become Model.setObjectiveN calls on a model whose ModelSense is GRB.MAXIMIZE.

Write set_objective_n_args(levels). It returns one dict of keyword arguments per level, in the order of levels, with the keys index (the level's position in the list), priority, weight, abstol, reltol and name, so that each can be passed as model.setObjectiveN(expr, **args) and Gurobi optimizes the objectives in the same order, with the same senses and the same tolerances as MathOpt would. Any integers that give the right order are accepted. Gurobi's documentation (the setObjectiveN docstring of gurobipy 13.0 and the multi-objective attributes page) types ObjNPriority as an integer with default 0 and states no range, so it neither promises nor rules out negative priorities. The reference does not rely on them: it maps each MathOpt priority $p$ to $p_{\max} - p$, where $p_{\max}$ is the largest MathOpt priority in the list, so every Gurobi priority is 0 or more and the level MathOpt solves first gets the largest. The tests only compare the order the priorities give, so a negative mapping such as $-p$ passes them too.

The tests need no Gurobi license: they read your dicts. About eight lines.

A Manual Two-Pass Solve Is a Loop of Solve, Read, Keep


The third way needs no multi-objective support at all: any MIP solver, HiGHS here, solves each pass as an ordinary model. lexicographic.py is the whole method:




Each line is a piece of the pass formulation:


  • Solve. set_linear_objective replaces the model's objective with this level's, and solve runs HiGHS to a relative gap of 0, so best is the proven optimum $\Gamma_k$.
  • Read. allowed_loss is $\delta_k = \max(a_k, r_k |\Gamma_k|)$; abs keeps the loss positive when $\Gamma_k$ is negative.
  • Keep. The row's direction follows the sense: a maximized objective may fall by the loss, a minimized one may rise by it. The row is loosened by one more term, TOL $= 10^{-6}$, explained next.
  • Give the model back. The kept rows are deleted at the end. The same StartModel then serves the next question; without the deletes, a later run would still carry an earlier run's floors.


Why the kept row needs a numerical slack. With no tolerance, $\delta_k = 0$ and the row reads $f_k(x) \ge \Gamma_k$, where $\Gamma_k$ is the value the solver reported. Pass $k$'s own plan should meet that row with equality, but in floating point the reported value and the value of the returned plan can differ in the last digits. kept_row.py solves the risk pass on GridCap small and compares the two:






The plan that proved the optimum violates the exact row by $3.6 \times 10^{-12}$. HiGHS still solved pass 2 here, but that rests on how strictly the solver checks a row, which is not the model's business. solve_levels therefore subtracts TOL from a floor (adds it to a ceiling), so the plan pass $k$ returned always meets the row with room to spare. $10^{-6}$ $k is a thousandth of a dollar, far below any tolerance a planner sets; outcome.floor records the bound without it. Lesson AUGMECON: avoiding weakly efficient points's best_of adds the same TOL for the same reason.


Where solve_in_order copies the model through export_model(), this version edits the caller's model and undoes the edits. Both are sound; the copy is safer when other code holds the model, the in-place edit is cheaper for a sweep of many tolerances on one model.


Now the three implementations on four questions, each compared with Gurobi's plan:






All three return the same plan for every question, project for project, which answers the audit team. "Same plan" compares the start years of every project, not only the objective values. It could have failed even with correct code: when several plans tie on the last objective, two solvers may return different ones. That did not happen here, but a test of an implementation should compare objective values first and plans only when ties are ruled out.


Solve Each Pass to a Zero Gap, or the Gap Becomes a Tolerance


Every implementation above solved each pass to a relative gap of 0. A MIP solver is often told to stop earlier, once the best plan found is within a relative gap of the best bound (lesson Best bound, incumbent, absolute and relative gap explains the gap), and Gurobi's default gap is not 0 either. In a lexicographic solve that matters, because the kept row is built from what pass 1 returned. With no tolerance at all, the manual passes with pass 1 stopped at a 5% gap:






At a 5% gap, pass 1 stopped with a plan worth $24,071k, $189k below the optimum, and the row kept NPV above that instead of above $24,260k. Pass 2 then gave up $162k of NPV for $1,771.3k more risk removed, a trade nobody asked for. Pass 2 even found a plan with more NPV than pass 1 returned: $24,098k. The gap acted as a tolerance of unknown size, set by when the solver happened to stop. The row itself never makes pass 2 infeasible, because the plan pass 1 returned always meets it; the harm is the opposite, a floor set too low. (In floating point, it is the TOL of the previous section that guarantees "always meets it". This program's row has none, to show the gap alone, and pass 2 still solved at both gaps.)


Gurobi does the same inside setObjectiveN. Its documentation says the value later passes must respect is computed from the pass's best plan, its best bound and the MIP gaps, and only then relaxed by reltol and abstol. So MIPGap loosens every pass:



At the default gap the plan is the exact one; at 1% and 2% the NPV pass gives up $64k and $133k with no tolerance set. The rule for all three implementations: solve every pass but the last to a gap of 0 or very close to it, and state the tolerance on purpose. If a pass cannot reach a zero gap in the time available, the row can be built from the pass's best bound instead of its plan. For a maximized objective the bound is at least the optimum, so the floor never falls below the optimum minus the tolerance you chose. The price: when the remaining gap is larger than the tolerance, the floor can sit above every plan, and the next pass is infeasible. Neither choice is free, so the run's record should say which one was made.

Problem statement


A water utility picks which water mains to renew this year with a MathOpt model: one binary per main, and a budget row. It ranks two objectives: first the most leaks avoided, then the fewest customer disruption hours. The production service runs on HiGHS, which refuses auxiliary objectives, so the ranking must be solved by hand, and the auditors want it to give the same answer as a native hierarchical solve such as Gurobi's setObjectiveN would.


Write two_pass(model, first, second, *, first_max, second_max, abs_tol=0.0, rel_tol=0.0). first and second are linear expressions over the model's variables, and first_max / second_max say whether each one is maximized. The function solves



with HiGHS, each pass to a relative gap of 0, and returns the pair (first value, second value) of pass 2's plan (mathopt.evaluate_expression(expr, result.variable_values()) evaluates an expression).


Loosen the kept row by a numerical slack of $10^{-6}$ beyond $\delta$ (subtract it from a floor, add it to a ceiling), as lexicographic.py does in lesson Three implementations: auxiliary objectives in MathOpt, setObjectiveN in gurobipy, and a manual two-pass solve: a solver can report $\Gamma_1$ a hair above the value of the plan it returned, and the row must not exclude that plan. The reference does this; the tests' values are whole numbers, far apart compared with $10^{-6}$, so a row without it gives the same answers on them.


Before returning, delete the kept row, so that the model has only the rows it came with. The objective need not be restored: the reference leaves pass 2's objective in the model, because every call sets its own objective before it solves, and the tests check only the rows.


The tests compare your pair with an enumeration of every plan of their small instances, which is the answer a native hierarchical solve returns. About fifteen lines.

Summary


  • MathOpt stores the hierarchy in the model, and every runner solver refuses it. Add auxiliary objectives term by term (in OR-Tools 9.15, add_auxiliary_objective(expr=...) erases the terms of the auxiliary objectives already in the model), and solve them in order; no MathOpt-with-Gurobi result runs here.
  • gurobipy solves the hierarchy natively, and its priorities run the other way. Highest priority first, one ModelSense with weight=-1 for a minimized objective, abstol 1e-6 by default, and reltol ignored for LPs.
  • A manual two-pass solve is a loop of solve, read, keep. It runs on any MIP solver and gave the same plan as setObjectiveN on every question tried. Loosen each kept row by a tiny TOL, because a solver can report its best a hair above its own plan's value.
  • Solve each pass to a zero gap, or the gap becomes a tolerance. A 5% gap in HiGHS's pass 1, or a 1% MIPGap in Gurobi, gave up NPV that no tolerance allowed.

Design Note: Keep the Question in One Place, and Let the Solve Be Swappable


The three implementations share one question: an ordered list of objectives, each with a sense and two tolerances. Write that list once, as data (Level here, the auxiliary objectives and ObjectiveParameters in MathOpt), and let one function turn it into solves. Then the service can use the manual passes on HiGHS, an analyst can check them with setObjectiveN, and a test can compare the two on every scenario, as three_ways.py does. The test is cheap, and it is what catches a port that copied MathOpt's priority numbers into Gurobi.
