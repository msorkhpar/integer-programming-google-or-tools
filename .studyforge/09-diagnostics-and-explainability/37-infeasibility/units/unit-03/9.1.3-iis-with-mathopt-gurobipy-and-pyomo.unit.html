An IIS Is One Conflict: Irreducible, but Neither Unique nor the Smallest

An IIS is a set of the model's constraints (rows, variable bounds, and for a MIP the integrality of variables) with two properties:

  1. infeasible: no point meets all of them;
  2. irreducible: drop any one member and the rest can all be met.

Irreducible does not mean smallest. A model can have many IISs of different sizes, and a tool returns one of them. Gurobi's reference for computeIIS says so: the result is not necessarily the smallest IIS. Nor is an IIS the whole story. It explains one reason the model is infeasible, and other reasons can remain after it is fixed. Both facts show up on the Budget Lock scenario.

The Deletion Filter Keeps the Conflict It Tests Last

The deletion filter (John Chinneck's method, which Pyomo's documentation names as the source of its own tool) starts from all the rows and drops them one at a time. If the rest is still infeasible, the row was not needed and stays out. If the rest becomes feasible, the row goes back. filters.Oracle answers each "is this set of rows infeasible?" question. It works on a zero-objective copy (lesson Infeasible, unbounded, or the solver can't tell) and switches a row off by removing both of its bounds:

The variables keep their bounds and integrality throughout. They are what makes $x_{i,t}$ a yes-or-no decision, not rules a planner wrote. So the IIS this filter finds is a set of rows, read together with every bound. The filter itself:

The filter tries the rows in the order it is given them. Here it runs in the order the model builds them (once_P001 first, force_P032_2028 last) and in the reverse order:

Two different IISs, from the same filter on the same model. Both cost 70 solves, one per row. The order chooses between them: a row is dropped whenever the rest is still infeasible without it, and early in the pass the rest still holds every other conflict. So the rows tested first are the most likely to be dropped, and the conflict that survives is the one whose rows come last. In build order the board's overrides come last, and the override conflict survives. In reverse they come first and are dropped, because P017's crew conflict still holds without them.

That makes the order a tool. Test the rows you would rather not blame first, and the rows you want a planner to look at last.

The Additive Filter Builds a Conflict From Nothing

The additive filter works the other way round. Start with an empty conflict. Add rows one at a time until the set turns infeasible: the row that tipped it belongs to the conflict. Start again from the conflict found so far, and stop when the conflict alone is infeasible:

In build order, the must-do rows come before the crew and override rows, so the first conflict to close as rows are added is P017's. The filter returns a third answer for the same order. It used 138 solves against the deletion filter's 70, because each of its three rounds scans the rows again from the start. An additive pass pays off when a conflict closes early in the list, since every row after that point is never tested.

Each filter's answer is irreducible by construction: the deletion filter keeps a row only when removing it made the rest feasible, and the additive filter adds only rows that the set needed. The module's tests check both answers row by row: dropping any one member makes the set feasible.

Problem statement

A school's timetabling model has two kinds of rules. Hard rules are physics and law: a room holds one class at a time, a teacher works at most six periods. Soft rules are requests someone made and could withdraw: "7A only in the mornings", "the lab is closed on Tuesday". When the timetable has no solution, the deputy head wants a conflict made of soft rules only, the ones a person can change, read together with every hard rule.

You get an oracle, infeasible(rules) -> bool, which says whether the timetable has no solution when exactly the rules in the set rules are switched on. Write conflict_among(soft, hard, infeasible):

  • if all the rules together are feasible, return None;
  • if the hard rules alone are already infeasible, return [] (no soft rule is to blame);
  • otherwise run a deletion filter over the soft rules, in the order given, with every hard rule switched on in every question, and return the soft rules that are left, in the order given.

What is left must be irreducible among the soft rules: with the hard rules on, the kept soft rules are infeasible, and dropping any one of them makes them feasible. About twelve lines.

Gurobi's IIS has six rows, two more than the filter's budget conflict: P039's must-do row and the 2030 distribution crews. It also has 25 variable bounds. The filter treats all 160 bounds as a fixed background and so can only trade rows. Gurobi treats bounds as members it may leave out, so its IIS can drop a bound and keep a row instead. Both answers are irreducible, each by its own rules. To make Gurobi choose among rows only, as the filter does, force every bound into the IIS. The force attributes take 1 (always in), 0 (always out) or −1 (Gurobi decides, the default):








With the bounds forced in, Gurobi returns the four-row budget conflict that the filter's loop found second. Forcing budget_2028 out sends it to P017's conflict. Forcing crews_transmission_2028 in gives the crew conflict. Each of the three conflicts the loop found can be had from Gurobi by saying which rows to keep or exclude. Gurobi's reference warns that forcing too much out can leave a set that is not infeasible at all, and then computeIIS raises an error.


Lesson computeIIS, feasRelax and setObjectiveN said that a binary's bounds never take part in an IIS, yet the IIS above lists 25 bounds of 0-1 variables. Both are true, because the variable type decides. Gurobi's attribute reference says the bounds of a GRB.BINARY variable are implicit in its type and never take part in an IIS. MathOpt has no binary type: a 0-1 decision is an integer variable with bounds 0 and 1, and convert.to_gurobi copies it as GRB.INTEGER with those bounds, which Gurobi treats as bounds like any other. Retyping the same variables as binary takes the bounds out of the IIS:






With no bound left to trade, Gurobi returns the same four-row budget conflict as with every bound forced in. So a rule written as a bound on a binary can never be named by Gurobi's IIS, and a rule written as a bound on a 0-1 integer is named only as a variable's bound, not as the rule.


Pyomo: write_iis Asks Gurobi, the MIS Tool Solves the LP Relaxation


Pyomo has two tools, and they work differently. write_iis(model, file, solver="gurobi") hands the model to Gurobi's persistent interface, calls computeIIS and writes the IIS to an .ilp file (CPLEX and Xpress are the other choices). compute_infeasibility_explanation(model, solver) is a filter of its own. First it gives every row and bound an elastic variable (lesson Elastic constraints and feasibility relaxation) and collects what had to bend. Then it runs a deletion filter over those rows. It takes any solver; here it gets HiGHS. Both run on convert.to_pyomo's copy, where each row is rows[<name>]:





write_iis returns Gurobi's six-row IIS, the same as gurobipy's default, since it makes the same call. The MIS tool returns the four-row crew conflict, plus seven variable lower bounds, in 30 solves. Then comes the warning in the last line. "crew-cut" is the Budget Lock's crew cut alone, P017's conflict, which the MILP cannot meet. The MIS tool declares it feasible.


The reason is in the tool's source (pyomo/contrib/iis/mis.py). Before it starts, it turns every variable bound into a row and sets every variable's domain to the reals. The tool works on the LP relaxation, where integrality is gone. P017's conflict exists only for integers: with $x_{\text{P017},2030} = x_{\text{P017},2031} = 0.5$, each year needs 6.5 crew-months against 12, and the relaxation is happy. gurobipy confirms the tool's other answer is an LP answer. The IIS of the relaxed model (model.relax(), every integer variable made continuous) matches the MIS tool's, row for row:



So for a MIP, an LP-based tool finds only the conflicts that survive relaxation, and can call a MIP feasible when it is not. Use it on an LP, or as a first pass. For a MIP, use a filter whose oracle solves the MIP, as filters.Oracle does, or a MIP-aware IIS like Gurobi's. Pyomo's documentation adds that the MIS tool is meant for IPOPT, logs its findings rather than returning them, and that its tolerance is whatever the solver uses.

Problem statement


A rail operator's maintenance planner gets "conflicts" from three tools: its own filter, a commercial solver's IIS, and a library that works on the LP relaxation. Before a conflict goes to the track engineers, the planner wants it audited against the model the engineers actually use.


You get the claimed conflict, a list of rule names, and an oracle, infeasible(rules) -> bool, which answers for the real model (integers included) with exactly the rules in rules switched on. Write audit(claim, infeasible) returning a dict with two keys:


  • "infeasible": whether the claimed rules, all switched on, really have no solution;
  • "not_needed": the members of the claim, in the claim's order, that could each be switched off while the rest of the claim stays infeasible. An irreducible conflict has none. When the claim is not infeasible at all, this list is empty.


Test each member against the rest of the claim with only that one member removed. About six lines.

Summary


  • An IIS is one conflict: irreducible, but neither unique nor the smallest. The Budget Lock scenario has three conflicts among its rows alone.
  • The deletion filter keeps the conflict it tests last. One solve per row (70). The order picks which conflict survives, so put the rows you want named last.
  • The additive filter builds a conflict from nothing. 138 solves here, and cheaper when a conflict closes early in the list.
  • Every conflict, one at a time: find one, switch off one of its rows, look again. Three conflicts, 211 solves.
  • computeIIS counts variable bounds as members. Its default IIS had six rows and 25 bounds. With every bound forced in (IISLBForce, IISUBForce), it chose among rows only, and IISConstrForce picked the conflict. The bounds of a variable typed GRB.BINARY never take part; MathOpt's 0-1 integers, copied as GRB.INTEGER, do.
  • Pyomo's write_iis asks Gurobi. Its MIS tool solves the LP relaxation, so it missed P017's integer conflict and declared that scenario feasible.

Design Note: Hold the Bounds, Filter the Rules


filters.Oracle switches rows on and off but never touches a variable's bounds or integrality. That choice sets the vocabulary of the answer. Every member of the IIS is a row with a name a planner wrote (a budget, a crew cap, an override), never "x_P036_2027 ≥ 0", which no planner can act on. Gurobi's default IIS is just as correct and harder to explain: 25 of its 31 members are bounds (of 0-1 variables typed integer; typed binary, they could not be members). When the IIS will be shown to people, pick the members it may contain before you compute it, as IISLBForce and IISUBForce do in gurobipy.
