The Model

The model of lesson Infeasible, unbounded, or the solver can't tell, unchanged, with its formulation and row labels there. This lesson reads row names, never rows, so here is the vocabulary it translates, with the data each kind of row carries:

Row nameRuleData the message needs
must_P017$\sum_{t \in T_i} x_{i,t} = 1$the project's name and window $T_i$
force_P023, force_P032_2028$\sum_t x_{i,t} \ge 1$, $x_{i,f_i} \ge 1$the project, the forced year
after_P023_2029$\sum_{u \le t} x_{c,u} \le \sum_{s \le t - L_c} x_{p(c),s}$child, parent, lag $L_c$
budget_2028$\text{spend}_y \le B_y$$B_y$, and GridCap's own figure if the scenario changed it
crews_transmission_2030crew-months used $\le K_{q,y}$$K_{q,y}$, and GridCap's own figure
floor_Coast, alt_G001, once_P001, drop_P040as in lesson Infeasible, unbounded, or the solver can't tellthe region's floor; the group's members; the project

A row name is built from a kind and its indices (budget and 2028), so the translator splits the name and looks the indices up in the portfolio and the scenario.

A Planner Message Names Rules and Projects, Never Rows

message.describe(name, portfolio, scenario) turns one row name into one sentence. Each kind of row gets its own wording, with the project's id and name, money in $k, and a note when a number is the scenario's rather than GridCap's own:

Three choices make the difference between a translation and a message:

  • Say who set the number. "Finance locked the 2028 budget at $6,000k (GridCap's figure: $8,120k)" tells the reader that the number is a decision someone made, and whom to ask.
  • State a precedence row as the condition it is. The row after_P023_2029 holds for every plan that does not start P023 in 2029. What it forbids is P023 in 2029 without P022 by 2028, so that is what the sentence says.
  • Name the project twice. The id (P023) is what planners search for. The name (Valley pole run replace (A023)) is what they recognize.

Problem statement

A city's road-resurfacing model names its rows like this, and its conflict finder returns a list of such names. The council's planners want each one as a sentence. The table gives the exact sentence for each kind of row:

Row nameSentence
cap_2027The 2027 resurfacing budget is $12,500k.
need_R12R12 Elm Street must be done this plan.
pin_R31_2027Council fixed R31 Harbour Road to 2027.
crew_north_2027The north district has 3 paving crews in 2027.
before_R07_R12R07 Mill Lane must finish before R12 Elm Street starts.
any other name, such as noise_R12_nightRule noise_R12_night has no description yet.

A district with one crew gets the singular: The west district has 1 paving crew in 2029. A row of a known kind that names a job, year or district missing from the data (need_R99 when jobs has no R99) gets the same fallback sentence as an unknown kind: Rule need_R99 has no description yet.

jobs maps a job id (letters and digits, no underscores) to its street; caps maps a year to the resurfacing budget in $k, written with a thousands separator; crews maps (district, year) to the number of paving crews. A district name may contain underscores (south_east); in the sentence each underscore becomes a space.

Write translate(conflict, jobs, caps, crews) returning the sentences, in the conflict's order. The sentence helper is a good place for the per-row work. About twenty lines.

Show the Arithmetic: Every Way to Start the Projects, and Where It Runs Out


A list of rules says that they clash. A planner who does not trust the model wants to see why. For the small conflicts an IIS gives, the "why" can be worked out completely. List the projects the conflict requires, and the start years its rows leave each one. Then try every combination, and for each, find the budget or crew row it overruns:



starts builds the year lists from the rows. A must-do project gets its window. A forced project gets its window, or only the forced year. And a parent gets the years its child's precedence row allows: when the conflict pins P023 to 2029, its parent P022 may start only in 2027 or 2028. On the override conflict with the 2028 budget, that gives two combinations:



Every combination fails, which is the conflict, shown in sums a planner can check by hand. The cheapest combination misses by $40k, and that is exactly the 2028 budget increase in the priced repair of lesson Elastic constraints and feasibility relaxation. The arithmetic and the elastic model agree.


The enumeration is safe here because an IIS is small: three projects with at most two start years each. On a conflict with many projects it would grow quickly, and the message should then show only the combination that comes closest.

Problem statement


The road program's conflict finder has named a conflict: some jobs that must be done, the years each may still be done in, and the yearly resurfacing budgets they overrun. Each job is paid in full in the year it is done, and money does not carry over between years. Finance asks one question: what is the least total increase of the yearly budgets that would let every job in the conflict be done?


For one choice of a year for each job, the increase is the sum, over the years, of how far that year's spending goes over its budget (0 for a year within budget). The answer is the least such increase over every choice. An IIS names only a few jobs, so trying every choice is fine.


Write smallest_raise(years, cost, caps): years maps each job to the years it may be done in, cost maps each job to its cost ($k), and caps maps each year of the plan to its budget ($k). Return (increase, choice), where choice maps each job to its year in a cheapest choice. When several choices tie, return the first one found when jobs are taken in sorted order and each job's years in the order given. About twelve lines.

Each Conflict Ends With the Changes That End It, in the Planners' Words


An IIS has a property that makes the last line of a message easy to write. Remove any one of its rules and the rest can hold. So every rule in the conflict that a person can change is a way out of that conflict. remedy says each way out in words, and returns nothing for the model's own rules (precedence, "at most once", alternatives), which no meeting can change:




The sentence says "this conflict" on purpose. Ending one conflict need not give a plan. Lesson IIS with MathOpt, gurobipy and Pyomo's loop showed that the override conflict with the 2028 crews hides a second one with the 2028 budget. A message that offered "raise the 2028 budget" as the fix would be wrong. So a message lists every conflict, and then one repair for the whole scenario, checked by a solve.


One Message for the Whole Scenario


lock_message.py puts the module together. It runs the pre-solve checks (lesson Validating inputs before the solve), finds every conflict with the deletion-filter loop (lesson IIS with MathOpt, gurobipy and Pyomo), explains each one with this lesson's functions, and then takes the priced repair of lesson Elastic constraints and feasibility relaxation. It writes the repair as a new scenario and solves it, so that the message never promises a plan the model has not found:




The whole message, as a planner receives it:



Read it as the board would. Conflicts 1 and 2 share the board's two overrides, so one decision (stop forcing P023, or let P032 start another year) ends both. Conflict 3 is the crew cut and was found before any solve. If the board keeps its overrides, the cheapest way to a plan is $40k and seven crew-months, and that plan is worth $17,060k. No row name appears anywhere in the message. Every number in it can be checked against the data, and the repair has been checked by a solve.


Summary


  • A planner message names rules and projects, never rows. Say who set each number, state a precedence row as the condition it forbids, and name each project by id and by name.
  • Show the arithmetic. For an IIS's few projects, try every start-year combination and show where each one runs out. The closest miss, $40k, matched the elastic repair.
  • Each conflict ends with the changes that end it, in the planners' words. Any one changeable rule of an IIS ends that conflict, and not necessarily the scenario's infeasibility.
  • One message for the whole scenario: the check, every conflict, and one repair checked by a solve. That is section 9's milestone.

Challenges

  2. The two override conflicts repeat three of their four rules. Rewrite explain so that a message with several conflicts lists shared rules once and says which conflicts they belong to.

Design Note: The Translator Is a Table, Kept Next to the Model


describe and remedy know every kind of row the model builds, and nothing else. When a new rule family enters the model (a regional cap, a vendor limit), its name pattern, its sentence and its remedy have to enter the translator in the same change, or the message falls back to the raw row name. A test that builds every kind of row and checks that describe never returns the name itself catches the gap. The module's tests check the weaker version: the message for P017 contains no row name.
