Every program in lessons Containerizing a solver service to S3 and a local SQLite file for snapshots and results called S3, Batch or Step Functions, and none of them reached AWS. They ran against moto, a Python library that imitates AWS services inside the test process: boto3 sends its requests as usual, and moto answers them from memory, with AWS's response shapes and error codes. That is how GridCap's service can be tested on every commit, offline, in seconds, with no account and no bill. It is also how a test suite can pass while the code is wrong, if you do not know what moto checks and what it does not. This lesson sets up moto safely, writes pytest tests with it, and maps its limits with programs that ran. (GridCap is fictional; no number in it is real.)

No model is built or changed here: the code under test stores and runs the model of lesson AWS Batch on Fargate, Step Functions and Lambda: who does what.

Fake Credentials Come First, So No Test Can Sign as Anyone

boto3 signs every request with credentials it finds in the environment, a config file, or the machine's role. A test machine may have real ones: a developer's laptop usually does. If a test then creates a client outside moto's mock, by mistake, its requests are signed as that developer and sent to AWS. moto's documentation therefore recommends setting fake credentials before anything else, in a fixture. The module's fake_aws.py sets the five variables it lists, and points boto3 at no config file:

moto_safety.py first runs a child process with no AWS variables at all, as a test run on a clean machine would, and calls S3 without moto; then it calls S3 inside the mock:

Without credentials boto3 refuses to sign, before any request leaves. With the fake ones, a request that escaped the mock would be signed with the key testing, which belongs to no one, and AWS would reject it. Inside the mock, the bucket exists only in moto's memory, and the account is moto's placeholder 123456789012. No real account id, key or region tied to a person appears anywhere in the course's code or output.

mock_aws Gives Every Test a Fresh, Empty AWS

mock_aws works as a decorator, a context manager, or with start() and stop(). Each time it starts, the fake AWS is empty; when it stops, everything in it is gone. The moto documentation's advice is to start it before creating any boto3 client, so that no client is set up against the real endpoints. moto Returns AWS's Errors and Pages, So Test Them

What moto does well is the contract of each call: the shapes of responses, the error codes, the paging. Code that handles those can be tested exactly. moto_limits.py stores 1,005 result objects and lists them two ways:

The S3 API reference says a ListObjectsV2 call returns at most 1,000 keys, sets IsTruncated, and hands back a continuation token for the rest. moto does the same, so code that forgot to page fails a test with 1,005 objects instead of failing in production in the month the bucket passes 1,000 results. The paginator follows the tokens for you; lesson S3 and a local SQLite file for snapshots and results's rebuild uses it.

Errors come back with AWS's codes, so code can tell them apart:

They mean different things to the service. A missing result key is normal (the run is still waiting), and S3Store.get_result turns it into None. A missing bucket is a broken deployment, and must raise. Testing both against moto pins that difference down.

Problem statement

The trim planner's results live in S3 at trim-results/<survey id>/<run id>.json. The planners' tool shows every run of a survey, and a busy survey can have thousands. Its first version made one list_objects_v2 call, and nobody noticed for a year.

In run_listing.py, write runs_of(s3, bucket, survey_id): the run ids that have a result for that survey, sorted as text. The rules:

  • List every key, on every page: one list call returns at most 1,000 keys. Use the client's paginator, as lesson S3 and a local SQLite file for snapshots and results's rebuild does.
  • Only keys directly under trim-results/<survey id>/ count. Survey ids have different lengths: the runs of S-70 are not runs of S-7.
  • A run's result is a file named <run id>.json right in that folder. Other files (t-1.log) and files in deeper folders (old/t-0.json) are not runs.
  • A survey with no results gives []. A bucket that does not exist is not "no results": let S3's NoSuchBucket error propagate.

The tests run against moto, which pages like S3. About 10 lines.

moto Accepts What AWS Would Refuse, So Validate Before You Call


moto imitates the services' behaviour, not all of their checks. The same program tried four things AWS documents as refused or as doing work, and moto accepted every one:



What AWS does instead, from its documentation:


  • Checksums. S3 computes its own checksum of an upload and validates it against the one the client sent before storing the object. moto stored the body under a checksum it does not match.
  • State machine definitions. The Amazon States Language requires StartAt to match, exactly, the name of one of the states; moto stored a definition whose StartAt names none. moto's documentation also says that by default an execution runs none of its states and returns static data, which is why lesson AWS Batch on Fargate, Step Functions and Lambda: who does what called the failure function by hand.
  • Batch jobs. With use_docker off, as this module configures it, moto's documentation says job scripts are not executed and are assumed to succeed. A job with no settings at all "succeeded".
  • Batch names and timeouts. SubmitJob allows letters, numbers, hyphens and underscores in a job name, starting with a letter or number; run 0002! breaks both rules. A job's timeout is at least 60 seconds. moto accepted both.
  • Permissions. moto's IAM page says that by default it does not authenticate or authorize anything: every call above was made with the key testing, which no IAM user owns. A test against moto never fails because a role lacks a permission. (set_initial_no_auth_action_count turns checking on, for the services that support it.)


So a green moto suite proves the code handles AWS's responses, and nothing about whether AWS would accept its requests. Two habits close most of the gap:


  • Check requests in your own code, before the call, against the documented rules: job names, timeouts, Fargate sizes (lesson AWS Batch on Fargate, Step Functions and Lambda: who does what), a definition's states. The checks are then tested like any other function, and run in production too.
  • Assert on what was sent, not on what moto says happened. Read the job back with describe_jobs, as lesson AWS Batch on Fargate, Step Functions and Lambda: who does what's test does, or capture the request parameters with a botocore event hook (client.meta.events.register("provide-client-params.batch.SubmitJob", ...)), and assert on those. Never assert that a job SUCCEEDED: moto would say so for any job.


Permissions are checked another way: by reading the policy (lesson Terraform for the optimization stack) and, before the first deployment, by one run in a test account, which this course does not do.

Problem statement


This lesson found that moto accepted a job name and a timeout that AWS Batch refuses. The service will check every SubmitJob request itself before sending it, so the moto suite can test the checks and production gets them too.


In submit_check.py, write problems(request). request is the keyword arguments of a batch.submit_job call, as a dict. Return every rule it breaks, as these exact texts, in this order:


  1. jobName 'NAME' is not a valid job name unless the name is 1 to 128 characters of letters, digits, hyphens and underscores, with a letter or digit first.
  2. timeout N s is under 60 s if timeout.attemptDurationSeconds is given and under 60.
  3. retry attempts N is outside 1-10 if retryStrategy.attempts is given and outside 1 to 10.
  4. Under containerOverrides.resourceRequirements: VCPU and MEMORY must be given together if only one of the two is there; otherwise, if both are, VCPU V with MEMORY M is not a Fargate size (with the values as given) unless the memory is one FARGATE lists for that vCPU count. Both values are strings, as boto3 sends them; the vCPU count may be "0.5".
  5. environment variable NAME is set twice for each repeat of a name in containerOverrides.environment.


A request without a timeout, retry strategy, size or environment has nothing to check there. FARGATE (the table of lesson AWS Batch on Fargate, Step Functions and Lambda: who does what) and the name pattern NAME are given; about 20 lines remain.

Summary


  • Fake credentials come first, so no test can sign as anyone. Set moto's testing values in a fixture before any client exists; without credentials boto3 refuses to sign.
  • mock_aws gives every test a fresh, empty AWS. Start the mock, then make the client, in that order, in fixtures.
  • moto returns AWS's errors and pages, so test them. 1,000 keys per list call; NoSuchKey versus NoSuchBucket.
  • moto accepts what AWS would refuse, so validate before you call. It accepted a wrong checksum, a broken state machine, an invalid job name and a 30 s timeout, marked an unrunnable job SUCCEEDED, and checks no permissions.

Design Note: Three Layers of Checking


moto is the middle of three layers. Below it, plain unit tests check the pure functions (the canonical form, the settings, the request checks) with no AWS at all. moto adds the calls: does the code send the right requests in the right order, and read the responses and errors correctly? Above it, one run in a real test account checks what only AWS knows: permissions, quotas, networking, the image actually starting. This course has no account, so it stops at moto, and says so; the habit of validating requests yourself moves as much as possible of the top layer down into the bottom one.
