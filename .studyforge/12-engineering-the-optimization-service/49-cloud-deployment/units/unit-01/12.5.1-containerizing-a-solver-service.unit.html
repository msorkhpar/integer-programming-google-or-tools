GridCap's job API from lesson Long solves: submit, poll, fetch runs on one developer's laptop. Operations want it on AWS, next to the data, and the first question they ask is "what exactly do we run?" On the laptop the answer is "whatever is installed": a Python version, an OR-Tools wheel, a FastAPI release, and the HiGHS build that OR-Tools bundles. Install them again on another machine a month later and any of them may have moved, and a solver that moved can return a different plan for the same snapshot (lesson Versioned input snapshots, pinned solvers and run manifests). This lesson packages the service as a container image: one file that holds the operating system layer, the Python interpreter, every library at a fixed version and the course's code. Every machine that runs the image runs the same thing. (GridCap is fictional; no number in it is real.)

This lesson is read-along for its Docker parts. The course's runner has no Docker and no network, so the Dockerfile and compose file below were never built or run; they are shown as text, in fences marked as read-along. Every Python program the lesson quotes did run, in the runner, and its output is printed under it.

A few words first. An image is a read-only template for a container; a container is one running instance of an image, with its own processes, file system and environment variables. A Dockerfile is the recipe that builds an image, one instruction per line. A registry stores images by name and tag; on AWS it is ECR (Elastic Container Registry).

The Model

The container runs the planning model unchanged; lesson AWS Batch on Fargate, Step Functions and Lambda: who does what restates it whole, because that is where the solve worker runs it. This lesson adds one small model of its own, to show how a solver decides how many threads to use: pick at most three of eight crew jobs, most value first.

Sets. $J = \{0, \dots, 7\}$, the crew jobs.

Parameters. $v_j$, the value of job $j$: $v = (7, 5, 9, 4, 6, 8, 3, 2)$; at most 3 crews.

Variables. $\text{pick}_j \in \{0, 1\}$ for every $j \in J$.

An Image Pins the Solver, Its Python and Every Library

A solve depends on more than the model. It depends on the solver's version (OR-Tools 9.15 bundles its own HiGHS), on the Python that loads it, on the C library under that Python, and on every package the code imports. The OR-Tools installation guide recommends installing the Python package with pip, and PyPI publishes OR-Tools 9.15.6755 as prebuilt wheels only. So the image installs exactly that version, from a requirements file with every direct dependency pinned:

(deploy/requirements.txt.) A version range such as ortools>=9.15 would let the next build pick up 9.16 without anyone deciding to. A pinned file still leaves the dependencies of these packages free; a lock file that lists every package with its hash (pip install --require-hashes) closes that gap, and is the next step for a production service.

The course's own runner is an example of the idea: every program in this course runs in one pinned image, which is why the output printed on these pages is the output you get.

One Image, Two Commands: the API and the Solve Worker

The Dockerfile builds in two stages. The first installs the pinned packages; the second starts from a clean base, copies in only the installed packages and the code, and is the image that ships. Build tools and caches stay behind in the first stage. The files are laid out as they would sit at the root of the service's repository:

The decisions in it:

  • The base image names an exact Python, 3.14.7, the runner's version. Docker's best-practice guide goes one step further, pinning the base by its digest (FROM image:tag@sha256:...), at the price of updating the pin by hand when the base gets security fixes.
  • CMD is in exec form, a JSON list. The Dockerfile reference explains that the shell form (CMD fastapi run ...) runs the command under /bin/sh -c, so the program is not process 1 and does not receive the stop signal Docker sends; the exec form runs the program itself.
  • The default command starts the API of lessons A REST API with FastAPI and Long solves: submit, poll, fetch (lesson A REST API with FastAPI showed fastapi run). The solve worker is in the same image, under a different command. One image means the API and the worker can never disagree about a library version.

Problem statement

The vegetation crew-roster optimizer (a CP-SAT model of section 4) is moving into a container, and operations will start it as a Batch job with its settings in environment variables. Last season a roster job ran with a mistyped season for six hours before anyone noticed, and once with an access key pasted into its environment.

In roster_settings.py, write read_settings(env). It returns (settings, []) when the environment is usable, and (None, problems) otherwise, with every problem found, not only the first. The variables:

VariableRuleDefault
ROSTER_BUCKETrequired, non-emptynone
SEASONrequired; a whole number from 2025 to 2040none
CREWSa whole number from 1 to 504
DRY_RUNtrue or false, in any letter casefalse

settings is {"bucket": str, "season": int, "crews": int, "dry_run": bool}. In addition, any variable whose name contains SECRET, PASSWORD or ACCESS_KEY is a problem: credentials come from the job role, never from the environment.

The problem texts, exactly: ROSTER_BUCKET is not set, SEASON is not set, NAME='text' is not a whole number, NAME value is outside low-high (for example CREWS 0 is outside 1-50), DRY_RUN='text' is not true or false (with the text as given), and NAME must not be set: use the job role. A whole number is what int() accepts: "4.5" is not one. The default applies only when a variable is absent: CREWS set to the empty text is present, and int("") refuses it, so it gives CREWS='' is not a whole number. (For the two required variables, empty counts as not set.) The helper whole is declared for you; about 25 lines remain.

The Image Runs as a Non-Root User and Holds No Credentials


Two rules keep a leaked or misused image from doing much harm:


  • Run as an ordinary user. Unless a Dockerfile says otherwise, the container's processes run as root. The useradd line creates a system user solver (with no home directory, and /srv/data as the one folder it may write), and USER solver makes every later instruction, and the container's command, run as that user. Docker's best-practice guide recommends exactly this.
  • Put no secret in the image. Anyone who can pull an image can read every file and every ENV in it. So the image holds no AWS keys and no .env file. Tell the Solver How Many CPUs the Container Has


A Batch job on Fargate asks for a number of vCPUs, 2 in this module's job definition. A process inside the container may still see more. Python's documentation says os.cpu_count() returns the number of logical CPUs in the system, and os.process_cpu_count() the number this process may use by CPU affinity; neither is defined as the container's share. Python 3.13 added an override, the PYTHON_CPU_COUNT variable, which both functions then report. cpu_count.py asks a child Python without and with it:






The runner's own count is not printed: it is whatever machine runs the course. With the override, both functions say 2. The job definition sets PYTHON_CPU_COUNT to the job's vCPU count, so any library that sizes a thread pool from os.cpu_count() sizes it to the job.


Solvers decide their own thread counts. CP-SAT's num_workers parameter defaults to 0, which the parameter file of OR-Tools describes as trying to use all cores on the machine; 1 means no parallelism. Inside a container, "the machine" may be the host. PYTHON_CPU_COUNT does not help here: it changes what Python's own functions report, and CP-SAT counts cores in its C++ code, not through Python. A Local Stack: the Image Beside moto's Server


Before anything reaches AWS, a developer can run the image locally. The compose file starts the API next to moto's server (the same fake AWS the course's programs use, as a container), with moto's fake credentials and the SQLite index on a named volume:



AWS_ENDPOINT_URL sends every boto3 call to moto's server instead of AWS. The ports are bound to 127.0.0.1, so nothing outside the developer's machine can reach them. The build carries a project label, so old images of this project can be pruned by label without touching any other project's.


AWS_SECRET_ACCESS_KEY: testing looks like what the Dockerfile check above refuses, and it is not the same thing. testing is the dummy value moto's getting-started guide tells you to set, so that boto3 finds a credential and never reaches for a real one; it is no key to any AWS account. It also lives in the compose file on the developer's machine, not in the image: the image carries no credentials, and in AWS the job gets them from its role.


Summary


  • An image pins the solver, its Python and every library. Pin versions in a requirements file; a hashed lock file pins the rest.
  • One image, two commands. The API is the default CMD; Batch's job definition runs the worker from the same image. Exec-form commands receive the stop signal.
  • Settings come from the environment, all checked before the solve. The worker reports every problem at once and exits 2; a written result exits 0.
  • The image runs as a non-root user and holds no credentials. USER, a .dockerignore, and a job role at run time.
  • Tell the solver how many CPUs the container has. PYTHON_CPU_COUNT for Python, num_workers for CP-SAT; never leave a solver to count the host.

Design Note: Why Not One Container per Request


A simpler design runs the solve inside the API's container, as lesson Long solves: submit, poll, fetch did with a thread pool. It works until two large solves arrive at once and share the API's CPUs, or a solver crash ends the API's process (lesson Long solves: submit, poll, fetch showed one). Putting the solve in its own container, started per run, gives each solve its own CPUs, memory and time limit, and leaves the API small. The cost is start-up time: a container must be scheduled and its image pulled before the solve begins, which is why short requests stay in the API and only solves go to Batch (lesson AWS Batch on Fargate, Step Functions and Lambda: who does what).
