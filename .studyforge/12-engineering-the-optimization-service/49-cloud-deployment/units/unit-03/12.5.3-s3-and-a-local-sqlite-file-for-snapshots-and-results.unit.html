Lesson Versioned snapshots and content hashes stored each snapshot as a file named by its digest, on one machine's disk. Lesson Storing scenarios and results in SQLite stored scenarios and runs in a SQLite file. Now the solve runs in a container that Batch starts on a machine nobody chose (lesson AWS Batch on Fargate, Step Functions and Lambda: who does what), and that container cannot see the API's disk. The snapshot it reads and the result it writes must live somewhere both can reach, durably, and the regulator's question from lesson Versioned snapshots and content hashes still stands: which exact inputs produced the plan of record? This lesson splits storage in two. Amazon S3, AWS's object store, holds the content: every snapshot and every result, written once under a key derived from what it is. A local SQLite file next to the API holds one small row per run that points at those objects, so the questions planners ask ("every run of this snapshot", "what is still waiting") are SQL queries. (GridCap is fictional; no number in it is real.)

S3 here is moto's fake (lesson Testing AWS code against moto); no AWS is reached. A few terms: S3 stores objects (a body of bytes plus a little metadata) in a bucket, each under a key, a string such as results/730c…/run-0007.json. The slashes are only characters of the key; listing by a prefix such as results/ is how a "folder" is read.

A Snapshot's Key Is Its Digest, So Equal Content Is One Object

The store keeps lesson Versioned snapshots and content hashes's idea and moves it to S3: a snapshot's key is snapshots/sha256/<digest>.json, where the digest is the SHA-256 of the snapshot's canonical form, and the object's body is those canonical bytes. S3Store.put_snapshot:

Results go under the snapshot they solved, one object per run: results/<digest>/<run_id>.json. Every result of one snapshot is then one prefix listing away, and the key can be computed by anyone who knows the run and its snapshot, which lesson AWS Batch on Fargate, Step Functions and Lambda: who does what's poll relies on.

Every Write Is Conditional: S3 Refuses to Replace an Object

A plain put_object replaces whatever is at the key. Two workers retrying the same result, or a script "fixing" a snapshot, would overwrite history without a trace. S3 supports conditional writes: with the header If-None-Match: *, the S3 documentation says a write succeeds only if no object exists at the key, and otherwise fails with 412 Precondition Failed; of two such writes racing for one key, the first to finish wins. boto3 sends it as IfNoneMatch="*":

The two callers read the refusal differently, and that is the point of returning a flag:

  • A snapshot that already exists is a success. Same key means same content, so there is nothing to write. put_snapshot ignores the flag.
  • A result that already exists is an error. A run writes one result; a second write for the same run is a bug or a race, and must not replace the first:

S3 also has strong read-after-write consistency (its documentation states it for every PUT and DELETE of an object): once a write returns, every read sees it. So a poll that finds no result object right after the worker wrote one cannot happen.

Every Read Re-Hashes, and Versioning Keeps What an Overwrite Replaced

A conditional write protects against callers that use it. Anyone with write permission can still call put_object without the condition. So, as in lesson Versioned snapshots and content hashes, get_snapshot hashes the bytes it reads and compares the result with the key before trusting them:

The program overwrites the lean-2029 snapshot, unconditionally, with its 2029 budget changed from $7,000k to $7,900k in the stored bytes, then reads it:

Refusing the edit protects the next solve; it does not bring the inputs back. Versioning does. The bucket was created with versioning on (lesson Terraform for the optimization stack sets it in Terraform), and the S3 documentation explains that a versioned bucket keeps every version of an object: an overwrite adds a new current version, and a delete adds a delete marker. The original snapshot is still there:

The earlier version still hashes to its key, so the inputs of every run that read it can be recovered and checked. The two defences work together: the digest detects a change, and versioning keeps what the change replaced. Lesson Terraform for the optimization stack also blocks the IAM permissions that would allow the overwrite in the first place.

Problem statement

GridCap's asset team uploads condition surveys: a survey id, a region and a list of readings, one per asset. The risk model reads them, and an auditor must be able to fetch exactly the survey a risk score used. Store them in S3 the way the lesson stores snapshots.

In survey_store.py, write:

  • canonical(survey): the survey as bytes, so equal content gives equal bytes. The readings list has no meaningful order: sort it by asset_id. Then json.dumps with sorted keys, separators (",", ":") and ensure_ascii=True, encoded as ASCII.
  • put_survey(s3, bucket, survey): store the canonical bytes at survey_key(digest), where the digest is their SHA-256 in hex, and return the digest. The write must never replace an object that is already at the key: use S3's conditional write. A refusal because the key is taken (PreconditionFailed) is not an error; any other error (a missing bucket, say) must propagate.
  • get_survey(s3, bucket, digest): (survey, "ok") if the object's bytes hash to digest; (None, "corrupted") if they do not; (None, "missing") if there is no object (NoSuchKey). Any other error propagates.

The tests run against moto with fake credentials. survey_key is given; about 25 lines remain.

S3 answers "give me this key" and "list this prefix". It does not answer "which runs of snapshot 730c… finished optimal, best NPV first". A query like that wants rows. So the API keeps a SQLite file, as lesson Storing scenarios and results in SQLite did, with one row per run that points at its objects:



What goes where follows lesson Storing scenarios and results in SQLite's rule, "store as a whole what is used as a whole; store as rows what is queried":


  • The snapshot and the result are content, read whole by the worker and by the API. They live in S3. The index stores only their keys, never a copy, so the two cannot disagree.
  • The run's status and NPV are what planners filter and sort by. They are columns.
  • The last CHECK ties the two together: a run is submitted exactly when it has no result key. A finished status without a pointer to its result is refused by the database itself, whoever writes.


The connection is opened with lesson Storing scenarios and results in SQLite's connect (foreign keys on before any transaction, explicit transactions). finish is an UPDATE ... WHERE run_id = ? AND status = 'submitted', so a second poll that finds the same result changes nothing (lesson Storing scenarios and results in SQLite's version check in the WHERE clause, here on the status). run_index_demo.py indexes three runs (two of GridCap small, one of the lean-2029 snapshot), lets the worker finish two of them, and polls all three:

The file stays with the API. SQLite keeps a whole database in one local file with no server (lesson Storing scenarios and results in SQLite), which suits one API process that owns it. The Batch container and the Lambda function never touch the file (lesson AWS Batch on Fargate, Step Functions and Lambda: who does what's design note); they write to S3, and the API records what they wrote.


The Index Can Be Rebuilt From S3, Except for Runs Still Waiting


Because every result object carries its run id, snapshot digest, status and NPV, S3 holds everything the index says about a finished run. If the SQLite file is lost, a listing of results/ rebuilds it. rebuild uses a paginator, because a single list call returns at most 1,000 keys (lesson Testing AWS code against moto shows what happens without one):

Summary


  • A snapshot's key is its digest, so equal content is one object. Results live under the snapshot they solved: results/<digest>/<run_id>.json.
  • Every write is conditional. IfNoneMatch="*" makes S3 refuse to replace an object (412); an existing snapshot is fine, an existing result is an error.
  • Every read re-hashes, and versioning keeps what an overwrite replaced.
  • A local SQLite file indexes the runs, and S3 holds their content. Keys and queried fields are columns; a CHECK ties submitted to "no result key"; a poll records a result it finds.
  • The index can be rebuilt from S3, except for runs still waiting.

Design Note: Two Stores, One Direction of Truth


Two stores invite the question "which one is right?" Here the answer is fixed by direction: S3 is written first and never changed, and the index only ever points at S3 objects that exist. A row can lag behind S3 (a result written that no poll has recorded yet), but never run ahead of it, because finish takes its key from an object it just read. A rebuild repairs lag; nothing has to repair a row that points at nothing. Keeping the index to keys and queried fields, never copies of content, is what keeps that direction simple.
