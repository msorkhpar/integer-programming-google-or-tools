Everything is now in place to deploy GridCap's service: an image (lesson Containerizing a solver service), the Batch and Step Functions design (lesson AWS Batch on Fargate, Step Functions and Lambda: who does what), the store and index (lesson S3 and a local SQLite file for snapshots and results), a moto test suite (lesson Testing AWS code against moto), and the Terraform (lesson Terraform for the optimization stack). Done by hand, a release is a dozen commands typed in the right order by whoever has the AWS keys, and the day someone skips the tests or applies from a stale branch, the plan of record runs on code nobody reviewed. CI/CD (continuous integration and delivery) moves those commands into a file in the repository that a service runs on every change: the tests on every pull request, and the build and deploy on every merge to main. This lesson reads GridCap's workflow for GitHub Actions, GitHub's CI service, and checks it with a program. (GridCap is fictional; no number in it is real.)

This lesson is read-along for its workflow. The course does not run GitHub Actions: the file lives at deploy/github-workflows/ci.yml, not under .github/workflows/, so no service runs it. workflow_review.py parses it and reasons about it, and its output is printed. No model is built or changed here.

A Workflow Is Jobs, a Job Is Steps, and needs Orders the Jobs

A workflow is a YAML file. on names the events that start it; jobs holds the jobs, each run on a fresh machine (a runner) as a list of steps: a shell command (run) or a reusable action (uses). Jobs run in parallel unless one needs another. The head of GridCap's workflow:

It starts on every pull request, and on every push to main (a merge). Its three jobs are test, image (needs test) and deploy (needs test and image), and the last two carry if: github.event_name == 'push'. GitHub's workflow syntax reference states the rule that decides what runs: if a job's if is false it is skipped, and if a job it needs fails or is skipped, it is skipped too, all the way down the chain, unless its if uses a function such as always(). workflow_review.py applies that rule to the file for each event:

A pull request runs only the tests. A merge runs all three, in order, and a failing test stops the build and the deploy, because they need it. (The program reads only this file's simple ifs; it is a model of the rule, not of GitHub's expression language.)

One trap when a program reads a workflow. PyYAML follows YAML 1.1, in which a bare on is a boolean, so the key comes back as True:

GitHub reads the file its own way, so the workflow is fine; a script that looks up flow["on"] gets a KeyError. Quote it ("on":) or look up True when you parse workflows yourself.

CI Gets AWS Access From OIDC, Never From Stored Keys

The image and deploy jobs must act in AWS. The old way stores an access key as a repository secret; it never expires, and anyone who can change a workflow can print it. GitHub's documentation describes the replacement, OpenID Connect (OIDC): the job asks GitHub for a short-lived signed token that says which repository, branch and environment it runs for, and AWS exchanges it for temporary credentials of a role whose trust policy accepts exactly those claims (the audience sts.amazonaws.com, and a subject naming the repository). Nothing long-lived exists to steal. In the workflow it takes two things:

id-token: write lets the job request the token; configure-aws-credentials trades it for the role's credentials. Each job assumes its own role: gridcap-ci-push may push images to the registry, gridcap-ci-deploy may apply Terraform. The program confirms no secret is referenced anywhere:

Pin Every Action to a Commit and Give the Token Least Privilege

An action is someone else's code running with your job's permissions. A tag such as @v5 can be moved by whoever controls the action's repository, so the next run can execute different code. GitHub's security-hardening guide recommends pinning each action to a full-length commit SHA, which cannot move, with the version in a comment for people. The SHAs in this file are all zeros: placeholders, because the course cannot look up and verify each release's commit. A real workflow replaces each with the commit of the release its comment names.

The same guide says to give the workflow's GITHUB_TOKEN (the credential every job gets for GitHub itself) the least access it needs. The workflow sets contents: read at the top, and only the two jobs that talk to AWS add id-token: write. The program prints each job's needs, permissions, pins and environment:

The workflow syntax reference says a permissions block sets every scope it does not name to none, and that the job's block is applied after the workflow's. So image and deploy repeat contents: read, which checking out the code needs; without it they would have id-token alone.

Problem statement

The vegetation team is writing its own CI workflow for the trim planner. Before any workflow in the organisation may run, a lint step reads it, parsed by PyYAML, and refuses the habits this lesson warns about.

In workflow_lint.py, write lint(workflow). workflow is the parsed file (a dict; remember that PyYAML reads the key on as True, which this check does not need). Return the sorted findings, each once, as these exact texts:

  • workflow: no top-level permissions when the workflow has no permissions key, and workflow: permissions write-all when it is the string write-all. A job whose permissions is write-all gives JOB: permissions write-all.
  • JOB: REF is not pinned to a commit SHA for every uses: value not of the form owner/name@ followed by a full 40-character lower-case hex SHA. A local action, whose uses starts with ./, is code in the same repository and needs no pin.
  • JOB: uses secret NAME for every secrets.NAME found anywhere in a job's steps (run, with, env, at any depth), except GITHUB_TOKEN, the token GitHub gives every job.
  • JOB: id-token: write without an AWS credentials step when a job's permissions grant id-token: write and none of its steps uses aws-actions/configure-aws-credentials. A job with no permissions key of its own gets the workflow's, so a workflow-level id-token: write counts for it; a job that sets its own permissions uses only those. (The write-all finding, above, looks only at what each level writes itself.)

PINNED, SECRET, AWS_STEP and texts (every string inside a value) are given; about 20 lines remain.

Deploy Builds One Image per Commit, Then Plans, Checks and Applies Behind an Environment


The image job tags each image with the commit that built it, ${{ github.sha }}, and pushes it to the immutable repository of lesson Terraform for the optimization stack:



Every image is then traceable to a commit, and every run's container to its image. A planner's question "which code solved this?" has an answer: the job definition names the tag, and the tag is the commit.


The deploy job runs lesson Terraform for the optimization stack's loop, with its check between plan and apply:



plan_guard.py is the service repository's copy of lesson Terraform for the optimization stack's rule, exiting non-zero on a blocked plan. A non-zero exit fails the step, the job stops, and apply never runs. The plan is made with the new image's tag as -var "image=...", so the job definition's revision points at exactly the image this run built.


The job also names an environment, production. In GitHub, an environment can carry protection rules, such as required reviewers (up to six; one approval is enough); the workflow syntax reference says every protection rule must pass before a job that references the environment is sent to a runner. So a merge to main runs the tests and builds the image by itself, and the apply waits for a person to approve it.

Before the trim planner's workflow goes live, the team wants to answer "if this job fails, what still runs?" for any workflow, without pushing commits to find out. Model GitHub's rule from the lesson.


In job_outcomes.py, write outcomes(jobs, event, failing=frozenset()). jobs maps each job's name to its settings: needs (one name or a list, maybe missing) and if (maybe missing). It returns each job's outcome for one event: "success", "failure" or "skipped". A job that runs ends in "failure" if its name is in failing, and in "success" otherwise.


  • An if of the form github.event_name == 'NAME' skips the job when the event is not NAME.
  • A job whose needs did not all succeed (one failed, or one was skipped) is skipped, unless its if contains always(), which runs it whatever its needs did.
  • An if may hold both, joined by && (always() && github.event_name == 'push'). Both parts must hold: the event test is applied first, so on another event the job is skipped even with always(); on the named event, always() runs it whatever its needs did.
  • The dict may list a job before the jobs it needs; decide each job only after its needs.


You may assume the needs form no cycle and name only jobs in jobs. EVENT and needs_of are given; about 15 lines remain.

Summary


  • A workflow is jobs, a job is steps, and needs orders the jobs. A job whose need failed or was skipped is skipped; pull requests run the tests only. PyYAML reads on as True.
  • Tests run on every change, against moto, with no credentials.
  • CI gets AWS access from OIDC, never from stored keys. id-token: write and a role per job.
  • Pin every action to a commit and give the token least privilege. A permissions block sets every scope it does not name to none.
  • Deploy builds one image per commit, then plans, checks and applies behind an environment.
