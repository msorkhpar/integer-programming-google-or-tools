In AWS someone has to create them too, the same way in staging and in production, and change them later without breaking the runs already stored. Clicking through the console does not repeat, and a script of boto3 calls does not know what already exists. Terraform does both: you describe the resources you want in files, it compares them with what exists, shows you the difference as a plan, and makes only that change. This lesson reads the GridCap stack's Terraform and writes a check that refuses a plan which would destroy history. (GridCap is fictional; no number in it is real.)

This lesson is read-along for its Terraform. The course's runner has no Terraform and no network, and the course has no AWS account: the .tf files below were never planned or applied. The Python programs that read the policy and a plan did run, and their output is printed. No model is built or changed here.

Terraform Describes the Stack, plan Shows the Change, apply Makes It

Terraform's configuration language, HCL, describes each piece as a resource block: a type from a provider (here hashicorp/aws), a local name, and arguments. A resource can refer to another's attributes, aws_s3_bucket.runs.arn, and Terraform orders the work from those references. It records what it created in a state file, which maps each block to the real resource's id.

The working loop has three commands:

CommandWhat it does
terraform plan -out=tfplancompare the files with the state and the real resources; save the planned changes
terraform show -json tfplanthe saved plan as JSON, for programs to read
terraform apply tfplanmake exactly the saved changes, nothing else

Terraform's documentation calls the saved plan file opaque, meant for apply, and says to treat it as sensitive. Applying the saved file, rather than planning again inside apply, means what was reviewed is what happens. The stack's files sit in deploy/terraform/: variables.tf for what changes per environment (bucket name, image, subnets), main.tf for the resources, outputs.tf for the names the API's configuration reads afterwards.

The Bucket Keeps History: Versioning, No Public Access, prevent_destroy

The bucket holds every snapshot and result (lesson S3 and a local SQLite file for snapshots and results). Three blocks protect it:

  • prevent_destroy makes Terraform fail any plan that would destroy the bucket, including a replacement (destroy, then create). Terraform's documentation notes the limit: delete the whole block from the files and the protection goes with it.
  • Versioning is its own resource in the AWS provider. Lesson S3 and a local SQLite file for snapshots and results showed why it matters: an overwritten snapshot was still recoverable. The provider's documentation adds that destroying this resource suspends versioning on the bucket.
  • The public access block turns on all four of S3's Block Public Access settings. The provider defaults each to false; AWS recommends turning all four on. Planning data never needs a public URL.

The image registry gets the same treatment for a different reason:

With immutable tags, a tag pushed once can never point at another image. CI tags each image with its commit (lesson CI/CD with GitHub Actions), so a job definition that names a tag always runs the same bytes, which is lesson Containerizing a solver service's point about pinning, carried to the registry.

Problem statement

The trim planner's job role gets its own policy file, and the platform team wants each new policy checked in CI against the requests the job will make, and the ones it must never make. The lesson's allows knew only Allow statements written as lists. This one must handle what real policy files contain.

In iam_check.py, write allowed(policy, action, resource) for one identity policy document:

  • A statement applies when one of its Action patterns matches the action and one of its Resource patterns matches the resource. Action and Resource may each be a list of patterns or a single string (one pattern).
  • In a pattern, * matches any run of characters (also none) and ? exactly one character; every other character matches only itself. Actions match in any letter case (S3:getobject is s3:GetObject); resources match case exactly.
  • The answer is True only if some applying statement has "Effect": "Allow" and none has "Effect": "Deny". An explicit Deny always wins; with no applying statement, the request is denied.

This is a model of one policy, as the lesson's is: no conditions, no other policy types. The helper names matches, as_list and applies are declared for you; about 10 lines remain.

A Plan Is Data: Stop the Ones That Destroy History


terraform show -json turns a saved plan into JSON, documented in Terraform's "JSON output format". Each entry of resource_changes has the resource's address and a list of actions: ["no-op"], ["create"], ["read"], ["update"], ["delete"], or a replacement, ["delete", "create"] (destroy first) or ["create", "delete"] (create first). A program can read it before apply runs, and refuse. plan_review.py stops any plan that would delete a resource holding history: the bucket, its versioning, or the image registry.






The plan it reads, deploy/terraform/sample-plan.json, was written by hand in the documented shape; no Terraform ran. It holds one change of each kind: someone removed the versioning block (a destroy), renamed the compute environment (the provider says a new name forces a new resource, so a replacement), updated the Lambda code, and added a policy:



prevent_destroy on the bucket would not have caught this: the bucket is not destroyed, only its versioning resource, whose block was deleted from the files. The plan check sees the plan, not the files, so it catches it. Replacing the compute environment passes: it holds no data, and queued jobs are the only thing to plan around. Lesson CI/CD with GitHub Actions runs this check in CI, between plan and apply.

The vegetation team's Terraform puts its buckets inside a module and sometimes has to delete a scratch bucket on purpose. Their CI needs a gate that reports what a plan does and blocks only the deletes nobody approved.


In plan_gate.py, write gate(plan, protected, allowed=frozenset()). plan is the JSON of terraform show -json (this lesson): a resource_changes list whose entries have an address, a type, a mode ("managed", or "data" for a data source) and change.actions. Return a pair:


  • the sorted addresses to block: every change whose type is in protected, whose actions delete it (a plain delete, or a replacement in either order), and whose address is not in allowed. A resource inside a module has an address such as module.storage.aws_s3_bucket.runs; its type is still aws_s3_bucket.
  • a dict counting the changes by verb, from VERBS: ["delete", "create"] and ["create", "delete"] are one replace each. Every change counts, data-source reads included. Verbs with no change are left out.


VERBS is given; about 8 lines remain.

Summary


  • Terraform describes the stack; plan shows the change; apply makes it. Apply the saved plan, so what was reviewed is what happens.
  • The bucket keeps history: versioning, all four public-access blocks, prevent_destroy; the registry's tags are immutable.
  • Batch and Step Functions are declared the way the programs created them; the state machine reads the same definition file. No database resource: the index is the API's SQLite file.
  • Each role gets only what its part needs. The job reads snapshots/* and writes results/*.
  • A plan is data: stop the ones that destroy history. resource_changes[].change.actions.

Design Note: The Files Are the Review


With Terraform, a change to the stack is a change to text: it goes through a pull request, a reviewer reads the diff, CI prints the plan, and the check of this lesson refuses what no reviewer should have to catch by eye. The console and ad-hoc scripts skip all of that, and leave a stack nobody can rebuild. Terraform's state file is the price: it must be stored safely (it is kept out of the image by lesson Containerizing a solver service's .dockerignore) and shared by everyone who applies.
