The GridCap service now has an image (lesson Containerizing a solver service). In lesson Long solves: submit, poll, fetch its solves ran on worker threads inside the API's own process, one machine for everything. On the medium portfolio a solve can take many minutes; in the planning cycle's last week, a dozen planners submit scenarios within an hour. The API should answer in milliseconds whatever the solver is doing, and each solve should get its own CPUs, its own memory and its own time limit. AWS offers several services that can run code. This lesson gives each part of a run to the one built for it: AWS Batch on Fargate runs the solve, Step Functions watches it, Lambda does the short clean-up, S3 holds the data (lesson S3 and a local SQLite file for snapshots and results), and the API keeps answering. (GridCap is fictional; no number in it is real.)

Everything runnable here talks to moto, a library that imitates AWS inside the Python process (lesson Testing AWS code against moto covers it). No AWS account is used, and the account id in every ARN, 123456789012, is moto's placeholder.

The Model

The worker solves the model of lesson Schemas for model inputs from a validated snapshot, unchanged. It is restated here whole.

Sets. $Y$ the plan's years, in order; $P$ the candidate projects; $T_i$ the start years of project $i$: the years $t$ with $e_i \le t \le l_i$ and $t + d_i - 1 \le \max Y$; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, each with parent $p(c)$ and lag $L_c$; $Q$ the programs, with $q(i)$ the program of project $i$; $R$ the regions, with $r(i)$ the region of project $i$.

Parameters. $e_i, l_i$, the earliest and latest start years; $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k), $d_i$ its years of work, and $\text{capex}_i = \sum_k c_{i,k}$; $\text{npv}_{i,t}$ ($k); $m_i$, crew-months per year of work; $B_y$, the budget of year $y$ ($k); $K_{q,y}$, the crew-months of program $q$ in year $y$; $\text{floor}_r$, the least region $r$ receives over the plan ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$.

Constraints.

What changes is where it runs: in a container started for one run, with a time limit from the run's settings (lesson Containerizing a solver service). On GridCap small it solves to an NPV of $22,741k, as in lesson Data-quality checks that prevent infeasibility.

Each Service Does the Part It Is Built For

A run has five parts, and each needs something different:

PartNeedsWho does it
accept the scenario, answer pollsanswers in milliseconds, always upthe API (lesson Long solves: submit, poll, fetch), with the SQLite run index (lesson S3 and a local SQLite file for snapshots and results)
keep the snapshot and the resultdurable, write-once objectsS3 (lesson S3 and a local SQLite file for snapshots and results)
solveminutes to hours, several CPUs, gigabytes of memoryAWS Batch on Fargate
wait for the solve, react when it failsruns as long as the job, retries, branches on errorsStep Functions
write a failed result when the job never coulda few seconds of code, on demandLambda

The choice follows from documented limits:

  • Lambda runs a function for at most 900 seconds (15 minutes), with up to 10,240 MB of memory. A solve has no such bound: the medium portfolio with a long limit, or the large one, can take an hour. A function stopped at 15 minutes leaves no result at all. So Lambda never solves; it does the small glue steps, which finish in seconds.
  • AWS Batch runs a container as a job: it queues jobs, starts each one when capacity is free, and records its status until it ends as SUCCEEDED or FAILED. On Fargate, AWS supplies the machine: no servers to patch or scale, and each job gets exactly the vCPUs and memory its definition asks for. A job's own timeout (at least 60 seconds) is its only time bound.
  • Step Functions runs a state machine: a JSON definition of steps (states) and the moves between them. A Standard workflow may run for up to a year, so it can wait for the longest solve. It is the part that knows what to do when the job fails.

The API does none of the waiting. It stores the snapshot, starts the run, writes one index row, and answers 202 Accepted as in lesson Long solves: submit, poll, fetch. Later polls read the index, and the result object in S3.

A Job Definition Fixes the Image, Size, Timeout and Retries; a Submission Names the Run

Batch separates what every solve shares from what one run needs. The job definition is the template, registered once (by Terraform in lesson Terraform for the optimization stack): the image, its command, its size, the two roles, a timeout and a retry count. batch_stack.py registers it in moto:

The fields the AWS Batch documentation requires for Fargate are all here: platformCapabilities of FARGATE, the container type, an execution role (what Fargate itself uses to pull the image and write logs), and the size as resourceRequirements. The job role is separate: it is what the solve's own code may do, read snapshots and write results, and nothing else (lesson Terraform for the optimization stack writes it). assignPublicIp is DISABLED; the documentation says that a job whose subnet has no NAT gateway needs it ENABLED for outbound network access, so this design assumes subnets with a NAT gateway.

Fargate sizes come in fixed pairs. A job asks for vCPUs and memory, and Fargate accepts only these combinations (from the AWS Batch API reference for ResourceRequirement):

0.25512, 1024, 2048
0.51024 to 4096, in steps of 1024
12048 to 8192, in steps of 1024
24096 to 16384, in steps of 1024
48192 to 30720, in steps of 1024
816384 to 61440, in steps of 4096
1632768 to 122880, in steps of 8192

So "1 vCPU and 12 GB" is not a size: it becomes 2 vCPUs (the smallest that allows 12,288 MiB), or the memory comes down. The worker's 2 vCPUs and 8,192 MiB is a valid pair.

A submission names one run. submit_solve sends what changes per run, as environment overrides that the worker's settings read (lesson Containerizing a solver service):

Two choices to notice:

  • The job's timeout is longer than the solver's limit. The solver stops itself at its limit and writes a time_limit result with its best plan. Batch's timeout is the backstop for a job that hangs: the documentation says a job stopped by its timeout is not retried, and it writes nothing. If the two were equal, Batch could kill the worker in the seconds it needs to write the result, and the planner would lose a plan the solver had found. Ten minutes of margin covers pulling the image, reading the snapshot and writing the result.
  • Batch has no idempotency token. SubmitJob takes no client token, so the same call sent twice starts two jobs. The next section puts the run's start behind Step Functions, whose execution name does deduplicate.

Problem statement

The vegetation team's trim planner is a CP-SAT model that assigns line-clearance crews to circuits. It now runs as a Batch job on Fargate: the job definition trim-solve and the queue trim-queue exist. What is missing is the call that submits one plan's solve, sized for the plan.

In trim_jobs.py, write submit_trim(batch, queue, definition, plan_id, circuits, limit_s). It makes one batch.submit_job call and returns the jobId Batch gives back. The call carries:

  • jobName: job_name(plan_id). Batch accepts only letters, digits, hyphens and underscores, with a letter or digit first, and at most 128 characters. Replace every other character with -, drop leading hyphens and underscores, and cut to 128. ("#7 west/north" gives "7-west-north".)
  • the given jobQueue and jobDefinition;
  • containerOverrides with environment PLAN_ID (the plan id as given), TIME_LIMIT_S (str(limit_s)) and CPSAT_WORKERS (the vCPU count, as a string), and resourceRequirements VCPU and MEMORY (strings), from SIZES: up to 500 circuits, 1 vCPU and 2,048 MiB; up to 5,000, 2 vCPUs and 8,192 MiB; more, 4 vCPUs and 16,384 MiB. Each is a valid Fargate pair.
  • timeout: {"attemptDurationSeconds": ...}, twice the solver's limit, and never under Batch's minimum of 60 seconds.

Step Functions Waits for the Job and Catches What the Worker Cannot


The worker writes a result for every way a solve can end (lesson Long solves: submit, poll, fetch's statuses). But some failures happen outside the worker: the image cannot be pulled, the container runs out of memory, or Batch's timeout stops it. Then no result is written, and a planner would poll submitted forever. A state machine closes that gap. Its definition is read-along JSON in the Amazon States Language, deploy/stepfunctions/solve-run.asl.json:



  • batch:submitJob.sync is Step Functions' "run a job" pattern: it submits the Batch job and waits until the job finishes, then moves on. A field ending in .$ takes its value from the execution's input by a JSONPath ($.run_id).
  • Catch sends any error (States.ALL) to RecordFailure, with the error added to the input under error (that is what ResultPath does in a catcher).


How a state reacts to an error, as the Step Functions documentation describes it: the state's Retry list is tried first, and the first retrier whose ErrorEquals names the error retries the state, up to its MaxAttempts (3 unless set; 0 means never), waiting IntervalSeconds and then multiplying the wait by BackoffRate. When no retrier matches, or the matching one has used its attempts, the Catch list is scanned in order and the first catcher that names the error decides the next state. With neither, the whole execution fails. Two names are wildcards: States.ALL matches any error and must stand alone, in the last retrier or catcher; States.TaskFailed matches any error except States.Timeout, which a task reports when it runs past its own TimeoutSeconds.


step_functions.py reads the definition and prints each state, where it goes next and where an error goes:



RecordFailure calls a Lambda function, the one short task in the design. It writes a failed result in the run's place, unless the worker wrote one after all:



Its retry rule in the definition retries Lambda's own transient errors (Lambda.ServiceException, Lambda.SdkClientException), so a second call must be harmless. It is, because a result is written only if none exists (S3's conditional write, lesson S3 and a local SQLite file for snapshots and results). moto stores a state machine but runs none of its states, so the program calls the function itself, twice, with the input the catcher would pass. The key it returns has the shape results/<digest>/<run>.json; the program prints the 64-character digest cut to its first 12 characters and ...:



The execution's name is the run id, and that makes starting a run idempotent. The Step Functions API reference says that for a Standard workflow, starting an execution with the name and input of one that is still running returns that execution instead of starting another, and that the same name with different input is refused with ExecutionAlreadyExists. The API's retry of a "start run" call therefore cannot start a second solve. moto behaves the same way here:




So in production the API starts the state machine with the run's input rather than calling submit_job itself; submit_solve above is what the Solve state does on its behalf, and is the call this module tests. The Step Functions documentation adds that a closed execution's name is refused too, and can be reused only 90 days after it closed, so a run id is never recycled.

Problem statement


GridCap's report-publishing state machine has a Task state that posts a finished plan to the planners' reporting system. That system throttles, times out and rejects bad input, and the operations team wants to know, before deploying, what the state will do for a given run of errors. Write a function that answers it, by the rules the lesson quotes from the Step Functions documentation.


In error_routing.py, write route(state, errors). state is a Task state's dict (its Retry and Catch lists may be missing). errors are the error names of consecutive failed attempts; if the state is still going after the last one, the next attempt succeeds. Return the list of what happened, one entry per error, using "retry", "catch:<Next>" and "fail", and "succeeded" at the end if the state got there. Stop at the first catch or fail.


  • For each error, the first retrier whose ErrorEquals names it decides. If that retrier has retries left (MaxAttempts, 3 when missing; 0 means never), it is a retry, counted against that retrier only.
  • Otherwise (no retrier names the error, or the first one that does is used up) the first catcher whose ErrorEquals names the error gives catch:<its Next>. With no such catcher, fail.
  • Write matches(names, error): States.ALL matches any error; States.TaskFailed matches any error except States.Timeout; any other name matches only itself.


Waiting times (IntervalSeconds, BackoffRate) do not change the route; ignore them. About 20 lines remain.

Summary


  • Each service does the part it is built for. The API answers; S3 keeps data; Batch on Fargate solves; Step Functions waits and catches; Lambda (900 s at most) does short glue, never the solve.
  • A job definition fixes the image, size, timeout and retries; a submission names the run. Fargate accepts only listed vCPU and memory pairs. The job's timeout exceeds the solver's limit.
  • Step Functions waits for the job and catches what the worker cannot. submitJob.sync waits; a Catch routes a failed job to a Lambda that writes a failed result once.
  • Batch has no idempotency token; a Step Functions execution name does. Name the execution after the run.
  • moto marks Batch jobs SUCCEEDED without running them. Trust the result object, not the job status.

Design Note: Why the Index Is Not Written by the Cloud


The index is a SQLite file on the API's own disk (lesson S3 and a local SQLite file for snapshots and results), so neither Batch nor Lambda writes to it: they would need a path into the API's machine. Instead, everything the cloud produces lands in S3 under a key the API can compute from the run (results/<digest>/<run>.json), and the API records it on the next poll. The cloud parts never need to know the index exists, and the index can be rebuilt from S3 if its file is lost.
