The scenario service of lessons Scenarios as data: create, copy, optimize to Planning-cycle states and locking forgets everything when its process stops. Its rules also live only in Python: any script that opens the data directly can edit a locked scenario, delete an audit entry, or save half a run. GridCap's planners need the base scenario, the three-overrides copy, the trail of who changed what, and both runs to be there tomorrow, exactly as they were left, and they need the rules to hold whoever writes to the store.

This lesson stores scenarios, audit entries and runs in SQLite, a database engine that keeps a whole database in one file and ships with Python as the sqlite3 module, so it needs no server and runs in the course's offline runner. It moves the rules of the earlier lessons into the database where it can: transactions keep a change and its audit entry together, the version check becomes part of the UPDATE, and triggers and a partial unique index refuse what no caller may do. The lesson ends with the module's whole workflow: copy a scenario, override three projects, re-optimize, and diff the two runs in SQL.

GridCap is a fictional utility's portfolio, generated for this course; no number in it is real. The people (planner-a, ...) are placeholders. The programs put their database in a temporary directory and delete it when they finish.

The Model

Storage does not change the model: every run stored here solved the model of lesson Manual overrides as bounds, with an audit trail, restated here.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k), from the scenario's stored inputs; $l_{i,t}$ and $u_{i,t}$, the bounds set by the scenario's overrides (lesson Manual overrides as bounds, with an audit trail).

Variables. $x_{i,t} \in \{0, 1\}$ with $l_{i,t} \le x_{i,t} \le u_{i,t}$ for every $i \in P$ and $t \in T_i$; $\text{started}(i) = \sum_{t \in T_i} x_{i,t}$ and $\text{by}(i, t) = \sum_{s \in T_i,\, s \le t} x_{i,s}$.

Constraints.

A stored run keeps the solution $x^*$ as one row per funded project, (project, start_year), which is the pair $(i, t)$ with $x^*_{i,t} = 1$.

A Scenario's Inputs Are One JSON Column, and a Run's Plan Is Rows

Four tables hold everything. Here are the scenario and run tables of store.SCHEMA:

The fourth table, audit, has one column per field of lesson Manual overrides as bounds, with an audit trail's AuditEntry, with the bound changes in a JSON column.

Two choices shape the schema, and they go opposite ways for a reason.

A scenario's inputs are one JSON text column. The service always reads and writes the inputs as a whole: to build a model, to compute the snapshot, to copy. Nobody asks the database "which scenarios have a 2030 budget above $8,000k". So the inputs are stored as the same canonical JSON that Scenario.inputs() produces, and the snapshot sits in its own column beside them. SQLite keeps JSON as ordinary text, and the CHECK (json_valid(inputs)) refuses text that is not well-formed JSON. The state, version, cycle and names are separate columns because the service does query them: every write filters on version, and the lock rule below filters on cycle and state.

A run's plan is rows, one per funded project, because plans are queried: the diff at the end of this lesson compares two runs project by project in SQL. The primary key (run_id, project) makes "one start year per project per run" a rule the database keeps.

STRICT after a table makes SQLite enforce the declared column types, which ordinary SQLite tables do not: without it, a text value such as 'soon' in the INTEGER column start_year would be stored as it is. A STRICT table converts a value only when nothing is lost, and refuses the rest. INTEGER PRIMARY KEY gives each run an id the database assigns, which is where ids come from in a real service (lesson Scenarios as data: create, copy, optimize's design note). The run keeps the version and snapshot it was solved on, so lesson Planning-cycle states and locking's question "does this run belong to the scenario's current inputs?" can be answered from the tables.

Foreign Keys Are Off Until a Connection Turns Them On, Outside Any Transaction

REFERENCES scenario (scenario_id) declares a foreign key: every run must name a scenario that exists. SQLite's documentation says foreign key enforcement is off by default, must be switched on by each connection with PRAGMA foreign_keys = ON, and cannot be switched on in the middle of a transaction, where the pragma does nothing and reports no error. Python's sqlite3 adds a twist. With autocommit=False, which its documentation recommends, a transaction is always open, starting with connect() itself. fk_pragma.py tries both orders on two in-memory databases.

Two of the features this lesson uses are recent, so check your versions before you copy the code. The autocommit argument of sqlite3.connect() and the Connection.autocommit attribute exist from Python 3.12 on; on an older Python, connect() refuses the argument. FULL OUTER JOIN, used by the diff query at the end of this lesson and by its last practice, is understood by the SQLite library from version 3.39.0 on; an older library reports a syntax error. Python's sqlite3 uses the SQLite library it was built with, which is not always the newest one on the machine. The first line fk_pragma.py prints is the runner's two versions, both new enough:

A Change and Its Audit Entry Commit Together, or Not at All

A transaction is a group of statements the database applies as one: all of them, or none. In sqlite3, a connection used as a context manager (with conn:) commits when the block ends normally and rolls back when it raises; it does not close the connection, which the programs do with contextlib.closing. The store wraps every change that belongs together in one such block. An override and its audit entry are one change:

If _write refuses (a stale version, below), the block raises and the audit entry is never stored, so the trail cannot claim an override that the scenario does not have. The reverse holds too: an override cannot be stored without its entry. Lesson Manual overrides as bounds, with an audit trail's check that the trail replays to the overrides in force depends on this.

A run is three changes: the run row, its run_start rows, and the scenario's move to Post-Opt.

Every value reaches SQL through a ? placeholder, never through string formatting. The sqlite3 documentation insists on this to prevent SQL injection: a planner's reason containing a quote, such as no crew ' OR 1=1 --, stays text instead of becoming SQL. sqlite_store.py tries to save a run whose plan has a project with no start year, which the NOT NULL on start_year refuses after the run row was already inserted:

Still two runs. The run row inserted before the failure was rolled back with it, so the store never holds a run without its plan, which a diff would read as "funds nothing".

Problem statement

Riverbend Water (invented for this practice) keeps one cost estimate per main-replacement project: one estimate row and its estimate_line rows (estimate.py has the schema; a line's amount may not be negative). Engineers revise estimates often, and a revision replaces the project's earlier estimate. A report that finds a header without its lines prints a $0 job, and one that finds no estimate at all drops the project, so a failed revision must leave the old estimate exactly as it was. Street names such as O'Brien Street are common.

Write save_estimate(conn, project, lines) in estimate.py. lines is a list of (item, amount). It replaces the project's estimate, if it has one, with a new header and the given lines, and returns the new estimate_id. If any line is refused by the database, the exception reaches the caller and the database is as it was before the call. A saved estimate must be visible to other connections to the same database file. connect already opens connections with foreign keys on and autocommit=False (an argument of Python 3.12 and later; the runner has 3.14.7). The foreign key is checked on every statement, so to replace an estimate, delete the old estimate's lines before its header: a header deleted while its lines still point at it is refused. About eight lines.

The Version Check Is the UPDATE's WHERE Clause, and rowcount Says Whether It Held


Lesson Planning-cycle states and locking compared versions in Python. Reading the version and then writing is two steps, and another process could write in between. In SQL the check and the write are one statement:



The UPDATE changes the row only if it still has the version the caller read. Cursor.rowcount reports how many rows an UPDATE changed, so 0 means somebody else wrote first. version = version + 1 is computed by the database from the row it is changing, never from a number the caller sends. sqlite_store.py sends an edit of S-002 stamped with version 2 after the scenario has moved on:



_write also runs lesson Planning-cycle states and locking's transition table before the UPDATE (TRANSITIONS.get((state, action))), so the state machine and the version check guard every path that changes a scenario.


The Database Refuses What No Caller May Do


Some rules must hold even for code that never calls the service: a maintenance script, a colleague's notebook, a bug in a future handler. Those rules go into the schema.




A trigger is SQL the database runs when a table is changed. BEFORE UPDATE ... WHEN OLD.state = 'Budget Lock' fires on any update of a row that is locked (OLD is the row before the change), and RAISE(ABORT, ...) stops the statement, undoes what it did, and returns the message as an error. The audit triggers fire on every update or delete of the trail, which makes it append-only for every writer.


A partial index indexes only the rows its WHERE clause selects. Declared UNIQUE, it makes a column unique among those rows only: here, cycle is unique among locked scenarios, so a cycle has at most one plan of record, while any number of unlocked scenarios share it. That is lesson Planning-cycle states and locking's loop over all scenarios, kept by the database.

The first two came from raw UPDATE and DELETE statements that no service code wrote; the third came through store.lock, whose own Python has no "one per cycle" check at all. All three are refused by the database. The message of the last one is the database's, not a planner's sentence; a service catches IntegrityError and translates it, as lesson Turning an IIS into a planner message translates rows into rules.

Each run records the version and snapshot it was solved on. Run 1 started from version 2 of the base (after its check); run 2 from version 5 of the copy, after three overrides and a check. The trail of the copy, read back from the audit table:



The diff of the two runs is one query. A full outer join keeps every project that is in either plan, with NULL on the side that lacks it, which is exactly the shape of selected, deferred and shifted:



A row with no year in run a is selected, one with no year in run b is deferred, and one with two different years is shifted. IS NOT treats NULL as an ordinary value, so a project present on one side only passes the filter; with <>, any comparison with NULL is unknown and the row would be dropped. :a and :b are named placeholders, the other style the sqlite3 documentation describes.

Summary


  • A scenario's inputs are one JSON column, and a run's plan is rows. Store as a whole what is used as a whole; store as rows what is queried. STRICT enforces column types.
  • Foreign keys are off until a connection turns them on, outside any transaction. With autocommit=False the pragma is silently ignored; send it first.
  • A change and its audit entry commit together, or not at all. with conn: commits or rolls back the whole block; values go through ? placeholders.
  • The version check is the UPDATE's WHERE clause, and rowcount says whether it held. Zero rows changed means a stale read.
  • The database refuses what no caller may do. Triggers freeze locked scenarios and the audit trail; a partial unique index allows one plan of record per cycle.
  • Diff runs in SQL with a full outer join over the plan rows.

Design Note: Rules in Two Places, on Purpose


Several rules here exist twice: the Python service checks the transition table and the lock conditions, and the database refuses locked updates and a second plan of record. The service's checks give a planner a clear sentence and run before any SQL; the database's checks hold for every writer, including ones that skip the service. A rule kept only in Python is a convention; a rule kept only in the database answers with messages like UNIQUE constraint failed: scenario.cycle. Keeping both, and testing that they agree (lesson Unit-testing one constraint at a time), gives clear messages and rules that hold.
