Lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock set out what each stage of GridCap's planning cycle allows, and enforced it with a dictionary and one if in a single program. A planning service has more to guard against than one program does. Several planners work on the same scenario at once, from different browser tabs. A solve takes minutes, and somebody edits the scenario while it runs. Two managers each believe their scenario is the one going to finance. This lesson turns the stages into rules a service checks on every request: a transition table, a version number on every scenario, and a lock that admits one plan of record per planning cycle.

GridCap is a fictional utility's portfolio, generated for this course; no number in it is real. The people (planner-a, manager-a, ...) are placeholders. The service here keeps its scenarios in memory, so the rules can be read without a database; lesson Storing scenarios and results in SQLite moves the same rules into SQLite.

The Model

The rules of this lesson decide when a scenario may be optimized, not what is optimized. Every run solves the model of lesson Manual overrides as bounds, with an audit trail, unchanged, restated here.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k), from the scenario; $l_{i,t}$ and $u_{i,t}$, the bounds that the scenario's overrides set (lesson Manual overrides as bounds, with an audit trail), $0$ and $1$ by default.

Variables. $x_{i,t} \in \{0, 1\}$ with $l_{i,t} \le x_{i,t} \le u_{i,t}$ for every $i \in P$ and $t \in T_i$; $\text{started}(i) = \sum_{t \in T_i} x_{i,t}$ and $\text{by}(i, t) = \sum_{s \in T_i,\, s \le t} x_{i,s}$.

Every Request Is Checked Against One Transition Table

A state machine is a set of states, a set of actions, and a table that says, for each state and action, which state comes next, or that the action is refused. Writing the planning cycle this way puts every rule of lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock in one place:

A pair that is not in the dictionary is refused. cycle_states.py prints the whole table, every state against every action:

Each cell is a rule a planner can read:

  • Initial takes edits and moves to Pre-Opt on check, the data checks that must pass before a scenario may be solved. This service records only the move; the checks themselves are those of lessons Validating inputs before the solve and Data-quality checks that prevent infeasibility.
  • Pre-Opt takes edits and moves to Post-Opt when a run finishes.
  • Post-Opt allows a rerun of the same inputs (an "ad hoc rerun") and stays there. An edit sends the scenario back to Pre-Opt, because its plan no longer matches its inputs, which is lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock's rule that every override needs a rerun.
  • Budget Lock refuses everything. A change after lock is a copy.

One function moves a scenario, and every request goes through it:

The program walks the base scenario through the cycle, trying a few things the table forbids:

Keeping the rules in a table, rather than in if statements spread across the handlers, has two practical gains. The table can be printed, as above, and reviewed by someone who does not read Python. And adding a stage or an action changes one dictionary, with every handler picking it up, instead of a hunt for every if that should have changed.

A copy is not in the table because it does not change the scenario it copies. Any scenario may be copied, a locked one included, and the copy always starts in Initial with a parent_id, as in lesson Scenarios as data: create, copy, optimize.

Problem statement

A school district (invented for this practice) approves its yearly building-repair program with the workflow in TABLE (in approval.py): a draft is edited and submitted, the board approves or rejects a submission (a rejected program goes back to Draft), and an approved program can only be archived. An auditor wants three answers from the table itself, never from a second copy of the rules:

  • allowed(state): the sorted list of actions the state accepts.
  • walk(state, actions): apply the actions in order and return (final state, None); if an action is refused, stop there and return (the state it was refused in, that action).
  • reachable(state): the sorted list of every state that some sequence of allowed actions can lead to from state, state itself included. The board's question is whether an approved program can ever get back to Draft.

A Write Names the Version It Read, and a Stale Write Is Refused


Two planners open S-001 in two tabs. planner-a cuts the 2029 budget and saves; a minute later planner-b, whose tab still shows the old budgets, changes 2031 and saves. If the service simply stored whatever arrived, planner-b's save would write back the old 2029 budget along with the new 2031 one, and planner-a's cut would vanish without a trace. That is a lost update.


The cure used here is optimistic locking: every scenario has a version number, every read returns it, every write must state the version it read, and the service refuses a write whose version is no longer current. Nothing is held locked while a planner thinks, which is why it is called optimistic; the conflict is caught when it happens, at the write.




read hands back a deep copy, so a planner's unsaved changes live only in that copy: the stored scenario changes only through edit, which checks the version first. concurrent_edits.py plays the two tabs:



planner-b's first save is refused, not merged. The service cannot know whether the 2031 change still makes sense with the new 2029 budget, so it asks the person to read the scenario again and decide. After the second read and save, both changes are in the scenario: 8,000 for 2029 and 7,000 for 2031.


Every successful write adds one to the version, state moves included, so a version number names exactly one state of the scenario.

Problem statement


The school district's (invented for this practice) facility planners edit repair plans from several laptops at once. A plan is a dict such as {"roofs": 400, "boilers": 250}. Two planners who read the same plan and both save would lose one of the two changes, so the store keeps a version number per plan, starting at 1.


Finish Store in store.py:


  • read(plan_id) returns the plan and its version. A caller may change the dict it gets back as much as it likes; that must not change the stored plan.
  • save(plan_id, read_version, plan) stores plan and returns the new version, one more than before, if the plan is still at read_version. Otherwise it returns None and stores nothing. A caller who keeps changing its dict after a save must not change the stored plan either.

A Run Belongs to the Version It Started From


A solve on GridCap medium or large can take minutes (lesson Long solves: submit, poll, fetch runs such solves as jobs). While it runs, a planner may edit the scenario. When the run finishes, its plan answers the old inputs. If the service attached it anyway, the scenario would sit in Post-Opt with a plan that no run of its current inputs produced.


So a run carries a ticket: the scenario id, the version it started from, and a private copy of the inputs it solves. The ticket is taken when the run starts, and the run is attached only if the scenario is still at that version:



The run solves ticket.inputs, never the stored scenario, which may change under it. In the program a planner edits the 2030 budget while the run is out:



The stale run's NPV, $23,866k, is a real number for the inputs of version 4. Shown beside the budgets of version 5 it would overstate the plan by $358k. The service refuses it, the scenario stays in Pre-Opt, and the rerun on version 5 is the one attached. This is the "result current" check of lesson Scenarios as data: create, copy, optimize made into a rule: there it was a function a caller could forget to call, here the service will not attach a run that fails it.


Budget Lock Needs a Current Optimal Run, and a Cycle Has One Plan of Record


Locking is the last move, and the most consequential one: the locked plan is the plan of record, the one finance budgets against and the regulator sees (lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock). lock checks three things before it moves the scenario:



  • The table. Only a Post-Opt scenario may be locked.
  • A current, optimal run. The run's snapshot must equal the scenario's, and the run must have found a plan. In this service the table already guarantees the first, because any edit leaves Post-Opt; the check stays as a second line of defence, since a lock is too important to rest on one rule. An infeasible run also ends in Post-Opt (a run finished), so the status check is not redundant: an infeasible scenario has no plan to lock.
  • One plan of record per cycle. Every scenario belongs to a planning cycle, here 2027 plan. If another scenario of the same cycle is already locked, the lock is refused.


The end of concurrent_edits.py locks S-001, then tries to lock an alternative scenario of the same cycle:



Without that rule, two locked scenarios could both claim to be the plan of record, and finance and the regulator could be handed different plans, each correctly locked. Replacing a plan of record is a decision, which this service would model as an explicit action (unlock the old one with a reason, then lock the new one), never as a side effect of locking something else. Lesson Storing scenarios and results in SQLite enforces this rule in the database itself, where two service processes cannot both pass it.

Summary


  • Every request is checked against one transition table. A state and an action give the next state, or a refusal; the table is printable and is the only place the rules live.
  • A write names the version it read, and a stale write is refused. Optimistic locking prevents lost updates without holding anything locked while people think.
  • A run belongs to the version it started from. A run solves a private copy of the inputs and is attached only if the scenario has not changed since it started.
  • Budget Lock needs a current optimal run, and a cycle has one plan of record. Locking checks the table, the run's snapshot and status, and the other scenarios of the cycle.

Design Note: Refuse, Don't Merge


Both conflicts in this lesson, two planners editing one scenario and an edit during a run, could be "resolved" automatically: merge the two budget changes, or attach the stale run with a warning. The service refuses both instead, and asks a person to look again. A merged scenario is one that no person reviewed, and an attached stale run is a plan that no run of the current inputs produced. Lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock's rule was that every change goes back through the model; this lesson adds that every change goes back through a person who saw the current version.
