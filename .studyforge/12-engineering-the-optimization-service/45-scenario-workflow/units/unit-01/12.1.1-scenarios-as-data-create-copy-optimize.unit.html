GridCap's planners have been answering what-if questions from a notebook. They load the small portfolio, change a budget in a dictionary, rerun the model, and paste the NPV into a spreadsheet. Finance asks what happens if 2030 gets $860k less, $7,750k instead of $8,610k. Someone edits the dictionary, reruns, and a week later nobody can say which pasted NPV belongs to which budget, or whether the base plan on the projector was solved before or after the edit.

Lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock described the cure in words: a scenario is a copy with its own snapshot, never an edit of another scenario. This lesson writes it as code a service can rely on. A scenario becomes a plain record of inputs. A copy shares nothing that can change with its parent. The record survives a trip through JSON, so it can be stored and sent over a network. And optimizing a scenario is a function that builds the model from the record and stamps the result with the inputs it used.

GridCap is a fictional utility's portfolio, generated for this course; no number in it is real. The people in the examples (planner-a, planner-b, ...) are placeholders.

The Model

Every scenario in this module builds the same model from its own data; only the parameters and the bounds differ. It is the multi-period model of lessons Start-time variables x(i,t) and timing windows to Aggregated vs. cumulative (disaggregated) forms with the must-do, alternative and parent rules of lessons Must-do vs. discretionary planning groups to Mutually exclusive alternatives (repair vs. replace), built by plan_model.build.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use (its window); $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups, each a set of projects; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$, the NPV of project $i$ started in year $t$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work, $k = 0, 1, \dots$ ($k); $B_y$, the budget of year $y$ ($k), taken from the scenario; $l_{i,t}, u_{i,t}$, the bounds of each start variable, $0$ and $1$ unless an override changes them (lesson Manual overrides as bounds, with an audit trail).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$, with $l_{i,t} \le x_{i,t} \le u_{i,t}$: project $i$ starts in year $t$. We write $\text{started}(i) = \sum_{t \in T_i} x_{i,t}$ and $\text{by}(i, t) = \sum_{s \in T_i,\, s \le t} x_{i,s}$.

A Scenario Is a Record of Inputs, Kept Apart From the Model

A scenario is one named set of planning inputs (lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock). In code it is a plain record, a Python dataclass with no solver object inside it. scenario_record.py creates GridCap's base scenario and prints what the record holds:

The record has two kinds of field, and the difference matters for everything that follows:

  • Inputs are what the model is built from: data (which portfolio), budget, overrides (empty until lesson Manual overrides as bounds, with an audit trail) and settings (the solver and its gap tolerance).
  • Metadata says who made the scenario, when, under what name, and which scenario it was copied from: scenario_id, name, created_by, created_at, parent_id.

The portfolio itself is not copied into the record. data names it by size and seed, which is enough to regenerate it, and stores its content hash (GridCap's Portfolio.content_hash(), the sha256 of its canonical JSON) as proof of which data was meant. Forty projects with their cost profiles and NPVs would make every scenario large, and every copy would duplicate them. Lesson Versioned snapshots and content hashes turns this reference into versioned snapshots of the input data.

Why keep the model out of the record? A MathOpt model is built for one solve: it holds solver-ready variables and rows, it cannot be written to JSON, and it is not something two planners can share. The OR-Tools MathOpt overview stresses that a MathOpt model is defined independently of any solver; this lesson goes one step further and keeps the model out of the stored data altogether. The record is small, readable and storable; the model is rebuilt from it on every run.

The Snapshot Covers the Inputs, and Nothing About Who or When

Lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock introduced the snapshot, the sha256 hash of a scenario's inputs written in one canonical form. Here it is computed from inputs() only:

sort_keys=True and the compact separators (",", ":") make one text for one set of inputs, whatever order the dictionaries were filled in; Python's json documentation names those separators as the most compact form. The program renames the scenario, then changes one budget by $1k:

Renaming the scenario and changing who made it leave the snapshot alone, because neither changes the model. A $1k change to one budget gives another snapshot, because it changes a row. That split is what lets a service answer "were these two runs solved on the same inputs?" by comparing two strings, and answer it correctly even when the two scenarios have different names or owners.

The data reference is checked too. A scenario whose data no longer matches its hash is refused before any model is built:

The program asked for seed 2028 while the recorded hash belongs to the default seed, 2027, so the regenerated portfolio is different data. Building a model from it would silently plan a different utility under the old scenario's name.

Problem statement

A water utility, Riverbend Water (invented for this practice), keeps its pumping plans as records like this one:

Its run service must tell whether two plans were solved on the same inputs. The inputs are the fields named in INPUT_KEYS: demand, budget and solver settings. Everything else (id, name, owner, creation time) is metadata and must not affect the answer.

Write snapshot(record) in snapshot.py. It returns the sha256 hex digest of the record's inputs only, written as text that is the same for the same inputs however their dictionaries were filled in. Records in the tests may carry metadata keys you have not seen. Every record carries all three input keys; one that lacks an input is malformed, and the reference lets it raise KeyError rather than hash an incomplete plan (no test sends one). About four lines.

A Copy Shares Nothing Mutable With Its Parent


Finance's question needs a second scenario that starts from the base's inputs. The tempting copy is copy.copy. It is a shallow copy: a new object whose fields point at the same inner objects as the original, as Python's copy documentation puts it. copy_pitfall.py makes one and cuts the 2030 budget:






The copy and the base share one budget dictionary, so the edit to the copy changed the base. Its snapshot moved with it, and any result solved earlier from the base no longer matches the base's inputs. Nothing raised an error. This is the notebook's bug from the opening, moved into code.


A copy must give the new scenario its own containers. copy_scenario builds a new record with a new dictionary for every field that can change, and a link back to the parent:




Three things to read in that output. The copy starts with the base's snapshot, because its inputs are equal. Editing the copy leaves the base's budget and snapshot untouched. And parent_id records where the copy came from, so a reviewer can always trace a scenario back to the one it was made from.


dict(s.budget) copies one level, which is enough here because the values inside are integers and Override records (lesson Manual overrides as bounds, with an audit trail) are frozen dataclasses, which nobody can change in place. data is shared on purpose: DataRef is frozen too, and both scenarios mean the same portfolio. A record with nested mutable values would need copy.deepcopy, which copies every level.

Besides a yearly budget, a plan holds, for each district, a list with the number of crews available in each month, and a list of tags. Analysts copy a plan to try a storm-reserve variant, then change budgets and individual months in the copy.


Write copy_plan(p, plan_id, name, by) in plan.py. It returns a new Plan with the given id, name and author, inputs equal to p's, and parent_id naming p. Nothing the copy holds may be an object that p also holds, at any depth, so that no edit to the copy, however deep, can change p. About four lines.

A Scenario Survives a Round Trip Through JSON


A scenario that only lives in one Python process cannot be stored in a database (lesson Storing scenarios and results in SQLite) or sent to an API (lesson A REST API with FastAPI). to_json writes the whole record, inputs and metadata, as canonical JSON, and from_json reads it back. JSON has one trap for this record. Its object keys are always strings (Python's json documentation says every key is converted to a string), so the years come back as '2027', not 2027:



A model builder that looked up budget[2030] in the raw JSON would raise KeyError, or worse, find nothing and use a default. from_json turns the keys back into integers and the override lists back into Override records, and the test that matters is the last line: the record read back equals the record written, and so does its snapshot. If a field were lost or retyped on the way, one of the two would be False.


Optimize Builds the Model From the Scenario and Stamps the Result With Its Snapshot


optimize takes a scenario and returns a Result. It regenerates and checks the portfolio, turns the overrides into bounds, builds the model, solves it with HiGHS through MathOpt, and reads the plan only when the solve is optimal, as the OR-Tools MathOpt samples check the termination reason before reading a solution:



The function reads nothing but its argument: no global budget, no model left over from an earlier run. That is what makes a rerun meaningful. optimize_scenarios.py runs the base and the copy, then the base again:



The answer to finance: the $860k cut costs $373k of NPV ($24,260k less $23,887k). The plan drops the Coast line job P016, which spends $310k and $950k in its two years of work, funds the small Valley trim P006 instead, and moves P018 a year later. The diff line uses the three lists of lesson Scenario diffs: selected, deferred, shifted: projects the new plan selects, defers, or shifts to another year. The rerun of the base gave the same plan, on this machine and these versions; lessons Where nondeterminism comes from: threads, time limits, ties and Seeds, threads and deterministic work limits, solver by solver say when reruns repeat and when they need more than equal inputs.


Each Result carries the snapshot of the inputs it was solved on. That stamp is how a service knows whether a result still describes its scenario:






Someone changed the copy's 2031 budget after its run. The stored result still says $23,887k, but it answers a question nobody is asking any more. A service that compares the two snapshots shows the result as stale and asks for a rerun; one that does not compare them puts an old NPV beside new budgets, which is the projector mix-up from the opening. Lesson Planning-cycle states and locking turns this check into a rule the planning cycle enforces.


Summary


  • A scenario is a record of inputs, kept apart from the model. Inputs (data, budgets, overrides, settings) build the model; metadata (id, name, who, when, parent) does not.
  • The snapshot covers the inputs, and nothing about who or when. Equal inputs give equal snapshots whatever the name; a $1k change gives another one. The data is named by its hash and refused if it no longer matches.
  • A copy shares nothing mutable with its parent. A shallow copy shares the budget dictionary, so editing the copy edits the base; copy_scenario gives the copy its own containers and a parent_id.
  • A scenario survives a round trip through JSON. JSON keys are strings, so the years must be turned back into integers; the record read back equals the record written.
  • Optimize builds the model from the scenario and stamps the result with its snapshot. A result is current only while its snapshot equals its scenario's.

Design Note: Ids and Clocks Come From Outside


Every function here takes the scenario id and the time as arguments instead of calling uuid4() or datetime.now() itself. The programs pass fixed values (S-001, a Clock that steps five minutes), so they print the same output on every run and their tests can check it. In a service the id comes from the database (lesson Storing scenarios and results in SQLite) and the time from the server's clock in UTC, but the functions do not change: whoever calls them decides where ids and times come from.
