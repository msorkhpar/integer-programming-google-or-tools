  15. Overrides as bounds, with an audit trail

It is the second week of the planning cycle, and GridCap's planners have opened a copy of the base scenario called q2-overrides. Three planners and a manager change it over one morning. One promises the Ridge customers that the P024 undergrounding starts in 2029, then moves the promise to 2030. Another takes the Valley line P032 out until a study is done. A third keeps the Coast job P036 out of 2027 and 2028 for lack of crews, and adds an outage window to P021 that the manager later lifts. Two requests are mistakes and must be refused. A month later an auditor asks why P024 starts in 2030 and P032 is not in the plan. The answer cannot be "someone changed it": it has to name the person, the time, the reason, and exactly what the change did to the model.

Lesson Manual overrides as fixed bounds showed the mechanics: an override that fixes start variables is a change of their bounds, it can be undone by restoring them, and it is priced by solving with and without it. This lesson builds the record keeping around those mechanics, which a planning service needs and a model alone cannot give: a check before any bound moves, an append-only audit trail (a log of every change, kept in the order it happened, that is only ever added to), and a way to find which overrides broke a scenario that will not solve.

GridCap is a fictional utility's portfolio, generated for this course; no number in it is real. The people (planner-a, planner-b, planner-c, manager-a) and their reasons are invented placeholders.

The Model

The model of lesson Scenarios as data: create, copy, optimize, whole, with this lesson's part marked: each override sets the bounds $l_{i,t}$ and $u_{i,t}$ of its project's start variables. No override adds or removes a row.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years; $O$ the overrides in force, at most one per project, each a triple (project $i$, kind, year $y$).

Parameters. $\text{npv}_{i,t}$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k), from the scenario; $l_{i,t}$ and $u_{i,t}$, the bounds of $x_{i,t}$, set by the table below (this lesson).

Override on project $i$$(l_{i,t}, u_{i,t})$ for each $t \in T_i$
none$(0, 1)$
start_in $y$$(1, 1)$ if $t = y$, else $(0, 0)$
out$(0, 0)$
not_before $y$$(0, 0)$ if $t < y$, else $(0, 1)$
not_after $y$$(0, 0)$ if $t > y$, else $(0, 1)$

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$, with $l_{i,t} \le x_{i,t} \le u_{i,t}$ $\leftarrow$ this lesson. We write $\text{started}(i) = \sum_{t \in T_i} x_{i,t}$ and $\text{by}(i, t) = \sum_{s \in T_i,\, s \le t} x_{i,s}$.

Objective.

Constraints.

The bounds are part of each variable, not rows; plan_model.build sets them last, after every row is written, with x[key].lower_bound, x[key].upper_bound = lower, upper. MathOpt's Variable has setters for both properties, and the OR-Tools sample time_indexed_scheduling.py uses the same move to forbid start times before a job's release. The one override kind of lesson Manual overrides as fixed bounds that is not a bound, "fund it in any year", is a rule on the sum $\text{started}(i) = 1$ and needs a row; this service does not accept it (see the design note).

An Override Is a Request, Checked Against the Data Before Any Bound Moves

An override arrives as a request from a person, and a person can ask for something the data does not allow. Lesson Manual overrides as fixed bounds found the dangerous case: a start year outside the project's window has no variable at all, so "start in that year" quietly becomes "never". A service must catch that before the bounds are written, not after a solve has hidden it. The override itself is a small frozen record holding only what the model needs:

bounds_of turns it into the bounds of the table above, and check refuses it when those bounds would not mean what the planner asked for:

The rule behind leaves_none is general: an override that sets every start variable of a project to $(0, 0)$ takes the project out of the plan, whatever it was called. That is correct for out, a silent surprise for a not_before past the window's end, and impossible for a must-do, whose must row $\text{started}(i) = 1$ would make the model infeasible.

    Overrides that narrow a window

    • each kind of override sets the lower and upper bounds of the project's start variables
    • an override that would close every start year is refused before any bound moves

    Not startedPassed

Problem statement

Riverbend Water (invented for this practice) lets its engineers narrow when a main replacement may start. Each project has a start window, a range of years, and one start variable $x_t \in \{0,1\}$ per year $t$ of the window, with bounds $l_t \le x_t \le u_t$. Three kinds of override exist:

  • start_in, with years = (y,): the project starts in year $y$.
  • only_between, with years = (a, b): the project may start only from $a$ to $b$, both included; it does not have to start at all.
  • skip_years, with any number of years: the project may not start in those years (a road is closed, a festival needs the street); it does not have to start at all.

Write bounds_for(kind, years, window) in overrides.py. It returns {t: (l_t, u_t)} for every year t of the window, with (0, 1) for a year the override leaves free. An override that would set every year of the window to (0, 0) would quietly take the project out of the plan, which is not what was asked: return None for it instead, so the service can refuse it. A start_in year outside the window falls under that rule too. A kind that is none of the three narrows nothing: every year of the window gets (0, 1). About twelve lines.

The Trail Records Who, When, Why and the Bounds That Moved, and Is Only Ever Appended To


The Override record holds what the model needs; the AuditEntry around it holds what the people need:



The split is the one lesson Scenarios as data: create, copy, optimize made between inputs and metadata. The scenario's snapshot covers Override (project, kind, year) because the bounds change the model; it does not cover by, at or why, which change nothing the solver sees. Two planners who make the same override give the same snapshot, and the trail still says which of them did it.


changes is the line an auditor reads most closely: every start variable whose bounds moved, from what to what. It is computed by comparing the bounds before and after, so it is exact even when one override replaces another. The whole trail of the morning:

When Overrides Make a Scenario Infeasible, the Trail Finds Which Ones


Every override passed check one at a time, yet together they can still leave no feasible plan. In the scenario early-starts, three planners each fix a different Valley or Plains project to start in 2027, for good reasons of their own, and one adds an unrelated outage window:



The three forced projects spend $9,540k in 2027 against a budget of $8,890k. The solver's answer is one word, INFEASIBLE. Lesson IIS with MathOpt, gurobipy and Pyomo finds conflicts by asking a solver for an irreducible infeasible subsystem (IIS), a smallest set of rows and bounds that cannot hold together. The design note of lesson Why selected, why deferred: forcing in and out explains why an override written as a bound is a poor fit for that tool: Gurobi's IIS never names a binary variable's bounds (Gurobi's reference for its IIS attributes says so), so the very override that caused the conflict could not appear in the explanation.


The trail gives another way, which needs no IIS and works with any solver. Each override in force is an entry with a person and a reason. Drop the overrides one at a time, newest first, and re-solve: an override whose removal leaves the scenario still infeasible is not needed for the conflict, so it stays dropped; one whose removal makes the scenario solvable is part of the conflict, so it goes back.






This is the deletion filter of lesson IIS with MathOpt, gurobipy and Pyomo, run over overrides instead of rows. Four overrides needed four solves. The outage window on P021 was dropped and stayed dropped, because the scenario was still infeasible without it. Each of the other three was needed, and the three together are still infeasible on their own. The filter keeps an override only when the solve without it was feasible, so dropping any single one of the three makes the scenario solvable; that is what makes the set irreducible. The answer is the sentence a planning meeting needs: these three 2027 starts, by these two people, for these reasons, do not fit in the 2027 budget together; one of them has to give.


The filter assumes the scenario without any override solves, which is true here because the base solved. If the base itself were infeasible, the conflict would lie in the data or the rules, and the IIS tools of lessons IIS with MathOpt, gurobipy and Pyomo to CP-SAT assumptions as a conflict finder are the right ones.

Summary


  • An override is a request, checked against the data before any bound moves. A start year outside the window, an override that leaves a project no start year, and a must-do taken out are refused with a sentence, and the refusal is recorded too.
  • The trail records who, when, why and the bounds that moved, and is only ever appended to. A new override on the same project supersedes the old one; a revocation is a new entry; replaying the trail rebuilds the overrides in force.
  • When overrides make a scenario infeasible, the trail finds which ones. Drop overrides one at a time and keep only those whose removal makes the scenario solvable; the entries name the people and reasons.

Design Note: A Service Accepts Only Overrides It Can State as Bounds


Lesson Manual overrides as fixed bounds allowed "fund it, in any year", which needs a row, and lesson Why selected, why deferred: forcing in and out wrote every forcing as a named row so an IIS could name it. This service takes the other side: every override it accepts is a set of bounds, and a project that must be funded in some year is handled by choosing the year (start_in), which a planner who promises a project to customers has to do anyway. The gain is that an override never changes the model's rows, so two scenarios always have the same rows and differ only in parameters and bounds, and the audit entry can list exactly which variables moved. The cost is the one this lesson paid for in its last section: an IIS cannot name a bound, so the service finds conflicting overrides with its own deletion filter over the trail.
