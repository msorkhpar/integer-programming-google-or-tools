Every planning cycle, GridCap's planning database exports one JSON document for the optimization service: the years, the budgets, the crews, the regional floors and the 40 candidate projects. The service builds the model from it, solves, and stores the result with the scenario (lesson Storing scenarios and results in SQLite). Last cycle the export team renamed one column. Nothing crashed, and one child project quietly lost its one-year lag behind its parent. This lesson puts a schema at the door of the service, so that a document like that is refused, with the reason, before any model is built. GridCap is a fictional utility; its numbers describe no real company.

Lesson Typed inputs with dataclasses and pydantic introduced pydantic on one CSV row at a time: BaseModel, field types and bounds, field and model validators, and ValidationError. This lesson uses the same tools on a different unit: the whole snapshot, as it crosses the boundary between two programs. A snapshot is one complete set of model inputs, frozen at one moment; lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock gave each scenario a snapshot id, and lesson Versioned snapshots and content hashes shows how that id is computed. A schema is the written rule for what a valid snapshot looks like: which keys, which types, which bounds, and which references must resolve.

The course's runner has pydantic 2.14.1 and no other schema library (pandera, for one, is not installed), and FastAPI, which lesson A REST API with FastAPI uses for the service, builds on pydantic. So the schema is a set of pydantic models.

The Schema Is the Model's Sets and Parameters, Written as Types

A schema for model inputs is not designed from the file. It is read off the model: every set and every parameter the model uses becomes a field, and every assumption the model makes about them becomes a type, a bound or a rule. Here is the planning model the service solves (section 6's multi-period model; lesson Data-quality checks that prevent infeasibility restates it, and its program is plan_model.py).

Sets. $Y$ the plan's years, in order; $P$ the candidate projects; $T_i$ the start years of project $i$: the years $t$ with $e_i \le t \le l_i$ whose work ends inside the plan, $t + d_i - 1 \le \max Y$; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups, each a set of projects; $C \subseteq P$ the child projects, each with parent $p(c)$ and lag $L_c$ years; $Q$ the programs (transmission, distribution, vegetation), with $q(i)$ the program of project $i$; $R$ the regions, with $r(i)$ the region of project $i$.

Parameters. $e_i, l_i$, project $i$'s earliest and latest start year; $c_{i,k}$, what project $i$ spends in its $k$-th year of work, $k = 0, \dots, d_i - 1$, where $d_i$ is its number of years of work ($k); $\text{capex}_i = \sum_k c_{i,k}$ ($k); $\text{npv}_{i,t}$, its NPV if it starts in year $t$ ($k); $m_i$, the crew-months it needs in each year of work; $B_y$, the budget of year $y$ ($k); $K_{q,y}$, the crew-months program $q$ has in year $y$; $\text{floor}_r$, the least region $r$ must receive over the plan ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$.

The project record is the row model of lesson Typed inputs with dataclasses and pydantic grown to everything the model reads, and the snapshot nests it with the year, crew and floor records:

A field whose type is another model, such as budget: tuple[YearAmount, ...], is a nested model: pydantic validates each record of the list as a YearAmount. YearAmount has two fields, year: int and amount: NonNegativeInt; CrewLimit and RegionFloor are built the same way. Budgets, crews and floors are lists of records rather than dicts keyed by year, because JSON keys are always strings: a record keeps the year an integer and gives each value a name. Contract is the base class every part shares; the third section shows what it sets.

One Schema Validates the Whole Snapshot and Reports Every Problem in One Pass

schema_whole.py plants errors in a copy of the export. First, five at once:

Pydantic does not stop at the first bad field: it validates every field of every record and returns all the failures in one ValidationError, each with its location. budget.1.amount is the amount of the second budget record; projects.6.cost_profile.1 is the second year of work of the seventh project, P007. A sender fixes all four in one round instead of four.

Four, not five. The unknown parent P099 is a rule across records, written as a model validator on Snapshot (below), and an after-validator runs only on a model whose fields all passed. So the problems come in two layers: field problems first, and reference problems once the fields are clean. P030's problem is reported because it is a model validator of ProjectIn, whose own fields were all valid.

The references are the rules no single record can break. Each says that something the model will look up exists, exactly once:

Counter (from collections) counts how often each key occurs, and gives 0 for a key it never saw, so "missing" and "twice" are the same test: a count other than 1. Program.__args__ is the tuple of names in the Literal type. The validator collects every problem before it raises, for the same reason pydantic collects field errors. Four reference errors, planted together:

The location () is the empty tuple: the error belongs to the whole snapshot, not to a field.

Each of these would otherwise fail later, and worse. plan_model.py keeps the projects in a dict by id, so of a project exported twice, whichever copy comes last silently wins, even when the two copies disagree on its cost. It reads the budget as budget[y], so a missing 2031 raises a KeyError deep inside the model build, with no word about the export. A builder written with budget.get(y, 0) would be worse still: it would set $B_{2031} = 0$ and solve a model in which nothing can be spent in 2031.

The schema's job ends here: if a snapshot passes, the model can be built from it, every set and parameter present and well typed. Whether the model then has a plan, and whether the numbers are believable, is the job of lesson Data-quality checks that prevent infeasibility.

  1. Coding practice

    A schema for a bus-replacement snapshot

    • a snapshot schema nests its records, bounds each parameter, and checks every reference across records in one model validator that reports every problem at once

    Not startedPassed

Problem statement

A city transit agency plans which buses to replace in which year, and its planning tool sends the optimization service a snapshot as JSON. The service's model is small:

Sets. $H$ the horizon's years; $D$ the depots; $V$ the buses, each kept at a depot $d(b) \in D$; $T_b = \{e_b, \dots, l_b\}$ the years bus $b$ may be replaced in.

Parameters. $c_b$, the cost of replacing bus $b$ ($k); $A_y$, the budget of year $y$ ($k).

Variables. $x_{b,y} \in \{0, 1\}$ for $b \in V$, $y \in T_b$: bus $b$ is replaced in year $y$.

Constraints.

In fleet.py, finish the schema so that a snapshot is accepted exactly when this model can be built from it and its parameters make sense: one variable family per bus (no bus listed twice), every bus at a listed depot, one budget row for every year of the horizon (not zero, not two), a window that holds at least one year, a cost above zero, and a budget of zero or more. Rules across records go in FleetSnapshot.references_resolve; when several fail, one ValueError must name every bus and year involved. The tests validate JSON text with FleetSnapshot.model_validate_json and look for the ids and years in the error's messages. About fifteen lines.

At a Machine Boundary, Forbid Unknown Keys and Turn Off Guessing


Lesson Typed inputs with dataclasses and pydantic used pydantic's defaults, which suit a person's spreadsheet: unknown columns are ignored, and a string that clearly means a number is converted (lax mode). The service's sender is a program, and every surprise in its output is a bug in that program. Two settings make the schema say so. Both sit on the base class that every part of the snapshot inherits:



extra="forbid" refuses a key the model does not declare (the default, "ignore", drops it). strict=True turns off conversion: a value must already have its field's JSON type. Both can be overridden for one call (model_validate_json(text, extra="ignore"), strict=False), which schema_boundary.py uses to put the two policies side by side. First, last cycle's export, in which P023's parent_lag column arrived renamed to lag:



With "ignore" the document is accepted. lag is dropped as unknown, parent_lag is missing, and its default fills the gap: P023's lag becomes 0. In the model, that changes the rows $\text{after}_{\text{P023},t}$: P023 may now start in the same year as its parent P022, not a year later. No error, no warning, a different plan. A default on a field is convenient for a person typing a document and dangerous for a program sending one, because a renamed key turns into the default without a sound. With "forbid", the same document is refused and the message names the key.


Next, four ways an exporter can send a number or a flag in the wrong JSON type:



Lax mode converts every one it can read without losing information, and here each conversion happens to give the right value. That is the problem: an exporter that writes budgets as strings, or flags as "no", has a bug that will one day write something lax mode reads differently from what was meant. Lesson Typed inputs with dataclasses and pydantic's lax rules are right for a planner's CSV, where every cell is text. Between two programs that both speak JSON, a string where a number belongs is never right, and strict mode says so the first time it happens.


Strict mode checks values against JSON types when it validates JSON text. A JSON array is the JSON form of a tuple, so years: [2027, ...] passes. The export's Python dict, validated as Python data with model_validate, is refused, because there a Python list is not a tuple:



So the service validates what it receives, the JSON text, with model_validate_json, and never a dict that some other code built from it.


The Schema Is a Versioned Contract, Published as JSON Schema


A schema the sender cannot read is a rule they find out about by being refused. Pydantic writes each model out as a JSON Schema, a standard JSON document describing which keys, types and bounds an object may have, that any language can check against. schema_contract.py prints a few parts of Snapshot.model_json_schema():



Every rule written as a type is in it: extra="forbid" became additionalProperties: False, NonNegativeInt became minimum: 0, the id pattern is there, and the nested models sit under $defs. The rules written as Python code, the two model validators, are not: JSON Schema cannot say "every parent is a project", so the published document describes the structure and the service still runs the validators. FastAPI publishes the JSON Schema of every request model in its API description automatically, which is how lesson A REST API with FastAPI's service will hand this contract to the export team.


A contract changes. When the model gains a parameter, or a field is renamed, old exports must not be read as if they were new ones. That is what schema_version: Literal[1] is for: the field must be present and must be 1, so a document from before versions, or from a newer exporter, is refused:



An old document is not ignored or guessed at. It is brought up to date by an explicit step, one per version, before validation. Before versions existed, the export called the lag column lag:






Compare this with the extra="ignore" run above. The same renamed column, handled by a rule that knows what lag meant, keeps P023's lag of 1. The upgrade is code with a test, written once, and the schema stays strict.

Problem statement


The transit agency's fleet export is read by another program, and two versions of it are in use. Version 3, the current one, gives each bus an id, a depot, a cost in $k and a must_replace flag (the model's $\text{replace}_b$ row is an equality only for such buses). Version 2, still sent by one older depot system, called the depot garage and had no must_replace at all: in version 2 no replacement was mandatory.


In contract.py, make the schema a contract for documents sent by a program, and bring version 2 documents forward:


  • Contract refuses keys the schema does not declare and refuses values in the wrong JSON type (a number sent as text, a flag sent as text), and its objects cannot be changed after loading.
  • Fleet accepts version 3 only.
  • upgrade(raw) turns a version 2 document into the version 3 document it means, and leaves any other document as it is, for the schema to accept or refuse. It must not drop keys it does not know: a key that is wrong in version 2 is still wrong after the upgrade. depot and must_replace are such keys: version 2 never had them, so a version 2 document whose buses carry either one (a must_replace flag, or a depot beside the garage) is left as it is, still at version 2, and the schema refuses it. Guessing which depot or flag was meant would hide the sender's mistake.


parse(text) is written; it returns None for any document the contract refuses. About ten lines.

Summary


  • The schema is the model's sets and parameters, written as types. Read it off the formulation: each parameter a field, each assumption a type, bound or rule.
  • One schema validates the whole snapshot and reports every problem in one pass. Field problems come first; references across records (unique ids, known parents, a budget and crews for every year) come from a model validator once the fields are clean. A snapshot that passes can be built into a model.
  • At a machine boundary, forbid unknown keys and turn off guessing. extra="forbid" stops a renamed key from becoming a default; strict=True refuses a value in the wrong JSON type. Validate the JSON text, not a dict built from it.
  • The schema is a versioned contract, published as JSON Schema. model_json_schema() gives the sender the structural rules; schema_version refuses documents of another version, and an explicit upgrade step brings old ones forward.

Design Note: The Schema Lives With the Model, Not With the Export


It is tempting to let the export team own the schema, since they produce the document. But every rule in it comes from the model: which parameters exist, which may be zero, which ids must resolve. When the model changes, the schema must change in the same commit, and the version with it. So the schema sits beside plan_model.py, and the export team receives it as JSON Schema, generated from that code, never retyped.
