The schema of lesson Schemas for model inputs now guards GridCap's optimization service: every snapshot it accepts has every field typed and every id resolved, so the model can be built. That is not the same as a model worth solving. This cycle's export passes the schema and still says that P015 must wait for P016 while P016 waits for P015. Another passes and has every budget in millions of dollars where the model expects thousands. One of these comes back from the solver INFEASIBLE with no reason given; the other comes back OPTIMAL with two projects silently gone. This lesson adds the layer between the schema and the model that catches both: a quality gate of named rules, each with a severity. GridCap is a fictional utility; the planted errors are typical of real exports, the data is not real.

Lesson Validating inputs before the solve wrote five pre-solve checks: tests on the input that can prove no plan exists without solving, such as a must-do project that alone overspends every year it may start in. It also taught what makes a check sound: it fires only when no plan can exist. This lesson builds on both. It turns checks into a gate the service runs on every snapshot, adds rules that look across several projects at once, and separates findings that must stop the run from findings that only need a reader.

The Model

The gate reads the snapshot and reasons about the model's rows without building them. The model is the one of lesson Schemas for model inputs, unchanged, here whole so that each rule can name the rows it protects.

Sets. $Y$ the plan's years, in order; $P$ the candidate projects; $T_i$ the start years of project $i$: the years $t$ with $e_i \le t \le l_i$ and $t + d_i - 1 \le \max Y$; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, each with parent $p(c)$ and lag $L_c$; $Q$ the programs, with $q(i)$ the program of project $i$; $R$ the regions, with $r(i)$ the region of project $i$.

Parameters. $e_i, l_i$, the earliest and latest start years; $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k), $d_i$ its years of work, and $\text{capex}_i = \sum_k c_{i,k}$; $\text{npv}_{i,t}$ ($k); $m_i$, crew-months per year of work; $B_y$, the budget of year $y$ ($k); $K_{q,y}$, the crew-months of program $q$ in year $y$; $\text{floor}_r$, the least region $r$ receives over the plan ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$.

Objective.

Constraints.

The precedence row $\text{after}_{c,t}$ is the cumulative form of lesson Aggregated vs. cumulative (disaggregated) forms: if child $c$ has started by year $t$, its parent has started by year $t - L_c$. On GridCap small the model solves to an NPV of $22,741k, the base plan of lesson Infeasible, unbounded, or the solver can't tell.

A Quality Gate Runs Every Rule After the Schema and Before the Model

A quality rule is a function that reads a valid snapshot and returns findings. A finding is a record, as in lesson Validating inputs before the solve's design note: which rule, how serious, about what, and the numbers.

Severity is Literal["error", "warning"]. An error blocks the solve; a warning lets it run and goes into the run's report. The third section is about which is which.

The gate is the list of rules and one function that runs them all. It never stops at the first finding, for the reason pydantic does not stop at the first bad field: the sender fixes everything in one round.

Every rule takes the same two arguments: the snapshot, and the last accepted snapshot of the same scenario (or None), for the rules that compare one cycle with the last. Adding a rule is adding a function to RULES; lesson Validating inputs before the solve's five checks fit the same shape. The service runs, in order: the schema (can the model be built?), the gate (is the data worth solving?), then the model. On the clean export the gate is silent and the solve is the base plan:

Rules Across Projects Catch Errors No Single Field Shows

Lesson Validating inputs before the solve's checks each read one project, one group or one region against one limit. The errors that pass a schema most easily are the ones that need two or more projects to see. Two of them, planted in quality_gate.py; the schema accepts both, because every field is well typed and every parent exists.

A parent cycle. The export sets P015's parent to P016, with a lag of 1. P016's parent is already P015. Each is now the other's prerequisite:

The solver does not say "infeasible". Neither project is must-do, so the plan that funds neither satisfies every row, and the solver returns it, $104k below the base plan:

The base plan funds P015. With the cycle it cannot: funding P015 by year $t$ needs P016 by year $t - 1$, which needs P015 by year $t - 1$, and so back until no year is left. This is the quiet failure: an OPTIMAL plan that has lost a project because of a typo in a link, with nothing in the result to say so. The rule follows each project's chain of parents and reports a project that comes back to itself. The warning below it is a second rule seeing the same typo from another side; the third section explains why it is only a warning.

A must-do child whose parent cannot start early enough. The export marks P023 must-do and types its lag as 3 instead of 1. P023 may start only in 2029; its parent P022 may start from 2027:

The rule compares the earliest the parent can start, plus the lag, with the latest the child can start. If that is too late, no start year of the child has a parent start early enough, so every row $\text{after}_{c,t}$ forces $x_{c,t} = 0$:

starts gives $T_i$, the start years whose work ends inside the plan, the same function the model builder uses, so the rule and the model cannot disagree on the windows. Here $\min T_{\text{P022}} + 3 = 2030 > 2029 = \max T_{\text{P023}}$. For a must-do child that means $\text{must}_{\text{P023}}$ cannot hold, and the solver's INFEASIBLE is certain; the rule says why in one line, with the numbers.

The third cross-project rule adds up what every plan must pay for. A must-do project must be funded ($\text{must}_i$), and through $\text{after}_{c,t}$ so must its parent, and the parent's parent:

Every required project starts in a year of $T_i$, so all its work falls inside the plan, and adding the budget rows over all years gives $\sum_{i \text{ required}} \text{capex}_i \le \sum_y B_y$ in every plan. If the required total is larger, no plan exists: the rule required-over-budget is sound. The walk up the parents makes it stronger without making it unsound, because an ancestor of a must-do is funded in every plan too. The pid not in need test also stops the walk on a cycle.

  1. Coding practice

    Cross-job checks for a track-renewal snapshot

    • rules that look across several jobs at once, counting a required job's prerequisites as required, and firing only when no plan can exist

    Not startedPassed

Problem statement

A rail operator plans track and signal renewals over a few years. Each job uses one crew type for a number of crew-weeks; each crew type has a supply of crew-weeks over the whole horizon. Some jobs are required, a job may need another job done first (after), and some jobs are alternatives: at most one job of each exclusive group may be done. The operator's model, with $J$ the jobs, $R \subseteq J$ the required jobs, $a(j)$ the prerequisite of job $j$ (if any), $E_g$ the jobs of exclusive group $g$, $w_j$ the crew-weeks of job $j$, $k(j)$ its crew type and $S_k$ the supply of crew type $k$:

The snapshot has passed its schema. Before the solve, find the clashes between jobs that prove no plan exists. First write down which jobs every plan must do, and why the rows force each of them. Then, in cross.py, write required(snapshot) and cross_checks(snapshot), which returns a sorted list of (rule, subject) pairs:

  • ("exclusive-required", g), once per exclusive group $g$ that holds two or more jobs every plan must do;
  • ("crew-short", k) for each crew type $k$ whose supply is below the crew-weeks of the jobs every plan must do.

A rule may fire only when no plan can exist. The schema has already checked that every job's crew type is a key of crews, so you may assume it; the reference loops over the crew types in crews and would never report a type missing from it. About fifteen lines.

Severity Follows What a Finding Proves: Errors Block, Warnings Report


A gate that blocks a good snapshot is worse than none: the planners lose a cycle and soon stop trusting it. A gate that lets a broken snapshot through hands them a wrong plan. The severity of a finding decides which mistake the gate can make, so it follows a rule:


  • Error: the finding proves the snapshot breaks its contract (a parent cycle cannot exist in real work) or proves the model has no plan (a sound pre-solve check, as in lesson Validating inputs before the solve). The solve is refused.
  • Warning: the finding is possible but unusual, and may be exactly what the planners meant. The solve runs, and the finding goes into the run's report next to the plan.


severity.py runs four snapshots through the gate, each compared with the last accepted one, the clean export:



A must-do child pulls in its parent. Making P016 must-do is a planner's decision, and a legitimate one. Its parent P015 is optional, so the model must fund P015 too, and does:



The plan costs $2,672k of NPV against the base. That may surprise the planner who only asked for P016, so the gate says why P015 is in the plan. It is a warning: nothing is wrong, and refusing the run would refuse a decision the planners are entitled to make.


The same rule, two severities. parent-too-late fires on P016 when its lag is typed 2: P015 can start in 2029 at the earliest, plus 2 is 2031, and P016 may start only in 2030. Since P016 is optional, the model simply never funds it, which is a plan; the warning says P016 can never be chosen, so a planner who wanted it knows to look. The same finding on the must-do P023 above proved there is no plan, so there it was an error. The code that chooses is the line severity = "error" if c.must_do else "warning".


A units error: one error and five warnings that explain it. The budgets arrived in millions, rounded to whole numbers: 9, 8, 9, 9, 8. The schema accepts them, since each is a non-negative integer. required-over-budget proves no plan exists ($7,630k required against $43k) and blocks the run. That error alone says that the data is wrong. The budget-drift warnings, which compare each year's budget with the last accepted snapshot and fire when it moves by more than a factor of 3, say how: every year shrank about a thousandfold, the signature of a units mistake.


A real budget cut passes. Finance cuts 2029 by 20%, to $7,008k. A factor of 0.8 is well inside the drift limit, no rule fires, and the solve runs to an NPV of $22,352k. The gate must let such a snapshot through: a cut is what the planning cycle is for.


Why is drift a warning and not an error, when it caught the units mistake? Because a large change is not proof of a wrong one. A new regulatory program can triple a year's budget. The drift rule cannot tell a tripling from a typo, so it reports and lets the sound rules decide whether to block. Here a sound rule did block. On a snapshot where every budget grew fivefold, no sound rule would fire: the solve would run, and the drift warnings would sit in the report beside a plan that a planner can check.

Problem statement


A water utility's planning tool exports a main-replacement snapshot each cycle, and this cycle's export has six defects planted in it. Your gate must reject it, and find all six.


Each job $j$ has a cost profile $c_{j,0}, c_{j,1}, \dots$ (one entry per year of work, $k), a window $e_j \le t \le l_j$ of start years, a required flag, and possibly a prerequisite $a(j)$ with a lag $L_j$: job $j$ may start in year $t$ only if $a(j)$ started in a year $s \le t - L_j$. Each year $y$ of the horizon $H$ has a budget $B_y$. The model has $x_{j,t} \in \{0, 1\}$ for each start year $t \in T_j$, where $T_j$ holds the window's years whose whole work falls inside the horizon: the snapshot's horizon is a list of consecutive years, and $t$ is in $T_j$ when $e_j \le t \le l_j$, $t$ is at least the horizon's first year, and $t + |c_j| - 1$ (the job's last year of work) is at most the horizon's last year. Summary


  • A quality gate runs every rule after the schema and before the model. Each rule returns Finding(rule, severity, subject, detail); the gate runs all of them and reports everything.
  • Rules across projects catch errors no single field shows. A parent cycle drops projects from an OPTIMAL plan without a word; a must-do child whose parent cannot start early enough makes the model infeasible; the required projects, ancestors included, cannot cost more than all budgets.
  • Severity follows what a finding proves. An error proves a broken contract or no plan, and blocks; a warning flags what is possible but unusual, and is reported with the plan. The same rule can be either, depending on whether the project is required.

Design Note: The Gate Never Repairs


The units error has an obvious repair: multiply every budget by 1,000. The gate does not make it. A repair is a guess about what the sender meant, and a guess applied silently is the same kind of quiet failure the gate exists to stop. The gate reports, with the numbers, and the sender fixes the export; the fixed snapshot gets a new digest (lesson Versioned snapshots and content hashes), so the record shows which data the plan came from.
