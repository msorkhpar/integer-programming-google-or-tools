GridCap's planning model has been rewritten for the service this section builds, and the pull request is green: the test suite solves the tiny portfolio, checks that the plan breaks no rule, and checks that its NPV is the one on record. Then a reviewer notices that the rewritten precedence row compares the parent's start with the child's start and forgets the lag. The tests never saw it. This lesson shows why a test of the whole model can pass with a rule broken, and how to test each rule on its own, with a hand-made instance, a plan it must accept and a plan it must refuse. GridCap is a fictional utility's portfolio; the instances in the tests are made up by hand.

The Model Under Test, One Rule per Function

The model is the multi-period selection of lessons Start-time variables x(i,t) and timing windows and Must-do vs. discretionary planning groups to Precedence with lags. Its rows are written by five functions in plan_model.py, one per rule, and the rule's label below is the prefix of the row names its function writes (budget_2029, after_P023_2029).

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use (its window); $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups, each a set of projects; $C \subseteq P$ the child projects, each with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$, the NPV of project $i$ started in year $t$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work, $k = 0, 1, \dots$ ($k); $B_y$, the budget of year $y$ ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$. There is no variable for a year outside the window.

A Whole-Model Test Can Pass With a Broken Rule

bugs.py holds five broken copies of the rules. Each differs from the correct function in one line, the kind of change a refactor or a hurried fix leaves behind:

BugRuleThe changed line does
budget skips the last yearbudgetloops over years[:-1]
must-do written as <=mustwrites started <= 1 for a must-do
precedence ignores the lagaftersums the parent up to $t$, not $t - L_c$
alternatives count one yearaltcounts each member's earliest-start variable only
precedence adds 1 to the lagaftersums the parent up to $t - L_c - 1$

The last one is the only bug that makes the model stricter: it refuses plans the rules allow. The other four make it looser.

The usual end-to-end test solves a portfolio and checks the answer: the plan breaks no rule, which audit.violations re-checks in plain Python from the data, and the NPV equals the correct model's. blind_spot.py runs that test on GridCap tiny and small with each bug swapped in:

On tiny, three of the five bugs pass. The reason is in the data: a broken row only shows when the optimum would use the freedom it wrongly gives, or wants a plan it wrongly takes away. Tiny's best plan never wants a child one year early, or two alternatives at once, so the solver never tries to, and a model that allows it returns the same plan. On small, where the optimum does push against those rules, four bugs fail, but the too-strict lag still passes: small's best plan has no child starting exactly at its lag, so the plans that bug wrongly forbids were not wanted anyway.

A whole-model test checks one point, the optimum of one instance. A rule is a statement about every plan. Testing a rule through the optimum means hoping the instance happens to lean on it.

One Rule, One Hand-Made Instance Where It Alone Can Bind

A unit test of a constraint isolates it twice. It builds the model with that rule and no other, so nothing else can refuse a plan, and it uses an instance made by hand so that the rule binds. A rule binds a plan when the plan sits exactly at its limit or would break it. tiny.py makes such instances short: project(...) fills every field a rule does not read, and portfolio(...) gives every year a budget of 10,000, far above anything two or three small projects can spend, unless the test says otherwise:

The budget test needs a year where the budget is tight and two plans on either side of it. Project A spends 60 in its first year and 40 in its second; project B spends 1. Only 2029's budget is set, to 40:

Every number in the test can be checked by eye, and every choice is deliberate. The tight year is the last one, because "the last year" is where off-by-one loops fail. A's spend reaches 2029 only through its second year of work, so a model that charged the whole cost to the start year would treat 2029 differently. And the two plans differ by $1k, the smallest step money can take in GridCap's integer $k, so the test pins the limit exactly.

Each test takes the rule set as a parameter with the real rules as its default. Pytest calls it with the default; one_rule.py, below, calls it with each broken copy.

Fix the Plan, Then Ask the Solver: Allowed or Refused

A unit test of a rule asks one question: does the model accept this plan? A solver answers it if the plan leaves it no choice. accepts fixes every start variable, to 1 for the plan's starts and 0 for all others, by setting both bounds, then solves and reads the termination reason:

Three details matter, and each is a way to get the helper wrong:

  • Fix every decision, not only the plan's. If only the plan's starts were fixed to 1, the solver could switch on other projects too. A plan that leaves out a must-do would then look allowed, because the solver adds the must-do for you. The decisions left free must be none.
  • Fix the decisions, and only the decisions. This model has no other variables, but many models do: a continuous overtime or slack variable, a carry-over amount (lesson Carry-over budgets and multi-year caps). Those are the model's to choose once the plan is fixed. Fixing them to 0 would refuse plans the rules allow.
  • A start outside the window is refused, not skipped. The model has no variable for it, so a helper that ignored unknown starts would test some other plan than the one asked about.

The bounds are put back afterwards, so one built model can answer many questions. MathOpt reports OPTIMAL when the fixed values meet every row; the objective value is irrelevant here. The once rule is the one rule a plan written as {project: year} cannot break, since a dictionary holds one year per project, so its test calls accepts with two starts for the same project:

Problem statement

A hospital plans its equipment renewals with a small model, and its engineers want unit tests of the form "this plan must be allowed, that one refused". They need one helper first: verdicts(model, x, plans), which says, for each plan in a list, whether the model accepts it.

The model the tests build, for projects $i$ with start windows $T_i$ and a cost $c_i$ paid in the start year:

$o_t$ is overtime spending, which the hospital may use when a year runs over. It has no objective; any plan that meets the rows is acceptable.

Write verdicts(model, x, plans). x maps each (project, year) to its start variable, and each plan maps each started project to its start year; every project not in a plan is not started. Return one answer per plan, in order: True when the model accepts exactly that plan, False when it refuses it. A plan that starts a project in a year the project has no variable for is refused. Solve with HiGHS through MathOpt.

The engineers share one model between many questions, and a planner may already have fixed a start by its bounds (an override). While a plan is being asked, the plan alone decides every start: fix each start variable to 1 or 0 as the plan says, replacing whatever bounds it had, an override's included. When verdicts returns, put the bounds back, so every start variable has the bounds it had when the function was called. About twelve lines.

Problem statement


A tree-trimming contractor's planning model has a crew rule, and the rule has no tests. Jobs take one or more years of work and use a given number of crew-months in each of those years; each year has a fixed number of crew-months. With $x_{j,s} = 1$ when job $j$ starts in year $s$, and $m_{j,k}$ the crew-months job $j$ uses in its $k$-th year of work ($k = 0, 1, \dots$):



Your job is not to write the rule but to write the cases that test it. cases() returns a list of hand-made cases (jobs, crews, plan, allowed); the comments in crew_cases.py give each field's shape. Each case should be small enough to check by eye: one or two jobs, and crew numbers chosen so that the crew rule decides.


The tests build a model with the crew rule alone for each case, fix the plan, and check your verdict, so every verdict must be the correct rule's, and your cases must hold at least one allowed and one refused plan. Then they run your cases against three wrong versions of the rule, each a mistake real code makes, and some case must catch each one, that is, get a different verdict from it than the one you wrote:


  • a rule written as if the limit were strict, so a year may use at most $K_y - 1$ crew-months;
  • a rule whose loop over the years stops one year early, so 2029 is never checked;
  • a rule that charges all of a job's crew-months to the year it starts.


Write the cases. About five lines.

Summary


  • A whole-model test can pass with a broken rule. It checks one optimum; on GridCap tiny three of five broken rules left the optimal plan unchanged, and on small one still did.
  • One rule, one hand-made instance where it alone can bind. Build the model with that rule only, on an instance small enough to check by eye.
  • Fix the plan, then ask the solver: allowed or refused. Fix every decision variable by its bounds, leave helper variables free, and refuse a start the model has no variable for.
  • Pair every refused plan with an allowed one, at the boundary. The allowed half catches a rule that is too strict, which no check of the solver's own plans can see.

Design Note: Why the Model Is Built From a Dictionary of Rules


The usual model builder is one long function. Its rows can only be tested together, so every test is a whole-model test. Writing one function per rule, and letting build take any subset, costs a few lines and makes each rule testable alone. The same seam lets a test swap in a broken copy, which is how this lesson checks its own tests: a test suite that no broken rule can fail is not testing anything (lesson Property-based tests with Hypothesis calls this the test of the tests).
