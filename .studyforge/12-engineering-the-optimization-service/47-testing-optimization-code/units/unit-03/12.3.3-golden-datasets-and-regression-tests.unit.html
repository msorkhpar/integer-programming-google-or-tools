GridCap's planning service will change every month: a faster model builder, a new rule, a solver upgrade. Each change must leave last month's answers alone unless it was meant to change them. The unit tests of lesson Unit-testing one constraint at a time and the properties of lesson Property-based tests with Hypothesis say whether the rules hold; they do not say whether the plan for GridCap small is still the plan the planners reviewed. A golden dataset does: a fixed set of scenarios with their reviewed results stored next to the code, and a regression test that solves them again and compares, field by field, within stated tolerances, with a diff that says what moved. GridCap is a fictional utility's portfolio.

The Model Under Test

The model is lesson Unit-testing one constraint at a time's, unchanged.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, each with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$, the NPV of project $i$ started in year $t$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$.

A Golden Record Stores the Input's Identity and the Reviewed Result

The golden scenarios are chosen like test cases, each for a reason: GridCap tiny and small as generated, small with its 2028 budget cut by 20% so that a different year binds, and a two-project instance with a tie (two equal projects and room for one), which exists to catch a change in how ties are broken:

A record holds what a reviewer approved, and one more thing, the input's identity:

  • input_sha256 is the first 16 hex digits of the SHA-256 of the portfolio's canonical JSON, with its projects sorted by id, so the same data read in another row order has the same hash (lesson Versioned snapshots and content hashes covers content hashes of snapshots). It lets the test tell "the model changed" from "the data changed".
  • status, objective, plan and spend are the result. The objective is rounded to 3 decimals before it is stored, so the file does not record the solver's noise digits. spend is recomputed from the data and the plan, in whole $k, so it is exact.

The records live in src/golden/plan_results.json, written with sorted keys and one field per line, so that a change shows as a readable diff in code review:

Compare Field by Field, Within Tolerances Stated in Business Units

Which fields must match exactly, and which within a tolerance, is a decision to write down, field by field:

  • Status, plan and spend: exactly. They are discrete: a project is in or out, in 2028 or 2029, and the spend is a sum of integers.
  • Objective: within a tolerance in the objective's own units. The solver computes it in floating point, and HiGHS returns values with noise in the last digits. The tolerance here is 0.01 $k, $10, stated next to the reason for it:

An absolute tolerance in dollars says what a planner would call "the same". A relative tolerance would scale with the portfolio: 1e-6 of a $24,260k NPV is $24, and of a $2B portfolio (lesson What "optimal at 0.01%" means on a $2B portfolio) it is $2k. Neither is wrong, but the unit must be stated. Exact float equality is wrong, and regressions.py shows why on a real solve:

compare checks the fields in order of how much they explain, and returns one line per difference:

A changed input stops the comparison: when the data moved, every other difference is expected and says nothing about the model. A changed status stops it too: an infeasible run has no plan to diff. After that, the plan is compared over the union of both plans' projects, so an added project is reported as well as a dropped one, and a project in both plans is checked for its year.

A list of lines, rather than assert expected == actual, is the point of the function. A plain equality on two dictionaries of 27 projects fails with a wall of nested data; these lines say what moved, in the planners' words. A test then asserts that the list is empty, and pytest prints the list when it is not. On the current model, golden.py passes every scenario:

    A readable diff for a crew roster

    • each field is compared exactly or within a tolerance stated in its own units, with one readable line per difference

    Not startedPassed

Problem statement

A utility's line-maintenance group assigns jobs to crews with a model that minimizes cost, and keeps golden records of a few rosters. Their regression test compares records with == and fails with a screen of nested dictionaries whenever anything moves, including the last digits of a float. Write the comparison that replaces it.

The docstring of roster_golden.py gives a record's shape, and TOLERANCE gives what "the same" means for each float field, in that field's own units: $1 for cost, 0.01 hours for overtime. Write compare(expected, actual), returning one line per difference, in this order and format:

  • if the status differs, only status: <old> -> <new>, and nothing else, because a roster that did not solve cannot be compared field by field;
  • cost: <old> -> <new>, both with two decimals, if the costs differ by more than the tolerance;
  • for each job in either record, in sorted order, assign: <job> <old crew> -> <new crew> if its crew differs, writing none for a record that does not assign it;
  • for each crew in either record, in sorted order, overtime <crew>: <old> -> <new>, two decimals, if the hours differ by more than the tolerance; a crew a record does not list has 0 hours.

An identical record gives an empty list. About fifteen lines.

A Golden Test Catches Regressions, Not Rule Errors


regressions.py makes four changes in memory and compares each with the golden file. The first two are lesson Unit-testing one constraint at a time's broken precedence rows:



The first bug changes small's plan, and the diff says how much value it gained by breaking the rule, $53k, and which projects moved. The second passes every scenario. A golden test asks one question, "did the answer change?", and the too-strict row does not change any of these four answers. That is the same blind spot as lesson Unit-testing one constraint at a time's whole-model test, because a golden test is a whole-model test, repeated on a few fixed points. It is excellent at catching an unintended change, and it says nothing about whether the stored answer was right. The unit tests and properties answer that; the golden test guards what they approved.


Note also which scenarios caught bug 1: only small. A golden set is worth what its scenarios lean on, which is why each one should be chosen for something that binds.


Tell a Data Change and a Tie From a Regression


The other two changes are not model bugs, and the comparison has to say so:



Change 3 lowers one budget, as a new data snapshot might. Without the input hash the test would report a long plan diff and someone would hunt for a model bug that does not exist. With it, the first and only line says the scenario's data are no longer the reviewed data. The fix is to decide whether the scenario should follow the new data, then regenerate that record and review its diff.


Change 4 reads the same two projects in the opposite order. The input hash is unchanged (it sorts the projects), the value is unchanged, and the plan funds B instead of A: the solver broke a tie, two plans of equal value, the other way. Lesson Alternative optima and deterministic tie-breaking shows where ties come from and how a second criterion picks one plan on purpose. Whether a tie flip is a failure depends on the contract: if planners were promised a specific plan, it is; if they were promised the best value, it is not. The golden test here fails on it, because a plan nobody reviewed should not ship silently, and the last line tells the reviewer it is a tie rather than a worse plan.

Update a Golden File on Purpose, and Review the Diff


A golden file goes stale whenever an answer is meant to change: a new rule, a corrected cost, a new scenario. Updating it is part of the change, never a way to make a red test green. golden.py does both jobs: run plainly, it compares; run with --update, it rewrites the file:




The rule that keeps the file honest: update it in its own commit, or in the same commit as the change that explains it, and read the diff of the JSON in review as carefully as the code. Because the file is written with sorted keys and one field per line, a moved project is one changed line and a new objective is another. A reviewer who sees 20 plan lines change in a commit titled "refactor the builder" has found a bug.


Summary


  • A golden record stores the input's identity and the reviewed result. Scenarios are chosen to make different rules bind; the input hash separates data changes from model changes.
  • Compare field by field, within tolerances stated in business units. Status, plan and spend exactly; the objective within $10, never by float equality; one readable line per difference.
  • A golden test catches regressions, not rule errors. It guards answers that the unit tests and properties approved; a too-strict rule that changes none of its answers passes it.
  • Tell a data change and a tie from a regression. Check the input hash first; name a same-value plan change as a tie.
  • Update a golden file on purpose, and review the diff. One field per line, sorted keys, and a commit that explains why the answers moved.

Design Note: Why the Golden File Stores Rounded Objectives


The stored objective is rounded to three decimals and compared within $10. Storing the raw float would put the solver's noise digits into the file, so a solver upgrade that moved the noise would show as a changed line in every record's diff, and reviewers would learn to skip those lines. The rounding keeps the file stable; the tolerance, far larger than the rounding, keeps the test stable.
