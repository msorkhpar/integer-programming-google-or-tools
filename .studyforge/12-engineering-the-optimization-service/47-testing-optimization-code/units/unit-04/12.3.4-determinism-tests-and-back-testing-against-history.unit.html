Two questions remain before GridCap's test suite is complete. The first comes from the regulator: if the planning team reruns last month's snapshot, will it get last month's plan, byte for byte? The second comes from finance: had this version of the model been used in past planning cycles, what would it have chosen, and how does that compare with what was approved? A determinism test answers the first on every commit. A back-test answers the second by replaying past cycles through today's model. GridCap is a fictional utility, and so is its history: the past cycles in this lesson are invented by the course, as the section on back-testing explains.

The Model Under Test

The model is lesson Unit-testing one constraint at a time's, unchanged.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, each with parent $p(c)$ and lag $L_c$ years.

A Determinism Test Runs Fresh Processes and Compares Bytes

Lesson Building the deterministic run harness builds the full tool: it reruns one snapshot in fresh processes, compares whole run manifests byte for byte, and names the fields that differ. A test suite needs the same idea in a smaller form, small enough to run on every commit. determinism.py keeps its three essentials:

  • Fresh processes. Each run is a new Python process, because some state lives for a whole process (HiGHS fixes its thread count at the first solve, lesson Common vs. solver-specific parameters, and what each solver rejects), and because a service worker or a rerun next year is a new process too.
  • A different hash seed in each. Python salts the hash of every str and bytes with a random seed per process unless PYTHONHASHSEED fixes it, so the order a set of project ids iterates in can change between processes. Each child gets its own seed, 1, 2, 3, ..., on purpose, so a result that depends on that order shows up as a difference instead of hiding.
  • Bytes, not values. Each child prints its golden record (lesson Golden datasets and regression tests) as canonical JSON: sorted keys, no spaces. The parent compares SHA-256 digests of the output, so any difference at all, in the plan, the spend or the status, makes the digests differ.

subprocess.run with env replaces the child's whole environment, so the mapping starts from os.environ and adds the two variables the child needs. check=True turns a crashed child into a CalledProcessError, so a crash fails the test instead of being compared as empty output. On the four golden scenarios, five processes each:

The determinism test asserts that each list of digests has one distinct value. It does not compare them with a stored digest: that is the golden test's job, and keeping the two apart means a determinism failure always means "runs disagree", never "the answer moved".

What a pass proves has limits, which lesson Building the deterministic run harness lists: the same software on the same machine repeats. Run the test in the image that runs production, and treat a solver upgrade as a change that needs the golden file reviewed again.

A Determinism Test Must Be Able to Fail

A test that has never failed may be unable to: it may compare a field that never changes, or run everything in one process. So the suite keeps a known-bad case next to the real ones and asserts that it fails. Here the bad case is lesson Where nondeterminism comes from: threads, time limits, ties's bug: the child reads the tie scenario's projects in the order a set of their ids iterates, which depends on the hash seed:

Two of the five processes funded A, as the golden record says (their digest, cac71e767635, is the one the id-order runs printed), and three funded B. Only a tie can do this: the two plans have the same value, so the solver's choice between them follows the order the rows were built in. Whether a scenario without a tie shows the bug depends on whether its optimum is unique (challenge 1 asks you to try GridCap small); the tie scenario exists to give the test something it must catch. The fixes are lesson Where nondeterminism comes from: threads, time limits, ties's (build from a sorted order) and lesson Alternative optima and deterministic tie-breaking's (a tie-break the model states).

    Bytes that repeat for a routing run

    • a determinism comparison must tell real differences from noise, or it can never fail
    • runs are compared as canonical bytes, with clocks left out and floats rounded

    Not startedPassed

Problem statement

A parcel company's routing service must give the same routes every time it reruns a day, and its determinism test compares run records from fresh processes. Compared as they are, two records never match: each holds the time the run started and how long it took, its cost carries floating-point noise, and its set of unserved stops prints in whatever order the process's hash seed gives.

The docstring of run_bytes.py gives a record's shape. Write:

  • canonical(record), the record as bytes that are equal exactly when two runs did the same work: without the two clock fields (started_at, and wall_seconds inside stats), with every float rounded to 6 decimals and -0.0 written as 0.0, with dictionary keys sorted, each set as a sorted list, and each list kept in its order, since a route visits its stops in order;
  • repeats(records), True when every record in the list has the same canonical bytes.

json.dumps(..., sort_keys=True, separators=(",", ":")) writes compact JSON with sorted keys; JSON has no sets, so turn them into lists first. About fifteen lines.

Back-Testing Replays Past Cycles Through Today's Model


A back-test runs today's model on the inputs of past planning cycles and sets each result beside the plan that cycle approved. It does not say which plan was right; the past did not happen under today's rules. It says how today's model would have behaved on real situations, which surfaces differences a planner can explain or must question.


A real back-test needs an archive: for each past cycle, the input snapshot the cycle used (lesson Versioned snapshots and content hashes's versioned snapshots) and the plan it approved. GridCap has no past, so history.py invents one, and says so in its docstring:


  • the snapshot of cycle $Y$ is GridCap small generated with seed $Y$, its years moved to start in $Y$;
  • the plan approved in cycle $Y$ is what an earlier version of the model chose on that snapshot. That version charged each project's whole cost to its start year, the lump-cost shortcut lesson Cash-flow spreading across years warns about.


Nothing in this history is a real utility's decision, and nothing below is evidence about how real planners or real models behave. What it shows is the shape of the test, and what reading one is like.

Read Every Difference as a Question, Not a Verdict



Read it as a reviewer would, one line at a time.


  • Today's model is feasible on every past snapshot and its plans break no rule. That part is a test: assert it, because a model change that made an old snapshot infeasible would be a regression in the data the service must still be able to replay.
  • Every approved plan overspends in a later year under today's accounting. That is not a bug in the past plans. The earlier model charged a two-year project's whole cost to its start year, so it saw nothing in the second year; spread over its real years of work, the cost lands in years the earlier model thought were free. The first line of each cycle names the year. This is the finding that would have justified the model change, and a back-test is how a team shows it.
  • Today's NPV is higher in every cycle, by $1,329k to $3,586k. That number cannot be read as "today's model is better by that much": part of the gain comes from plans the past model refused and part from the past model's plans being worth less once their costs are counted in the right years. It is a question to put to finance, not a result to report.
  • Projects moved, added and dropped are the list a planner reviews: for each, is the reason one of today's rules, a cost now counted correctly, or something to question?


A back-test is slower than the rest of the suite (one full solve per past cycle) and its interpretation needs people, so it runs when the model changes and before Budget Lock (lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock), not on every commit. Its pass/fail part is small: every past snapshot still solves, and today's plans break no rule. The rest is a report.

Where Each Kind of Test Runs


The four lessons of this module give five kinds of test. They differ in what they catch and in how often they can run:


TestLessonCatchesWhen
one rule at a timeUnit-testing one constraint at a timea rule too loose or too strict, namedevery commit
propertiesProperty-based tests with Hypothesisthe instance nobody wrote; with a witness, too-strict modelsevery commit, fixed seed; more examples nightly
goldenGolden datasets and regression testsany unintended change to reviewed answersevery commit
determinismDeterminism tests and back-testing against historyruns that disagreeevery commit (few runs); lesson Building the deterministic run harness's ten runs before Budget Lock
back-testDeterminism tests and back-testing against historyhow a model change plays on past cycleseach model change, and before Budget Lock


No one kind is enough. Lesson Unit-testing one constraint at a time's too-strict lag passed the whole-model test, every validity property and every golden scenario, and was caught by one unit test's allowed half and by the witness property.


Summary


  • A determinism test runs fresh processes and compares bytes. Each run gets its own hash seed; the digests of canonical output must all be equal. It is lesson Building the deterministic run harness's harness, small enough for every commit.
  • A determinism test must be able to fail. Keep a known-bad case, here rows read in set order on a tie scenario, and assert that it fails.
  • Back-testing replays past cycles through today's model. It needs an archive of snapshots and approved plans; GridCap's history is invented by this course.
  • Read every difference as a question, not a verdict. Assert that past snapshots still solve to valid plans; report the rest for planners and finance.

Design Note: Keep Determinism and Golden Tests Apart


It is tempting to make one test do both: solve in five processes and compare each digest with a stored one. Then a failure could mean either "the runs disagree" or "the answer moved", and the first thing anyone does is work out which. Two tests, each with one question, fail with an answer instead. The same thinking keeps the back-test's assertions to the few facts that must hold, and leaves the rest as a report for people.
