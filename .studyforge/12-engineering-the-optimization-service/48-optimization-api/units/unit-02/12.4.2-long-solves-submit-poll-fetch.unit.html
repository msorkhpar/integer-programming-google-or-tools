The planning tool's team tries lesson A REST API with FastAPI's API on the medium portfolio, 400 projects over ten years, and the request never comes back. The solve is still running, but the browser, and every proxy between it and the API, has its own timeout, and one of them gives up first. A planner then clicks again and starts a second solve of the same scenario. The answer is to stop solving inside the request. This lesson turns each solve into a job: one request submits it and gets an id back at once, later requests poll its status, and a last one fetches the result. It also gives every way a solve can end its own status, and keeps a crashing solver from taking the service down with it. (GridCap is fictional; no number in it is real.)

The Model

The jobs solve the model of lesson A REST API with FastAPI, restated here whole. Two things change around it, not in it: a request may now name any GridCap size, up to the 10,000-project large; and every job runs with a time limit and a relative gap tolerance of 0, so a stop before the proof is visible as a gap.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$, the NPV of project $i$ started in year $t$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k), the request's value if it sends one.

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$.

Objective.

Constraints.

The relative gap the jobs report compares the best plan found, worth $v$, with the solver's bound $\bar v$, a value no plan can beat (lesson Best bound, incumbent, absolute and relative gap): $\text{gap} = (\bar v - v) / |v|$, with 1 as the smallest divisor, and never below 0 (relative_gap below takes $\max(0,\ \bar v - v)$, so a bound under the value gives 0). A gap of 0 means the plan is proven best.

A Long Solve Must Not Hold the Request Open

With the solve inside the request, three things go wrong at once:

  • Something times out before the solve ends. The planner's browser, a proxy, a load balancer: each closes a connection that stays silent too long, and the API cannot know which will give up first. The solve keeps running for nobody.
  • A retry starts a second solve. The planner, or the tool, sends the request again, and two solves of the same scenario now compete for the machine.
  • Nobody can ask how it is going. A request either answers or it does not; there is no "still running, 40% of the way" in between.

So the API splits one long exchange into three short ones:

StepRequestAnswer
submitPOST /jobs with the scenario202 Accepted at once, with a job id
pollGET /jobs/{id}the job's status, as often as the caller likes
fetchGET /jobs/{id}/resultthe result once the job has finished; 409 Conflict before

202 Accepted is the HTTP code for "received, and the work will happen later". 409 Conflict says the request clashes with the current state of the thing it names: the result does not exist yet. The caller decides how often to poll; every poll is cheap, because it only reads a status.

BackgroundTasks Runs After the Response, and Keeps No Status

FastAPI has a built-in way to run work after a reply: a path function takes a BackgroundTasks argument and calls add_task(function, ...). The FastAPI docs say these tasks run after the response is sent, and suggest a bigger tool, Celery, for heavy computation that does not need to share memory with the app. background_tasks.py builds a job API on it, with time.sleep(1) standing in for a one-second solve:

The post took a full second, and the first poll already saw the final status. A server sends the reply first and runs the task afterwards; a TestClient hands you the response only after the task has run too. So a test written this way can never see a job queued or running, and a slow solve makes every test that submits one as slow as the solve.

The test client is not the only problem. BackgroundTasks gives you no job id, no status, no queue and no limit on how many solves run at once; the jobs dict above is something the code had to add by hand. Fifty submits would start fifty solves side by side. A job service needs a place that owns each job, and a pool of workers of a size it chooses.

A Job Store Keeps Each Job's State, and an Executor Runs the Solves

Python's concurrent.futures module has the worker pool: an executor. You hand it a function and its arguments with submit, it returns at once with a future (an object that will hold the function's return value, or its exception, once it finishes), and its worker threads run the submitted calls in order. JobStore in jobs.py keeps one record per job, by id, around the executor's futures:

Each decision in these lines:

  • The status is read from the future, never stored twice. A future knows whether its call has started (running()) and finished (done()). A finished job's status is the one its outcome carries. Nothing can go stale, because there is no second copy to update.
  • One worker thread. max_workers=1 solves one job at a time, and the others wait in the executor's queue. A machine solving one MIP is busy; two at once share the cores and each takes longer. The pool's size is the service's choice, and it is the throttle BackgroundTasks lacked.
  • A lock around the dict. Requests are answered on several threads at once (lesson A REST API with FastAPI's threadpool), so two submits could otherwise interleave their reads and writes. threading.Lock lets one thread in at a time.
  • Ids come from a counter (job-1, job-2, ...), so the programs' output repeats run after run. A real service would use uuid.uuid4().hex, which nobody can guess or count.

A thread pool can do this only if a solve lets other threads run. Python runs one thread's Python code at a time (the global interpreter lock), and a native library can hold that lock or release it while it computes. The next run polls throughout two solves and times every poll.

Problem statement

The crew-roster optimizer assigns line crews to weeks of work, and on a full season it runs for several minutes. The scheduling tool cannot hold an HTTP request open that long, so it needs a job API: submit a roster request, poll its status, fetch the result when it is done.

In crew_jobs.py, write create_app(solve, workers=1). solve is given to you by the caller (the tests pass small stand-ins); it takes a RosterRequest, may take minutes, returns a dict with a "status" key, and may raise. The API:

  • POST /jobs with a RosterRequest body answers 202 at once with {"job_id": ..., "status": "queued"}. The solve runs on one of workers worker threads, never inside the request.
  • GET /jobs/{job_id} answers {"job_id", "status", "message", "ahead"}. For a queued job, ahead is how many queued jobs were submitted before it, so the tool can say "2 jobs ahead of yours"; the job being solved is not counted, and ahead is 0 for any job not queued. The status is "queued" until a worker starts the job, "running" while it solves, then the "status" of the dict solve returned. If solve raises, the status is "failed" and the message carries the exception's text; the worker goes on to the next job.
  • GET /jobs/{job_id}/result answers 200 with the dict solve returned (or {"status": "failed", "message": ...} for a failed job), and 409 while the job is queued or running.
  • An id the API never gave out gets 404 on both GET paths.

Unlike the lesson's store, this one keeps each job's status in a record the worker updates itself, so the status says what the worker has done rather than what the executor reports. Guard the shared dict with a lock: the endpoints and the worker threads touch it at the same time. The job record, the lock, the pool, the submission order and a find that answers 404 are written; about 30 lines remain.

Every Way a Solve Ends Has Its Own Status


A planner reading a poll must know what to do next, and "done" does not say. Lesson Infeasible, unbounded, or the solver can't tell separates the ways a solve ends; the service gives each one a status of its own, with a message in the planner's words:


StatusWhenWhat the planner does
queued, runningthe job has not finishedpoll again later
optimalplan found and proven bestuse it
time_limitthe limit stopped the solve; a plan with its gap, or no planuse it with its gap, or run longer
infeasibleproven: no plan meets every rule and budgetchange the scenario
failedthe solve broke; nothing was learned about the scenarioreport it; the inputs were not judged


outcome_of reads MathOpt's termination reason and limit (lesson Reading SolveResult: termination, primal and dual solutions, statistics) and writes that table in code:



Everything else (unbounded, a numerical error, a limit the service never set) lands in failed with the solver's own reason in the message: none of them says anything about the planner's scenario. The worker around it, run_job, builds and solves the model, and turns any exception into a failed outcome, so a broken solve never escapes into the executor:



The __context__ line is lesson Common vs. solver-specific parameters, and what each solver rejects's: in OR-Tools 9.15, a refused solve raises an AttributeError whose real reason is on its __context__. job_outcomes.py submits six jobs to one store, one for each way to end, and prints each outcome (numbers that vary from run to run, such as a time-limited plan's NPV, are masked as $...k). The small portfolio's must-do P017 costs $5,310k in 2030 or 2031, so budgets of $5,000k in both years leave it no start:






Read the two time_limit lines and the infeasible line together. The large job found no plan, and its message says that proves nothing; reporting it as infeasible would send a planner to cut a budget rule that may be fine. Only the 2030-31 cut was proven to have no plan.


Now the failed line. The job asked HiGHS for 2 threads, and the earlier jobs in the same process had solved with HiGHS's own default. Lesson Common vs. solver-specific parameters, and what each solver rejects showed why that fails: the first HiGHS solve in a process fixes HiGHS's thread count, and a later solve asking for a different count is refused with kError [INTERNAL]. The worker caught it, the job ended failed, and the next job ran normally. The lesson for the service is about the request model, not the worker: highs_threads should never have been a request field. A setting that belongs to the whole process (HiGHS's threads, and with them the run's reproducibility, section 10) is the service's configuration, fixed once at start-up. A request may carry only what can differ from one solve to the next: the scenario and its time limit.

Problem statement


The crew-roster service solves with CP-SAT (lesson Integer and Boolean variables, linear constraints over integers), not MathOpt, and CP-SAT has its own status codes. The job service still promises its callers the same four finished statuses as the lesson's: optimal, time_limit, infeasible and failed. Something has to translate.


Write outcome(status, objective, bound, limit_s) in roster_outcome.py. The roster model maximizes; objective and bound are the solver's objective_value and best_objective_bound, and limit_s is the time limit the job ran with (the only limit the service sets). Return a dict with status, value (the roster's value, or None when there is no roster), gap (or None) and a one-sentence message for the planner.


CP-SAT's statuses, as lesson Integer and Boolean variables, linear constraints over integers teaches them:


CP-SAT statusWhat it says
cp_model.OPTIMALa roster was found and proven best
cp_model.FEASIBLEa roster was found; a limit stopped the search before the proof
cp_model.INFEASIBLEproven: no roster meets every rule
cp_model.UNKNOWNa limit stopped the search before any roster was found or any proof
cp_model.MODEL_INVALIDthe model itself was refused


Map each to the service status that tells a planner the truth, as lesson Infeasible, unbounded, or the solver can't tell's distinctions do. The gap is the distance from the roster's value to the bound, as a share of the roster's value (with 1 as the smallest divisor, so a roster worth 0 does not divide by zero). A roster proven best has a gap of exactly 0.0, whatever the two numbers say; a roster stopped by the limit has the gap computed from them, never below 0; a job with no roster has None. The tests use two real CP-SAT solves and three hand-made statuses, so any correct mapping passes.

A Solver Crash Must Not Take the API With It


run_job catches every Python exception. It cannot catch a crash in native code: when a C++ solver reads memory it should not, the operating system ends the whole process with a signal, and every thread in it, the API's included, dies at once. Lesson A PuLP model end to end with CBC found one such crash in the runner: a process that has imported PuLP is killed with SIGSEGV on a HiGHS MIP solve through MathOpt. This module's code never imports pulp; legacy_report.py plays a dependency that does, as a report helper might:



With the solve in a thread of the API's process, thread_crash.py runs that service in a child process (because the crash ends whichever process has it) and reports how it ended:



The API process is gone, and with it every job in its store, the queued ones included. The fix is to run each solve in a separate worker process. concurrent.futures.ProcessPoolExecutor is an executor whose workers are child processes, and JobStore takes any executor, so the API code does not change. crash_isolation.py:






The worker process died, and its future ended with a BrokenProcessPool exception instead of a result. JobStore.outcome turns that into a failed outcome, so the job reads failed like any other failure, and the API kept answering. A pool that lost a worker refuses all further work, so the program replaces it with a fresh ProcessPoolExecutor, and the next job solved normally.


Two details of worker processes. Each worker starts as a fresh Python that imports the program's main file again, so crash_isolation.py keeps its top level to the standard library and its work in main(), behind if __name__ == "__main__":. And everything sent to a worker or returned from it is copied between processes (pickled), so the request and the Outcome must be plain data, which a pydantic model and a dataclass are.


The import order mattered here too. Lesson A PuLP model end to end with CBC shows only that a process which has imported pulp crashes; pulp_order.py runs the three orders, each in its own process, on a MIP with one integer variable and one row:



Only pulp imported before OR-Tools crashed. That is why legacy_report.py imports pulp at its top, and why crash_isolation.py imports nothing heavy at its own top: a fresh worker process loads legacy_report first. It is also a warning against trusting the order: one reshuffled import line in a module far from the solver decides whether the service crashes. Keep the two libraries out of one process instead.


A process per worker is also what lesson AWS Batch on Fargate, Step Functions and Lambda: who does what scales up: there, each job runs in its own container on AWS Batch, the API only records and hands out jobs, and the job store moves from a dict in memory to storage that survives a restart.


Summary


  • A long solve must not hold the request open. Submit answers 202 and an id, poll answers a status, fetch answers the result, or 409 before it exists.
  • BackgroundTasks runs after the response, and keeps no status. A TestClient returns only after the task ran (the post took 1 s), and there is no id, queue or limit.
  • A job store keeps each job's state, and an executor runs the solves. The status is read from the job's future; one worker thread solves while polls answer in under 0.1 s.
  • Every way a solve ends has its own status: optimal, time_limit (with or without a plan), infeasible (proven only), failed (the solve broke). Process-wide solver settings, such as HiGHS's threads, are the service's configuration, never a request field.
  • A solver crash must not take the API with it. In a thread it killed the process with SIGSEGV; in a ProcessPoolExecutor it failed one job, and a new pool ran the next.

Design Note: Where the Job State Lives


This lesson keeps jobs in a dict, in the API's memory. It is the simplest thing that works, and it has one hard limit: restart the API, and every job, queued, running or finished, is gone, while a planner may still hold its id. Lesson Storing scenarios and results in SQLite stores scenarios and results in SQLite, and lesson AWS Batch on Fargate, Step Functions and Lambda: who does what runs each solve as a container job on AWS. In that design the API writes a row per job, a separate worker (or AWS Batch) picks it up and writes the outcome back, and a poll is a database read. The endpoints, statuses and result schema of this module do not change; only what JobStore stands for does. Keeping create_app(store) separate from any one store is what makes that move cheap.
