GridCap's planners do not run Python. They work in a planning tool, a web application with tables of projects and budgets, and today, when they want a plan, they email an analyst, who changes a budget in a script, runs it, and pastes the result back into a spreadsheet. The planning tool's team asks for something they can call themselves: send a scenario, get a plan. This lesson builds that: a small web API in front of the course's planning model, written with FastAPI and tested without ever starting a server. (GridCap is the course's fictional utility; no number in it is real.)

A few words first. An API (application programming interface) is a set of requests one program can send another. A web API receives them over HTTP, the protocol a browser uses: each request names a method (GET to read, POST to send something to be processed) and a path such as /plans, and may carry a body, here always JSON. Each reply carries a three-digit status code (200 means it worked) and its own body. REST is the usual style for such APIs: paths name things (a plan, a portfolio), and the method says what to do with them. FastAPI is a Python library for writing web APIs. Its home page describes it as built on standard Python type hints, with Starlette handling the web part and pydantic the data part. Pydantic (lesson Typed inputs with dataclasses and pydantic) turns a class with type hints into a validator that checks and converts incoming data.

The Model

The API solves the multi-period model of lessons Start-time variables x(i,t) and timing windows and Cash-flow spreading across years, unchanged except that a request may replace any year's budget. This lesson adds no row; the marked parameter is the one the request sets.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups, each a set of projects; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$, the NPV of project $i$ started in year $t$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work, $k = 0, 1, \dots$ ($k); $B_y$, the budget of year $y$ ($k): the request's value for $y$ if it sends one, else the portfolio's.

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$.

An Endpoint Is a Path, a Method and a Function

In FastAPI, you create an application object and attach Python functions to it with decorators. @app.get("/health") says: when a GET request for the path /health arrives, call the function below and send back what it returns, converted to JSON. The FastAPI docs call such a function a path operation function, and the pair of method and path an endpoint. Here are the planning API's three endpoints, from plan_api.py:

Three things FastAPI reads from these few lines:

  • {name} in a path is a path parameter. FastAPI passes that part of the URL to the argument of the same name, so GET /portfolios/tiny calls portfolio_info(name="tiny").
  • An argument typed as a pydantic model is the request body. make_plan(request: PlanRequest) tells FastAPI to parse the JSON body, check it against PlanRequest, and pass the result in.
  • The return type is the response model. -> PlanResponse makes FastAPI check what the function returns against PlanResponse, keep only its fields, and convert it to JSON. The docs note that a return value that does not fit becomes a server error, never a wrong reply.

make_plan is the whole optimization step: it builds the model with the request's budgets merged over the portfolio's ({**pf.budget, **request.budget}: a later dict wins on a shared key), solves it with HiGHS through MathOpt (lesson Model, variables, constraints, objective), and reads the plan with starts_of and the spend with spend_of, both in plan_model.py.

Calling it with no server

A web API normally runs inside a server, a program that listens on a network port and hands each incoming request to the application. You do not need one to call the API. FastAPI's TestClient (re-exported from Starlette, built on the HTTP library httpx) sends requests straight into the application object, in the same process, and returns real HTTP responses. Everything in this module runs that way, because the course's runner has no network. From first_calls.py:

The tiny portfolio's plan funds five of its eight projects for an NPV of $2,473k, and spends less than each year's budget. Look at the budget keys: 2027 was an int in Python and arrives as the string "2027". JSON allows only strings as object keys, so every dict[int, ...] loses its key type on the way out. Lesson Result schemas planners can consume returns spend as a list of rows for this reason.

TestClient also prints a warning on import in the runner: Starlette 1.10 announces that its test client will move from httpx to a package named httpx2. It works the same either way. The programs filter that one warning out, so their output shows only what they print.

To serve the same app to other machines, you would start a server. The FastAPI docs show fastapi dev for development and fastapi run for production, both of which start Uvicorn, a server program. This is read-along only: the course runs no server, and the runner image does not include one.

The server would then answer the same requests at http://<host>:8000/plans. Lesson Containerizing a solver service packages the service in a container for exactly that.

The Request Is a Pydantic Model, and FastAPI Refuses What It Does Not Fit

The request a planner tool sends is a contract: which portfolio, which budgets to change, how long the solver may run. PlanRequest writes that contract as a pydantic model:

Each line is a rule:

  • Literal["tiny", "small"] allows exactly those two strings. (The API solves inside the request, so it offers only the portfolios that solve in well under a second; lesson Long solves: submit, poll, fetch lifts that.)
  • dict[int, Money]: the keys must be whole numbers, and each value an int that is ge=0 (greater than or equal to 0). Field(...) attaches such constraints, and Annotated lets one constrained type be reused.
  • default_factory=dict gives each request its own empty dict when the field is left out.
  • gt=0, le=60: the time limit is above 0 and at most 60 seconds.
  • extra="forbid" refuses a field the model does not declare. Pydantic's default is to ignore one, which would let a misspelled budgets fall away silently and the job run on the default budgets.

When the body does not fit, FastAPI never calls make_plan. It answers 422 Unprocessable Entity with a list of errors, each giving the field's location (loc) and a message. From bad_requests.py:

The first five were refused by pydantic, each with the exact place the planner tool must fix. The budget key "2028" arrived as a string and was accepted as the year 2028, because pydantic converts a string that spells an integer; "next year" does not, so it was refused.

The last two came from the endpoints' own code. Whether 2035 is one of the plan's years depends on the portfolio, which the request model does not know, so make_plan checks it and raises HTTPException(status_code=422, ...). FastAPI turns that exception into a reply with the given code and {"detail": ...} as the body. GET /portfolios/huge gets 404 Not Found: the path names something that does not exist.

The order matters. Every check here runs before a model is built. A negative budget that reached the model would not fail: it would produce a model with no plan, and the planner would read "infeasible" when the truth is "you sent a typo".

Problem statement

A vegetation team plans which overhead circuits to trim this season. Their scheduling tool will call an API with a JSON body like this:

The optimizer behind the API trusts its input: a negative budget or a repeated circuit would build a model that answers a question nobody asked. So the API must refuse such a request with a 422 before any model is built, and say which field is wrong.

In trim_api.py, add the rules to the two pydantic models. The endpoint is written. The rules:

  • budget is a whole number of $k, zero or more. A zero budget is a real request: trim nothing.
  • circuits has at least one circuit, and no two circuits share a circuit_id.
  • A circuit's circuit_id is not empty, its miles is above zero, and its cost is zero or more.
  • A field the API does not know, at the top or inside a circuit, is refused, not ignored: a misspelled budjet must never fall back to a default.

The tests send requests through FastAPI's TestClient and check the status codes, so any way of writing the rules that pydantic enforces passes. About ten lines.

An Infeasible Scenario Is an Answer, Not an HTTP Error


Now a request that fits every rule but asks for the impossible. Must-do project P002 spends $2,730k in 2028 (the plan above shows it), so a 2028 budget of $1,000k leaves the model no plan:






The reply is 200 OK with status: infeasible. That is a choice, and the right one. An HTTP status code says how the exchange went, not what the answer was. The request was well formed, the server worked, and the optimizer answered the planner's question: no plan meets these budgets. That answer goes in the body, where the planner tool reads it (lesson Infeasible, unbounded, or the solver can't tell separates infeasible from the other ways a solve ends; lesson Long solves: submit, poll, fetch gives each its own status). The codes this API uses:


CodeMeaning hereExample
200 OKthe request was processed; read the body for the answera plan, or status: infeasible
404 Not Foundthe path names something that does not existGET /portfolios/huge
422 Unprocessable Entitythe body does not fit the request's rulesa negative budget
500 Internal Server Errorthe server itself faileda bug, or a solver crash


If infeasible were a 4xx, the planner tool could not tell "you sent a broken request" from "your scenario has no plan", and those need different actions: fix the request, or change the scenario. If it were a 500, monitoring would page an engineer for a planner's budget cut.

Problem statement


The trim team now wants the API to choose. A request lists the circuits, each with its trim cost ($k) and its risk_reduction (expected outage-minutes avoided per year), the season's budget, and the ids of circuits that must_trim (a regulator's order, say). The answer is the set of circuits that avoids the most outage-minutes while the total cost stays within the budget, with every must-trim circuit in it.


Write the endpoint select in trim_select.py. The request and response models are written.


  1. Write the formulation first, on paper: the sets, the parameters with their units, a variable per circuit with its domain, the objective with its sense, and each constraint with a label. Then build it with MathOpt and solve with HiGHS.
  2. Answer status: "optimal" with chosen (circuit ids, sorted), their total cost and total risk_reduction.
  3. When no selection can trim every must-trim circuit within the budget, the request was still a good request: answer 200 with status: "infeasible", no circuits, and zeros.
  4. A must_trim id that names no circuit in the request is a bad request: raise an HTTPException with status 422 before building anything. So is a request that lists the same circuit_id twice: chosen could not say which of the two was meant, so answer 422 for it too.


The tests check the answers to small requests, so any correct formulation passes.

A Blocking Solve Belongs in a def Path, Never in async def


FastAPI accepts a path function written with def or with async def, and the two run differently. The FastAPI docs on concurrency say a def path operation function is run in an external threadpool, so it cannot block the server. An async def function runs directly on the server's event loop, the single thread that switches between requests whenever one of them waits with await. A solve never awaits: mathopt.solve holds its thread until it returns. Put it inside an async def, and the event loop can do nothing else meanwhile.


def_or_async.py measures it. Each path blocks for one second with time.sleep(1), standing in for a solve, and three requests are sent at the same moment from three threads:




Under async def, the three requests ran one after another: the third planner waited three seconds for a one-second answer, and a fourth request of any kind, even GET /health, would have waited too. Under def, FastAPI ran each call in its own worker thread and all three finished together. Every path in this module that solves is a def.


This is not yet a fix for long solves. A def path still holds its request open for as long as the solve runs, and the threadpool has a fixed number of threads. A solve that takes minutes needs a different shape, which is lesson Long solves: submit, poll, fetch.


FastAPI Writes the API's Description From the Same Models


Every FastAPI application describes itself in OpenAPI, a standard format listing an API's paths, methods, parameters and replies, with data shapes written in JSON Schema. A served app publishes it at /openapi.json and draws interactive pages from it at /docs. The same description is available in code from app.openapi(); openapi_view.py prints part of it:






FastAPI added the 422 reply to every path that takes input, because it does the validation itself. It did not discover the 404 that portfolio_info raises: that entry is there only because the decorator declares it with responses={404: ...}. A reply the code raises but the decorator does not declare is invisible to the planner tool's developers.


The request model's part of the description is pydantic's JSON Schema for PlanRequest (PlanRequest.model_json_schema()), and each rule above appears in it:



extra="forbid" became "additionalProperties": false, ge=0 became "minimum": 0, gt=0 became "exclusiveMinimum": 0, and the Literal became an enum. Only portfolio is required, because the other two fields have defaults. The rules are written once, in the model, and the validation, the 422 messages and the published description all come from that one place.


Summary


  • An endpoint is a path, a method and a function. A decorator binds them; a path parameter, a pydantic body and a return type are read from the function's signature. TestClient calls the app with no server.
  • The request is a pydantic model, and FastAPI refuses what it does not fit. A body that breaks a rule gets 422 with the field's location, before any model is built.
  • An infeasible scenario is an answer, not an HTTP error. 200 with status: infeasible; 4xx only for a bad request, 5xx only for a broken server.
  • A blocking solve belongs in a def path, never in async def. Three one-second calls took 3 s under async def and 1 s under def.
  • FastAPI writes the API's description from the same models. OpenAPI and JSON Schema come from the models and decorators; declare every reply you raise.

Design Note: Validate at the Edge, Model in the Middle


The checks in this lesson sit at the edge of the service: the request model and the first lines of an endpoint. The model builder (plan_model.build) checks nothing and trusts its input. You could put the checks in the builder instead, so that every caller, not only the API, benefits. Lessons Schemas for model inputs and Data-quality checks that prevent infeasibility do part of that for the data itself. The split here is by audience: the edge refuses what a caller can fix and names the field; the builder assumes a valid scenario and states the model. A check in both places is fine; a check in neither is how a typo becomes "infeasible".
