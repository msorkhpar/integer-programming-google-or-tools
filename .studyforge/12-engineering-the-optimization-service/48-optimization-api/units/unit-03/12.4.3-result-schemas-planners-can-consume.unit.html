The planning tool's developers now poll jobs and fetch results, and they start building screens: a plan table, a chart of spend against budget by year, a banner with the job's status. Within a week they have questions the API cannot answer. Is npv in dollars or thousands? Why are the years strings? What does a missing gap mean, and can status say anything other than the values they have seen? A result is read by another team's code, which cannot ask. This lesson writes the result as a schema: every field named, typed and described, the rules between fields enforced before a result leaves the service, and a way to change it later without breaking the tool. (GridCap is fictional; no number in it is real.)

The Model

The jobs solve the model of lessons A REST API with FastAPI and Long solves: submit, poll, fetch, restated here whole; this lesson adds no row. What it adds is a report of the model's own expressions: the spend of each year, the left side of $\text{budget}_y$, is what spend_by_year returns next to $B_y$.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$, the NPV of project $i$ started in year $t$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k), the request's value if it sends one.

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$.

Objective.

Constraints.

In the result, spend is $\text{spend}_y$ evaluated on the plan, budget is $B_y$, and headroom is $B_y - \text{spend}_y$. npv is the objective's value, bound the solver's bound on it, and gap is $\max(0,\ \text{bound} - \text{npv}) / \max(|\text{npv}|,\ 1)$, lesson Long solves: submit, poll, fetch's formula: 1 is the smallest divisor, so a plan worth 0 still has a gap, and a bound below the value gives a gap of 0.

A Result Carries the Plan, the Money by Year, the Value, the Gap, the Status and a Message

schemas.py defines the result as three pydantic models: one row per funded project, one row per year, and the result around them.

Why each field is there, and in this shape:

  • status and message come first in meaning. A planner reads the status to know what kind of answer this is (lesson Long solves: submit, poll, fetch's table) and the message for what to do. Literal fixes the four values, so a tool can switch on them and know the list is complete.
  • npv, bound and gap travel together. NPV alone hides whether the plan is proven; lesson Writing results for planners, finance and auditors shows finance reading NPV with its status and gap. bound lets a tool show the best value still possible.
  • The plan is a list of rows, not a dict. Each row repeats what a table needs (program, region, cost, value) so the tool joins nothing. Lesson A REST API with FastAPI showed dict[int, ...] keys arriving as strings; rows keep year an integer and the rows in order.
  • spend_by_year puts each year's spend next to its budget. The headroom is the first number a planner asks about after a budget cut. Every number is computed from the data by spend_of, not read back from the model, so the check is independent of the solve (lesson Writing results for planners, finance and auditors).
  • snapshot and job_id tie the result to its inputs. The snapshot is lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock's id: a hash of the request, the portfolio's content hash and the solver settings, so two results with equal snapshots came from equal inputs. schema_version is the subject of the last section.
  • Every field has a description with its unit. Money is in $k everywhere, and the description says so, in the published schema, where the tool's developers will look.

The infeasible result has the same fields, with null where there is no number and empty lists where there are no rows. A tool draws both with the same code; it never has to check whether a key exists.

The message is written from the fields, never typed separately (lesson Writing results for planners, finance and auditors's rule): the NPV in "Best plan found and proven: NPV $24,260k." is npv, formatted. An infeasible result's message says what to check, not which rows conflicted; lesson Turning an IIS into a planner message turns an IIS into a message that names the projects and rules, and a service that runs it would put that text here.

Every Field Has One Meaning, and the Schema Refuses Results That Contradict Themselves

Types and field rules check one field at a time. Some mistakes are between fields: an optimal result with no NPV, an infeasible one with a plan, a gap with no bound to measure it from. A planner tool that receives one will show something false, and its developers cannot tell whether the tool or the service is wrong. Pydantic's @model_validator(mode="after") runs after every field has been checked, sees the whole object, and refuses it by raising ValueError:

The last rule is an equivalence: a gap is present if and only if both numbers it is computed from are. A time_limit result may go either way (with a plan and a gap, or with neither), and the rules allow both. schema_rules.py builds one consistent result, two odd ones, and five that break one rule each:

Field rules report the field (['gap'], ['status']); the model validator reports the model as a whole, with its message. The program also builds two odd results that pass: an optimal result with a bound of 950 and a gap of 0.06, and a time_limit result with no plan but a bound of 1,000. The validator checks only the three pairings in its code; it does not check that a proven plan's gap is 0, or that the gap equals its formula. Those numbers come from outcome_of, and the module's tests check them there. Because fetch returns a PlanResult, a bug in the worker that built such a result would end in a server error inside the service, not in a wrong screen at the planner's desk. That is the right place for it to fail.

Problem statement

The trim service from the earlier practices now runs as jobs, and a scheduling tool reads its results. Each result says how the job ended, which circuits to trim, how many crew hours that takes in each month against the crews' capacity, and how good the plan is. The tool's developers will build screens on it, so the service must never send a result whose fields disagree with each other: an "optimal" result with no value, or an "infeasible" one that lists circuits.

Write the rules into TrimResult and MonthHours in trim_result.py:

  • status is one of optimal, time_limit, infeasible, failed, and message is not empty.
  • gap is never below zero, and it is given exactly when both value and bound are.
  • An optimal result carries a value (0 is a value). An infeasible or failed result carries no value and lists no circuits.
  • A month is 1 to 12; crew_hours and capacity are zero or more. hours_by_month lists each month once, in increasing order, and no month's crew hours exceed its capacity.

Put the rules about one field on the field, and the rules that compare fields in one @model_validator(mode="after") that raises ValueError. Pydantic reports either as a ValidationError. The tests build results by hand, each pairing an accepted one with a refused one, so any way of writing the rules that pydantic enforces passes.

A job that stops with no plan still has a bound: MathOpt's best_objective_bound() is always available (its docstring says so), and with no plan in hand it can be infinite. inf_and_null.py solves the large portfolio with a 1-second limit and follows that number into JSON:






The JSON standard has no infinity and no NaN. Python's json.dumps writes Infinity anyway, a token many JSON parsers in other languages refuse, so the planner tool's code would fail on a reply that Python produced without complaint. With allow_nan=False, Python refuses too. Pydantic chooses a third way:






Pydantic wrote the infinite float as null, silently, and then refused to read its own output back, because a float field does not accept null. A schema that says "number" sends null: the tool's developers, reading the schema, would not expect it. The honest version declares the field float | None and puts None there on purpose when the number does not exist:



That is what PlanResult does: outcome_of (lesson Long solves: submit, poll, fetch) sets bound only when it has a plan, and npv, bound and gap are all float | None. The rule for every number in a result: if it can be missing, say so in the type, and send null; never let an infinity or a NaN reach the JSON writer.

Problem statement


A trim job has finished. The worker knows how it ended (status, message), the plan's value (outage-minutes avoided per year, or None when there is no plan), the solver's best bound, and the circuits chosen. The scheduling tool wants a TrimResult (the schema is in the file) it can draw as-is.


Write build_result(status, message, value, bound, chosen, work, capacity) in trim_builder.py:


  • circuits: the chosen circuit ids, sorted.
  • hours_by_month: one row for every month in capacity, in increasing month order, with the crew hours the chosen circuits need that month (work[circuit] = (month, crew_hours)), 0 for a month with no work, and that month's capacity. A result with no plan has no rows.
  • bound: the solver's bound, except that an infinite bound (what a solve with no plan reports) becomes None. JSON has no infinity, and the result must read back from its own JSON.
  • gap: (bound - value) / |value|, with 1 as the smallest divisor so a plan worth 0 still has a gap; None when there is no value or no finite bound. The job maximizes, so a bound below the value means the plan is proven: clamp that gap to 0, never report it negative (the schema's ge=0 refuses a negative gap).


The tests call build_result with small hand-made jobs. About fifteen lines.

A Planner Tool Declares Only What It Reads, and the Service Only Adds Fields


The planner tool is another program, with its own release schedule. planner_client.py plays it: its own pydantic models declare only the fields it reads (no bound, no snapshot, no region), and it draws a summary from a result for the small portfolio with the 2029 budget cut to $7,000k:






The cut cost $615k of NPV ($24,260k before), and the plan now spends 2030's budget to the last thousand. The tool parsed the service's JSON with model_validate_json and drew every number from it, without knowing about the fields it does not declare: pydantic's default for undeclared fields is to ignore them. (The order of keys inside a JSON object carries no meaning either; pydantic reads each field by name.) That default is what lets the service grow. The program then changes the result in two ways:






Adding a field broke nothing. Renaming one broke the tool at once, although the number was still there under a new name. So the service follows one rule: add fields, never rename, remove or change the meaning of one within a schema version. A change of that kind is a new schema_version, served next to the old one until every tool has moved. The request side is the opposite: lesson A REST API with FastAPI's extra="forbid" refuses unknown request fields, because a field the service ignores there is a planner's setting that silently did nothing. Be strict in what the service accepts and in what it promises, and let its readers ignore what they do not need.


Summary


  • A result carries the plan, the money by year, the value, the gap, the status and a message, as rows and typed fields with units, tied to its inputs by job id and snapshot.
  • Every field has one meaning, and the schema refuses results that contradict themselves. Field rules check one field; a model validator checks the pairs (optimal needs npv; infeasible has no plan; a gap needs both numbers).
  • No plan means null, never infinity. JSON has no infinity; json.dumps writes Infinity anyway, and pydantic writes null for a float it then cannot read back. Declare float | None.
  • A planner tool declares only what it reads, and the service only adds fields. An added field was ignored; a renamed one failed with "Field required".

Design Note: One Schema, Several Readers


Lesson Writing results for planners, finance and auditors writes three texts, for planners, finance and auditors, from one record. This lesson's PlanResult is that record made public: each reader's screen is drawn from the same fields, and no reader gets a number another does not. It would be tempting to add a field per screen (planner_summary, finance_table) and let the service format each. Then a change in one screen becomes a schema change for every tool. Keep the schema as data, with one short message for the case where the planner needs words, and let each tool format the rest.
