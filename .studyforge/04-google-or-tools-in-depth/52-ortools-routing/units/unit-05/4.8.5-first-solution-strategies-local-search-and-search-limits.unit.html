  16. Search strategies, local search and limits

The Valley plans of lessons Time windows and service times (VRPTW) and Optional visits with penalties, and pickup and delivery came from one search setting: build a first solution with PATH_CHEAPEST_ARC, then improve it with the default local search. Lesson Time windows and service times (VRPTW) already caught that setting out: a model with an extra cost found a plan with less driving (261 minutes) than the plain model's plan (287). So the plain search stopped early, at a plan that was not the best the model allows. The planner now asks three questions: how much better can the search do, how do I make it do so, and will the plan be the same if I run it again tomorrow morning?

This lesson answers them with the routing library's search parameters: the first-solution strategy, the local search metaheuristic, and the limits that stop the search. Every number here comes from runs stopped by a count of solutions or by reaching a local minimum, never by a clock, so each prints the same on every run. The model is lesson Time windows and service times (VRPTW)'s: four crews, 18 sites, windows, inspection time, 9 kits per van. The drive times are fictional.

A First-Solution Strategy Builds the Starting Routes

The search has two phases. First it builds one complete set of routes with a constructive rule, the first-solution strategy. Then local search improves it. The routing options guide lists the strategies; the ones in the table below work like this:

StrategyHow it builds routes
PATH_CHEAPEST_ARCextend each route from its start by the cheapest arc to an unvisited stop
PATH_MOST_CONSTRAINED_ARClike the above, but prefer the most constrained arc
SAVINGSthe Clarke and Wright savings algorithm: start with one route per stop, merge the pairs that save most
CHRISTOFIDESa variant of Christofides' algorithm, built on a matching
PARALLEL_CHEAPEST_INSERTIONinsert the cheapest stop at its cheapest position, all routes at once
LOCAL_CHEAPEST_INSERTIONinsert stops one by one, in creation order, each at its cheapest position
GLOBAL_CHEAPEST_ARCrepeatedly connect the two stops that make the cheapest segment
LOCAL_CHEAPEST_ARCtake the first stop with no successor yet and connect it to its cheapest one
FIRST_UNBOUND_MIN_VALUEtake the first stop with no successor and connect it to the first stop available
BEST_INSERTIONinsert by the model's whole cost; the guide says it works with optional stops only
ALL_UNPERFORMEDdrop every stop; it finds a solution only if every stop is optional
AUTOMATIClet the solver choose from the model (the default)

strategy_table.py runs each strategy on the four-crew Valley day three ways. Its first column stops the search at the first solution found (solution_limit = 1), so it shows each strategy's own construction:

Read the first column. The first solutions range from 277 to 522 drive minutes, and four strategies build no feasible routes at all on this model. Two of those failures are the guide's own rules: every Valley site is mandatory here, and ALL_UNPERFORMED and BEST_INSERTION need optional stops. The other two, CHRISTOFIDES and PARALLEL_CHEAPEST_INSERTION, failed to build a complete plan that keeps every window, kit and shift rule of this model, although PARALLEL_CHEAPEST_INSERTION built the routes of both pickup-and-delivery models in lesson Optional visits with penalties, and pickup and delivery. When the first phase fails, local search never starts, which is why those rows fail in every column. A strategy is a choice per model, and trying three or four on your own data is part of building one.

Local Search Improves Them, and a Metaheuristic Escapes Local Minima

Local search changes the current routes a little at a time. Each kind of change is an operator: relocate one stop, exchange two stops, cross two routes' tails, reverse a segment (2-opt), move a pickup and its delivery together. The default parameters switch on most of them (DefaultRoutingSearchParameters().local_search_operators). A change that breaks a rule (a missed window, an overfull van) is refused, so the search only ever moves between feasible plans.

Greedy descent accepts a change only if it lowers the cost, and stops when no change does. That point is a local minimum: no single move improves it, but a very different plan may be better. In the table's second column, each strategy's start descends to a different local minimum, from 253 to 287. Which minimum you reach depends on where you start.

A metaheuristic is a rule for leaving a local minimum on purpose. The guide lists GREEDY_DESCENT, GUIDED_LOCAL_SEARCH, SIMULATED_ANNEALING, TABU_SEARCH and GENERIC_TABU_SEARCH, and calls guided local search generally the most efficient for vehicle routing. Guided local search adds a penalty to the arcs that the current local minima use, so the search is pushed to try routes without them, then judges plans by their real cost. With it (third column), every strategy that finds a first solution ends at 253 drive minutes after 300 solutions: 34 minutes less than the 287 that lesson Time windows and service times (VRPTW)'s plain search found for this same model (four crews, trucks of 9 kits). Lesson Optional visits with penalties, and pickup and delivery's no-drop run, 283 minutes, is not a fair comparison: it used three crews with vans of 12 kits, a different model.

Is 253 optimal? The routing library cannot say. It does not compute a lower bound, so there is no gap (lesson Best bound, incumbent, absolute and relative gap) to report; "seven different starts all ended at 253" is evidence, not proof. When proof matters, a MIP or CP-SAT model of a small instance can give one, as the brute force of lesson The routing model: index manager, transit callbacks and the TSP did for eight sites.

Stop on Solutions, Not Seconds, When a Result Must Repeat

A metaheuristic does not stop at a local minimum, because leaving local minima is its job. It stops when a search limit is reached. The routing options guide lists three:

ParameterStops the search ...Default
solution_limitafter that many solutionsunlimited
time_limitafter that much wall time (time_limit.FromSeconds(30))unlimited
lns_time_limit(per neighbor) after that much time completing one large-neighborhood move100 ms in OR-Tools 9.15

The guides use time_limit, and for a production run that is the natural choice: the planner gets a plan in 30 seconds whatever happens. But a time limit makes the result depend on the machine. A faster computer, a busier one or another OR-Tools build finds more or fewer solutions in the same seconds, and so stops at a different plan. Lesson Optional visits with penalties, and pickup and delivery met an example: the dropped-visits guide's page, whose program stops after one second, reports nodes 6 and 15 dropped for 7,936; the course's copy, stopped after 100 solutions instead, drops 15 and 16 for 7,548, and prints that on every run.

When a result must repeat (a test, a report two people must reproduce, a plan you will compare with tomorrow's), fix the strategy and stop on a count. The module's builder does exactly that:

and the table program checks it by running the same setting twice:

A solution limit can still be combined with a generous time limit as a safety net, as long as the time limit is never the one that stops a run whose result you print. Lesson Deterministic time, seeds and reproducible runs makes the same point for CP-SAT, which offers a deterministic time limit; OR-Tools 9.15's routing_parameters.proto has no such field, so a solution count is the repeatable stop. (Setting log_search = True prints the search's progress, which helps when you tune a limit.)

    Search settings that repeat

    • a first-solution strategy builds one complete set of routes, and some strategies build none on a given model
    • greedy descent stops at a local minimum, and a metaheuristic such as guided local search leaves it on purpose
    • a fixed strategy with a solution limit repeats, while a time limit depends on the machine

Problem statement

A laundry's dispatch report is checked by two people every morning, and they must get the same routes from the same data. The routing code is fine; the search settings are not. Write search_parameters(strategy, metaheuristic=None, solutions=None) in search.py. It turns names such as "SAVINGS" and "GUIDED_LOCAL_SEARCH" into OR-Tools search parameters, and enforces the team's rule for repeatable runs:

  • the run never stops on wall time, so the parameters carry no time limit;
  • a metaheuristic that leaves local minima on purpose (anything but GREEDY_DESCENT) always has a solution limit: solutions if given, otherwise DEFAULT_SOLUTIONS (200);
  • GREEDY_DESCENT and the default search stop at their local minimum by themselves, so they get a solution limit only when solutions is given.

There is no model to formulate here: the routing model is fixed, and the choice is how to search it. Before you code, write the rule above as a small decision table (metaheuristic named or not, solutions given or not, the resulting solution_limit), and say which enum class each name belongs to in routing_enums_pb2.

The tests read the parameters and run one small model twice. About eight lines.

The Status Says Whether You Have Routes, Not Whether They Are Optimal


After a solve, routing.status() returns a RoutingSearchStatus. The table program collected every status it saw at each stage:



The statuses, from routing_enums.proto and the routing options guide:


StatusMeaningWhat to do
ROUTING_SUCCESSroutes found; the search ended normallyuse them
ROUTING_PARTIAL_SUCCESS_LOCAL_OPTIMUM_NOT_REACHEDroutes found, but a limit stopped the search before a local minimumusable; more search would improve them
ROUTING_OPTIMALsolved to optimalityuse them (none of this module's runs reported it)
ROUTING_FAILno routes foundtry another strategy, or check the data
ROUTING_FAIL_TIMEOUTthe time limit came before any routesmore time, another strategy, or check the data
ROUTING_INFEASIBLEthe problem was proven infeasiblefix the data or the rules
ROUTING_INVALIDthe model or parameters are not validfix the code
ROUTING_NOT_SOLVEDnot solved yet


The first column's runs stopped after one solution, before any local minimum, and their status says so. ROUTING_SUCCESS does not mean optimal: the greedy-descent column reports it for plans from 253 to 287. And a failure is rarely a proof: lesson Vehicles, capacities and dimensions (CVRP)'s two crews with 24 kits for 33 needed got ROUTING_FAIL_TIMEOUT, not ROUTING_INFEASIBLE. Read the status before you read the plan, and when it is a failure, check the simple arithmetic (total demand, windows reachable from the yard) before you blame the search.


Start From Yesterday's Routes


Planners rarely start from nothing. Yesterday's routes are a good plan for a day that changed a little, and crews prefer routes they know. The common routing tasks guide shows how to hand the search a starting plan: build an assignment from routes with ReadAssignmentFromRoutes, then search from it with SolveFromAssignmentWithParameters. The routes are lists of nodes, one per vehicle, without the depot. One step is easy to miss: when you give a starting plan, close the model with your parameters first (CloseModelWithParameters), or reading the routes closes it with the default parameters.




Yesterday's routes are lesson Time windows and service times (VRPTW)'s 287-minute plan. Today, once with the same sites and windows and once with A305's window changed to close at 13:00 (yesterday's plan reached it at 15:00):



When yesterday's plan still fits, ReadAssignmentFromRoutes returns it with its cost (287), and the search improves it to 253 in 100 solutions. When a rule changed and the plan breaks it, the call returns None; the program falls back to a fresh solve instead of failing. Two notes for practice:


  • Starting from a plan does not keep the plan. Local search is free to move every stop, and here it did. If crews must keep most of their routes, that is a rule (a penalty per change, or fixed assignments), not a starting point.
  • ReadAssignmentFromRoutes is a feasibility test. Lesson Optional visits with penalties, and pickup and delivery used it to check hand-built plans; here it tells you that yesterday's plan no longer fits before the search starts.

The Model


This lesson changes the search, not the model. The model searched is lesson Time windows and service times (VRPTW)'s, restated here so the lesson stands alone. It is a vehicle routing model, searched by the routing library's heuristics.


Sets. $N$ the nodes, node 0 the yard and 1 to 18 the Valley sites; $V$ the crews, $|V| = 4$; $I$ the indices: one per site, a start $s_v$ and an end $e_v$ per crew.


Parameters. $c_{ab}$ drive minutes (integers, fictional); $\text{service}_a$ inspection minutes; $[a_i, b_i]$ arrival windows; $H = 480$ the shift's end; $W = 120$ the most waiting at one stop; $k_a$ kits; $K = 9$ kits per van.


Variables. $\text{next}_i$, $\text{vehicle}_i$; $0 \le \text{time}_i \le H$ (Time cumul); $0 \le \text{wait}_i \le W$ (Time slack); $0 \le \text{load}_i \le K$ (Kits cumul). All integer.

Summary


  • A first-solution strategy builds the starting routes. Strategies differ by model; on the Valley day their first plans ranged from 277 to 522 minutes and four built none.
  • Local search improves them, and a metaheuristic escapes local minima. Greedy descent stops at the first local minimum (253 to 287 here); guided local search with 300 solutions reached 253 from every start. No bound, so no proof of optimality.
  • Stop on solutions, not seconds, when a result must repeat. A time limit's result depends on the machine; a fixed strategy with a solution limit prints the same plan every run.
  • The status says whether you have routes, not whether they are optimal. ROUTING_SUCCESS is not optimality, and ROUTING_FAIL_TIMEOUT is not infeasibility.
  • Start from yesterday's routes with CloseModelWithParameters, ReadAssignmentFromRoutes and SolveFromAssignmentWithParameters, and fall back to a fresh solve when they no longer fit.

Design Note: A Search You Can Explain


A routing plan reaches a planner as "the solver says". It should reach them as "this setting, this many solutions, this cost, and this is what the cost is made of". That means a fixed strategy and a solution limit in anything you report, the status printed next to the plan, the penalties separated from the driving (lesson Optional visits with penalties, and pickup and delivery), and, when you can afford it, a second strategy as a check: when two different starts end at the same cost, that is worth saying; when they do not, the search needed more solutions.
