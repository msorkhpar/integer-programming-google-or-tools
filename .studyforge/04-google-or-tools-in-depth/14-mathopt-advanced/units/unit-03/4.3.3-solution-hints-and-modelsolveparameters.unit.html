  16. Hints and model parameters

Every month GridCap's planners re-solve the five-year plan after small changes: a revised cost here, a little more budget there. Last month's approved plan is sitting in a file, and it is usually close to this month's answer. Can the solver start from it instead of from nothing? This lesson shows how to hand a MIP solver a starting plan, a solution hint, through MathOpt; how to tell from the solver's log whether it used the hint (the result alone cannot tell you); and the other fields of ModelSolveParameters, the object that carries everything about a solve that is tied to this particular model. GridCap is a fictional utility.

The Model

The multi-period timing model of lesson Indicator constraints, with this month's one change marked. Its decisions are start-time variables: $x_{i,t}= 1$ if project $i$ starts in year $t$ of its window $T_i$; a project starts at most once and spends its cost profile from its start year on. (Lesson Start-time variables x(i,t) and timing windows, in section 6, builds this model step by step.) A hint changes nothing in the model: it is advice to the solver about where to look, not a rule about which plans are allowed.

Sets. $P$ the projects; $Y$ the years; $T_i \subseteq Y$ the start years of project $i$; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C$ the child projects, with parent $p(c)$ and lag $L_c$.

Parameters. $\text{npv}_{i,t}$ ($k); $c_{i,k}$, project $i$'s spend in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k), with $B_{2031}$ raised by 200 this month.

Variables. $x_{i,t} \in \{0, 1\}$ for $i \in P$, $t \in T_i$.

Objective.

Constraints, with $\text{spend}_y = \sum_{i \in P} \sum_{t \in T_i,\, t \le y} c_{i,\,y-t}\, x_{i,t}$:

Raising a budget only adds plans, so last month's plan still satisfies every row. That makes it a feasible hint, the best kind.

A Hint Is a Starting Plan, Passed in ModelSolveParameters

MathOpt splits a solve's settings in two:

  • SolveParameters (lesson Common vs. solver-specific parameters, and what each solver rejects) holds settings that make sense for any model: time limit, gap, threads, log output.
  • ModelSolveParameters holds settings that name this model's variables or rows, so they cannot be written before the model exists: hints, filters, a starting basis, per-objective tolerances (lesson Prioritized objectives with add_auxiliary_objective).

A hint is a SolutionHint: a dict from variables to values (variable_values), plus, for LP solvers, a dict from rows to dual values (dual_values). It goes into ModelSolveParameters(solution_hints=[...]), a list, and the parameters go to solve as model_params:

round turns each value of last month's result into an exact 0 or 1: a solver returns values like 0.9999999 for a binary, and a hint should say what the plan is, not repeat the round-off. Three hints of three kinds:

  • complete: a value for every one of the 80 variables, and the plan they describe is allowed;
  • partial: values for only some variables, here the 27 starts that were 1; the solver has to fill in the rest;
  • wrong: values for every variable that break the rules (every project started in every year).

The SolutionHint docstring says what a solver may do with each: many MIP solvers accept partial or infeasible hints and solve a small sub-MIP (a MIP over the unhinted or conflicting variables) to complete or repair them. A solver that accepts only one hint uses the first one in the list. Two facts about the API are easy to get wrong: MathOpt has no model.add_solution_hint(), the hint goes only through ModelSolveParameters; and CP-SAT's own API (lesson Hints, assumptions and SufficientAssumptionsForInfeasibility teaches it) uses a different call, model.add_hint, for the same idea.

Problem statement

A courier firm re-plans its weekly delivery routes with a MIP: a binary $y_r$ per candidate route $r$, 1 if the route runs this week. Most weeks look like the last one, so the planners want to start the solver from last week's plan.

Write hint_params(y, chosen, complete), which returns a mathopt.ModelSolveParameters holding one SolutionHint built from last week's plan. y is a dict from route name to its binary variable; chosen is the set of route names that ran last week.

  • complete=True: every route gets a value, $y_r = 1$ for $r$ in chosen and $y_r = 0$ otherwise.
  • complete=False: only the chosen routes get a value, $y_r = 1$; the solver fills in the rest.

One test solves with your parameters and reads HiGHS's log, as lesson Solution hints and ModelSolveParameters did; the others read the hint back. About five lines.

Only the Log Says Whether a Hint Was Used


The docstring is frank about the rest: how a hint is used, if at all, depends on the solver, and the reliable way to know is to read the solver's log with and without it. MathOpt passes each log line to a message callback, msg_cb, during the solve; mathopt.list_message_callback(log) makes one that appends the lines to a list. The program solves with each hint on each MIP solver and keeps only the log lines about hints:






Read it solver by solver.


  • HiGHS calls a hint a "MIP start". The complete hint was checked and accepted as a first incumbent worth 24,260, last month's NPV. For the partial hint, HiGHS solved a sub-MIP with the 27 hinted values fixed and completed it into the same plan. The wrong hint was rejected outright.
  • SCIP stores a hint as a "solution candidate". The complete one became its first incumbent ("new primal bound 2.426000e+04", that is, 24,260). For the partial and the wrong hints its log has no line at all: from the log, you cannot tell that SCIP did anything with them.
  • CP-SAT checks the hint before searching: complete and feasible; incomplete (it reports how many of the variables still free after presolve were hinted, twice, as its presolve runs in stages); or complete but infeasible, which it then tries to repair.


And in every row the answer is the same: NPV 24,298, this month's optimum, $38k above last month thanks to the extra $200k. A hint never changes the answer of a solve that runs to optimality. It can change how fast a good plan is found, which matters when a time limit stops the solve early (lesson Stopping on gap, time, nodes or solution count), and the log is where to see whether it had the chance.

Problem statement


A planning service passes a solution hint on every solve and keeps each solve's log. Its dashboard should show, per solve, what the solver did with the hint. Write hint_verdict(solver, log), where solver is "HIGHS", "GSCIP" or "CP_SAT" and log is the list of log lines. It returns one of "accepted", "partial", "repairing", "rejected" or "unknown", from these lines (lesson Solution hints and ModelSolveParameters shows them all):


SolverA line containingVerdict
HiGHSAttempting to find feasible solution by solving MIP for user-supplied valuespartial
HiGHScannot yield feasible solutionrejected
HiGHSMIP start solution is feasibleaccepted
SCIPfeasible solution given by solution candidate storageaccepted
CP-SATThe solution hint is complete and is feasibleaccepted
CP-SATThe solution hint is incompletepartial
CP-SATThe solution hint is complete, but it is infeasiblerepairing


When a log has lines for more than one verdict, the first row of the table that matches wins: HiGHS logs a completed partial hint with both its "Attempting" line and a "MIP start solution is feasible" line, and that hint was partial. A log with none of its solver's lines is "unknown": silence is not evidence either way. About twelve lines.

Filters Choose Which Values Come Back


A large model's result holds a value for every variable, most of them 0 in a selection model. ModelSolveParameters can ask for less. variable_values_filter takes a VariableFilter: skip_zero_values=True drops the zeros, filtered_items=[...] keeps only the variables listed. (dual_values_filter and reduced_costs_filter do the same for an LP's duals and reduced costs.)






The program prints how many values each solver returned, and every returned value that is not exactly 1:



The plan starts 27 projects. SCIP returned exactly their 27 values. HiGHS returned 28: one variable came back as $-2.2 \times 10^{-15}$, a binary that is 0 up to floating-point round-off, and "skip zero values" skips only values that are exactly zero. So a filter shortens the result; it does not clean it. Read a binary as chosen when its value is above 0.5, never when it is "not zero". filtered_items returns its variables whatever their values, zeros included.


An LP Starts From a Basis, Not a Hint


For an LP solved by simplex, the useful starting point is not a plan but a basis: the record of which variables and rows were at their bounds at the last vertex (lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP). The SolutionHint docstring says simplex solvers prefer a basis to a hint. Lesson Re-solving after the data changes kept one solver alive across solves to reuse its basis; ModelSolveParameters(initial_basis=...) hands a basis saved from one result to a new, separate solve:






The medium portfolio's LP relaxation (each x made continuous by setting integer = False), with the 2030 budget cut by 10%: from scratch, GLOP needed 338 simplex iterations; from the basis of the solve before the cut, 32, to the same objective. A basis can be stored with the result and used by any later process; a kept-alive solver cannot.


Some Fields Are Requests a Solver May Ignore


Two more fields describe how the solver should work rather than what it returns:


  • branching_priorities={variable: int}: branch on higher-priority variables first (lesson Branching on a fractional variable explains branching);
  • lazy_linear_constraints={row, ...}: rows the solver may hold back and add only when a solution breaks them. The docstring says this changes no plan's feasibility and that solvers without support ignore it.






All three solvers accept both fields and return the optimum. Whether any of them acted on them, the output cannot say, and this lesson does not claim it. Treat such fields like a hint: advice whose effect you measure, in the log or in the time to a good plan, on your own model.

Summary


  • A hint is a starting plan, passed in ModelSolveParameters. ModelSolveParameters(solution_hints=[SolutionHint(variable_values={...})]), given to solve as model_params; it may be complete or partial.
  • Only the log says whether a hint was used. HiGHS, SCIP and CP-SAT each log a complete feasible hint; HiGHS completes a partial one and rejects a wrong one; SCIP's log is silent on both. The optimum is the same with any hint.
  • Filters choose which values come back. skip_zero_values drops exact zeros only: HiGHS returned a $-2.2 \times 10^{-15}$.
  • An LP starts from a basis, not a hint. initial_basis cut GLOP's re-solve from 338 iterations to 32.
  • Some fields are requests a solver may ignore. Branching priorities and lazy rows were accepted by every MIP solver here; their effect is for you to measure.

Design Note: Keep Last Month's Plan as Values, Not as a Result


hints.py turns last month's result into a plain dict of rounded values before it builds any hint. A SolveResult belongs to the model and the run that made it; a dict of 0s and 1s keyed by project and year can be saved, compared with this month's plan, and turned into a hint for any model that has the same decisions. Keep plans as data, and hints, comparisons and reports all start from the same place.
