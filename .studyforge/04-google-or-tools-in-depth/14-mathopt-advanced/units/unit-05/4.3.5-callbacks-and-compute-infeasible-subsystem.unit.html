Two requests reach GridCap's modeling team in the same week. Operations wants to watch a long solve as it runs: every better plan the solver finds, and a way to stop as soon as one is good enough. And finance has sent a scenario the model calls INFEASIBLE, with no plan at all; they want to know which of their numbers to blame. Both needs reach inside the solve. The first uses callbacks, functions of yours that the solver calls while it works. The second uses an irreducible infeasible subsystem (IIS), a smallest set of rules that cannot all hold at once. This lesson shows MathOpt's API for both, which solvers in OR-Tools 9.15 support which parts, and how to get an IIS when the solver will not compute one. GridCap is a fictional utility.

Its decisions are start-time variables: $x_{i,t}= 1$ if project $i$ starts in year $t$ of its window $T_i$; a project starts at most once and spends its cost profile from its start year on. A Message Callback Hands You the Solver's Log, Line by Line

The simplest callback is the one lesson Solution hints and ModelSolveParameters used to read hints: msg_cb, a function that receives the solver's log as a list of lines, each time the solver writes some. HiGHS, SCIP and CP-SAT all call it (lesson Solution hints and ModelSolveParameters read all three logs this way). MathOpt ships three ready-made ones in message_callback.py: list_message_callback(sink) appends the lines to a list, printer_message_callback(prefix=...) prints them, and log_messages sends them to Python's logging. A message callback is plain Python, so it can also filter. The program below uses two of them. First HiGHS solves the small portfolio with its log kept in a list; nothing reaches the terminal during the solve, and the program afterwards prints four lines it picks from the list. The SCIP> lines are the printer's, written during SCIP's solve of the tiny portfolio (optimum 2,473). The printer comes from OR-Tools' remote_solve.py sample. A Solve Callback Runs at Events the Solver Supports

A solve callback is called by the solver at events during the search, receives data about the search so far, and can answer. Three pieces make one:

  • a CallbackRegistration: which events to call it at (events={...}), and whether it may add rows (add_lazy_constraints, add_cuts);
  • the callback, a function from CallbackData to CallbackResult, passed to solve as cb;
  • CallbackData, what the solver hands over: the event, a solution (a dict from variables to values, at events that have one), mip_stats (the best bound and incumbent so far, node counts), and the runtime.

The events for a MIP, as the Event docstring in callback.py describes them:

EventWhensolution holds
MIP_SOLUTIONthe solver found a new feasible integer solutionthat solution
MIPperiodically in the search loopnothing
MIP_NODEinside a node of the search treethe node's LP relaxation, if any

The same callback, three very different stories:

  • SCIP called it 191 times, and the values go down as well as up: 19,911, then 16,582. SCIP reports every feasible solution its heuristics find, not only better ones. A callback that wants "the best plan so far" must keep the best itself.
  • CP-SAT called it 16 times, with values only rising. It ran with threads=1: CP-SAT's default of several parallel workers finds solutions in an order that changes from run to run, and one worker makes the list repeatable.
  • HiGHS never called it, and raised no error either. The next check shows that is not about this event.

SCIP and CP-SAT refuse what they cannot do, before the solve starts, with a reason on __context__. Problem statement

An operations dashboard shows a long MIP solve's progress as a line: the value of the best plan found so far, after each solution the solver reports. Lesson Callbacks and compute_infeasible_subsystem showed that SCIP reports every feasible solution its heuristics find, worse ones included, so the callback has to keep the best itself.

Write make_tracker(objective, maximize). objective is a dict from variable to its objective coefficient; maximize says the sense. It returns a pair (callback, history):

  • history, a list, empty at first;
  • callback, a function for Event.MIP_SOLUTION. Given a mathopt.CallbackData, it computes the reported solution's objective value $\sum_v c_v \cdot \text{solution}[v]$, appends the best value seen so far (the largest when maximizing, the smallest when minimizing) to history, and returns an empty mathopt.CallbackResult().

The tests call your callback with hand-made CallbackData and also register it on a real SCIP solve. About twelve lines.

A Callback Can Stop the Solve


A callback's answer is a CallbackResult. Setting terminate=True asks the solver to stop as soon as it can. mip_stats gives the incumbent's value (primal_bound) and the best bound (dual_bound), so a callback can stop at a gap of its own choosing (lesson Best bound, incumbent, absolute and relative gap defines the gap):






SCIP stopped with a plan worth 24,059 and a proven bound of 24,510: the plan is within $(24{,}510 - 24{,}059) / 24{,}059 = 1.9\%$ of the best possible. The termination is FEASIBLE, not OPTIMAL, with limit INTERRUPTED, so a program reading the result knows why the search stopped (lesson Reading SolveResult: termination, primal and dual solutions, statistics). Two details from the CallbackResult docstring: a solver may not stop at once and may call the callback again, and once terminate has been returned, a later False does not take it back. For a fixed gap, the relative_gap_tolerance parameter does the same job without code (lesson Stopping on gap, time, nodes or solution count); a callback earns its place when the rule is your own, such as "stop when a plan funds every must-do region at 95%" or "stop when the user clicks Cancel".

A Lazy Constraint Is Added Only When a Solution Breaks It


A callback at MIP_SOLUTION can also reply with rows the solution breaks. These are lazy constraints: rules left out of the model, then added by the callback the first time a solution breaks one. OR-Tools' tsp.py sample uses them for a rule with too many rows to write: it checks each solution for subtours and adds only the cut rows that solution breaks. The pattern needs add_lazy_constraints=True in the registration and result.add_lazy_constraint(row) in the callback.


Here the rule is GridCap's crew limit: at most $K = 2$ transmission projects may start in one year. It has only five rows, so writing it up front is the sensible choice, and the program does that first as the reference answer. Then the same rule goes in lazily:






The dict maps each year to the transmission projects started in it. Without the rule, 2028 and 2030 start three each. rows sent counts the rows the callback returned.


  • SCIP added rows as solutions broke the rule and ended at 24,050, the same NPV as the model with every row written up front, with at most 2 starts in every year.
  • CP-SAT refuses lazy constraints, with a clear reason.
  • HiGHS accepted the registration, never called the callback, and returned a plan that breaks the rule: 3 starts in 2028 and in 2030, and an NPV of 24,260 that no allowed plan reaches. Nothing in the result says so.


That last line is the most dangerous output in this module: an OPTIMAL status on a plan that breaks a business rule. The defence: check the plan against the rules after every solve, in plain Python, as starts_per_year does here. (Lesson What a loose M does to the LP bound and to numerics, in section 6, gives the same advice for big-M rows, whose plans can break a rule through the solver's tolerance.) And never send a callback-dependent model to a solver you have not seen call your callback.


compute_infeasible_subsystem Names a Minimal Conflict, With Gurobi Only


Now finance's scenario: the board promises P032 for 2027, and the 2030 and 2031 budgets are capped at 5,000 each. The model has no plan:






"Infeasible" says no plan meets every rule, not which rules clash. An irreducible infeasible subsystem (IIS) answers that: a set of the model's constraints (rows, variable bounds, integrality) that cannot all hold together, and is irreducible: drop any one of them and the rest can hold. It is one explanation of the conflict, small enough to read. A model can have several, and an IIS is one of them, not necessarily the smallest.


MathOpt's call is mathopt.compute_infeasible_subsystem(model, solver_type). Its docstring in solve.py says the only supported solver is Gurobi, and the runner agrees:



What the call returns is still worth knowing well, because the next section builds the same result by hand. A ComputeInfeasibleSubsystemResult has three fields:


FieldMeaning
feasibilityINFEASIBLE if a conflict was proven; FEASIBLE or UNDETERMINED otherwise, and then the rest is to be ignored
infeasible_subsystema ModelSubset: which constraints are in the conflict
is_minimalTrue if the subset is irreducible; the docstring warns MathOpt's model changes can leave it not quite minimal


A ModelSubset lists the conflict in three parts: linear_constraints and variable_bounds, dicts from a row or a variable to a ModelSubsetBounds(lower=..., upper=...) saying which of its two bounds take part, and variable_integrality, the set of variables whose integrality takes part. The sides matter: a row $\ell \le a^\top x \le u$ is two rules, and an IIS often needs only one of them. In OR-Tools 9.15 the Python reader of this result also raises NotImplementedError if the subsystem contains indicator, SOS or quadratic constraints (compute_infeasible_subsystem_result.py), so a model with indicators cannot get its IIS read back in Python.


A Deletion Filter Finds One by Hand, in the Same Result Type


Without Gurobi, an IIS can be found with any solver that can say "infeasible", by the deletion filter (Chinneck's method). Go through the model's bounds one at a time. Drop the bound, then solve:


  • still infeasible: the bound was not needed for the conflict, so leave it dropped;
  • now feasible: the bound is part of the conflict, so put it back.


At the end, every bound left is needed, and the set is irreducible. Each test is a feasibility question, so the objective is set to 0 first; the cost is one solve per bound, which is fine for a few hundred rows and slow for a large model. find_iis.deletion_filter works on a copy (made as in lesson Prioritized objectives with add_auxiliary_objective), and returns the same ComputeInfeasibleSubsystemResult Gurobi's call would:




The candidates are both sides of every row, and both sides of the variables the caller names: here the promised start, whose lower bound of 1 was a scenario decision. The 0-and-1 bounds of the other binaries are what makes them binaries, and are left alone. report reads the result as a planner would:



Three rules clash: P017 is a must-do project that can start only in 2030 or 2031 and spends 5,310 in its start year, and both of those years are capped at 5,000. Notice what is not in the subsystem: the board's promise of P032. Finance's question was "which number do we blame?", and the answer is the caps, not the promise. Raising either cap to 5,310, or moving P017's window, makes the scenario feasible again. Only the lower side of must_P017 (an equality, $= 1$) is in the conflict: "at most once" is harmless; "at least once" is the problem.

Summary


  • A message callback hands you the solver's log, line by line. msg_cb=list_message_callback(log) works with HiGHS, SCIP and CP-SAT.
  • A solve callback runs at events the solver supports. SCIP calls MIP_SOLUTION (for every solution found, not only improvements) and MIP_NODE; CP-SAT calls MIP_SOLUTION and MIP; HiGHS accepts every event and never calls the callback.
  • A callback can stop the solve. CallbackResult(terminate=True) ended SCIP at 1.9% from the bound, FEASIBLE with limit INTERRUPTED.
  • A lazy constraint is added only when a solution breaks it. SCIP matched the up-front model; CP-SAT refuses; HiGHS silently ignored the rule and returned a plan that breaks it.
  • compute_infeasible_subsystem names a minimal conflict, with Gurobi only. HiGHS, SCIP and CP-SAT refuse it with UNIMPLEMENTED.
  • A deletion filter finds one by hand, in the same result type. The scenario's conflict was P017's must-do row against both caps; the promise of P032 was not part of it.

Design Note: Return the Library's Type, Even From Your Own Code


deletion_filter could return a list of names. It returns a ComputeInfeasibleSubsystemResult instead, the type Gurobi's call returns, built from MathOpt's own ModelSubset and ModelSubsetBounds. Everything that reads an IIS, such as report here or a planner message in lesson Turning an IIS into a planner message, is then written once against one type, and the day a supported solver is available, the hand-made filter can be swapped for compute_infeasible_subsystem without changing a reader.
