  16. Incremental solving

Finance is preparing for a budget meeting and wants GridCap's planners ready for any outcome: what does the plan lose if 2029 is cut by 5%, by 10%, by 20%? And what if the board rules out P032, a $5,680k transmission project? Each question changes one or two numbers of a model that is otherwise the same. This lesson answers them all with one model and one solver: edit the model, re-solve, put the edit back. It also shows which edits a solver applies in place and which make MathOpt quietly start the solver over, and the two mistakes that make scenario code give wrong answers. GridCap is a fictional utility.

Lesson Re-solving after the data changes introduced mathopt.IncrementalSolver on an LP and measured its warm start in simplex iterations. This lesson is about MIPs, where the solvers differ more, and about scenario code that stays correct.

The Model

The multi-period timing model of lesson Indicator constraints, with the data each scenario changes marked. Its decisions are start-time variables: $x_{i,t}= 1$ if project $i$ starts in year $t$ of its window $T_i$; a project starts at most once and spends its cost profile from its start year on. (Lesson Start-time variables x(i,t) and timing windows, in section 6, builds this model step by step.)

Sets. $P$ the projects; $Y$ the years; $T_i \subseteq Y$ the start years of project $i$; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C$ the child projects, with parent $p(c)$ and lag $L_c$.

Parameters. $\text{npv}_{i,t}$ ($k); $c_{i,k}$, project $i$'s spend in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k), with $B_{2029}$ cut by a share $s \in \{5\%, 10\%, 20\%\}$ in the cut scenarios.

Variables. $x_{i,t} \in \{0, 1\}$ for $i \in P$, $t \in T_i$, with $x_{\text{P032},t} \le 0$ for every $t$ in the "without P032" scenario (an upper bound of 0, so the project cannot start).

Objective.

Keep a Handle on What a Scenario Changes, and Put It Back

A scenario is an edit of the model, and an edit needs a handle on the thing it changes. That is why plan_model.build returns a PlanModel holding the start variables x[pid, t] and the budget rows budget[y] by key, not just the model. With handles, every kind of change is one call:

ChangeCallLesson
a row's limitrow.upper_bound = ..., row.lower_bound = ...Re-solving after the data changes
a coefficient in a row or in the objectiverow.set_coefficient(v, a), model.objective.set_linear_coefficient(v, c)Re-solving after the data changes
a variable's boundsv.lower_bound = ..., v.upper_bound = ...this one
a variable's typev.integer = False (or True)Solution hints and ModelSolveParameters
a new row or variablemodel.add_linear_constraint(...), model.add_variable(...)Re-solving after the data changes

an indicator constraint's rowdelete it and add it again; it cannot be editedIndicator constraints

An edit stays in the model for every solve that follows, so a scenario must put back what it changed before the next one runs. budget_cut.py does that with a small context manager, a function used in a with block that runs code on the way in and, thanks to finally, on the way out, even if the block raises an error:

edited(row, "upper_bound", 7_000) sets the bound for the block and restores the old one after it. It works for any attribute with a setter: a row's bounds, a variable's bounds, integer.

    A new limit for an indicator constraint

    • changing one bound of an indicator constraint by deleting it and adding it back whole

    Not startedPassed

Problem statement

A district heating model has indicator constraints such as "if boiler $b$ runs ($z_b = 1$), then $40 \le \text{heat}_b \le 120$". Scenario runs need to change a rule's upper limit, and MathOpt cannot edit an indicator constraint (lesson Indicator constraints): it has to be deleted and added again.

Write replace_upper(model, ic, new_upper), which replaces the indicator constraint ic by one identical in every part except its upper bound, now new_upper, and returns the new constraint object. "Every part" is: the indicator variable, the value that switches it on, the lower bound, the variables and coefficients of the row, and the name. The old object must not be used afterwards, which is why the function returns the new one. About eight lines.

Lesson Indicator constraints rebuilds an indicator constraint from its parts: ic.terms() gives the row's (variable, coefficient) pairs, mathopt.fast_sum(t.coefficient * t.variable for t in ic.terms()) turns them back into an expression for implied_expr, and implied_lb and implied_ub take the bounds. There is no offset to carry: MathOpt moves a constant in the row into its bounds when it stores the constraint, so the stored expression's constant is 0. Read every part before you delete ic.

One IncrementalSolver Answers Every Scenario


mathopt.IncrementalSolver(model, solver_type) keeps one solver alive across solves. Each call to its solve() sends the solver only what changed in the model since the last call. Used as a context manager, it frees the solver when the block ends (its docstring recommends it; close() does the same by hand). The budget scenarios, all on one model built once:








Each cut is taken from the original budget, 8,760, because edited put the bound back after the scenario before. The last line checks it. The NPV falls with every deeper cut: $190k at 5%, $207k at 10%, $615k at 20%. The lists say how the plan absorbs it: a few projects dropped, more moved to another start year. They are one optimal plan per scenario, not the only one: where two plans tie on NPV, another solver, or another version, may return the other. That is also why the 20% plan can keep P016 while the 10% plan drops it.


Ruling out a project is a scenario too. Its start variables get an upper bound of 0 for the length of the block; contextlib.ExitStack enters several edited blocks at once and leaves them all:






P032 is worth $112k of NPV to the plan, and once its bounds are back the model solves to the base NPV again: the edits left no trace.

Problem statement


A school district picks which building repairs to fund this summer, with a binary $x_j$ per repair, value $v_j$, cost $c_j$ and one budget row:



The board wants the best value under several cuts of $B$: for each share $s$ in cuts, the optimum with the budget row's limit at $(1 - s) B$, where $B$ is the limit the row has when the function is called.


Write cut_table(model, budget_row, cuts), which returns a list with the optimal objective value for each share, in order. Use one mathopt.IncrementalSolver on HiGHS for all of them, and edit the row's upper_bound rather than building anything new. When the function returns, the model must be exactly as it was, limit included. About ten lines.

Whether the Solver Updates in Place Depends on the Solver and the Edit


What does IncrementalSolver.solve() do with the changes? Its source in solve.py answers: it asks the solver it holds to apply them. If the solver says it cannot, MathOpt throws that solver away and builds a new one from the whole model, without telling you. Either way the result is right; what differs is whether the solver kept its copy of the model, and with it any state it could reuse.


update_or_rebuild.py makes six edits in a row, solving after each, and checks whether the object the IncrementalSolver holds is still the same one. It reads a private attribute, _proto_solver, so treat it as a diagnostic for learning, not as code to ship:




  • SCIP applied five of the six edits in place, and rebuilt only when a variable stopped being integer.
  • HiGHS and CP-SAT rebuilt after every edit. Through MathOpt in OR-Tools 9.15, an IncrementalSolver on either is a fresh solve each time, the same finding lesson Re-solving after the data changes made for HiGHS on an LP.
  • All three end at the same NPV, 27,514 (high, because the edits included deleting the 2031 budget row). A rebuild costs time, never correctness.


"In place" means the solver kept its model; it does not by itself mean the MIP search starts from where the last one ended. This program measures no speed, and for a MIP the gain depends on the solver and the edit. What the table does settle is the choice of tool: for many scenarios of one model, an IncrementalSolver is never worse than a fresh mathopt.solve, and on SCIP it avoids rebuilding the solver's model; on HiGHS and CP-SAT it gives nothing, and editing the model in place is still worth it, because it saves rebuilding your model.


Undo Every Edit, and Never Delete What a Scenario Only Switches Off


Two mistakes make scenario code quietly wrong. The first is a relative edit that is never undone:






The second scenario was meant to be "a 5% cut" and ran as a 9.75% one, and nothing failed. Either compute each scenario from the original data, as the loop with edited does with (1 - share) * small.budget[2029], or restore after each scenario, and best both.


The second mistake is deleting what a scenario only needs to switch off. Deletion cannot be put back with an assignment, and every reference to a deleted variable stops working:






The Variable object still exists in Python, but the model no longer has the element it points to (id 79, the last of the 80 start variables). Deleting a variable also removes it from every row and the objective, so adding it back would mean rebuilding all of those. To take a project out of one scenario, bound its variables to 0, as the "without P032" scenario did; delete only what is gone for good. The upper bound is the one that matters: a lower bound of 1 would do the opposite and force the project in. Setting its NPV to 0 in the objective is not the same thing: the project could still start and spend budget for no value, which is a different scenario from "without". Indicator constraints are the one exception, because they cannot be edited at all (lesson Indicator constraints): to change one, delete it and add a new one, and replace your handle.

Summary


  • Keep a handle on what a scenario changes, and put it back. A builder that returns rows and variables by key makes each scenario one edit; a context manager restores it even on errors.
  • One IncrementalSolver answers every scenario. Three 2029 cuts and a ruled-out project, on one model built once; the cuts cost $190k, $207k and $615k of NPV.
  • Whether the solver updates in place depends on the solver and the edit. In OR-Tools 9.15, SCIP applied bound, coefficient, row and variable edits in place; HiGHS and CP-SAT rebuilt after every edit, silently and correctly.
  • Undo every edit, and never delete what a scenario only switches off. Relative edits pile up; a deleted variable's references raise ValueError.

Design Note: Scenarios Are Data, Edits Are Code


budget_cut.py lists its scenarios as numbers (0.05, 0.10, 0.20) and has one piece of code that turns a number into an edit and back. Adding a scenario is adding a number. The same split scales to the scenario tables planners ask for: a list of scenarios, each a set of (handle, attribute, value) edits, and one loop that applies, solves, records and restores. Section 12 builds that loop into a service.
