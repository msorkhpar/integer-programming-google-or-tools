A GridCap planner reports that "the solver got stuck" on the medium portfolio: it ran out its limit and the gap stayed above 4%. Stuck where? Finding plans, or proving that no better plan exists? The status and the objective cannot say; the log can. CP-SAT can write a running account of everything it does: the model it received, what presolve did to it, every new plan and every better bound as they happen, and a final summary. This lesson turns the log on, captures it, and reads it section by section, on GridCap small (where the search finishes) and GridCap medium (where it does not).

GridCap is a fictional utility's portfolio; none of its numbers are real. The model is lesson Workers, search strategies and LNS's, unchanged (cpsat_plan.build). Every run here uses one worker, so the log's content repeats from run to run (lesson Deterministic time, seeds and reproducible runs); the times in it do not, so the programs replace every measured time with <time>.

log_search_progress Writes the Log, and log_callback Catches It

Logging is off by default. solver.parameters.log_search_progress = True turns it on; the parameters proto calls it the main logging switch. By default the log goes to standard output. In a service or a test you want it as data instead, and two more settings do that: log_to_stdout = False keeps it off the screen, and solver.log_callback is a function CP-SAT calls with each piece of the log:

A list's append is a perfectly good callback: after the solve, log holds the whole log. The program then masks the times with two regular expressions, one for numbers followed by s, ms, us or ns and one for walltime:, usertime: and time: fields:

The log is long (about 300 lines for this 80-variable model), so the program prints it a section at a time. The rest of the lesson reads those sections in order.

The Header and Model Statistics Say What the Solver Was Given

The first line is the OR-Tools version, the first thing to check when two machines disagree (lesson Deterministic time, seeds and reproducible runs). The second lists every parameter that is not at its default. If a setting you thought you made is missing from this line, it never reached the solver.

This is the model exactly as your code built it, before CP-SAT changed anything:

  • The fingerprint is a hash of the model. Two runs with the same fingerprint solved the same model; a changed fingerprint means the model changed, even if nobody meant to change it.
  • 80 variables, all Booleans in [0,1], all in the objective: the 80 start variables of GridCap small (one per project and allowed start year), each worth its NPV. Lesson Start-time variables x(i,t) and timing windows, later in the course, builds such start-year variables in depth. A count you did not expect is a modeling bug found before any solving.
  • The constraint counts are grouped by kind. kLinear1, kLinear2 and kLinear3 are linear constraints with one, two and three terms; kLinearN are the longer ones (21 of them, 240 terms in all). They add up to 68 rows: 40 once rows, 4 must-do, 2 alternative groups, 2 precedence, 5 budgets and 15 crew rows (lesson Workers, search strategies and LNS's model). The long ones include the budget and crew rows, which sum over many projects; a one-term row is, for example, the once row of a project with a single start year.

Then comes presolve, many lines long, each line one presolve step with its time and its effect. At its end is the presolve summary, one line per rule that fired and how often. Three of them are about variables:

An affine relation is a variable that presolve found to be a fixed linear function of another ($a = 1 - b$, for example), so one of the two can go. The 13 unused variables are ones presolve could take out of the search entirely; their values are filled back in after the solve. The model after presolve shows the result:

80 variables became 66, and the 68 linear rows became 51 constraints of new kinds. Presolve recognized that many small linear rows over Booleans are really logic: an at-most-one (no more than one of these literals is true, which is what a once row or an alternative group says), a bool_and with an enforcement literal (if this is true, those are all true), a bool_or (at least one is true), an exactly-one. These are clauses that CP-SAT's Boolean (SAT) engine handles directly. What is left as kLinearN are 14 rows that remain true sums.

Comparing the two blocks is the quickest test of a model's shape. A presolve that removes most of a model means much of it was decided by the data; a presolve that removes nothing on a model full of logic means the logic was written in a form presolve could not read.

Problem statement

A warehouse team keeps its CP-SAT logs and wants a dashboard of how much presolve shrinks each model. A CP-SAT log describes the model twice: in the block that starts with Initial optimization model (the model as written) and in the block that starts with Presolved optimization model (the model after presolve). In each, the line starting #Variables: gives the number of variables.

Write variables_before_and_after(log) in log_sizes.py. log is the whole log as one string. Return a pair of integers: the variable count before presolve and after it.

Write the helper variables_in(log, header) first: find the line that starts with header, then the first #Variables: line after it. CP-SAT writes large counts with an apostrophe between thousands, as in #Variables: 1'331. About eight lines.

Each Progress Line Is an Event: a New Plan or a Better Bound


After presolve, the search. Each line starting with # reports one event, with the same layout: the event, the time, best: the value of the best plan so far, next:[low,high] the range of objective values still in play, and the worker that caused it.



The four kinds of line:


  • #1, #2, ... a new, better plan. best: jumps to its value, and the low end of next: moves to one more than it: for a maximization with an integer objective, the next plan worth finding must be worth at least best + 1.
  • #Bound a better bound. The high end of next: falls: no plan is worth more than this. The first one, from initial_domain, is the bound from the variables' domains alone ($64,284k); the next, after initial_propagation, is already less than half of it.
  • #Done the search finished: it proved that no plan in the remaining range exists, so the best plan is optimal. The last #Bound line still says 25,418; the proof that closed the range came as the search ended, which is why the summary below reports a bound of 22,741.
  • #Model (not in this run) reports that the model shrank during the search, for example as variables became fixed.


The last word on each line is the subsolver that caused the event. With one worker it is always main; with several, it is one of the names in lesson Workers, search strategies and LNS's lists, which tells you which part of the portfolio found each plan and each bound (the CP-SAT Primer reads this column the same way).


Now the medium run that "got stuck", one worker and 3 units of deterministic time. Its log is hundreds of lines, so the program reads its progress lines as data and summarizes them:






Three readings answer the planner:


  1. No #Done line: the last event is a plan, so the limit stopped the search, not a proof.
  2. The plan side moved: from $208,873k to $215,024k across 17 plans, $6,151k in all.
  3. The bound side barely moved: after the first plan it fell only from $225,336k to $224,292k, $1,044k.


So the search was not stuck finding plans; it was stuck proving. Where the bound starts says nothing about presolve: presolve's work is read in its own summary lines before the search, not in the first #Bound. The CP-SAT Primer reads the log the same way: improving plans with a flat bound point to a weak bound, while a flat plan with a moving bound means the solver is busy with the proof. Lesson Workers, search strategies and LNS gave the remedy for this case: more workers bring subsolvers such as max_lp and core that raise the bound, and the 8-worker run closed the gap below 1%.

The Response Summary Is the Run's Final Word


Between the search and the summary, the log prints tables of statistics per subsolver: timing, search counts, clauses, LP sizes and cuts. The CP-SAT Primer notes that they are mainly for CP-SAT's developers. The last block is for you:



FieldMeaning
statusOPTIMAL, FEASIBLE, INFEASIBLE, MODEL_INVALID or UNKNOWN
objective, best_boundthe best plan's value and the proven bound; equal here, so the gap is 0
booleans, integersthe variables the search worked with (after presolve: 66 Booleans)
conflicts, brancheshow many times the search hit a contradiction, and how many decisions it made
propagations, integer_propagationshow many deductions propagation made
restarts, lp_iterationssearch restarts, and simplex iterations of the LP relaxation
walltime, usertimeseconds on the clock (masked here, since they never repeat)
deterministic_timethe work done, in the unit of lesson Deterministic time, seeds and reproducible runs
gap_integralthe gap integrated over time: smaller means the gap closed sooner
solution_fingerprinta hash of the plan: equal fingerprints mean the same plan; two different plans can tie on the objective and still have different fingerprints


Why 68 integers next to 66 Booleans, in a model whose variables are all Booleans? The proto (cp_model.proto, CpSolverResponse) lists num_integers and num_booleans without saying how they are counted, so variable_counts.py measures it on five Booleans, with presolve off so that the counts are the model's own:




The two counts are not disjoint. A Boolean that only appears in clauses is counted once, as a Boolean. A Boolean that appears in a weighted linear row is also given an integer form for that row, so it is counted in both; and a weighted objective adds one more integer variable, its value. So integers is not a count of the integer variables you created: in the GridCap run the Booleans sit in budget and crew rows, so they are counted again as integers, and the solver's extra integer variables (of the kind the objective adds above) bring the count above 66.


Every field is also on the solver object, so code never has to parse this text:



solver.status_name(status), solver.objective_value, solver.best_objective_bound, solver.num_branches, solver.num_conflicts, solver.wall_time and solver.deterministic_time give the numbers, and solver.response_stats() returns the summary block as a string, which is the thing to write to a service's own log after every solve. When the full log is too much to keep, keep this block and the version line: together they say what ran and what came out.

Design Note: Logs Are for People, Fields Are for Code


The log is the best tool for understanding one run and a poor interface for programs: its layout is not part of any API, and a new OR-Tools version may change it. Code that decides things (stop, alert, retry) should read the fields on the solver object, and the log should be stored for the person who will investigate. The practices of this lesson parse log text because archived logs are often all that is left of an old run; for new runs, prefer solver.objective_value and its siblings.
