  17. Hints, assumptions and sufficient assumptions

Every year GridCap re-plans its portfolio, and two questions come back each time. First: last year's plan was good, so can the solver start from it instead of from nothing? Second: when the regulator's scenario cuts the budget and the model answers INFEASIBLE (no plan keeps every rule), which of the dozens of rules are to blame? CP-SAT answers the first with solution hints and the second with assumptions. This lesson shows both on GridCap, and what each one does and does not promise.

GridCap is a fictional utility's portfolio; none of its numbers are real. The model is the one of lesson Workers, search strategies and LNS, cpsat_plan.build.

The Model

The plan is lesson Workers, search strategies and LNS's model with one change, marked below: every rule group except "once" gets its own Boolean flag, and the rule holds only when its flag is 1. This is what cpsat_plan.build(portfolio, flags=True) builds; the rule names are the labels.

Sets. $P$ the projects; $Y$ the years; $T_i$ the start years of project $i$; $M$ the must-do projects; $\mathcal{G}$ the alternative groups; $C$ the child projects, with parent $p(c)$ and lag $L_c$; $G$ the programs; $R$ the rule names: one per must-do project, group, child and start year, budget year, and program and year with crew work.

Parameters. $\text{npv}_{i,t}$, $c_{i,k}$, $B_y$, $m_i$, $K_{g,y}$, $d_i$ as in lesson Workers, search strategies and LNS; $s$, the scenario's budget factor (0.97 for the budget cut in the hint sections, 0.6 in the infeasible scenario).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$, $t \in T_i$: project $i$ starts in year $t$. $f_r \in \{0, 1\}$ for every $r \in R$: rule $r$ is on. $\leftarrow$ new

Objective. $\max \sum_{i \in P} \sum_{t \in T_i} \text{npv}_{i,t}\, x_{i,t}$

Constraints. Each row except once$_i$ holds only if its flag is 1 ($f \Rightarrow \text{row}$, written .only_enforce_if(flag)).

The assumptions are $f_r = 1$ for every $r \in R$: the solver must treat every rule as on. Without assumptions, the flags are ordinary variables and the solver would switch rules off to earn more NPV. The table maps labels to rule names, as in lesson Workers, search strategies and LNS:

LabelRule name
must$_i$, alt$_g$must_P017, alt_G001
after$_{c,t}$after_P023_2029
budget$_y$, crews$_{g,y}$budget_2030, crews_vegetation_2031

The flagged model is used from the section on assumptions on. The hint sections use the plain model of lesson Workers, search strategies and LNS.

A Hint Is a Suggested Plan, Never a Constraint

A solution hint is a value you suggest for a variable: model.add_hint(var, value). The OR-Tools sample solution_hinting_sample_sat.py hints two of three variables; the CP-SAT docs say a hint may cover only some variables, may even be infeasible, and that the solver tries to follow it for a while before returning to its usual search. It is guidance, not a rule: no plan is ever refused for disagreeing with a hint.

The natural hint is last cycle's plan. The program takes the plan one worker finds on GridCap medium with 3 units of work, then re-plans with 1 unit, with and without hinting it. Each start variable gets a hint, 1 if the old plan starts the project in that year and 0 otherwise:

A solution callback (lesson Objectives, integer scaling and solution callbacks) records the first plan found and counts the improving plans:

With the hint, the first plan the solver reports is the hint itself, $215,024k, and the search improves on it to $215,109k. Without it, the solver starts at $208,873k and ends at $214,532k with the same work. When the rules have not changed, a hint is a head start.

Now cut every year's budget by 3%, the kind of change a rate case brings:

The old plan overspends the new budgets, so it is no longer a plan at all. The hinted run still works (a hint is never a constraint), but it is no better: its first plan is worse than the unhinted one, and it ends $201k lower. A hint helps when it is a plan of the model you are solving. Before trusting one, check it.

Two related settings from the parameters proto: use_optimization_hints (on by default) makes the search follow the hint, and repair_hint asks the solver to try to repair an infeasible hint into a feasible one. model.clear_hints() removes every hint, for example before trying another one.

Fixing Every Variable to Its Hint Tests Whether the Hint Is Feasible

solver.parameters.fix_variables_to_their_hinted_value = True turns the hint into a constraint: every hinted variable is fixed to its hinted value. If every variable is hinted, nothing is left to decide, and the solve answers one question: does this exact plan keep every rule? The CP-SAT Primer recommends this as the dependable way to check a hint.

OPTIMAL here means "the one plan left is feasible, so it is also the best of the plans left", and INFEASIBLE means the old plan breaks a rule of the new model. Hint every variable, the zeros included. The setting fixes hinted variables only; a variable with no hint stays free for the solver to set. A check that hints only the ones would therefore accept a plan that leaves out a must-do project, since the solver is free to switch that project on.

An Assumption Is a Literal the Solver Must Take as True


A literal is a Boolean variable or its negation. An assumption is a literal the solver must treat as true for this solve: model.add_assumptions([a, b, c]). It works like adding $a = 1$, with one difference that is the point of this lesson: when the model is infeasible, the solver can report which assumptions it needed to prove that. So you guard each rule with its own flag, written model.add(...).only_enforce_if(flag) (lesson Native logic: AddBoolOr, AddImplication, OnlyEnforceIf), and assume every flag.


The OR-Tools sample assumptions_sample_sat.py shows the mechanics with three rules that cannot hold together, $x > y$, $y > z$ and $z > x$, each guarded by a flag:






solver.sufficient_assumptions_for_infeasibility() returns variable indices, not names or variable objects: 3, 4 and 5 are the indices of a, b and c (each variable's .index). A Deletion Filter Shrinks the Named Flags to a Minimal Set


A set of rules is a minimal clash when the rules in it cannot all hold, but dropping any one of them leaves a set that can. (This is the CP-SAT counterpart of the irreducible infeasible subsystem, or IIS, that MathOpt's compute_infeasible_subsystem finds in lesson Callbacks and compute_infeasible_subsystem.)


The deletion filter finds one with one solve per rule. Start from the sufficient set. For each rule in turn, solve with that rule switched off and the rest still assumed. If the model is still infeasible, the rule was not needed: leave it out for good. If it becomes feasible, the rule is part of the clash: keep it.




Switching a rule off is just not assuming its flag: the flag is then a free variable, and the solver sets it to 0 whenever the rule is in the way.



Twenty-eight rules shrink to three, and the three tell a story a planner understands at once: P017 is a must-do project costing $5,310k in a single year, it may start only in 2030 or 2031, and at 60% neither year's budget can pay for it. Every check the program prints confirms the set is minimal: dropping any one of the three rules makes the scenario feasible. The three answers are also the three ways out: make P017 optional, or raise the 2030 or the 2031 budget.


Two cautions. The filter costs one solve per rule in the sufficient set, so on a model with thousands of flags, group rules (one flag per budget year rather than per row, as here) before you start. And a model can hold several separate clashes; the filter returns one of them. Fix it, run again, and the next one appears.

Summary


  • A hint is a suggested plan, never a constraint. Last cycle's plan is a head start when it is still feasible, and no help when it is not.
  • Fixing every variable to its hint tests whether the hint is feasible. Hint every variable, zeros included, and set fix_variables_to_their_hinted_value.
  • An assumption is a literal the solver must take as true. Guard each rule with a flag via only_enforce_if, assume every flag, and use one worker.
  • sufficient_assumptions_for_infeasibility names flags that clash, not always the fewest. It returns variable indices; map them to rule names. On GridCap it named all 28.
  • A deletion filter shrinks the named flags to a minimal set. One solve per rule; what is left is a clash with no rule to spare.

Design Note: One Flag per Rule Group


cpsat_plan.build gives one flag to each must-do project, group, budget year and program-year, not one per variable or per coefficient. That choice sets the vocabulary of the answer: the deletion filter can only name things that have flags. A flag per row is the finest answer a planner can act on (a row is a rule they wrote); a flag per rule family ("all budgets", "all crews") is cheaper to filter and is a good first pass on a large model, followed by a finer pass inside the family it names.
