  17. Element, table and forbidden assignments

Lessons Interval variables and NoOverlap and Cumulative resources: crews and outage windows scheduled jobs whose length was known. GridCap's vegetation planners have more choices than that. A Coast circuit can be trimmed by hand (slow and cheap), with a mechanical mower or saw (faster, dearer), or with an aerial saw slung under a helicopter (fastest, dearest), and the choice sets both the job's weeks and its cost. Some combinations do not exist at all: GridCap's own crews have no aerial saw; the contractor has no climbers. And between jobs the crews travel: three crews move between four regions and the yard week by week, and a move from the Coast to the Ridge in one week is too far to drive.

These are rules of the form "this quantity is read from a list by that choice", "only these combinations exist" and "never this pair". CP-SAT has a constraint for each: element, table (add_allowed_assignments) and its opposite (add_forbidden_assignments). The lesson starts where the OR-Tools scheduling guide starts its employee example, with the nurse roster, and ends with a roster of GridCap's crews. (GridCap is fictional; the method data, prices and travel costs below are invented for the lesson.)

A Roster Is One Boolean per Person, Day and Shift

The OR-Tools guide Employee Scheduling rosters 4 nurses over 3 days of 3 shifts. Its model has no intervals at all: time comes in a few fixed slots, so it uses one Boolean per nurse, day and shift, $x_{n,d,s} = 1$ if nurse $n$ works shift $s$ on day $d$, and three families of rows:

nurses.py builds it as the guide does, with add_exactly_one and add_at_most_one (lesson Native logic: AddBoolOr, AddImplication, OnlyEnforceIf) for the first two families, and counts every schedule with a solution callback (lesson Objectives, integer scaling and solution callbacks) and enumerate_all_solutions:

5,184 schedules, the number the guide reports. (A model with no objective that has been enumerated completely ends with status OPTIMAL.) The last section of this lesson moves this roster onto GridCap's crews. First, the constraints it will need.

Element Reads a List at a Variable Index

Back to one crew and the four Coast jobs P011, P012, P014 and P015. Each job $j$ has three methods, numbered 0 (manual), 1 (mechanical) and 2 (aerial), and for each a length in weeks $W_{j,m}$ and a cost $C_{j,m}$ in $k:

Let the method be an integer variable $m_j \in \{0, 1, 2\}$. Then the job's length is $W_{j,m_j}$: a list read at a position the solver chooses. That is the element constraint:

and in CP-SAT, add_element(index, expressions, target). Here the array holds constants, the lengths or the costs; since OR-Tools 9.12 it may also hold variables or linear expressions, and the index must land on a position of the array. Each job gets a method, a length and a cost, tied by two elements, and its interval takes the length as a variable size:

new_interval_var with a variable size still adds end = start + size (lesson Interval variables and NoOverlap), so when the solver picks a faster method the interval shrinks. The crew does the jobs one at a time (add_no_overlap(tasks)), every end is at most the deadline, and the objective is the total cost. methods_element.py solves it for three deadlines:

With 14 weeks, hand work fits (4 + 6 + 2 + 2 = 14) and is cheapest. With 8, the crew must save 6 weeks, and the cheapest way is mechanical on three jobs (2 + 3 + 2 + 1 = 8) for $40k more. With 5, the two long jobs go aerial (1 + 2 + 1 + 1 = 5). The deadline buys speed, and element is what lets the price of speed be read from the data.

One Boolean per Option Does the Same, and an Interval's Size Must Be Affine

The CP-SAT Primer advises against reaching for element when Booleans will do: one Boolean per job and method, $u_{j,m}$, exactly one of them true, and the length and cost as weighted sums,

Both forms say the same thing, and a Boolean form is often clearer: each $u_{j,m}$ can appear directly in other rules ("at most two aerial jobs a season" is a sum of $u_{j,2}$).

There is one catch in CP-SAT. An interval's start, size and end must each be affine: one variable times a constant, plus a constant, or a constant. A weighted sum of three Booleans is not. methods_booleans.py tries it first:

The fix is to give the sum a name, an integer variable equal to it, and to use that variable as the size:

The cost needs no such variable: the objective accepts any linear expression. The answers are the element model's:

Which to use? Element when the index is itself meaningful (a method number, a position in a sequence, a region, as in the last section), Booleans when the options appear in other rules. Either way, check the result against the other form once, as this section did.

The programs here print the cost with solver.objective_value. That value is a Python float, even when every coefficient is a whole number, and a function that returns a cost must turn it into an int with care. objective_float.py prices a rental two ways, in $k per day (coefficients 0.1 and 0.7) and in $100 per day (coefficients 1 and 7):

The true cost is $20k, but with float coefficients the value is computed in floating point and lands just below 20; int() cuts off the fraction and returns 19. round() returns the nearest whole number, 20, so use round(solver.objective_value) whenever the cost is a whole number. With whole-number coefficients you can also read the objective expression itself: solver.value(cost) returns an int.

Problem statement

A one-driver courier service plans tomorrow's delivery runs. Each run can be made with any vehicle in its list, and each vehicle gives the run a length in hours and a cost in dollars: a cargo bike is slow and cheap, a van is quicker and dearer. The driver makes one run at a time, and every run must end by the deadline hour. Hours are numbered from 0.

Write cheapest_runs(runs, deadline) in courier.py. runs maps a run to (hours, costs), two lists of the same length, one entry per vehicle. Return (total_cost, plan), where plan maps each run to (vehicle, start): the vehicle's index in the run's lists and the run's start hour, chosen so that the total cost is as small as possible. Every instance in the tests has a plan. total_cost is an int: solver.objective_value is a float, so convert it with round(...), as the reference does, never with int(...), which turns a value such as 49.99999999999999 into 49.

The model, with $R$ the runs, $h_{r,v}$ and $c_{r,v}$ the hours and cost of run $r$ by vehicle $v$, $V_r$ the vehicle indices of run $r$, and $D$ the deadline:

The cost $c_{r, v_r}$ is a second element (or a Boolean per vehicle with weighted sums). Remember that an interval's size must be a single variable, not a sum. The tests check the plan you return and its cost, so any optimal plan passes. About twenty lines.

A Table Lists Every Combination That Is Allowed


Now add a second choice: who does the job, GridCap's own crew or a contractor. The two do not offer the same things:


MethodOwn crewContractor
manualyesno (no climbers)
mechanicalyesyes, $15k dearer
aerialno (no aerial saw)yes


A rule over several variables at once, "the tuple (method, who, weeks, cost) is one of these rows", is a table constraint: add_allowed_assignments(expressions, tuples). The assignment of the listed variables must equal one of the tuples, exactly. For each job the table has four rows, one per offer:



The table does two jobs at once. It forbids the combinations nobody offers (manual by the contractor, aerial by the own crew), and it defines the length and the cost of the ones that exist, including a cost that depends on both choices. Element reads one list by one index; a table relates any number of variables.


Keep the table whole. Split it into two smaller tables, allowed (method, who) pairs and allowed (method, cost) pairs, and each pair is still right on its own, but the link between who and cost is gone: mechanical appears with the own crew and with the contractor, and with $75k and with $90k for P011, so the split tables let the contractor do P011 mechanically at the own crew's $75k. Only a row that names all the variables together says which price goes with which provider.


who is a Boolean, hired[j], 1 when the contractor does the job, and a Boolean is an integer variable with values 0 and 1, so it can sit in the table. It is also a presence literal: each job has an optional interval on the own crew, present when ~hired[j] (the negation, "not hired"), and one on the contractor, present when hired[j], as crews were chosen in lesson Interval variables and NoOverlap:




With two crews working in parallel, week 8 costs $245k against $255k for one crew: the contractor takes P012 at the mechanical price plus $15k, and everything else is done by hand. Every chosen row is one the table allows: no manual job goes to the contractor and no aerial job to the own crew. At week 2 there is no plan. P012 takes at least 2 weeks (aerial, so the contractor), which fills the contractor's two weeks; the own crew would then need the three other jobs in 2 weeks, and the fastest it can do them is mechanical, 2 + 1 + 1 = 4 weeks.


A table is the right tool when the allowed combinations are a short, explicit list. The CP-SAT Primer notes it pays off when the table's variables also appear in other constraints, as here, where weeks feed the intervals and cost the objective.

Forbidden Pairs and a Flattened Element Price a Crew's Moves


Now the nurse roster, moved onto GridCap. Three crews (A, B, C) work an eight-week stretch. Each week a crew is in exactly one place: one of the four regions or the yard. The vegetation plan says how many crews each region needs each week, and every crew must spend at least one week in the yard for equipment service. Moving a crew costs money, from a 5 × 5 table of travel costs, and a move between the Coast and the Ridge in a single week is not allowed (two days' drive each way).


The guide's Booleans carry over directly: $y_{c,w,p} = 1$ if crew $c$ is in place $p$ in week $w$, with exactly one place per crew and week, and one row per region and week for the demand. The travel rule is about pairs of consecutive weeks, and for that an integer is handier than five Booleans: the crew's place $a_{c,w} \in \{0, \dots, 4\}$, which a linear row ties to the Booleans,



(exactly one $y_{c,w,p}$ is 1, so the sum is that place's number). The forbidden moves are a forbidden-assignment constraint on the pair: add_forbidden_assignments([a[c,w], a[c,w+1]], [(COAST, RIDGE), (RIDGE, COAST)]) says the pair may take any value except those two rows. The shift-scheduling example in the OR-Tools repository (shift_scheduling_sat.py) forbids a night shift followed by a morning shift with a clause on the two Booleans; the table form says the same for integer places.


The travel cost of a move is $T[a_{c,w}][a_{c,w+1}]$, a two-dimensional table read at two variable indices. Element takes one index, so flatten the table row by row into a list of 25 numbers, where entry $5p + q$ is $T[p][q]$ (row $p$, the place the crew leaves; column $q$, the place it goes to), and index it with the linear expression $5\,a_{c,w} + a_{c,w+1}$. With $n$ places the multiplier is $n$, the length of a row, so that each pair of places gets its own entry; a plain sum $a_{c,w} + a_{c,w+1}$ would not, since Coast to Ridge and Valley to Valley both add up to 2. The order matters: $5\,a_{c,w+1} + a_{c,w}$ reads $T[q][p]$, the move the other way, which is the same number only while the table is symmetric, as this one is; a climb up to the Ridge that costs more than the drive down would break it. Summary


  • A roster is one Boolean per person, day and shift. Exactly-one and at-most-one rows, and a count range for fairness; the guide's nurse roster has 5,184 schedules.
  • Element reads a list at a variable index. add_element(index, expressions, target); the target may then be an interval's size, a cost or anything else.
  • One Boolean per option does the same, and an interval's size must be affine. Name a weighted sum with an integer variable before using it as a size.
  • A table lists every combination that is allowed. add_allowed_assignments(vars, tuples) forbids the missing combinations and defines values that depend on several choices at once.
  • Forbidden pairs and a flattened element price a crew's moves. add_forbidden_assignments removes listed tuples; a 2-D cost table is a flat list read at $n\,p + q$.

Design Note: Enumerating Is a Test, Not a Report


nurses.py counts 5,184 schedules, a number you can also work out by hand (the guide does). A count that matches a hand count is a strong test that the model says what you meant: one missing row and the count jumps, one extra row and it drops. Keep enumeration for small instances where you know the answer; on a real roster the count is astronomically large and the search for all of them never ends.
