  15. Versions and backends

A GridCap engineer pastes a snippet from an old blog post into the planning service: pywraplp.Solver.CreateSolver("GUROBI"). Another copies mathopt.SolverType.GLPK from the SolverType list. Both look like valid OR-Tools code, both pass a code review, and neither runs in the service's container. Which solvers you can actually call depends on three things the code does not show: the OR-Tools version you installed, which solvers that build was compiled with, and which outside libraries and licenses the machine has.

This lesson measures all three in the course runner, the offline container every program of this course runs in, which pins OR-Tools 9.15.6755. It asks each API which solvers it accepts, tries Gurobi both ways, and then makes each API refuse something, to show where each one puts its "no". That last part matters more than it looks: MathOpt, CP-SAT, the linear solver wrapper, the graph solvers and routing each report a refusal in a different place, and code that looks in the wrong place carries on with a wrong answer. GridCap is a fictional portfolio; this lesson needs none of its data.

A backend here is the solver an API hands your model to: HiGHS, SCIP and GLOP are backends of MathOpt and of the linear solver wrapper. A refusal is the solver declining a request (a model type it cannot solve, a solver that is not there), as opposed to an answer such as "infeasible".

The Model

The refusal tests use a one-continuous model, small enough to read at a glance. Lesson Switching solvers: HiGHS, SCIP, CP-SAT, GLOP, Gurobi, later in this section, solves it with every MathOpt solver.

Variables. $a \in [0, 10]$, continuous; $b \in \{0, 1, \dots, 10\}$, integer.

Its optimum, measured in lesson Switching solvers: HiGHS, SCIP, CP-SAT, GLOP, Gurobi later in this section, is $a = 8.6216$, $b = 4$, value 20.3078. Any answer with a fractional $b$ is therefore not an answer to this model: it tells you the solver ignored the integrality. The backend survey solves an empty model, with no variables and no rows, which every solver that is present can solve.

One Version Number Covers the Whole Package, and Each Solver Inside Has Its Own

OR-Tools is versioned as one package, and every solver in it ships at whatever version that release bundled. The program prints the package's version, what pip installs with it, and the version each solver reports:

Read it from the top:

  • The version is 9.15.6755, from both ortools.__version__ and the C++ side (init.OrToolsVersion). Pin the whole string (ortools==9.15.6755), as the course runner does.
  • pip brings six libraries with it, and one has a narrow range: protobuf<6.34,>=6.33.1. Any other package that needs a protobuf outside that range cannot share an environment with this OR-Tools. Check that line before you add OR-Tools to a service with other dependencies.
  • Google's own solvers carry the OR-Tools version (GLOP, CP-SAT); the open-source solvers it bundles carry their own: SCIP 10.0.0 (with SoPlex 8.0.0 as its LP solver), CBC 2.10.12, CLP 1.17.10. The OR-Tools v9.15 release notes list the same SCIP, and HiGHS v1.12.0, among the release's dependencies.
  • The wrapper's version string for HiGHS is wrong. It says "PDLP Solver". The program then ran a one-variable MIP through CreateSolver("HIGHS"), catching what the solver writes to the terminal, and HiGHS's own first line says Running HiGHS 1.12.0 (the rest of that line, a git hash and a copyright notice, is cut). In the last section the same ID solves a MIP to a whole-number answer, which PDLP, an LP solver, cannot. The backend is HiGHS; only its label is wrong, so never decide which solver ran from SolverVersion() alone.

The release notes are where version-specific behavior is written down, and 9.15's are worth reading before you upgrade or downgrade: they add Python 3.14 and drop 3.8, add HiGHS solution hints to MathOpt, and list known issues, one of which you will meet below (CP-SAT's status_name()).

Each API Has Its Own List of Backends, and Only Some Are Compiled In

The two APIs that take a model and a choice of solver each have a list of solver names. A name on the list is not a promise that the solver is there. The program asks each API about every name:

SolverType has eleven members, and five solve: SCIP (GSCIP), GLOP, CP-SAT, PDLP and HiGHS. Five more have a name but no code behind it in this build: they are "not registered", and "support for this solver has not been compiled". Gurobi is the odd one, with its own section below. The AttributeError is a bug in OR-Tools 9.15's Python wrapper, which lesson Common vs. solver-specific parameters, and what each solver rejects, later in this section, takes apart: MathOpt meant to raise a ValueError, and the reason survives only on the exception's __context__, the earlier exception Python keeps attached to the one it raised. The MathOpt page of the OR-Tools documentation also lists FICO Xpress, and the 9.15 release notes say MathOpt supports it; the Python SolverType of this build has no member for it at all.

The linear solver wrapper picks its solver by a string ID at creation:

Eight IDs give a solver. Three are LP solvers (IsMip() is false): GLOP, PDLP and CLP. Five solve MIPs: HiGHS, CBC, SCIP, CP-SAT and BOP. CLP and CBC are COIN-OR's open-source LP and MIP solvers; BOP is a Google solver for integer models, which refuses continuous variables (the last section shows it). The four commercial or external IDs give None. So the wrapper has three solvers that MathOpt lacks here (CLP, CBC and BOP), and MathOpt's HiGHS, SCIP, GLOP, PDLP and CP-SAT are all in the wrapper too.

The wheel holds a third LP/MILP API, model_builder (ortools.linear_solver.python), which the course does not use; asked the same question, it accepts five:

The rest of the package has no list to ask. CP-SAT is its solver. The graph solvers, the knapsack solver and routing each run their own algorithm. The knapsack solver does let you pick among its algorithms by a SolverType (lesson What's in OR-Tools: MathOpt, CP-SAT, linear solver wrapper, routing, graph used the multidimensional branch-and-bound one), but every one of them is part of the wheel.

Problem statement

A logistics team (not GridCap) runs its MIP models through OR-Tools' linear solver wrapper, and lets each deployment list its preferred solvers in order, such as ["GUROBI", "CBC", "SCIP"]. The same list runs on laptops, on build machines and in containers that have different solvers, so the service must use the first preference that is actually there and can solve a MIP.

Write pick_backend(preferences) in backend.py. It returns the first solver ID in preferences for which both hold, or None when none does:

  • pywraplp.Solver.CreateSolver(id) returns a solver, not None;
  • that solver solves MIPs: its IsMip() is true. An LP-only solver given an integer variable solves the LP relaxation and still reports OPTIMAL (the lesson's last section shows it), so it must never be picked for a MIP.

Never fall back to a solver that is not in the list. The tests run in the course runner's OR-Tools 9.15.6755. About six lines.

Gurobi Is on Every List, and Loads Through Neither API in the Course Runner


Gurobi is a commercial solver whose code is not in OR-Tools at all. Both MathOpt and the wrapper load Gurobi's own shared library at run time, if they can find it, and Gurobi then wants a license. The runner has no Gurobi installation, but it does have the gurobipy package (section 5 uses it), and that wheel ships a Gurobi library. The program asks both APIs for Gurobi, then points each of them at that library in a child process, because a library OR-Tools rejects stops the whole process:




Then each API is pointed at gurobipy's library in a child process of its own (attempts holds the one line of code each child runs), and only the line that names the cause is printed:






With nothing to load, MathOpt fails with a C++ bad_function_call that names no cause, and the wrapper returns None. Pointed at the library (MathOpt through init.CppBridge.load_gurobi_shared_library, the wrapper through a GUROBI_HOME folder, which is where it looks), both stop with the same check: OR-Tools 9.15 needs a function, GRBcopyparams, that the libgurobi130.so inside the gurobipy 13.0.3 wheel does not have, and the process aborts (exit code $-6$ is the abort signal). The 9.15 release notes list Gurobi 13.0.0 as supported by the linear solver; that support does not reach the library this wheel ships.


So in this course Gurobi is used through gurobipy directly (section 5, from lesson Models, attributes and the matrix API), never through MathOpt or the wrapper, and no program needs a license to reach this point: every attempt above fails before a license is looked for. On a machine with a full Gurobi installation that OR-Tools supports, plus a license, the same SolverType.GUROBI call is all it takes (lesson Switching solvers: HiGHS, SCIP, CP-SAT, GLOP, Gurobi). Never put a license file in a repository or an image; mount it at run time (lesson Licenses: size-limited, academic, and cloud/container (WLS), in section 5).

A refusal never comes back as a result; mathopt.solve raises before solving, and in 9.15 the reason is on __context__ (lesson Common vs. solver-specific parameters, and what each solver rejects shows how to turn it back into the ValueError MathOpt meant). The wrapper, given the same model:






The wrapper returns None from CreateSolver, or a status from Solve, and sometimes does not refuse at all. A missing solver is None, with no exception: code that skips the if not solver check of the OR-Tools samples fails later, at its first method call on None. Then the dangerous line: GLOP, an LP solver, took a model with an integer variable, said OPTIMAL, and returned $b = 3.5487$, the LP relaxation's answer. Where MathOpt's GLOP refused, the wrapper's GLOP silently dropped the integrality. HiGHS solved the real MIP ($b = 4$). CP-SAT refuses in two places, depending on when it can tell:






CP-SAT raises a TypeError while you build, or returns MODEL_INVALID from solve. A fractional coefficient is caught at once, at add. A model that only turns out wrong as a whole (here, a variable whose range is empty) is solved and comes back with the status MODEL_INVALID, and model.validate() says why (lesson Integer and Boolean variables, linear constraints over integers, later in this section, uses it). The last line is a 9.15 bug, listed among the release's known issues: solver.status_name() with no argument, meant to name the last solve's status, raises TypeError instead. Pass the status, as above.


The special-purpose solvers and routing:



The graph and knapsack solvers raise a TypeError for a fractional number, at the call that receives it: they take whole numbers only, so scale money to whole $k or cents first. The flow solvers return a status from solve(): INFEASIBLE when the arcs cannot carry the supply, UNBALANCED when supplies and demands do not sum to zero. Nothing is raised, so the status check is yours to write. It is a comparison with the solver's own OPTIMAL, done before any cost is read:

Summary


  • One version number covers the package; each bundled solver has its own. The runner pins OR-Tools 9.15.6755: SCIP 10.0.0, HiGHS 1.12.0, CBC 2.10.12, CLP 1.17.10. The wrapper mislabels HiGHS as "PDLP Solver"; the solver's own banner is right.
  • Each API has its own list of backends. MathOpt solves with SCIP, GLOP, CP-SAT, PDLP and HiGHS; the wrapper adds CLP, CBC and BOP. Names on a list that are not compiled in are refused.
  • Gurobi loads through neither API in the course runner: the gurobipy 13 library lacks GRBcopyparams, and loading it aborts the process. Gurobi is used through gurobipy.
  • Each API reports a refusal in its own place: MathOpt raises; the wrapper returns None or a status, and its LP solvers drop integrality silently; CP-SAT raises while building or returns MODEL_INVALID; the graph and knapsack solvers raise on fractions and flows return a status; routing returns None and keeps the reason in status().

Design Note: Make the Environment a Test, Not an Assumption


Every finding in this lesson is a fact about one build of OR-Tools, and it can change with the next one: a solver gets compiled in, a label gets fixed, a refusal becomes a different exception. So a service that depends on a backend should check it the way backend_grid.py does, once at start-up or in its test suite: create the solver, solve an empty or tiny model, and fail loudly if the answer is not what it expects. Pin the exact OR-Tools version alongside that test, and read the release notes before moving the pin.
