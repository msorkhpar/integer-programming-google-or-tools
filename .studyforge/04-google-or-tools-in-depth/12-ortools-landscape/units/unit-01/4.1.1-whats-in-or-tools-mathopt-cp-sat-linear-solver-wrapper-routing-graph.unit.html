  15. What's in OR-Tools

GridCap's planning team has three jobs on its desk this week. Finance wants this year's capital projects picked under the budget. The field manager wants four line crews sent to four substations with the least total travel. And an inspection crew needs a round trip from the depot through five substations. Everyone on the team has heard "use OR-Tools" for all three, and the first thing a new engineer finds is that OR-Tools is not one solver with one way of writing a model. It is a package of several solvers, each with its own Python API (application programming interface: the classes and functions you call), built for different kinds of problem.

This lesson opens the package and solves each of the three jobs with the part of OR-Tools built for it, and the first job with four parts at once, so you can see what each family looks like in code and what it costs you. Every later module of section 4 takes one family and goes deep; this one is the map. GridCap is a fictional utility's portfolio, generated for this course, and the crews, substations and distances below are invented for this lesson.

The Model

The three jobs, stated before any code. Each is small on purpose: the point is how each API takes it, not how hard it is.

Job 1: the budget pick (GridCap tiny, one period, the budget row only; lesson Model, variables, constraints, objective adds the other rules).

Sets. $P$, the 8 projects of GridCap tiny.

Parameters. $v_i$, the NPV of project $i$ if it starts as early as it can ($k); $c_i$, its capex ($k); $B = 7{,}390$, the capital budget ($k).

Variables. $x_i \in \{0, 1\}$ for every $i \in P$: 1 if project $i$ is funded.

Objective and constraint.

A model with one row of this kind (pick items, each with a value and a weight, under one capacity) is a knapsack problem, named after packing a bag.

Job 2: crews to substations.

Sets. $K$, the 4 crews; $S$, the 4 substations.

Parameters. $h_{k,s}$, the travel hours for crew $k$ to reach site $s$ (whole hours).

Variables. $y_{k,s} \in \{0, 1\}$: 1 if crew $k$ goes to site $s$.

Pairing each member of one group with exactly one member of another at least total cost is the assignment problem.

Job 3: the inspection tour.

Sets. $N = \{0, 1, \dots, 5\}$, the depot (0) and five substations.

Parameters. $d_{i,j}$, the road distance from stop $i$ to stop $j$ (whole km).

Decision. For each stop $i$, the stop $\text{next}_i \in N$ the crew drives to after it.

One vehicle, every stop once, shortest round trip: the traveling salesperson problem (TSP). It can be written as a MILP, but the routing library below takes it in this form directly: you give it the distances, and its decision is the next stop of each stop.

OR-Tools Is One pip Package Holding Several Separate Solver Families

pip install ortools installs one package, and the families live in separate subpackages with separate Python modules. The program imports the module each family is used through and checks that the classes this section starts from are there:

Every import worked and no name is missing. Read the table as the package's map:

  • MathOpt (math_opt) is OR-Tools' solver-independent modeling layer for LP and MILP: you write a model of variables, linear constraints and an objective once, and hand it to any of several solvers (lesson The problem zoo: LP, MILP, CP, NLP and how to pick met it; the next two modules, MathOpt core and MathOpt advanced, teach it).
  • CP-SAT (sat) is Google's constraint-programming solver over integers (the module CP-SAT core, from lesson Integer and Boolean variables, linear constraints over integers). It has its own model class, and it is also one of the solvers MathOpt can hand a model to.
  • The linear solver wrapper (linear_solver, imported as pywraplp) is OR-Tools' older API for LP and MILP models, with the same idea as MathOpt (one model, a choice of solvers) and a different syntax. Existing code often uses it, and so do the OR-Tools guide pages on LP and MIP; lessons Reading pywraplp code and Migrating a pywraplp model to MathOpt teach you to read it and move it to MathOpt.
  • Routing lives in constraint_solver, in the same pywrapcp module as OR-Tools' original constraint solver (which this course does not use). In 9.15 there is no ortools.routing Python package; the OR-Tools 9.15 routing samples import from ortools.constraint_solver too.
  • Graph (graph) holds the network solvers: maximum flow, minimum-cost flow and the assignment solver. Knapsack sits on its own, in algorithms.

The "other" line is the rest of the wheel. Some of it is plumbing the families use (init, util, service, and the parameter definitions in glop, bop, pdlp); some is outside this course (set_cover, packing, scheduling's file readers). You will not import them in section 4.

A wrapper, in all of this, is a Python layer over C++ code: every solver here is written in C++ and compiled into the wheel, and the Python modules call into it. That is why a solver can print straight to your terminal past Python's print (lesson Model, variables, constraints, objective, later in this section, meets HiGHS lines printed that way), and why lesson Versions and the backends that ship with it finds some errors only in a log.

The three functions are the same five steps (a model, binary variables, the budget row, the objective, a solve) with three spellings. Where they differ is the point:

MathOptCP-SATlinear solver wrapper
the modelmathopt.Modelcp_model.CpModelthe solver object itself

variablescontinuous, integer, binaryinteger and Boolean onlycontinuous, integer, binary

The second row is the one that shapes code. MathOpt keeps the model free of any solver, so switching solver is one argument (lesson Switching solvers: HiGHS, SCIP, CP-SAT, GLOP, Gurobi). The wrapper builds the model inside a solver object, so switching means recreating it. CP-SAT is one solver, with an API made for it. The third row is the other split: CP-SAT has no continuous variable at all (lesson Integer and Boolean variables, linear constraints over integers), so a model with amounts that can be fractional belongs in MathOpt or the wrapper.

Two things the short CP-SAT function above skips, which any real use needs. First, solver.solve returns a status, the solver's verdict, and a program reads it before it reads a plan: cp_model.OPTIMAL means the plan is proven best, cp_model.FEASIBLE that a limit stopped the search with a plan that is not proven best, and the others (INFEASIBLE, MODEL_INVALID, UNKNOWN) leave no plan to read. Second, CP-SAT's rows take whole-number coefficients only (lesson Versions and the backends that ship with it shows a row with 0.37 in it refused), but its objective may have decimals. The program solves the budget pick once more, with NPV in $M to two decimals, and checks the status first:

The decimal objective was accepted and gave the same four projects. Lesson Integer and Boolean variables, linear constraints over integers teaches the statuses in full, and lesson Objectives, integer scaling and solution callbacks how CP-SAT handles an objective with decimals.

Problem statement

A school district (not GridCap) funds building repairs from a yearly budget. Its finance office keeps every cost in millions of dollars with two decimals (1.15 is $1,150,000), and wants the pick made in CP-SAT, because its other planning models already use it.

Write pick(values, costs, budget) in pick.py. It returns the indices of the repairs to fund, in increasing order, for this model:

Sets. $I = \{0, 1, \dots, n-1\}$, the repairs.

Parameters. $v_i$, the value of repair $i$ (a score, with up to two decimals); $c_i$, its cost ($M, two decimals); $B$, the budget ($M, two decimals).

Variables. $x_i \in \{0, 1\}$ for every $i \in I$.

CP-SAT accepts whole numbers only in a row, so state the budget row in hundredths of a million, where every cost and the budget are whole. Turn each number into hundredths with care: a value such as 1.15 * 100 is not exactly 115 in floating point. Use cp_model.CpModel, new_bool_var, add, maximize and cp_model.CpSolver, as lesson What's in OR-Tools: MathOpt, CP-SAT, linear solver wrapper, routing, graph did. About ten lines.

Two facts from the lesson you will need. CP-SAT's objective accepts decimal coefficients, so the values may stay as they are, or be scaled to hundredths like the costs; either gives the same pick. And solver.solve(model) returns a status: read the plan only when it is cp_model.OPTIMAL or cp_model.FEASIBLE. Funding nothing always fits the budget, so this model always has a plan.

The Special-Purpose Solvers Take One Problem Shape, and No Model at All


The rest of the package does not take models. A special-purpose solver is an algorithm for one problem shape: you hand it the data of that shape (values and weights, a cost matrix, a network) and it hands back the answer. There are no variables and no constraints to write, and nothing else can be added. Job 1 is a knapsack, so the knapsack solver takes it as three lists, adapted from the OR-Tools example knapsack.py:




init takes the values, a list of weight rows (one row per capacity; here one, the budget) and the capacities. The program runs all four functions:






Four APIs, one answer: fund P001, P004, P005 and P006 for $4,876k of NPV, spending $7,370k of the $7,390k. The knapsack solver needed the least code, and it is the least flexible. It takes more capacity rows (one weight row per capacity), but nothing else: GridCap's real selection also has must-do projects, "at most one of these alternatives" and "a child only with its parent" (lesson Model, variables, constraints, objective), and init has no argument for any of them. The moment a rule is not a capacity, the general model is the tool.


Job 2 is an assignment problem, and the graph package has a solver for exactly that shape, SimpleLinearSumAssignment, adapted here from the OR-Tools example assignment_linear_sum_assignment.py. Its input is one arc per (crew, site) pair with a cost:




right_mate(k) is the site paired with crew k. The same program also writes Job 2 as the general model of the formulation, in CP-SAT, with one add_exactly_one per crew and per site:






Both find the 15-hour plan. It is not the plan of sending each crew to its own nearest site: the Plains crew's nearest is S1 (5 hours), which the Valley crew needs more (2 hours), so Plains goes to S4 (6 hours). Finding that is the whole job of an assignment algorithm.


with_assignment_solver checks solve()'s return value before it reads a cost. That value is a status, and the assignment solver has three. When no pairing exists, it says so in the status and raises nothing:






Compare the status with the solver's own OPTIMAL (solver.OPTIMAL), and read optimal_cost() and right_mate only when they are equal. POSSIBLE_OVERFLOW means the costs are too large for the solver's whole-number arithmetic.


The other two graph solvers take networks: SimpleMaxFlow (the most that can move from a source to a sink through arcs of limited capacity) and SimpleMinCostFlow (move given supplies to given demands at least cost). Lessons Graph and flow solvers: SimpleMaxFlow and SimpleMinCostFlow and Special-purpose solvers: LinearSumAssignment, KnapsackSolver and bin packing teach all three, plus the knapsack solver, and checks each against the MIP it replaces. Two facts about them come up in lesson Versions and the backends that ship with it: they take whole numbers only (a fraction raises a TypeError), and the flow and assignment solvers report an impossible problem through a status returned by solve, not an exception.

Problem statement


A water utility (not GridCap) sends its repair crews to depots each morning, one crew per depot, and wants the least total travel. Some crews are not cleared for some depots. The data is a matrix hours[k][d]: whole travel hours for crew k to reach depot d, or None where crew k is not cleared for depot d. There are as many crews as depots.


Write pair(hours) in pairing.py with OR-Tools' assignment solver, linear_sum_assignment.SimpleLinearSumAssignment. It returns (total_hours, depot_of), where depot_of[k] is the depot crew k goes to, or None when no pairing gives every crew a depot it is cleared for. The problem it solves:


Sets. $K$, the crews; $D$, the depots ($|K| = |D|$); $A \subseteq K \times D$, the cleared pairs (the entries that are not None).


Parameters. $h_{k,d}$, the hours for each $(k, d) \in A$.


Variables. $y_{k,d} \in \{0, 1\}$ for every $(k, d) \in A$.



You do not write this model: the assignment solver takes it as arcs. Give it one arc per cleared pair (add_arc_with_cost), call solve(), and read optimal_cost() and right_mate(k). Check what solve() returns before you read anything: it is a status, one of OPTIMAL, INFEASIBLE and POSSIBLE_OVERFLOW, and you compare it with the solver's own solver.OPTIMAL. About ten lines.

Routing Is Its Own Library, Built Around Vehicles, Stops and Callbacks


Job 3 goes to the routing library, a solver made for vehicle routes: one or many vehicles, a depot, stops, and the rules real routes carry (vehicle capacities, time windows, stops that may be dropped at a price; the OR-Tools routing guide lists these as variants of the vehicle routing problem). The program is adapted from the OR-Tools example tsp_cities.py, with five invented substations on a grid of km:






Three things in this code exist nowhere else in OR-Tools:


  1. An index manager. RoutingIndexManager(stops, vehicles, depot) translates between your stop numbers ("nodes") and the solver's internal indices, which are different because each vehicle has its own start and end. Every callback converts with IndexToNode.
  2. Costs as callbacks. You do not give the solver a matrix; you register a Python function (RegisterTransitCallback) that it calls for the cost of any arc, and tell it that function is the cost of every vehicle.
  3. A search, steered by parameters. PATH_CHEAPEST_ARC is the rule for the first route: start at the depot and keep extending the route by the cheapest next leg. How the search goes on from that first route is set by more parameters (lesson First-solution strategies, local search and search limits).


The status is ROUTING_SUCCESS, not ROUTING_OPTIMAL. Both names are in the library's status list, printed above, and ROUTING_SUCCESS means it found a route, not that it proved none is shorter. The OR-Tools routing guide says the same in plain words: the library sometimes returns routes that are good rather than optimal. That is the trade the routing library makes, and it is why a planner who needs proven optima on a small instance still writes a MILP. The routing lessons at the end of this section, from lesson The routing model: index manager, transit callbacks and the TSP on, teach the library: dimensions, capacities, time windows, droppable visits and the search settings.


Summary


  • OR-Tools is one pip package with separate solver families, each in its own module: math_opt, sat, linear_solver (pywraplp), constraint_solver (pywrapcp, routing), graph and algorithms (knapsack).
  • MathOpt, CP-SAT and the linear solver wrapper take a general model. They spell the same five steps differently; MathOpt names the solver at solve, the wrapper at creation, and CP-SAT is its own solver with integers only.
  • The special-purpose solvers take one problem shape and no model. The knapsack and assignment solvers matched the general models' answers here, with less code and no room for a single extra rule.
  • Routing is its own library: an index manager, cost callbacks and a search, which returns good routes (ROUTING_SUCCESS) without proving them optimal.

Design Note: The Family Is Chosen by the Problem's Shape, Not by Habit


All four APIs answered Job 1 the same way, and that is the usual case for small problems: the choice of family rarely changes the answer, but it decides what you can add later. A knapsack solver is a dead end the day a must-do rule arrives; a general model is not. A routing library gives up proofs of optimality to handle routes that a MILP could not solve in time at all. Lesson Choosing an API for a problem turns these trade-offs into a procedure.
