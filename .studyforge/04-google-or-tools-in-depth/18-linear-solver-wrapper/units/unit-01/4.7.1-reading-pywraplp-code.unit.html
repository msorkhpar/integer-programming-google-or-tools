GridCap's planning team inherits a script from a contractor. It chooses which projects to fund under the capital budget, and it has worked for years, but nobody on the team has read it closely. It does not use MathOpt, the API this course has used since section 1. It imports ortools.linear_solver.pywraplp, OR-Tools' older linear solver wrapper. The OR-Tools documentation calls it MPSolver, and its pages on LP, MIP, assignment and bin packing are written with it. A lot of existing code is too, so you have to be able to read it before you can trust it, fix it or port it (lesson Migrating a pywraplp model to MathOpt does the port).

This lesson teaches the wrapper the way the OR-Tools pages "Solving an LP Problem" and "Solving a MIP Problem" do: create a solver, add variables, add rows, set the objective, solve, and read the status before the values. It ends by reading the inherited script line by line against its model. GridCap is a fictional utility's portfolio, and the script was written for this course. There are four rules, one per heading.

A pywraplp Program Picks Its Back End by Name, and the Solver Holds the Model

Every pywraplp program starts the same way:

CreateSolver takes the name of a back end: the engine that will do the actual solving. GLOP is Google's LP solver and SCIP is an open-source MIP solver. If the name is unknown, or that back end was not built into this copy of OR-Tools, or it needs a licence that is missing, CreateSolver returns None and raises no error. So the OR-Tools samples follow it with if not solver: return. This program asks for each name in the course's runner image:

Three things to read in it:

  • The name decides LP or MIP. IsMip() says whether the back end handles integer variables. GLOP, PDLP and CLP are LP solvers. SCIP, CBC, SAT (CP-SAT) and HIGHS solve MIPs. The next section shows what happens to a script that creates "GLOP" and then adds integer variables.
  • Commercial back ends are names too. Gurobi, Xpress and CPLEX are reachable through the same call when their libraries and licences are installed. Here they are not, so the call returns None, and OR-Tools logs a warning about the missing library on standard error.
  • SolverVersion() is a label, and it can be wrong. For "HIGHS", OR-Tools 9.15 prints "PDLP Solver", the label of a different back end, and the two rows disagree on IsMip(): PDLP is an LP solver, while the "HIGHS" solver says it handles integers. If you need to know which back end ran, look at the name you passed in.

The deeper point is in the comment on the first line: in pywraplp, the solver object is the model. Variables and rows are created by methods of solver, and they belong to it. To try the same model on another back end, you build it again in a new solver object. Lesson Migrating a pywraplp model to MathOpt shows that MathOpt splits these two jobs: a Model holds the variables and rows, and the solver is named only when you call solve.

Variables, Rows and the Objective Come From the Solver, in Two Styles

Lesson The problem zoo: LP, MILP, CP, NLP and how to pick solved this small model with MathOpt (it is the model of the OR-Tools page "Solving a MIP Problem"):

Here it is in pywraplp, adapted from the OR-Tools samples simple_lp_program.py and simple_mip_program.py. It is built three times: with continuous variables solved by GLOP, with integer variables solved by SCIP, and with integer variables handed to GLOP:

The first two are the answers lesson The problem zoo: LP, MILP, CP, NLP and how to pick found: 25 for the LP and 23 for the MIP. The third is the trap the back-end table warned about. IntVar asked for whole numbers, GLOP returned $y = 2.5$ with status OPTIMAL, and nothing complained. An LP solver solves the LP relaxation, whatever the variables were declared as. (Its "best bound" of $-\infty$ is simply not a MIP bound: GLOP never computes one.) When you read a script, check that the back end's name matches the variables.

The calls map one to one onto the parts of a model:

Part of the modelpywraplp call
continuous variable, $l \le x \le u$solver.NumVar(l, u, name)
integer variablesolver.IntVar(l, u, name)
binary variable, $x \in \{0, 1\}$solver.BoolVar(name), the same as IntVar(0, 1, name)
no boundsolver.infinity(), or -solver.infinity() below
a row written as an expressionsolver.Add(expr <= b, name); >= and == work too
objective written as an expressionsolver.Maximize(expr) or solver.Minimize(expr)

Every variable is created with its bounds, so a reader finds the domain at the creation line: NumVar(0.0, infinity, "x") is $x \ge 0$, continuous. Names are optional, but they cost nothing and are what you search for in an exported model, so give every row one.

Older scripts, and the OR-Tools sample mip_var_array.py, use a second style, which builds rows coefficient by coefficient. That suits data held in a matrix, and you will meet it often:

RowConstraint(lb, ub, name) creates an empty row with a lower and an upper bound, $lb \le \sum_j a_j x_j \le ub$, and SetCoefficient fills in one $a_j$ at a time. A coefficient that is never set is 0. The objective works the same way: solver.Objective() returns it, SetCoefficient fills it, and SetMaximization() (or SetMinimization()) sets its sense.

Notice the 0 in RowConstraint(0, BOUNDS[i], ...). Every row of this model is ranged: it has a lower bound as well as an upper one. Reading the code fast, you would write the model as four "$\le$" rows, but the solver received eight inequalities. The quickest way to see what a solver really holds is to ask it for the model as text. ExportModelAsLpFormat(False) writes it in LP format, a plain-text format for models that most solvers can read. The program prints it before solving:

That is the export's objective and its eight inequalities, two per row for row0 to row3; the export also prints a header, the variables' bounds and the list of integer variables, left out here. The exporter writes each ranged row as two lines, _rhs for the upper bound and _lhs for the lower one. In the answer below no lower bound is binding: at the optimum every row's activity (its left-hand side, evaluated at the solution) is well above 0. row1 has a $-9$, though, so some other plan could push its activity below 0, and the hidden lower bound would then cut that plan off. When you port or rewrite a coefficient-style script, carry both bounds of every RowConstraint. A row with no lower bound is written RowConstraint(-solver.infinity(), ub, name).

The program printed these activities by reading the model back. solver.constraints() lists the rows, and each row answers name(), lb(), ub() and GetCoefficient(var). That is how to inspect a pywraplp model you did not write.

Problem statement

A water utility's planning script keeps its rows as data, so that planners can edit them in a spreadsheet. Each row is a tuple (name, lower, coefficients, upper): coefficients maps a variable's name to its coefficient, and lower or upper is None when the row has no bound on that side. A variable missing from coefficients has coefficient 0 in that row.

Write add_rows(solver, x, rows) in rows.py, which adds every row to a pywraplp solver in the coefficient style: one RowConstraint per row, filled with SetCoefficient. x maps variable names to the solver's variables. Each row is

with $\ell_r = -\infty$ when lower is None and $u_r = +\infty$ when upper is None.

Solve Returns an Integer Status, and Values Exist Only When It Says So


solver.Solve() returns a status, and in pywraplp the status is a plain integer. The class gives the integers names:



  • OPTIMAL (0): a solution was found and proved best, within the MIP gap tolerance (lesson Best bound, incumbent, absolute and relative gap defines the gap; lesson Migrating a pywraplp model to MathOpt shows why the tolerance matters).
  • FEASIBLE (1): a solution was found, but a limit, such as the time limit, stopped the search before it was proved best.
  • INFEASIBLE (2) and UNBOUNDED (3): no plan satisfies the rows, or the objective can improve without end.
  • ABNORMAL (4), MODEL_INVALID (5), NOT_SOLVED (6): the back end failed, the model is malformed or Solve has not run.


That is why the samples print status 0 and compare the result with a name: if status == pywraplp.Solver.OPTIMAL:. A script that prints the raw status prints a number, and 2 tells nobody anything.


Now the trap. Here is a model that no values can satisfy, $x + y \ge 20$ with $x \le 3$ and $y \le 10$, and what the solver says when it is asked for values anyway:






No exception. The model is infeasible, yet solution_value() answers 0.0 for each variable and the objective reads 0.0. A script that only reads values carries on, and a report built from them says "fund nothing, value $0". An all-zero plan is often a believable answer, so nobody notices. MathOpt raises a ValueError in the same situation (lesson Migrating a pywraplp model to MathOpt). In pywraplp, read the status first, and read values only after OPTIMAL or FEASIBLE.

A Legacy Script Reads Line by Line Against Its Model


Here is the inherited script. Read it the way you would in a code review: for each block, say which part of the model it builds.



Block by block:


  1. SetTimeLimit(60_000) is in milliseconds: a minute, not 16 hours. MathOpt takes a timedelta, and a port that passes the number straight through as seconds changes the limit a thousandfold.
  2. BoolVar makes one binary per project: $x_i \in \{0, 1\}$, fund project $i$ or not.
  3. The budget row is built coefficient by coefficient, with $-\infty$ as its lower bound: $\sum_i c_i x_i \le B$.
  4. A must-do project is not a row. SetBounds(1, 1) fixes the variable's bounds to $[1, 1]$. That is the same rule as the row $x_i = 1$, but it does not appear in solver.constraints(), so a reader who lists the rows to understand the model misses it.
  5. A child project needs its parent: $x_c \le x_{p(c)}$, one named row per child.
  6. Alternatives: at most one project per group, $\sum_{i \in g} x_i \le 1$. solver.Sum(list) adds up a list of variables, like Python's sum.
  7. The objective: maximize total value, coefficient by coefficient.


The script then solves, keeps the plan only when the status is OPTIMAL or FEASIBLE, and returns the funded projects:




The rows the solver lists for tiny are the budget, one parent row and one alternative row. P002, a must-do project, has no row of its own, exactly as block 4 predicts. The small portfolio's $25,336k is the plan to check any port against: same data, same model, same value. Summary


  • A pywraplp program picks its back end by name, and the solver holds the model. CreateSolver(name) returns None for a back end that is missing, and the name decides LP or MIP. Variables and rows belong to that solver object.
  • Variables, rows and the objective come from the solver, in two styles. NumVar, IntVar and BoolVar take their bounds; rows come from Add(expr) or from RowConstraint(lb, ub) plus SetCoefficient. A RowConstraint with a finite lower bound is a ranged row, and ExportModelAsLpFormat shows what the solver really holds.
  • Solve returns an integer status, and values exist only when it says so. After INFEASIBLE, solution_value() still answers 0.0, with no exception.
  • A legacy script reads line by line against its model. Map each block to a set, a variable, a row or the objective, and look for rules hidden in variable bounds.

Design Note: A Status Check Belongs Next to Every Read


pywraplp returns values whatever the status, so the check cannot be left to the caller's memory. Keep one small function that turns a solved solver into an answer, or into nothing: it reads the status first and returns no plan unless the status is OPTIMAL or FEASIBLE. Every report then goes through it. The legacy script does this already: its early return status, None, [], solver is the most valuable line in it. Practice 2 builds that function.
