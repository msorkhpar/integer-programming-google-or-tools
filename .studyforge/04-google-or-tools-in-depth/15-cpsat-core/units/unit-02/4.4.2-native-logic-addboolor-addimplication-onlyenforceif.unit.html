  17. CP-SAT's native logic

A MILP states a rule between yes/no decisions as a linear row over binaries. "Fund P030 or P032, not both" becomes $x_{030} + x_{032} \le 1$; "undergrounding P034 needs P013 or P040" becomes $x_{034} \le x_{013} + x_{040}$. Each such row is correct, and each needs a moment of algebra to write and a truth table to check. A rule that switches a whole linear row on or off needs more: a big-M row, where a constant $M$ times a binary loosens the row when the binary is 0. $M$ has to be computed from bounds in the data, at least as large as the most the row could be broken by when it is switched off; a value too large weakens the model, and can leak through the solver's tolerance. Section 6 teaches these linear forms in depth (lesson AND, OR, NOT, XOR and implication as linear constraints for logic rows, lesson Deriving big-M from bounds for deriving $M$, lesson What a loose M does to the LP bound and to numerics for what a loose $M$ does). This lesson shows each linear row it needs next to its CP-SAT form, so it does not depend on them.

CP-SAT was built for this kind of rule. It has constraints that are logic (an OR, an AND, an implication), and any linear row can be switched on by a truth value with no big-M at all. This lesson rewrites GridCap's bundle rules with them: parents, alternatives, the engineers' four rules and an all-or-nothing bundle. It is the same model as lesson Integer and Boolean variables, linear constraints over integers; only the way the rules are written changes.

GridCap is a fictional utility's portfolio, generated for this course; the rules are invented for the course.

A Literal Is a Boolean Variable or Its Negation

CP-SAT's logic constraints take literals. A literal is a Boolean variable x, or its negation ~x ("not x"), which is true exactly when x is false. You never create ~x: the ~ operator gives it, and ~~x is x again. The OR-Tools example on literals shows just that, adapted here:

A MILP writes "not funded" as $1 - x_a$, an expression. CP-SAT's ~x is not an expression to be moved around a row; it is a truth value the logic constraints read directly, and it costs nothing. Older code writes it x.Not(); OR-Tools 9.15 accepts both, and its examples use ~x.

A rule can be said in several ways, and CP-SAT accepts each. The OR-Tools example on reified constraints writes "if b, then x and not y" three times: as an AND switched on by b, as two implications, and as two ORs. The truth-table helper of this module fixes the three Booleans to each of their 8 combinations and asks CP-SAT whether the constraints still hold:

Each combination prints as its digits in the order bxy, so 110 means $b = 1, x = 1, y = 0$. All three allow the same five: every combination with $b = 0$, and with $b = 1$ only $x = 1, y = 0$. So "if b then x" is the same rule as "not b, or x", and you can write whichever reads best.

Each Logic Constraint Allows Exactly the Assignments Its Name Says

CP-SAT's logic constraints, from the cp_model.py docstrings, each checked with the truth-table helper:

ConstraintMeansThe linear row of a MILP
add_bool_or(l1, l2, ...)at least one literal is true (a clause)$x_a + x_b \ge 1$
add_bool_and(l1, l2, ...)every literal is trueeach $x = 1$
add_implication(a, b)if a then b$x_a \le x_b$
add_at_most_one(...)at most one is true$\sum x \le 1$
add_exactly_one(...)exactly one is true$\sum x = 1$
add_bool_xor(l1, l2, ...)an odd number are trueneeds extra variables
add(a == b)the two are equal$x_a = x_b$

Read the table against the linear rows. add_implication(a, b) refuses only 10 ("a without b"), as $x_a \le x_b$ did. add_bool_or(~a, ~b, c) refuses only 110: it is "if a and b, then c", because "a and b imply c" is false only when a and b are true and c is false, and so is the clause "not a, or not b, or c". The only constraint here without a short linear row is XOR; its docstring also says it does not support only_enforce_if, the switch the next sections use.

A clause is an OR of literals. Every rule about yes/no decisions can be written as clauses, and clauses are what the SAT part of CP-SAT works with best (the Primer's Basic Modeling chapter says short add_bool_or clauses are efficient). That is the practical reason to write logic as logic: the solver receives the rule in the form it reasons with, instead of a row it has to recognise.

GridCap's Rules Become One Constraint Each, With No Big-M

The lesson's model on GridCap small, first with no extra rule, then with each rule alone, then with all five. Each rule is written once in CP-SAT and once as the linear row of the table above, and HiGHS solves the linear version through MathOpt:

On every line CP-SAT and HiGHS agree on the value, so the logic constraint and the linear row allow the same plans, as the truth tables said they would. (Lesson AND, OR, NOT, XOR and implication as linear constraints, in section 6, solves the same rules on a model without the crew rows and the credit line, so its numbers differ from these.)

The parent and alternative rules are now native too: selection(small, native=True) writes them as add_implication and add_at_most_one, and lesson Integer and Boolean variables, linear constraints over integers's linear version reaches the same optimum, $25,374k (the module's tests check it).

Read each line against its rule. Under bundle, the plan had P019 without P024, and the cheapest repair is to drop P019 (and P008) rather than add P024. Under both_need, the solver drops P022 rather than buying P033, so the "if both" never happens. A logic constraint, like a row, is satisfied in whatever way costs least.

None of these rules needed a big-M, and none needs one as a linear row either: a rule among yes/no decisions is a row or two with no $M$, as the table above shows. What CP-SAT changes here is the writing and the reading. add_bool_or(x["P013"], x["P040"]).only_enforce_if(x["P034"]) says the engineer's sentence in the engineer's order, and a reviewer checks it without redoing the algebra. Where CP-SAT removes the big-M is the next section: a linear row switched by a decision.

Problem statement

A software team (not GridCap) picks which features ship in the next release. The product owner's rules come in four kinds, each a list of tuples of feature names:

  • requires: (a, b), "feature a needs feature b";
  • excludes: (a, b), "a and b never ship in the same release";
  • needs_one_of: (a, [o1, o2, ...]), "a needs at least one of the options";
  • bundles: (a, b), "a and b ship together or not at all".

x[f] is the Boolean "feature f ships". In logic, the four kinds are

Write add_rules(model, x, requires, excludes, needs_one_of, bundles) in release.py: one CP-SAT constraint per rule, with no linear algebra and no big-M. The tests fix which features ship and ask CP-SAT whether the rules allow it. About eight lines.

OnlyEnforceIf Switches a Linear Row On a Conjunction of Literals


only_enforce_if(l1, l2, ...) can follow any constraint that supports it (linear rows, add_bool_or, add_bool_and and most others; not add_bool_xor). The constraint then holds when every listed literal is true, and is ignored otherwise. The listed literals are its enforcement literals. Here it is in three shapes on GridCap small (lesson Indicator constraints vs. big-M, in section 6, sets it beside MathOpt's indicator constraints):










  1. One literal. "If P032 (the Valley line rebuild) is funded, the rest of Valley's capex stays within $4,000k", because the outage leaves the region's construction managers no time for more. The optimum drops P032 and keeps $11,870k of other Valley work, worth more than P032. As a big-M row this would be $\text{rest} \le 4{,}000 + M(1 - x_{032})$, with $M$ at least the largest value the rest of Valley can reach minus 4,000, $11,850k: when $x_{032} = 0$ the row must allow every value the rest can take (lesson Deriving big-M from bounds, in section 6, derives such bounds in depth). In CP-SAT there is no $M$ to compute, to keep up to date when the data changes, or to get wrong.
  2. A conjunction. "If P017 and P028 are both funded, at most 4 other transmission projects." Passing two literals means both: the row holds when P017 and P028 are funded. (Two copies of the row, one enforced by each literal, would mean something else: each copy holds when its own literal is true, so the row would hold whenever either project is funded.) The optimum funds both and keeps exactly 4 others. A MILP would need a big-M times $(2 - x_{017} - x_{028})$, or first a new binary that linear rows force to be 1 exactly when both are (lesson AND, OR, NOT, XOR and implication as linear constraints, in section 6, writes such an AND).
  3. A negated literal. "A $150k program-office fee applies when vegetation capex passes $2,000k." The fee is a Boolean fee, and the row "vegetation capex at most $2,000k" is enforced when the fee is not paid: only_enforce_if(~fee). The optimum trims vegetation to $1,800k and pays no fee. The plan before had $2,260k of vegetation; it would now pay the fee and be worth $25,374k − $150k = $25,224k, less than the $25,363k of the trimmed plan.


The rule to remember: only_enforce_if means "if", not "if and only if". When its literals are false the row is simply not checked, and nothing forces it to be false. That is enough here, and the next section shows when it is not.

Write the Side the Objective Would Exploit, or Both


An enforced row is half-reified: the literal implies the row, and nothing goes the other way. A reified constraint, an "if and only if", is two half-reified ones: the literal implies the row, and its negation implies the row's opposite. The OR-Tools guide on channeling builds one this way, a Boolean b that is true exactly when $x \ge 5$: model.add(x >= 5).only_enforce_if(b) and model.add(x < 5).only_enforce_if(~b).


When is one side enough? When the objective only ever pushes the literal one way, and that way is the side you wrote. The fee above is a cost, so the solver wants fee false; the row enforced on ~fee stops it from being false when spending is high. The other direction (fee true while spending is low) is allowed but never chosen, because it only costs money.


Turn the fee into a $100k rebate that the vegetation program earns when its capex passes $2,500k, and the same pattern breaks. The solver now wants rebate true:






The first model claims the rebate with only $2,260k of vegetation work. Its row says "no rebate implies at most $2,500k", which says nothing about a rebate with little spending, and the solver took the $100k. The second model writes the side the objective would exploit, "rebate implies more than $2,500k", and the solver earns the rebate honestly: it raises vegetation to $2,740k, and the plan is worth $25,458k, $84k more than without a rebate. Both models are OPTIMAL; only the first is wrong. No solver status catches a half-reification written on the wrong side.


When the Boolean is a flag that the objective does not drive, or drives both ways in different scenarios, write both sides. With both rows, the flag tells the truth whichever way the objective pulls it:






veg >= 2_501 and veg <= 2_500 are exact opposites because capex is in whole $k; in CP-SAT that is always true of a row (every value is an integer), so the opposite of $\text{expr} \le T$ is $\text{expr} \ge T + 1$. The rule, "pin only the side the model would exploit, or both when unsure", holds for linear rows too (lesson AND, OR, NOT, XOR and implication as linear constraints, in section 6, applies it); here there is no big-M on either side.

Summary


  • A literal is a Boolean variable or its negation. ~x is free, and every logic constraint takes literals.
  • Each logic constraint allows exactly the assignments its name says. add_bool_or, add_bool_and, add_implication, add_at_most_one, add_exactly_one, add_bool_xor and add(a == b); a truth table checks any of them.
  • GridCap's rules become one constraint each, with no big-M. CP-SAT and HiGHS agree on every rule's optimum; the logic version says the rule in its own words.
  • OnlyEnforceIf switches a linear row on a conjunction of literals. No $M$ to compute; several literals mean all of them.
  • Write the side the objective would exploit, or both. only_enforce_if is "if", not "if and only if"; for a flag, write both rows.

Design Note: Name the Rule, Then Pick Its Form


engineers_rules.py keeps each rule as a name with two forms side by side, the CP-SAT constraint and the MathOpt row. Writing rules as data like this keeps the business sentence next to its code, lets a test run each rule alone, and makes porting between solvers a matter of adding a column. When a model's rules come from people who are not modelers, keep their sentence as the rule's comment and its name as the constraint's name (with_name), so a planner reading an infeasibility report later (lesson Hints, assumptions and SufficientAssumptionsForInfeasibility) sees words they wrote.
