  15. CP-SAT variables, rows and statuses

GridCap's planners have one more lever this year. The capital budget of the small portfolio is $38,390k, and the treasury has arranged a credit line on top of it: four tranches of $500k each, drawn whole, each costing $300k in interest and fees over the plan. Drawing a tranche pays only if the projects it lets in are worth more than $300k. The planners also want each program's work kept within the crew-months its own crews can give over the five years.

You could write this as a MILP in MathOpt, as lessons Decisions, objectives and constraints: turning a planner's question into a model and Yes/no decisions, and why rounding an LP fails did. This module writes it in CP-SAT, OR-Tools' other integer solver, which lesson The problem zoo: LP, MILP, CP, NLP and how to pick used briefly. CP-SAT stands for constraint programming with a SAT solver inside: it searches over variables that take whole-number values, deducing from each constraint which values are still possible, and it learns from every dead end (the CP-SAT Primer's chapter on its search describes the machinery; this module needs only its consequences). Those consequences are the rules of this lesson: every variable is an integer with a known finite range, every constraint has whole-number coefficients, and every answer starts with a status that says what kind of answer it is.

GridCap is a fictional utility's portfolio, generated for this course. None of its numbers describe a real company, and the credit line is invented for this lesson.

The Model

The one-period selection of lesson Decisions, objectives and constraints: turning a planner's question into a model, with a crew row per program and the credit line.

Sets. $P$, the projects (40 on GridCap small); $G$, the programs (transmission, distribution, vegetation), with $P_g \subseteq P$ the projects of program $g$; $M \subseteq P$, the must-do projects; $C \subseteq P$, the child projects, each with a parent $p(c)$; $\mathcal{A}$, the alternative groups, each a set of projects of which at most one may be funded.

Parameters. $v_i$, the NPV of project $i$ if it starts as early as it can ($k); $\text{capex}_i$, its total cost ($k); $n_i$, the crew-months it needs over its life (its crew-months per year of work times its years of work); $N_g$, the crew-months program $g$'s own crews give over the five years; $B = 38{,}390$, the capital budget ($k); a tranche is $500k and costs $300k; there are 4 tranches.

Variables.

$x_i = 1$ if project $i$ is funded; $k$ is the number of tranches drawn. $k$ is a general integer variable: an integer that can take more values than 0 and 1.

Objective.

Constraints.

Every coefficient here is a whole number: GridCap keeps money in whole $k and crew-months as whole months. That is what makes this model a CP-SAT model as it stands. The code names the rows budget, crews_transmission, must_P003, parent_P016 and alt_G001.

A CP-SAT Program Is a Model, a Solver and a Status Check

Every CP-SAT program has the same four steps, and the OR-Tools guide CP-SAT Solver teaches them on a model so small it has no data at all: three variables that each take a value 0, 1 or 2, and one constraint, $x \ne y$. The program below is that example, adapted:

  1. The model. cp_model.CpModel() is an empty container. It holds variables, constraints and at most one objective, and nothing is solved while you fill it.
  2. The variables. new_int_var(lb, ub, name) makes an integer variable that may take any whole value from lb to ub, both included. The name is for printing and for the solver's log.
  3. The constraints. model.add(...) takes a comparison between linear expressions, here x != y.
  4. The solver and the status. cp_model.CpSolver() runs the search; solve(model) returns a status, a code that says what the solver found. Only after checking it does the program ask for values, with solver.value(var).

The model has no objective, so any assignment that satisfies the constraint is as good as any other, and the solver reports OPTIMAL for the first one it finds: with nothing to optimize, "a solution was found" and "an optimal solution was found" are the same statement.

The method names are snake_case (new_int_var, solve, status_name). Older code and older answers online use CamelCase (NewIntVar, Solve); OR-Tools 9.15 still accepts those names, and the cp_model.py source marks them as deprecated aliases. This course writes snake_case, as the OR-Tools guides now do.

Every Variable Is an Integer With a Finite Domain

A variable's domain is the set of values it may take. CP-SAT has no other kind of variable: no continuous variable, and no integer without bounds. There are three ways to make one:

  • new_bool_var(name) is the 0/1 variable, the binary of lesson Yes/no decisions, and why rounding an LP fails. It is an integer variable with the domain 0..1, so it can appear in sums with a coefficient like any other. It is also a truth value: ~x is "not x", which lesson Native logic: AddBoolOr, AddImplication, OnlyEnforceIf builds on.
  • new_int_var(lb, ub, name) is a general integer, here the tranche count $k$ of the model.
  • new_int_var_from_domain(domain, name) takes any finite set of integers, given as a cp_model.Domain. Domain.from_values lists the values; Domain.from_intervals takes ranges such as [[0, 0], [500, 2000]] ("nothing, or at least 500"). A MILP has no such variable: it would need one binary per allowed value, or a binary and two rows for the gap.

Asked for the smallest draw that covers a $700k shortfall, the solver can only answer with a value of the domain:

Why the bounds must be finite. CP-SAT reasons about each variable as a range of whole numbers and narrows the range as the search goes (this narrowing is called propagation). It also adds up the largest and smallest values each constraint's left side can take, in 64-bit integers, and it checks that no such sum can overflow before it starts. A variable with a huge range fails that check, and the solver refuses the model rather than risk a wrong answer:

kint64max is the largest 64-bit integer, $2^{63} - 1$, so a domain must lie within about $\pm 4.6 \times 10^{18}$. model.validate() returns an empty string for a valid model and the reason otherwise; call it when a solve says MODEL_INVALID. The practical rule is stronger than "don't overflow": take each bound from the data. The tranche count is at most 4 because the credit line has 4 tranches; a spend is at most the sum of the capex that could be in it. The CP-SAT Primer recommends keeping every domain as tight as the data allows, because the solver's work on a variable grows with the part of its range it has to reason about.

A Linear Constraint Has Whole-Number Coefficients

model.add takes a comparison between two linear expressions: sums of variables times numbers, plus a constant. <=, >= and == work as in MathOpt. Two more forms are CP-SAT's own:

  • add_linear_constraint(expr, lb, ub) states $lb \le \text{expr} \le ub$ in one constraint, a ranged row (a floor and a cap on the same sum).
  • != is not linear (the allowed values form two separate pieces, below 3 and above 3), and a MILP would need a binary and two big-M rows to state it. CP-SAT takes it directly. The Primer warns that many != constraints can be slow, and offers add_all_different for "all of these differ".

What model.add refuses is a coefficient that is not a whole number:

The refusal happens in Python, when the row is built, before any solve. A right-hand side such as 7.5 is refused the same way. The second line is the solve of the four valid rows with maximize(crews): $a = 1$ (so $b = 0$), and the range row allows $2\,\text{crews} - 1 \le 7$, so crews is at most 4; 4 is not 3, so it is allowed.

This is the price of CP-SAT's exact integer arithmetic: there is no tolerance. A MILP solver accepts a value within its integrality tolerance of a whole number as whole (lesson What a loose M does to the LP bound and to numerics, in section 6, shows what such a tolerance lets through); CP-SAT's values are Python ints, and a row either holds exactly or it does not. Data with fractions has to be multiplied out to whole numbers first, and lesson Objectives, integer scaling and solution callbacks shows how to do that without changing which plans a row allows.

Problem statement

A food bank (not GridCap) leases vans for its weekend drive. Each van type $t$ carries $\text{cap}_t$ pallets and costs $c_t$ dollars for the weekend. The dealer has $a_t$ vans of the type, and leases them only in packs of $k_t$ (a pack of 2 means 0, 2, 4, ... vans). The drive must move demand pallets, the board approved budget dollars, and every van needs one of the drivers volunteers.

Read the Status Before You Read a Value


solver.solve(model) returns one of five statuses. The program below provokes each of them on GridCap small, using the lesson's model and some deliberately broken versions of it (one search worker throughout, so every run repeats exactly; lesson Deterministic time, seeds and reproducible runs explains why that matters):



StatusMeaningIs there a plan to read?
OPTIMALa solution was found and proved best (for a model with no objective: a solution was found)yes
FEASIBLEa solution was found, but the search stopped before proving it bestyes, with a gap
INFEASIBLEproved that no assignment satisfies every constraintno
MODEL_INVALIDthe model breaks a rule of CP-SAT (overflow, an empty domain, ...); model.validate() says whichno
UNKNOWNthe search stopped (a limit) before it found a solution or proved there is noneno


Each line of the output is one cause:


  • FEASIBLE. stop_after_first_solution = True stops the search at the first plan, worth $24,419k. The bound ($25,852k) is the best value the solver can still not rule out; the true optimum lies between the two. A limit that stops the search with a plan in hand gives the same status; lesson Objectives, integer scaling and solution callbacks shows it for a callback that stops the search.
  • UNKNOWN. No conflicts allowed and no presolve: the solver stopped before it had any plan. The OR-Tools guide names the usual cause, a time or memory limit reached before the first plan.
  • INFEASIBLE. With the capital budget cut to $5,530k, even the must-do projects ($7,630k) do not fit, with all four tranches ($2,000k) drawn. No plan exists, and CP-SAT proved it.
  • MODEL_INVALID. A row with coefficients of $2^{61}$ on a variable that can reach 4 could overflow, so the model is refused before any search, and validate() names the row.


So a program tests the status first, as the OR-Tools example did, and reads values only for OPTIMAL or FEASIBLE (and says which, because a FEASIBLE plan may not be the best). The lesson's model, solved in full:

The planners draw three tranches, not four. The third $500k of credit lets in projects worth more than its $300k cost; the fourth would not. Three ways to read a solution:


  • solver.value(expr) returns the value of a variable or of any linear expression, as a Python int. The program asks for the capex of the plan with solver.value(capex), where capex is the sum $\sum_i \text{capex}_i x_i$ built from the model's variables, so the check uses the same expression the row used.
  • solver.boolean_value(literal) returns a Boolean as True or False (funded() uses it).
  • solver.objective_value and solver.best_objective_bound are properties, not methods, and are floats, because an objective may have float coefficients (lesson Objectives, integer scaling and solution callbacks).

Problem statement


A dispatch team (not GridCap) runs CP-SAT models of many shapes from one service, and the service has to tell its callers what came back. Last week it returned "plan: []" for a model the solver had refused, and the caller read that as "load nothing".

KeyValue
"status"the status's name, such as "OPTIMAL"
"plan"the sorted names whose Boolean is true, when the status carries a solution; else None
"objective"the objective value rounded to an int, when there is a solution and the model has an objective; else None
"proven"True only when the solution was proved best
"reason"for an invalid model, the solver's explanation of what is wrong; else ""

Summary


  • A CP-SAT program is a model, a solver and a status check. CpModel, new_*_var, add, CpSolver().solve(model), then the status, then solver.value.
  • Every variable is an integer with a finite domain. new_bool_var, new_int_var(lb, ub) and new_int_var_from_domain; bounds from the data, and a domain beyond about $\pm 4.6 \times 10^{18}$ makes the model invalid.
  • A linear constraint has whole-number coefficients. add and add_linear_constraint(expr, lb, ub); != is allowed; a float coefficient is refused with a TypeError when the row is built.
  • Read the status before you read a value. OPTIMAL and FEASIBLE carry a plan; INFEASIBLE, MODEL_INVALID and UNKNOWN do not.

Design Note: Keep a MathOpt Twin While You Learn


cpsat_models.py builds the lesson's model twice, once in CP-SAT and once in MathOpt, and first_selection.py checks that HiGHS finds the same value. While a model is new, or when you port a MILP to CP-SAT, a twin like this catches a row written wrongly in one of the two: two solvers agreeing on a value is good evidence that both models say the same thing. Once the model is trusted, the twin becomes a test (this module's tests keep it) rather than code that runs every time.
