  17. Objectives, scaling and callbacks

Two requests reach GridCap's planning team in the same week. The asset-health group wants a plan that avoids the most expected equipment failures over the next five years, and its numbers are probabilities such as 0.1701 and 0.0493, not whole $k. The steering committee wants something else: it scores each project in points of $500k of NPV, rounded, because it does not trust NPV estimates to better than that, and it asks for every plan with the best score so it can choose among them itself.

Both requests run into CP-SAT's integer world. Fractional data has to become whole numbers without changing the answer, and "every best plan" needs a way to watch the solver's solutions as it finds them. This lesson covers the objective, the scaling, and the solution callback, a piece of your code that the solver calls each time it finds a solution.

GridCap is a fictional utility's portfolio, generated for this course; the failure probabilities come from its invented asset data, and the scoring rule is invented for the lesson.

The Model

Both requests use lesson Native logic: AddBoolOr, AddImplication, OnlyEnforceIf's model (the selection with crew rows and native logic for the parent and alternative rules) with the credit line closed, $k = 0$, and a new objective.

New parameters. $q_i \in [0, 1]$, the probability that the asset project $i$ works on fails in the next five years, given that it is working now, from its Weibull curve (lesson Predictive vs. prescriptive: where PoF/RUL predictions stop and optimization starts): $q_i = \dfrac{F(a_i + 5) - F(a_i)}{1 - F(a_i)}$ with $F$ the curve and $a_i$ the asset's age. $s_i = \operatorname{round}(v_i / 500)$, the committee's score of project $i$, in points.

One Linear Objective, and OPTIMAL Means Within the Gap Limit

A CP-SAT model has at most one objective, set with model.maximize(expr) or model.minimize(expr), where expr is a linear expression. A second call replaces the first; model.clear_objective() removes it, and model.has_objective() says whether there is one. After a solve, solver.objective_value is the plan's value and solver.best_objective_bound the best value no plan can beat: for a maximization, an upper bound, as in lesson Best bound, incumbent, absolute and relative gap.

How close the two must be before CP-SAT stops is a parameter, relative_gap_limit (default 0) or absolute_gap_limit (default $10^{-4}$, so for a whole-number objective, an exact proof). The gap is

for objective $O$ and bound $B$. With a gap limit of 1%, CP-SAT stops at a plan $980k below the true optimum and still says OPTIMAL. The status means "optimal within the gap limit you set", the same convention lesson What "optimal at 0.01%" means on a $2B portfolio described for MILP solvers. A program that sets a gap limit compares objective_value with best_objective_bound to know how far from proven it is.

The last line replaces the objective with minimize(sum of x), the fewest projects that keep every rule. The answer, 39, is the number of must-do projects on GridCap medium: the rules force those and nothing else.

Scale a Row Exactly, With a Whole-Number Multiplier

Lesson Integer and Boolean variables, linear constraints over integers showed that model.add refuses a fractional coefficient. The fix is the one the OR-Tools guide Solving an Optimization Problem uses: multiply the whole row by a number that clears the fractions. Its first constraint is $x + 3.5y + 1.5z \le 25$; times 2, it is $2x + 7y + 3z \le 50$, which allows exactly the same whole-number points. The example, adapted:

For any row with decimal data the multiplier is the least common multiple (LCM) of the coefficients' denominators: write each coefficient as a fraction in lowest terms ($1.5 = 3/2$, $0.75 = 3/4$), and take the smallest number every denominator divides. Multiplying by it makes every coefficient whole. The right-hand side may still be fractional, and then there is one more step, which is safe because the left side is now a whole number for every plan: a whole number is at most $30.4$ exactly when it is at most $30$, so a $\le$ row rounds its bound down, and a $\ge$ row rounds it up.

Fraction("0.75") reads the decimal text exactly as $3/4$. (Reading the float 0.75 would work here too, but a float such as 0.1 is not exactly one tenth, and Fraction(0.1) has a denominator of $2^{55}$; start from the text, or from data already in whole units.) A crew row on five yes/no jobs:

The denominators are 2, 2, 4, 2 and 2, so the multiplier is 4, and $7.6 \times 4 = 30.4$ rounds down to 30. The program checks all 32 plans: the scaled row allows exactly the plans the original does. Rounding each coefficient instead (Python's round sends 2.5 to 2, to the even neighbour) gives a different row that allows different plans, and a model built on it answers a different question.

Problem statement

A data team (not GridCap) feeds CP-SAT models from spreadsheets whose numbers have decimals: bench hours per sample, grams of protein per portion, litres per bottle. Every row has to reach the solver with whole numbers, and must allow exactly the integer points it allowed before.

Write scale_row(coefficients, rhs, sense) in scaling.py. The coefficients and the right-hand side come as decimal text ("1.25"), and sense is "<=", ">=" or "==". Return the pair (whole_coefficients, whole_bound): lists and numbers of Python ints. For a row

find the smallest whole $m \ge 1$ that makes every $m\,c_j$ whole, and return $m\,c_j$ and a whole bound $b'$ such that $\sum_j m\,c_j\,x_j \;\square\; b'$ allows exactly the same integer points. Think about each sense separately: what is the right whole bound when $m\,b$ is not whole? For "==", return None as the bound when no integer point can meet the row.

fractions.Fraction("1.25") reads decimal text exactly. The tests compare the original row and yours on every small integer point. About ten lines.

Scale an Objective Enough to Keep Its Order


An objective is more forgiving than a row, and CP-SAT treats it differently. model.maximize accepts float coefficients: cp_model.proto says the solver scales such a floating-point objective to integers itself before it searches. A row has to be exact, because a plan either keeps it or does not; an objective only has to rank the plans in the right order. The asset-health model shows both ways, and what too little scaling does:






  • Floats as given. CP-SAT finds the plan HiGHS finds, 6.3036 expected failures avoided.
  • Times 1, rounded. Every probability below 0.5 rounds to 0, so the objective cares about one project only and ignores the rest. The solver proves an optimum of the rounded model (status OPTIMAL), and that plan avoids 1.2351 failures, five fewer than the best. The status is about the model it was given; the model was wrong.
  • Times 10. Each probability keeps one decimal. The plan is close, 0.0585 failures short.
  • Times 100 and 1000. Two decimals already rank the plans as the floats do, on this data.


How much is enough depends on how close the plans' values are, so there is no universal factor. Two checks work on any model: compute the true objective of the plan the scaled model returns (as the program does) and compare it with a finer scaling, or with the float objective. The scale also has a cost. Larger coefficients mean larger sums, and every sum must stay inside CP-SAT's 64-bit range (lesson Integer and Boolean variables, linear constraints over integers); the CP-SAT Primer also warns that finer resolution can make the solve much slower, so use the coarsest scale that keeps the plan's true value, and test it.


A Solution Callback Sees Every Improving Plan


When CP-SAT optimizes, it finds a first plan and then better and better ones until it proves the last one best. A solution callback lets your code see each of them: subclass cp_model.CpSolverSolutionCallback, write on_solution_callback, and pass an instance to solver.solve(model, callback). Inside it, self.value(v), self.boolean_value(v), self.objective_value and self.best_objective_bound read the solution just found. The printer below is adapted from the OR-Tools example that prints intermediate solutions; it records each solution's objective, the bound at that moment and the number of projects:






On GridCap medium the search reports 21 solutions, each better than the last. The first is already only about 1% below the bound; the last is the optimum, found while the bound was still $179k above it. The proof came after the last solution, which is why the callback never sees the bound reach the objective. The run uses one search worker, and the second run produced exactly the same sequence; with several workers the solutions arrive in an order that can change from run to run (lesson Deterministic time, seeds and reproducible runs).


The callback can also end the search. self.stop_search() asks the solver to stop; the solve then returns the best plan so far, with status FEASIBLE:






Compare it with the gap limit of the first section: the parameter stops with OPTIMAL, the callback with FEASIBLE. The callback is the tool when the stopping rule is your own (a target value, a deadline from a business calendar, a plan that passes a check the model cannot state). Keep its work small: the solver waits for your Python code at every solution, and the Primer notes that a slow callback slows the solve.

Every Optimal Plan: Optimize, Fix the Objective, Enumerate


solver.parameters.enumerate_all_solutions = True makes CP-SAT report every solution of a model to the callback, not just improving ones. The OR-Tools guide's example lists all 18 assignments of $x, y, z \in \{0, 1, 2\}$ with $x \ne y$ this way. The parameter's documentation in sat_parameters.proto has two conditions that matter here:


  • it enumerates the solutions of a problem without an objective;
  • presolve can remove feasible solutions, so when this parameter is on and keep_all_feasible_solutions_in_presolve is unset, CP-SAT sets it to true for you.


So "every optimal plan" takes two solves. The first finds the best score $S^*$. The second adds the row $\sum_i s_i x_i = S^*$ (at_best in the model), removes the objective, and enumerates; every solution of that model is an optimal plan of the first. The collector is adapted from the OR-Tools example search_for_all_solutions_sample_sat.py:








Nine plans score the best 52 points. They share 13 projects and differ in the rest, and their NPVs range from $24,645k to $25,190k: the committee's rounding hides a $545k difference, which is exactly the information it needs to choose. On GridCap tiny the program also checks the method against brute force: of all $2^8 = 256$ subsets of the 8 projects, the ones that keep every rule and reach the best score are the same 5 plans.


Three details make the method sound:


  1. Prove the optimum first. If the first solve stops at FEASIBLE, $S^*$ may not be the best score, and the "optimal plans" are only the plans with that score. The program refuses to go on without OPTIMAL (and with a gap limit, OPTIMAL is not a proof; leave it at 0 here).
  2. Remove the objective. The last line of the output is the same enumeration with the objective left on: the solver reported 2 solutions, the improving ones, and the 9 tied plans never appeared.
  3. Count plans, not solutions. A solution assigns every variable. If the model has variables outside the plan (here the tranche count $k$, fixed at 0), two solutions can carry the same plan, so the program keeps the set of distinct plans. The parameter's documentation adds that with several workers the same solution may be reported more than once; one worker avoids that, and the set would absorb it anyway.


If the tied plans are too many to list, add a tie-break to the model instead, for example "best score, then highest NPV" as a second solve with the score fixed (lesson Prioritized objectives with add_auxiliary_objective does this in MathOpt), or stop the enumeration after a number of plans with stop_search.

  • Scale a row exactly, with a whole-number multiplier. The LCM of the denominators, and the bound rounded down for $\le$ (up for $\ge$); rounding the coefficients changes the plans a row allows.

Design Note: A Callback Observes; It Does Not Model


CP-SAT's callbacks read solutions and can stop the search; they cannot add a constraint while the solver runs (the Primer says so explicitly: no lazy constraints). Keep it that way in your own code. A rule that matters to the plan belongs in the model, where the solver can reason with it and prove the optimum under it; a callback that throws away solutions it dislikes leaves the solver proving optimality of a model that is not the one you meant. Use the callback for what only it can do: watching, recording, and deciding when to stop.
