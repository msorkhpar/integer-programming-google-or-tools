  16. Common and solver-specific parameters

GridCap's planning service now takes its solver from configuration, as lesson Switching solvers: HiGHS, SCIP, CP-SAT, GLOP, Gurobi advised. The first night it runs on SCIP instead of HiGHS, it works. The first night someone sets threads: 4 for a faster run, the HiGHS deployment crashes with AttributeError: 'StatusNotOk' object has no attribute 'canonical_code', a message that says nothing about threads, HiGHS or what to change.

MathOpt's SolveParameters holds two kinds of setting. Common parameters (time_limit, threads, relative_gap_tolerance, ...) have one name for every solver, and MathOpt translates them. Solver-specific parameters are each solver's own options, passed through untouched. A solver that cannot honour a common parameter refuses the whole solve. This lesson measures which solver refuses what in OR-Tools 9.15, teaches you to read the refusal (which this version hides), and shows when to reach past the common names to a solver's own options. GridCap is a fictional portfolio.

Common Parameters Have One Name for Every Solver, and Each Solver Accepts Only Some

mathopt.SolveParameters is a dataclass; you pass the fields you want and leave the rest None, which means "the solver's own default". Its docstring describes each common field; grouped by purpose, they are:

GroupFields
Stoppingtime_limit (a timedelta), iteration_limit, node_limit, solution_limit, cutoff_limit, objective_limit, best_bound_limit
Optimalityrelative_gap_tolerance, absolute_gap_tolerance (lesson Best bound, incumbent, absolute and relative gap)
Machinethreads, random_seed
Outputenable_output (print the solver's log), solution_pool_size (lesson Reading SolveResult: termination, primal and dual solutions, statistics)
Algorithmlp_algorithm (lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP), and four efforts: presolve, cuts, heuristics, scaling

The four efforts take an Emphasis: OFF, LOW, MEDIUM, HIGH or VERY_HIGH. The Emphasis docstring sets the rule: a solver without the feature accepts only None (some also accept OFF), and a solver that cannot turn the feature off refuses OFF.

"Common" means the name is shared, not that every solver honours it. The program asks each solver for each parameter, one solve per cell, and records whether mathopt.solve ran or raised:

The first four columns solve the LP relaxation, the last three the MILP. What to take from it:

  • Only three parameters work everywhere: time_limit and the two gap tolerances. The MathOpt docstring says time_limit is always passed to the solver; a job that must run on any solver can rely on those three and nothing else.
  • HiGHS refuses threads, even threads=1, and solution_pool_size, cuts, and two stopping values, cutoff_limit and objective_limit; on a MILP it also refuses a third stopping value, best_bound_limit, and iteration_limit and lp_algorithm. It is the course's default solver, so these are the refusals you will meet first.
  • CP-SAT refuses the LP-flavoured settings (iteration_limit, lp_algorithm, scaling), and node_limit, heuristics and the objective and bound limits: it is not an LP-based branch-and-bound solver.
  • PDLP refuses most of the list. It takes the gaps, a time or iteration limit, threads and solution_pool_size.
  • SCIP accepts the most on a MILP, and refuses only three of the stopping values: iteration_limit, objective_limit and best_bound_limit.
  • A refusal is about the pair (solver, model). HiGHS takes lp_algorithm and iteration_limit on the LP and refuses them on the MILP.

Values are checked too, by MathOpt itself, for every solver: threads=0, a negative time_limit or a negative gap is refused before any solver sees it (the next section shows the messages).

Problem statement

An airline's crew-pairing service runs on whichever solver its configuration names, and its operators set four things: a time budget in seconds, a relative gap, a thread count and a random seed. They can also ask a MILP solve to stop at its first plan, for a quick feasibility check. The service must never send a parameter the chosen solver refuses, because in OR-Tools 9.15 a refusal stops the solve.

Write params_for(solver, seconds, rel_gap, threads, seed, first_plan=False) in params.py. It returns a mathopt.SolveParameters with:

  • time_limit set to seconds as a datetime.timedelta, and relative_gap_tolerance set to rel_gap, for every solver;
  • threads set to threads, except for HiGHS, which refuses the common parameter;
  • random_seed set to seed, except for PDLP, which refuses it;
  • solution_limit=1 when first_plan is true, for HiGHS, SCIP and CP-SAT only (GLOP and PDLP solve LPs and refuse a solution limit).

Every field you do not set stays at its default, None, which means the solver's own default. The tests build the parameters for each solver and solve a model with them, so a refused setting shows up as an exception from mathopt.solve.

A Refusal Is Raised as an AttributeError in OR-Tools 9.15, and Its Reason Is on __context__


A refused solve raises an exception from mathopt.solve; it never returns a result. MathOpt meant that exception to be a standard Python one: its solve.py catches the C++ error (a StatusNotOk, which carries an absl status code and a message; absl, short for Abseil, is Google's open-source C++ library that OR-Tools' C++ code uses, and a status code is its number for the kind of error) and converts it, by the table in its errors.py:


C++ status codePython exception MathOpt raises
INVALID_ARGUMENT (3)ValueError
FAILED_PRECONDITION (9)AssertionError
UNIMPLEMENTED (12)NotImplementedError
INTERNAL (13) and anything elsemathopt.InternalMathOptError (a RuntimeError)


In OR-Tools 9.15 the conversion itself fails. It reads an attribute, canonical_code, that the StatusNotOk class in the installed pybind11_abseil does not have, and the AttributeError from that line is what reaches you. Python keeps the exception that was being handled when a new one is raised as the new one's __context__, so the real error is still there:




too_many is SolveParameters(threads=2). The hidden StatusNotOk has a code (3, which is INVALID_ARGUMENT) and a message, the solver's own reason. Look for it on __context__, not on __cause__: nothing raised the AttributeError from the real error, so __cause__ is empty. (Earlier lessons printed str(error.__context__), which is the message with the code's name appended in brackets.) The same bug hides every refusal of this module: GLOP's "does not support integer variables" in lesson Switching solvers: HiGHS, SCIP, CP-SAT, GLOP, Gurobi, the duplicate names of lesson Model, variables, constraints, objective, and each -- in the grid above: every one of them raises the same AttributeError, with the reason only on __context__.


You do not have to live with the AttributeError. A small wrapper does the conversion MathOpt meant to do, with MathOpt's own table (mathopt.status_proto_to_exception), and leaves any other AttributeError alone:



With it, every refusal reads as what it is:




Every refusal here is INVALID_ARGUMENT, so a ValueError: the request was wrong, and retrying it unchanged will fail again. That is the distinction a service needs. A ValueError from solve is a configuration or modeling error, to report and fix; an InternalMathOptError is a solver failure, which may be worth one retry; and a TerminationReason (lesson Reading SolveResult: termination, primal and dual solutions, statistics) is an answer, not an error. The wrapper is written so it keeps working when a later OR-Tools fixes the bug: then the except AttributeError never fires and MathOpt raises the right exception itself.


Read a message for what it says, too. "Not supported for HiGHS" means the parameter is wrong for that solver; "invalid parameters" with a SolveParameters. prefix means the value is wrong for every solver; "does not support integer variables" means the model is wrong for that solver.

Problem statement


A logistics platform logs every solve that MathOpt refuses, and its on-call engineers want one line per refusal: the status code's name and the solver's message. In OR-Tools 9.15 a refusal reaches you as AttributeError: 'StatusNotOk' object has no attribute 'canonical_code', and the real error is on the exception's __context__: an object with an integer code and a message. A later OR-Tools that fixes the bug raises MathOpt's own exception instead, whose message ends with  (was C++ INVALID_ARGUMENT) or another code's name.


Write refusal(error) in refusal.py, returning (code_name, message):


  • When error.__context__ has a code and a message, return the code's name from CODE_NAMES (or "UNKNOWN" for a code not in it) and that message as it is.
  • Otherwise, when the error's text ends with  (was C++ NAME), return NAME and the text before that suffix.
  • Otherwise return "UNKNOWN" and the error's text, str(error).


CODE_NAMES is given: it maps the absl status codes MathOpt uses to their names.

Solver-Specific Parameters Are Each Solver's Own Options, and They Win Over Common Ones


Each solver has far more settings than the common list. SolveParameters has one field per solver for them, each in that solver's own message type:


FieldTypeHow a setting is written

The SolveParameters docstring states two rules this section checks: a value set both as a common and as a solver-specific parameter takes the solver-specific one, and the specific parameters of solvers other than the one in use are ignored. The program runs one option per solver, then each rule, on GridCap medium where a node limit has something to stop:




(run solves and prints the reason, the limit, the objective and, for HiGHS, the node count.) Line by line:


  • The first two lines stop at the same place and find the same plan: HiGHS's own mip_max_nodes is what the common node_limit becomes. But the result's limit differs. Set through the common name, MathOpt knows why HiGHS stopped (NODE); set as a HiGHS option, it does not (UNDETERMINED). A handler that reports the limit (lesson Reading SolveResult: termination, primal and dual solutions, statistics) loses information when a limit is set the specific way, so prefer the common name when one exists. SCIP's adapter reports NODE either way.
  • CP-SAT and GLOP take their options as fields: stop_after_first_solution stopped CP-SAT at its first plan, and use_dual_simplex switched GLOP to the dual simplex method.
  • Both set, the specific one wins: with node_limit=1 and mip_max_nodes=50, HiGHS searched 51 nodes, not 1, and still reported the limit as NODE.
  • Other solvers' options are ignored, silently, however wrong their values. That is what lets one SolveParameters carry settings for several solvers, and also why a Gurobi setting does nothing on HiGHS.
  • A misspelled option of the solver in use is refused, with the solver's message. The common names are checked by MathOpt; the specific names are checked only by the solver, and only when it runs.


Where the specific option names come from: HiGHS's option list in its own documentation, SCIP's parameter list (names like limits/nodes, limits/gap), and the .proto files in OR-Tools for CP-SAT, GLOP and PDLP. They change between solver versions, so pin the solver version with the code that sets them.


HiGHS Fixes Its Thread Count at the First HiGHS Solve of a Process


HiGHS's refusal of threads says the setting "must be set using globals". HiGHS also has an option named threads of its own, and its behaviour explains the message:




The first HiGHS solve in the process set the thread count to 1, and a later request for 2 was refused with an INTERNAL error, which solve_or_explain would raise as InternalMathOptError. The refusal's "globals" and this behaviour point the same way: HiGHS's thread count is a setting of the whole process, fixed by its first solve, not of one solve. For a service that means: decide HiGHS's thread count once, at start-up, and pass the same value on every solve or none at all. For reproducible runs, which need a fixed thread count (section 10), this is the setting to pin.


A Cutoff Stop Is Reported by the Solver and Unreadable in the 9.15 Wrapper


One more wrapper bug sits in the result, not the request. cutoff_limit asks the solver to give up once it proves no plan can reach that value (lesson Stopping on gap, time, nodes or solution count). The SolveParameters docstring says such a stop ends NO_SOLUTION_FOUND with the limit CUTOFF. SCIP and CP-SAT accept the parameter, so the program sets a cutoff below and above GridCap small's optimum of $22,532k:






A cutoff the optimum beats changes nothing. A cutoff above the optimum makes both solvers stop as documented, and the result never reaches you: MathOpt's result protocol numbers the cutoff limit 12 (LIMIT_CUTOFF in result.proto), the Python Limit enum has no member for it, and parsing the result raises ValueError. Unlike the parameter refusals, this one has no __context__ to read; the solve ran and its answer is lost. In OR-Tools 9.15, treat a ValueError naming "not a valid Limit" from a solve with a cutoff as "no plan reaches the cutoff", or leave cutoff_limit unset.


Summary


  • Common parameters have one name for every solver, and each solver accepts only some. Only time_limit and the two gap tolerances worked on every solver here.
  • HiGHS refuses threads, solution_pool_size, cuts, cutoff_limit and objective_limit (and on a MILP best_bound_limit, iteration_limit and lp_algorithm); CP-SAT refuses node_limit and the LP settings; PDLP refuses most of the list. Refusals depend on the model too.
  • A refusal raises an exception before solving. In OR-Tools 9.15 it is an AttributeError; the real error is on __context__, with .code and .message, and mathopt.status_proto_to_exception turns it into the ValueError MathOpt meant.
  • Solver-specific parameters are each solver's own options. They win over common ones, other solvers' options are ignored, a misspelled name is refused, and a limit set this way can come back as UNDETERMINED.
  • HiGHS fixes its thread count at the first solve of a process; later solves must ask for the same count or none.
  • A cutoff stop raises ValueError: 12 is not a valid Limit in OR-Tools 9.15.

Design Note: Build Parameters Per Solver, in One Place


The OR-Tools sample facility_lp_benders.py has a function that returns a different SolveParameters for each solver it supports, and raises for any other. That is the shape to copy. A planning service keeps one function, params_for(solver, settings), that turns its own settings (a time budget, a gap, a thread count) into what each solver accepts, skips what a solver refuses, and is tested by one solve per solver. Everything else in the service passes the solver and the settings through without looking at them. When a new OR-Tools release changes what a solver accepts, the grid program above finds it and this one function changes.
