  15. Switching solvers

GridCap's planning service runs the selection model on HiGHS. A colleague asks for a second opinion from SCIP before a board meeting, finance wants the LP budget prices from GLOP, and the vendor evaluation needs a Gurobi run. With MathOpt that is the same model handed to four solvers, and the code change is one argument. What changes with the solver is everything around that argument: which models it accepts, what it returns, and how much of its answer you can trust.

This lesson hands one GridCap model to every solver OR-Tools 9.15 ships, as an LP and as a MILP, and reads what comes back. The solver names follow MathOpt's SolverType: GLOP (Google's simplex LP solver), PDLP (Google's first-order LP solver, lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP), HIGHS (the open-source LP and MIP solver this course uses by default), GSCIP (SCIP, an open-source MIP solver, through Google's wrapper) and CP_SAT (Google's constraint-programming solver over integers, taught from lesson Integer and Boolean variables, linear constraints over integers). GridCap is a fictional portfolio.

The Model

Both models are GridCap small's project-selection model of lesson Model, variables, constraints, objective.

Sets. $P$ the candidate projects; $Y$ the plan's years; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$.

Parameters. $v_i$, the NPV of project $i$ at its earliest start ($k, an integer); $c_{i,y}$, what it spends in year $y$ ($k, an integer); $B_y$, the budget of year $y$ ($k).

Variables. MILP: $x_i \in \{0, 1\}$ for every $i \in P$. LP relaxation: $0 \le x_i \le 1$.

The Solver Is an Argument to solve, Never Part of the Model

selection.build returns a model that names no solver. The program builds both versions once and hands each to all five solvers, catching the solves that are refused:

The solve here is selection.solve, which calls mathopt.solve and keeps the bundled HiGHS's stray output off the screen (lesson Model, variables, constraints, objective). The solver went in as a value, S.GLOP through S.CP_SAT, and nothing else in the program changed. Several OR-Tools samples (time_indexed_scheduling.py, facility_location.py, writing_seminar.py) do the same at the command line: their solver is a flag whose type is SolverType, so a run can switch solvers without an edit. That is the pattern to copy: the model builder knows nothing of solvers, and the solver is configuration.

The grid answers four questions about the solvers, one per section below: which model types each accepts, what each returns, where CP-SAT's answer goes wrong, and which solvers you can use at all.

Each Solver Accepts Only the Model Types It Can Solve, and Says So Before Solving

The MILP column shows the first rule: GLOP and PDLP solve LPs only, and refuse a model with an integer variable. The refusal is an exception from mathopt.solve, raised before any work, never a status; in OR-Tools 9.15 its message is hidden on the exception's __context__ (lesson Common vs. solver-specific parameters, and what each solver rejects). It is a good refusal: it stops you from getting an LP answer to a yes/no question.

The LP column shows the second: only some solvers return dual values. GLOP and HiGHS return duals and a basis (both use simplex); PDLP returns duals but no basis (it does not use simplex); SCIP solves the LP and returns no duals at all. The SolverType docstring says it plainly for SCIP: no dual data for LPs, prefer GLOP. So "read the budget's shadow price" (lesson Reading SolveResult: termination, primal and dual solutions, statistics) is a job for GLOP or HiGHS, and a program that switches solver must check has_dual_feasible_solution() rather than assume.

The three MILP solvers agree: the same value, $22,532k, and the same 25 projects. Agreement on a small model is a cheap and strong test of a model; when a solver change moves the objective, the first suspects are a tolerance (lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP) and a model feature one solver reads differently, which is what CP-SAT does in the LP column.

CP-SAT Needs Integers, and Rounds a Continuous Model Without Warning

The LP column's last line is wrong. CP-SAT reported OPTIMAL 22,532.0 for the LP relaxation, whose optimum the other four agree is $23,669.5k. It solved a different model. CP-SAT works over integers only; the CP-SAT page of the OR-Tools documentation says to scale any non-integer terms to integers before using it, and MathOpt's SolverType docstring calls its handling of continuous variables experimental support to "rescale and discretize". The program shows what that did here:

The LP's optimum funds four projects in part. CP-SAT returned no fractions at all: every $x_i$ came back 0 or 1, so it answered the MILP, and called that the optimum of the LP. A model with one continuous variable shows the same thing on a smaller scale:

HiGHS sets the continuous a to 8.6216, where the cap row is tight. CP-SAT stopped at a = 8, a whole number, and still said OPTIMAL. Its value is a feasible plan, so nothing breaks; it is just not the optimum of the model you wrote, and no field of the result says so. The rule that follows: hand CP-SAT only models whose variables are all integer, with integer data where you can (GridCap's money is in whole $k for that reason), and send anything with a continuous variable to HiGHS or SCIP. Problem statement

A city's parks department picks which playground renovations to fund this year. The candidates sit in a pandas DataFrame with the columns project_id, cost and value (both in $k) and must_do (a bool: safety work that must be funded). The department wants one function it can run on HiGHS, SCIP or CP-SAT and get the same answer.

The model, with $P$ the rows of the DataFrame and $B$ the budget:

Write solve_selection(df, budget, solver) in selection.py. It returns a pair: the objective value of the plan, and the sorted list of the project_ids it funds (those whose $x_i$ is above 0.5).

  • solver is a mathopt.SolverType. If it is one of LP_ONLY (GLOP and PDLP, which refuse integer variables), raise ValueError with the solver's name in the message, before building or solving anything, so the caller never meets OR-Tools' own refusal.
  • If the solve ends with any reason other than OPTIMAL, raise RuntimeError with the reason's name in the message.

Five Solvers Are Built Into the pip Package, and Gurobi Needs Its Own Library and License


SolverType lists more solvers than the OR-Tools wheel contains. Asking for each one shows which are there:






SCIP, GLOP, CP-SAT, PDLP and HiGHS are compiled in. GLPK, OSQP, ECOS, SCS and Santorini have a SolverType but no code behind it in this build: the full message adds that support for the solver has not been compiled, so naming one is refused at once.

Summary


  • The solver is an argument to solve, never part of the model. Build once, solve with any SolverType, and make the solver configuration.
  • Each solver accepts only the model types it can solve. GLOP and PDLP refuse integer variables, with an exception raised before solving.
  • Only GLOP, HiGHS and PDLP return LP duals; SCIP and CP-SAT do not, and no solver returns duals for a MILP.
  • CP-SAT needs integers. Handed a continuous variable, it rounds it and still reports OPTIMAL; give it all-integer models only.
  • Five solvers are compiled into the pip package: GLOP, PDLP, HiGHS, SCIP, CP-SAT. Gurobi needs its own library and license, and does not run through MathOpt in the course runner.

Design Note: Test a Model on Two Solvers


Switching solver costs one argument, so use it in tests. A test that solves a small instance with HiGHS and with SCIP and asserts the objective values agree (within a tolerance, lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP) catches two kinds of bug at once: a model that a solver reads differently than you intended (the CP-SAT case above) and a solver bug in a new release. It does not catch a model that is wrong in the same way for every solver; that needs hand-built feasible and infeasible plans, as the course's modeling practices use. Section 12 builds both kinds of test into the planning service.
