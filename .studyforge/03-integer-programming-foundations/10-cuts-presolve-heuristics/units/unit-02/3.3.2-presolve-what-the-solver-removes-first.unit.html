  19. Presolve

GridCap's five-year capital plan for the medium portfolio is a selection model with 400 projects and 80 rows. Its HiGHS log says the solver searched a model with 17 rows and 172 columns. A planner who sees that asks two fair questions: what happened to the other 228 projects, and how do we know the solver did not throw away the best plan with them? The answer is presolve, the first thing a MIP solver does, and this lesson rebuilds its main rules in a few dozen lines of Python, runs them on the same model, and checks the answer. GridCap is a fictional utility; its numbers are teaching data.

The Model

The five-year selection model, selection.five_year. Each project is funded or not, and if funded it starts at its earliest start year and spends its cost profile from there. The board approves budgets five years ahead, so only the first five years of the plan have a budget row; spend after them is not capped in this model.

Sets. $P$ the projects; $Y = \{2027, \dots, 2031\}$ the five plan years; $M \subseteq P$ the must-do projects; $C \subseteq P$ the child projects, each with a parent $p(c)$; $\mathcal{G}$ the alternative groups, each a set of projects of which at most one may be funded.

Parameters. $v_i$, the NPV of project $i$ at its earliest start ($k); $c_{i,y}$, what project $i$ spends in year $y$ if it starts at its earliest start ($k, 0 in a year it is not worked); $B_y$, the budget of year $y$ ($k).

Variables. $x_i \in \{0, 1\}$ for every $i \in P$: 1 if project $i$ is funded.

The must-do rows are written as constraints, not as bounds on purpose: a planner can then list them, name them and switch one off, and presolve turns them into bounds anyway, as this lesson shows.

Presolve Rewrites the Model Into a Smaller One With the Same Optimal Value

Presolve is a set of reductions, each a rule that rewrites the model into a smaller or tighter one, applied again and again until none applies. A reduction may fix a variable, delete a row, or change a coefficient. Each must keep at least one optimal plan of the original model, so the optimal value never changes. After the solver has solved the smaller model, postsolve undoes the reductions in reverse, turning the answer into a plan for the model you wrote.

HiGHS prints its presolve in the log (lesson Reading an LP solver log read the same lines for an LP):

Each of the first two lines is the size after a round of reductions; rows 17(-63) reads "17 rows left, 63 removed"; <t> stands for a time, masked because it changes on every run. The last block is what the search actually works on. Lesson Reading a full MIP log line by line reads the rest of this log, including the line about the integral objective.

HiGHS does not say which rule removed what. To see that, presolve.py implements four reductions on a plain 0-1 model: a BinaryModel holds the objective, the rows (each $\sum_j a_j x_j \le b$ or $= b$) and each variable's bounds lo and hi. from_selection reads the MathOpt model into one. Run until nothing changes, it prints each pass:

Four rules take the model from 80 rows and 400 columns to 35 and 199. HiGHS's documentation names the first two kinds in its description of one of its presolve modes for LPs, the "initial sweep": fixed variables, empty rows and columns, rows with a single coefficient, and rows that the bounds of their variables already satisfy. HiGHS gets further, to 17 and 172, with more reductions than these four; the sections below explain the four, one per heading, and the last section of the lesson compares the two.

A Row With One Variable Is a Bound, and a Fixed Variable Is a Number

must_P002 reads $x_{P002} = 1$. A row with a single variable is not a constraint between decisions; it is a bound on one variable, and here both bounds are 1. So presolve sets $lo = hi = 1$ and deletes the row. The same goes for a one-variable $\le$ row: $a\, x_j \le b$ with $a > 0$ and $b / a < 1$ leaves only $x_j = 0$ for a binary; with $b / a \ge 1$ it says nothing and goes.

A variable whose bounds are equal is no longer a decision. Presolve substitutes it: in every row it appears in, its term moves to the right-hand side, and its objective term becomes a constant. Once a must-do's $x_i = 1$ is substituted, each budget row it spends in no longer mentions it, and that row's right-hand side is smaller by what the project spends that year.

That is where the 39 singleton rows of pass 1 went, and with them 39 columns. Substitution can make new singleton rows: an after row $x_c - x_{p(c)} \le 0$ whose parent is fixed at 1 becomes $x_c \le 1$, which says nothing, and goes in the next pass. Reductions feed each other, which is why presolve runs in passes.

Activity Bounds Prove a Row Redundant or Fix a Variable

The activity of a row is its left-hand side, $\sum_j a_j x_j$. Over the variables' bounds it has a least and a most value: each positive coefficient contributes least at the variable's lower bound and most at its upper bound, and a negative coefficient the other way round.

Three conclusions follow for a row $\sum_j a_j x_j \le b$:

  • If $\overline{L} \le b$, no choice of the variables can break the row. It is redundant: delete it. That is what happened to budget_2027: every project that spends in 2027 adds up to $41,990k, under the $42,810k budget, so funding all of them still fits.
  • If $\underline{L} > b$, no choice satisfies the row: the model is infeasible, and presolve can say so before any search. presolve raises an error then.
  • If setting one variable to its upper bound pushes even the least activity over $b$, that variable can only take its lower bound. For a binary with $a_j > 0$ and $lo_j = 0$: if $\underline{L} + a_j > b$, then $x_j = 0$. With $a_j < 0$ the same argument fixes $x_j = 1$.

The third rule never fires on the five-year model, so here it is on a three-project row where it does. PA is a must-do:

The must row fixes PA at 1. Now the least activity of the budget row is 6, and adding PB (4) or PC (3) would make it 10 or 9, over 8. Both are fixed at 0; the budget row then has nothing left in it and goes. Presolve solved this model on its own: only one plan is feasible.

A Variable That Only Helps Is Set to Its Best Value


Look at a project that spends nothing in the five plan years, and is in no after or alt row. Its column has no entries at all, and its objective coefficient is positive. Funding it adds value and touches no row, so a plan without it is never better than the same plan with it. Presolve sets it to 1.


The general rule is dual fixing (it reasons about the objective, the "dual" side, rather than about the rows alone). For a maximization with $\le$ rows: if $v_j \ge 0$ and every coefficient of $x_j$ in the rows is $\le 0$, raising $x_j$ never hurts the objective and never tightens a row, so $x_j = hi_j$. A parent appears in its child's after row with coefficient $-1$, so a parent with no other entries qualifies too.



On the five-year model, this is the reduction that removes most columns:



Of the 162 variables fixed without a must-do row, 142 belong to projects that start too late to spend in the plan years. The other 20 spend in the plan years, but by the rule they can only have had coefficients $\le 0$ in the rows still present: they spend only in budget_2027, which presolve had already deleted, or they appear only as a parent. A project that spends nothing but sits in an alternative group is not fixed: its coefficient in the alt row is $+1$, and funding it would block its alternatives.


Dual fixing keeps at least one optimal plan, but not necessarily all of them. If two plans have the same best value and one leaves a free project out, presolve's version keeps it in. For a model that must list every optimal plan, this matters; for one that needs a single best plan, it does not.

Problem statement


A vegetation-management model maximizes $\sum_j c_j x_j$ over $x_j \in \{0, 1\}$ under rows $\sum_j a_{r,j}\, x_j \le b_r$. Some $c_j$ are negative: optional overtime shifts cost money and are worth taking only when they let other work in. Write the dual-fixing reduction.


Write dual_fixings(objective, rows) in dual.py. objective maps each variable to $c_j$; rows maps each row name to a pair (coefs, rhs), where coefs maps the row's variables to their $a_{r,j}$ (a variable in no row has no entry anywhere). Return a dict of the variables to fix:



where $r$ runs over every row that contains $x_j$. This is the lesson's rule, $c_j \ge 0$ as in its presolve code: a variable worth exactly 0 whose entries are all $\le 0$ is fixed at 1 (funding it costs nothing and loosens its rows, so some optimal plan includes it), and a variable worth 0 with a positive entry is left free. The reference solution tests c >= 0 for the first case and c < 0 for the second. Apply the rule once, to the model as given; don't substitute and repeat.

Coefficient Tightening Makes the LP Bound Tighter Without Changing Any Plan


Some reductions remove nothing and still help: they make the LP relaxation (lesson Cutting planes: Gomory and cover cuts by hand) tighter, so its bound is closer to the best plan. Coefficient tightening is the classic one. Take a row $\sum_j a_j x_j \le b$ over binaries and a variable $x_k$ with $a_k > 0$. Without $x_k$, the row's most activity is $\overline{L} - a_k$. If that is below $b$ by $d > 0$,



then the row cannot bind when $x_k = 0$, and lowering both $a_k$ and $b$ by $d$ keeps every 0-1 point's verdict:


  • with $x_k = 1$, the row reads $(a_k - d) + \text{rest} \le b - d$, which is the original row with $d$ subtracted from both sides;
  • with $x_k = 0$, the new row reads $\text{rest} \le b - d = \overline{L} - a_k$, and the rest can never exceed its own most activity, so this holds for every point, as the original row did.


Fractional points are another matter. The row $5 P_A + 2 P_B + 2 P_C \le 6$ has most activity 4 without $P_A$, so $d = 6 - 4 = 2$:



Same 0-1 plans, and the LP bound drops from 8 to 6.5 against a best plan of 6. The point $(0.4, 1, 1)$ satisfies the old row ($2 + 2 + 2 = 6$) but not the new one ($1.2 + 2 + 2 = 5.2 > 4$): the tightened row works like a cut that presolve found for free.



The most activity is recomputed for every variable, because each change lowers it. It applies only to rows that one large coefficient dominates. GridCap's budget rows hold dozens of projects of similar size, and there it finds nothing:

Problem statement


A crew-allocation model has knapsack rows $\sum_j a_j x_j \le b$ with $a_j > 0$ and every $x_j \in \{0, 1\}$ free. Before the search, presolve should tighten them, so the LP relaxation gives a better bound with the same 0-1 plans.


Write tighten(coefs, rhs) in tighten.py. Go through the variables in sorted order of their names. For each variable $k$, with the row as it is at that moment, compute



and if $d > 10^{-9}$, replace $a_k$ by $a_k - d$ and $b$ by $b - d$. Return the pair (new_coefs, new_rhs): a new dict, with the dict you were given left as it was. Each later variable sees the row after the earlier changes.

Postsolve Puts the Plan Back Together


The presolved model is a model of its own, over the 199 variables left, with the value of the fixed ones as a constant. Solve it, put the fixed values back, and check the result against the model you wrote:



Both solves use relative_gap_tolerance=0.0, which makes HiGHS prove the optimum exactly rather than stop within 0.01% of it (lesson Reading a full MIP log line by line shows the difference). The presolved model's value plus the constant equals the full model's: no plan was lost. In a real solver, postsolve is more involved: a reduction such as coefficient tightening changes a row, and postsolve must also map the dual values and the bases back. For a 0-1 model's plan, putting the fixed values back is all of it.


Turning Presolve Off Changes the Work, Not the Answer


MathOpt's common presolve parameter switches HiGHS's presolve off:




The search now works on all 80 rows and 400 columns. HiGHS still counts 39 columns as "domain fixed", the number of must-do projects, each fixed at 1 by its one-variable row, but keeps them in the model. With presolve on, the same run ended with the same value after 79 nodes:



So on this model, presolve made the search smaller in rows and columns, and the search took more nodes, not fewer. That is not a contradiction: what happens after presolve (the cuts found, the heuristics' luck, the restarts lesson Reading a full MIP log line by line shows) depends on the model the search starts from, and a node count is not a time. Presolve's guarantee is the one this lesson proved, a smaller model with the same optimal value, and whether it speeds up a given model is something to measure, never to assume. (The value is 274,979 here rather than 274,999 because these runs keep HiGHS's default gap tolerance of 0.01%, the option mip_rel_gap; lesson Reading a full MIP log line by line explains it.) HiGHS's documentation says the same in general: presolve is on by default because it usually saves far more time than it costs, and the option exists for the models where it does not.


Summary


  • Presolve rewrites the model into a smaller one with the same optimal value, and postsolve maps the answer back. HiGHS's log shows the sizes; on the five-year model, 80 rows and 400 columns become 17 and 172.
  • A row with one variable is a bound, and a fixed variable is a number: it is substituted into every row and the objective.
  • Activity bounds prove a row redundant or fix a variable: $\overline{L} \le b$ deletes the row, $\underline{L} > b$ proves infeasibility, $\underline{L} + a_j > b$ fixes $x_j = 0$.
  • A variable that only helps is set to its best value (dual fixing); on the five-year model it removes 162 columns.
  • Coefficient tightening makes the LP bound tighter without changing any plan, when one coefficient dominates a row.
  • Turning presolve off changes the work, not the answer. Measure before deciding it helps.

Design Note: Write the Model Plainly and Let Presolve Simplify It


It is tempting to do presolve's work by hand: leave the must-do projects out of the model, drop the budget row that never binds. Don't. A must-do row you wrote is a rule a planner can read, test and switch off; a must-do you removed by hand is a silent assumption, and next year's data may break it. budget_2027 is redundant this year because the projects fit; next year it may bind. Presolve redoes these reductions on every solve, for free, on the data of that solve. Write the model as the business states it, and read the presolve lines of the log to see what the data made redundant.
