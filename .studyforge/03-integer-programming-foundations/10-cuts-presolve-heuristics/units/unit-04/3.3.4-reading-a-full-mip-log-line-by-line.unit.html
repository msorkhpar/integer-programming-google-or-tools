  19. Reading a MIP log

The five-year plan for GridCap medium is about to run every night. Most nights nobody will read its log. The night a planner says "the plan changed and nothing in the data did", or "it says optimal, but is it?", the log is where the answer is. Lesson Reading an LP solver log read an LP log; a MIP log has everything an LP log has, plus a table of the search: the bounds closing in, the heuristics that found each plan, the cuts, and the restarts. This lesson reads one complete HiGHS MIP log from the first line to the last, with lessons Cutting planes: Gomory and cover cuts by hand to Primal heuristics: rounding, diving, RINS behind it. GridCap is a fictional utility; its numbers are teaching data.

The Model

The five-year selection model of lesson Presolve: what the solver removes first, solved by HiGHS with its default settings.

Sets. $P$ the projects; $Y = \{2027, \dots, 2031\}$; $M \subseteq P$ the must-do projects; $C \subseteq P$ the child projects, with parent $p(c)$; $\mathcal{G}$ the alternative groups.

Parameters. $v_i$ the NPV of project $i$ ($k); $c_{i,y}$ its spend in year $y$ at its earliest start ($k); $B_y$ the budget of year $y$ ($k).

Variables. $x_i \in \{0, 1\}$ for every $i \in P$: 1 if project $i$ is funded.

On GridCap medium: 400 variables, and 80 rows (5 budget, 39 must, 18 after, 18 alt).

Ask for the Log, and Mask Only What Changes Between Runs

MathOpt hands each batch of log lines to the function passed as msg_cb. Collecting them in a list keeps the whole log, in order, for a person or a test to read:

The dup2 lines point the process's standard output at /dev/null during the solve, because the HiGHS bundled with OR-Tools 9.15 prints a stray debug line on some MIP solves, even with no log asked for: HighsMipSolverData::transformNewIntegerFeasibleSolution tmpSolver.run();. It is C output, held in a buffer and written when the program exits, so solve_with_log flushes that buffer into /dev/null (the fflush line) before it gives standard output back. The log itself arrives through msg_cb and is not affected. mask_times replaces what changes from run to run:

Everything else in this log came out the same on every run of this program on the course's runner image: same rows, same nodes, same values. The section 10 lesson Where nondeterminism comes from: threads, time limits, ties explains when a solver's search is repeatable and when it is not; the times never are.

The whole log is printed by full_log.py. The sections below take it a piece at a time, in order.

The Header and Presolve Say What the Search Will Work On

  • The first line checks the model you built: 80 rows and 400 columns, as counted above, and "400 integer variables (400 binary)". A MIP whose integer count is 0 has lost its integrality (a forgotten is_integer=True), and HiGHS would solve an LP.
  • Coefficient ranges are read as in lesson Reading an LP solver log: the smallest and largest absolute values, here spend of about $6,000k at most in the matrix, and budgets of about $40,000k on the right. Nothing spans more than five powers of ten.
  • Presolve (lesson Presolve: what the solver removes first) leaves 17 rows and 172 columns: most of the 228 removed columns are projects with nothing to decide.
  • Objective function is integral with scale 1 means every objective coefficient is an integer (after multiplying by the scale, 1 here), and every variable of the objective is integer. So every plan's value is an integer. HiGHS uses that fact at the end, as this lesson shows.

This is the model the search works on, after presolve: 172 binary columns and nothing else, so the other column counts (integer, implied int., continuous, domain fixed) are all 0.

The Legend Names Every Source of a New Plan

Each row of the table that follows starts with one of these letters when a new incumbent was found, and the letter says by what. Most name primal heuristics of lesson Primal heuristics: rounding, diving, RINS's kind: rounding (R, C, Z), sub-MIPs (L, the family of RINS), shifting and feasibility pumps. B (branching) and T (evaluate node) name plans the search itself turned up, and X a plan you supplied. Upper and lower case differ: Z is ZI Round, z is the trivial zero plan. HiGHS's option list names several of these heuristics, each with a switch: feasibility jump, RINS and RENS run by default, ZI Round and shifting only when switched on (mip_heuristic_run_zi_round, mip_heuristic_run_shifting). The letters are HiGHS's own; other solvers print other logs.

Each Row of the Table Is a Snapshot of the Search

One row is the state of the search at one moment. HiGHS's documentation does not describe this table. The meanings below come from the header, from numbers this log checks against its own report and against the SolveResult, from HiGHS's documented terms (primal bound, dual bound, gap), and, for Leaves, Expl., Cuts, InLp and Confl., from the HiGHS source code that prints the row (printDisplayLine in HighsMipSolverData.cpp). The source quoted on this page is HiGHS 1.12.0, the version whose number is in the HiGHS library OR-Tools 9.15 ships. The columns, in order:

ColumnMeaning
Srcthe source letter of a new incumbent; blank on a periodic report
Proc.nodes processed so far (79 on the last row, as the report's Nodes and node_count say)
InQueueopen nodes waiting to be explored
Leavesleaf nodes of the tree, counted from the last restart
Expl.the share of the search tree already closed, in percent
BestBoundthe dual bound: no plan is worth more (for a maximization)
BestSolthe incumbent's value, the primal bound: the best plan found so far
Gap$\lvert \text{BestBound} - \text{BestSol} \rvert / \lvert \text{BestSol} \rvert$
Cutscuts held in HiGHS's cut pool right now (lesson Cutting planes: Gomory and cover cuts by hand); not a running total
InLpcuts currently in the LP, the rows beyond the model's own
Confl.conflicts held in HiGHS's conflict pool right now (below the table)
LpItersLP iterations so far, in all LPs (9,738 on the last row, as in the report)
Timewall-clock seconds (masked here)

A conflict is a combination of variable fixings that HiGHS has found can lead to no plan worth keeping. In the source, when a node's LP is infeasible, or its bound cannot beat the incumbent, HiGHS works out which of the node's fixings caused it (addInfeasibleConflict and addBoundExceedingConflict in HighsSearch.cpp) and stores that set in its conflict pool. Other nodes that repeat the combination can then be cut off without solving their LP. Confl. is the pool's current count (getNumConflicts: conflicts added minus conflicts deleted), so like Cuts it can fall as well as rise.

The gap is the one number to watch. When it reaches the tolerance, the search stops.

The Root Rows Show Heuristics Racing the Bound Down

Every row has Proc. 0: all of this happens at the root, before the first branch. Read down:

  • z, p, J: three cheap plans (trivial zero, trivial point, feasibility jump) found before any LP is solved: LpIters is still 0. BestSol is always a value of the model you wrote, the columns presolve removed included (on the last row it is 274,979, the report's primal bound and the SolveResult's objective), so even the trivial zero plan is worth 163,973, not 0. BestBound is inf because no LP has given a bound yet, and the gap is Large.
  • R: the root LP is solved (16 simplex iterations) and its value, 275,164.826811, becomes the bound. It is the LP relaxation bound that GLOP printed in lesson Cutting planes: Gomory and cover cuts by hand (275,164.8). Randomized rounding of the LP point gives a plan worth 271,757: gap 1.25%.
  • L, L: cuts appear (906 in the pool, 39 of them in the LP) and the bound falls to 275,107.2, and two sub-MIP heuristics find 274,960 and 274,969. The gap is 0.05%.

The program log_and_result.py reads the lettered rows and recomputes each gap:

So HiGHS's gap is relative to the incumbent: $(275{,}164.827 - 271{,}757) / 271{,}757 = 1.254\%$. The log rounds it to two decimals. Notice that both sides move: heuristics push the incumbent up, and cuts push the bound down. Before any branching, the gap went from Large to 0.03%.

Problem statement

GridCap's nightly job keeps the HiGHS log of every run, and the planners want a chart of the bound and the incumbent over the search. The first step is reading one line of the progress table.

Write parse_row(line) in rows.py. A progress row is a line whose first character is a space, whose second character is the source letter or a space, and whose remainder, split on whitespace, has exactly 12 fields:

FieldProc.InQueueLeavesExpl.BestBoundBestSolGapCutsInLpConfl.LpItersTime
Example0000.00%275164.8268112717571.25%000160.1s

where Proc. is a whole number and Expl. ends in %. For a progress row, return a dict with the keys src (the letter, or "" for a blank), nodes (Proc., an int), bound and incumbent (BestBound and BestSol as float; the text inf is float("inf")), gap (the Gap as a fraction, so 1.25% is 0.0125, or None when the log prints Large), cuts and lp_iters (int). For any other line, return None.

How strict to be: the reference solution checks exactly four things, the leading space, the 12 fields, Proc. made only of digits, and Expl. ending in %, and nothing else. It takes any character in the second position as the source letter (a letter it has never seen, say Q, is still a row), and it does not check the other fields beyond converting them: on a real HiGHS row they are always numbers, inf or Large. The tests never pass a line that clears the four checks and then fails a conversion.

The Report Is the Verdict, and Optimal Means Within the Gap Tolerance



Line by line:


  • Status Optimal: the gap is within the tolerance. Not "proved best": see below.
  • Primal bound 274979: the incumbent's value. Dual bound 275006: the bound. It was 275,006.946429 in the last row; because the objective is integral, no plan can be worth a fraction, so the bound is rounded down to the integer 275,006.
  • Gap 0.00982% (tolerance: 0.01%): $(275{,}006 - 274{,}979) / 274{,}979 = 27 / 274{,}979$. The tolerance is HiGHS's default relative gap, option mip_rel_gap, documented as $\lvert ub - lb \rvert / \lvert ub \rvert$ with default $10^{-4}$, where $ub$ is the primal bound (HiGHS minimizes internally). With the unrounded bound the gap would be $27.946 / 274{,}979 = 0.0102\%$, just over it; the integral objective is what brought the gap under the tolerance at this point.
  • P-D integral is HiGHS's primal-dual integral (primal_dual_integral in its documented HighsInfo, which gives no more than the name). The source (updatePrimalDualIntegral in HighsMipSolverData.cpp) says what it is: every time the bound or the incumbent changes, HiGHS adds the seconds since the last change times the gap during those seconds. It is the area under the gap-against-time curve, small when the gap closes early. Because it is measured in seconds, it changes from run to run, so it is masked.
  • Solution status feasible, then the incumbent checked against the original model: its objective, and its largest bound, integrality and row violations, all 0.
  • Max sub-MIP depth 4: a sub-MIP heuristic (source letter L) solves a smaller MIP with many variables fixed, and that smaller MIP can run sub-MIPs of its own. In the source (solveSubMip in HighsPrimalHeuristics.cpp) each sub-MIP's depth is one more than its parent's, and the line reports the deepest nesting reached: here a sub-MIP four levels down.
  • Repair LPs 4 (0 feasible; 0 iterations): when a plan found on the presolved model breaks a bound, row or whole-number rule of the original model once presolve is undone, HiGHS tries to repair it. It rounds every integer variable, fixes it there, and solves an LP over the rest (transformNewIntegerFeasibleSolution in HighsMipSolverData.cpp). The line counts those LPs, sub-MIPs' included, and how many gave a plan; here none did, and the plans HiGHS kept came from elsewhere. The stray debug line of the first section is printed by this repair step, just before each repair LP is solved, which is why it appears on some MIP solves and not others. HiGHS's documentation describes neither line.
  • Nodes 79, matching the last row.
  • LP iterations 9738, split by what they were spent on: strong branching (trying candidate branches before choosing one, lesson Node and variable selection), cut separation, and heuristics; the other 1,292 are not broken down. Nearly half of all the LP work here was heuristics.
  • WARNING comes from HiGHS: OR-Tools 9.15 attaches to its log with a method HiGHS has deprecated. It is printed on every run, as in lesson Reading an LP solver log, and says nothing about the model.

Design Note: Keep the Log Next to the Plan


A plan without its log cannot be explained a month later. The nightly job should write the masked log to a file next to the plan, with the solver's version and the parameters. Then "the plan changed" becomes a diff of two logs: different row counts mean the data changed; same counts but a different Gap or Nodes mean the search went differently; a Status other than Optimal means it was stopped. The section 10 lesson Versioned input snapshots, pinned solvers and run manifests builds that into a run manifest.
