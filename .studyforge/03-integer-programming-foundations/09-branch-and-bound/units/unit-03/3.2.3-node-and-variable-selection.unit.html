GridCap's planners move from one capital budget to a budget for each of the five years 2027 to 2031, on the small portfolio. The model gets four more rows, and the branch-and-bound of lessons Branching on a fractional variable and Bounds, incumbents and pruning still finds the best plan. But the same search can take 147 nodes or 10,425, depending on two choices the earlier lessons made without comment: which waiting node to solve next, and which fractional variable to split. Neither choice changes the answer; both change the work, sometimes by a factor of 70. This lesson names the classic rules for each choice, runs every combination on the same model, and reads what the numbers say.

The Model

The selection model of lesson Branching on a fractional variable, with the one capital budget row replaced by one row per year. Every project starts in its earliest year, as in the one-period model, and spends its cost profile from there.

Sets. $P$, the projects (40 on small); $Y$, the plan's years (2027 to 2031); $M \subseteq P$, the must-do projects; $C \subseteq P$, the projects with a parent $p(c)$; $\mathcal{G}$, the alternative groups.

Parameters. $v_i$, the value of project $i$ ($k); $s_{i,y}$, what project $i$ spends in year $y$ if it starts in its earliest year $e_i$, that is its cost profile's entry for year $y - e_i$, or 0 when the project is not being worked on in $y$ ($k); $B_y$, the budget of year $y$ ($k).

A project's cost profile is its spend in each year of work, in order: entry 0 for its first year, entry 1 for its second, and so on. GridCap stores it with each project, and p.spend(start) turns it into a year-by-year dict. One project of GridCap small (cost_profile.py):

So $x_{P013}$ appears in budget_2028, budget_2029 and budget_2030, with coefficients 440, 330 and 240.

Variables. $x_i \in \{0, 1\}$ for every $i \in P$: 1 if project $i$ is funded.

Objective and constraints.

The rows are named budget_2027 to budget_2031; build(small, yearly=True) in selection.py (shown in lesson Branching on a fractional variable) makes them. HiGHS's optimum for this model is 22,532.

The Node Rule Decides Which Waiting Node Comes Next

Every time a node is branched, its two children join the list of waiting nodes: made, but not yet solved. The node rule (also called node selection) picks which waiting node to solve next. The three classic rules:

RuleTakes nextKept in
depth-firstthe deepest waiting node, the newest among equalsa stack (last in, first out)
best-first (best bound)the node with the highest bound, the oldest among equalsa heap ordered by bound
breadth-firstthe oldest waiting nodea queue (first in, first out)

A waiting node's bound is its parent's LP value, since its own LP is not solved yet (lesson Bounds, incumbents and pruning). In bnb.py the rule is a small class:

A list used as a stack (pop()) is depth-first: the node just pushed is the deepest one waiting, because it is a child of the node just solved. pop(0) turns the list into a queue, which is breadth-first. Python's heapq always hands out the smallest entry, so best-first stores -node.bound to get the largest bound first, and node.id breaks ties in favour of the older node. Every search in lessons Branching on a fractional variable and Bounds, incumbents and pruning was depth-first.

On tiny, best-first goes like this:

Nodes 1 and 2 both wait with the root's bound 3,770.1, so the older, node 1, goes first. After it, node 2 (bound 3,770.1) beats nodes 3 and 4 (bound 3,695.5) and is solved, at 3,054.7. Then node 3 holds the best bound and turns out to be the optimal plan. From there every waiting bound is below 3,627: node 4 is solved and pruned, and nodes 5 and 6, whose parent bound was 3,054.7, are pruned without solving their LPs at all. Five LPs instead of 21.

On the small portfolio with yearly budgets, branching on the first fractional variable each time:

nodes counts every node taken from the waiting list, LPs the ones whose LP was solved (the rest were pruned on their parent's bound), most waiting the largest size the waiting list reached, and first plan at node how many nodes were taken before the first incumbent. All three find 22,532, HiGHS's optimum. The next three rules read the table.

Depth-First Keeps Few Nodes Waiting and Reaches a Plan Quickly

Depth-first never had more than 14 nodes waiting. Each step down the tree leaves one sibling waiting, so the list holds at most about one node per level of the current path, and a 0-1 tree on 40 variables has at most 40 levels. Memory stays small no matter how big the tree grows.

It also found its first plan at node 47, against 554 for best-first. Diving fixes one more variable at every step, and with enough variables fixed the LP has no room left to be fractional, so plans appear at the bottom of the first dive. An early plan matters for two reasons: it lets the bound test start pruning (lesson Bounds, incumbents and pruning), and if the search is stopped early, there is a plan to hand the planners.

The cost is the number of nodes: 1,705, and every one needed its LP solved. Depth-first finishes one subtree before looking at any other, so if it dives into a poor region it searches that region to the bottom, with a weak incumbent that prunes little. The tiny run in lesson Bounds, incumbents and pruning did exactly that: 13 nodes under $x_{P003} = 1$ before reaching the side of the tree where the optimum was.

Best-First Solves the Fewest Nodes Because It Never Opens a Node Below the Optimum

Best-first took 1,065 nodes and solved only 587 LPs: 478 nodes were pruned on their parent's bound without an LP. There is a short argument for why best-first is economical.

Take any node whose bound is above the optimum $z^*$. No search with these branching decisions can prune it: the bound test needs an incumbent of at least its bound, and no plan is worth more than $z^*$. So every search must solve such nodes. Best-first solves almost nothing else. It always takes the highest bound, so while any waiting bound is above $z^*$ it takes one of those; once the optimum is the incumbent, every remaining bound at or below it is pruned without its LP. Apart from ties at $z^*$ itself, the nodes best-first solves are exactly the ones every search must solve.

The cost is memory and late plans. The highest bounds sit near the top of the tree, so best-first keeps going back to shallow nodes and leaves their deep children waiting: 504 waiting at once, 36 times depth-first's 14. On large models that list can outgrow the machine's memory. And plans live at the bottom of the tree, so the first one came only at node 554. Stop the search at node 500 and best-first has nothing to show.

Breadth-First Is the Rule to Avoid

Breadth-first solves every node of one depth before any node of the next. It took 10,425 nodes and held 3,366 waiting. It shares best-first's flaw (plans come only from the bottom, so it found the first one at node 5,196 and pruned little before then) without its reason (the order ignores the bounds). It appears here as a baseline.

A common design mixes the first two rules: dive depth-first from a node for a while to find plans, then jump back to a node with a high bound. Lesson Primal heuristics: rounding, diving, RINS looks at diving as a way of finding plans.

  1. Coding practice

    Pick the next node

    • best-first solves only nodes whose bound is above the optimum, at the price of memory
    • breadth-first takes nodes in the order they were made
    • depth-first keeps about one node per level waiting and finds plans early
    • depth-first takes the deepest node, best-first the highest bound, breadth-first the oldest

Problem statement

A crew-rostering MILP runs a branch-and-bound whose waiting nodes are kept in one plain list, and the team wants to switch node rules with a parameter instead of three data structures.

Write next_node(waiting, rule) in next_node.py. Each waiting node is a tuple (id, depth, bound): id counts up as nodes are made (a larger id is a newer node), depth is its distance from the root, and bound is its parent's LP value. The problem is a maximization. Return the id of the node to solve next:

ruleTakes
"depth"the greatest depth; among equal depths, the newest (largest id)
"best"the highest bound; among equal bounds, the oldest (smallest id)
"breadth"the oldest (smallest id)

waiting is never empty, and its entries can be in any order.

The Variable Rule Decides Which Fractional Variable to Split


When a node's LP has several fractional variables, the variable rule (also called branching variable selection) picks the one to branch on. Every choice is correct, since every split keeps all plans (lesson Branching on a fractional variable); the choice changes how fast the bounds fall. bnb.py has three rules:



  • First takes the first fractional variable in the model's order. It is cheap and blind.
  • Most fractional takes the variable whose value is closest to 0.5: min(v, 1 - v) is its distance to the nearer of 0 and 1, and the rule takes the largest. The idea is that the LP is least sure about it. max keeps the first variable among ties.
  • Strong branching tries each candidate: it solves both children's LPs and measures how far each child's value drops below the node's. It takes the candidate with the largest product of its two drops. The next rule explains why the product.


A variable rule only matters when there is a choice. On the one-row model of lesson Bounds, incumbents and pruning the LP rarely has more than one or two fractional variables, because the budget row can hold only one project at a fraction (plus any project tied to it by a parent or alternative row). Each yearly row can hold one of its own:



That is why this lesson uses the yearly model: with 5 rows there are real choices to make.

Strong Branching Buys a Smaller Tree With Extra LPs


Every combination of the three node rules and three variable rules, on small with yearly budgets:



Memory follows the node rule, not the variable rule. Whatever the variable rule, depth-first kept at most 15 nodes waiting, best-first between 72 and 504, and breadth-first between 1,259 and 3,366. A better variable rule shrinks best-first's list, but it stays far above depth-first's.


The LPs column counts strong branching's trial LPs too. Strong branching made the smallest tree under every node rule. Under best-first it cut the tree from 1,065 nodes to 147, and even with its trial LPs counted it solved fewer LPs (375) than the other rules. Under depth-first it saved nodes (1,291 against 1,705) but more than doubled the LPs (3,667). This program also wastes some of that work: the trial LPs of the chosen variable are the children's LPs, and it solves them again when the children are taken. A solver keeps them.


Why the product of the drops? A split is useful when it lowers the bound on both sides: then both children are more likely to be pruned. Take two candidates. Splitting $x_a$ drops the bound by 30 in one child and 0.1 in the other; splitting $x_b$ drops it by 6 and 5. The sum prefers $x_a$ (30.1 against 11), but $x_a$'s second child is almost the parent again, so nearly nothing was gained on that side. The product prefers $x_b$ (30 against 3). Lifting each drop to at least $\varepsilon$ keeps one zero drop from making every candidate score 0. A child that is infeasible counts as an infinite drop: that side of the tree is gone, the best outcome there is.


Strong branching on every candidate at every node is expensive, so a search can estimate the drops instead. A common estimate is the pseudo-cost: the average drop per unit of change seen each time a variable was branched on before. Pseudo-costs cost nothing to apply but know nothing at the start, so a typical design uses strong branching on a variable until it has been branched on a few times, then trusts its pseudo-cost. That idea is usually called reliability branching. HiGHS documents its threshold as the option mip_pscost_minreliable, "minimal number of observations before MIP solver pseudo costs are considered reliable", 8 by default; lesson Reading a full MIP log line by line's HiGHS log counts the LP iterations its strong branching spent.

No Rule Wins Everywhere, So Measure on Your Own Model


The table has surprises. Most-fractional made the tree larger than first-fractional under depth-first (1,991 against 1,705) and smaller under best-first (693 against 1,065). Strong branching saved LPs under best-first and cost LPs under depth-first. None of these results is a law: they are measurements on one model, and a different portfolio or one more row could reorder them. What holds generally is the shape of the trade-offs:


RuleGainsPays
depth-firstlittle memory, plans earlymore nodes when the first dives are poor
best-firstfewest nodes that must be solvedmemory, and no plan until late
breadth-firstnothingmemory, late plans, many nodes
first or most fractionalfreeblind to how much a split helps
strong branchingthe largest bound drops, so small treestwo trial LPs per candidate
pseudo-costsstrong branching's aim at no costpoor guesses until history builds up


When a model is slow in a real solver, these are among the settings worth trying, and the way to choose is the way this lesson chose: run each option on the same instances and count. MathOpt has one solver-independent handle on them, ModelSolveParameters(branching_priorities=...): variables given higher values are branched on first, and the rest keep the solver's default priority. Any other control over these rules, where a solver offers one, is in that solver's own parameters. Section 5's lesson on honest benchmarking (Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean) shows how to do that fairly over several instances and seeds.


Summary


  • The node rule decides which waiting node comes next. Depth-first uses a stack, best-first a heap ordered by bound, breadth-first a queue.
  • Depth-first keeps few nodes waiting and reaches a plan quickly, but can spend many nodes in a poor part of the tree.
  • Best-first solves the fewest nodes because it never opens a node below the optimum, but holds many nodes waiting and finds its first plan late.
  • Breadth-first is the rule to avoid.
  • The variable rule decides which fractional variable to split. It matters only when the LP has several fractional variables, which needs several rows.
  • Strong branching buys a smaller tree with extra LPs. It scores each candidate by the product of its two children's bound drops; pseudo-costs estimate those drops from history.
  • No rule wins everywhere, so measure on your own model.

Design Note: Why a Waiting Node Carries Its Parent's Bound


A waiting node's own LP would give a tighter bound, and best-first would order nodes better with it. But solving a node's LP when it is made, rather than when it is taken, solves the LP of every node that is later pruned on its parent's bound: 478 of them in the best-first run above. Storing the parent's value is free, which is why this module's search keeps it. A refinement is to store an estimate as well (the parent's bound minus the pseudo-cost of the branching), which ranks waiting nodes better at no LP cost.
