GridCap's planners send the tiny portfolio to HiGHS: eight candidate projects, a $7,390k capital budget, one must-do project, one project that needs another, and two projects that are alternatives to each other. HiGHS answers: fund P001, P002, P005 and P006, worth $3,627k. There are $2^8 = 256$ yes/no plans, so trying them all would have worked here. For the small portfolio's 40 projects there are about $1.1 \times 10^{12}$, and for the medium portfolio's 400 the number has 121 digits. HiGHS does not try them all. It runs branch-and-bound, the method at the core of MILP solvers, and this module builds it by hand.

Branch-and-bound rests on one move: solve an LP, find a variable the LP set to a fraction, and split the problem in two on that variable. This lesson takes that move apart in five rules, then repeats it until the tiny problem is solved.

The Model

The one-period selection model of lesson The problem zoo: LP, MILP, CP, NLP and how to pick, the model HiGHS solved above.

Sets. $P$, the candidate projects (P001 to P008 on tiny); $M \subseteq P$, the must-do projects; $C \subseteq P$, the projects that need a parent project, with $p(c)$ the parent of $c$; $\mathcal{G}$, the alternative groups, each a set of projects of which at most one may be funded.

Parameters. $c_i$, the capex of project $i$ ($k); $v_i$, its value, the NPV if it starts as early as it can ($k); $B$, the capital budget ($k).

Variables. $x_i \in \{0, 1\}$ for every $i \in P$: 1 if project $i$ is funded.

Dropping Integrality Gives an LP Whose Value Bounds Every Plan From Above

Replace $x_i \in \{0, 1\}$ by $0 \le x_i \le 1$ and keep every row. The result is an LP, the LP relaxation of the model ("relaxed" because one rule was loosened, not changed). An LP is what GLOP solves (section 2). Solved, next to the MILP:

The LP's value, 3,770.1, is higher than the best real plan's 3,627. It always is at least as high, because every allowed plan is also a point of the relaxation (lesson The integrality gap, measured on GridCap gives the argument). For a maximization:

That inequality is the "bound" in branch-and-bound. An LP value is an upper bound: a number no plan can beat. The gap between the two, here 143.1, is the integrality gap; lesson The integrality gap, measured on GridCap measures it across GridCap. This lesson needs only its sign.

A Fractional Value Marks the Variable to Branch On

An LP solution whose variables are all 0 or 1 is a real plan, and by the inequality above it is then the best plan: nothing beats the LP, and this plan reaches the LP's value. The tiny LP is not that lucky. Two variables are fractions: $x_{P003} = x_{P004} = 0.099$.

The fraction has a plain reading. P001, P002 and P006 cost 6,850, which leaves 540 of the 7,390. P007 would be the best use of it, but it is P006's alternative. Next is P004, which needs P003, so the row parent$_{P004}$ makes the LP buy the two together: 5,470 of capex for 2,696 of value, $2{,}696 / 5{,}470 = 0.493$ per dollar, a hair above P005's $123 / 250 = 0.492$. The LP spends the 540 on that pair and buys $540 / 5{,}470 = 0.099$ of it. A planner cannot fund 9.9% of a tower replacement, and rounding does not rescue the plan. Rounding both up costs $6{,}850 + 5{,}470 = 12{,}320$, far over budget; rounding both down gives P001, P002 and P006, worth 3,504, a real plan but not the best one (lesson Yes/no decisions, and why rounding an LP fails shows this failure in general).

A variable whose LP value is not a whole number is fractional, and it is where branching starts. Solvers compute values in floating point, so "not a whole number" has to allow for noise: a value of 0.9999999 is 1 that picked up rounding error, not a fraction. The library calls a value fractional when it is more than $\varepsilon = 10^{-6}$ away from the nearest whole number:

round(v) is the nearest whole number, so the test also works for a variable that may take values above 1 (a count of crews, later in this lesson). On the root LP it returns ["P003", "P004"]. MILP solvers apply the same kind of tolerance to the plans they return, which is why lesson Start-time variables x(i,t) and timing windows reads a 0-1 variable as "funded" when its value is above 0.5 rather than equal to 1.

Problem statement

A depot-planning MILP decides how many trucks to station at each depot (a whole number, often more than 1) and whether to open each depot (0 or 1). Its LP relaxation has just come back from the solver, and the branch-and-bound loop needs to know which variables are still fractions.

Write fractional(x, tol=1e-6) in fractional.py. x maps each variable's name to its LP value. Return the names of the variables whose value is more than tol away from the nearest whole number:

in the order x lists them. A value such as 0.9999999 is a whole number that picked up float error, so it is not fractional. Values can be above 1 (truck counts) or below 0 (a change in a count).

Branching Splits the Problem Into Two Children That Keep Every Integer Plan


Pick one fractional variable, say $x_{P003} = 0.099$. Every real plan has $x_{P003} = 0$ or $x_{P003} = 1$, nothing in between. So the problem splits into two smaller problems, called children:



The split is branching, and $x_{P003}$ is the branching variable. It has three properties, and all of branch-and-bound depends on them.


  1. No real plan is lost. Each allowed plan sits in exactly one child, so the best plan overall is the better of the two children's best plans.
  2. The fractional LP point is cut off. The point with $x_{P003} = 0.099$ is in neither child, so neither child's LP can return it again. The search cannot repeat itself.
  3. Each child is smaller. It has one more variable fixed, so after at most $|P|$ splits on a path, every variable is fixed and nothing is left to split.


Each child can be split again, and its children too. Drawn out, the problems form a search tree: the original problem is the root at the top, each problem is a node, and a node's children hang below it. A node's depth is the number of splits between it and the root, which for 0-1 variables is the number of variables it has fixed.


A program checks the first property on tiny by listing all 256 plans and keeping the allowed ones:






allowed checks the four kinds of rows on a 0-1 plan. Of the 256 plans only 32 obey every row, and the split puts 22 in one child and 10 in the other, none in both and none in neither. The best plan overall, 3,627, is the better of the two children's bests. Branch-and-bound never lists plans like this; the listing only shows that branching keeps every plan somewhere.


Each Child Is the Same LP With One Bound Changed


Writing "the model plus $x_{P003} = 0$" needs no new row. The relaxation already has the bounds $0 \le x_{P003} \le 1$; the down child lowers the upper bound to 0, and the up child raises the lower bound to 1. So a node of the search is just a list of fixings, and solving it means setting bounds and calling the LP solver again:



The model is built once; only the bounds change between nodes. A child's LP can be infeasible: fixings can contradict a row, for example two projects fixed at 1 whose capex is over budget. Then the child holds no plan at all. Solving the two children of the root:






Both children's values are below the root's 3,770.1, and they always will be at most the parent's: a child's LP has the parent's rows and one tighter bound, so its allowed set is a part of the parent's, and the best over a part is never better than the best over the whole. Going down the tree, bounds only fall.


Each child is still fractional, on a different variable. The down child takes half of P008, which now fits; the up child, having paid for P003 (worth only 576), takes 63.3% of P004. So each child splits again.

where $\lfloor v \rfloor$ (floor) is the largest whole number not above $v$ and $\lceil v \rceil$ (ceiling) the smallest not below it. No whole number lies strictly between them, so the three properties hold as before. For a 0-1 variable, floor is 0 and ceiling is 1, which gives $x = 0$ and $x = 1$: the 0-1 split is the special case.

Branching Stops at a Node Whose LP Is Infeasible or Integral


Two kinds of node need no more splitting. An infeasible node holds no plan, so there is nothing below it to find. An integral node, one whose LP solution has no fractional variable, holds a real plan, and that plan is the best one in the node: no plan in the node beats the node's LP, and this plan reaches it. Either way the node is a leaf. Every other node is split on a fractional variable.


The library function branch_and_bound does the splitting. Its core lines:



A node's fixed is its parent's fixings plus one, so a node deep in the tree carries every decision on the path from the root. waiting holds the nodes made but not yet solved; this run always takes the newest one next, and lesson Node and variable selection is about that choice. Each child also stores its parent's LP value as its bound, which lesson Bounds, incumbents and pruning puts to use. The best integral leaf so far is kept in search.value and search.plan; the output calls it the incumbent, a term lesson Bounds, incumbents and pruning develops. choose_variable with its default rule returns the first fractional variable in project order. To prune a node is to stop the search below it; the word is used for every kind of leaf.


Run on tiny with prune=False, which switches off the one kind of pruning that lesson Bounds, incumbents and pruning adds, the whole tree prints. Each line is a node: its number, its fixing, its LP value and what happened. Indentation is depth.



Read the first path. The root is split on $x_{P003}$, and the up child (node 2) is taken first. It is split on $x_{P004}$; node 4 fixes P004 too, and P002 + P003 + P004 cost 8,200, over budget, so it is infeasible. Node 3 drops P004 and the path goes on, fixing one project per level, until node 13 is integral at 2,833: P001, P002 and P003. Only then does the search come back up and take the down children it left waiting, and the last one, node 23, is the best plan, 3,627, the value HiGHS returned.


The tree has 29 nodes, against 256 plans. It is smaller because a leaf ends a whole subtree: node 4 is infeasible, so none of the plans that fund P002, P003 and P004 together is ever looked at. Notice also how much of the work happened below node 2, whose LP value was 3,054.7. Once node 13 had found a plan worth 2,833 and node 23 one worth 3,627, nothing below a node with LP 3,054.7 could win. Lesson Bounds, incumbents and pruning turns that observation into the rule that gives branch-and-bound its name.


Summary


  • Dropping integrality gives an LP whose value bounds every plan from above. Every allowed plan is a point of the relaxation, so $z_\text{LP} \ge z_\text{MILP}$ for a maximization.
  • A fractional value marks the variable to branch on. Test the distance to the nearest whole number against a tolerance, never 0 < v < 1 with exact floats.
  • Branching splits the problem into two children that keep every integer plan. Every plan is in exactly one child, the fractional LP point is in neither, and each child has one more fixing.
  • Each child is the same LP with one bound changed. A child's LP value is never above its parent's.
  • A general integer branches on floor and ceiling: $x \le \lfloor v \rfloor$ or $x \ge \lceil v \rceil$.
  • Branching stops at a node whose LP is infeasible or integral. An integral LP solution is the best plan in its node.

Design Note: Why Branch on Variables and Not on Something Else


Any split that sends every plan to one side and the fractional point to neither side would do. A solver could split on a sum, for example $x_{P003} + x_{P004} \le 0$ against $x_{P003} + x_{P004} \ge 1$, or on the budget row. Splitting on one variable is the common default because it is cheap to apply (two bound changes, no new rows), it keeps the LP the same size, and its children are easy to name in a log. Branching on a sum of variables in a group, such as an alternative group, can balance the tree better; that is the idea behind the SOS constraints some solvers offer (lesson The lambda (SOS2-style) formulation built from binaries builds the same effect from binaries: MathOpt's documentation lists SOS constraints among its model features, but its Python API in OR-Tools 9.15 has no call that adds one).
