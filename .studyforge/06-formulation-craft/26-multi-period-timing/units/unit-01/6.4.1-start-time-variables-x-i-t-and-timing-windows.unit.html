  15. Start-time variables and timing windows

The one-period selection model (lessons Decisions, objectives and constraints: turning a planner's question into a model and The problem zoo: LP, MILP, CP, NLP and how to pick) answers whether to fund each project. GridCap's planners now work on a five-year plan for the small portfolio: 40 projects, a budget for each of 2027 to 2031, and for each project a window of years it may start in. A project that starts late loses value (the risk it would have removed is carried for longer), so the question becomes whether and when. Four rules, one per heading, turn "when" into variables a MILP can handle.

One Binary per Project and Start Year Turns "When" Into "Whether"

Give each project $i$ one binary for each year $t$ it may start in:

For the tiny portfolio that gives 13 variables:

Why not one integer variable "start year" per project, taking values 2027 to 2031? Because every quantity that depends on the start year (the NPV, the spend in each year, the crews needed) would then be a nonlinear function of that integer. With one binary per year, each of them is a plain sum: the NPV of project $i$ is $\sum_t \text{npv}_{i,t}\, x_{i,t}$, linear in the $x$. That trade (more variables, every expression linear) is the point of the time-indexed formulation.

A Project Starts at Most Once, and a Must-Do Starts Exactly Once

Nothing so far stops the model from starting a project in 2027 and in 2029, and collecting its NPV twice. One constraint per project closes that:

started(i) is the sum over the project's start years, and it is worth naming, because almost every later rule speaks about it: "P004 needs P003" becomes $\text{started}(P004) \le \text{started}(P003)$, and an alternative group becomes a sum of started terms. The sum is 1 if the project is funded at all and 0 if it is not, so it plays the role the single $x_i$ played in the one-period model.

Forget the "at most once" row and the failure is quiet: the model returns a plan worth more than any real one, with a project listed twice. A test that checks every project starts at most once catches it in a line (lesson Unit-testing one constraint at a time).

A Timing Window Is Enforced by the Variables You Never Create

P001 may start in 2028 or 2029, so x[P001,2027] does not exist. You could create it and add $x_{P001,2027} = 0$; leaving it out is simpler and shrinks the model before the solver sees it:

On the large portfolio the windows cut the variables by a factor of four, and every variable you do not create is one the model never has to build, store or send to the solver. Section 11 measures what that saves.

The trap is the other end of the window. A project with a three-year cost profile that starts in 2030 would still be spending in 2032, outside the plan. GridCap's windows already stop every project in time; with your own data, check that $t + \text{duration} - 1$ is inside the horizon for every variable you create, or the model will fund work it never pays for.

Rows can run the other way too. The once and must-do rows sum one project's variables over its years; a rule about a year sums over projects instead: $\sum_{i \in P,\ t \in T_i} x_{i,t}$ for one fixed $t$ counts the projects that start in year $t$, and a project with no variable for that year simply has no term in the sum. A year in which no project may start has an empty sum: there is nothing to bound, so write no row for it. Every per-year budget of the next lesson is a sum of that shape.

In code, the empty sum needs care. Python's sum over no terms is the plain number 0, not a MathOpt expression, so a row built from it is a comparison of two numbers, and MathOpt refuses it. empty_sum.py caps GridCap tiny at one start per region and year; Coast's only project, P003, may start only in 2027, so Coast's 2028 and 2029 sums are empty:

0 <= 1 is the Python value True, and add_linear_constraint raises a TypeError on a bool. There are two ways out. Skip the row when its set is empty, as above: it bounds nothing. Or start the sum from an empty expression, mathopt.LinearExpression(), so that the result is an expression even with no terms; Python's sum takes it as its start:

The second way writes the two empty rows, $0 \le 1$, which every plan satisfies, and HiGHS solves the model as usual. Wrapping a finished sum, mathopt.LinearExpression(sum(...)), also turns the 0 into an expression. An empty row is harmless only when it is true: the last line puts a floor of 1 on an empty sum, $0 \ge 1$, and HiGHS reports the model INFEASIBLE. That is right if the rule really demands a start where none is possible, and a bug to look for if it does not.

The MathOpt sample time_indexed_scheduling.py in the OR-Tools repository is this formulation outside GridCap. Jobs run one at a time on a single machine; job $i$ takes $p_i$ periods and may not start before its release time $r_i$, and the goal is the smallest sum of completion times. It has one binary per job and start time, a "starts once" row per job, and one row per time $t$ that sums, over every job, the start variables that would have it running at $t$: the per-year shape just described. The sample handles a release time the other way from this lesson: it creates every $x_{i,t}$ and sets the upper bound of the early ones to 0. time_indexed.py builds it both ways:

Both give the same schedule; the variables differ. On the sample's own three-job test data one variable is saved, and on eight jobs with release times drawn from 1 to 79 a quarter of them, 362 of 1,424. A bound of 0 is the easy way to forbid a start in a model that already exists (lesson Manual overrides as fixed bounds uses it for manual overrides); leaving the variable out is the better way when you build the model. The machine rows also meet the empty-sum case: at a time before any job may start, no variable exists to sum, so the program writes no row there.

    Crews and coordinated outages

    • one binary per project and allowed start year makes every start-dependent quantity linear
    • a timing window is enforced by creating start variables only for the window's years

    Not startedPassed

Problem statement

A rural electric cooperative is scheduling its feeder upgrades year by year, and the model in outages.py already has a start variable x[(pid, year)] for each project and each year in its window, a row saying each project starts at most once, and a row saying each must-do project starts exactly once. Two rules from the operations team are missing:

  • Crews. Each year only a few line crews can be mobilized: at most max_starts[year] projects may start in that year, must-do projects included. A year in which no project may start has nothing to cap, so it gets no row. In Python an empty sum is the number 0, and MathOpt refuses a row built from it (a TypeError about a bool): skip the row, or start the sum from mathopt.LinearExpression(), as the lesson shows.
  • Coordinated outages. Some pairs of upgrades sit on the same feeder and need one shared outage. For each pair in coordinated, either neither project is funded, or both are and they start in the same year.

Write add_outage_rules(model, x, projects, max_starts, coordinated) so the model allows exactly the schedules that keep both rules.

The model so far, with $P$ the projects, $T_i$ the years project $i$ may start in, $M \subseteq P$ the must-do projects, $Y$ the years with a crew cap $K_y$, and $D$ the coordinated pairs:

Write your rows in this notation first, each with its quantifier and a label, then code them. Mind the pairs whose windows do not line up: there is no variable for a year outside a project's window.

The tests fix a schedule by setting the variables' bounds and ask the solver whether it is allowed, so any correct formulation passes. About ten lines in total.

Problem statement


A gas utility's planners run the main-replacement model every month and hand its answer to a reporting job. The job needs two things from each solve: every project's start year, and which funded projects were pushed past the first year they could start. It also must not report a schedule that is not one: last month a run stopped early and handed over values like 0.5, and the report rounded them into a plan nobody had approved.


Write two functions in starts.py:


  • read_starts(values, projects, tol=1e-6) takes the values the solver returned, values[(pid, year)], one for each start variable, and returns every project's start year, or None for a project that is not funded. It raises ScheduleError when the values are not a schedule.
  • deferrals(starts, projects) returns, for each funded project that starts after its earliest allowed year, how many years later it starts.


In the lesson's notation, the solver returns a value $\hat x_{i,t}$ for each $i \in P$ and $t \in T_i$, and a solver only promises those values to within a tolerance $\varepsilon$ of the domain $\{0, 1\}$. Before you code, write down in that notation which values are a schedule (when is $\hat x_{i,t}$ read as 1, as 0, or as neither, and how many years of one project may read as 1), and what a project's start year $s_i$ and its deferral are in terms of $\hat x_{i,t}$ and $\min T_i$.

The Model


The whole multi-period model timing_model.build solves, in one place. This lesson added the start variables and the once and must rows; the budget rows come from lesson Cash-flow spreading across years and the precedence rows from lesson Aggregated vs. cumulative (disaggregated) forms.


Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use (its window, cut so the work ends inside $Y$); $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups, each a set of projects; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.


Parameters. $\text{npv}_{i,t}$, the NPV of project $i$ started in year $t$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work, $k = 0, 1, \dots$ ($k); $B_y$, the budget of year $y$ ($k).


Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$. No other variable exists, so no other start is possible.

Summary


  • One binary per project and start year turns "when" into "whether". Every quantity that depends on the start year becomes a linear sum.
  • A project starts at most once, and a must-do exactly once. started(i) replaces the one-period $x_i$ in every rule that follows.
  • A timing window is enforced by the variables you never create. Check that every created start year finishes inside the horizon.
  • The schedule is read off the variables that are 1. Compare each start with the earliest allowed year to find and explain deferrals.

Design Note: Start Variables or Step Variables


An equivalent model uses $z_{i,t} = 1$ if project $i$ has started by year $t$, with $z_{i,t} \ge z_{i,t-1}$. The two are linked by $x_{i,t} = z_{i,t} - z_{i,t-1}$, so their LP relaxations are the same. Start variables make NPV and spend easy to write; step variables make "has started by" rules easy. Lesson Aggregated vs. cumulative (disaggregated) forms writes precedence in the "by year $t$" style using sums of start variables, which gives you the step variable's strength without a second set.
