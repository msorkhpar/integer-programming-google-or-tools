GridCap's Ridge engineers send the planners three new rules for the small portfolio. The P028 tower-set replacement in 2030 takes a line out of service, and while it is out the load has to run through a Ridge circuit that has already been put underground (P024 or P037): P028 needs one of them. The three Plains feeder replacements P013, P026 and P040 are one program, approved as a whole or not at all. And the three Ridge vegetation jobs P008, P020 and P035 share one crew mobilization, so they must start in the same year. The first rule links a child project to its parents; the other two make a bundle, a group that is funded, or scheduled, as one. This lesson writes each as rows of the multi-period model, measures what each costs, and checks the dependency graph before the solve, in four rules.

GridCap is a fictional utility's portfolio, generated for this course. Its data already has two parent-child pairs (P016 needs P015, and P023 needs P022 with a one-year lag); the rules above are invented for the lesson.

A Child Needs Its Parent: Started by Year t Only if the Parent Had Started by Then

Section 9.1 of MIT's 15.053 text (see Further reading) writes a contingent investment, "j only if i", as one row on two binaries, $x_j \le x_i$: if $x_j = 1$ then $x_i$ must be 1, and if $x_i = 0$ then $x_j$ must be 0. The contingent project sits on the small side of the row. (The text names its two projects the other way round, so its row reads $x_j \ge x_i$ for "i only if j"; it is the same row.) With start-year variables the rule also has a time: the parent must be under way when the child starts. Lesson Aggregated vs. cumulative (disaggregated) forms wrote it one row per year of the child's window, with $\text{started\_by}(i, t) = \sum_{u \in T_i,\ u \le t} x_{i,u}$, which is 1 if project $i$ has started in year $t$ or earlier:

with $L$ the lag in years (0 here: the parent may start in the same year as the child). In the child's last year the row reads $\text{started}(c) \le \text{started\_by}(p, \cdot)$, so it also says "no child without its parent". A child with two parents can mean two different things, and the rows differ:

  • Needs all of them: one such row per parent.
  • Needs any one of them: one row per year whose right side sums the parents, $\text{started\_by}(c, t) \le \sum_{p} \text{started\_by}(p, t - L)$. The sum is at least 1 as soon as one parent has started, which is all the child needs.

needs_rows.py solves the model with each version and prints the start years of the three projects (- for not funded):

  • No rule. The best plan funds P028 (the most valuable project in the portfolio, $4,268k of NPV) and neither undergrounding job. That is exactly the plan the engineers say cannot be built.
  • Needs P024. The plan keeps P028 and adds P024 in 2029, before P028's start, for $273k of NPV. It also funds P037 in 2031; the rule does not ask for that, it is just the best use of the money once P024 is in.
  • Needs all. P037 cannot start before 2030, so P028's 2030 row needs both P024 and P037 started by 2030. That costs more than P028 is worth to the plan, which now drops all three: a loss of $870k against the plan without the rule.
  • Needs any. The rule is met by P024 alone, so it costs the same $273k as "needs P024".

The difference between "all" and "any" here is $597k. Ask which one the engineers mean, every time a child has more than one parent.

All-or-Nothing Is an Equality Between Members

A bundle is a set of projects $B$ that is funded whole or not at all. Pick one member $b_1$ and tie each other member to it:

If $b_1$ is funded, every member is; if it is not, none is. That is $|B| - 1$ rows. Two other forms are common and allow the same plans: a new binary $z_B$ with $\text{started}(j) = z_B$ for every member (one more variable, $|B|$ rows), and the pair of parent rows $\text{started}(j) \le \text{started}(b_1)$ and $\text{started}(b_1) \le \text{started}(j)$, which says the same thing as the equality in twice the rows. A bundle is a parent-child rule that runs both ways.

Only whether the members are funded is tied. Each member still chooses its own start year.

A Bundle That Starts Together Is an Equality per Year

"One crew mobilization" asks for more: the members start in the same year. Tying the started sums is not enough, because P008 could start in 2031 and P020 in 2030 with both sums equal to 1. The year has to be tied, one row per year and member:

where $T_B = \bigcap_{i \in B} T_i$ is the set of years in which every member may start. A member's start variable for a year outside $T_B$ can never be 1 in such a plan, because the others cannot join it there, so it is fixed to 0 (the "apart" rows below; lesson Manual overrides as fixed bounds shows that a fixed variable is better written as a bound). If $T_B$ is empty, the bundle can never be funded.

The "together" rows imply the "all or nothing" rows: summing $x_{j,t} = x_{b_1,t}$ over the common years gives $\text{started}(j) = \text{started}(b_1)$ once the other years are fixed to 0. bundles.py solves each bundle three ways:

Each cost is measured against that bundle's own "no bundle" line, which is the same $24,260k plan both times.

  • Plains feeders. The best plan funds only P026. All of the program costs more than it returns in the years it would run, so the bundle drops all three, and the plan loses P026's contribution net of what the freed money buys: $121k. "All or nothing" is a real choice between all and nothing, and here nothing wins.
  • Ridge vegetation, all or nothing. The best plan already funds all three, in 2031, 2030 and 2027, so the rule costs nothing.
  • Ridge vegetation, same year. The only year all three may start is 2030. Starting all three then is worth less than dropping them, so the plan drops them, for $294k.

The two Ridge rows are the point of this section: the same three projects, the same "all of them", and a $294k difference that comes only from the timing.

Problem statement

A regional rail line plans its works for 2027 to 2030. The model in rail.py has a binary x[pid, t] for each project and each year t in its starts, and it already says that no project starts twice. Two rules remain:

  • Signal blocks. Each list in blocks is a block of signal upgrades that one crew commissions together: either every upgrade of the block is done, all starting in the same year, or none is.
  • Platforms. platforms maps a platform extension to the track upgrades that can carry its longer trains. A platform extension may start in year t only if at least one of its track upgrades started in year t - 1 or earlier.

Write add_works_rules(model, x, projects, blocks, platforms) so that the model allows exactly the plans that keep both rules.

The model so far, with $P$ the projects and $T_i$ the start years of project $i$:

Name the remaining sets (the blocks, the years every member of a block may start in, each platform's track upgrades) and write your rows, each with its quantifier and a label, before you code them. Ask what a block member's variable for a year that another member cannot use must be.

A sum over a set that can be empty, such as a project's start years up to t, is the number 0 in Python, and MathOpt refuses a row with no variable on either side. Skip such a row, or start the sum from mathopt.LinearExpression() (lesson Start-time variables x(i,t) and timing windows).

The tests fix every x[pid, t] through its bounds and ask the solver whether the model accepts the plan, so any correct formulation passes. About fifteen lines.

  • a track upgrade started in the platform's own year does not count








Read the Dependency Graph Before You Solve


Parent links form a graph: an arrow from each child to each parent. Three facts about it can be read before any model is built, and each one changes the plan in a way the solver will not explain:


  • A must-do child makes its parents must-dos. If P023 must be funded and needs P022, P022 must be funded too, and so must P022's own parents. The model enforces this already; the check tells the planner, who may not know that marking one project mandatory mandated another.
  • A child whose window closes before its parent's opens can never be funded. If the parent's earliest start plus the lag is after the child's latest start, the child's needs rows force it to 0 in every year. The model drops it without a word.
  • Two projects that need each other are a bundle. "A needs B" and "B needs A" together are the all-or-nothing rows, and with lag 0 both ways, the same-year rows. A cycle in parent links is usually a data error, and if it is meant, it should be written as a bundle.

With the lag at 2, P016 silently leaves the plan. With the cycle, P015 and P016 are forced into the same year, 2030, and P015 moves from 2029 to get there. A planner reading only the plan would see two changes and no cause.


The ancestors walk follows one parent per project, as GridCap stores it. With several parents per child (needs all), the walk becomes a search over every parent, and a project reached by two paths is still one project, funded once.

Problem statement


A water utility's planners keep asking two questions about their project list before any model is solved. Each project has a cost (in $k) and a tuple of needs: the projects that must also be funded for it to go ahead. A needed project may have needs of its own, and two projects may need the same one.


  • "What does it take to fund this project?" entry_cost(projects, pid) returns the cost of pid plus the cost of every project it needs, directly or through other needed projects. A project that is needed along two paths is still built, and paid for, once.
  • "Which projects are required only because something required needs them?" implied_required(projects, required) returns the set of projects that are not in required but that some project in required needs, directly or indirectly.


projects maps each id to a Project. No project needs itself, directly or indirectly.

The Model


The planning model with this lesson's rows marked. Each program adds one rule to it at a time.


Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years of project $i$; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, each with a set of parents $\text{Par}(c)$ and a lag $L_c$ years (the data has one parent per child; P028 gets two in this lesson); $\mathcal{B}$ the bundles, each a set $B \subseteq P$ with a first member $b_1$; $\mathcal{B}^{\text{yr}} \subseteq \mathcal{B}$ the bundles that start together, with $T_B = \bigcap_{i \in B} T_i$.


Parameters. $\text{npv}_{i,t}$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k).


Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$. We write $\text{started}(i) = \sum_{t \in T_i} x_{i,t}$ and $\text{started\_by}(i, t) = \sum_{u \in T_i,\, u \le t} x_{i,u}$.

Summary


  • A child needs its parent: started by year t only if the parent had started by then. Several parents mean "all" (a row per parent) or "any" (one row on their sum); here the difference was $597k.
  • All-or-nothing is an equality between members. $|B| - 1$ rows tie whether each member is funded; each still picks its own year.
  • A bundle that starts together is an equality per year. Tie the start variables in the common years and fix the others to 0; the same three Ridge jobs cost $0 as a bundle and $294k as a same-year bundle.
  • Read the dependency graph before you solve. Must-do children, children that can never start, and cycles all solve to OPTIMAL; only a check names them.

Design Note: A Bundle Is Data, Not Code


The bundles in this lesson are lists in a program. In a planning tool they are records: a name, a kind ("all or nothing", "same year") and the members, owned by the planners and checked like any other input (lesson Data-quality checks that prevent infeasibility). One function turns every record into rows, and the dependency check runs over the same records. Then "why was P026 dropped?" has an answer a planner can read: it is in the Plains feeders bundle, and the bundle did not pay for itself.
