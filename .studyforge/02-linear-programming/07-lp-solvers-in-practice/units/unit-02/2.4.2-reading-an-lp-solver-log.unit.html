GridCap's weekly funding LP (lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP) is moving into a scheduled job. Most weeks nobody looks at it. The week a planner says "the numbers look wrong" or "the run took an hour", the first thing anyone asks for is the solver's log: the lines a solver writes while it works, saying what model it received, what it removed, how each iteration went and how it ended. This lesson reads one log from top to bottom, then two logs of runs that went wrong, then the same facts in GLOP's and PDLP's words. GridCap is a fictional utility; its numbers are teaching data.

The Model

The log below is the log of the funding LP of lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP, unchanged. Stated in full, so the log can be checked against it line by line:

Sets. $P$ the candidate projects; $Y$ the plan's years, the first being $y_0$; $M \subseteq P$ the must-do projects.

Parameters. $c_{i,y}$, what project $i$ spends in year $y$ if it starts at its earliest start ($k, 0 in a year it is not worked); $v_i$, its NPV at its earliest start ($k); $B_y$, the budget of year $y$ ($k).

Variables. $0 \le f_i \le 1$ for every $i \in P$, the share of project $i$ funded; $r_y \ge 0$ for every $y \in Y$, the money carried out of year $y$, with $r_{y_0 - 1} = 0$.

Ask for the Log With msg_cb, and Keep It as Lines

A solver writes nothing unless asked. MathOpt's solve takes a msg_cb argument, a function it calls with each batch of new log lines. Passing a list's extend method collects the whole log, in order, as a Python list:

A list is better than the terminal: a scheduled job can write it to a file next to the result, and a test can search it. mask_times replaces every wall-clock time in the log with <t>, because times change on every run and this page quotes the log exactly as the program printed it. Nothing else in the log is changed. Every log below is the medium funding LP solved with solve_with_log.

The Header Says What the Solver Received

HiGHS, the course's default solver, starts by describing the model it was handed:

Check the first line against the model before reading further: 49 rows are the 10 cash rows and 39 must rows, 410 columns (variables) are 400 shares and 10 carries. A count that does not match what you meant to build is a bug found before any solving, such as a loop that added each row twice. The 706 nonzeros are the entries of the constraint matrix that are not zero: each cash row holds the spend of every project worked that year, plus its carry terms.

The four ranges give the smallest and largest absolute value of each kind of number, rounded to a power of ten:

RangeWhat it coversHere
Matrixcoefficients in the rows1 (a carry, a must row) to 5,990 (a project's spend)
Costobjective coefficientsthe NPVs, 12 to 5,875
Boundfinite variable bounds other than 0the shares' upper bound, 1
RHSright-hand sides of the rows1 (must rows) to 42,870 (a budget)

Ranges spanning a few powers of ten, as here, are normal. A matrix range like [1e-04, 1e+07] is a warning: solvers compare numbers against tolerances near $10^{-6}$ to $10^{-9}$, and coefficients eleven orders of magnitude apart make those comparisons unreliable. The usual fix is to change units (money in $M rather than $, for instance) before building the model.

Presolve Shrinks the Model Before Any Iteration

Presolve is a pass that simplifies the model before the algorithm starts: it fixes variables whose value is forced, removes rows that say nothing new, and merges what can be merged. Section 3 covers it for integer models (lesson Presolve: what the solver removes first). In the log:

Each line is the model's size after one round. rows 10(-39) reads "10 rows left, 39 removed": the 39 must rows, since $f_i = 1$ fixes a variable, and a fixed variable is a number, not a decision. 39 of the 42 removed columns are those fixed shares; the other 3 went in further reductions (GLOP's log at the end of this lesson names its own steps). What remains is the real problem: 10 cash rows over 368 columns. The algorithm solves that smaller LP, and postsolve then maps its answer back to the original variables:

In the second line HiGHS solves the original model starting from that mapped-back answer, to confirm it. Here that took no further pivots: the footer counts 14 iterations, the same 14 the iteration lines show.

The Iteration Lines Track the Objective and the Infeasibilities

The first line names the algorithm: dual simplex (lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP), run on one thread ("serial"). EKK is the name of HiGHS's simplex code. Then one line every so often, with:

  • Iteration: pivots so far.
  • Objective: the objective at the current point. It is negative because HiGHS works on a minimization: maximizing $\sum v_i f_i$ is the same as minimizing $-\sum v_i f_i$, and the log shows the second. The sign flips back in the footer.
  • Infeasibilities num(sum): how many quantities are still wrong, and by how much in total. Pr: counts primal infeasibilities, rows or bounds the current point breaks. Du: counts dual infeasibilities, variables whose reduced cost (lesson Shadow prices, reduced costs and ranging from a solver) says the objective could still improve. Ph1: marks phase 1, the start-up phase that looks for a first point to work from. A line can carry both counts, separated by ;.

On a run of 14 pivots there are only two lines. On a long run there are many, and the pattern to look for is the counts falling to 0(0) and the objective moving steadily. An objective that stalls for thousands of iterations while the counts stay put is what a struggling run looks like.

The Footer Is the Verdict: Status, Iterations, Objective

  • Model status is the outcome. Optimal here.
  • Simplex iterations counts all pivots. A barrier run prints IPM iterations instead, IPM standing for interior point method (lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP); the word before iterations names the kind.
  • Objective value is in the model's own sense, so positive again: 234,898.12.
  • P-D objective error is the relative difference between the primal objective and the dual objective. At an optimum they are equal (strong duality, lesson Weak and strong duality, complementary slackness), so 0 means the solver's two views of the answer agree.
  • HiGHS run time is the wall-clock time, masked here.
  • The WARNING comes from the way OR-Tools 9.15 attaches itself to HiGHS's log, and it is printed on every run, good or bad. It says nothing about your model.

The same facts are on the SolveResult, and a program reads them there rather than from the log:

The log is for people, and for what the result does not carry: the size before and after presolve, the coefficient ranges, the progress over time.

A Failed Run's Objective Line Means Nothing

Cut 2027's budget to $1,000k, below the $3,040k the must-do projects spend that year, and solve again:

Presolve found the contradiction before any iteration, so there is no iteration line and no iteration count in the footer. Then the trap: the footer still prints Objective value : 0.0. There is no plan, so there is no objective; the line is printed anyway. A script that reads the objective line without the status line reports a plan worth $0.

The second run makes a common modelling slip: a new project's share is added to the objective with coefficient 900, but its upper bound of 1 and its spend in the cash rows are both forgotten. Nothing limits it:

Unbounded means the objective can grow without limit while every row holds. Presolve could only tell that the model was infeasible or unbounded, so HiGHS ran primal simplex to decide which. Its lines show it: primal infeasibilities reach 0(0) (it found points that keep every row), while dual infeasibilities never do (the objective can always still improve). The footer's objective, 196,144, is just where the solver stopped walking up an endless direction, and the P-D error is inf because there is no finite dual objective. The result even holds a feasible point, which is why the status, not the presence of a point or an objective, decides what a run means.

The rule for logs is the rule for results (lesson The problem zoo: LP, MILP, CP, NLP and how to pick): read the status first. Only Optimal makes the objective line an answer.

    Read the verdict of a HiGHS log

    • an infeasible or unbounded run prints an objective line that is not an answer

Problem statement

A pumping-station operator runs its energy LP every night on HiGHS and keeps only the log. Their monitoring script needs the verdict from it: how the run ended, how much work it did, and the objective, but only when the objective is an answer.

Write read_footer(log) in footer.py. log is the list of lines a HiGHS solve wrote. Return a dict with three keys:

  • "status": the text after Model status ("Optimal", "Infeasible", "Unbounded", ...).
  • "iterations": a dict from the kind of iteration to its count, read from each footer line ending in iterations, keyed by the line's first word: Simplex iterations: 7 gives {"Simplex": 7}. A run with no such line gives {}.
  • "objective": the number after Objective value as a float when the status is "Optimal", and None for any other status, even though HiGHS prints the line anyway.

The footer's labels are padded with spaces to line up their colons, so split each line at its first : and strip both sides, rather than matching exact spacing. Lines without a : are skipped.

GLOP and PDLP Logs Carry the Same Facts in Other Words


Every solver's log has a header, a presolve report, progress lines and a verdict, written in its own format. GLOP, on the same LP:



The same 49 rows, 410 columns and 706 entries, and the same reduction to 10 rows and 368 columns, now step by step: a row with a single variable (each must row) fixes that variable, the fixed variables leave, and columns that are multiples of one another are merged. Then scaling: GLOP multiplies rows and columns by factors so that the coefficients sit between 0.23 and 1, which keeps its tolerances meaningful. Scaling changes numbers, never the model's size: the row and column counts stay 10 and 368. GLOP's progress lines report the objective at some of its pivots, and its verdict is at the very end:



deterministic_time is a measure of work that, unlike time, is the same on every run of the same model and parameters, so it is the one to compare between runs.


PDLP's progress lines are a table, one row every 64 iterations here:



The first two columns count work. iter# is the iteration number. kkt_pass counts passes through the constraint matrix since the start: one pass is one product with the matrix and one with its transpose (for a quadratic objective, also one with its matrix), the work of one PDLP iteration (lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP). It is a decimal because a pass over part of the matrix counts as a fraction. Here it runs one ahead of the iteration count (65.0 at iteration 64, 257.0 at 256), and it is the fairer measure of PDLP's work between runs, since time depends on the machine.


The three columns after time are the three measures PDLP stops on (lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP), each relative to the size of the data: rel_prim_res, how much the rows are broken; rel_dual_res, how far the prices are from satisfying their own conditions; and rel_gap, the gap between the primal and dual objectives. The gap can be negative, so it is its size that has to be small. PDLP checks the three every so often (every 64 iterations in this run) and stops at the first check where all three are below its tolerance, here iteration 256. The middle block repeats the three in absolute terms: prim_resid is not zero at the end (0.0048 in the last table row), which is the sliver by which PDLP's point breaks rows and the reason its objective sat just above the simplex one in lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP.


After the verdict, PDLP's log ends with one more row in the same format as the table, under Final solution stats:



It repeats its own header, then gives the measures of the point PDLP actually returns. The line Solution point type names that point: the current iterate, the last $(x, y)$ pair. PDLP's log format documents that these final stats are measured on the original problem, whatever rescaling or presolve was used. The progress rows can describe a different candidate point (the format lists several, among them the average of the iterates since the last restart), which is why this row's measures differ from the table's row 256 although the iteration is the same. All three are still below $10^{-6}$. A program that parses the log meets this row like any progress row: it starts with an iteration number, and it is the last one.

Problem statement


A team runs a very large transport LP with PDLP and wants to know, from the log alone, how many iterations a tighter or looser tolerance would have needed, without solving again. PDLP's log reports its progress as a table: each row starts with the iteration number, and the block between the first and second | holds three relative measures, rel_prim_res, rel_dual_res and rel_gap.


Write two functions in converged.py:


  • table_rows(log) returns every progress row as a tuple (iteration, rel_prim_res, rel_dual_res, rel_gap), in log order. A progress row is a line whose text before the first | starts with a whole number; the header row ( iter# ...) and every other line are skipped. The final-stats row at the end of a log is a progress row too.
  • converged_at(log, tol) returns the iteration of the first progress row where all three measures are within tol: $\text{rel\_prim\_res} \le tol$, $\text{rel\_dual\_res} \le tol$ and $|\text{rel\_gap}| \le tol$. The gap is signed, and it is its size that has to be small. If no row gets there, return None.

Summary


  • Ask for the log with msg_cb, and keep it as lines. A list can be saved with the result and searched by a test.
  • The header says what the solver received. Check the sizes against the model; read the coefficient ranges for scaling trouble.
  • Presolve shrinks the model before any iteration. Fixed variables and redundant rows leave first; postsolve maps the answer back.
  • The iteration lines track the objective and the infeasibilities. Pr: counts broken rows, Du: counts possible improvements; both reach 0(0) at an optimum.
  • The footer is the verdict. Status first; only Optimal makes the objective line an answer.
  • GLOP and PDLP say the same things in other words. PDLP stops when relative primal residual, dual residual and gap are all small.

Design Note: Keep the Log With the Result


A log printed to a terminal is gone when the job ends, and the week someone asks why a number moved is never the week the job ran. Saving the list solve_with_log returns next to the result costs a few kilobytes and answers the first three questions of any investigation: what model the solver received, what it removed, and how it ended.
