A technical screen is short and broad: one interviewer, a shared editor, many quick questions from every area of the job, a couple of traps, and one small model to write and run. The aim is not depth on any one topic but no gaps anywhere. Give each rapid question a two- or three-sentence answer, the way you would on a call, then open the model answer. The interviewer's company and data are fictional, like GridCap.

Rapid Round: Short Answers Across Every Area

Q1. LP, MILP or constraint programming: how do you pick?

Model answer

An LP decides amounts and solves fast because it allows fractions; for yes/no decisions its value is an upper bound, not a plan. A MILP adds whole-number variables and a search, and is the default for capital planning; its answer is never better than its LP relaxation. Constraint programming searches over logic and integers directly and suits scheduling and dense logic, with integer data. Curves keep their guarantees only if they bend the right way; otherwise approximate them with linear pieces.

Taught in: lesson The problem zoo: LP, MILP, CP, NLP and how to pick.

Q2. The data team gives you PoF predictions. Why not just fund the riskiest assets?

Model answer

A prediction describes the future without you; a prescription chooses what you do. Ranking by risk ignores costs and rules: it can fund two alternatives on one asset and drop a must-do. Predictions enter the model as coefficients and their errors travel with them, so ask how wrong a coefficient can be before the plan changes.

Taught in: lesson Predictive vs. prescriptive: where PoF/RUL predictions stop and optimization starts.

Q3. Linearize "value $v$ only if both A and B are funded".

Model answer

Replace the product $x_A x_B$ with a binary $z$. Because $z$ earns a reward, the solver pushes it up, so it needs the rows that push it down: $z \le x_A$ and $z \le x_B$. A cost on $z$ would need the row that pushes it up, $z \ge x_A + x_B - 1$. Writing all three is always correct. HiGHS refuses the product itself.

Taught in: lesson Linearizing binary × binary and binary × bounded continuous; lesson AND, OR, NOT, XOR and implication as linear constraints.

Q4. "At most one of these eight projects." One row or 28 pair rows?

Model answer

One row, $\sum_{i \in S} x_i \le 1$. It allows the same 0/1 plans as the 28 pair rows, gives a tighter LP bound (the pair rows let every project take a half) and is far smaller. "A implies B" is one row too, $x_A \le x_B$.

Taught in: lesson At-least-k, at-most-k, exactly-k; lesson AND, OR, NOT, XOR and implication as linear constraints.

Q5. A single-budget selection is a knapsack. Is it easy?

Model answer

With whole-number costs, dynamic programming over budget amounts solves it in $n \times B$ steps: pseudo-polynomial, fast when the budget is a small number, still exponential in its number of digits. With several budget rows (one per year) there is no single ratio to rank by, greedy rules miss the optimum and the table needs one axis per row; that is where a MILP solver earns its place.

Taught in: lesson 0-1 and multi-dimensional knapsack; lesson Why MILP is hard: combinatorial growth in numbers.

Q6. What is a cover inequality?

Model answer

A set of projects $C$ that cannot all fit, $\sum_{i \in C} c_i > B$, gives the valid row $\sum_{i \in C} x_i \le |C| - 1$. It removes fractional LP points the budget row allows without removing any plan; on GridCap tiny two cover cuts turned the LP bound 3,268.17 into the optimum 3,021 with no branching. Solvers find and add such cuts themselves.

Taught in: lesson Cover inequalities that tighten budget rows; lesson Cutting planes: Gomory and cover cuts by hand.

Q7. You added a regional spending rule and the model still solves. Done?

Model answer

A model that solves is not yet a model that is right: a model with no such rule at all also solves, and it allows every plan. Read the model back (domains, names, units), and let tests that fix allowed and refused plans check each rule. Under Spec-Driven Development the rule's spec gives scenarios, each scenario becomes a test that pairs an allowed and a refused plan, and the tests run and fail on the old code before the code changes: in the project lesson A regional spend share: the first change from proposal to archive the six tests of a regional spend share failed on the code before the change and passed after it.

Taught in: lesson Unit-testing one constraint at a time; lesson A regional spend share: the first change from proposal to archive.

Q8. Where do bad inputs get caught?

Model answer

Before the model. A schema written from the formulation's sets and parameters validates the whole snapshot in one pass and refuses unknown keys; a quality gate then runs every rule across projects (parent cycles, a must-do child whose parent cannot start in time, required work that costs more than all budgets) and reports all findings with a severity. An error blocks; a warning is reported with the plan.

Taught in: lesson Schemas for model inputs; lesson Data-quality checks that prevent infeasibility; lesson Validating inputs before the solve.

Trap Questions: Quick Answers That Are Wrong

T1. "The integrality gap is tiny here, so rounding the LP answer is good enough." Fair?

What is wrong

A small gap means a close bound, not a safe rounding: lesson The integrality gap, measured on GridCap shows a 1% gap beside a rounded plan worth only 2% of the best. Rounding up or to the nearest can also break the budget (it did on all 30 small portfolios for rounding up), and a rounded plan comes with no proof. Solve the MILP and report its bracket.

Taught in: lesson Yes/no decisions, and why rounding an LP fails; lesson The integrality gap, measured on GridCap.

T2. "Look up which solver is fastest on the public benchmarks and use it." Sound?

What is wrong

Mittelmann's public pages lost CPLEX and Xpress after 2018 and Gurobi in August 2024, so "X is fastest" cannot be checked there. Benchmark your own models: a fixed instance set, several seeds, time to a stated gap and the shifted geometric mean; start from the requirements as yes-or-no tests, and weigh license cost and container fit beside speed.

Taught in: lesson The landscape: Gurobi, CPLEX, Xpress, HiGHS, SCIP, CBC, CP-SAT; lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean; lesson Writing a solver recommendation.

T3. "The run says OPTIMAL, so the plan follows every rule." Safe to assume?

What is wrong

OPTIMAL is a claim about the model, not about the rules the business meant. A cycle of parent links or a child that can never start still solves OPTIMAL, quietly dropping or bundling projects; a loose big-M can let the integrality tolerance switch a rule off. Check the plan against the rules with code that shares nothing with the model: it reads only the data and the plan.

Taught in: lesson Parent-child bundles and all-or-nothing; lesson What a loose M does to the LP bound and to numerics; lesson Scheduling vegetation crews across circuits; lesson Property-based tests with Hypothesis.

The first code practice is that checker, for the whiteboard's rules, written before the model: in a screen, it is often the first thing asked after "how would you test it?".

  1. Coding practice

    An independent plan checker

    • check a returned plan against every rule from the data alone, and name each rule it breaks

    Not startedPassed

Problem statement

A telecom operator wants every plan its optimizer returns checked by code that shares nothing with the model: it reads only the data and the plan. Write broken_rules(plan, projects, limits) in checker.py. plan is the set of funded project ids. It returns the sorted list of labels of every rule the plan breaks, and an empty list when it breaks none:

  • "budget": the plan's total cost is above limits.budget;
  • "crews": its total crew-weeks are above limits.crew;
  • "region_<r>": more projects in region r than limits.region_cap[r]; a region with no entry in limits.region_cap has no cap, however many of its projects are funded;
  • "conflict_<a>_<b>": both projects of a pair in limits.conflicts are funded;
  • "needs_<a>_<b>": for a pair (a, b) in limits.needs, a is funded without b.

Report every broken rule, not only the first. About fifteen lines.

Summary


  • Rapid round. LP for amounts, MILP for yes/no plans, CP for dense logic and scheduling; predictions are coefficients, not plans; a product of binaries is an AND written with rows; one at-most-one row beats every pair row; a knapsack's DP is pseudo-polynomial; cover rows tighten a budget; a model that solves is checked by tests; bad inputs are caught before the model.
  • Traps. A small integrality gap does not make rounding safe; public benchmarks no longer compare the commercial solvers, so benchmark your own models; OPTIMAL is about the model, so an independent checker reads the plan against the rules.
