System Design: Scenarios Are Data, and Every Run Is Reproducible

Q1. Design the scenario workflow: planners create, copy and optimize scenarios through the planning cycle.

Model answer

A scenario is a record of inputs (data, budgets, overrides, settings) kept apart from the model, with metadata (id, name, who, when, parent) that never enters the model. Its snapshot is a hash of the inputs only, so equal inputs give equal ids, and a result is current only while its snapshot equals its scenario's. A copy shares nothing mutable with its parent. The cycle's states (Initial, Pre-Opt, Post-Opt, Budget Lock) live in one transition table that every request is checked against; a write names the version it read, and a stale write is refused (optimistic locking, the version check in the UPDATE's WHERE clause). Budget Lock needs a current optimal run, and a cycle has one plan of record. Overrides are requests checked against the data and appended to an audit trail. In the course all of this is stored in SQLite, with the database itself refusing what no caller may do (triggers freeze locked scenarios, a partial unique index allows one plan of record per cycle). Lesson Planning-cycle states and locking built the optimistic locking; lesson Storing scenarios and results in SQLite built the triggers and the partial unique index.

Taught in: lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock; lesson Scenarios as data: create, copy, optimize; lesson Manual overrides as bounds, with an audit trail; lesson Planning-cycle states and locking; lesson Storing scenarios and results in SQLite.

Q2. Follow one run from the planner's click to the result on screen.

Model answer

The API validates the request against its schema (422 for a bad body), writes the snapshot to S3 under its digest, and answers 202 with a run id. A Step Functions execution, named after the run so a retry cannot start it twice, submits an AWS Batch job on Fargate that runs the solver container from the same image as the API; the job reads the snapshot, re-hashes it, solves with pinned settings and writes the result under the snapshot's key, conditionally, so nothing is overwritten. A failed job is caught and a failed result written once. The planner's screen polls the run's status and fetches a result with the plan, money by year, value, gap, status and a message; an infeasible scenario comes back as a result, not an error.

Taught in: lesson Long solves: submit, poll, fetch; lesson Result schemas planners can consume; lesson AWS Batch on Fargate, Step Functions and Lambda: who does what; lesson S3 and a local SQLite file for snapshots and results; mock 5 (Mock 5: production, trust and performance) for the trust questions that follow.

Q3. The cloud team offers GPU instances for the solver jobs. What changes in the design?

Model answer

Less than they expect, and the GPU stays optional. The CPU path remains the default, and a GPU job falls back to it with the same answer within tolerance. The job detects a GPU when it starts rather than assuming one: in the CUDA build of HiGHS, PDLP with no GPU killed the process instead of returning an error (lesson Detecting a GPU, with a CPU fallback that gives the same answer showed it), and a container engine without the NVIDIA runtime passes no GPU through. So the design checks whether the compute environment that runs the solve offers GPUs at all, and if it doesn't, adds GPU instances as a second queue beside the CPU one. The default image stays free of CUDA; a separate, optional GPU image carries HiGHS's CUDA build and cuOpt. What goes there is large LPs, with the method fixed to PDLP so that a rerun repeats; a MILP's branch-and-bound stays on the CPU either way. The run's manifest records the device, the method and the tolerance, and a plan from a GPU MILP solve is checked for feasibility and objective on the CPU before it can reach Budget Lock.

Follow-ups. "Is it worth the instances?" Measure at your own sizes: on a 1M-variable transportation LP the GPU cut 10.3 s on the CPU to under 2 s, while a small LP gains nothing and the first solve pays about 0.2 s of CUDA start-up. "Two GPU runs disagreed; what now?" That is round 3 of lesson Mock 5: production, trust and performance.

Taught in: lesson Detecting a GPU, with a CPU fallback that gives the same answer; lesson PDLP on CPU vs. GPU: a measured comparison with HiGHS (cuPDLP-C) and OR-Tools; lesson Determinism on a GPU: what repeats, what doesn't, and what the manifest records; lesson One run policy for threads, workers and the GPU; lesson AWS Batch on Fargate, Step Functions and Lambda: who does what.

Explaining: Numbers With Their Units, Direction and Conditions

Q4. In an LP for crew planning, the dual value of the contractor-hours row is 0.07 in $k per hour. Explain it to a finance partner.

Model answer

Say its unit, its direction and its range, in the partner's units: one more contractor hour is worth $70 of value, for small changes, until another row starts to bind; the solver's ranging gives that range. Inside the range, price times amount is exact; beyond it, in a maximization, the price overstates the gain, so a large change needs a re-solve. A negative price is the marginal cost of a commitment. And if the model were a MILP, there would be no price to explain: tell finance the steps of the budget-value curve instead (mock 4).

Taught in: lesson Shadow prices, reduced costs and ranging from a solver; lesson Explaining a dual value to a finance partner; lesson The marginal value of the next dollar.

Q5. One run, three readers: planners, finance and auditors. What does each get?

Model answer

Write one record per run (inputs, snapshot, status, bound, plan, diff, priced reasons, spend, checks) and generate every text from it. Planners read projects: in, when, out, the rule behind each in words, the price of undoing it, and the close calls. Finance reads money by year against budget and against the previous plan, the change in value, and whether it is proven (NPV with its gap). Auditors read inputs, software and settings, and rule checks computed from the data that they can repeat without the model; a rerun is stated as evidence.

Taught in: lesson Writing results for planners, finance and auditors; lesson What planners, finance and regulators each need from the optimizer.

Trap Questions: Answers That Fail a Design Review

T1. "Lambda is serverless and scales, so run the solve in a Lambda function." Good design?

What is wrong

A Lambda invocation runs for at most 900 seconds, and a capital plan can take longer; Lambda does short glue (writing a failed result, routing). The solve runs neither in Lambda nor in the API process, which only answers requests: it runs as an AWS Batch job on Fargate, whose timeout is set above the solver's own limit, and Step Functions waits for it.

Taught in: lesson AWS Batch on Fargate, Step Functions and Lambda: who does what.

T2. "If the scenario is infeasible, the API returns HTTP 500." Right?

What is wrong

An infeasible scenario is an answer: 200 with status: infeasible and the planner message. 4xx is for a bad request (FastAPI's 422 for a body that breaks the schema), 5xx only for a broken server. And infeasible is reported only when proven; a limit with no plan is its own status.

Taught in: lesson A REST API with FastAPI; lesson Long solves: submit, poll, fetch.

T3. "Money not spent is carried over, so write the cash row as an equation: spend plus carry-out equals budget plus carry-in." Correct?

What is wrong

Money that is neither spent nor carried lapses, so the cash row is an inequality, $\text{spend}_y + r_y \le B_y + r_{y-1}$. Written as an equation, it forces every unspent dollar into the carry, and with a cap on the carry a plan that spends less than it could becomes infeasible: a feasible plan turns into an infeasible model.

Taught in: lesson Carry-over budgets and multi-year caps.

T4. "CapEx, OpEx and the resilience fund add up to the yearly budget, so one pooled row per year is enough." Is it?

What is wrong

One pooled budget allows plans the pots refuse: a plan can spend the fund's money on CapEx work. Each pot gets its own row per year. To find which pot's row costs the most, drop it and solve again: in an integer program a row with slack can still keep out a whole project.

Taught in: lesson Carry-over budgets and multi-year caps.

T5. "Override A costs $300k and override B $200k, so together they cost $500k." Safe to add?

What is wrong

Costs of decisions do not add up: in lesson Manual overrides as fixed bounds four overrides cost $618k one at a time and $927k together, and the costs of mandates do not add either (lesson Must-do vs. discretionary planning groups). The four together cost more than the sum of their single costs, so more than any one of them: no rule of thumb (the sum, the largest single cost, or a discount for overlap) stands in for the joint cost. Price the set by solving with all of them, and change one input at a time when you need to charge a difference to its cause.

Taught in: lesson Manual overrides as fixed bounds; lesson Must-do vs. discretionary planning groups; lesson Scenario diffs: selected, deferred, shifted.

Problem statement

A rail operator's planners ask, for every track renewal, "what would it cost to decide the other way?". costs.py already builds the one-budget selection: a binary per renewal, the budget row, a row per must-do, and the most value as the objective. Write decision_costs(projects, budget):

  • Solve once, to proven optimality (the module gives EXACT), and note which renewals are funded.

Modeling Round: Carry-Over Cash and a Regional Floor


The hiring manager: "Our budgets carry over: what a year does not spend may be spent later, but at most half of a year's budget can be carried out of it. Projects spend over several years. Each region must see at least a minimum spend over the plan. Write the model, then code it."


Model formulation
Sets. $P$ the projects; $Y = (y_0, \dots, y_n)$ the plan's years in order; $T_i \subseteq Y$ the start years of project $i$; $R$ the regions, $P_r$ the projects in region $r$.


Parameters. $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k); $\alpha$, the share of a year's budget that may be carried out of it; $F_r$, region $r$'s minimum spend over the plan's years ($k); $v_{i,t}$, the value of starting $i$ in year $t$.


Variables. $x_{i,t} \in \{0, 1\}$ for $i \in P$, $t \in T_i$; $r_y \ge 0$, the money carried out of year $y$ ($k), with $r_{y_0 - 1} = 0$. Write $\text{spend}_y(S) = \sum_{i \in S} \sum_{t \in T_i,\ 0 \le y - t < |c_i|} c_{i,y-t}\, x_{i,t}$.

Problem statement


This is the modeling round's whiteboard, coded. A water authority's model in cash.py has a start variable x[(pid, year)] per project and allowed start year, the row that each project starts at most once, spend(x, projects, year) (what a set of projects spends in one year, as an expression), and an objective. Write add_cash_rules(model, x, projects, budgets, carry_share, floors):


  • Carry-over. What a year does not spend may be carried into the next year and spent there. Money neither spent nor carried lapses. Nothing comes into the first year. The last year may carry money out too, under the same cap, but no year follows to spend it, so it lapses; giving the last year a carry variable or not changes no plan, and the tests allow both.
  • Carry cap. A year carries out at most carry_share times its own budget.
  • Floors. Each region in floors spends at least its floor in total over the plan's years (budgets lists them); spend after the last year does not count. A region in floors that can spend nothing in those years (no projects, or none that can spend inside the plan) still has its floor, so a positive floor there allows no plan. Its total is an empty sum, which in Python is the number 0, not an expression, so start the sum from mathopt.LinearExpression() to keep the floor a row.


Write the formulation first: the new variables with their domains, each row with its quantifier and a label. The tests fix the start variables and leave your other variables free, so any correct formulation passes. About twelve lines.

  • System design. A scenario is a record of inputs named by its snapshot; states live in one transition table; stale writes are refused; one plan of record per cycle; the run goes API, S3, Step Functions, Batch on Fargate, S3, poll and fetch.
