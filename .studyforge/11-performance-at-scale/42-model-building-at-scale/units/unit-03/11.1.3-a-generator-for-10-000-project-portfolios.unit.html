Performance work needs data at the size you will run, and GridCap's planners will not hand over next year's 10,000 real projects to a test suite. So the course generates them: generate("large") in the course's gridcap package makes a fictional portfolio of 10,000 projects over 10 years. A generated portfolio is only useful if it is the same portfolio every time someone asks for it, and if every portfolio it can make is one the model can use. This lesson takes GridCap's generator apart for those two properties: reproducible from a seed, and checked by a test of its invariants at many seeds, not one.

The Model

The generated portfolio feeds the timing model of lessons Start-time variables x(i,t) and timing windows and Cash-flow spreading across years, which this lesson builds once per seed to check that it is feasible.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$.

The Same Seed Gives the Same Portfolio, in This Process and in a Fresh One

A seed is the number a pseudo-random generator starts from: the same seed gives the same sequence of "random" numbers, so the same seed gives the same portfolio. GridCap's generator is built so that this holds byte for byte, on any machine, by three choices its docstring states:

  • One stream, one method. It draws every random number from one random.Random, seeded from the seed and the size, and calls only its random() method. Python's documentation guarantees that random() keeps producing the same sequence for the same seed across Python versions; it makes no such promise for the helpers built on top (randint, choice, shuffle), whose algorithms may change. The generator builds its own between and pick on random() instead.
  • Its own integer arithmetic. Money is rounded to integers by the generator's own code, so no library's rounding can change a cost.
  • No numpy random numbers. numpy promises the same stream for its Generator methods only on the same build of numpy on the same machine; a feature release may change them. That is fine for a simulation and wrong for a dataset whose hash is pinned.

Portfolio.content_hash() is the SHA-256 of the portfolio's canonical JSON (sorted keys, no spaces), so two portfolios with equal hashes are equal field for field. gridcap's own tests pin the hash of every size at the default seed. reproducible.py checks the large one, then generates it again in two fresh Python interpreters, each with a different PYTHONHASHSEED, the variable that salts Python's hashing of strings (so a set of project ids iterates in a different order):

The same seed gives the same 10,000 projects in this process and in processes that hash strings differently: nothing in the generator depends on the order of a set or a dict built from hashed keys. Another seed gives another portfolio; the 25 and 26 projects that match by id and cost profile are coincidences among 10,000 draws. The hash is what a run manifest records to say which portfolio a plan was made from (lesson Versioned input snapshots, pinned solvers and run manifests).

One Shared Stream Ties Every Draw to Every Draw Before It

A single stream has a cost that shows up the first time the generator changes. Every draw takes the next number from the stream, so adding one draw anywhere shifts every number after it, and every project generated after that point changes. streams.py shows it on a toy generator of (kind, cost, earliest start) triples, written two ways. Version 2 adds one draw, a crew size, for distribution projects only. One way draws everything from one shared stream; the other gives each project a stream of its own, seeded from the portfolio's seed and the project's position:

Each project prints as its kind's first letter, its cost and its earliest start (d162/2027 is a distribution project costing 162 that may start in 2027):

  • With one shared stream, project 4 (the first distribution project) took the new draw, and every project after it changed: different kinds, costs and starts, though nothing about them was meant to change. Every test and every lesson output that used them would change too.
  • With a stream per project, nothing that existed changed. The new draw comes last in each project's own stream, so it moves no other number.
  • Both are prefix-stable here: the first 8 projects of a 10,000-project portfolio are the 8-project portfolio, because each project's draws happen in one place, in order. A generator that drew all kinds first, then all costs, would lose that: the cost of project 1 would come after 10,000 kinds in one portfolio and after 8 in the other.
  • Per-project seeds must not collide. seed * 1_000_000 + i gives every (seed, project) pair its own number while there are fewer than a million projects. The tempting seed + i would give project 1 of seed 7 the stream of project 0 of seed 8, so two "different" portfolios would share almost every project, shifted by one.

GridCap uses one shared stream, and accepts the cost knowingly: its tests pin each size's hash, so any change to the generator fails them, and the change then has to be made on purpose, with every lesson's output regenerated in the same commit (a comment above the pinned hashes in GridCap's generator tests says so). A generator that will keep growing fields is better served by a stream per item.

Problem statement

A distribution utility (fictional) wants a test portfolio of feeders for its performance work, from a few hundred up to 100,000. Each feeder has a length (1 to 40 km), a number of customers (50 to 5,000) and the crew-days its inspection takes (2 to 20). The data will be pinned by a hash in tests and grown over time, so the generator has to keep four promises:

  • reproducible: the same n and seed give the same feeders, also in a new Python process whose PYTHONHASHSEED differs;
  • prefix-stable: the first 10 feeders of a 1,000-feeder portfolio are the 10-feeder portfolio of the same seed;
  • seeds do not overlap: seed 8 is not seed 7 shifted by one feeder;
  • every value in range, ids numbered F00001, F00002, ... in order.

Write generate_feeders(n, seed) in feeders.py, returning a list of Feeder. The helper between(draw, low, high) turns one random() draw of a random.Random into a whole number from low to high. Use only random.Random and its random() method (through between), as GridCap does, so the numbers stay the same across Python versions. The ranges allow fewer than a million feeders. About six lines.

Invariants State What Every Portfolio Must Satisfy, and a Test Checks Them at Many Seeds


A reproducible generator can still make a portfolio the model cannot use. An invariant is a rule every portfolio must satisfy whatever the seed: something a builder, a test or a lesson relies on without checking. GridCap's are the ones its generator was written to guarantee, and the ones the timing model needs:


InvariantWhy the model needs it
project ids are uniquevariable and row names are made from them, and names must be distinct
every project's asset existsasset-risk models (section 7) join projects to assets
each window lies inside the horizon, with the work ending by the last yearno cost lands in a year with no budget row
an NPV for every allowed startevery $x_{i,t}$ has an objective coefficient
a child's parent exists and can start at least the lag before the child's latest startotherwise every $\text{after}_{c,t}$ forces the child to 0
alternatives come in pairsthe $\text{alt}_g$ rows describe repair or replace
must-dos fit the yearly budget, started as early as they canotherwise $\text{must}_i$ and $\text{budget}_y$ conflict
must-dos fit the regional caps the same waymodels with regional caps were infeasible before this held


invariants.py writes each one as a check that returns a readable line per violation, so a good portfolio gives an empty list. Two of them:






The rules are necessary, but the property that matters most is the one they are for: the model has a feasible plan. That can be checked directly, without a solver. The plan "every must-do at its earliest start, nothing else" should satisfy every row, so build the model (with lesson Vectorized model building from DataFrames's matrix builder, which takes a tenth of a second) and multiply. With the matrix as three arrays, the value of every row for a plan $x$ is $Ax$, and np.bincount sums each row's terms in one call:




The program checks GridCap large at ten seeds, then plants a violation, a must-do made to cost one whole year's budget more, to show that the checks can fail:



Why ten seeds, when gridcap's own tests already check these rules? Because they check them at the default seed only, and on tiny, small and medium: the large portfolio and every other seed were never checked. An invariant is a claim about every seed. A test at one seed checks one portfolio; a test at many seeds (the module's tests use three for large, and the program ten) is what makes "the generator never does this" believable. A check that has never failed proves little either, which is why the program plants a violation and watches both the rule and the feasibility check catch it. The two answer different questions: the plant shows that a check can fail, not that other seeds pass it, and only the checks at other seeds show that.

Problem statement


A grid operator (fictional) generates planned-outage schedules for testing its maintenance scheduler: thousands of schedules from different seeds. Before any of them reaches the scheduler, each is checked against the rules every schedule must keep. An outage takes a site out of service for weeks consecutive weeks from start_week, and needs crew crews in each of those weeks.


Write violations(outages, crews_per_week) in outages.py. It returns a list of strings, one per broken rule, each starting with the rule's name and a colon; a schedule that keeps every rule gives an empty list. The rules and the lines they produce:


RuleBroken whenLine
unique idsan id is used by more than one outageunique ids: O1, once per such id
inside the yearan outage lasts no week, starts before week 1, or runs past week 52inside the year: O7
one outage per sitetwo outages at one site are out in a common weekone outage per site: O1 and O2, smaller id first
crews sufficethe outages active in a week need more than crews_per_week crewscrews suffice: week 12 needs 5, by week


active_weeks(o) gives the weeks an outage is out. The lines come in the table's order: the unique ids lines first (ids sorted), then the inside the year lines in the order the outages are listed, then the one outage per site lines (by the list position of the pair's smaller-id outage, then of the other), then the crews suffice lines by week, earliest first. Ids are compared as strings, so "smaller id first" puts O10 before O2; two outages sharing one id are left to the unique-ids rule. The crews rule counts every week an outage is active, including the weeks past 52 of an outage that also breaks "inside the year".


The tests check the rule names, the full line for the crews rule and for duplicate ids, and the full list for one schedule that breaks every rule. About fifteen lines.

Count What the Generator Puts Into the Model


The generator's knobs decide the model's size, family by family. scale.py counts both sides for every size, using lesson Vectorized model building from DataFrames's entry tables:



Here once counts the once and must rows together (one per project), starts the variables, and budget nz the nonzeros in the budget rows alone. What the table says about scale:


  • Variables grow with projects times window length: 2.0 starts per project on small, about 2.2 on medium and large, so 10,000 projects make 21,843 binaries.
  • Most rows are one per project. The once/must rows are 10,000 of large's 11,467; the after rows grow with children times their windows (882 rows for 419 children).
  • The budget rows are few and dense. Ten rows hold 35,404 of the 63,048 nonzeros, more than half, because every start variable pays into every year its project works. Each one ties thousands of projects together, where a once row ties a project's two or three starts.


A generator for performance work should be checked for this too: a portfolio ten times larger whose structure is different (no children, no must-dos, all one-year projects) would measure a different model, and the speed-ups of lesson Vectorized model building from DataFrames would not carry over.


Summary


  • The same seed gives the same portfolio, in this process and in a fresh one. GridCap draws only random() from one seeded stream, does its own integer arithmetic, and pins each size's content hash.
  • One shared stream ties every draw to every draw before it. A new draw changes every later item; a stream per item, seeded so no two collide, changes none.
  • Invariants state what every portfolio must satisfy, and a test checks them at many seeds. Eight rules, plus a feasible plan checked as $Ax$ within the row bounds, hold at ten seeds of GridCap large; a planted overspend breaks both.
  • Count what the generator puts into the model. GridCap large is 21,843 binaries and 11,467 rows, and its 10 budget rows hold more than half of the 63,048 nonzeros.

Design Note: A Generator Is Code Under Test Like Any Other


It is tempting to treat generated data as a fixture: produced once, trusted forever. But the generator is code, and its output is the input of every lesson and test downstream. So it gets what other code gets: a pinned output for the cases everyone uses (the content hashes), properties checked over many inputs (the invariants at many seeds), and a planted failure to prove the checks can fail. When a generator change breaks a pinned hash, that is the system working: decide whether the change is wanted, then regenerate on purpose.
