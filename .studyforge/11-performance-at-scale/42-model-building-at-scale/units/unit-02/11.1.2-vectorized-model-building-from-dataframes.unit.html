GridCap's planning data does not arrive as Python objects. It arrives as an export from the planning database: flat tables, one row per project, one row per start year with its NPV, one row per year of budget. The team's builder reads those tables into pandas and walks them row by row, and lesson Measuring build time vs. solve time measured the result: most of a minute for the large portfolio, spent mostly in pandas, asking the same question of a whole table thousands of times. This lesson rebuilds the same model from the same tables in about a tenth of a second, and proves it is the same model.

The Model

The timing model of lessons Start-time variables x(i,t) and timing windows and Cash-flow spreading across years, unchanged; the lesson changes only how it is built.

Sets. $P$ the projects; $Y$ the plan's years; $T_i \subseteq Y$ the start years project $i$ may use; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the budget of year $y$ ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$.

Objective.

Constraints.

The after row is written with every variable on the left, the way MathOpt stores it (lesson Model, variables, constraints, objective): $+1$ on the child's starts up to $t$, $-1$ on the parent's starts up to $t - L_c$.

Read the Data as Tables, One Row per Fact

gridcap.save_csv writes a portfolio as the flat files a planning export has (lesson Preparing model input with pandas read them into pandas). tables.py reads the four the timing model needs into a Tables object: projects (one row per project), starts (one row per allowed start year, with its NPV), costs (one row per year of work) and budget (one row per year). The projects file stores each cost profile as one text cell, "1320;1320"; a model needs one row per year of work, so the reader splits the text into a list and turns each list element into a row of its own:

explode repeats a row once per element of a list cell, and groupby(...).cumcount() numbers the rows of each project 0, 1, 2, ..., which is exactly $k$, the year of work. The file is read with keep_default_na=False, so a project with no parent has the empty text "" in parent, not a missing value, and a test like parent != "" means "has a parent". On GridCap small:

The starts table is already the list of variables: one row per $x_{i,t}$, in the order the loop builder creates them (projects in order, start years ascending). Every coefficient of the model is a fact in one of these tables, or a join of two of them.

Every Row Family Is a Table of (row, column, coefficient)

A linear model is a sparse matrix (lesson Sparse model matrices and why solvers rely on sparsity): each constraint is a row, each variable a column, and only the nonzero coefficients are stored. So build the matrix the way pandas likes to work, as a table with one line per nonzero, (row, col, coef), computed for a whole family of rows at once with joins and filters instead of loops.

First the columns. Variable number col is row number col of the starts table:

The budget family is one join. Every start variable pays its project's whole cost profile, shifted to its start year, so join the columns to the cost rows on project_id; the year that cost lands in is start + k, and that year is the row's key:

That is $c_{i,y-t}$ for every $(i, t, y)$ at once: the join pairs each $x_{i,t}$ with each $c_{i,k}$, and $y = t + k$. A cost that would land after the plan's last year finds no budget row and is dropped when the terms are matched to rows; GridCap's windows are cut so that never happens.

The after family is two joins with a filter each. One row per child and child start $t$; then $+1$ on the child's own starts $u \le t$, and $-1$ on the parent's starts $s \le t - L_c$:

The once/must and alt families are the same idea with no filter. Each family gives a table of rows (key, name, lb, ub) and a table of terms (key, col, coef); entries numbers the rows family by family, in the loop builder's order (once and must, alt, after, budget), and swaps each term's key for its row number. On GridCap small, with the entries of one child's row:

P016 may start only in 2030, so it has one after row: $x_{P016,2030} - x_{P015,2029} - x_{P015,2030} \le 0$, "P016 starts in 2030 only if P015 started by 2030". That is the formulation's $\text{after}_{c,t}$ with $L_c = 0$, read straight off the table.

    Crew-hours rows as one table

    • each family of rows is computed as a table of row, column and coefficient with joins and filters
    • the planning export is read as tables, and a packed cost profile becomes one row per year of work

    Not startedPassed

Problem statement

A transmission operator (fictional) schedules line inspections week by week. Each task may start in some weeks, and needs a given number of crew-hours in each week of its work: a three-week inspection might need 5, 0 and 3 hours (the middle week waits for a permit). Each week has a crew capacity. The planners' data arrives as two DataFrames, and you are to build the capacity rows' coefficients as one table, the way lesson Vectorized model building from DataFrames builds the budget rows.

The model's capacity rows, with $J$ the tasks, $S_j$ the weeks task $j$ may start in, $W$ the planning weeks, $h_{j,k}$ the crew-hours task $j$ needs in its $k$-th week of work ($k = 0$ is its start week) and $C_w$ the capacity of week $w$:

Write hours_entries(options, profile, weeks) in entries.py. options has one row per variable $y_{j,s}$, with columns task and start; the variable's column number is its position in options: 0 for the first row, 1 for the next, and so on. profile has columns task, k and hours. weeks lists the planning weeks.

Return a DataFrame with columns week, col and coef, one row per nonzero coefficient of the $\text{crew}_w$ rows: the variable in column col carries coef hours in week week's row. Leave out zero coefficients and weeks outside weeks, and sort the rows by week, then by column (the row-major order a ModelProto wants). Use joins and filters on whole columns; no loop over rows is needed. About eight lines.

Hand MathOpt the Whole Matrix as a ModelProto


MathOpt's Python objects (Variable, LinearConstraint) are created one call at a time, which is the per-row cost pandas just avoided. But a model also has a second form: the ModelProto, the protocol buffer that mathopt.solve exports and hands to the solver (lesson Measuring build time vs. solve time). Its fields are arrays: variable ids, bounds, integer flags and names; row ids, bounds and names; and the matrix as three parallel arrays, row_ids, column_ids and coefficients. Model.from_model_proto builds a Model from one. So the builder fills the arrays from the tables:




A proto is only valid if it keeps the rules written in OR-Tools' model.proto and sparse_containers.proto, and the builder keeps each one on purpose:


RuleHow the builder keeps it
variable and row ids are nonnegative and strictly increasingnp.arange for columns; rows numbered in order
nonempty names are distinctnames come from unique keys: project and start, family and key
matrix entries in row-major order, no (row, col) pair twicesort_values(["row", "col"]); each join gives a pair once
every row and column id in the matrix existsterms are matched to rows by merge, which drops a term with no row
an entry not listed is zerozero coefficients are left out (the proto's comments call a listed zero wasted space)


What happens when a rule is broken? proto_rules.py exports a two-variable model ($x + 2y \le 2$, row r), breaks it four ways, and loads each copy:



  • A listed zero is dropped on loading, as MathOpt drops a zero coefficient added call by call (lesson Model, variables, constraints, objective): row r has no entry for the new variable z. So a stray zero cannot make two equal models export differently; the builder leaves zeros out anyway, since they are waste.
  • Order and ids are checked when the proto is loaded, with an error that names the rule. Forget the sort and from_model_proto refuses the model at once.
  • Names are checked only at solve time, as they are for a model built call by call (lesson Model, variables, constraints, objective): the twin x loads and the solve refuses it, far from the line that made it. A builder that makes names from data must make them unique itself.


The model that comes back has no Python dictionary of variables, so read the plan through the column numbers: model.get_variable(col) returns the variable whose id is col. The program solves the small model it built:

A Fast Builder Is Correct Only If Its Exported Model Equals the Slow One's


Speed is worth nothing if the fast builder makes a different model: a budget row off by a year solves happily and plans the wrong work. So a rewrite of a builder comes with a test that the new model is the old model, and MathOpt gives a precise one. export_model() returns the whole model as one ModelProto, and two protos compare equal with == only if every id, name, bound, integer flag, matrix entry and objective coefficient agrees. The test needs no solver and no tolerance:






Three builders written three ways make byte-for-byte the same model on all three sizes. The module's tests run the same comparison at two more seeds of the medium portfolio.


Proto equality is strict about order, too: variable 0 must be the same variable in both. When a check fails, == says only "different". same_model.py then compares the models by name: canonical turns a model into dictionaries keyed by variable and row names, which leaves out the order things were added in, and differences lists the names that disagree.




The program compares the loop builder's small model with three others: the matrix builder's; the matrix builder fed the starts table sorted by year first, so its variables come in another order; and the matrix builder fed cost rows shifted one year late, the off-by-one a rewrite can introduce:



Read the three lines together:


  • Equal protos settle it. The matrix model is the loop model.
  • Unequal protos with no differences by name mean the same model in another order. It solves to the same optimum, but a test that wants byte equality must build in the reference's order, which is why entries numbers rows family by family exactly as the loop builder adds them.
  • Differences by name are a real bug, and they say where: the 2027 budget row lost every term, and each later row holds the previous year's costs.


Comparing by name with == on coefficients works here because both builders compute every coefficient from the same integers. When two builders compute a coefficient by different arithmetic (a discount factor multiplied in a different order, say), the floats can differ in the last digit while the models mean the same thing; then compare coefficients with a small relative tolerance, as lesson Testing numerical code with pytest: tolerances, fixtures, parametrize does for numbers in tests, and keep bounds, integer flags and names exact.

Problem statement


GridCap's finance team rewrote the NPV calculation behind the objective. The new code discounts each year's benefit in a different order of multiplications, so a few coefficients now differ from the old builder's in the last binary digit, and it also creates variables in a different order. An exported-proto comparison calls every such pair of models different. The team wants a check that calls them the same model and still catches every real change.


Write same_model(a, b, rel_tol=1e-9) in compare_models.py. It compares two MathOpt models by name, so the order variables and rows were added in does not matter, and returns True when they state the same model:


  • the same variable names, each with the same bounds and the same integer flag;
  • the same row names, each with the same bounds and the same set of variables in its terms;
  • the same objective sense (maximize or minimize) and the same set of variables in the objective;
  • every coefficient, and the objective's offset, equal within a relative tolerance: use math.isclose(x, y, rel_tol=rel_tol, abs_tol=0.0).


Names, bounds, integrality and sense are compared exactly: none of them comes from arithmetic that rounds. A variable that appears in one model's row and not in the other's is a difference, even if the other model would have given it a coefficient near 0. Read a model with model.variables(), model.linear_constraints() and row.terms(), and model.objective with its is_maximize, offset and linear_terms() (lesson Model, variables, constraints, objective). Run the file to see why exact comparison fails: 0.1 * 3 == 0.3 is False in floating point. About twenty lines.

Vectorizing Pays at Scale and Costs on Small Models


With the identity settled, the timings mean something. speedup.py times all three builders in one process, five repeats each after a warm-up (one repeat for the slow builder on large, which takes most of a minute). One run on the author's machine; yours will differ:




  • At 10,000 projects the matrix builder is about 300 times faster than the slow builder and about 6 times faster than the loops. It builds GridCap large in about a tenth of a second, the section's milestone of a large portfolio "built in seconds" with room to spare.
  • On small, the matrix builder is the slower of the two fast ones. Each pandas operation has a fixed cost, and the matrix builder does a few dozen of them whatever the size; with 80 variables that fixed cost is all there is, so the loops win, 0.002 s against 0.018 s.
  • The loop builder is fast because it has no hidden scans. It walks Python objects it already has, with dictionary lookups. The slow builder's problem was never Python loops as such; it was a full-table scan inside a loop (lesson Measuring build time vs. solve time).


So the order of work for a slow builder is: measure, find the repeated scan, replace it with a join or a dictionary built once, check the exported model is unchanged, and only then measure again. Most of the speed comes from the first fix; going all the way to arrays pays when the model is large or rebuilt often.


Summary


  • Read the data as tables, one row per fact. explode and groupby(...).cumcount() turn a packed cost profile into one row per year of work; the starts table is the list of variables.
  • Every row family is a table of (row, column, coefficient). Joins pair variables with the data that gives their coefficients, and filters keep the pairs a row's quantifier allows.
  • Hand MathOpt the whole matrix as a ModelProto. Model.from_model_proto takes arrays; the proto's rules (increasing ids, distinct names, row-major entries) are the builder's to keep, and zeros are dropped.
  • A fast builder is correct only if its exported model equals the slow one's. export_model() compared with == needs no solver; when it fails, a comparison by name says what differs.
  • Vectorizing pays at scale and costs on small models. 300 times faster than the slow builder on GridCap large, slower than plain loops on GridCap small.

Design Note: Keep a Slow, Obvious Builder as the Reference


The matrix builder is harder to read than the loop builder: the after family is two joins and two filters where the formulation has two sums. That is the price of speed, and the reason this module keeps build_loops around even though it is never the fastest. It reads like the formulation, so a reviewer can check it against The Model line by line, and the identity test then carries that review over to the fast builder for free. When the model changes, change the obvious builder first, then make the fast one equal it again.
