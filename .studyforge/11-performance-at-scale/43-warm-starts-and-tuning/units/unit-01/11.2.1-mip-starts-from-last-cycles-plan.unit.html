GridCap re-plans its capital portfolio every January. Last January the Ridge region's ten-year plan was solved to optimality and approved. Now 2027 is over: the twelve projects the plan started in 2027 are under way, finance has revised the budgets, the engineers have re-costed some projects, and five new candidates have been added. The planners solve again, and the obvious question is the one lesson Solution hints and ModelSolveParameters raised: can the solver start from last year's plan instead of from nothing? Lesson Solution hints and ModelSolveParameters showed how to hand MathOpt a hint. This lesson is about what to hand it and whether it helps: how last cycle's plan becomes a start for this cycle's model, why it usually needs repair first, how each solver reports what it did with it, and how to measure the effect without fooling yourself. GridCap is a fictional utility; its numbers are teaching data.

A MIP start (Gurobi's name; MathOpt calls it a solution hint, CP-SAT a hint) is a complete or partial assignment of values to a model's integer variables, given to the solver before it begins. If the solver accepts it as a feasible plan, that plan is its first incumbent, the best plan found so far (lesson Primal heuristics: rounding, diving, RINS). A start never changes which plans are allowed or which one is optimal.

The Model

The multi-period timing model of lesson Start-time variables x(i,t) and timing windows, for one region. One region of a GridCap medium portfolio, about 80 to 110 projects, is small enough to solve to optimality hundreds of times, which is what a benchmark over many runs needs. plan_model.region_portfolio keeps one region's projects (a child only if its parent is in the region) and scales each year's budget to the region's share of the portfolio's spend, raised where needed so that every must-do project fits at its earliest start.

Sets. $P$ the region's projects; $Y$ the plan's years, ten of them; $T_i \subseteq Y$ the years project $i$ may start in; $M \subseteq P$ the must-do projects; $\mathcal{G}$ the alternative groups; $C \subseteq P$ the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $\text{npv}_{i,t}$, the NPV of project $i$ started in year $t$ ($k); $c_{i,k}$, what project $i$ spends in its $k$-th year of work ($k); $B_y$, the region's budget in year $y$ ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$.

This cycle's model has the same rows over new data: $Y$ is the next ten years, $P$ loses the projects already committed or whose windows have passed and gains new candidates, each $T_i$ loses the year that is over, and $B_y$ and some $c_{i,k}$ are revised. A start is a value $\hat x_{i,t} \in \{0, 1\}$ for some or all of this cycle's variables. It is advice to the solver, not a row: nothing above changes when a start is given.

A Plan Rolls Forward One Year, and Its First Year Becomes Fixed

A multi-period model is normally used in a rolling format: solve it, carry out the first period's decisions, and a period later slide the model forward one period with better data and solve again. LINDO's text on multi-period planning (chapter 9) describes exactly this, and the risk that comes with it: the new optimum can differ sharply from the last one, which the people carrying it out find unsettling. cycles.next_cycle builds next year's model from this year's portfolio and the approved plan:

The projects the plan started in the year that is over are committed: they are being built, so they are no longer decisions, and what they will still spend comes off the later budgets. The horizon loses 2027 and gains 2037. Then the new data arrives, drawn from a seeded random generator so that every run of the course sees the same next cycle: each budget revised by $-3\%$ to $+3\%$, one project in eight re-costed 20% higher (its NPV drops by the extra cost), and five new candidates. A project whose window has passed without a start drops out, and so does a child whose parent can no longer start. A child of a committed parent keeps its lag as an earliest start year:

Two of the first five budgets went up and three went down, by a few percent. That is a quiet year. It is still enough to make last year's plan illegal, as the next sections show.

Last Cycle's Plan Must Be Mapped Onto This Cycle's Variables

A start is given per variable, and this cycle's variables are not last cycle's. A decision of the old plan, "P031 starts in 2030", carries over only if this cycle's model still has the variable $x_{P031,2030}$. Three things can happen to each old decision and each new variable:

  • kept: the project is still a decision and its old start year is still in its window, so the start gives that variable 1;
  • no variable: the project is committed (its start year is over) or dropped, so the old decision has nowhere to go;
  • new: a project with no old decision. A complete start gives each of its variables 0, which means "not funded" until the solver finds otherwise.

Of the plan's 59 starts, 47 still have their variable, and the 12 without one are exactly the 12 committed projects. The new candidates are numbered N001 to N005 by next_cycle, which is how carry_forward tells them apart. The carried plan is still a plan in the data sense, a dict from project to year, and turning it into a complete start is one more line: 1 for each variable the plan uses, 0 for every other variable of the model.

Why complete? A partial start (values for only some variables, typically only the 1s) leaves the solver to fill in the rest by solving a small MIP of its own, which lesson Solution hints and ModelSolveParameters's HiGHS log showed and which costs work. Gurobi's documentation says the same of its partial MIP starts: completing them means solving subproblems, which can be expensive, and its StartNodeLimit parameter caps the nodes spent on it. HiGHS has the same kind of cap, the option mip_max_start_nodes (500 nodes by default, per its option list).

Problem statement

A city transit agency re-plans its bus replacements every January. Last year's approved plan, old_plan, maps each bus it replaces to a year. This year's model has one binary variable $x_{b,y}$ for each bus $b$ and each year $y \in W_b$ it may now be replaced in, given as windows[b]. The year first_year has just begun: the replacements planned for it are under way, so they are commitments, not decisions. Some buses are new to the list this year, and some old years are no longer allowed (a supplier moved a delivery).

Before you code, write the rule in this notation: for each $b$ and $y \in W_b$, what value $\hat x_{b,y}$ the start gives, in terms of last year's year $s_b$ (when $b$ was in the old plan) and the first year $y_0$; and which buses form the committed set.

Write two functions in fleet.py:

  • committed(old_plan, first_year) returns the set of buses last year's plan replaces in first_year.
  • carry_forward(old_plan, windows, first_year) returns a complete start: a dict with one value, 1.0 or 0.0, for every (bus, year) of windows. It keeps last year's decision wherever this year's model can still express it, and gives no other year a 1.

windows may still list a committed bus (one replaced in first_year), even with first_year among its years. That bus is already being replaced, so it is not a decision to hint: the start gives it 0.0 in every year of its window. Only a replacement planned after first_year is carried forward as a 1.

The tests call your functions with small plans; no solver runs. About ten lines.

Check the Start Against This Cycle's Rows Before Any Solver Sees It


Last year's plan was optimal for last year's data, which means it used nearly every dollar of every budget. This year three of the first five budgets are lower and fourteen projects cost more. Before handing the carried plan to any solver, check it against this cycle's rows. plan_model.broken evaluates a plan, as data, against every row of the model and returns the names of the rows it breaks:




The carried plan breaks eight of the ten budget rows. It is not a plan of this cycle's model, and its NPV, 40,005, means nothing. Two steps turn it into one:


  1. Repair: while a budget row is broken, drop the optional project with the least NPV per $k among those spending in a broken year, and its children with it. Must-do projects are never dropped. Eight projects go, and the plan fits: 36,251.
  2. Fill: the repair freed money, and new candidates have none of it yet. Add the projects the plan leaves out, best NPV per $k first, each at its earliest start year that keeps every row (the greedy fill of lesson Primal heuristics: rounding, diving, RINS, now over start years). Sixteen projects come in: 37,809.



The greedy row is the same fill run from nothing but the must-do projects: a start that needs no last cycle at all. It is worth 33,512, 16.5% below this cycle's optimum of 40,136; the repaired and filled plan is 5.8% below. Over all eight regions, rolled forward the same way:



Every carried plan breaks between four and nine budget rows. The repaired and filled plan is within 2.7% to 6.7% of the optimum, and it beats the greedy plan on seven of the eight cycles; on Coast-1 the greedy plan is closer. (Names ending in -2027 and -1 are the medium portfolios drawn with seeds 2027 and 1.) So the rule: a plan carried from last cycle is a draft, never a start. Check it against this cycle's rows, repair it, and fill it before any solver sees it. The next section shows what happens when you skip that.

Problem statement


A water utility renews pipe in one-year jobs. Each job $j$ has a cost $c_j$ ($k, all spent in the year it is done), a value $v_j$ ($k), the years $Y_j$ it may be done in (earliest first), and a must-do flag. Each year $y$ has a budget $B_y$. The planners' model has a binary $x_{j,y}$ for each job and each $y \in Y_j$, at most one year per job (exactly one for a must-do), and one budget row per year. Solves are stopped early on busy nights, so they want a plan in hand from the first moment: a greedy one, handed to the solver as a start.


Before you code, write the greedy rule as an order on the jobs and a placement rule: which jobs come first, how the others are ranked (ties by name), and which year a job takes given the money left in each year, $B_y - \sum_{j' \text{ placed in } y} c_{j'}$. A job that fits no year is left out. The must-do jobs come first and are ranked among themselves by the same rule as the others, so when two must-do jobs compete for one year, the one with more value per $k gets it.


Write two functions in renewal.py:


  • greedy_plan(jobs, budget) returns {job name: year} for the jobs the rule places.
  • as_hint(x, plan) turns a plan into a mathopt.SolutionHint for the variables x[(name, year)]. Give the solver a complete start, as lesson MIP starts from last cycle's plan does.


One test builds the model and asks HiGHS, through MathOpt, whether it accepts your start, by reading its log. About fifteen lines.

Each Solver Says in Its Own Words Whether It Took the Start


start_logs.py hands four starts to HiGHS and SCIP through MathOpt (lesson Solution hints and ModelSolveParameters's ModelSolveParameters(solution_hints=[...])) and to Gurobi through its own API, where a MIP start is the Start attribute of each variable:



and keeps only the log lines about the start. The four starts are the carried plan and the repaired-and-filled plan, each given complete (every variable, zeros included) and as its 1s only:



(<t> masks a time, which changes on every run.) Read it start by start:


  • The carried plan, complete. HiGHS rejects it in one line. Gurobi names the first row it breaks (budget_2028, overspent by $120k), tries once more to repair it, and gives up. SCIP says nothing: its log does not show the start at all. None of the three gets a plan out of it, and for HiGHS and SCIP the program checks that the whole run was the one they make with no start at all:



  • The carried plan, 1s only. HiGHS and Gurobi both try to complete it and fail: fixing 47 starts that already overspend 2028 leaves nothing feasible to complete. Leaving out the zeros does not make an infeasible start feasible.
  • The repaired plan, complete. All three accept it as their first incumbent, worth 37,809. This is the only case where every solver's log confirms the start.
  • The repaired plan, 1s only. HiGHS and Gurobi complete it (HiGHS solves a MIP over the 137 variables left free) into the same plan. SCIP's log is silent again.


Gurobi's documentation lists these messages: "Loaded user MIP start" for a start accepted as it is, "User MIP start produced solution" for one it repaired or completed, and "did not produce a new incumbent" for one it discarded. It also separates the MIP start from a variable hint (VarHintVal, with a confidence VarHintPri): a start asks the solver to build one feasible plan from the values, while hints steer heuristics and branching through the whole solve and need not be feasible. MathOpt's SolutionHint and CP-SAT's add_hint are, despite the name, starts in this sense; lesson Hints, assumptions and SufficientAssumptionsForInfeasibility showed CP-SAT trying to repair an infeasible one.


The rule: only the log, read with and without the start, tells you whether a solver used it (the MathOpt SolutionHint docstring says so too). A silent log, as SCIP's is for three of the four, means you do not know.


A Start Is Measured by the Work to a Good Plan, Over Seeds and Cycles


Does an accepted start make the solve faster? "It found the optimum, and the start was in the log" proves nothing; lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean showed that one run, or one seed, can show a speed-up that is not there. So the measurement follows lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean's rules:


  • A fixed instance set, chosen first: the eight next-cycle models above.
  • Several seeds: 1, 2 and 3, each (cycle, seed) one paired observation, 24 in all.
  • Deterministic work, not seconds: HiGHS and SCIP count LP iterations; Gurobi counts work units (its documentation: very roughly a second, depending on the machine and the model), read here in thousandths. Every run uses one thread.
  • Ratios of shifted geometric means, with the count of observations where the start needed less and more work (W/L).


And one thing lesson Honest benchmarking: instance sets, seeds, time-to-gap, shifted geometric mean did not need: the work at which each plan was found. A MIP solver reports every new incumbent as it finds it; runs.py records each as a pair (work, NPV). SCIP calls a MathOpt callback on Event.MIP_SOLUTION, whose mip_stats carry the LP iterations so far. (The callback.py docstring lists Gurobi and CP-SAT for this event; SCIP calls it too here, and prints two ERROR lines on standard error when a callback is registered, while solving normally.) HiGHS ignores MathOpt callbacks (lesson Callbacks and compute_infeasible_subsystem), so its plans are read from its log's progress table, where each row that shows a better BestSol is a new plan at LpIters. Gurobi's callback reads GRB.Callback.WORK at each MIPSOL.



From the events, three measures. The time to first incumbent is the work at the first event, and "its gap" is how far that plan is below the cycle's optimum. The work to 1% is the work at the first plan within 1% of the optimum. The work to proof is the whole run's work, with the gap tolerance at 0:






What the three tables say:


  • Every solver finds a first plan with almost no work, start or no start. The time to first incumbent rounds to 0 in every row: before the first LP iteration, the solvers' own trivial heuristics have something. What the start changes is that first plan's quality: 4.2% below the optimum against 80.2% (HiGHS), 24.1% (SCIP) and 29.4% (Gurobi). Measured alone, "time to first incumbent" would call the start useless; measured with the plan's gap, it is the start's whole effect.
  • The work to a plan within 1% hardly moves, and can get worse. HiGHS 0.97 with 9 wins and 11 losses; SCIP 1.21, worse, losing 12 of 20; Gurobi 0.84 but losing 13 of 22. The solvers' own heuristics find plans within 1% within a few hundred LP iterations anyway, and a start changes the search's path, which can delay them.
  • The work to proof is about the same. SCIP's 0.88 (18 wins, 6 losses) is the one consistent gain; HiGHS's 1.00 and Gurobi's 0.95 are noise-sized. Proving optimality means pushing the bound down to the optimum (lesson Best bound, incumbent, absolute and relative gap), and a start does nothing for the bound.
  • The carried, infeasible start changed Gurobi's path (its rows differ from "none") without ever becoming a plan; HiGHS and SCIP dropped it, so it is not in their tables (start_logs.py shows why).


So the common advice is right that a good start gives the solver an incumbent at once, and so a bound to prune with; on these models that did not translate into a faster proof, except a 12% saving for SCIP. Measure it on your own models before promising it.

Problem statement


A hospital builds its nurse rosters with a MIP that minimizes cost, and its scheduling team wants to know whether starting each solve from last month's roster helps. For each run the solver's callback records an event $(w_k, z_k)$ every time it reports a plan: $w_k$ is its deterministic work at that moment and $z_k$ the plan's cost. The events come in the order found, and a solver may report a plan that is no better than one it already had.


Before you code, write each measure in this notation, for a run with events $(w_1, z_1), \dots, (w_n, z_n)$:


  • the work to the first plan;
  • the work until a plan within a share $\sigma$ of the best known cost $z^*$ was found (say what "within" means as an inequality on $z_k$, for any sign of $z^*$);
  • the plan in hand after $W$ units of work: the cost of the best plan found by then.


Write work_to_first(events), work_to_within(events, best, share) and in_hand(events, budget) in incumbents.py. A measure with no plan to report is math.inf for work and None for a cost. The tests pass small event lists; no solver runs. About six lines.

A Start Is Insurance for a Solve That Is Stopped Early


If the start barely speeds up the proof, why give one? Because real solves are stopped: by a time or work limit, by a gap target, by the night ending. A stopped solve returns the best plan it has. The second half of each program asks what that plan is worth after a fixed amount of work: the mean gap, over the 24 observations, of the best plan found within that much work.





The tables are HiGHS, SCIP and Gurobi, in that order. At zero work the plan in hand can be better than the first plan of the tables above, because a solver may find several plans before its first LP iteration and keeps the best. Stopped after 50 LP iterations, HiGHS without a start hands back a plan 24% below the optimum on average; with the repaired start, 4.2%. Gurobi stopped at zero work has no plan at all without a start. By 1,000 LP iterations (or 20 thousandths of a Gurobi work unit) every row is within about half a percent, and the start's advantage is gone; SCIP's and Gurobi's repaired rows are even slightly behind there. The last line of each program solves the eight repaired-start runs of seed 1 again and checks that every number repeated, so these tables can be quoted.


That is what a start buys: a floor under the plan a stopped solve returns, at no cost to the answer of a solve that finishes. It is worth most when solves are stopped early, which is the normal case for large models such as the 10,000-project portfolio of lesson A generator for 10,000-project portfolios, and inside the heuristics of lesson Rolling horizon and LNS heuristics. And because the greedy plan, which needs no last cycle, gives most of the same floor, a new model with no history can still start from something.


Summary


  • A plan rolls forward one year, and its first year becomes fixed. Committed projects leave the decisions and their remaining spend leaves the budgets; the horizon slides one year.
  • Last cycle's plan must be mapped onto this cycle's variables. Keep a decision where its variable still exists, drop it where it does not, give new projects 0, and hand over a complete start.
  • Check the start against this cycle's rows before any solver sees it. Every carried plan broke four to nine budget rows; repaired and filled, it came within 2.7% to 6.7% of the optimum.
  • Each solver says in its own words whether it took the start. HiGHS, SCIP and Gurobi all logged the repaired complete start; the carried one was rejected or silently dropped; SCIP's log was silent on three of the four starts.
  • A start is measured by the work to a good plan, over seeds and cycles. On 24 paired runs the start cut the first plan's gap from 24% to 80% down to 4.2%, barely changed the work to 1%, and saved 12% of the proof only for SCIP.
  • A start is insurance for a solve that is stopped early. After 50 HiGHS LP iterations the plan in hand was 4.2% from optimal with the start and 24% without; by 1,000 the difference was gone.

Design Note: A Start Is Data You Can Test


start_effect.py never hands a solver a start it has not first checked with broken, and starts.py works only on plans as dicts. That keeps the expensive question ("does it help?") separate from the cheap one ("is it a plan?"). The cheap one runs in microseconds, needs no solver, and catches the mistake that cost every carried start here its value. Write the repair and the check as plain functions with tests, as the practices do, and the solver only ever sees starts that are plans.
