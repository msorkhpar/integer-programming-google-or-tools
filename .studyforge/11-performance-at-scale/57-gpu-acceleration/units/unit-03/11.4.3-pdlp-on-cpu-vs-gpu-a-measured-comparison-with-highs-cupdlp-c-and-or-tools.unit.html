  16. CPU against GPU, measured

GridCap's infrastructure team has to decide whether the nightly LP runs need a GPU. The vendor slides say "up to 100× faster". The team's question is narrower: faster than what, on which LPs, at which accuracy, on our machine? This lesson builds the program that answers it: one model generator, every solver the machine has, every answer checked against a CPU reference, and the times printed beside the accuracy. It runs on every machine; the GPU columns appear only where there is a GPU. The numbers below are one machine's, and the lesson says so wherever it quotes them. GridCap is a fictional utility; its numbers are teaching data.

The Model

The transportation LP of lesson Detecting a GPU, with a CPU fallback that gives the same answer, grown: $n$ sources and $n$ destinations, $n^2$ variables, $2n$ rows and $2n^2$ nonzeros.

Sets. $S$ the sources and $D$ the destinations, $\lvert S \rvert = \lvert D \rvert = n$.

Parameters. $a_i = 10n + (i \bmod 7)$, the supply of source $i$; $d_j$, the demand of destination $j$, the total supply split as evenly as integers allow; $k_{i,j} \in \{1, \dots, 99\}$, the unit cost, from a fixed-seed generator (the seed the toolchain's GPU probes used, so its measurements and these describe the same LPs).

Variables. $x_{i,j} \ge 0$, the units moved from $i$ to $j$.

Objective.

Constraints.

The sizes run from $n = 30$ (900 variables) to $n = 1000$ (a million variables, two million nonzeros), the largest size this lesson runs, which leaves the build machine's 8 GB card room to spare.

A Fair Comparison Runs Every Solver on the Same Model and Checks Every Answer

compare.py builds each LP once and hands the same numbers to each solver:

  • HiGHS interior point on the CPU (solver="ipm"), the reference: it converges to $10^{-8}$ by default and its answer is the yardstick for the others;
  • OR-Tools PDLP on the CPU, one thread, at its default $10^{-6}$;
  • HiGHS PDLP on the GPU (cuPDLP-C, solver="pdlp"), at HiGHS's default pdlp_optimality_tolerance, $10^{-7}$, only where gpu_available();
  • cuOpt PDLP (method set to PDLP), at its default tolerance, $10^{-4}$ relative, only where gpu_available().

Every answer is compared with the interior point objective, relatively. The CPU half runs on every machine and prints the same numbers everywhere:

OR-Tools' PDLP lands within $10^{-7}$ of the interior point objective at every size. Its iterations barely grow with the size: 960 for 900 variables, 1,536 for 90,000. That is the first reason first-order methods scale: the work per iteration grows with the nonzeros, and on this family the number of iterations hardly does.

Three rules make the comparison fair. The model is built once and every solver reads the same numbers, so a difference is the solver's, never the builder's. Times cover the solve alone, not the model building (lesson Measuring build time vs. solve time measured the two apart). And no time is quoted without the accuracy that was bought with it, because a solver that stops at $10^{-4}$ is doing less work than one that stops at $10^{-8}$.

Handing HiGHS a Whole Model: highspy.HighsLp

The module's highs function, like the first practice below, does not add variables and rows one call at a time: it fills one highspy.HighsLp object with the whole model and passes it to HiGHS with passModel. highs_lp.py shows every field on a three-variable toy (not GridCap data): maximise $5x_0 + 4x_1 + 2x_2$ subject to $2x_0 + 3x_1 + x_2 \le 5$ (cap) and $x_0 + x_1 + 2x_2 \ge 1$ (need), with $x_0 \ge 0$ integer, $0 \le x_1 \le 1$ and $x_2 \ge 0$. It builds the matrix both ways:

  • num_col_ and num_row_ give the sizes; col_cost_, col_lower_ and col_upper_ hold one entry per variable, row_lower_ and row_upper_ one per row. A row with one side gets highspy.kHighsInf (or its negative) on the other, as in lesson Why first-order LP methods suit a GPU: PDHG and PDLP's two-sided rows.
  • The matrix is three lists. Column-wise (MatrixFormat.kColwise), start_[k] is where column $k$'s entries begin in index_ (their row numbers) and value_, and start_ ends with the number of entries; row-wise (kRowwise, the form lps.highs uses) is the same with rows and columns swapped. Both give the same answer above.
  • integrality_ holds one HighsVarType per variable (kInteger or kContinuous); left unset, the model is an LP, which is why the third line reaches 12.5 with $x_0 = 2.5$.
  • sense_ is ObjSense.kMaximize or ObjSense.kMinimize.

Problem statement

A distributor ships from $m$ depots to $n$ customers. Depot $i$ holds $a_i$ units, customer $j$ needs $d_j$, a unit on route $(i, j)$ costs $k_{ij}$, and each route can carry at most $q_{ij}$ units. A depot need not ship everything it holds. The team wants the cheapest shipping plan, and it wants the LP handed to HiGHS in the column-wise form that GPU solvers read fast, so that the same model object runs on the CPU and, where there is one, on the GPU.

Before you code, write the formulation: the variables with their bounds, the objective, and one labelled row per depot and per customer, with the direction of each. Then build it in routes.py: build(supply, demand, cost, cap) returns a highspy.HighsLp with the depot rows first (rows $0 .. m-1$), the customer rows after them (rows $m .. m+n-1$), and variable $i \cdot n + j$ for route $(i, j)$. Store the matrix column-wise (highspy.MatrixFormat.kColwise): start_[k] is where column $k$'s entries begin in index_ (the row numbers) and value_. solve(lp, solver) is given. On the GPU image with a GPU, test_the_routes_are_solved_at_the_cheapest_cost also solves your model with HiGHS's GPU PDLP. On a machine without a GPU that test runs its CPU part only, and it says nothing about the GPU part: no test is reported as skipped. About fifteen lines.

On the Build Machine's GPU, the Large LPs Are Where It Pays


The course ran compare.py 30 100 300 1000 once on its build machine: an 8 GB laptop NVIDIA GPU, in the GPU image (driver CUDA 13.2, runtime CUDA 13.3.29, HiGHS 1.14.0 built with CUDA, cuOpt 26.10.0). Times are wall seconds of one run; cuOpt's column is cuOpt's own solve time, which leaves out its process start and imports. They depend on the machine, its load and the run, and your numbers will differ:




At a million variables the GPU wins clearly: HiGHS's PDLP took 2.4 s against 13.0 s for the interior point on the CPU, 5.4 times faster, and cuOpt's PDLP 1.1 s, 11.6 times faster. At $n = 300$ the two GPU solvers and the CPU interior point are within a factor of two. At $n = 100$ and below, the CPU wins by a wide margin: the interior point needed 0.007 s for 900 variables, and neither GPU solver finished in less than 0.18 s.


The CPU PDLP column shows that the algorithm alone is not the speed-up. On the CPU, OR-Tools' PDLP is slower than the interior point at every size up to 300 and only a little faster at 1,000. PDLP pays off when its matrix-vector products run on the card.


Small LPs Lose to Start-Up and Fixed Costs


A GPU solve has costs that do not depend on the LP's size: copying the model to the card's memory, starting its kernels, copying the answer back, and, for the first GPU solve in a process, starting CUDA itself. compare.py measures that on a 100-variable LP before anything else:




The first GPU solve took about 0.2 s more than the second, which is CUDA starting up; and even the second took 0.21 s for an LP the CPU solves in milliseconds. Those are fixed costs, and a small LP never earns them back. The HiGHS documentation says the same: the GPU helps mainly on large LPs, and on small ones PDLP on a GPU can be slower than on the CPU. A service that solves many small LPs keeps them on the CPU, and one that sends a large LP to the GPU starts CUDA once per process, not once per solve. GridCap small's LP, at 80 variables, is a CPU job.


Accuracy Differs by Default: 2e-9 Against 3e-5


The GPU answers on the same run, against the CPU interior point:




The two GPU solvers run the same kind of algorithm and stop at different places. HiGHS's PDLP lands within $2 \times 10^{-9}$ of the optimum on the large LPs; cuOpt's within about $3 \times 10^{-5}$, because its default tolerance is $10^{-4}$ relative (its documentation lists PDLP's default accuracy as $10^{-4}$, against $10^{-8}$ for its barrier method). cuOpt's plan for the million-variable LP breaks a row by 20 units. Each supply row holds about 10,000 units, so that is 0.2% of one row; the tolerance is measured against the norm of all 2,000 row bounds together, not row by row (lesson Why first-order LP methods suit a GPU: PDHG and PDLP).


So part of cuOpt's lead in the time table is accuracy it did not buy. Before comparing times, either set the solvers to the same tolerance or state each one's beside its time, as this lesson does. And a planner who needs every supply row kept to the unit cannot use a $10^{-4}$ answer as it is, from any device.

Problem statement


An analytics team has timed its LP solvers on its own machine: several CPU and GPU solvers, several LP sizes $n$, each run repeated. Each record holds the solver, the device ("cpu" or "gpu"), the size n, the seconds, whether it was the process's first GPU solve (first_in_process), and its rel_error against a CPU reference. They want two numbers per decision, computed by a rule, not by eye:


  • speedups(records, needed): for each size, the speed-up = (best CPU solver's time) / (best GPU solver's time), where a solver's time is the median of its runs at that size, a process's first GPU solve is left out (it also starts CUDA), and a GPU solver counts only if every run of it at that size has rel_error <= needed. A run left out as a process's first is left out of that accuracy check too: an inaccurate first run does not disqualify its solver. The value is None when no GPU solver counts, and None when the size has no CPU run (there is nothing to compare with). Return a dict from every size in the records to its speed-up.
  • crossover(table): the smallest size from which the GPU is faster (speed-up above 1) at that size and at every larger size in the table, or None.


Write both in speedup.py. The tests pass lists of records; no solver runs. About twenty lines.

Summary


  • A fair comparison runs every solver on the same model and checks every answer. One builder, times of the solve alone, and an accuracy beside every time.
  • On the build machine's GPU, the large LPs are where it pays. At a million variables HiGHS's GPU PDLP was 5.4 times and cuOpt's 11.6 times faster than the CPU interior point; at 10,000 and below the CPU won.
  • Small LPs lose to start-up and fixed costs. About 0.2 s to start CUDA once per process, and about 0.2 s per GPU solve even on a 100-variable LP.
  • Accuracy differs by default: 2e-9 against 3e-5. HiGHS's PDLP stops at $10^{-7}$, cuOpt's at $10^{-4}$; cuOpt's million-variable plan broke a row by 20 units.

Design Note: The Comparison Prints What It Did Not Measure


compare.py prints its CPU half on every machine and its GPU half only where there is a GPU, and the times table is labelled "this machine, this run". That keeps the program honest wherever it runs: a learner without a GPU sees exactly what their machine did, the course's page states which numbers came from the build machine, and the times never pretend to be a property of the algorithm.
