  16. What repeats on a GPU

GridCap's regulator can ask, months later, for the exact run behind an approved plan. Section 10 built the answer for the CPU: pinned solvers, one thread or a deterministic work limit, and a run manifest that records what went in and what came out, so a rerun can be compared with it (lessons Seeds, threads and deterministic work limits, solver by solver and Versioned input snapshots, pinned solvers and run manifests). Now part of the nightly work runs on a GPU. This lesson measures what repeats there and what does not, and changes the manifest so that it records the device, the method and the tolerance, and so that its comparison asks for equal bits only where they were promised. GridCap is a fictional utility; its numbers are teaching data.

Two words used throughout. Two runs are bit for bit the same when the objective and every value of the plan are equal as stored numbers, byte for byte; a 16-hex-digit digest (the start of a SHA-256 hash of those bytes) stands for them, and equal digests mean equal bits. Two runs agree within tolerance when their objectives differ by at most a stated relative amount and both plans keep the rows (lesson Detecting a GPU, with a CPU fallback that gives the same answer).

On the CPU, a Fixed Solver, Method and Thread Count Repeat Bit for Bit

repeat.py runs each solver twice in one process on each LP and compares the digests:

Every configuration repeated itself, including PDLP on four threads. But the four-thread run is not the one-thread run: it took 1,536 iterations instead of 1,472 and ended on different bits. The comment on num_shards in OR-Tools' solvers.proto gives the reason: PDLP splits its vectors into shards for the threads, the roundoff depends on the number of shards, and reproducible results need the same number. So the thread count is part of what a run promises, as lesson Seeds, threads and deterministic work limits, solver by solver found for the MIP solvers.

The same programs printed the same digests in the CPU image and in the GPU image on the build machine:

The GPU image's highspy is a different build of HiGHS 1.14.0 (compiled with CUDA, yet reporting the same version), and its CPU methods still gave the same bits as the CPU image's wheel on this machine. That is a measurement, not a promise: a different processor or a different build can round differently, and only a rerun on that machine shows it.

On the GPU, PDLP Repeated Bit for Bit, Run After Run

The GPU half of repeat.py, on the build machine (an 8 GB laptop NVIDIA GPU, one run of the program; each cuOpt solve in a process of its own):

Both GPU PDLP implementations repeated themselves exactly, and the toolchain's probes found the same for the 90,000- and million-variable transportation LPs, in one process and in new containers. A GPU is not random by nature: a computation whose order of operations is fixed gives the same bits every time. What breaks repeatability is an order that changes from run to run, as the next two sections show.

Repeating itself does not make a GPU run equal to a CPU run. HiGHS's GPU PDLP and OR-Tools' CPU PDLP are different code on different hardware, and their answers to the same LP differ in the last digits; the manifest below compares them within a tolerance.

cuOpt's Concurrent Default Is a Race: Record Which Method Won

cuOpt's default LP method is concurrent: it starts PDLP, barrier (interior point) and dual simplex at once and returns the answer of whichever finishes first. Which one finishes first can change from run to run, and the three stop at different accuracies. The toolchain's probe saw it happen on the 300 × 300 transportation LP: one run returned 1,000,007.04 (PDLP won, $3.1 \times 10^{-5}$ from the optimum, within its $10^{-4}$ tolerance) and the next 1,000,038.0 (another method won). Three more runs of repeat.py:

Dual simplex won all three this time, so all three agree. That does not make concurrent mode repeatable; it means this race had the same winner three times on an idle machine. A busier GPU or CPU can change the winner, and the answer with it. Two rules follow:

  • When a result must repeat, set the method. This module's cuopt(m, "pdlp") sets method to PDLP, which repeated in every run measured.
  • When the method is concurrent, record the winner. cuOpt's get_solved_by() returns it (repeat.py prints it); a manifest that records it can at least say which algorithm produced each answer, and a comparison of two concurrent runs with different winners is a comparison within tolerance, never of bits.

cuOpt's MILP Did Not Repeat, Even in Its Determinism Mode

cuOpt's MILP solver runs heuristics and branch and bound in parallel on the CPU and the GPU (lesson MIP on a GPU: what cuOpt accelerates and why branch-and-bound stays on the CPU), and their timing decides which plans are found first. The toolchain's probe solved a 300-binary GridCap-like MILP twice with the defaults: 14.6 s and 30.0 s, both to the default gap, with objectives equal to about $10^{-16}$ and different plans. Lesson MIP on a GPU: what cuOpt accelerates and why branch-and-bound stays on the CPU's run on GridCap medium found the same: two runs, two different plans.

cuOpt has a setting for this, mip_determinism_mode. On the probe's MILP it was far slower (4,600 nodes in 300 s, against 820,000 in 18 s by default) and, stopped by its time limit, still did not repeat. milp_gpu.py tried it on GridCap medium with a 20-second limit:

Both runs explored exactly 127 nodes, which suggests the search itself followed the same path; but both were stopped by the clock, and a clock stops a run at a different point each time (lesson Where nondeterminism comes from: threads, time limits, ties), so the plans differ. The probe also found that work_limit, the setting that would stop it at a fixed amount of work instead, did not stop it. On cuOpt 26.10.0, then, no setting the course found makes a MILP result repeat, and the course never quotes a cuOpt MILP plan as reproducible. HiGHS on one thread does repeat (lesson MIP on a GPU: what cuOpt accelerates and why branch-and-bound stays on the CPU), and it stays the solver of the plan of record.

Problem statement

A grid operator keeps a record of every LP and MILP run: its inputs (a snapshot id), the device, the solver, the method, the threads, the tolerance, the versions, the kind ("lp" or "milp"), the objective and a digest of the solution's bits. When a run is repeated, the auditors want a verdict that holds a rerun to its bits only where the configuration promised them, and to a tolerance everywhere else.

Bits are promised when the two runs agree on every one of inputs, device, solver, method, threads, tolerance and versions, unless the method is "concurrent" (a race whose winner can change) or the run is a cuOpt (solver == "cuopt") MILP, whose plans did not repeat with any setting.

Write in repeats.py:

  • bits_promised(a, b): True when the rule above promises equal bits;
  • verdict(a, b, tol): "not comparable" when the inputs differ; where bits are promised, "identical" when digest and objective are equal and "different" otherwise; else "within tolerance" when the objectives differ by at most tol relatively (divided by $\max(1, \lvert a\text{'s objective} \rvert)$), and "different" otherwise.

The tests pass run records; no solver runs. About fifteen lines.

The Manifest Records the Device, the Method and the Tolerance


Lesson Versioned input snapshots, pinned solvers and run manifests's manifest recorded the inputs, the solver with its parameters, the versions and the result, and left out the clock and anything that names the machine. For runs that may happen on a GPU it needs three more facts, because each one changes the bits:


  • the device, and for a GPU its model and CUDA versions, never its UUID. highspy reports 1.14.0 in both images, the CUDA build included, so the version alone does not say which build ran;
  • the method, which for cuOpt's concurrent mode is the winner, not the request;
  • the tolerance, because a run at $10^{-4}$ and a run at $10^{-8}$ are different promises, and the threads, as the CPU section showed.

The device is where this solve ran: a CPU solve on a machine that has a GPU records "cpu", so its manifest matches the same solve on a machine without one. A concurrent run records the winner as its method and "concurrent" as requested, and the inputs record whether the model is an LP or a MILP.


The comparison asks for equal bits only where the reference table at the end of this lesson promises them: from a repeat, a run whose solver block (name, method, requested, tolerance, threads, device) and versions are all the same, and only if that configuration repeats. Two runs of cuOpt's concurrent mode are never held to bits, even with the same winner, and neither are two cuOpt MILP runs. Everything else is compared within the tolerance:




The program compares real CPU runs, and then two pairs of made-up records that show the two exceptions: the OR-Tools record relabelled as two concurrent cuOpt runs whose plans differ, and again as two cuOpt MILP runs whose plans differ. No cuOpt solve runs for those two lines; they test the rule, not the solver.



A repeat with the same configuration must be identical, and one whose plan changed is different, which is the alarm lesson Building the deterministic run harness's harness raises. The four-thread run and the interior point run are other configurations, so they are held to the tolerance, which they meet. The two made-up cuOpt pairs have equal solver blocks, but neither configuration promised bits, so a changed plan is not an alarm: their objectives are compared within the tolerance, and a cuOpt MILP plan is also checked as a plan (lesson MIP on a GPU: what cuOpt accelerates and why branch-and-bound stays on the CPU).

Problem statement


A water utility's optimisation service writes a manifest entry for every solve, and its runs now happen on CPUs and on a GPU, with HiGHS, OR-Tools and cuOpt. The auditors need each entry to say what was promised, and to name nothing that identifies a machine.


Write entry(settings, result, device) in manifest.py. settings holds the solver, method, tolerance and threads the service asked for; result is what the solver returned (it may hold more than the manifest should); device is where the solve ran: {"device": "cpu"}, or a GPU report with "device": "gpu", the card's name, driver_cuda, cuda_runtime and other fields, some of which identify one card. Return:


  • a "solver" block with the keys name (the solver's name, from settings["solver"]), method, tolerance, threads and device; for a GPU also device_name (the card's model), driver_cuda and cuda_runtime, and nothing else from the report;
  • when the method asked for is "concurrent", the block's method is the one that won (result["solved_by"]), and the block also holds the key requested with the value "concurrent" (inside the "solver" block, not beside it); with no winner in the result, return None instead of an entry. A run that is not concurrent has no requested key;
  • a "result" block with only status, objective, x_digest and iterations (those present).

Summary


  • On the CPU, a fixed solver, method and thread count repeat bit for bit. OR-Tools' PDLP on 4 threads repeated itself but differed from 1 thread (1,536 against 1,472 iterations); the same CPU solves gave the same digests in both images on the build machine.
  • On the GPU, PDLP repeated bit for bit, run after run. HiGHS's and cuOpt's PDLP both did; a GPU is not random, an order of operations that changes is.
  • cuOpt's concurrent default is a race: record which method won. Set method when a result must repeat; record get_solved_by() when it is concurrent.
  • cuOpt's MILP did not repeat, even in its determinism mode. Different plans at the same gap; determinism mode stopped by the clock differed too.
  • The manifest records the device, the method and the tolerance. Equal bits are asked only of a repeat; across devices, configurations or methods, results agree within tolerance.

Design Note: A Manifest States Its Own Promise


compare reads from the manifests themselves whether bits were promised: same solver block and versions, and a configuration that repeats, bits; anything else, tolerance. No caller decides it case by case. Recording the device and method in the solver block is what makes that possible, and leaving out the card's UUID and the machine's name is what keeps two identical machines' manifests identical.
