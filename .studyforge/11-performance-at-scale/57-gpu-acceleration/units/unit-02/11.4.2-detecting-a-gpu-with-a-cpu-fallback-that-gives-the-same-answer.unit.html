  16. Detecting a GPU and falling back

GridCap's planning service runs in three places: on the analysts' laptops, which have no NVIDIA GPU; on the build server that runs the tests, which has none either; and on one workstation with a GPU, where the large nightly LPs go. It is one code base. The code must find out where it is, use the GPU when there is one and it answers, fall back to the CPU otherwise, and give the same answer in all three places, where "the same" is a tolerance the team writes down. This lesson builds that pattern on the course's GPU helper, 00-base/gpu.py, and on the toolchain's optional GPU image. GridCap is a fictional utility; its numbers are teaching data.

This course runs every program in a container image (scripts/runner.py). The default image is the CPU image. The optional GPU image adds HiGHS built with CUDA (NVIDIA's GPU programming platform), so that highspy can run PDLP on the card (HiGHS calls it cuPDLP-C), and NVIDIA's cuOpt solver. The runner starts the GPU image only when it is present and Docker can reach a GPU, and the CPU image otherwise, with no error.

The Model

Two LPs, each solved on every device. The first is GridCap small's LP relaxation, exactly as in lesson Why first-order LP methods suit a GPU: PDHG and PDLP (80 variables $0 \le x_{i,t} \le 1$, maximise NPV, rows $\text{once}_i$, $\text{must}_i$, $\text{alt}_g$ and $\text{budget}_y$). The second is a transportation LP, the model lesson PDLP on CPU vs. GPU: a measured comparison with HiGHS (cuPDLP-C) and OR-Tools grows to a million variables:

Sets. $S$ the sources and $D$ the destinations, $n$ of each.

Parameters. $a_i$, the supply of source $i$; $d_j$, the demand of destination $j$, with $\sum_j d_j = \sum_i a_i$; $k_{i,j} \in \{1, \dots, 99\}$, the cost of moving one unit from $i$ to $j$, drawn from a fixed-seed generator.

Variables. $x_{i,j} \ge 0$ for every $i \in S$, $j \in D$: the units moved.

Objective.

Constraints.

lps.transport(n) builds it for $n$ sources and $n$ destinations; here $n = 100$, so 10,000 variables and 200 rows.

Ask Once: Is There a GPU This Process Can Use?

00-base/gpu.py answers that question for every program, test and practice of the course:

  • gpu_available() is True only when two things hold: the program runs in the GPU image (it carries a file, /opt/gpu/variant.json, that lists its CUDA, HiGHS and cuOpt versions), and the CUDA driver reports a device. The GPU image on a machine whose GPU did not reach the container is a CPU machine, and so is the CPU image on a machine with a GPU.
  • It asks the driver in a child process, so the calling program never starts CUDA itself: a process forked from one that has started CUDA cannot use it.
  • describe() returns one line that names the device, for every output that states one.
  • requires_gpu() marks a pytest test that runs only where gpu_available(), and is skipped with the reason everywhere else.

On the CPU image, and on the build machine's GPU image, describe() printed (on these pages, the card's model name in a GPU line is shown as its class, in square brackets):

The GPU line names the card's model, its compute capability (its CUDA generation), and two CUDA versions: the driver's and the one the image was built with. It names no single card or machine: two machines with the same card print the same line. Never print a card's UUID, the machine's host name or a path under a home directory in an output that is shared; cuOpt's log does name the UUID in its header, which is one reason the next sections keep that log off the console.

Never Ask highspy for PDLP Without a GPU

HiGHS chooses its LP method with the option solver: "simplex", "ipm" (interior point) or "pdlp". The HiGHS documentation says a GPU build without a GPU returns an error for its native PDLP; the toolchain measured something worse for the CUDA build's PDLP, cuPDLP-C, which has no CPU path at all: with no GPU, solver="pdlp" prints cusparseCreate(): CUDA context cannot be initialized and kills the process with a segmentation fault. A try/except cannot catch that; the program is gone. So the check comes first, in the one function that sets the option:

The CPU image's highspy is the ordinary wheel, with a CPU PDLP of its own, but the course never uses it: the same line of code must be safe in both images, and highs(m, "pdlp") either runs on a GPU or raises an exception the program can catch. A module test checks that it raises when gpu_available() is False.

cuOpt Runs in a Process of Its Own

cuOpt cannot share the course's Python environment, because the toolchain found the two cannot be installed together: its data library, cuDF, needs pandas and numpy versions older than the ones the course pins. The GPU image gives cuOpt a virtual environment of its own, and gpu.run_cuopt(script, *args) runs a script with that environment's interpreter, in a new process. What is kept apart is the environment and the process, not the hardware: cuOpt shares the machine, the GPU image and the card with HiGHS, and lesson PDLP on CPU vs. GPU: a measured comparison with HiGHS (cuPDLP-C) and OR-Tools runs both on the same GPU, one after the other. lps.cuopt writes the model and the settings to a JSON file, runs cuopt_worker.py on it, and reads one JSON line back:

A separate process has two more uses. If cuOpt crashes, only the worker dies, and the caller gets an exception it can handle. And cuOpt writes its log to the console by default, with the card's UUID, the CPU model and the memory in use in its header; the worker sends the log to a file instead and returns only the lines it was asked for, never one of those:

run_cuopt itself refuses to start without a GPU, so lps.cuopt is only ever called behind a gpu_available() check.

Fall Back When the GPU Is Missing or Its Answer Is Not Optimal

fallback.solve_lp tries HiGHS's PDLP on the GPU when there is one, accepts its answer only if HiGHS reports Optimal, and otherwise solves on the CPU with HiGHS's interior point method. It returns the result and the list of what it tried:

The CPU path, which runs on every machine, compared with HiGHS's simplex method as the reference:

On the build machine's GPU image, the GPU path printed (one run, on an 8 GB laptop NVIDIA GPU):

The transportation LP went to the GPU and came back Optimal, 3.3 parts in a billion from the simplex objective. GridCap's LP did not: the GPU's PDLP returned the status Unknown, and the fallback solved it on the CPU. The last line shows why HiGHS refused the answer. Its objective was within $3.1 \times 10^{-8}$ of the optimum and its plan kept every row to $9.2 \times 10^{-8}$, but its prices broke the dual rows by up to 1,100. PDLP stops on relative measures (lesson Why first-order LP methods suit a GPU: PDHG and PDLP), and the HiGHS documentation warns that HiGHS may then refuse an answer PDLP calls optimal, and says to read the infeasibilities in its HighsInfo. A program that took the objective without the status would have used a result HiGHS did not stand behind; this one never does.

So the fallback has two triggers, and both are needed: no GPU (do not even try) and a GPU answer the solver does not report as optimal (try, then solve on the CPU).

    A fallback chain that never crashes and never settles

    • a solve skips GPU solvers without a GPU, survives one that fails, and accepts only an optimal answer

Problem statement

A logistics team's nightly job tries a list of LP solvers in order: GPU solvers first, CPU solvers after. The machine may have no GPU, a GPU solver may raise (out of memory, a driver fault), and a solver may finish without an optimal answer. The job must never call a GPU solver on a machine without a GPU, must not die because one solver failed, and must never hand on an answer its solver did not call optimal.

Write solve_with_fallback(model, solvers, gpu) in fallback.py. Each solver is a dict with a name, a needs_gpu flag and a solve function that takes the model and returns a dict with a "status". Go through the solvers in order:

  • a solver that needs a GPU when gpu is False is not called, and logged as "<name>: skipped (no GPU)";
  • a solver that raises is logged as "<name>: error", and the next one runs;
  • any other solver is logged as "<name>: <status>"; the first whose status is "Optimal" is the answer.

Return (result, log), with result None when no solver answered "Optimal". The tests use fake solvers, and one real LP solved with highspy on whatever the machine has: test_a_real_lp_is_solved_on_whatever_this_machine_has tries HiGHS's GPU PDLP first on the GPU image with a GPU. On a machine without a GPU it checks the CPU path only, and it says nothing about the GPU part: no test is reported as skipped. About fifteen lines.

The Same Answer Means Within a Stated Tolerance


The GPU's answer to the transportation LP is not the simplex answer bit for bit: its objective is 227,776.999 against 227,777.000. Nor is the CPU interior point's, in general. Different algorithms, and the same algorithm on different hardware, add numbers in different orders, and floating-point addition is not associative (lesson Floating point, tolerances, and why 1e-6 matters). So "the same answer on every device" is a tolerance, stated in the code:




Two tests, both needed:


  • The objective, relatively: $\lvert z - z_\text{ref} \rvert / \max(1, \lvert z_\text{ref} \rvert) \le 10^{-6}$. An absolute test would be too strict for a portfolio worth $227 million and too loose for one worth $200k.
  • The plan keeps the rows, to $10^{-6}$ times the largest row bound. An objective can match while the plan overspends a budget: a plan that breaks a row can be worth more than the optimum (lesson Simplex, interior point and PDLP: GLOP, HiGHS, PDLP saw PDLP land above the maximum).


The tolerance is checked against an answer from a different solver on the CPU, never against the GPU's own report. A module test runs the same check on the GPU image with a GPU: HiGHS's GPU PDLP on the 100 × 100 transportation LP agrees with the CPU interior point within $10^{-6}$, and does not match it bit for bit. Lesson Determinism on a GPU: what repeats, what doesn't, and what the manifest records asks which runs should match bit for bit.

Problem statement


A routing team solves the same LP on laptops (CPU only), on a build server, and on a GPU workstation, and keeps a record of each run: the device ("cpu" or "gpu"), the solver, the objective, and a digest of the solution's bits. Before a release they want one function that says whether a set of runs agrees, by a rule written down once:


  • one CPU run is the reference: the first CPU run in the list. With no CPU run there is no reference, and the result is exactly ["no CPU reference"]: no other check runs, so not even a repeat that differs is reported until a CPU run is added;
  • runs of the same solver on the same device are repeats, and a repeat must give the same digest and objective as that pair's first run, else "<device>/<solver>: repeat differs";
  • every run's objective must be within tol of the reference's, relatively (divided by $\max(1, \lvert\text{reference}\rvert)$), else "<device>/<solver>: off the reference".


Write check_runs(runs, tol) in runs.py, returning the problems sorted, each once; an empty list means the runs agree. One test, test_real_runs_on_this_machine_agree_and_a_run_off_by_a_thousandth_is_caught, solves a small LP with highspy on this machine; on the GPU image with a GPU it adds two GPU PDLP runs. On a machine without a GPU that test runs its CPU part only, and it says nothing about the GPU part: no test is reported as skipped. About fifteen lines.

Summary


  • Ask once: is there a GPU this process can use? gpu_available() needs the GPU image and a device the driver reports; describe() names the device without naming the machine.
  • Never ask highspy for PDLP without a GPU. The CUDA build's PDLP kills the process with no GPU; check first, so the failure is an exception.
  • cuOpt runs in a process of its own. Its environment cannot share the course's; a worker process also contains a crash and keeps the log, which names the card's UUID, off the console.
  • Fall back when the GPU is missing or its answer is not optimal. On GridCap's LP the GPU PDLP said Unknown, with dual rows broken by 1,100, and the CPU answered.
  • The same answer means within a stated tolerance. Relative objective and scaled row breach, against a CPU answer from another solver.

Design Note: The Device Is a Fact, the Fallback Is a Rule


gpu_available() reports a fact about the machine; solve_lp applies a rule to it. Keeping them apart means the rule can be tested on any machine with use_gpu=False or True passed in, and the fact is asked in one place, in a child process, once. The same split runs through the course's tests: the CPU half of every test carries the grade, and requires_gpu() adds checks without removing any.
