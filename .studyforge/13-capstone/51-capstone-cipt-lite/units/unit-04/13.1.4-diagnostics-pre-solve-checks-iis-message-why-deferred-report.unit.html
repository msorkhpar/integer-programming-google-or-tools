Pre-Solve Checks Run First and Catch What One Limit Can Refuse

Most infeasible scenarios are one typo, and a typo deserves a one-line answer, not a search. Lesson Validating inputs before the solve's checks read one project, group or region against one limit, before any model is built. CIPT Lite runs them on the required projects, the must-dos and every project a planner forced in or fixed to a year (overrides count, lesson Manual overrides as fixed bounds): each must have a start left; each must fit the yearly budgets and its program's crews on its own in some start year; together, their least spend in each year must fit that year's budget; no two may be alternatives; and each region's floor must be reachable. The year check is the gate rule of lesson Data: load, validate and snapshot the portfolio, now with the scenario's overrides and locked numbers. That gate, gate(pf), reads only the portfolio: it counts the export's must-dos against the export's budgets, so it sees neither a scenario's overrides nor its locked numbers. Every check compares a least demand with a most supply, so it is sound: it never refuses a scenario that has a plan. budget_lock.py also runs a second scenario, the same lock with the 2027 budget typed as $428k instead of $42,810k:

Passing the checks does not mean a plan exists (lesson Validating inputs before the solve): the clash is between several rules at once, and finding it needs the solver.

Problem statement

Budget Lock week at the practice utility (a fictional one): finance and the board send a scenario that changes the snapshot's numbers before the run. A scenario may lock a year's budget, cut crews (by program and year), force_in projects, fix_start a project to one year, and force_out projects. Before any solve, CIPT Lite runs pre-solve checks that each read one project, group or region against one limit, so a typed number is caught with its own name instead of a bare INFEASIBLE (lesson Validating inputs before the solve).

Every check must be sound: it fires only when no plan can exist, so a scenario that has a plan never gets a finding. A check compares the least a required project must take with the most a limit can give.

Write, in checks.py, required(snapshot, scenario): each must-do and each forced project with its window's start years, and each fixed project with only its fixed year. required keeps them all: a required project that is also forced out keeps its window, and a fixed year outside the window is kept as given, because those are exactly the cases checks must report as no-start. Then checks(snapshot, scenario), which returns a list of (rule, subject) findings, in this order:

rulesubjectfires when
no-startthe projecta required project is forced out, or its fixed year is outside its window (then skip its other checks)
alone-over-budgetthe projectno start left to it keeps its own spend within every year's budget
alone-over-crewsthe projectno start left to it keeps its crews (needed in every year of work) within its program's crews
required-over-budgetthe year, as textthe least that the required projects must spend in that year exceeds its budget
required-alternativesthe grouptwo or more required projects share a group
floor-out-of-reachthe regionthe capex of every project in the region that is not forced out is below its floor

The first three come per required project, in id order; then years in order, groups and regions sorted. A required project's least spend in a year is the minimum over the starts left to it. The budgets and crews in force are the snapshot's, replaced by the scenario's where it sets them; starts, spend, budgets and crews are given.

A Deletion Filter Names the Rules That Clash


An irreducible infeasible subsystem (IIS) is a set of rows that has no solution while every proper subset of it has one (lesson IIS with MathOpt, gurobipy and Pyomo). MathOpt's compute_infeasible_subsystem finds one with Gurobi only (lesson Callbacks and compute_infeasible_subsystem), so CIPT Lite finds one by hand, with the deletion filter: switch a candidate row off; if the model is still infeasible, the conflict does not need that row, so leave it off; otherwise switch it back on. What survives is irreducible.


Two choices make it fast and its answer useful. The candidates are only the limits: must-do and forced rows, and the budget, regional, crew and floor rows. The rows that describe the decisions (once, alternatives, precedence) stay on, because "a project starts at most once" is not a number anyone at Budget Lock can change. And the filter tries whole families first, then the rows inside the families it kept (lesson CP-SAT assumptions as a conflict finder):



Switching a row off sets its bounds to $\pm\infty$, and the objective is cleared while the filter runs, since each solve only asks whether any plan exists. On the Budget Lock scenario the budget, regional and floor families can all go; the must and crew families cannot, so their 69 rows are filtered one at a time: 5 family solves and 69 row solves, 74 in all. The run setting's gap plays no part here, because with no objective each solve only has to find a plan or prove there is none.


The Message States the Rules, the Arithmetic and One Checked Change


A row name is not a message. Lesson Turning an IIS into a planner message's rules for one: name rules and projects, never rows; say who set each number; show the arithmetic; end with the change that ends the conflict, checked by a solve. CIPT Lite's message does each in turn:



The conflict is small enough to read whole. P097 works two years, 2029 and 2030, with 8 crew-months in each; P370 needs 11 in the year it starts, and it can only start in one of those two years; 8 + 11 = 19, one more than the 18 the contractor change left. The 2028 budget lock is not in the conflict: whatever it costs, it is not why there is no plan.


The arithmetic lines are computed, not written: for every combination of start years the conflict leaves the required projects, the program adds up their use of each limit in the conflict and prints the first one that runs out. The proposed change is searched among the numbers the scenario itself set (the locked crews and budgets), one step at a time, and each candidate is accepted only when a full solve of the changed scenario finds a plan. A conflict can have several ways out: by the same arithmetic, 19 crew-months in 2030 would end this conflict too, and so would relaxing a mandate, but a mandate is a regulator's number, not finance's, so the message offers the change finance can make.

Problem statement


Finance has locked the practice utility's numbers for the year (the utility is fictional), and the locked scenario has no plan. Planners will not read row names or a solver status; they need one message: which rules clash, the arithmetic that shows it, and the smallest change to a number the scenario set that gives the scenario a plan, checked by a solve.


lock.py gives you milestone 2's model: build(snapshot, scenario) returns a Built with the MathOpt model, the start variables x and rows, every row by name (must_J1, force_J4, alt_G1, after_J5_2028, budget_2029, region_North_2028, crews_lines_2028, floor_South). A scenario's fix_start and force_out are bounds on the variables, not rows. Also given: feasible(b) (does the model have a plan?) and describe(row, snapshot, scenario), one row in the planners' words.


Write:


  • conflict(b): a deletion filter (lesson IIS with MathOpt, gurobipy and Pyomo) over the limit rows only, the families in LIMITS; the decision rows (once, alt, after) stay on. Switch a row off by setting its bounds to $-\infty, +\infty$; if the model is still infeasible, leave it off for good, otherwise switch it back on. First do this for each whole family, in the order of LIMITS (skipping a family with no row), then for each row of the families that stayed, in the order the model holds them (lesson CP-SAT assumptions as a conflict finder). Return the rows left, sorted, and the number of feasible calls. Count only the family and row calls: conflict does not first solve to confirm the scenario is infeasible (message is only called on one that is). Whatever happens, give every row its own bounds back before you return.
  • required(snapshot, scenario, rows): each project a must_ or force_ row of the conflict names, with its window's start years, in the conflict's order; then each project the scenario fixes, by id, with its fixed year only.
  • arithmetic(snapshot, scenario, rows): for every combination of the required projects' starts (itertools.product, in required's order), the first budget_ or crews_ row of the conflict, in its sorted order, that the combination overruns, counting only the required projects. Lines read - J1 2027, J2 2028: the 2027 budget needs $200k, has $150k. or - J1 2027, J2 2028: lines crews in 2028 need 4, have 3.; a combination that overruns none gets no line.
  • repair(snapshot, scenario, rows): for each conflict row, in order, that is a number the scenario set: a crews row, raise it by 1 at a time; a budget row, by $10k at a time. The steps stop at the snapshot's own figure and never pass it: a budget locked at $155k with a snapshot figure of $200k tries $165k, $175k, $185k and $195k, and not $200k, because $205k would be past it. Return the first value that feasible(build(...)) accepts, as lines crews in 2028 at 4 instead of 3 or the 2027 budget at $200k instead of $150k, or None. Every dollar amount in the message, here and in the arithmetic lines, is written with a thousands separator: $1,250k.
  • message(snapshot, scenario), exactly these lines:The - <describe(row)> line comes once for each conflict row, in the conflict's order, and the - <id> is fixed ... line once for each project the scenario fixes, by id. <N> counts the conflict rows and the fixed projects, and the last line is No single number of the scenario ends it. when repair finds nothing.


The header names the planning step, Budget Lock '<name>', where the lesson's library writes Scenario '<name>': every scenario this practice sees is a Budget Lock one. The lesson's message also numbers its rules and reports the pre-solve checks and the solve count; this one leaves those out, so that its lines are the conflict, the arithmetic and the change. Lesson Turning an IIS into a planner message explains why the message names rules, shows the arithmetic and checks its repair by a solve.

Why Deferred: The Rows That Refuse It, and What Forcing It In Costs


With the base scenario there is a plan, and the asset team asks why P399, a Valley line rebuild worth $3,506k, is not in it. Lesson A binding-constraints report answers the first half with no solve: add the project to the plan at each of its start years, and list the rows the result breaks. Lesson Why selected, why deferred: forcing in and out answers the second: force it in, solve again, and compare. why_deferred_report.py does both for the three deferred projects with the highest NPV at their earliest start:




The cost is an interval, and the reason is the run setting. Both solves stop within 0.1% of their bound, so neither value is known exactly: the base plan is worth between its plan value and its bound, and so is the forced plan. Forcing a project in adds a row, so it can never raise the best value, and why_deferred raises a low end below 0 to 0 (max(0.0, ...)). The cost of forcing is at least the base plan's value less the forced bound, and at most the base bound less the forced plan's value:



For P399 that is between $272k and $709k: whatever the exact optimum, the plan is better without it. The other two:

Problem statement


The practice utility's planners (a fictional utility) read the best plan and ask about one project it left out: why is it deferred, and what would funding it cost? Milestone 4 answers both, for any project, with numbers a planner can check.


why.py gives you milestone 2's model and tools: build(snapshot, scenario) (a scenario's force_in list becomes a row $\sum_t x_{i,t} \ge 1$), solve(b) (HiGHS to a zero gap), plan_of(b, result) and check(snapshot, scenario, plan), the rule checker that names every row a plan breaks from the data alone.


Write:


  • refused_by(snapshot, scenario, plan, pid): for each start year $t$ of the deferred project, the rows that the plan as it stands, with the project added at $t$, breaks (lesson A binding-constraints report: on a MILP the row that blocks is the one a whole project cannot fit, slack or not). Return {start year: [row names]}, with each list exactly as check returns it: must_ rows, then alt_, then after_, then for each year in order its budget_, region_ and crews_ rows, then floor_ rows. Rows the plan already breaks without the project are not taken out: they are listed at every start.
  • forcing_cost(snapshot, scenario, pid): solve the scenario, then solve it again with pid forced in (lesson Why selected, why deferred: forcing in and out). Return Forced(cost, gives_way), where cost is the base objective less the forced one, and gives_way lists, by project id, every project of the base plan that the forced plan drops ("J3 dropped") or moves ("J1 2028->2027"). When the forced model has no plan, return None: a forcing the rules cannot satisfy is answered by a rule, not by a price.
  • cost_interval(base_primal, base_bound, forced_primal, forced_bound): on a large portfolio both solves stop at a relative gap, so each objective is only known between its plan's value (primal) and its proven bound. For a maximization, the true cost lies betweenReturn the pair (low, high). Forcing a project in can never raise the best value, which is why the low end is never below zero.
