The last milestone puts the five before it behind an HTTP API: a client posts a snapshot and gets its digest, posts a job and gets an id at once, polls it, and fetches a result that names its snapshot; it can also ask for the NPV-risk frontier, so the board's choice of weights in lesson Value: NPV by start year, risk reduction from PoF/RUL, weighted value is made with the trade-off in view. The Model

The frontier endpoint solves the model of the lesson Model: Multi-Period Selection With All Section 6 Rules, unchanged (sets, parameters, $x_{i,t} \in \{0, 1\}$, and the rows once, must, force, alt, after, budget, region, crews and floor, written out there), with the risk coefficients $\text{rr}_{i,t}$ of the lesson Value: NPV by Start Year, Risk Reduction From PoF/RUL, Weighted Value and one row added, the ε-constraint of lesson The ε-constraint method:

solved once for each floor $\varepsilon$ between the risk removed by the NPV plan and the most risk any plan removes (the payoff table, lesson The ε-constraint method).

Snapshots and Results Live in S3, Job States in a Local SQLite File

Where each piece of state lives follows from how it is used. A snapshot is written once and read by every job that solves it, so it goes to S3 under its digest, as the store of lesson Data: load, validate and snapshot the portfolio did on disk (lesson Versioned snapshots and content hashes):

exists asks S3 for the object's metadata with head_object, which returns no body and raises a ClientError with code 404 when the key is absent. S3 itself would accept a second put_object to the same key and replace the object; the exists check is what makes a repeated post store nothing. Reading re-hashes the bytes and refuses an object that no longer matches its name:

A job's result is written once, when the job ends, so it goes to S3 too, under results/<job id>.json. A job's state (queued, running, optimal, infeasible...) changes several times and is read on every poll, so it goes to a table in a local SQLite file, one row per job, declared STRICT so that a wrong type is refused rather than stored (lesson Storing scenarios and results in SQLite). That is the split of lesson S3 and a local SQLite file for snapshots and results, and the course uses no cloud database.

service_demo.py runs the whole service with no network. Before it imports boto3, it sets moto's fake credentials (AWS_ACCESS_KEY_ID=testing and the rest), so that no real account can ever be reached; inside with mock_aws():, every S3 call goes to moto's in-memory S3 (lesson Testing AWS code against moto). Problem statement

The planning service is moving its snapshots from a worker's disk to S3, so that every worker, and every auditor, reads the same inputs. Your milestone writes the store: each snapshot is kept once under its own content hash and checked again whenever it is read. The tests run against moto's in-memory S3 with moto's fake credentials: no account, no network. The practice portfolio is invented for a fictional utility.

A snapshot is a dict in the milestones' shape (years, rate, budget, region_budget, crews, floor, projects), with integer year keys in budget, in each region's region_budget, in each program's crews and in each project's npv. JSON can only write text keys, so the years come out of S3 as strings.

A Job Is Accepted at Once, Polled, Then Fetched


A medium solve takes many seconds, and an HTTP request must not wait for it (lesson Long solves: submit, poll, fetch). Submit checks the request, writes the job's row, hands the solve to an executor and answers 202 Accepted with the job's id and a Location header:



The request is a pydantic model with extra="forbid", a snapshot digest of exactly 64 hex digits, optional budget locks and a gap between 0 and 10% (lesson A REST API with FastAPI). The worker runs lesson Model: multi-period selection with all section 6 rules's model, checks the plan with check before it reports it, writes the result to S3 and the final state to SQLite. An infeasible scenario is an answer, infeasible with no plan, not an HTTP error (lesson A REST API with FastAPI):



Fetching before the job ends answers 409 Conflict: the result does not exist yet, and the reply says the job's state. The result is lesson Model: multi-period selection with all section 6 rules's run: the same NPV, bound and plan, because the service uses the same run setting, and lesson Trust: determinism harness, Hypothesis properties, golden test, warm start's harness already showed that run repeats. A request with a budget for a year outside the plan is refused before any job exists. The solve runs in a thread here, which keeps the demo in one process; lesson Long solves: submit, poll, fetch showed that a solver crash in a thread takes the whole process with it, and that a process pool limits it to one job.

Problem statement


A planning run takes minutes, and the service restarts whenever it is redeployed. Planners must be able to submit a run, close the browser, and fetch the plan after lunch, even if the service was restarted in between. Your milestone is the job API, with each job's state and result kept in a local SQLite file. The solves are stand-ins in the tests; the portfolio behind them is invented for a fictional utility.


create_app(solve, db_path) returns the FastAPI app. solve(budget) is the planning run: it takes {year: $k} budget overrides, with integer years, and returns a JSON-ready dict with a "status" of "optimal" or "infeasible"; it may also raise. The request model PlanRequest (only a budget field, extra fields refused) is given.

The Frontier Endpoint Returns Only Non-Dominated Plans


The weights of lesson Value: NPV by start year, risk reduction from PoF/RUL, weighted value picked one plan. The board asks what else it could have had, and the answer is the frontier: plans where no other plan has both more NPV and more risk removed (lesson Generating a frontier and presenting it to planners). The endpoint builds it by the ε-constraint method: the payoff table first (the NPV plan's risk, and the most risk any plan removes), then the best NPV at evenly spaced risk floors between them, then drops any point another point dominates:



Each floor is a row added before the solve and deleted after it, so one built model serves every point (lesson Incremental solving: edit the model, re-solve). Five points on GridCap medium:



Read it as planners would (lesson Generating a frontier and presenting it to planners): the first $96,000k or so of extra risk removed costs $1,378k of NPV, the next $50,000k costs $4,274k, and the last $50,000k costs $42,496k. The knee is between the fourth and fifth points. The weighted-value plan of lesson Value: NPV by start year, risk reduction from PoF/RUL, weighted value (NPV $182,952k, risk $431,580k) lies in that last, expensive stretch: the board's ratings chose a plan near the risk end.


Two cautions belong in the endpoint's documentation. Each point comes from a solve stopped at the run setting's 0.1% gap, so a point's NPV is within 0.1% of the best for its floor: the first point is $71k above the NPV run of lesson Model: multi-period selection with all section 6 rules, which is two plans inside one gap, not a contradiction. And five floors give five points, not the whole frontier; lesson AUGMECON: avoiding weakly efficient points's AUGMECON is the exact method when the board needs every plan.

Problem statement


Planners want to see the trade-off before they pick a plan: how much NPV each extra $1k of risk removed costs. Your milestone adds a frontier endpoint to the service. It answers with the plans the epsilon-constraint method finds, from the plan with the most NPV to the plan that removes the most risk, and never with a plan another returned plan beats on both counts. The practice portfolio is invented for a fictional utility; each project carries, beside npv, a risk table: the risk it removes ($k) for each start year, as milestone 3 computed it.


frontier_endpoint.py gives you milestone 2's model with a reduced rule set (build, solve, plan_of, check), objectives(snapshot, x), which returns the NPV and risk expressions, score(snapshot, plan), which returns {"npv", "risk", "plan"}, from_json, which turns a snapshot's text year keys back into integers, and the request model FrontierRequest (a snapshot and points from 2 to 11).

best(snapshot, first, then, floors)build a fresh model; add a row value >= floor for each entry of floors ({"risk": 120}); maximize first ("npv" or "risk"); if there is no plan return None; otherwise hold first at its optimum (a row value >= optimum - HOLD, with the given HOLD = 1e-6: the risk table is rounded to $0.001k, so an optimum need not be a whole number, and rounding it could cut off the optimum or let a worse plan in), maximize then, and return score of that planThe ε-constraint method, AUGMECON: avoiding weakly efficient points

Keep each point once: a point with the same NPV and the same risk removed as one already found is not added, even if its plan differs, so the first one found (the lowest floor) stays. Summary


  • Snapshots and results live in S3, job states in a local SQLite file. Content-addressed snapshots, re-hashed on read; results written once; states in a STRICT table. Tested with moto's in-memory S3 and fake credentials, with no network.
  • A job is accepted at once, polled, then fetched. 202 and an id, 409 until the result exists, infeasible as an answer; the worker checks every plan before reporting it.
  • The frontier endpoint returns only non-dominated plans. ε-constraint floors over one built model, dominated points dropped; on medium the knee is near $383,000k of risk removed.

Design Note: Each Piece of State Where Its Use Puts It


Nothing here was chosen for the technology. Snapshots are immutable and named by content, which is what an object store does best; results are written once and fetched by id, the same; a job's state is a small row that changes and is read constantly, which is what a database row is for, and a local SQLite file is enough for one service. The digest ties them together: every result names the snapshot it solved, and every snapshot can prove it is still the bytes that were solved.
