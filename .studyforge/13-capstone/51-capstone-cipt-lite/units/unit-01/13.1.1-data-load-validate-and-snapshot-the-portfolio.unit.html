GridCap's planning team wants one tool in place of the dozens of scripts the course has written: a small CIPT (Capital Investment Planning Tool) that takes the planning export, builds the multi-period model, values every project, explains its answers, proves it repeats itself, and answers over HTTP. This module builds it, on GridCap medium (400 projects over the ten years 2027 to 2036), one milestone per lesson. Every milestone assembles code you already wrote in an earlier module, so each lesson names the lesson that taught each part and spends its words on how the parts fit.

The first milestone is the one every later one stands on: read the export, refuse it if it is wrong, and give the accepted inputs a name that never changes. GridCap is a fictional utility; its data is generated by the course, and no number in it describes a real company.

The order is the order a request travels through the service: data, then model, then values, then the solve and its explanation, all of it repeatable, all of it behind an API. Each lesson's graded practice builds the same milestone on a small practice portfolio of its own, in the same shape throughout the module, so the practices too add up to one tool.

The export is the five CSV files and the portfolio.json that gridcap.save_csv writes (the course's gridcap package): one row per project, per start year's NPV, per asset, per budget and per crew limit. It is the shape a planning database's export has, and like any export it can be wrong in ways the model would never notice.

Read Every Cell and Keep Every Problem

gridcap.load_csv trusts its files: a cost typed 1,200 stops it with a ValueError at the first bad row, and a misspelt region goes straight into the model. The milestone's reader checks each cell as it converts it and records a finding (a rule, a severity, a subject and a detail) instead of raising, the pattern of lesson Typed inputs with dataclasses and pydantic's row validator:

Every column gets the check its meaning calls for, read off the model's parameters as lesson Schemas for model inputs reads a schema: costs and crew-months are whole numbers (money is whole $k), programs and regions come from a known list, a project's window must fit the horizon with all its years of work (lesson Start-time variables x(i,t) and timing windows), every start year in the window needs an NPV, and every parent and asset id must name a row that exists. Only when no cell has an error does the reader build a Portfolio.

planted_defects.py writes GridCap medium's export and plants six mistakes an export really makes, one at a time:

Each defect is refused with a sentence a planner can act on: which row, which column, what it holds. The first four are cell problems. The last two pass every cell check, because every cell in them is a valid value on its own; they need the next stage.

Rules Across Projects Run Only on Clean Cells

A parent cycle is two valid parent ids that point at each other. A budget of 391 is a valid whole number. Only a rule that looks at several rows at once sees the problem, and lesson Data-quality checks that prevent infeasibility calls those rules the quality gate. The milestone's gate has four: a project that is its own ancestor, a child whose parent cannot start early enough for any of its starts (an error for a must-do, a warning otherwise), two must-dos in one alternative group, and a year whose budget is below what must-do work has to spend in it whatever start years it gets:

The min over start years is what makes the rule sound: it never refuses a portfolio that has a plan, because no plan can spend less than that least amount (lesson Validating inputs before the solve). P097 is must-do and can start only in 2029, where it spends $880k, so a 2029 budget of $391k proves there is no plan.

The gate runs on a Portfolio, so it runs only after the cells are clean:

That ordering has a visible cost. With all six defects planted at once, the export is refused with the four cell errors only:

The cycle and the budget typo are found on the next attempt, after the four are fixed. That is the right trade: a cross-project rule on unclean cells would follow a parent id that names no project, or add a cost it could not read, and report nonsense with an error's authority. So the reader reports every cell problem in one pass, and the gate reports every cross-project problem in one pass, and neither guesses.

Problem statement

A fictional utility's planning database sends its portfolio export to CIPT Lite as text: one row per project and one per yearly budget, every cell a string, the way csv.DictReader hands them over. This cycle's export has six defects planted in it. Your reader must refuse it, find all six, and accept a clean export as the snapshot every later milestone uses.

The rows. export["projects"] holds rows with the columns id, program, region, cost (the yearly amounts in $k joined by ;), earliest, latest, must ("0" or "1"), parent (an id, or ""), lag, group (an alternative group, or "") and crews. export["budgets"] holds year and amount. export["years"] (a list of ints) and export["rate"] (text) are given.

The snapshot you build is the practice series' format, restricted to what this export carries:

A project started in year $t$ spends cost[k] in year $t + k$, so its start years are $T_j = \{e_j, \dots, l_j\}$, and every one of them must leave room for the whole profile inside the horizon.

In export.py, write the two stages (review, which runs them in order, and rejected are given). Each finding is a tuple (severity, rule, subject).

functioncontractlesson

Cell rules (all errors). A budget row whose year is not a whole number ("2O28") is a bad-budget with that text as its subject, and the year it was meant for then has no budget, so it also gets a missing-budget:

Cross-project rules:

rulesubjectfires whenseverity
parent-cyclethe ids on the cycle, sorted, joined with +following parents from a project leads back to iterror
parent-too-latethe childthe parent's earliest start plus the lag is after the child's latest starterror for a must-do child, warning otherwise

The cross rules read parents and costs as numbers and ids, so they run only once every cell is clean: an export with cell problems is refused on those alone, and its next version is checked again. Errors reject; a warning alone does not, and review then returns the snapshot. About seventy lines.

The practice simplifies the lesson's reader and gate: one cell rule, not-a-number, stands for the lesson's not-a-whole-number and below-minimum, and the gate has three rules instead of four (the lesson's two-must-do-alternatives is left out).

The Snapshot Is Named by the Hash of Its Canonical Content


An accepted export becomes a snapshot: the validated inputs, frozen and named by their content hash, so that every later run, manifest and result can say exactly which inputs it used (lessons Versioned input snapshots, pinned solvers and run manifests and Versioned snapshots and content hashes). The name is the SHA-256 of the canonical form, one chosen way to write the validated content: projects and assets sorted by id, every key sorted, every float fixed to six decimals, no spaces.



snapshot_medium.py puts the name to the test. It accepts GridCap medium, then exports the same content three ways and one changed way, and hashes the first export in two fresh processes with different hash salts:




Row order and a float's last digits do not change the content, so they do not change the digest; one cost $10k higher does. The digest is also the one the gridcap package pins for GridCap medium (Portfolio.content_hash(), df4edafe8608…), because that hash sorts keys and writes the generator's projects in id order too. The module's tests pin the full 64 hex digits, so a change to the reader or the canonical form that shifted a single byte would fail a test instead of quietly renaming every snapshot.


Medium has 400 projects and 382 assets: 18 pairs of alternatives (repair or replace) share one asset each.


The snapshot store keeps each snapshot once, under its digest, and checks the digest again on every read (lesson Versioned snapshots and content hashes):

Problem statement


The practice portfolio has passed milestone 1's reader. Every later run must now say which inputs it solved, in a way any worker can check on any day: by a digest of the snapshot's content. Two exports of the same content must get the same name, and any real change, however small, a new one.


The snapshot is the practice series' format: nested dictionaries keyed by year, region, program or project id, lists that carry their order (years, each cost profile, spent year by year), ints for money, and one float, rate.


In snapshot.py, write:

The documented byte form is what json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=True, allow_nan=False) writes: the planning team pinned the digest of their test snapshot from it, and your digest must match theirs byte for byte. Dictionaries in another order are the same content; a reversed cost profile is not. About thirty-five lines.

Summary


  • CIPT Lite is one program built in six milestones. Data, model, value, diagnostics, trust, service: each a module of src/, each importing only the ones before it, each assembled from lessons you have done.
  • Read every cell and keep every problem. Convert each cell with a check that records a finding instead of raising; build the portfolio only when no cell has an error. Six planted defects, six sentences a planner can act on.
  • Rules across projects run only on clean cells. Cycles, unreachable parents, mandated alternatives and must-do spend above a year's budget need several rows at once; each rule is sound, and none runs on values that could not be read.
  • The snapshot is named by the hash of its canonical content. Sorted records and keys, fixed floats, no spaces: the same content gives df4edafe8608 in any row order and any process, and a $10k change gives another name.

Challenges


  1. The gate's budget rule counts only must-do projects. A planner adds a fix_start override that requires P086 to start in 2027 (lesson Manual overrides as fixed bounds). Which stage should know about overrides, and what would the rule then add up?
  2. Two exports differ only in a project's name. Should their digests differ? Think of a report that quotes project names next to the digest.
  3. The reader refuses a whole export for one bad cell. Write down one case where a planner would rather drop the bad project and solve the rest, and what the result must then say.


Design Note: Refuse Loudly, Never Repair Quietly


The reader could have "fixed" 1,200 to 1200 and Vally to Valley. It does not, because a reader that guesses turns a data problem into a plan problem that nobody can trace: the plan would be built on inputs no one exported. Refusing with a finding sends the problem back to the system that made it, and the snapshot that is finally accepted is exactly what the export said.
