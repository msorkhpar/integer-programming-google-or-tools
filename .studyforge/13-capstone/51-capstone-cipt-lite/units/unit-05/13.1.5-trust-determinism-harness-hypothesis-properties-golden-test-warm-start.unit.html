A regulator reviewing GridCap's rate case asks the question every optimization tool must answer sooner or later: "If we run your tool on the same inputs next month, do we get the same plan, and how do you know the plan obeys your own rules?" Four pieces of section 10 and section 12 answer it, and this milestone fits them to CIPT Lite: a run manifest and a harness that reruns it in fresh processes (lessons Versioned input snapshots, pinned solvers and run manifests and Building the deterministic run harness), properties checked on hundreds of generated portfolios (lesson Property-based tests with Hypothesis), golden records that catch a regression (lesson Golden datasets and regression tests), and a warm start from last cycle's plan that must not cost any of the above (lesson MIP starts from last cycle's plan). Nothing here changes the model of lesson Model: multi-period selection with all section 6 rules; it changes what can be claimed about it. GridCap is a fictional utility's portfolio.

A Run Is Its Manifest, and the Harness Compares Ten of Them Byte for Byte

A run manifest records what went into a run and what came out, in canonical bytes, and nothing that names the clock, the machine or a person (lesson Versioned input snapshots, pinned solvers and run manifests). CIPT Lite's has four sections: the inputs (the snapshot digest of lesson Data: load, validate and snapshot the portfolio, the scenario, the objective, and the digest of any hint), the solver and its settings, the versions of Python and OR-Tools, and the result with its plan and its work counts. cipt_trust.py prints one, for GridCap small at a zero gap:

The work counts (nodes, simplex iterations) are there on purpose. Two runs that return the same plan by different searches are not the same run, and the counts are what shows it, where the objective alone would hide it.

The harness runs one config in ten fresh processes, each with its own PYTHONHASHSEED, so a set's iteration order, a per-process thread setting or a library's hidden state cannot hide behind one process's luck (lesson Building the deterministic run harness). It compares the manifests' bytes:

trust_medium.py puts the run setting of lesson Model: multi-period selection with all section 6 rules through it on GridCap medium, and then a config built to fail, the zero-gap model stopped by a two-second clock limit:

Ten processes, one manifest: the same 209 starts, the same bound and the same 791 nodes each time. That is what one HiGHS thread and a stopping rule that counts the search (a gap) rather than the clock buy (lesson Seeds, threads and deterministic work limits, solver by solver). The clock-limited config fails, as it must: a clock stops the search wherever the machine happens to be, and the harness's error names the fields that changed between runs. A harness that never fails proves nothing, so this known-bad config stays in the module's program beside the good one (lesson Determinism tests and back-testing against history).

The PASS holds for this machine, this OR-Tools (9.15) and this Python; the manifest records all three, so a later run on other versions is compared knowing they changed.

Problem statement

A small utility's planning service (fictional, like its practice portfolio) is about to put its plans in front of a regulator. The regulator's first question is whether the same inputs always give the same plan. Your milestone answers it with evidence: every run writes a manifest, and a harness reruns one configuration in fresh processes and compares the manifests byte for byte.

run_harness.py gives you the practice portfolio SNAPSHOT (a reduced rule set: must-do and at-most-once rows and yearly budgets), snapshot_for(config), which applies a config's budget overrides, and solve(snapshot, objective, order, seed), a CP-SAT solve on one worker. A config is a dict such as {"objective": "npv"}, {"objective": "count", "order": "set"} or {"objective": "npv", "budget": {"2028": 200}}. A config may also give a "seed". A key the config leaves out takes its default: objective "npv", order "sorted", seed 0. The seed is passed to solve and recorded as the manifest's random_seed; it is CP-SAT's seed, not the child process's PYTHONHASHSEED. The bottom of the file already runs one config given on the command line and prints its manifest's canonical bytes: that is the child process.

Properties Must Hold on Every Drawn Portfolio


The harness shows the model repeats itself; it does not show the model is right. Lesson Property-based tests with Hypothesis's property tests do that on inputs nobody chose by hand: a Hypothesis strategy draws small portfolios, each feasible by construction around a witness plan drawn first, with every rule CIPT Lite has (must-dos, parents with lags, alternatives, yearly, regional and crew limits, floors). Each limit is drawn either tight (a little above the witness's use) or loose, so that every rule gets cases where it binds and cases where it leaves the plan free. Then one function checks every property from the data:



The plan must break no rule (by check, which never sees the model), its reported value must be the plan's value recomputed from the data, it must be no worse than the witness, and $10k more in every year's budget must never lower the value. The settings are lesson Property-based tests with Hypothesis's for repeatable runs: 200 examples, derandomize=True, no example database, no deadline. properties_200.py runs the correct model, and then two builders with a bug planted, each a slip a refactor can make:



Both bugs are caught, and Hypothesis shrinks each failure to a small case that still fails (lesson Property-based tests with Hypothesis): a child started in its parent's year when the lag is one year, and a two-year project whose second year's crews were never counted. Each counterexample names the broken row, so it reads as a bug report.


The witness carries most of the weight here. Without it, many drawn portfolios would have no plan, and a property test that skips them tests less than it seems; with it, every one of the 200 cases tests the solver's plan against a plan known to be valid.

The reference draws its portfolios this way; other choices pass as long as every planted bug is still caught:


  • Costs and windows. A cost profile of one or two years, each amount a multiple of $10k from $10k to $90k. The window lies inside 2027 to 2029 and leaves room for the whole profile: the latest start is at most 2029 minus the profile's length plus one.
  • Links. A parent is drawn from the projects already drawn, or none; the lag is 0 or 1 when there is a parent; the group is none (two chances in three) or "G1".
  • The witness. One start year is drawn in the window. The project may join the witness only if its parent is in it and started at least the lag earlier, and no project of its group is in it; if it may, a coin decides.
  • Must-dos. Only a project the witness funds can be a must-do, and a second coin decides whether it is one. A project outside the witness is never a must-do, so the witness keeps every must-do row.
  • NPV. A base value from −$10k to $100k at the earliest start, $5k less for each year the start is later.

A Golden Record Catches a Regression, Not a Rule Error


Properties check rules; they do not check that this month's answer is last month's. A golden record stores a reviewed result: the snapshot it came from, the status, the objective and the plan's digest (lesson Golden datasets and regression tests). CIPT Lite keeps three, in golden/cipt_golden.json, chosen so that different rules bind: GridCap small as exported, small with its 2028 budget cut to $6,000k, and medium with the run setting. The comparison speaks in business terms and separates a changed input and a tie from a regression:




The objective is compared within $10 (0.01 in $k), far above HiGHS's noise in the last digits and far below the smallest project. Fresh runs, then a run in which someone loosened the gap to 1%:



The loosened gap returned a plan $584k worse, and nothing else in the suite would have said so: the plan breaks no rule, so a check of it finds nothing, and it repeats ten times out of ten, so the harness passes. Only a record of the reviewed answer catches it. The reverse holds too: a rule written too strictly from the start would be in the golden record, approved, and the golden test would guard it. That is why the three pieces are kept together, and why a golden file is rewritten only on purpose (python3 trust_medium.py --write-golden) with its diff reviewed.


A Warm Start Is Last Cycle's Plan, Repaired and Handed Over as a Hint


Next cycle finance cuts 2028 to $40,000k, and the planners want the new plan to stay close to the old one where it can, and to arrive quickly. Lesson MIP starts from last cycle's plan's recipe: map last cycle's plan onto this cycle's variables, repair it until it breaks no rule, and hand the whole of it to the solver as a solution hint in ModelSolveParameters(solution_hints=...) (lesson Solution hints and ModelSolveParameters).




repair drops optional projects from the years whose limits the plan breaks, least NPV per $k first, each with its children, and never a must-do. The hint sets every start variable, 0 or 1, so the solver receives a complete plan to check rather than a partial one to finish (MathOpt's documentation says solvers may accept partial and even infeasible hints, and repair them with a sub-MIP of their own).



Last cycle's plan broke only the cut year; dropping seven projects repaired it. With the hint, HiGHS proved its plan within the gap in 29 nodes instead of 337, and the plan it stopped on is $37k better, since each search stops at the first plan proved within 0.1%. One scenario is not a measurement (lesson MIP starts from last cycle's plan measured over seeds and cycles); what this run does show is the last line: the hint is an input, recorded in the manifest by its digest, and the hinted run is as repeatable as the cold one.

Design Note: Four Tests, Four Questions


Each piece answers one question and is blind to the others': the harness asks "the same run?", the properties "a valid plan?", the golden record "the reviewed answer?", and the warm start's own harness run "still the same run once we add a hint?". A tool that has only one of them will one day pass it with a wrong answer; this lesson's 1% gap passed two of the four. Keeping all four is cheaper than finding out which one was missing.
