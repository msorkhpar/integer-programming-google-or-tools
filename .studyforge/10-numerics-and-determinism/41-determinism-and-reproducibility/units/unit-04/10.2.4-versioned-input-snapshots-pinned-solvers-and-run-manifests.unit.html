Two years after the 2026 plan of record, GridCap's regulator asks for it to be reproduced: same inputs, same model, same result, or an explanation of every difference. The planning team still has the plan. Does it have what produced it? Which portfolio file, after which edits? Which budget figures? Which version of OR-Tools, which solver, which seed and limits? If any of these was not written down at the time, the plan cannot be reproduced, only re-derived, and a re-derived plan may differ for all the reasons of lessons Where nondeterminism comes from: threads, time limits, ties to Alternative optima and deterministic tie-breaking.

This lesson writes down everything a run read, in a form that a later run can be compared with byte for byte: a snapshot of the inputs with a digest that names it, pinned solver versions checked at start-up, and a run manifest that records inputs, software and result in one canonical document. A Snapshot Is the Digest of the Inputs in One Canonical Form

A snapshot is the set of a model's inputs, frozen: the portfolio, the budgets, the overrides, the settings. To compare two snapshots, or to name one in a report, write it out in one canonical form, a text that equal inputs always produce and different inputs never do, and take its SHA-256 digest: a 64-hex-digit fingerprint that changes completely if a single character of the text changes. The hard part is the canonical form. snapshot.py tries the usual ways to get it wrong:

Line by line:

  • Dict order. json.dumps writes a dict's keys in the order they were inserted, so the same inputs built in another order give another digest. sort_keys=True writes them sorted, and the digests agree. str() of a dict follows insertion order too (the third line), so code that builds the dict the same way writes the same text on every run.
  • Sets. JSON has no set, so json.dumps refuses one. The tempting fix, str(the_set), writes the set in its iteration order, which depends on the process's hash salt (lesson Where nondeterminism comes from: threads, time limits, ties): two processes, two digests for the same set. Sort it first, and it digests the same everywhere.
  • Floats. 0.1 + 0.2 is written 0.30000000000000004, not 0.3: two computations of "the same" amount can differ in their last digit (lesson Floating point, tolerances, and why 1e-6 matters) and so in their digest. Keep money in whole units ($k as integers, as GridCap does) or round it before it enters a snapshot.
  • Key types. JSON keys are always strings, so {2027: 1} and {"2027": 1} write the same text. Usually that is what you want; just know that the digest cannot tell them apart.
  • GridCap's own hash (Portfolio.content_hash(), which uses sort_keys and fixed separators) is the same when the portfolio is generated again and changes when one budget moves by $1k.

The course's canonical form, used for every manifest in this module, is three settings of json.dumps:

sort_keys fixes the order, separators fixes the spacing, and ensure_ascii writes any non-ASCII character as an escape, so the bytes do not depend on a text encoding. Lists keep their order, so a list in a snapshot must be one whose order means something, or be sorted before it goes in.

Write snapshot_digest(inputs) that returns the 64-character hex digest. Equal inputs must give the same digest whatever order their dicts were built in and in any Python process; a changed number or string, or an item added to or removed from a list or set, must give a different digest. Inputs hold dicts with string keys, lists, sets of strings, strings and numbers, nested to any depth.

The canonical form, as in the lesson, is JSON with sorted keys and each set written as its sorted list. That form does not tell every pair of inputs apart, and the tests don't ask it to: a set and a list holding the same items in sorted order give the same digest, and so would a dict keyed by the number 2027 and one keyed by the string "2027", since JSON writes every key as a string. That is why keys must be strings and a field must always hold the same kind of value.

The Solver's Version Is an Input Too: Pin It and Record It


Lesson Where nondeterminism comes from: threads, time limits, ties listed the solver and its version among a run's inputs, and Gurobi's determinism article makes "the same version" a condition of getting the same result. The version you have is whatever the environment installed, so a reproducible run pins it (names the exact version in the environment's requirements; this course's runner image pins every package) and checks it, because a pin in a file does not stop someone running the code in another environment:






The first line answers a question that trips people up: which HiGHS does MathOpt run? The OR-Tools wheel carries its own HiGHS and SCIP libraries, and OR-Tools' release notes for v9.15 name them: HiGHS 1.12.0 and SCIP 10.0.0. The highspy package installed beside it is HiGHS 1.14.0, a different version used only by code that imports highspy (Pyomo's and PuLP's HiGHS interfaces, for example). So the OR-Tools version pins both the HiGHS and the SCIP that MathOpt runs, and the highspy version pins something else. A manifest records the OR-Tools version for the first, and highspy's only for runs that use it.


check_pins returns the mismatches rather than raising, so the caller decides; a service should refuse to start on any, and a harness (lesson Building the deterministic run harness) should record them. The last line shows what a stale pin looks like.


A Run Manifest Records What Went In and What Came Out, and Leaves Out the Clock


A run manifest is the record of one solve that another run is compared with. It holds:


  • inputs: the snapshot's digest and the model's options;
  • solver: its name and every parameter passed;
  • versions: Python, OR-Tools (and gurobipy when it ran), and the platform's operating system and processor architecture;
  • result: status, objective, bound, the plan and its digest, and the work done (nodes, iterations, branches, deterministic time).


solve_once.py writes it at the end of every run:






Two runs of GridCap small on HiGHS, one manifest printed field by field (the plan cut to its first three starts), and the two compared:



The two runs wrote identical bytes, so their SHA-256 digests match. Three choices made that possible.


The clock is kept apart. The wall time of a run is a fact about the machine and its load, not about the plan; it differs on every run (lesson Where nondeterminism comes from: threads, time limits, ties), so a manifest that held it could never match another. run returns it beside the manifest, under clock, where a log or a dashboard can use it. The same goes for anything else that varies by run and not by inputs: a start time, a process id, a temporary directory.


Nothing names the machine or a person. The platform field says Linux-x86_64, an operating system and an architecture. It does not say which machine: no host name, no user name, no home directory, no license id. Those would break byte equality between machines, and a manifest is shared, archived and attached to filings, so it must not carry anything that identifies a person or a machine. Lesson Licenses: size-limited, academic, and cloud/container (WLS) applies the same rule to Gurobi's license messages.


The work done is in. Nodes and iterations are not needed to use the plan, but they repeat when a run truly repeats (lesson Seeds, threads and deterministic work limits, solver by solver), and they differ first when something changed. A clock-limited run that happened to return the same plan still shows different iteration counts (lesson Where nondeterminism comes from: threads, time limits, ties), so keeping them makes the manifest stricter than the plan alone.


The plan itself is stored sorted (sorted([pid, t] ...)), so the order in which the code collected the starts never reaches the bytes.

Summary


  • A snapshot is the digest of the inputs in one canonical form. Sort keys, sort sets, fix the separators, keep money in whole units; then equal inputs give equal digests in every process.
  • The solver's version is an input too: pin it and record it. The OR-Tools wheel carries its own HiGHS (1.12.0 in v9.15) and SCIP; highspy is another HiGHS. Check pins at start-up.
  • A run manifest records what went in and what came out, and leaves out the clock. Inputs, solver and parameters, versions, and the result with its work counts, in canonical bytes; wall time and anything naming the machine or a person stay out.

Field of a manifestWhy it is there
inputs.snapshotthe digest of the data; equal digests mean equal data
inputs.* (model options)the question asked and how the model was built
solver.name, solver.paramsseed, threads, limits, tolerances: each changes the path (Seeds, threads and deterministic work limits, solver by solver)
versions.*Python, OR-Tools (which fixes MathOpt's HiGHS and SCIP), gurobipy, OS and architecture
result.status, objective, boundwhat was proved
result.plan, plan_digestthe plan itself, sorted, and its fingerprint
result.statswork counts: they differ first when a run changed
not in it: wall time, start timevary on every run
not in it: host, user, paths, license idsname a machine or a person

  3. Two machines run the same manifest config: one Linux-x86_64, one Darwin-arm64. Their manifests differ in versions.platform only. Is that a failure? What would you check next?


Design Note: One Canonical Function, Used Everywhere


Every digest in this module goes through one function, canonical. A snapshot hashed one way and a manifest compared another way will disagree for reasons that have nothing to do with the solve. Put the canonical form in one place, test it once (practice 1 does), and call it from the snapshot, the manifest and the harness alike.
