GridCap's planning service can call four solvers: HiGHS and SCIP through MathOpt, CP-SAT, and Gurobi for the teams that hold a license. The platform team must write one page of policy for each: which settings to pin so a rerun repeats, which limit to stop the search with, and which pieces of common advice are wrong. Two pieces of that advice are on trial in this lesson: "set Method=2 to make Gurobi deterministic" and "num_search_workers with a seed makes CP-SAT repeat".

Lesson Where nondeterminism comes from: threads, time limits, ties named the sources of a different answer: threads, clocks and ties. This lesson goes through the settings that control them, solver by solver, and runs each one. The model is lesson Where nondeterminism comes from: threads, time limits, ties's timing model, unchanged, with the NPV objective unless a run says otherwise; every run is a fresh process (repeat.py), and each block of output says which fields repeated. Three Settings Decide Whether a Run Can Repeat

Every solver here has the same three knobs, under different names:

  • The seed. A solver makes some choices at random: which of two equal candidates to branch on first, how to perturb an LP to avoid stalling. The random numbers come from a generator started from a seed, so a fixed seed gives the same choices. A seed is a label for one path, not a setting to tune.
  • The thread count. Several threads can make a run race (lesson Where nondeterminism comes from: threads, time limits, ties). Some solvers are built so that a fixed number of threads still repeats; others are not. Either way, the count is an input, and "use every core" makes the machine part of the input.
  • The kind of limit. A clock limit stops the path at a different place each run; a work limit, counted in the solver's own units (nodes, iterations, deterministic time, work units), stops it at the same place.

MathOpt offers common names for these (random_seed, threads, time_limit, node_limit), and its docstrings say only what each limits: the seed's valid range depends on the solver and an out-of-range seed is clamped, and nothing in them promises that a seed makes a run repeat. That is each solver's business, so this lesson measures it. solve_once.py turns a run's parameters into MathOpt's, sending HiGHS's thread count through HiGHS's own options because MathOpt refuses the common threads for HiGHS (lesson Common vs. solver-specific parameters, and what each solver rejects):

HiGHS: A Seed, a Thread Count Fixed per Process, and a Node Limit for Work

HiGHS's options list has random_seed (default 0), threads (default 0, meaning HiGHS decides) and time_limit in seconds. It lists no limit on deterministic time; the limits that count work are counts of steps, such as mip_max_nodes for branch-and-bound nodes, which MathOpt's node_limit reaches (the runs below stop at exactly 300 nodes). GridCap medium, stopped at 300 nodes, under three seeds and then under two thread counts, each setting run twice:

Each seed repeats itself exactly, down to the simplex iterations, and each seed takes another path to another plan: three seeds, three plans, three bounds after the same 300 nodes. The thread count changed nothing on this model: one thread, four threads and HiGHS's own choice all gave the seed-1 run. That is a measurement on one model and one HiGHS version, not a promise for every model, so the policy still pins the count.

Pinning it has a HiGHS-specific rule. The first HiGHS solve in a process fixes the thread count for the whole process, and a later solve asking for a different count fails (lesson Common vs. solver-specific parameters, and what each solver rejects shows it). So a service decides the count once, at start-up, and passes that same value on every solve; a harness that compares thread counts runs each in its own process, as repeat.py does.

The HiGHS policy, then: a fixed random_seed, a thread count fixed for the process through highs=HighsOptionsProto(int_options={"threads": n}), and node_limit rather than time_limit when the run must repeat.

Problem statement

A freight company plans next week's truck loads with a MILP solved by HiGHS through MathOpt, every night, and wants each night's run to be repeatable from its manifest. The manifest records three numbers: a seed, a thread count and a node limit.

Write highs_parameters(seed, threads, nodes) that returns the mathopt.SolveParameters for such a run: the seed, a pinned thread count passed the way HiGHS accepts it through MathOpt, and the node limit as the only limit you add. Set no time limit, since a clock limit stops at a different point on every run. Leave the gap tolerances at their defaults: the reference sets nothing besides these three, and the gap is not set to 0. The tests solve a small model with what you return, always with threads=1.

CP-SAT: num_workers Is the New Name, and Only Interleaving Makes Workers Repeat


CP-SAT's parameters proto defines the worker count twice. num_workers is the current name; the proto calls num_search_workers deprecated and says it is still read when num_workers is 0. The program prints both fields' numbers in the proto and what setting the old one does:






They are two separate fields, and setting the old one leaves the new one at 0, its "not set" value, so the solver falls back to reading the old one. Code and articles written before the rename still work, which is why the old name keeps appearing. Neither name is a determinism setting. Four workers under each, with a seed and a deterministic limit, on GridCap medium:



The seed and the work limit did not stop four racing workers from ending at different plans. interleave_search, which the proto marks experimental and describes as deterministic whatever the number of workers, made every field repeat, and the two names gave the identical run. As in lesson Deterministic time, seeds and reproducible runs, the interleaved search ran well past its limit of 2 (8.2350 units here), so treat the limit as approximate in that mode.


solve_once.py sets CP-SAT's parameters by name, so a config can use either name:




The CP-SAT policy: num_workers (not the old name) and random_seed, a max_deterministic_time limit rather than max_time_in_seconds, and interleave_search = True whenever there is more than one worker; or one worker. Recheck the interleaved mode on every OR-Tools upgrade, since the proto calls it experimental.

Problem statement


A vegetation-management contractor rosters its tree-trimming crews with CP-SAT. The roster must be reproducible: the same data and the same three numbers from the run's manifest (seed, worker count, amount of work) must give the same roster on any rerun on the same OR-Tools version.


Write configure(solver, seed, workers, work). It sets the parameters of the given CpSolver so that a run with those three numbers repeats, whether workers is 1 or more, and returns the solver. work is the deterministic amount of work at which the search stops. Leave every other parameter at its default.

SCIP: Repeatable Here, and a Seed That Picks Among Tied Plans


SCIP's own parameter list includes randomization/randomseedshift, which shifts every random seed SCIP uses, its LP solver's included; permutation seeds, off by default; and parallel/mode, whose default is the deterministic mode. The runs here leave the thread count unset. Three runs on GridCap small's NPV question, the count question under two seeds, and GridCap medium stopped at 200 nodes under two seeds:



Every setting repeated, node counts included. On the NPV question SCIP found the same plan HiGHS did (092777a3fdd1), because there is only one best plan. On the count question, where many plans tie, the seed alone picked which one came back: seed 1 and seed 4 returned different plans, each one every time. That is the seed acting as a tie-picker, and the reason a seed belongs in the record of a run. On medium the two seeds ended at the same plan with different bounds, showing that they took different paths.


One caution from earlier in the course: on the indicator model of lesson Indicator constraints vs. big-M, SCIP's node count differed between runs with a fixed seed and one thread, while the values and statuses repeated. On this model the counts repeated. Check your own model before you put SCIP's node count in a comparison.


Gurobi: Deterministic for a Fixed Thread Count, and Method=2 Is Barrier


Gurobi's parameter reference and its support article "Is Gurobi deterministic?" say:


  • Gurobi is designed to be deterministic: the same model, parameters, version and computer give the same result and path, with several threads too;
  • Threads defaults to 0, meaning about as many threads as the machine has virtual processors;
  • Seed perturbs the path; TimeLimit is in seconds and can make runs differ, while WorkLimit counts work units (roughly a second of one thread's work) and is deterministic;
  • Method picks the algorithm for an LP or a MIP's root relaxation: 0 primal simplex, 1 dual simplex, 2 barrier, 3 concurrent (not deterministic), 4 and 5 deterministic concurrent, and -1 automatic, which can choose a non-deterministic concurrent run in some cases;
  • ConcurrentMIP, off by default, is not deterministic.


gurobi_settings.py checks this on GridCap medium (887 binaries, inside the size-limited license). Every Gurobi environment starts quiet, as in lesson Models, attributes and the matrix API, because Gurobi's messages can name the machine and the license holder, and the program prints only numbers:




The fingerprint is Gurobi's Model.Fingerprint attribute, a hash of the model as Gurobi received it, so equal fingerprints confirm that every run solved the same model. Reading the output against the two claims:


  • Gurobi is deterministic by default for a fixed thread count. The default run repeated in all three processes, nodes and work included. So did Threads=1 and Threads=4, each with its own path: the thread count is an input. The default uses the machine's processor count, so the default line is a fact about the machine these runs used; on yours it may show another plan. Pin Threads in a policy, and the default's repeatability then carries to any machine with the same version and enough cores.
  • Method=2 is barrier, not a determinism switch. It repeated, like every setting above, and it took another path to another plan. It does rule out the automatic choice of a concurrent LP run, which the support article warns can be non-deterministic, and so would 0, 1 or 4; but the default run here repeated without it. Pinning Method is a fine way to make the root algorithm explicit; it is not what makes Gurobi repeat.


Two more lines are worth reading. WorkLimit=0.2 stopped every run at the same node with the same plan, while TimeLimit=0.3 stopped each run after a different amount of work. And the four settings that finished, all OPTIMAL, report four objectives between 226,807 and 226,815: a MIP is "optimal" when its gap is within the tolerance (MIPGap, 0.01% by default), so plans worth $8k apart on a $227 million objective can all be optimal. Lesson Alternative optima and deterministic tie-breaking takes that up.


Summary


  • Three settings decide whether a run can repeat: a fixed seed, a fixed thread count, and a limit that counts work rather than seconds.
  • HiGHS: a seed, a thread count fixed per process, and a node limit for work. Each seed repeated and took its own path; set threads through HiGHS's options, once per process.
  • CP-SAT: num_workers is the new name, and only interleaving makes workers repeat. Four workers raced under either name; interleave_search repeated every field.
  • SCIP: repeatable here, and a seed that picks among tied plans. Every setting repeated here; seeds 1 and 4 returned different tied plans on the count question.
  • Gurobi: deterministic for a fixed thread count, and Method=2 is barrier. Every setting with a work limit or none repeated; the thread count and the method each changed the path.

Design Note: A Policy per Solver, Written Down


The three settings have different names and different traps in each solver: HiGHS's thread count sticks to the process, CP-SAT's workers need interleaving, Gurobi's default thread count is the machine's. Write the repeatable settings for each solver once, in one function per solver, and record what they were in every run's manifest (lesson Versioned input snapshots, pinned solvers and run manifests). A setting chosen in one place and recorded every time can be checked; one typed at each call site cannot.
