GridCap's board asks a blunt question before the rate case: how many of the forty projects on the small portfolio can we start within the five yearly budgets? The planning team runs the model, gets 33, and sends the list. The next morning an analyst reruns the same code on the same data to attach the plan to the filing. The answer is still 33, but the list is different. Neither list breaks a rule; both fund 33 projects. Which one is the plan of record, and why did the same program give two?

Lesson Deterministic time, seeds and reproducible runs measured one part of this on CP-SAT, and lesson The planning cycle: Initial, Pre-Opt, Post-Opt, Budget Lock locked a plan whose rerun matched while warning that a match is evidence, not a guarantee. This lesson names every source of a different answer, shows each with a program on the course's GridCap model, and gives each one a place to look. Lesson Seeds, threads and deterministic work limits, solver by solver then goes through the settings that control them, solver by solver; Alternative optima and deterministic tie-breaking deals with ties; Versioned input snapshots, pinned solvers and run manifests and Building the deterministic run harness build the record and the test that catch a difference.

GridCap is a fictional utility's portfolio; none of its numbers are real.

A Run Repeats Only Relative to Everything It Read

A run is deterministic when solving the same inputs again gives the same outputs: the same status, the same objective, the same plan. The catch is in "the same inputs". A solve reads far more than the data file:

  • the data, here the GridCap portfolio;
  • the model as built: which variables and rows exist, and also the order in which the code added them, because the solver receives them as numbered columns and rows;
  • the solver and its version;
  • the parameters: the seed, the thread count, the limits that stop the search, the tolerances that decide when a plan counts as optimal;
  • the machine: how many cores it has, and how busy it is while the solve runs.

Gurobi's own answer to "is Gurobi deterministic?" lists the same things: the same model, parameters, version and computer give the same result and the same path, and changing almost anything, down to the order of variables or constraints, can change it. That is true of every solver in this course. When a rerun differs, one of these inputs differed, and it is usually one of three: threads that race, a clock that stops the search, or ties between plans that are equally good, where any small change picks a different winner. The rest of the lesson shows each.

To see a difference you have to look for it the right way. The programs of this lesson run every solve in a fresh Python process and compare the results field by field. A fresh process matters for two reasons this lesson and the next show: Python gives each process its own hash salt, and HiGHS fixes its thread count at the first solve of a process (lesson Common vs. solver-specific parameters, and what each solver rejects). Rerunning inside one process can hide both. repeat.py starts each run as a child process with its own PYTHONHASHSEED (the variable that sets Python's hash salt; more on it below):

Each child, solve_once.py, builds the model a config describes, solves it, and prints a record of the run as one line of JSON (lesson Versioned input snapshots, pinned solvers and run manifests calls this record a run manifest). summary then prints each field's value if all runs agreed, and differs if they did not:

The plan is compared through plan_digest, a fingerprint: the first 12 hex digits of the SHA-256 hash of the plan's sorted (project, start year) pairs, so equal digests mean equal plans.

Parallel Workers Race, So the Plan Can Change Between Runs

A solver with several threads splits its work between them. CP-SAT runs a portfolio of different searches at once (lesson Workers, search strategies and LNS), and they pass plans and bounds to one another as they find them. How fast each thread runs is decided by the operating system, not by the solver, so which search finds which plan first, and what the others then build on, changes from run to run. Four workers, the same seed, and a deterministic limit of 2 (a limit on CP-SAT's own count of work, which lesson Deterministic time, seeds and reproducible runs introduced), on GridCap medium:

All five runs stopped at the limit with a feasible plan, and the plans they stopped with differ in value. Nothing in the inputs changed between the runs; only the timing of four threads did. Lesson Deterministic time, seeds and reproducible runs found the same with eight workers and showed the two ways out (one worker, or interleaved search); lesson Seeds, threads and deterministic work limits, solver by solver shows what HiGHS and Gurobi do with threads.

A Clock Limit Stops the Search Wherever the Clock Says

A time limit stops the search when a given number of seconds has passed on the clock. The search is the same sequence of steps each time, but how many steps fit in 3 seconds depends on how busy the machine is. HiGHS on GridCap medium, which it cannot prove optimal in a few seconds, stopped by a 3-second limit and then by a limit of 300 branch-and-bound nodes:

Under the clock the number of simplex iterations (the LP solver's steps) differs from run to run: each run stopped at a different point of the same path. Whether the plan differs too depends on whether a better plan turned up between those stopping points, so the program prints only the two fields above. While this lesson was written, some runs of it returned one plan three times and others returned different plans; nothing about a clock limit makes either outcome reliable. Under the node limit, a count of work rather than of seconds, every number repeats, iterations included. A work limit of this kind stops at the same point on every run, so it is the limit to use when a run must repeat; a time limit is the one to use when a planner is waiting (lesson Stopping on gap, time, nodes or solution count compares the stopping rules).

When Plans Tie, Input Order Picks the Winner

The board's question has many answers. Counting projects gives every start the same weight, 1, so any two plans that fund 33 projects are equally good, and the solver may return any of them. Lesson Alternative optima and deterministic tie-breaking counts them; here the question is which one comes back.

Suppose the code collects the project ids in a Python set before building the model, a common habit (a set removes duplicates). A set's iteration order depends on the hashes of its items, and Python salts the hashes of strings: each process mixes a random value into hash() of every str and bytes, so the hash of the same string is the same within one process but different in the next. The salt is set by the environment variable PYTHONHASHSEED: unset or random means a new salt per process; an integer fixes it; 0 turns the salting off. Two fixed seeds stand in for two ordinary runs:

hash() and the set's order change with the salt; sorted() and a SHA-256 digest from hashlib do not, because they depend only on the characters. With the default random salt, five processes gave five different hashes for the same string.

solve_once.py has an order option that builds the model from such a set:

The count question, solved four times with the projects in the portfolio's order and four times in a set's order, on HiGHS (with a zero gap tolerance, so each run proves its plan optimal) and on CP-SAT (one worker, a fixed seed):

Every run proves 33 optimal. With the projects in a fixed order, each solver returns the same plan every time, and with them in a set's order it does not, on either solver. The rows are the same in every run; only their order changed, and the order was enough to pick another of the tied plans. This is the morning analyst's story: two processes, two salts, two orders, two lists of 33.

Two more facts in that output matter. HiGHS and CP-SAT, each perfectly repeatable in the given order, return different plans from each other (e47f42d78207 and 7485409b35c7): a change of solver is a change of inputs too. And the NPV question, built in a set's order the same way, gives one plan in every run:

On GridCap small that question has a single best plan, so there is nothing for the order to pick between. Ties are a property of the question and the data, not of the solver.

So a set in model-building code is harmless when the model has one optimal plan and a source of irreproducible plans when it has several. The fix is cheap: build from a sorted or otherwise fixed order, never from a set's iteration order or from hash(). Gurobi's determinism article names Python sets as a cause of exactly this.

Summary


  • A run repeats only relative to everything it read. Data, the model's build order, the solver and its version, the parameters and the machine are all inputs. Compare reruns in fresh processes.
  • Parallel workers race, so the plan can change between runs. Four CP-SAT workers under a deterministic limit did not give one plan in five runs.
  • A clock limit stops the search wherever the clock says. A time limit stopped HiGHS at a different iteration each run; a node limit repeated every number.
  • When plans tie, input order picks the winner. Python salts string hashes per process, so a model built from a set's order returned a different one of the tied optimal plans in each process.

Design Note: Compare Runs in Fresh Processes


A loop that solves the same model five times in one Python process hides two of the sources above: every solve shares one hash salt, so a set has the same order each time, and HiGHS keeps the thread count its first solve chose. The loop then reports "repeatable" for code that is not. Start every run you compare in its own process, with its own hash seed, as repeat.py does; lesson Building the deterministic run harness builds the harness on that rule.
