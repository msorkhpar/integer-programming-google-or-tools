Request 8. Finance wants the plan as a table they can read: money and risk by year, against each year's budget, with a line saying how good the plan is. The operations analysts will run it themselves, so it needs a command, a version, and tests that tell them when a change has moved the answer. Same input, same report, every time.

The code before this lesson is snapshot steps/07; after it, steps/08. The fleets are invented (GridCap is fictional), and the report says so on its second line.

The Code Prints for Its Author, Not for Finance

After seven lessons the project answers every planning question so far, but the only way to get an answer is python -m renewal, which prints a few lines meant for the engineer: units replaced, the objective, the bound, a line per year. It has no version, so nobody can say which code made a given plan; it has no flags, so a different fleet size or budget means editing __main__.py; and nothing checks that the next change leaves a reviewed plan alone. The tests of the earlier lessons check rules, one at a time. None of them would notice if a refactoring kept every rule and moved forty units to other years.

The Design Decision: A Report Function, a Command, and a Golden File

Three pieces, each the smallest that does the job:

NeedChoiceAlternatives considered
a table finance readsfinance.py: lines per year, then Markdowna spreadsheet file (a new dependency); an HTML page (more than asked)
a way to run itcli.py with argparse, declared as the renewal command in pyproject.tomlkeep python -m only (no version, no install)
notice when an answer movesa golden report, reviewed once, compared on every test run (the section 12 lesson Golden Datasets and Regression Tests)value tolerances only (miss moved units)

The report's numbers come from one function, finance_lines, and the Markdown is only a rendering of them. Tests check the numbers against the plan; the golden file checks the rendering and the plan together.

The Model Does Not Change

This lesson changes no row, variable or objective. The model is the last lesson's, solved on the base curves by default. That is worth saying in a handoff: finance is told which model produced the table, and a reader of the code sees that the step touched reporting and packaging only.

The Change, File by File

finance.py (new): the plan as finance reads it. One YearLine per plan year, years with no work included, so the table always has the plan's ten rows:

finance_lines(fleet, request, plan) fills one YearLine per year of request.plan_years(), in order, and its body is yours to write in the practice. For each year: the units the plan replaces that year and the sum of their costs; the number of that year's pairs in report.outages and that number times request.outage_cost; as the total, that year's entry of report.spend_by_year with the request's outage cost, 0 for a year with no work; request.budget; and the sum of risk_removed(t, year, request) over the year's units, on the base curves.

The money comes from report.spend_by_year and report.outages, the same functions the tests of the outage lesson pinned; the risk from risk.risk_removed, the model's own coefficient. Nothing is computed twice in two ways. The last line of the report states the bound in finance's terms:

cli.py (new): the command. It holds the 500-unit request that __main__.py used to hold, scales it for larger fleets, and lets an analyst set the fleet size, seed, budget and gap:

main returns 0 when a plan was found and 2 when not, so a script that runs it can tell the two apart. A Plan carries its status as the termination reason's name, a string, so solve.py gains FOUND_NAMES, the names of the reasons in FOUND, and main tests the status against it:

main takes argv as an argument, so tests call it directly instead of starting a process.

__main__.py: one line. python -m renewal now runs the same main as the installed command:

pyproject.toml and __init__.py: a package with a version. The stub file becomes a project declaration: a name, a version, the pinned OR-Tools it was tested with, and the renewal command. __version__ repeats the version in the code, and a test keeps the two equal.

One limit, stated plainly: the course's runner image has no setuptools, so pip install . cannot build this package inside it, and the lesson does not claim it does. What the runner can do is pack the package into one runnable file with the standard library's zipapp, which is how handoff.py checks that the package runs from outside its folder.

The Report for the 500-Unit Fleet

handoff.py runs the command on the 500-unit fleet with the default request (gap 2%, per-unit outage rows, base curves):

Finance can read three things off it without knowing what a model is. The plan spends $98,130k of $100,000k, and $18,300k of that, almost a fifth, is outages, which is the cost of the substation rule. The risk removed per year falls steadily, from $103,272k for the 2027 work to $13,540k for 2036's, because each later replacement is counted over fewer of the 20 risk years and the riskiest units go first. And the last line says the plan is within 1.70% of the best any plan could do under these rules, which is the honest form of "optimal" at a 2% tolerance.

The Tests Guard the Numbers, the Report, Repeatability and the Declaration

  • the finance lines add up to the plan: on a 40-unit fleet, one line per year; units, totals and risk add up to the plan's own counts, spend_by_year and objective; and every year's total is its replacements plus its outages and within budget.
  • the report matches the reviewed golden file: main on a 30-unit fleet, exact solve, writes a report equal to tests/golden/plan_30.md, character for character. The golden file was produced once by this code and read before it was kept; a change that moves the plan fails this test until someone reviews the new report and replaces the file on purpose.
  • two runs write the same report: the same input gives the same bytes. HiGHS is run with its defaults here, and the test is what says that, on this fleet and image, its answer repeats (the determinism lessons, Where nondeterminism comes from: threads, time limits, ties to Building the deterministic run harness, list what would break it: threads, time limits, ties).
  • the package declares its version and command: pyproject.toml names renewal.cli:main as the renewal command, and its version equals renewal.__version__.

Of the four, only the golden test notices a plan that moved. The other three would pass on it: the finance lines add up to whatever plan the code found, two runs of the changed code still write the same report as each other, and the declaration test reads pyproject.toml and __version__, never a plan.

The golden fleet is small and solved exactly (--gap 0) on purpose. A golden test of a run stopped at 2% would compare whichever plan the solver stopped at, and a harmless change in the search could move it.

On the last lesson's code, the stub finance_lines returns no lines, the stub main returns 1, and the stub pyproject.toml declares no command; each test fails on that assertion. The practice is set up differently on one point: it gives pyproject.toml finished and read-only, with the command and the version declared, so in the practice the declaration test passes its first assertion and fails on its second, because the starting package has no __version__.

What the Step Did to the Code, and to the Project Overall

This step added 58 code lines and no branching to the model: the report and command are straight code. Over the whole module the package grew from 104 lines to 497 and the tests from 4 to 36, with about one line of test for every two lines of code. The two numbers that deserve a reviewer's eye are the branching ones. model.build reached 23 when crews and spares were added and 24 with the scenario objectives, and its reference copy keeps the old 23 alongside it. A next request should begin by splitting build into one function per constraint family, each taking the shared variables: the rows are already written as separate blocks, so the split moves code rather than changing it, and the reference-model test of the scale lesson says whether it was moved correctly.

Practice. This lesson's project practice starts from the code before this step, the whole package (snapshot steps/07). It is graded by the tests in the practice's tests/ folder and by a check that main.py prints the practice's expected/report.txt; the practice's statement gives the request main.py makes and the format of every line it prints. Problem statement

The plans are trusted, and finance sent the last request:

Request 8. Finance wants the plan as a table they can read: money and risk by year, against each year's budget, with a line saying how good the plan is. The operations analysts will run it themselves, so it needs a command, a version, and tests that tell them when a change has moved the answer. Same input, same report, every time.

You start from the model with scenarios. Write the plan as finance reads it: one line per plan year, years with no work included, with its units, replacement cost, outages and their cost, total, budget and the risk removed; then a Markdown report of those lines, their totals, and a sentence giving the solver's status and the bound no plan beats. Put it behind a command, renewal, that writes the report to a file or prints it, and give the package a version that matches pyproject.toml (given, read-only). The report for a 30-unit fleet must match the reviewed golden file in tests/golden/.

Run executes main.py, which runs the command's main on a tiny fleet: 25 transformers of GridCap, a fictional utility, drawn by renewal/fleet.py from seed 56, with a budget of $2,000k a year and the command's default gap, and prints the finance report. Its whole body is one call:

with main from renewal.cli. The report it prints, like the golden file, is Markdown:

with one <year> row per plan year, years with no work included, and a blank line after the title, after the fleet line and after the table. Money has a comma between thousands and no decimals; units and outages are plain counts. The Total row sums each column, the budget too. <gap> is (bound − value) / bound as a percentage with two decimals (f"{gap:.2%}", 0 when the bound is 0). expected/report.txt is the report it should print. finance_lines in renewal/finance.py

  • Contract. One YearLine per plan year, in order, years with no work included: year, units replaced, their replacement cost, the outages that year and their cost, the total (spend_by_year's figure), the budget, and the risk removed by that year's replacements (risk_removed, base curves). YearLine is a frozen dataclass of those fields, in that order.
  • Modeling idea. A report's numbers come from the same functions the model and its tests use, so they add up to the plan.
  • Taught in 14.3.8 Handoff: Tests, Packaging and a Report for Finance.

finance_report in renewal/finance.py

  • Contract. The Markdown report the golden file shows: a title with the plan's years, the fleet's size marked as fictional data, the table of finance_lines with a Total row, and a closing sentence with the solver's status, the bound, and the plan's gap to it.
  • Modeling idea. Report the bound and the gap, not the word optimal: they say how good the plan is.
  • Taught in 14.3.8 Handoff: Tests, Packaging and a Report for Finance.

main in renewal/cli.py

  • Contract. Parses --units (default 500), --seed (2027), --budget, --gap and --out; scales the 500-unit request by units // 500 (at least 1), overrides its budget and gap when given, plans the generated fleet, and writes finance_report to --out or prints it. Returns 0 when a plan was found, 2 when not. The package's __init__ declares __version__, equal to pyproject's version.
  • Modeling idea. A golden file pins the whole report; a change that moves the answer fails the test until a person reviews the new file.
  • Taught in 12.3.3 Golden Datasets and Regression Tests.

Summary


  • A handoff adds no rules. It adds a report function, a command, a version and tests that watch the answer, and leaves the model alone.
  • The report's numbers come from the code the tests already pinned, and the Markdown is only their rendering; its last line states the bound and the gap in finance's terms.
  • A golden file catches a moved plan that every rule test misses. Keep its run exact and small, and update it on purpose, after review.
  • Same input, same report is a test, not an assumption.

Design Note: The Report States the Bound, Not "Optimal"


OPTIMAL from a solver stopped at a 2% gap means "within 2%". Finance reads "optimal" as "best". So the report's last line says what the run proved, a bound no plan can beat and how close this one is, and keeps the solver's word for the status only. A handoff document that overstates the answer is a bug the tests cannot catch.
