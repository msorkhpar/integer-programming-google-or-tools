  16. The first request: replace the worst transformers

GridCap's asset team keeps a spreadsheet of its substation transformers. Every autumn an engineer sorts it by condition score, walks down the list and stops when the year's money runs out. This year the engineer has been asked to turn that habit into code, and writes the request down:

Request 1. We have $10,000k for transformer replacements in 2027. Replace the worst transformers we can afford. The list must be repeatable, so put it in code, with tests.

This module grows that request into a real planning model, one requirement per lesson. The project lives in complete snapshots: steps/00 is the code before this lesson, steps/01 the code after it. The fleet is invented, made by a seeded generator in the project (GridCap is fictional), and the first lesson starts where the engineer did: with the ranking.

The Starting Code Ranks by One Number and Stops at the First Unit That Does Not Fit

The skeleton has four modules. fleet.py holds one record per transformer and the generator; rank.py holds the asset team's rule; report.py adds up what a list costs and removes; and __main__.py prints this year's list. A transformer carries what the asset team knows about it:

FieldMeaning
tid, substation, regionidentity and where it is
kindsmall, medium or large, which sets its cost range and failure curve
ageyears in 2027
cost$k to replace it
cofconsequence of failure: $k that one failure costs (lesson Consequence of failure and risk = PoF × CoF)
conditionthe inspection score, 0 to 100, higher is worse
pofthe asset-health team's probability that it fails in 2027 (lesson Probability of failure and hazard curves (Weibull))

The ranking sorts by condition and takes units until the next one would break the budget:

The program first_request.py runs it on a 500-unit fleet. The measure of a list is the risk it removes: a unit's expected failure cost this year, $\text{pof}_i \times \text{cof}_i$ in $k (lesson Consequence of failure and risk = PoF × CoF), summed over the units replaced:

Nine units. The list is short because the worst-scored units are not cheap, and the walk stops at the tenth, which does not fit, although cheaper units further down would.

A Condition Score Is Not Risk, and the Ranking Cannot See Cost

Three things are wrong with the ranking, and only the last is about code:

  1. It ranks by condition, and condition is not risk. Condition says how worn a unit looks. Risk also needs what a failure costs: a worn unit feeding few customers can matter less than a fair one feeding a hospital.
  2. It ignores what a unit costs. Two $400k units can remove more risk than one $1,090k unit.
  3. It stops at the first unit that does not fit, and leaves money on the table.

The top of the worst-first list shows the first two:

All five score 100, so the sort cannot tell them apart and falls back on the id. T00033 and T00076 are the same kind at about the same age, with almost the same PoF; T00076's failure costs five times as much. The "in model" column is the plan of the next section: it keeps 2 of the 9 ranked units.

A better ranking fixes the first two faults: sort by risk removed per $k, and skip a unit that does not fit instead of stopping. It is a common next step, and the program tries it too:

The ratio ranking removes 3.5 times what worst-first removes. On one budget it comes close to the model, but not all the way:

The ratio ranking is a greedy rule for a knapsack: choose items, each with a value and a weight, to get the most value within a capacity (lesson 0-1 and multi-dimensional knapsack). Greedy by value per weight is good on one knapsack and still not optimal, because the last few choices depend on what exactly fits. More to the point for this project, a ranking cannot carry a second rule. The requests that follow add ten years of budgets, outages shared by a substation, crews per region and spare units. A ranking has nowhere to put any of them. A model does: each rule is one more row.

The Design Decision: State the Choice as a 0-1 Model, Keep the Ranking as a Baseline

The engineer has three options:

OptionForAgainst
keep worst-firstthe asset team knows itremoves 28% of what the best list removes here
ratio rankingsimple, close on one budgetno bound to say how close; cannot hold a second rule
0-1 model, solved by HiGHSbest list, with a bound; each rule is a rowa solver dependency and a model to test

The project takes the model, and keeps rank.py as a baseline to compare against: a plan that is worse than the asset team's list is a bug, and the comparison is the first thing a reviewer asks for. The model is written with MathOpt, the OR-Tools modeling layer (lesson Model, variables, constraints, objective), and solved with HiGHS. A solve also returns the bound (lesson Best bound, incumbent, absolute and relative gap): no list can remove more than it. Here the bound equals the plan's value, so the plan is proved best, which no ranking can say about itself.

The Model

The first model is a 0-1 knapsack with one row.

Sets. $I$, the transformers in the fleet.

Parameters. $r_i = \text{pof}_i \cdot \text{cof}_i$, the risk removed by replacing unit $i$ in 2027 ($k), since a new unit's chance of failing in its first year is negligible next to an old one's; $c_i$, its replacement cost ($k); $B$, the 2027 budget ($k).

Variables. $x_i \in \{0, 1\}$ for every $i \in I$: 1 if unit $i$ is replaced in 2027.

Constraints.

The Change, File by File

Six files change or arrive; one of them, risk.py, is only a stub for the next lesson. Each diff below is lifted from the two snapshots it names.

model.py (new): the formulation as code. Built keeps the handles the rest of the code needs: the model, the variables by transformer id, and the budget row. build writes the model above line for line, and its variables and its row are yours to write in the practice:

  • The variables. One binary $x_i$ per transformer of the fleet, made with model.add_binary_variable(name=...) and named x_<tid> (x_T00042), in a dict keyed by the transformer's id.
  • The row (budget). The sum of t.cost times $x_i$ over the fleet at most request.budget, added with model.add_linear_constraint(..., name="budget"), whose return value is the row handle Built keeps.
  • The objective. It is the one line of the body the page shows; the risk $r_i$ is fleet.risk(t):

solve.py (new): solving and reading the answer. Four names, all new:

  • FOUND is the pair of termination reasons that come with a plan, OPTIMAL and FEASIBLE (lesson Reading SolveResult: termination, primal and dual solutions, statistics); every other reason means no plan to read.
  • solve_quietly calls HiGHS with the process's output pointed away for the solve, so a stray line from the bundled HiGHS never reaches the report (the course's runs do the same). Two lines do the work. os.dup2(sink, 1) points file descriptor 1, the process's standard output, at /dev/null, which silences C code that never goes through Python's sys.stdout; the saved copy puts it back afterwards. ctypes.CDLL(None).fflush(None) calls the C library's fflush on every C stream before that, so output HiGHS left in C's buffer is written to /dev/null now, not to the report later.
  • is_feasible asks whether the result's termination reason is in FOUND.
  • read_plan turns a result into a Plan: the ids whose variable is above 0.5 (a binary comes back as a float within the solver's integrality tolerance, lesson Floating point, tolerances, and why 1e-6 matters), the objective, the bound and the termination reason (lesson Reading SolveResult: termination, primal and dual solutions, statistics).

risk.py (new): a stub for the next lesson. Nothing in this step calls it; it holds the names the next lesson fills in, each returning 0:

plan.py: the entry point stops ranking. In the skeleton, plan was a stub that returned the ranking and feasible a stub that allowed everything, so that this lesson's tests could import them and fail on their assertions. The Tests Pin the Mistakes a Ranking Makes, on Fleets Small Enough to Check by Hand

The tests never use the 500-unit fleet. Each builds a fleet of three to eight units where the right answer is known, the style of the section 12 lesson Unit-Testing One Constraint at a Time:

  • the riskiest, not the worst-scored: unit A scores 95 but its failure costs $1,000k; B and C score lower and cost $3,000k and $2,500k. The plan must be {B, C}.
  • money a ranking leaves: A, B and C cost $500k, $700k and $400k under a $1,000k budget. The ranking takes A, cannot fit B, and stops. The plan must be {A, C}.
  • the best subset: eight random units; the plan's value must equal the best of all 256 subsets, found by brute force. A model too small to get wrong by inspection is checked by enumeration.
  • the budget row, at its edge: a list that spends exactly $1,000k is allowed, and the same list plus a $10k unit is refused. An allowed plan and a refused one sit in the same test, so a model with no budget row fails it.

The new tests, run on the skeleton's code and then on this lesson's:

Before the change, every new test fails on an assertion that names the ranking's mistake: it picks {A} where {B, C} is right, stops at [A], misses the best subset by $1,081k, and allows a list over budget. The skeleton's four tests (the generator and the ranking) pass both times. Problem statement

The asset team sent the first request:

Request 1. We have $10,000k for transformer replacements in 2027. Replace the worst transformers we can afford. The list must be repeatable, so put it in code, with tests.

You start from the skeleton: it generates a fleet and ranks it worst condition first, stopping at the first unit that does not fit. Keep the ranking as a baseline, and make plan choose with a model instead. Each transformer is replaced this year or not, the replaced units together cost no more than the budget, and the plan removes the most risk, where a unit's risk is its probability of failure this year times its consequence of failure (fleet.risk). Build the model with MathOpt and solve it with HiGHS. Then write feasible, which pins one whole list and asks the solver whether the model allows it, so a test can show a list at the budget allowed and one just over it refused.

Blueprint

Write each method below. The tests check each one by itself and the whole program end to end, so you may change any other part of the code as you see fit.

plan in renewal/plan.py

  • Contract. Builds the model, solves it with HiGHS through MathOpt, and returns a Plan: each transformer whose variable is 1 mapped to FIRST_YEAR, the objective value, the dual bound, and the name of the termination reason as the status. With no plan found, a Plan with no replacements and the status alone. Nothing the solver prints may reach standard output, since Run's report is compared line by line.
  • Modeling idea. Read the termination first, then the variable values; a binary is 1 when its value is above 0.5.
  • Taught in 4.2.2 Reading SolveResult: Termination, Primal and Dual Solutions, Statistics.

build in renewal/model.py

  • Contract. A new module. Returns a Built, a dataclass holding the MathOpt model, the variables x keyed by transformer id, and the budget row: one binary variable per transformer named x_<tid>, one row named budget keeping the summed cost of the replaced units within request.budget, and the summed risk of the replaced units as the objective to maximize.
  • Modeling idea. A yes-or-no choice per unit under one budget is a 0-1 knapsack: the best list is a combination, which no ranking finds in general.
  • Taught in 6.3.1 0-1 and Multi-Dimensional Knapsack.

feasible in renewal/plan.py

  • Contract. Builds the same model, fixes the variable of every listed unit to 1 and of every other unit to 0, solves, and answers whether the solver found a plan.
  • Modeling idea. To test a rule, pin a whole plan with variable bounds and ask whether it is feasible; a pair of plans on either side of a limit shows the row is there and in the right place.
  • Taught in 12.3.1 Unit-Testing One Constraint at a Time.

Summary


  • A ranking sorts by one number and stops at the first unit that does not fit. Worst-first removed $3,255k of risk where the best list removes $11,533k.
  • A condition score is not risk, and a ranking cannot see cost. Risk is PoF times CoF, and the choice under a budget is a knapsack.
  • A better ranking comes close on one budget but proves nothing and holds no second rule. The 0-1 model gives the best list and a bound, and every later rule is a row.
  • The tests pin each mistake on a fleet small enough to check by hand, and pair an allowed and a refused list at the budget's edge.

Design Note: Keep the Baseline in the Code


rank.py is not deleted. The asset team trusts it, and a reviewer's first question about a model is "how does it compare with what we do now?". Keeping the baseline in the package, and printing both lists, answers that on every run and catches a class of bug no unit test sees: a model that is "optimal" for the wrong objective and does worse than the old habit.
