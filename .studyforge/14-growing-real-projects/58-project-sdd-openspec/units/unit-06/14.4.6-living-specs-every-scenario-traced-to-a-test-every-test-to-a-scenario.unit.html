Five changes are archived. The living specs describe the planner as it is, and GridCap's auditors, who review the planning process once a year, have read them. Their request:

Request 6. For every rule in these specs, show us the test that proves the planner keeps it. For every test, show us the rule it checks. If a rule has no test, we cannot rely on it; if a test checks no agreed rule, nobody agreed to what it enforces.

The code before this lesson is snapshot steps/05; after it, steps/06. GridCap and its auditors are fictional.

Nothing Links a Scenario to Its Test but a Habit

Since the first lesson, every scenario's test has been named after it: test_ and the scenario's name in lower case, each run of other characters an underscore, in the test file named after the capability, tests/test_capital_plan.py for capital-plan. That is a convention, and nothing checks it. The design decision of this change is how to make the link checkable:

OptionForAgainst
a marker on each test naming its scenariosurvives a test renameevery one of 32 tests must change
a table, scenario to test, kept in a fileexplicita third thing to keep in step, and it rots
the naming convention the tests already followno test changes; the name says what it checksrenaming a scenario breaks the link

The project takes the convention, and turns its weakness into a check: renaming a scenario without renaming its test is exactly what a trace should report. The trace reads the living specs only, openspec/specs/, because they are what the system is agreed to do; a scenario in a change not yet archived is not agreed yet. Test files named after no capability are outside the trace, so helpers and the course's own expected-output check do not count as tests without a scenario.

The First Trace Finds the Gap the Must-Do Change Left

Run with the trace of steps/06 on the project as it stands, steps/05:

Thirty-two scenarios have their test; one has none. It is the scenario the must-do change left open, and the archive warned about it and archived anyway. Since then the living spec has said the planner refuses such a request with a message naming the project. What the planner of steps/05 does instead:

No message, no plan, and no word about why. The reason is in the model. Project F has no year in the plan, so $T_F$ is empty and its row $\text{must}_F$ is $\sum_{t \in \emptyset} x_{F,t} = 1$, that is $0 = 1$. In Python the empty sum is the number 0, so starts == 1 is the plain value False, and CP-SAT's CpModel.add accepts a Boolean: for False it adds an empty clause, a constraint that can never hold. The model is infeasible, which is true, and useless to a planner, who needs to know which override to fix. The scenario said so in words; with no test, nobody saw the code did not.

The Change: Traceability for the Checker, and the Open Tasks Done

The proposal:

The delta adds one requirement to spec-checks, and the convention becomes part of it:

Its other three scenarios: a test with no scenario is reported; a test in the file of another capability does not count for this one; and this project's living specs and tests trace both ways. That last one makes the trace a test of the project, so from now on a scenario without a test fails the suite, and an archive warning like the must-do change's can no longer scroll past.

The change modifies no capital-plan requirement. The must-do scenario is already in the living spec; the code is catching up with it. A change does not need a delta for every file it touches, only for the behaviour it changes in the spec.

The Model

No row changes in this lesson. The full model, as steps/05 and steps/06 build it:

Sets. $P$, the projects; $Y = \{y_1, \dots, y_n\}$, the plan years; $T_i \subseteq Y$, the years project $i$ may start; $R$, the regions, with $P_r \subseteq P$; $S \subseteq R$, the regions with a share; $M \subseteq P$, the must-do projects.

Parameters. $c_i$, cost ($k); $v_i$, value ($k); $B$, the yearly budget ($k); $s_r \in \{0, \dots, 100\}$, the least share of region $r$ (%); $C \in \{0, \dots, 100\}$, the carry-over percent; $\bar r = \lfloor C B / 100 \rfloor$ ($k).

Variables. $x_{i,t} \in \{0,1\}$ for $i \in P$, $t \in T_i$; $r_y \in \{0, 1, \dots, \bar r\}$ for $y \in Y \setminus \{y_n\}$, with $r_{y_0} = r_{y_n} = 0$.

Objective.

Constraints.

What changes is the check before the model: a must-do $i$ with $T_i = \emptyset$ is refused, so the row $\text{must}_i$ is never built with an empty sum $\leftarrow$.

The Change, File by File

specs_check.py: test_name and trace. test_name is the naming convention, written once:

trace replaces the stub, and its body is the practice's to write. It works in three passes over two sets of pairs (test file, test name):

  1. What the specs want. For each living spec openspec/specs/<capability>/spec.md, the test file is test_ and the capability's name with - as _, plus .py, and each scenario of its requirements wants the pair (that file, test_name(scenario)), labelled <capability>: <scenario>.
  2. What the tests have. For each of those files that exists under tests/, Python's ast module reads the file's module-level functions whose names start with test_, without importing or running the file. Other test files are never read.
  3. The comparison. A pair in both sets is a scenario with its test; a wanted pair with no test is reported by its label; a found pair that no scenario wants is reported as tests/<file>::<test>. Both lists are sorted.

Keeping the file in the pair is what the third checker test above asks for: a set of test names alone would let test_fits in other's file count for demo's scenario.

The snapshot's specs_check.py also gains a trace command beside list, validate and archive, which prints the same counts and gaps and exits 1 on any gap. The practice does not ask for it: its tests and its report call the trace function. OpenSpec has no trace command; this one is the project's own, built on the same reading of requirements and scenarios as the validator.

What the Project Became

The planner grew by 55 lines in six changes, and its specs from nothing to 19 requirements and 37 scenarios, each with exactly one test. The largest function is still small, but request.check now holds four kinds of rule, and a seventh change should split it, behind the same tests. The style the project kept is the point of the module: every change started as a folder of words that the planners could read, every rule was a test before it was code, and every archived change left the specs true.

Practice. This lesson's project practice starts from the code of steps/05, with the specs and tests of steps/06. It is graded by those tests and by a check that main.py prints steps/06/expected/report.txt, which now ends with the trace.

The change is proposed and archived in openspec/: it adds a traceability requirement to the checker's spec, with the naming convention every test already follows. It also finishes the open tasks of the must-do change, whose scenario "A must-do that cannot start in the plan is refused" has been in the living spec with no test and no code. The specs, the tests and the expected report are given and read-only.

You start from the planner without the start cap, where specs_check.trace is a stub. Write the trace: every scenario of the living specs to the test named after it in its capability's test file, and every test of those files to its scenario, reporting both kinds of gap. Then make the planner refuse, before solving, a must-do project that cannot start in any plan year, naming it, where it now returns an infeasible plan with no word about why.

Run executes main.py, which plans a tiny portfolio: 12 projects of GridCap, a fictional utility, drawn by capplan/portfolio.py from seed 58, prints the plan, the refusal of the retired start cap, the line about the specs, and a last line with the trace; expected/report.txt is the report it should print. Submit runs every test in tests/, the earlier steps' included, and compares Run's report with the expected one.

Blueprint

Write each method below. The tests check each one by itself and the whole program end to end, so you may change any other part of the code as you see fit.

test_name in specs_check.py

  • Contract. A new function. test_ followed by the scenario's name in lower case, with each run of characters other than a-z and 0-9 replaced by one _, and no _ at either end of the name part: the scenario A must-do is refused! gives test_a_must_do_is_refused.
  • Modeling idea. The link between a scenario and its test is a naming convention the checker can check.
  • Taught in 14.4.6 Living Specs: Every Scenario Traced to a Test, Every Test to a Scenario.

trace in specs_check.py

  • Contract. Reads every scenario of root/openspec/specs/<capability>/spec.md and expects its test, named by test_name, in root/tests/test_<capability>.py with each - of the capability written as _ (capital-plan gives tests/test_capital_plan.py). Reads the module-level test functions (named test_...) of those files with ast, without importing them; other test files are ignored. Returns Trace(pairs, untested, untraced): the number of scenarios whose test was found, the sorted <capability>: <scenario> labels with no test, and the sorted tests/<file>::<test> names that match no scenario of their own file's capability.
  • Modeling idea. A scenario is matched to a test in its own capability's file only; a test of the same name elsewhere does not count.
  • Taught in 14.4.6 Living Specs: Every Scenario Traced to a Test, Every Test to a Scenario.

check in capplan/request.py

  • Contract. As before, and raises ValueError, naming the project, for a must-do whose window has no plan year.
  • Modeling idea. An empty window gives an empty sum, 0 == 1, which CP-SAT takes as a constraint that never holds; refuse it with a message first.
  • Taught in 14.4.6 Living Specs: Every Scenario Traced to a Test, Every Test to a Scenario.

main in main.py

  • Contract. As before, and a last line from specs_check.trace: 'trace: <pairs> scenarios with their tests, <n> with none, <m> tests with no scenario'.
  • Modeling idea. The project traces its specs to its tests on every run.
  • Taught in 14.4.6 Living Specs: Every Scenario Traced to a Test, Every Test to a Scenario.

Summary


  • A trace links every scenario of the living specs to its test, and every test to its scenario. Here the link is a naming convention, written into the checker's spec and checked on every run.
  • The first trace found a scenario archived without its test, and behind it a planner that answered INFEASIBLE where the spec promised a message.
  • An empty sum is the number 0, and 0 == 1 is False; CP-SAT accepts it as a constraint that never holds. The check before the model turns it into a message.
  • The trace reads living specs only, so it passes only after archive. A change is done when it is archived.
  • Living specs say what the system does; the archive says since when and why.

Design Note: Why the Checker Got a Spec of Its Own


specs_check.py is tooling, and could have stayed outside the specs. It has one because its rules are behaviour the project relies on as much as the planner's: if the keyword rule broke, specs without SHALL would pass; if the trace broke, a scenario without a test would. Writing them as requirements and scenarios put them under the same discipline: each rule has a test, the trace covers them, and a change to a rule is a delta someone reviews. OpenSpec does the same with its own repository, whose openspec/ folder specifies the CLI itself.
