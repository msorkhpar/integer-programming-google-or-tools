Each Rule Is a Function That Adds Rows With the Names It Owns

So far build wrote its two row families inline. Five more would make it a long function in which every rule edits the same lines. The design choices:

ChoiceForAgainst
keep writing rows inline in buildeverything in one placebuild grows with every rule; the rule's rows and its name scheme are far apart
one class per rule with apply and check methodseach rule can also check a plana class hierarchy for what are, today, five loops
one function per rule in rules.py, listed in RULES (chosen)a rule is read in one place; a new rule is a new function, and build stays the samethe order of RULES matters only for row order, which a reader might think matters for meaning

Each rule function receives built and adds rows through built.add(name, row). The rule owns its name prefix (must_, alt_, bundle_, after_), and that prefix is what the diagnostics of the lesson Why it failed, why it was deferred: a diagnostics layer will turn back into planner language.

Row order carries no meaning, but order is not always invisible: when several plans tie for the best value, which one HiGHS returns can depend on how the model was built. The section The Rules Cost $2,919k of Value and Break Nothing measures that on the demo export.

The Model

The model of the lesson Many years: start years, windows and cash-flow spreading with section 6's rules added. Helper sums keep the rows short: $\text{started}(i) = \sum_{t \in T_i} x_{i,t}$ is 1 if project $i$ is funded, and $\text{started\_by}(i, t) = \sum_{u \in T_i,\, u \le t} x_{i,u}$ is 1 if it has started by year $t$ (both from lesson Parent-child bundles and all-or-nothing).

Sets. $P$, $Y$, $T_i$ as before; $M \subseteq P$, the must-do projects; $\mathcal{G}$, the alternative groups, each a set of projects; $\mathcal{B}$, the bundles, each a set of projects whose first member by id is $b_1$; $C \subseteq P$, the child projects, with parent $p(c)$ and lag $L_c$ years.

Parameters. $c_{i,k}$, $v_i$, $B_y$ as before ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$, $t \in T_i$.

Objective.

Constraints.

The parent row is the cumulative form of lesson Aggregated vs. cumulative (disaggregated) forms: a child started by year $t$ needs its parent started by $t - L_c$. If the parent's window has no year that early, the right side is an empty sum, the row says $\text{started\_by}(c, t) \le 0$, and the child cannot start in $t$. Each rule comes from section 6: must-dos from lesson Must-do vs. discretionary planning groups, bundles and parents from lesson Parent-child bundles and all-or-nothing, alternatives from lesson Mutually exclusive alternatives (repair vs. replace), lags from lesson Precedence with lags.

The Change, File by File

cipt/rules.py is new. The two files now import each other: model.py imports RULES from rules.py to run them, and rules.py names Built in every rule's signature. Two imports at module level would be circular: whichever file Python loads first would ask for a name the other has not defined yet. rules.py breaks the circle by importing Built only for type checkers. With from __future__ import annotations, a signature's types are kept as text and never evaluated when the module runs, and typing.TYPE_CHECKING is False at run time, so the import inside the if never runs; a type checker or an editor still reads it. One of its five rules, from steps/03/cipt/rules.py, shows the shape every rule has:

The other rules are the practice's, and the one that carries this lesson's hardest row is parents, the row $\text{after}_{c,t}$ of the model above. For every project $c$ whose parent is set (it is None for a project with no parent), and for every start year $t$ of the child's own window, request.starts(c), it adds one row named after_<child>_<t>: the child's $\text{started\_by}(c, t)$ minus the parent's $\text{started\_by}(p(c), t - L_c)$, at most 0. The parent's record is request.project(c.parent) and the lag $L_c$ is c.parent_lag. The rows run over the child's window, not the parent's, and a row is added for every such $t$, even when the parent's side is the empty sum the paragraph under the model describes: that row is what stops the child from starting in $t$.

The bundle row is written as a difference equal to zero rather than started(j) == started(first): both sides of == would be expressions, and keeping one side a number makes every row of the model read "expression, bound". Problem statement

The planners checked the step-02 plan against their own lists and wrote back:

Three must-do projects are missing: P010, P017 and P039 are regulatory commitments, so they go in whatever they're worth. P030 and P031 are two ways to fix the same Valley line, and you funded both. Also, P023 can only start a year after P022 has started, P016 needs P015, and P011 and P012 are one Coast crew visit: both or neither. The export has all of this in its columns.

You start from the yearly planner of the lesson before. Make it keep the rules the export already holds: a must-do project is funded, at most one project of an alternative group is funded, a bundle is funded whole or not at all, and a child starts no earlier than its parent's start plus the lag. Give each rule its own function in a new file, cipt/rules.py, that adds its rows under names the planners can read, and let the model run the rules in turn. An export in which a project names a parent the export does not have is refused when it is read.

cipt/rules.py starts as the reference has it, with the five rule functions of the blueprint stubbed. Its imports are there (Built is imported inside if TYPE_CHECKING:, because model.py imports RULES from rules.py and a plain import back would be circular), and so is RULES, the tuple of rule functions build runs in order. cipt/value.py is the next lesson's stub, as the reference has it; no code of this step imports it, so leave it as it is.

The expected report is one of several tied best plans. To print that one, create the start variables project by project in export order, each project's start years in ascending order, and run the rules in the order once_or_must, alternatives, bundles, parents, budgets. The report's format is the one of the lesson before, unchanged.

Run executes main.py, which plans the demo export and prints the report; expected/report.txt is the report it should print. Submit runs every test in tests/, the earlier steps' included, and compares Run's report with the expected one.

Blueprint

Write each method below. The tests check each one by itself and the whole program end to end, so you may change any other part of the code as you see fit.

once_or_must in cipt/rules.py

  • Contract. Adds a row once_<id> (the project starts at most once) for each discretionary project, and a row must_<id> (it starts exactly once) for each must-do project.
  • Modeling idea. A must-do is the at-most-once row turned into an equality: the same sum of start variables, fixed to 1.
  • Taught in 6.5.1 Must-Do vs. Discretionary Planning Groups.

alternatives in cipt/rules.py

  • Contract. Adds a row alt_<group> per alternative group: the projects of the group start at most once between them.
  • Modeling idea. Mutually exclusive choices are one at-most-one row over their start variables.
  • Taught in 6.5.3 Mutually Exclusive Alternatives (Repair vs. Replace).

bundles in cipt/rules.py

  • Contract. Adds a row bundle_<first>_<other> for each further member of a bundle: that member is funded exactly when the bundle's first member, in id order, is.
  • Modeling idea. All-or-nothing is an equality between the funded indicators, chained to one member.
  • Taught in 6.5.2 Parent-Child Bundles and All-or-Nothing.

parents in cipt/rules.py

  • Contract. Adds a row after_<child>_<t> for each start year t of a child: the child started by t needs its parent started by t minus the lag.
  • Modeling idea. Precedence with a lag compares cumulative starts: started by t on the child, started by t - lag on the parent.
  • Taught in 6.5.4 Precedence with Lags.

budgets in cipt/rules.py

  • Contract. Adds a row budget_<y> per plan year: that year's spend, costs spread over the years of work, within that year's budget.
  • Modeling idea. The yearly budget of the lesson before is one more rule, written the way the others are.
  • Taught in 6.4.2 Cash-Flow Spreading Across Years.

build in cipt/model.py

  • Contract. Creates the start variables, keeps the Built that owns them and the named rows, runs every rule of rules.RULES on it in order, and sets the objective. Every row has the name its rule gave it.
  • Modeling idea. Each rule is a function that adds rows with the names it owns, so a new rule never changes build.
  • Taught in 14.2.3 Business Rules: Must-Dos, Bundles, Parents and Alternatives.

load_request in cipt/data.py

  • Contract. Also reads must_do, parent, parent_lag, alt_group and bundle for each project, and refuses an export in which a project names a parent the export does not have (ValueError, 'unknown parent').
  • Modeling idea. Validate the input before the solve: a rule that points at nothing is an error in the data, not a constraint.
  • Taught in 9.1.2 Validating Inputs Before the Solve.

Summary


  • The step-02 plan breaks four rules the export already holds: three must-dos missing, one pair of alternatives both funded.
  • Each rule is a function that adds rows with the names it owns. build runs RULES and no longer changes when a rule is added.
  • The rules cost $2,919k of value and break nothing on GridCap small.
  • A rule's test uses data where the old plan breaks that rule, so it fails without the rule.

Design Note: Rules as a List of Functions


RULES is a plain tuple. A registry with decorators, or plugins found by name, would let a rule be added without editing rules.py. That flexibility has no user here: every rule is reviewed with the planners and lives in this one file, where a reader can see all of them. The tuple is enough until someone needs to switch rules on and off per scenario, and the lesson Scenarios, overrides and snapshots shows that even then a scenario changes data, not the list of rules.
