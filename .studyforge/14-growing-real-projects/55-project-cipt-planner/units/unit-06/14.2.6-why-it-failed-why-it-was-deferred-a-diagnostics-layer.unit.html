Two messages arrived the same week. From finance, after trying a budget cut:

We cut 2030 and 2031 to $4M each and the planner just said "infeasible". Infeasible why? Which of our numbers is the problem?

And from a regional manager:

P030 is our biggest Valley project and it's not funded. Why not? What would it take?

"Infeasible" Names No Rule, and "Not Funded" Has No Reason

steps/05 returns a Plan with status="infeasible" and nothing else. The solver knows only that no assignment satisfies every row; it does not say which rows clash (lesson Infeasible, unbounded, or the solver can't tell). For a deferred project the plan says nothing either: the project's variables are 0, and the reason lies in the rows, the objective and every other project at once.

What the code does have, since the lesson Business rules: must-dos, bundles, parents and alternatives, is a name for every row, and names the planners can read: must_P017, budget_2030. A diagnostics layer can work in those names.

Relax One Named Row at a Time to Find the Rows That Clash

For "why infeasible", three tools from section 9 were candidates:

ToolForAgainst
MathOpt's compute_infeasible_subsystemone callin MathOpt only Gurobi offers it; HiGHS, the planner's solver, refuses it (lessons Callbacks and compute_infeasible_subsystem and IIS with MathOpt, gurobipy and Pyomo)
elastic rows with penalized slack (lesson Elastic constraints and feasibility relaxation)one solve; says how much to changeneeds a slack variable per row and a choice of penalties; answers "how much", not "which"
a deletion filter over named rows (lesson IIS with MathOpt, gurobipy and Pyomo) (chosen)works with any solver; returns an irreducible set: every row in it is needed for the clashone solve per row

A deletion filter goes through the rows in name order. It relaxes a row (sets its bounds to $-\infty$ and $+\infty$) and solves. If the model is still infeasible, that row was not needed for the clash, and it stays relaxed. If the model becomes feasible, the row is part of the clash, and its bounds are restored. At the end the unrelaxed rows form an irreducible infeasible set: together they have no plan, and without any one of them a plan exists. On GridCap small that is up to 50 solves of a small model.

For "why deferred", the answer is lesson Why selected, why deferred: forcing in and out: force the project in and solve again. If a plan exists, its NPV loss is the project's price, and the projects it pushes out are the trade. If no plan exists, the deletion filter runs on the forced model, with the forcing row kept, and names the rules that block the project.

The Model

The planning model is the model of the lesson Two goals: risk against NPV, unchanged. Diagnostics solve variants of it.

Sets, parameters, variables, rows. As in the lesson Two goals: risk against NPV: rows once, must, alt, bundle, after, budget and, when set, risk_floor. Write $R$ for the set of row names.

The relaxed model of the deletion filter. For a set $D \subseteq R$ of relaxed rows, the model keeps every row in $R \setminus D$ and drops the rows in $D$. The filter keeps a row $\rho$ in $D$ exactly when the model without $D \cup \{\rho\}$ is still infeasible:

The forced model of "why deferred". The planning model with one row more, for the project $j$ asked about, and the objective $\max \text{NPV}(x)$:

The Change, File by File

cipt/diagnose.py. Before: the stub of the lesson Two goals: risk against NPV, why_infeasible returning None. After, the filter, deletion_filter(built, keep=()), whose code the page leaves to the practice. It is the loop of the model block above, run on the rows of built.rows:

  • It goes through the row names in sorted order. A row named in keep is never relaxed; the forcing row of "why deferred" below is passed that way.
  • To relax a row, it saves the row's two bounds, then sets them to $-\infty$ and $+\infty$ (-math.inf and math.inf). If the model is now feasible, the row is needed for the clash, and its saved bounds go back. If the model is still infeasible, the row stays relaxed: it joins $D$.
  • It returns, sorted, the names of the rows that are not relaxed at the end: the conflict $R \setminus D$, with any rows of keep among them.

Relaxing changes the row's bounds in place; MathOpt's LinearConstraint has setters for lower_bound and upper_bound, so the model is never rebuilt. feasible is one solve and one comparison, from steps/06/cipt/diagnose.py:

Only the termination INFEASIBLE counts as "no plan". MathOpt also has INFEASIBLE_OR_UNBOUNDED, for a solver that proved one of the two without saying which, and feasible counts it as feasible. Every variable of the planner is binary, so its models can never be unbounded, and every infeasible request on this page and in the tests ended INFEASIBLE. The rows dictionary that the lesson The first request: fund projects within one budget started keeping "for later" is what lets the filter fit in eight lines.

describe turns a row name back into the planners' words, one branch per name prefix. From steps/06/cipt/diagnose.py:

name.partition("_") splits at the first underscore, so risk_floor is the kind risk. An alternative group is listed by its members, in id order, joined by a comma and a space (at most one of P030, P031); the risk floor is stated in $k with one decimal and thousands commas (remove at least $<floor>k of risk); a name with a prefix it does not know comes back as it is.

why_deferred adds the forcing row and either prices the project or explains it:

The forcing row is kept, because the question is "which rules stop this project", not "is the model feasible without forcing it", which it is.

cipt/__main__.py. The command line prints the conflict when the plan is infeasible and gains --why PROJECT, which prints the price or the blocking rules of a project the plan left out. From steps/06/cipt/__main__.py:

For a project the plan already funds, --why prints nothing after the report: there is no deferral to explain. For an infeasible request, the conflict is printed, --why is not answered, and the command returns 1.

Each Diagnostic Test Checks the Exact Set of Rows

From steps/06/tests/test_diagnose.py:

A test that only asked "does the conflict mention the budget" would pass on a filter that relaxed nothing and returned all rows. Checking the exact set checks that the set is irreducible.

The last "before" is the step-05 command line refusing an option it does not have yet: it exits with status 2 and prints nothing, while --why A on a funded project must print exactly the report the command prints without it.

Diagnostics Were the Largest Step So Far, and Changed No Model Code

Of the 126 new lines, 58 are the stubs of the next lesson; the diagnostics themselves are 56 lines in diagnose.py and 12 in the command line. model.py, rules.py and solve.py did not change: the layer is built entirely on the row names and the Built handles earlier steps put in place. describe is a chain of if branches, one per row prefix; each new rule must add one, and the next lesson does.

Practice. This lesson's project practice starts from steps/05, the whole package. It is graded by the tests in the practice's tests/ folder and by a check that main.py, which plans the demo export, prints what the practice's expected/report.txt holds. This step's main.py also asks why P003 is not in the demo plan, as --why P003 does: after the report it prints P003 cannot be funded. followed by the conflict message, whose first line is No plan meets these <n> rules together; drop or change any one of them: and whose next lines are <row>: <description>, one per row in name order; the frontier section of the lesson before follows.

You start from the planner of the lesson before, whose rows all carry names. When a request has no plan, name exactly the rules that clash, in the planners' words, so that dropping or changing any one of them gives a plan; a rule that plays no part in the clash is not named. When a project is left out, say what funding it would cost (the NPV given up and the projects dropped) or, when no plan can fund it, which rules block it. The command line explains an infeasible request, and --why PROJECT explains a project the plan leaves out.

--why for a project the plan funds prints nothing after the report; for an infeasible request the command line prints the conflict, does not answer --why, and returns 1.

Blueprint

Write each method below. The tests check each one by itself and the whole program end to end, so you may change any other part of the code as you see fit.

deletion_filter in cipt/diagnose.py

  • Contract. Returns, sorted, the names of an irreducible set of rows that cannot all hold: relax each row in name order, keep it relaxed while the model stays infeasible, restore it when relaxing it makes the model feasible. Rows named in keep are never relaxed.
  • Modeling idea. The deletion filter: the rows you cannot relax without the clash disappearing form a conflict, and dropping any one of them gives a plan.
  • Taught in 9.1.3 IIS With MathOpt, gurobipy and Pyomo.

feasible in cipt/diagnose.py

  • Contract. True unless HiGHS reports the model infeasible: only the termination INFEASIBLE counts as no plan, and INFEASIBLE_OR_UNBOUNDED counts as feasible (every variable is binary, so the model is never unbounded).
  • Modeling idea. The filter only asks one question of each solve: does a plan exist?
  • Taught in 9.1.1 Infeasible, Unbounded, or the Solver Can't Tell.

describe in cipt/diagnose.py

  • Contract. Returns one row in the planners' words, read from its name: spend in <y> within $<b>k, <id> is a must-do, <id> is forced in, at most one of <ids> (the group's members in id order, joined by a comma and a space), <a> and <b> are funded together or not at all, <child> started by <t> needs <parent> started by <t - lag>, remove at least $<floor>k of risk (one decimal, thousands commas) for the risk floor; the name itself for any other row. The kind is the part of the name before its first underscore.
  • Modeling idea. A conflict is only useful in the names people can change.
  • Taught in 9.1.6 Turning an IIS Into a Planner Message.

explain in cipt/diagnose.py

  • Contract. Returns a Conflict with the rows and a message: No plan meets these <n> rules together; drop or change any one of them: then one line <row>: <description> per row.
  • Modeling idea. Turn the IIS into a message that says what to change.
  • Taught in 9.1.6 Turning an IIS Into a Planner Message.

why_infeasible in cipt/diagnose.py

  • Contract. None when the request has a plan; otherwise the Conflict of the rows that clash.
  • Modeling idea. Run the filter only when the model is infeasible.
  • Taught in 9.1.3 IIS With MathOpt, gurobipy and Pyomo.

why_deferred in cipt/diagnose.py

  • Contract. Forces the project in with a row force_<id>. When that is feasible, returns the NPV the plan gives up and the funded projects it drops; when it is not, the Conflict of the rows that block it, the force row kept.
  • Modeling idea. Forcing a decision in and re-solving prices it; when no plan exists, the conflict says why.
  • Taught in 9.3.2 Why Selected, Why Deferred: Forcing In and Out.

main in cipt/__main__.py

  • Contract. Prints the report; for an infeasible request also prints the conflict message and returns 1. With --why PROJECT for a project the plan leaves out, prints <id> cannot be funded. <message> or Funding <id> costs $<cost>k of NPV and drops <ids or nothing>. (cost in whole $k, ids joined by a comma and a space); for a project the plan funds, nothing more.
  • Modeling idea. The command line is where the planners read the diagnostics.
  • Taught in 14.2.6 Why It Failed, Why It Was Deferred: A Diagnostics Layer.

Summary


  • "Infeasible" names no rule, and "not funded" has no reason, until the code works in row names.
  • Relax one named row at a time to find the rows that clash. The deletion filter returns an irreducible set, and describe puts each row in the planners' words.
  • Force a deferred project in to price it, or, when that is infeasible, to find the rows that block it.
  • Each diagnostic test checks the exact set of rows, which is what irreducible means.

Challenges


  1. The filter goes through rows in name order. Find an infeasible request with two different irreducible sets and show that a different order returns the other one.
  2. why_deferred reports the projects that the forced plan drops but not those it starts in a different year. Add the shifted ones, using the plans' starts.
  3. The filter solves once per row. Sort the rows so the once rows come last and count the solves that change nothing.


Design Note: Diagnose in the Names People Can Change


The filter could run over variables and bounds too, and would then sometimes name a variable bound in its conflict. No planner can act on "x_P017_2030 ≤ 1". Every row the filter can name is something a person set: a budget, a must-do flag, a lag. That is also why the next lesson writes scenario overrides as rows instead of bounds.
