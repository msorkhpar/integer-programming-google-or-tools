  17. The first request

This module grows one program, the CIPT planner (Capital Investment Planning Tool), from a first small request into the system a capital-planning team runs every cycle. Each lesson takes one new request from the planners and changes the code to meet it. The project lives in complete snapshots: steps/00 is the starting skeleton, and steps/NN is the project after lesson 14.2.NN. Every snapshot runs on its own and passes its own tests. The data is GridCap, the course's fictional utility; no number in it describes a real company.

The capstone (lessons Data: load, validate and snapshot the portfolio to Service: FastAPI job API, moto-tested S3 store, Pareto frontier endpoint) built a similar system milestone by milestone, from finished parts. Here the code starts small and grows, and the subject is how a design changes when requirements arrive one at a time.

The first request, as the planning lead wrote it:

We have $38.39M of capital for the next five years and 40 candidate projects on GridCap small. Tell us which to fund to get the most value. Use the NPV finance quoted for each project. We'll worry about years later.

The Skeleton Reads the Export and Prints a Plan, but Decides Nothing

One Envelope and Yes-or-No Choices Make a Knapsack

The request has one budget and one decision per project: fund it or not. That is the 0-1 knapsack of lesson 0-1 and multi-dimensional knapsack. Nothing about years enters yet; the planners said so.

The Model

Sets. $P$, the candidate projects.

Parameters. $c_i$, the capex of project $i$ ($k); $v_i$, its value, the NPV of a start in its earliest year ($k); $B$, the envelope ($k).

Variables. $x_i \in \{0, 1\}$ for every $i \in P$: 1 if project $i$ is funded.

Objective.

Constraints.

The row's label is the name the code gives it, budget. Every later lesson keeps that habit: a row's name in the code is its label in the formulation.

The Model Lives in One File and the Solver in Another

The design decision of this step is where the formulation and the solver go. Three choices were on the table:

ChoiceForAgainst
model and solve in one functionshortest code todayevery later rule and every solver setting edits the same function
model.py builds, solve.py solves and reads back (chosen)a rule changes one file, a solver setting another; tests call solve and check behaviourtwo files for twelve lines today
CP-SAT instead of MathOpt and HiGHSthe knapsack has integer dataCP-SAT works in integers, so the fractional risk values of the lesson Value: NPV by start year and risk reduction would have to be scaled (lesson Objectives, integer scaling and solution callbacks)

The planner uses MathOpt with HiGHS (lesson Model, variables, constraints, objective) from the start, so the solver does not change when the objective does.

The Change, File by File

cipt/model.py. Before: build returned an empty model. After, it is the model block above turned into MathOpt calls, and the page leaves its code to the practice. build(request) makes a mathopt.Model named after the request and returns Built(request, model, x, rows), the record steps/00 already defines:

  • x maps each project id to its binary variable $x_i$, named x_<id>, so reading the answer back needs no search.
  • rows maps the row's label to the row. It holds one row today, (budget): the capex $c_i$ of each project times its $x_i$, summed, at most the envelope capital_budget, under the name budget. The diagnostics of the lesson Why it failed, why it was deferred: a diagnostics layer find rows by these names.
  • The objective is the model block's: maximize the sum of each project's value $v_i$ times its $x_i$.
  • mathopt.fast_sum instead of sum: its docstring in the OR-Tools source says a row built from an empty list with fast_sum is safe, while sum of an empty list is the number 0 and the row becomes a Python bool that MathOpt refuses. An export with no projects then still builds.

cipt/solve.py. Before: three stubs, solve above, run_highs returning None and read_plan returning "not solved". After, in steps/01/cipt/solve.py, three parts. First the imports, the solver settings and the quiet solve:

  • highs_pb2 is the module of HiGHS's own options as MathOpt passes them on; HighsOptionsProto is its record, with one dictionary per option type (int_options, bool_options, ...). solve.py now imports Built and build from model.py.
  • PARAMS fixes HiGHS at one thread through its own options, because MathOpt's common threads parameter is refused by HiGHS (lesson Common vs. solver-specific parameters, and what each solver rejects). One thread also makes runs repeat, which the lesson Trust at scale: determinism harness, golden tests, warm starts relies on.
  • run_highs points the process's standard output at /dev/null during the solve, because the HiGHS bundled with OR-Tools can print a stray debug line on some MIP solves (lesson Model, variables, constraints, objective). A report that planners read must not carry it. Line by line:
    • sys.stdout.flush() writes out what Python has buffered so far, so no line of the report is lost into /dev/null.
    • os.dup(1) keeps a copy of the real standard output, file descriptor 1, and os.dup2(sink, 1) points descriptor 1 at /dev/null. Redirecting the descriptor, not sys.stdout, is what silences HiGHS: it is C++ code and writes to descriptor 1 without passing through Python.
    • ctypes.CDLL(None).fflush(None) flushes the C library's own output buffers. CDLL(None) opens the running process itself, whose symbols include the C library's fflush, and fflush(NULL) flushes every C stream. It runs while descriptor 1 still points at /dev/null, so text HiGHS left in a C buffer goes there, not into the report once the descriptor is restored.
    • finally restores descriptor 1 and closes the two spare descriptors, even when the solve raises.
  • status is MathOpt's termination reason in lower case: "optimal", "infeasible", and so on.
  • values[var] > 0.5 reads a binary that the solver returns as a float such as 0.9999999.
  • A funded project "starts in its earliest year". The model has no years; the plan records the year the planners assumed, so Plan keeps one shape from this step to the last.

cipt/plan.py, report.py, __main__.py. Unchanged. cipt/data.py gains one stub for the next lesson, Request.starts(project), which returns the earliest year alone; nothing calls it yet. The report that printed "not solved" now prints a plan:

Problem statement

The planning lead's first request:

We have $38.39M of capital for the next five years and 40 candidate projects on GridCap small. Tell us which to fund to get the most value. Use the NPV finance quoted for each project. We'll worry about years later.

The project you start from is the skeleton: it reads the export and prints a report, but its model is empty and solve funds nothing. Make the planner decide. Each project is a yes-or-no choice, the funded projects together may cost no more than the capital budget, and the plan has the most total value. Solve the model with HiGHS through MathOpt, keep anything HiGHS prints out of the report, and read the answer back as a Plan in which each funded project starts in its earliest year.

The command line, python -m cipt EXPORT.json, plans the export file it is given.

cipt/solve.py already imports MathOpt and holds stubs for run_highs and read_plan; write their bodies and make solve use them. cipt/report.py needs no change. It prints the report in this format, every amount in whole $k with thousands commas:

  • <request name>: <status>;
  • funded <n> of <all> projects, capex $<capex>k of $<capital budget>k, value $<value>k, where capex and value are the totals of the funded projects;
  • one line per funded project, in id order: two spaces, the id, two spaces, start <year>, two spaces, capex and a space and the capex right-aligned in 6 characters, two spaces, value and a space and the value right-aligned in 6 characters, two spaces, the project's name.

Run executes main.py, which plans the demo export in data/demo.json (GridCap tiny, a fictional utility) and prints the report; expected/report.txt is the report it should print. Submit runs every test in tests/, the skeleton's own included, and compares Run's report with the expected one.

Blueprint

Write each method below. The tests check each one by itself and the whole program end to end, so you may change any other part of the code as you see fit.

build in cipt/model.py

  • Contract. Takes a Request. Returns a Built holding a MathOpt model with one binary variable per project (named x_<id>), one row named budget that keeps the summed capex of the funded projects within capital_budget, and the summed value of the funded projects as the objective to maximize.
  • Modeling idea. A yes-or-no choice per project under one budget is a 0-1 knapsack: the best fill is a combination, which no sort by value per dollar finds in general.
  • Taught in 6.3.1 0-1 and Multi-Dimensional Knapsack.

run_highs in cipt/solve.py

  • Contract. Solves the model with HiGHS through MathOpt, on one thread, and returns the SolveResult. Nothing HiGHS prints may reach the program's standard output.
  • Modeling idea. The solver is a call with parameters; its log is not the planner's report.
  • Taught in 4.2.1 Model, Variables, Constraints, Objective.

read_plan in cipt/solve.py

  • Contract. Turns a SolveResult into a Plan: the status in lower case, each project whose variable is 1 mapped to its earliest start year, and the objective value. With no feasible solution, a Plan with the status alone.
  • Modeling idea. Read the termination first, then the variable values; a binary is 1 when its value is above 0.5.
  • Taught in 4.2.2 Reading SolveResult: Termination, Primal and Dual Solutions, Statistics.

solve in cipt/solve.py

  • Contract. Builds the model for a Request, solves it and returns the Plan.
  • Modeling idea. Keep building, solving and reading back in separate functions, so each can be tested and changed alone.
  • Taught in 14.2.1 The First Request: Fund Projects Within One Budget.

Summary


  • The skeleton reads the export and prints a plan, but decides nothing. The export carries every column from the start; each version reads the ones it uses.
  • One envelope and yes-or-no choices make a knapsack. One binary per project, one row.
  • A sort by value per dollar is not the best fill. On GridCap small it came up $208k short at a $15M envelope, and matched the model at $38.39M.
  • The model lives in one file and the solver in another. build names every row; solve runs HiGHS quietly on one thread and reads a Plan back.
  • Each test checks what the planners asked, on data small enough to solve by hand, and fails on the code before the step.

Challenges


  1. Find an envelope between $10M and $15M where greedy is short by more than $208k. What makes those envelopes bad for greedy?
  2. The export has a project with an NPV of zero at its earliest start. Does the model fund it when the money is there? Should it?
  3. Write a test that fails if read_plan used values[var] == 1.0 instead of > 0.5. Can you, with HiGHS on these models?


Design Note: Read Only the Columns You Use


The loader could have refused an export with columns it does not know, or mapped every column into the records at once. It does neither. Reading only what the code uses keeps the first version small, and the planners never have to make a special export for it. The cost is that a column the planner should use but ignores goes unnoticed: in this version the must-do flag is in the export and nothing reads it. The tests of the lesson Business rules: must-dos, bundles, parents and alternatives are what catch that, not the loader.
