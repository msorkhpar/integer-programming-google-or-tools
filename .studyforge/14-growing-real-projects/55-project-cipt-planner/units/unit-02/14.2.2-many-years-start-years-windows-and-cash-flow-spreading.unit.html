Finance read the first plan and sent it back:

Your plan spends $13.14M in 2027. We have $8.89M that year. The $38.39M was five yearly budgets added up, and they are not interchangeable: money not spent in a year does not roll over. Plan by year. A project may start in any year of its window, and its cost lands in the years it is worked on, not all at the start. And no plan may run past 2031.

The One-Envelope Plan Overspends the First Year

steps/01 has one number for money and no years. It funds a project "in its earliest year", which was the planners' assumption, not a decision. years.py takes the step-01 plan of GridCap small (the fictional utility's 40 projects) and computes what it spends in each calendar year, from the cost profiles the export has always carried:

The total fits; 2027 does not. The code cannot see it, for two reasons that both live in the data structures. Request has capital_budget, one number, so no year can have its own limit. Project has capex, one number, so the code cannot know that P022's $2,550k is spent as 360, 720 and 1,470 over three years. The model then has no variable that says when.

A Start-Year Variable per Project and Year Carries the When

Three designs were considered:

ChoiceForAgainst
keep $x_i$, add a second integer variable for the start yearfew variablesthe year a cost lands in becomes a product of two variables, which is not linear
$x_{i,t}$, one binary per project and allowed start year (chosen)each year's spend is linear in $x$ (lesson Start-time variables x(i,t) and timing windows); windows are just "no variable"more variables: 80 for GridCap small instead of 40
charge the whole cost to the start yearthe old budget row barely changeslesson Cash-flow spreading across years showed it overspends later years on this same portfolio

With $x_{i,t}$, a project's spend in year $y$ is $\sum_{t \le y} c_{i,y-t}\, x_{i,t}$: the start variable carries the slice of the profile that lands in $y$ (lesson Cash-flow spreading across years). A window is the set of $t$ that get a variable at all, cut so the work ends inside the plan.

The Model

The model of the lesson The first request: fund projects within one budget, with $x_i$ replaced by start-year variables and the envelope by yearly budgets. Every part of it changed, so it is given whole.

Sets. $P$, the projects; $Y$, the plan's years (2027 to 2031 for GridCap small); $T_i \subseteq Y$, the start years of project $i$: its window from the export, cut so that $t + d_i - 1 \le \max Y$, where $d_i$ is its number of years of work.

Parameters. $c_{i,k}$, what project $i$ spends in its $k$-th year of work, $k = 0, \dots, d_i - 1$ ($k); $v_i$, its value, still the NPV of a start in its earliest year ($k); $B_y$, the budget of year $y$ ($k).

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$ and $t \in T_i$: project $i$ starts in year $t$.

Constraints.

The code names the rows once_P001 and budget_2027. Note what the objective does not say: $v_i$ is the same for every start year, so the model has no reason to prefer an early start. That gap is left on purpose for the lesson Value: NPV by start year and risk reduction, where finance's NPV by start year fills it.

Every Year Now Fits, and Some Projects Start Late for No Reason

On GridCap small the step-02 model has twice the variables, and its plan fits every year:

The "of $42,230k" is the five yearly budgets of the export added up; the step-01 envelope was the export's separate capital_budget figure, $38,390k, so the yearly budgets hold $3,840k more in all. That is why the plan funds one more project and claims $1,643k more value even though each year is now a hard limit: money a year leaves unused is lost, as 2028's $320k is here.

Seven projects start after their earliest year. Some must, to fit a budget. But the objective values a late start the same as an early one, so the solver is free to push a start late for no reason at all. The value $29,027k is therefore not what this plan is worth: finance's NPV for a late start is lower. The lesson Value: NPV by start year and risk reduction fixes the objective.

Years Made the Data Richer and the Model Twice as Long

data.py grew almost as much as model.py: the years entered as data first (cost_profile, budget, duration, spend, starts), and the model only reads them. That is the style the planner keeps from here on: data records know the domain's arithmetic (what a start spends, which starts exist), and model.py only turns it into variables and rows.

Problem statement

Finance read the first plan and sent it back:

Your plan spends $13.14M in 2027. We have $8.89M that year. The $38.39M was five yearly budgets added up, and they are not interchangeable: money not spent in a year does not roll over. Plan by year. A project may start in any year of its window, and its cost lands in the years it is worked on, not all at the start. And no plan may run past 2031.

You start from the one-envelope planner of the lesson before. Change it to plan by year. Read each project's cost profile and latest start and each year's budget from the export, and let the model choose the year each funded project starts, inside its window. A project's cost is spent over its years of work, and each year's spend stays within that year's budget. No project may be funded with work that runs past the plan's last year. The plan says the year each funded project starts, and the report shows each year's spend against its budget.

Request.starts is a stub in cipt/data.py that returns the earliest year alone; Project needs the arithmetic of its profile too: how many years its work lasts, and what it spends in each calendar year for a given start. The report keeps its status line and its project lines and changes in two ways, every amount in whole $k with thousands commas:

  • the funded line's budget is the total of all yearly budgets: funded <n> of <all> projects, capex $<capex>k of $<sum of yearly budgets>k, value $<value>k, where value is still the funded projects' earliest-start value;
  • after it, before the project lines, one line per plan year in year order: <year> spend $<spend>k of $<budget>k (two spaces before the year and two after it), with 0 for a year nothing spends in.

Run executes main.py, which plans the demo export and prints the report; expected/report.txt is the report it should print. Submit runs every test in tests/, the earlier steps' included, and compares Run's report with the expected one.

Blueprint

Write each method below. The tests check each one by itself and the whole program end to end, so you may change any other part of the code as you see fit.

build in cipt/model.py

  • Contract. Takes a Request. Returns a Built with one binary x[(id, t)] per project and allowed start year t, a row once_<id> per project (it starts at most once), a row budget_<y> per plan year (that year's spread spend within that year's budget), and the summed value of the starts as the objective to maximize.
  • Modeling idea. A start-year variable per project and year carries the when, and the window is the set of variables that exist: a start outside it has no variable at all.
  • Taught in 6.4.1 Start-Time Variables x[i,t] and Timing Windows.

starts in cipt/data.py

  • Contract. Returns the start years a project may use: from the later of its earliest start and the plan's first year, to the earlier of its latest start and the last year that lets all its work end inside the plan. An empty range when no start fits.
  • Modeling idea. Cutting the window in the data keeps the model free of rows that only forbid impossible starts.
  • Taught in 6.4.1 Start-Time Variables x[i,t] and Timing Windows.

spend_by_year in cipt/model.py

  • Contract. Returns one linear expression per plan year, with an entry for every plan year (an empty sum when no start can spend in it): for every project and allowed start, each year's amount of its cost profile times that start's variable, summed into the calendar year it is spent in.
  • Modeling idea. A start in year t spends profile[k] in year t + k, so a yearly budget row sums over starts, not over projects.
  • Taught in 6.4.2 Cash-Flow Spreading Across Years.

read_plan in cipt/solve.py

  • Contract. Turns a SolveResult into a Plan whose starts map each funded project to the year its variable is 1.
  • Modeling idea. The schedule is read off the variables that are 1; the key of each variable says the year.
  • Taught in 6.4.1 Start-Time Variables x[i,t] and Timing Windows.

spend_by_year in cipt/report.py

  • Contract. Returns what a Plan spends in each plan year, in whole $k, from the funded projects' starts and cost profiles, with 0 for a year nothing spends in.
  • Modeling idea. Compute the report's numbers from the plan and the data, not from the model, so the report checks the model instead of repeating it.
  • Taught in 14.2.2 Many Years: Start Years, Windows and Cash-Flow Spreading.

render in cipt/report.py

  • Contract. Returns the report: the status line, the funded line with the total of all yearly budgets, one line per plan year reading <year> spend $<spend>k of $<budget>k, then one line per funded project.
  • Modeling idea. A yearly budget is only trusted when the report shows each year against its own limit.
  • Taught in 14.2.2 Many Years: Start Years, Windows and Cash-Flow Spreading.

load_request in cipt/data.py

  • Contract. Builds a Request from the export's dictionary: each project's cost profile, NPV for its earliest start, earliest and latest start; the plan's years; and the budget of each year, keyed by an int year. Refuses duplicate project ids.
  • Modeling idea. Read the columns the model needs now, and only those.
  • Taught in 14.2.2 Many Years: Start Years, Windows and Cash-Flow Spreading.

Summary


  • The one-envelope plan overspends the first year, by $4,250k on GridCap small, because neither the data nor the model had years.
  • A start-year variable per project and year carries the when. The window is the set of variables that exist, cut so the work ends inside the plan.
  • Spend is built once per year as an expression and bounded by that year's budget.
  • Every year now fits, and some projects start late for no reason: the value does not depend on the start year yet.

Design Note: Two Definitions of Spend, Kept Apart on Purpose


Lesson Cash-flow spreading across years argued for one definition of spend shared by every rule. The planner has two: the model's expressions and the report's integer sum. They serve different readers. Every rule inside the model uses the one expression; the report and the tests use an independent sum, so a model that miscounts spend cannot also approve its own plan. One definition inside the model, one independent check outside it.
