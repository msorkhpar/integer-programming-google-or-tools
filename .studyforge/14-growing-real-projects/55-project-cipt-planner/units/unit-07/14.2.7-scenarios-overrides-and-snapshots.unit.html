Planning season starts, and the requests multiply:

Finance wants to see the plan with $2.76M held back in 2029. P028 is waiting for a permit, so show us the plan without it. The board wants the Valley rebuild P030 in. We need all of these side by side, against the same export, and in six months we need to know exactly what each run was planned from and what it said.

Edited Copies of the Export Lose Track of What Was Planned

With steps/06, each of these requests means editing a copy of the export: change a budget, set P028's window to nothing, mark P030 as a must-do. Three problems follow. The edits are invisible: a copy with P030 marked must-do looks like an export in which P030 always was one. Nothing ties a plan to the file it came from, so "what was this run planned from" has no answer once the copy is edited again. And an edit like "mark P030 must-do" changes what the diagnostics of the lesson Why it failed, why it was deferred: a diagnostics layer say: a clash would name must_P030, a regulatory rule, when the real cause is a board decision.

A Scenario Is Data Beside the Export, and an Override Is a Named Row

The design has three parts, each from section 12:

  • A scenario is a small record: a name, budget changes, overrides and a note saying why (section 12, Scenarios as data: create, copy, optimize). It never edits the export; apply(request, scenario) makes a new Request.
  • An override is a planner's decision about one project: force it in (force_in), leave it out (force_out), or start it in a given year (fix_start).
  • A snapshot is the export exactly as received, stored under the sha256 of its canonical JSON in a SQLite file, with every scenario and every run (section 12, Storing scenarios and results in SQLite). A run records the snapshot's hash, so it can always be traced to the bytes it planned from.

Lesson Manual overrides as fixed bounds and section 12's Manual overrides as bounds, with an audit trail wrote overrides as variable bounds: cheap, and presolve removes them. The planner writes them as rows instead. The choice:

Override asForAgainst
bounds on $x_{i,t}$ (lesson Manual overrides as fixed bounds)no extra rows; presolve removes fixed variablesthe deletion filter of the lesson Why it failed, why it was deferred: a diagnostics layer relaxes only rows, so a clashing override would never be named
a named row per override (chosen)the diagnostics name it, as "the scenario funds P030"one row per override, a handful in practice

The decision follows from the previous lesson: the diagnostics speak in row names, so anything a person can change should be a row with a name.

The Model

The model of the lesson Two goals: risk against NPV, with the scenario's budgets and three override rows.

Sets. As in the lesson Two goals: risk against NPV, plus the scenario's override sets: $O^{\text{in}} \subseteq P$, $O^{\text{out}} \subseteq P$, and $F$, pairs $(i, s)$ of a project and the year it must start.

Parameters. As in the lesson Two goals: risk against NPV, with $B_y$ now the scenario's budget for $y$ where it sets one, and the export's otherwise.

Variables. $x_{i,t} \in \{0, 1\}$ for every $i \in P$, $t \in T_i$.

Objective.

Constraints.

$\text{started\_by}(i, s) - \text{started\_by}(i, s - 1)$ is $x_{i,s}$ when $s \in T_i$, so fix says "starts in exactly $s$". Written this way, a fixed year outside the window gives the row $0 = 1$, and the diagnostics name it instead of the code raising a KeyError.

The Change, File by File

cipt/scenario.py. Before: the stub of the lesson Why it failed, why it was deferred: a diagnostics layer, apply returning the request unchanged. After, from steps/07/cipt/scenario.py:

replace makes a new frozen Request; the one loaded from the snapshot is never changed, so one loaded export can serve every scenario. A scenario is stored as JSON, so Scenario turns itself into a plain dictionary and back. JSON keys are text, so the budget's years become strings on the way out and integers on the way in. From steps/07/cipt/scenario.py:

diff(base, other) in the same file lists the projects selected, deferred and shifted between two plans (lesson Scenario diffs: selected, deferred, shifted).

cipt/rules.py. One rule, overrides(built), the last of RULES, and the page leaves its code to the practice. It writes the three new row families of the model above from the request's override fields, each row through built.add and the helpers started and started_by of the lesson Business rules: must-dos, bundles, parents and alternatives:

  • $\text{in}_i$ for each project id in request.force_in, named in_<id>;
  • $\text{out}_i$ for each project id in request.force_out, named out_<id>;
  • $\text{fix}_{i,s}$ for each entry of request.fix_start, a dict from project id to the year $s$, named fix_<id>_<year>, written as the difference of two started_by sums, as the model block does, never as a lookup of x[id, s].

The fixed starts are added in project order, so their rows come out in the same order on every run, whatever order the scenario listed them in.

cipt/data.py. Request gains force_in, force_out and fix_start, all empty by default. They are not read from the export: only apply sets them.

cipt/diagnose.py. describe gains three branches, in, out and fix, as the lesson Why it failed, why it was deferred: a diagnostics layer predicted every new rule would need.

cipt/store.py. Before: a stub with the schema and empty methods. After, the snapshot is stored under its hash and checked against it when read. From steps/07/cipt/store.py:

canonical is JSON with sorted keys (sort_keys=True) and no spaces (separators=(",", ":") instead of the default ", " and ": "), so equal exports give equal bytes and equal hashes (lesson Versioned input snapshots, pinned solvers and run manifests). INSERT OR IGNORE makes saving the same export twice a no-op: the hash is the key. with self.db: commits on success and rolls back on an error.

The rest of the store saves a scenario beside its snapshot, loads it back, plans it and reads the runs. From steps/07/cipt/store.py:

save_scenario stores the scenario's canonical JSON under its name; INSERT OR REPLACE makes a second save under the same name replace the first. scenario(name) returns the stored scenario and its snapshot's hash. run(name) loads both, plans the scenario's request from the snapshot's bytes, and stores the run with the snapshot's hash and the plan's starts as canonical JSON. runs(name) returns every stored run of a scenario as a list of Plans, oldest first (ORDER BY id), each with its status, starts, NPV and risk, and the NPV as its objective.

cipt/solve.py and cipt/trust.py gain the stubs for the lesson Trust at scale: determinism harness, golden tests, warm starts. trust.py is new; no code of this step imports it, and in this lesson's practice it already holds these stubs.

Storage Added Two Files and Kept the Model Untouched

model.py did not change again. Everything a scenario changes reaches the model through the Request and one rule. describe is now the most-branched function: eleven paths, one per row kind. It is the one place where adding a rule means editing a second file, and a table from prefix to sentence would end that if a twelfth rule comes.

You start from the planner with diagnostics. Add scenarios: a named set of budget changes and overrides (projects forced in, forced out, or fixed to a start year) kept as data beside the export, never written into it. Each override becomes a named row, so a conflict can name it. Two plans are compared by the projects selected, deferred and shifted. Store each export once, as a snapshot under the hash of its content, refuse a stored snapshot whose content no longer matches its hash, and store each run with the snapshot it was planned from, in one SQLite file.

The canonical form of an export is its JSON with sorted keys and no spaces after , and :; the snapshot's hash is the sha256 hex digest of that text in UTF-8. Saving a scenario under a name that is already stored replaces it, and the runs of a scenario come back as Plans, oldest first.

Run's report gains a section: main.py now compares the demo plan with a scenario named more money that adds $1,000k to the budgets of 2028 and 2029. After the frontier section it prints an empty line, then scenario more money: NPV $<base npv>k -> $<scenario npv>k (whole $k, thousands commas), then selected <ids>; deferred <ids> with the ids joined by a comma and a space, or none, then one line shifted <id> <base start> -> <scenario start> per project that starts in another year.

cipt/trust.py holds the next lesson's stubs, as the reference has them; no code of this step imports it, so leave it as it is. Submit runs every test in tests/, the earlier steps' included, and compares Run's report with the expected one.

Blueprint

Write each method below. The tests check each one by itself and the whole program end to end, so you may change any other part of the code as you see fit.

apply in cipt/scenario.py

  • Contract. Returns the request with the scenario's budget changes laid over its budgets, its overrides (force_in, force_out, fix_start) set, and its name <request> / <scenario>. Refuses a scenario that names a project the export does not have.
  • Modeling idea. A scenario never edits the export: it is data beside it, applied to a copy.
  • Taught in 12.1.1 Scenarios as Data: Create, Copy, Optimize.

overrides in cipt/rules.py

  • Contract. Adds a row in_<id> (started once) per forced-in project, out_<id> (never started) per forced-out project, and fix_<id>_<year> (started in exactly that year) per fixed start.
  • Modeling idea. An override is a named row, so the diagnostics can name an override that clashes with a rule.
  • Taught in 6.5.6 Manual Overrides as Fixed Bounds.

describe in cipt/diagnose.py

  • Contract. Also describes in_<id>, out_<id> and fix_<id>_<year>: the scenario funds <id>, the scenario leaves <id> out, the scenario starts <id> in <year>.
  • Modeling idea. A new kind of row needs words the planners read.
  • Taught in 9.1.6 Turning an IIS Into a Planner Message.

diff in cipt/scenario.py

  • Contract. Returns the projects funded only in the other plan (selected), those funded only in the base plan (deferred), and those funded in both with different starts (shifted, as id, base start, other start).
  • Modeling idea. Planners compare plans by selected, deferred and shifted projects.
  • Taught in 9.3.3 Scenario Diffs: Selected, Deferred, Shifted.

canonical in cipt/store.py

  • Contract. Returns the export as JSON with sorted keys and no spaces, so equal exports give equal text.
  • Modeling idea. A hash identifies content only when the content is written one way.
  • Taught in 12.1.4 Storing Scenarios and Results in SQLite.

content_hash in cipt/store.py

  • Contract. Returns the sha256 hex digest of the canonical JSON.
  • Modeling idea. A snapshot is stored under the hash of its content.
  • Taught in 12.1.4 Storing Scenarios and Results in SQLite.

snapshot in cipt/store.py

  • Contract. Returns the stored export for a hash, and raises ValueError ('does not match') when the stored body no longer hashes to that value.
  • Modeling idea. Check the content against its hash on every read, so a changed byte is caught.
  • Taught in 12.1.4 Storing Scenarios and Results in SQLite.

run in cipt/store.py

  • Contract. Plans a stored scenario from its stored snapshot, stores the run (scenario, snapshot hash, status, NPV, risk, starts) and returns the plan.
  • Modeling idea. A run is traceable when it records the snapshot it planned from.
  • Taught in 12.1.4 Storing Scenarios and Results in SQLite.

Summary


  • Edited copies of the export lose track of what was planned, and make the diagnostics name the wrong rule.
  • A scenario is data beside the export, and an override is a named row, so a clashing override is named in planner language.
  • A snapshot is stored under the hash of its canonical JSON, and a changed byte is refused when it is read.
  • Scenarios run side by side against one snapshot; on GridCap small two different requests led to one plan.

Design Note: The Snapshot Is the Unit of Truth


The store keeps the export as received, not the Request the loader built from it. A loader bug fixed next year would change the Request, but not the snapshot, so an old run can be replayed against the same bytes with the new code, and the difference is the fix. Storing the Request instead would freeze the bug into every record.
