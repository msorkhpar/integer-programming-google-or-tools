  16. Overrides and explanations

With calendars in place (the lesson Weather and access windows: calendars and optional work), GridCap's vegetation planner started using the plan every week, and two requests followed:

Sometimes I know something the model doesn't. A crew is already on site near C17, so start it there in week 0. The county closes the road to C17 until October, so leave it. A landowner complained, so trim C02 first. I need to tell the planner these things and have it plan around them.

And when it can't, "INFEASIBLE" is not an answer. Last week I forced in five circuits after a storm and got an empty plan and that one word. Tell me which of my decisions clash, in my words, so I know what to give up.

The first request is overrides: a planner's decision that the plan must keep. The second is explanation: when no plan keeps every rule, a short list of the rules that cannot hold together. (GridCap and its seasons are fictional, generated by the project's seeded generator.) This lesson takes the project from steps/05 to steps/06.

The Planner Takes No Instructions, and Its Failure Says Nothing

steps/05 has one input, the season. A planner who wants C17 left out can only edit the season's data (delete the circuit, or set its window to nothing), which loses the record that it was a decision, by whom and why, and makes the next season's data wrong. And when a season is infeasible, make_plan returns Plan("INFEASIBLE"): a true statement that tells the planner nothing. CP-SAT proved that the rules cannot all hold, and the code threw that proof away.

An Override Is One More Rule, and Every Rule a Planner Can Change Sits Behind a Literal

Three override kinds cover the requests: pin (trim this circuit, optionally on this crew and from this week), skip (leave it for next season) and force (trim it this season, anyhow). Each is a rule of the same shape as a must: a few rows that hold when the override is in force.

For the explanation, the design options (lessons Validating inputs before the solve, Elastic constraints and feasibility relaxation and CP-SAT assumptions as a conflict finder compared them):

OptionWhat it givesWhy not, or why
Check the data before solving (lesson Validating inputs before the solve): sum the musts' costs, compare with the budgetinstant, and the message writes itselfonly for conflicts someone thought of in advance; two pins that overlap on one crew, or a pin outside a window, need the model
Elastic rows: add slack to every rule and minimize the slack (lesson Elastic constraints and feasibility relaxation)says how far each rule is from holdingchanges the objective and the model's meaning; the planner wants names, not amounts
One literal per changeable rule, solved as assumptions; CP-SAT names a set of them enough for the proof; a deletion filter makes it minimal (lessons Hints, assumptions and SufficientAssumptionsForInfeasibility and CP-SAT assumptions as a conflict finder)the rules that clash, by name, from the real modelchosen: it finds any conflict the model can prove, and needs no change to the model's meaning

An assumption is a literal the solver must take as true for this solve (lesson Hints, assumptions and SufficientAssumptionsForInfeasibility). Every rule a planner can change, each must, the budget and each override, is written as rows enforced by its own literal. A normal solve fixes all those literals to true, so the model means exactly what it meant before. When the season is infeasible, a second solve passes the literals as assumptions, and sufficient_assumptions_for_infeasibility returns those the proof used. That set is enough, but not always the smallest (lesson Hints, assumptions and SufficientAssumptionsForInfeasibility), so a deletion filter tries each name in turn: drop it, and if the rest still cannot hold, it stays dropped.

The hard facts stay hard: windows, crews' weeks off, one trim per crew at a time. They are physics, not decisions; an explanation that says "or let K1 work two circuits at once" is not one a planner can act on.

vegcrew/explain.py, new. Three small functions. holds asks whether a set of rules can all hold at once, with one worker, stopping at the first plan found, since only yes or no matters:

conflict(tm) asks CP-SAT for its set, filters it, and returns the rules that remain in the order they were made. It is the explanation, and the page leaves its code to the practice. Its contract is the method of An Override Is One More Rule, and Every Rule a Planner Can Change Sits Behind a Literal above, in four steps:

  • solve once with every rule literal of tm.rules as an assumption, after clearing any assumptions already on the model, with one worker (assumptions need a single worker); if the status is not INFEASIBLE, every rule can hold, and the answer is [];
  • read the solver's set with sufficient_assumptions_for_infeasibility();
  • run the deletion filter over that set: for each name in it, in turn, if the set without that name still cannot hold (holds answers False), leave the name out for good;
  • return the names that remain, sorted in the order the rules were made, which is the order of tm.rules.

The solver returns indices of literals (its docstring says "the indices of the infeasible assumptions"), not the literals, so map each literal's .index back to its rule name. The rules are made in a fixed order, each must in the inventory's order, then the budget, then the overrides in the order given, and the explanation lists its rules in that order, whatever order the solver named them in. The third function, why_infeasible, builds the model and maps the conflict's names to the planner's words:

vegcrew/planner.py. Shorter: it imports the model, and make_plan gains an overrides argument (a stub in steps/05), a data check before any model is built, the "every rule holds" row, and the explanation on failure:

check_overrides catches what is wrong with an override as data (an unknown circuit, crew or kind, a week outside the season) and returns every problem at once. These are typing mistakes, not conflicts, and the model is the wrong place to find them (lesson Validating inputs before the solve): a pin naming circuit Z9 would otherwise fail as a KeyError deep in build.

Problem statement

With calendars in place, GridCap's vegetation planner started using the plan every week, and wrote:

Sometimes I know something the model doesn't. A crew is already on site near C17, so start it there in week 0. The county closes the road to C17 until October, so leave it. A landowner complained, so trim C02 first. I need to tell the planner these things and have it plan around them. And when it can't, "INFEASIBLE" is not an answer. Last week I forced in five circuits after a storm and got an empty plan and that one word. Tell me which of my decisions clash, in my words, so I know what to give up.

You start from the calendar scheduler of the lesson before. Take the planner's overrides: pin a trim to a crew and a first week, skip a circuit, or force one in, each with a reason. Refuse an override that names nothing before any model is built. When a season has no plan, name a smallest set of the planner's rules that clash (the musts, the budget and the overrides, never the physics of crews and weeks) in the planner's words, and print them in the report. Split the model out of planner.py into model.py, and the explanation into explain.py.

The explanation. Name the rules in the order they are made: each must as its circuit comes in the season, then the budget, then the overrides in the order given. The tests compare the explanation with an exact tuple in that order.

The report. After the crew lines, a plan with an explanation prints these rules cannot all hold; change one of them: and one line per rule, two spaces, - and the rule's words. An INFEASIBLE plan has no trims: its status line reads status INFEASIBLE: 0 trims, cost $0k, risk carried $0k, and each crew's line shows only its weeks off.

main.py. After the tiny season's report it prints two more sections, each after an empty line. First the title skip C03: and the report of the tiny season with one override, Override("skip", "C03", reason="road closed"). Then the title pin C01 and C05 a week apart on K1: and the report with two, Override("pin", "C01", crew="K1", start=12, reason="crew is nearby") and Override("pin", "C05", crew="K1", start=13, reason="landowner asked"), which cannot both hold. Keep the line that sets planner.WORKERS = 1.

Run's report gains the two sections above, as expected/report.txt shows. Submit runs every test in tests/, the earlier steps' included, and compares Run's report with the expected one.

Blueprint

Write each method below. The tests check each one by itself and the whole program end to end, so you may change any other part of the code as you see fit.

build in vegcrew/model.py

  • Contract. The model of the lesson before, moved to model.py with crew_ids, horizon and start_domain, and built with the overrides. Every rule a planner can change sits behind a named literal, with its words: must_<cid> (<cid> is overdue and must be trimmed this season), budget (the season's budget is $<budget>k, the budget written with a thousands comma, as f"{budget:,}" writes it: $962k, $1,000k) and override_<i> (override <i>: followed by the override's own words, as Override.says gives them: trim <cid> on <crew> from week <start> (<reason>) for a pin, leave <cid> for next season (<reason>), trim <cid> this season (<reason>), with no reason given when the reason is empty). A skip leaves its circuit untrimmed; a pin or force trims it; a pin also fixes the crew and the first week it names. The rules are made in this order: each must as its circuit comes in the season's order, then the budget, then the overrides in the order given.
  • Modeling idea. A rule behind a literal holds only when its literal is true, so the search can be asked which literals cannot all be true.
  • Taught in 4.4.2 Native Logic: AddBoolOr, AddImplication, OnlyEnforceIf.

holds in vegcrew/explain.py

  • Contract. Answers whether the named rules can all hold at once: clears the model's assumptions, adds the named rules' literals as assumptions, and solves with num_workers = 1 and stop_after_first_solution = True; True unless the status is INFEASIBLE.
  • Modeling idea. Only yes or no matters, so the first plan found is enough.
  • Taught in 4.6.2 Hints, Assumptions and SufficientAssumptionsForInfeasibility.

conflict in vegcrew/explain.py

  • Contract. Returns a minimal list of rule names that cannot all hold, or [] when every rule can: the rules the solver names as sufficient for infeasibility (assumptions need one worker), then each dropped in turn and left out when the rest still cannot hold. The names come back in the order the rules were made, whatever order the solver named them in.
  • Modeling idea. Assumptions name a set of rules that is enough for the proof; a deletion filter makes it minimal.
  • Taught in 9.1.5 CP-SAT Assumptions as a Conflict Finder.

why_infeasible in vegcrew/explain.py

  • Contract. Builds the model of the season and its overrides and returns the words (TrimModel.says) of the rules in its conflict, in the conflict's order. The tests compare the explanation with an exact tuple in that order: musts, then the budget, then the overrides.
  • Modeling idea. A conflict is only useful in the words of the people who can change it.
  • Taught in 9.1.6 Turning an IIS Into a Planner Message.

check_overrides in vegcrew/planner.py

  • Contract. Returns what is wrong with the overrides as data, in order: override <i>: unknown kind <kind repr> unless the kind is pin, skip or force; override <i>: no circuit <cid>; override <i>: no crew <crew>; override <i>: week <start> is outside the season. Empty when nothing is.
  • Modeling idea. An override that names nothing is refused before any model is built.
  • Taught in 12.1.2 Manual Overrides as Bounds, With an Audit Trail.

make_plan in vegcrew/planner.py

  • Contract. Raises ValueError with the problems joined by ; when check_overrides finds any; otherwise solves with every rule's literal true, and when the season is INFEASIBLE returns a Plan whose explanation is why_infeasible's words.
  • Modeling idea. A failed plan says which of the planner's rules clash, not just that it failed.
  • Taught in 14.1.6 Planner Overrides and Why a Plan Failed.

format_plan in vegcrew/report.py

  • Contract. After the crews, when the plan has an explanation, the line these rules cannot all hold; change one of them: and one line - <words> per rule, in the explanation's order. An INFEASIBLE plan has no trims, so its status line reads 0 trims, cost $0k, risk carried $0k and each crew's line shows only its weeks off, ending in two spaces.
  • Modeling idea. The explanation is part of the answer, so the report prints it.
  • Taught in 9.1.6 Turning an IIS Into a Planner Message.

Summary


  • The planner took no instructions, and its failure said nothing. Overrides had to be data edits, and INFEASIBLE threw CP-SAT's proof away.
  • An override is one more rule, and every rule a planner can change sits behind a literal. The planning solve fixes the literals to true; the explaining solve passes them as assumptions.
  • Overrides have a price ($626k on the small season for two of them), and a clash names its rules, minimal by a deletion filter, in the planner's words with their reasons.
  • Six tests, including one that checks an innocent rule is left out of the explanation.

Design Note: Keep Physics Hard and Decisions Soft


Only rules a planner can change got literals: musts, the budget, overrides. Windows, time off and "one trim per crew at a time" did not. An explanation is useful only if every rule it names is one the reader can act on; "or let K1 work two circuits at once" is not. The line also keeps the explaining solve small: eight literals to filter, not one per row. If an explanation ever needs to name a window ("C01's ground is too wet in week 2"), give windows a literal then, and decide on purpose that a window is negotiable.
