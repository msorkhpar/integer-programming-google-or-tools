This module grows one project, GridCap's vegetation crew planner, from a first small request into a CP-SAT crew scheduler, one requirement per lesson. Each lesson starts from the code the last one left and ends with the code the next one starts from. The project is kept as complete snapshots, each a directory you can run on its own:

SnapshotWhat it is
steps/00the project before this lesson: a skeleton that loads a season and plans nothing
steps/01the project after this lesson
steps/NNthe project after the module's NN-th lesson, up to steps/08

Every snapshot holds the package vegcrew, its tests and a pytest.ini, so python -m pytest and python -m vegcrew run inside it. A lesson shows each file it changes, before and after, the formulation before and after, the tests it adds and how they fail on the old code, and what the step did to the code's size and style. Its practice starts you from the snapshot before the lesson and is graded by the tests of the snapshot after it.

GridCap is a fictional utility. The project generates its own seasons from a seed (vegcrew/generate.py); none of the circuits, costs or risks is a real utility's data.

The first request comes from GridCap's vegetation program manager:

We have $962k for tree trimming this year and twenty distribution circuits that are due. Tell me which ones to trim so that we take out the most tree risk. I don't need dates yet, just the list.

Trimming here means clearing the trees along a circuit's overhead lines, a whole circuit at a time. Each circuit has a cost, in $k, and a risk: the dollars a year of tree-caused outages and damage that a trim removes (an estimate of the kind lesson Risk reduction from an intervention, year by year computes). The manager asks for the set of circuits, within the money, whose risks add up to the most.

A Budget and Yes-or-No Choices Make a 0-1 Knapsack

Read the request as a model (lesson Decisions, objectives and constraints: turning a planner's question into a model): the decision is, for each circuit, trim it or not; the objective is the total risk removed, as large as possible; the one constraint is the money. That is the 0-1 knapsack of lesson 0-1 and multi-dimensional knapsack: items with a weight (cost) and a value (risk), one capacity row, each item taken whole or not at all.

There are three ways to answer it, and the choice is the lesson's design decision:

OptionWhat it givesWhy not, or why
Rank by risk per $k and fund down the lista spreadsheet answer anyone can checknot always the best set: a high-ratio circuit can block two that together remove more
Dynamic programming over budget amounts (lesson 0-1 and multi-dimensional knapsack)the exact best set, fast for one rowone more resource (crews, next lesson) needs one more table axis, and the table grows with every row
A MILP: one binary per circuit, solved by HiGHS through MathOpt (lesson Model, variables, constraints, objective)the exact best set, provenchosen: every later requirement is one more row or variable, not a new algorithm

The MILP wins on the next lessons, not on this one. A ranking might be good enough for a single budget row, but the manager's list of rules will grow, and a model can take rules one row at a time.

Variables. $x_c \in \{0, 1\}$ for every $c \in C$: 1 if circuit $c$ is trimmed this year.

The Change, File by File

Only vegcrew/planner.py changes for the requirement. (steps/01 also carries two one-line stubs for the lesson Crews and months: capacity over time, a constant in data.py and a field of Trim, so that the next practice's tests import cleanly; they do nothing yet.)

Imports and constants, added. MathOpt, the exact-gap setting, and a map from MathOpt's termination reasons to the plan's status words:

EXACT asks HiGHS not to stop until it has proved the plan optimal, with no relative gap (the gap is defined in lesson Best bound, incumbent, absolute and relative gap). MathOpt's SolveParameters docstring says a solver may stop, and report OPTIMAL, once the relative gap is at most its tolerance; with a tolerance above zero, a test that compares the plan with a brute-force answer could fail on a plan that is merely near the best.

build(season), added. This is the model, and the page leaves its code to the practice. It takes a Season and returns the MathOpt model with its variables, written the way The Model above reads:

  • one binary $x_c$ per circuit, named x_<cid> and keyed in the returned dictionary by the circuit id (x_C07 under "C07");
  • the row (budget), named budget: the summed $\text{cost}_c \, x_c$ of all circuits at most the season's budget;
  • the objective: maximize the summed $\text{risk}_c \, x_c$.

Lesson Model, variables, constraints, objective has every call it needs: mathopt.Model(name=...), add_binary_variable(name=...), add_linear_constraint(expression <= bound, name=...) and maximize. The snapshot names the model trim_<season name>.

Building and solving are separate functions on purpose. A test or a lesson program can build the model and look at it (its variables, its rows) without solving it, and the next lessons change the model in build while make_plan stays a reader of results.

make_plan(season), before and after. Before, it returned Plan("NOT_SOLVED"). After, it solves and turns the solver's answer into the plan's terms:

Three choices in it are worth naming. A status other than OPTIMAL or FEASIBLE returns an empty plan with that status, never an exception: "no plan" is an answer the caller must handle (lesson Infeasible, unbounded, or the solver can't tell). A circuit is chosen when its value is above 0.5, not equal to 1, because a MILP solver returns values within a tolerance of whole numbers (lesson Start-time variables x(i,t) and timing windows). And the totals are recomputed from the data, not read from the objective value, so they are exact integers in $k.

The Plan Beats the Ranking by $8k a Year

first_plan.py runs steps/01 on the small season, then funds the same circuits the spreadsheet way, by risk per $k down the list:

The two answers differ by one circuit. The ranking takes C02 and stops with $26k unspent; the model swaps C02 for C05, which costs $16k more, removes $8k a year more, and still fits. OPTIMAL says no set of circuits within $962k removes more than $2,114k a year. On twenty circuits the gap is small; the point is that the ranking has no way to know whether it is small.

Four Tests Pin the Requirement Down

A requirement is not done until a test says so. steps/01 adds tests/test_planner.py, with four tests, each for one thing the manager would check. The first is built by hand so that the right answer is obvious and the ranking gets it wrong:

The other three check that the plan never spends more than the budget on the small season; that it removes as much risk as the best of all $2^6 = 64$ subsets of the tiny season, found by brute force (lesson Decisions, objectives and constraints: turning a planner's question into a model's method); and that a zero budget is an answer, OPTIMAL with no trims, not an error. The brute-force test is the strongest of the four: it checks the optimum against an answer computed without any solver.

step01.py runs the new tests against the code before the lesson and after it. Before, every one of them fails on an assertion, which is what a practice starting from steps/00 needs: the tests run, and they say what is missing.

The Step Added One Function and Kept Every Other File

Seventeen lines of planner, one new function, and the tests grew by more than the code did (30 lines against 18). That ratio is normal for a model: the model is short, and the tests are where you say what "right" means. data.py's one extra line is the stub for the lesson Crews and months: capacity over time. Problem statement

GridCap's vegetation program manager sent the first request:

We have $962k for tree trimming this year and twenty distribution circuits that are due. Tell me which ones to trim so that we take out the most tree risk. I don't need dates yet, just the list.

You start from the skeleton: it generates a season, reads it into a Season and prints a report, but make_plan trims nothing. Make the planner decide. Each circuit is trimmed or not, the trimmed circuits together cost no more than the season's budget, and the plan removes the most risk a year. Build the model with MathOpt, solve it with HiGHS with no gap left between the plan and its bound, and read the answer back as a Plan with one Trim per trimmed circuit, the total cost and the total risk removed. A budget too small for any circuit is still an answer: an optimal plan with no trims.

The report is already written: vegcrew/report.py prints the season line, the status line and one line per trimmed circuit, and this step does not change it.

Run executes main.py, which plans the tiny season (six circuits of GridCap, a fictional utility, drawn by vegcrew/generate.py from seed 54) and prints the report; expected/report.txt is the report it should print. Submit runs every test in tests/, the skeleton's own included, and compares Run's report with the expected one.

Blueprint

Write each method below. The tests check each one by itself and the whole program end to end, so you may change any other part of the code as you see fit.

build in vegcrew/planner.py

  • Contract. Takes a Season. Returns a MathOpt model and its variables: one binary variable per circuit (named x_<cid>, keyed by the circuit id), one row named budget that keeps the summed cost of the trimmed circuits within the season's budget, and the summed yearly risk of the trimmed circuits as the objective to maximize.
  • Modeling idea. A yes-or-no choice per circuit under one budget is a 0-1 knapsack: the best list is a combination, which no ranking by risk per dollar finds in general.
  • Taught in 6.3.1 0-1 and Multi-Dimensional Knapsack.

make_plan in vegcrew/planner.py

  • Contract. Builds the model, solves it with HiGHS through MathOpt with a relative gap of zero, and returns a Plan: the status (OPTIMAL, FEASIBLE, INFEASIBLE, or the name of any other termination reason), one Trim per circuit whose variable is above 0.5, and their summed cost and risk removed. With no feasible solution, a Plan with the status alone. A budget too small for any circuit is an OPTIMAL plan with no trims.
  • Modeling idea. Read the termination first, then the variable values; a binary is 1 when its value is above 0.5.
  • Taught in 4.2.1 Model, Variables, Constraints, Objective.

Summary


  • The starting code loads a season and plans nothing. The plan's shape (Plan, Trim) is fixed before the model, so the model can change behind it.
  • A budget and yes-or-no choices make a 0-1 knapsack. A MILP was chosen over a ranking and over dynamic programming because later requirements add rows, not algorithms.
  • The plan beats the ranking. On the small season the model removes $2,114k a year against the ranking's $2,106k, and proves no set does better.
  • Four tests pin the requirement down, and each fails on an assertion against steps/00.

Design Note: Fix the Answer's Shape Before the Model


The skeleton fixed Plan before there was a model. Every later lesson changes the model: a month index, then CP-SAT intervals, then a new objective. The report, the tests and, in the lesson From script to service, and what the code became, an HTTP API read plans only through Plan and Trim, so most of those changes stay inside one file. When a field must be added (a crew, a start week), it is added to the plan, and everything that does not need it keeps working. A model's variables are an implementation detail; a plan is the contract.
