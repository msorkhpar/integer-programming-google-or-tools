The planner is trusted now: it keeps the calendars, takes overrides, explains a failure and gives the same plan every run (the lessons Weather and access windows: calendars and optional work to The same plan every run: determinism and regression tests). The last request comes from the team that builds GridCap's work-management system:

We don't want to run a Python script on someone's laptop. Give us an endpoint: we POST a season (the same JSON our inventory exports) and the planner's overrides, and get back the plan's record. Keep every plan you return, so we can fetch it again by its id months later, after the laptop is gone. Bad input should be refused with a reason, before anything runs.

(GridCap and its seasons are fictional, generated by the project's seeded generator.) This lesson takes the project from steps/07 to steps/08, and then looks back over all eight steps.

The Script Has No Door, and Forgets Every Plan

steps/07 is used from a shell: python -m vegcrew small --record plans a generated season and prints a record to standard output. There is no way to hand it a season from another system, no way to pass overrides except from Python, and no memory: a plan exists only as long as someone keeps the terminal's output. The record of the lesson The same plan every run: determinism and regression tests is exactly the answer the work-management team wants; what is missing is a way in and a place to keep it.

A Thin HTTP Layer Validates at the Edge and Calls the Library

The design decisions, each with its alternative:

DecisionChosenAlternative, and why not
How a caller reaches the plannera FastAPI app with POST /plans and GET /plans/{id} (the lesson A REST API with FastAPI in section 12)a command-line tool fed by files: no fit for another system calling it, and still no memory
How long a request may takethe solve runs inside the request, in a plain def endpoint, which FastAPI runs on a worker thread (the lesson A REST API with FastAPI in section 12)submit, poll, fetch with a job store (the lesson Long solves: submit, poll, fetch in section 12): needed when solves outlast a request; here the deterministic limit of the lesson The same plan every run: determinism and regression tests bounds the work, so not yet
Where input is checkedpydantic models on the request, then check_overrides (the lesson Planner overrides and why a plan failed)inside the model: a bad season would fail deep in build with a KeyError
Where plans are keptone SQLite table, one row per plan, the record as its canonical text (the lesson Storing scenarios and results in SQLite in section 12)files on disk: no ids and no safe concurrent writes; a database server: more than one table needs
What a failed season returns200 with status INFEASIBLE and the explanation (the lesson A REST API with FastAPI in section 12)an HTTP error: but "no plan keeps these rules" is an answer, not a fault

The service adds nothing to the planner's logic: every endpoint is a few lines that check input, call make_plan and plan_record, and store or fetch. That keeps everything the earlier lessons tested in the library, where the tests already are.

The model does not change in this lesson; its formulation is the lesson Planner overrides and why a plan failed's.

The first endpoint, post_plan, is where the service meets the planner, and the page leaves its body to the practice. It is @app.post("/plans") on a plain def post_plan(request: PlanRequest) -> dict, and it does four things in order, with no planning logic of its own:

  • take the validated season as a plain dictionary with request.season.model_dump(), and read it into a Season with the loader, season_from_dict;
  • turn each validated override into the library's Override, its fields passed as keywords;
  • run check_overrides, and if it finds problems, raise FastAPI's HTTPException with status code 422 and the list of problems as its detail, before any model is built;
  • otherwise plan with make_plan, make the record with plan_record, from the dumped season (not the Season), the plan and the overrides, save it in the store, and return {"id": <the id save returns>, "record": <the record>}. An infeasible season takes this path too.

The second endpoint reads a plan back:

Three details. The record's fingerprint is taken from model_dump(), the validated season with its defaults filled in, so two requests that mean the same season get the same fingerprint even if one left out an empty windows. A factory, create_app(db), instead of a module-level app, lets each test have its own database and lets a test open a second app on the same file. And the endpoint is def: a CP-SAT solve blocks, and an async def endpoint would block the server's event loop for every caller (the lesson A REST API with FastAPI in section 12).

The Service Answers, Refuses and Remembers

service_demo.py calls the app in-process through FastAPI's test client. The runner has no network, so no server is started; the test client sends real HTTP requests to the app object.

The first request skips C05 on the tiny season ("flooded"); the plan works around it. The second app, opened on the same SQLite file, returns the stored plan unchanged: the plan outlives the process that made it. Then the three kinds of refusal and failure, each where it belongs: pydantic's 422 for a malformed season, check_overrides' 422 for an override naming a crew that does not exist, and a 200 with an explanation for a season whose rules clash.

Six Tests Through the HTTP Layer

steps/08 adds tests/test_api.py, every test a request through the test client. The first checks that the service and the library agree, the property that keeps the service thin:

It compares trims and risk, not the whole record: the fingerprints differ on purpose (the service hashes the validated season, the library call the raw one). The others: a stored plan comes back by its id and an unknown id is a 404 with its message; a negative budget is a 422 naming the field; an override naming no circuit is a 422 listing the problem; an all-must season is a 200 with an explanation; and a plan survives a new app on the same SQLite file (pytest's tmp_path gives the file). Importing the test client prints a deprecation notice from Starlette 1.10 about httpx, so the test module imports it inside warnings.catch_warnings().

The stub app has no routes, so every request is FastAPI's own 404, and every test fails on its first status check. Each test checks the status code before it reads the body, so a missing route fails as an assertion and not as a KeyError.

Seventy-six lines, in two new files, and no line of the planner changed. That is the payoff of every earlier boundary: Plan from the lesson The first request: which circuits to trim this year, the record from the lesson The same plan every run: determinism and regression tests, check_overrides from the lesson Planner overrides and why a plan failed. The service is a translation between HTTP and those, and nothing more.

What the Code Became: Eight Requirements, Five Times the Code, One Model File

growth.py counts every snapshot:

Read it by rows and by columns.

  • The model is small. The rules live in one function, build, which reached 42 lines by the lesson Planner overrides and why a plan failed and stayed there: determinism and the service did not touch it. The planner file was rewritten once (the lesson A trim takes weeks on one crew: from MILP to CP-SAT intervals, MILP to CP-SAT) and shrank that time; it was split once (the lesson Planner overrides and why a plan failed) when it had four jobs.
  • The data grew as much as the model. data.py and generate.py went from 48 to 108 lines; a rule usually costs a line in the model and several in getting its data in with the right defaults (the lesson Weather and access windows: calendars and optional work).
  • Steps 06 to 08 added files, not length. explain.py, record.py, api.py and store.py each have one reason to change. The longest function is 42 lines, and the functions grew from 7 to 29.
  • The tests grew with the code from the first step, and ended at 289 lines and 40 tests against 446 lines of package, about two lines of test for every three of code. Their kinds widened step by step: hand-made seasons with their arithmetic in comments (every step), a brute force (step 1, rewritten in step 4), the rule written twice (step 4), exact explanation wording (step 6), golden records and fresh processes (step 7), HTTP (step 8).

And by what changed hands. Two requirements changed the model's kind: crews and weeks (a packing problem became a scheduling problem, and the solver changed) and growing risk (the objective began to depend on order, and the proof stopped finishing on the small season). Those two drove everything after: the time limit made runs differ (the lesson The same plan every run: determinism and regression tests), and the harder proof moved tests to seasons small enough to prove. Every other requirement was "one more rule" or "one more layer", and cost a few lines where it belonged.

Problem statement

The planner is trusted now, and the vegetation program asked for one more thing:

We don't want to run a Python script on someone's laptop. Give us an endpoint: we POST a season (the same JSON our inventory exports) and the planner's overrides, and get back the plan's record. Keep every plan you return, so we can fetch it again by its id months later, after the laptop is gone. Bad input should be refused with a reason, before anything runs.

You start from the planner with records. Put an HTTP service in front of the library: a POST of a season and its overrides answers with the plan's record and an id, and a GET of that id answers the same body later, from a new service on the same SQLite file too. Refuse a season that breaks the schema, or an override that names nothing, with 422 and the reason, before any model is built. A season with no plan is an answer, with its explanation. An unknown id is 404.

create_app in vegcrew/api.py

  • Contract. Returns a FastAPI app whose plans are kept in a Store on the SQLite file db. store.py is new: Store(path) opens one connection (check_same_thread=False, shared under a threading.Lock) and creates the table plans (id INTEGER PRIMARY KEY, input_sha256 TEXT, record TEXT), the record stored as dumps writes it; save(record) -> int inserts a row and returns its id; get(plan_id) -> dict | None returns the stored record parsed back with json.loads, or None for an id with no row. The request is checked by pydantic models in api.py: Span = tuple[int, int]; CircuitIn with id and region (str), miles (int, > 0), cost and risk (int, >= 0), weeks (int, >= 1), growth (float, >= 0), windows (list[Span], default []) and must (bool, default False); SeasonIn with name (default 'season'), budget (int, >= 0), crews (int, 1 to 50), months (int, 1 to 12), crew_off (dict[str, list[Span]], default {}) and circuits (list[CircuitIn], at least one); OverrideIn with kind (pin, skip or force), cid, crew (default None), start (default None) and reason (default ''); PlanRequest with season (SeasonIn) and overrides (list[OverrideIn], default []). POST /plans takes a PlanRequest; it answers 422 with the list of problems when check_overrides finds any, else plans the season (from the validated season's model_dump()) and answers {'id', 'record'}, an infeasible season included. GET /plans/<id> answers the same body, or 404 with no plan <id>.
  • Modeling idea. Validate at the edge, keep the service a thin layer over the library, and store every answer so it outlives the process.

Summary


  • The script had no door and forgot every plan. A service needs a way in, input checking at the edge, and storage.
  • A thin HTTP layer validates at the edge and calls the library. Pydantic models, check_overrides, make_plan, plan_record, and a one-table SQLite store, in 76 new lines; the planner did not change.
  • The service answers, refuses and remembers: 200 with a record, 422 with a reason, 200 with an explanation, and a plan fetched by id from a new process.
  • What the code became: 98 lines to 446, 3 tests to 40; one 42-line model function; two requirements that changed the model's kind, and six that each added a rule or a layer.

Design Note: The Service Is the Last Layer, Not the First


Built in the order of these lessons, the HTTP layer came last and cost 76 lines, because everything it needed already had a boundary: a plan type, a record, a data check, an explanation. Had the project started as a service, each requirement would have been threaded through request handling, and the tests would have needed a client to check a constraint. Grow the model and its tests as a library, give its answers a stable shape, and the service is a thin translation that can be replaced (by a job queue, or by another framework) without touching a rule.
